# Промпт генерации плана миграции сервиса к эталону

Универсальный промпт для команд сервисов Экосистемы (ДБО юрлиц).
**Версия 2.2 (2026-08-27) — В ОБКАТКЕ (песочница ext-sandbox), командам
пока выдаётся v1.1** (базовый файл без суффикса версии). Существенное
расширение против v1.x, отсюда мажорная версия.

Изменения 2.2 (по пилоту исполнения ступени 7: PRE-00…ISS-01 на
Корпоративных Картах, журнал SANDBOX.md): правила исполнителя ВЫНЕСЕНЫ
из плана в нормативный протокол канона `_meta/tools/step-protocol.md` —
план и промпты на него ссылаются, а не пересказывают (измерено: в
самодостаточных промптах ~55% объёма — дрейфующий пересказ протокола,
~15% — пересказ скиллов); карточка этапа обязана быть самодостаточной
для сборки промпта захода подстановкой в шаблон §10 протокола; план
включает раздел «Промпты заходов» — готовые промпты этапов файлами
`prompts/<ЭТАП>.md` в src-репозитории (передача в сессию — файлом, не
копипастом; инцидент: в сессию ушёл промпт чужого этапа); хэш канона
в промпты НЕ вписывается — свежесть сверяет сторож среза канона:
строка «срез канона: <hash>» в профиле источников против фактического
HEAD, автоматически при каждом прогоне selfcheck (дважды за пилот хэш
из промпта устаревал между генерацией и запуском); предусловия этапов — «принято приёмкой владельца», НЕ требования к
формату строк отчётов прошлых этапов (формат эволюционирует с
прибором).

Изменения 2.1 (по обкатке плана Корпоративных Карт на подсервисном
каноне, журнал SANDBOX.md песочницы): материализация утверждённой
разметки в ПРОФИЛЬ источников (источник истины для сторожа — профиль,
не план); фактическая дата среза выгрузки без псевдоточности; судьба
копий/тестов/черновиков — точечные page_id-списки «вне SRS» с
причинами, расхождение копии с актуальной — OQ; перечитка канона при
его правке посреди Q&A; локальные обозначения плана — только с
расшифровкой и запретом переноса в артефакты; отклонение от
утверждённой разметки — только с основанием фактами; однофайловые
слоты уровня куска — по conventions §3.1.

Изменения 2.0 (по A/B-эксперименту на срезе «Корпоративные Карты», ~630
файлов, песочница ext-sandbox, журнал SANDBOX.md): постраничная опись
строится МЕХАНИЧЕСКИ инструментом `source_inventory.py` — в контрольном
прогоне v1 опись «чтением всего» на 457 страницах выродилась в агрегаты
по веткам (суммы сходились, но 90% страниц потеряли пофайловую
идентификацию молча) при ×4 времени; классификация — по сигналам с
точечным чтением; полнота плана — инструментальным гейтом, строка
которого обязана попасть в сдачу; для крупных сервисов (≳200 страниц) —
декомпозиция по подсервисам.

## Как пользоваться (инструкция команде сервиса)

0. Подготовьте и проверьте окружение:
   - git настроен (`user.name`, `user.email`) — авторство коммитов миграции должно
     быть персональным; акцепт этапов при этом фиксируется НЕ локальными данными git,
     а approve и слиянием MR в основную ветку (статус вычисляется из git);
   - Python 3 доступен в PATH — инструмент проверки `_meta/tools/selfcheck.py` из
     репозитория канона работает на стандартной библиотеке.
1. Подготовьте репозиторий сервиса (src-<сервис>) с каталогом `confluence/` — полной выгрузкой
   ПРОМ-среза требований сервиса утилитой confluence-tree-exporter.
   Выгрузка должна быть БЕЗ CriticMarkup-разметки; если разметка есть — сначала доведите
   аналитику до чистового вида, это ваша зона ответственности.
2. Склонируйте репозиторий канона `https://gitlab.gboteam.ru/EAN/docs-o2new.git`
   (единый для всех команд) — канон лежит в его каталоге `_meta/`: шаблоны
   `_meta/templates/`, скиллы `_meta/skills/`, инструменты `_meta/tools/`.
3. Склонируйте репозиторий эталона
   `https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git` (единый для всех
   команд) — эталонный комплект лежит в корне репозитория (`brd/`, `srs/`,
   `glossary.md`, `traceability-matrix.md` и т. д.).
4. Склонируйте репозиторий стандартов `https://gitlab.gboteam.ru/ED/eco-techbook.git` —
   в нём конвенция `standards/analytics/conventions.md` и нотация
   `standards/analytics/notation.md`; держите их под рукой: на них опираются шаблоны
   и инструмент проверки. Репозиторий большой (~сотни МБ), из него нужны два каталога —
   клонируйте частично (нужен git ≥ 2.26; обычный полный клон тоже допустим):

   ```powershell
   git clone --filter=blob:none --sparse https://gitlab.gboteam.ru/ED/eco-techbook.git
   cd eco-techbook
   git sparse-checkout set standards/analytics cookbook/analytics
   ```

   (`cookbook/analytics` — git-процесс docs-репозиториев: MR, ревью; на него
   ссылаются стандарты.) `git pull` в таком клоне работает как обычно.
5. Склонируйте репозиторий спецификаций/контрактов внешних АС `https://gitlab.gboteam.ru/EAN/docs-external-contracts.git` (единый для всех команд).
6. Если в шагах 2–5 вы НЕ клонировали заново, а переиспользуете уже существующие
   клоны — непосредственно перед стартом промпта обновите каждый (`git pull`) и
   убедитесь, что он на своей основной ветке (`git branch --show-current`;
   у docs-external-contracts основная — `trunk`). Свежему клону это не нужно.
   Отставший или переключённый клон — типовая причина ложных находок и вопросов
   планировщика.
7. Проверьте готовность окружения одной командой (PowerShell, подставьте пути к клонам
   из шагов 2–3, для других оболочек - адаптируйте при необходимости):

   ```powershell
   python <клон-docs-o2new>\_meta\tools\selfcheck.py --docs <клон-docs-account-opening-request>
   ```

   вывод завершился строкой «ИТОГО: …» — окружение готово; вердикт самого прогона
   для этой проверки не важен.
8. Откройте Cursor или любое иное IDE, позволяющее вносить правки в локальные файлы и выберите **сильную модель с большим контекстным окном** (генерация
   плана — разовая задача, экономить на модели - настоятельно НЕ рекомендуется).
9. Заполните блок «Входные данные»: замене подлежат только значения в угловых скобках
   `<…>` ВНУТРИ этого блока — пути к репозиторию сервиса и локальным клонам, название
   сервиса и service-id, метка среза `version`, дата дедлайна, роль/имя акцептующего. Остальной текст промпта
   не меняйте: `<канон>` и `<эталон>` ниже по тексту — обозначения, определяемые в блоке
   «Входные данные» через введённые вами пути, их заполнять не нужно. Отправьте промпт
   целиком.
10. Модель сначала проведёт инвентаризацию и задаст вопросы — ответьте на них; только
   после этого она сгенерирует план. Не принимайте план с незакрытыми вопросами.

## Промпт (отправляется LLM целиком, с заполненными входными данными)

Ты — аналитик-архитектор миграции документации cо спецификацией требований сервиса 
из одного формата в другой. Твоя задача — построить **план миграции** требований сервиса 
из Confluence-выгрузки в формат Doc-as-Code, максимально близкий к эталонному сервису. 
Ты НЕ выполняешь миграцию — только исследуешь входные данные, задаёшь вопросы и пишешь план, 
по которому команда сервиса с помощью LLM выполнит перенос в критически короткий срок.

### Входные данные

- Репозиторий сервиса: `<путь>` — каталог `confluence/` с выгрузкой требований
  (markdown + сырой HTML таблиц, утилита confluence-tree-exporter).
- Каталог выходных данных: `<путь, например: <репозиторий сервиса>/docs>` — далее
  обозначается `<выход>`: корень создаваемого комплекта. Внутренняя структура НЕ
  задаётся здесь — она строится зеркально эталону (`<выход>/brd/`, `<выход>/srs/`,
  `<выход>/glossary.md`, `<выход>/traceability-matrix.md` и т. д.); именно `<выход>`
  передаётся гейту как `--docs` при приёмке этапов. Внимание: `<выход>` — корень
  комплекта, НЕ каталог `srs/`: в `srs/` лежит только SRS-слой, а BRD, глоссарий и
  матрица трассировки живут в корне — гейт, натравленный на `srs/`, их не увидит.
  Значение из этого блока — единственный источник: целевые пути, упомянутые в
  README src-репозитория (`output/…` и т. п.), — историческое наследие, ими не
  руководствоваться и вопросов по ним не задавать.
- Репозиторий канона (`https://gitlab.gboteam.ru/EAN/docs-o2new.git`): `<путь к каталогу
  _meta локального клона>` — далее обозначается `<канон>`: шаблоны `<канон>/templates/`,
  скиллы `<канон>/skills/`, инструменты `<канон>/tools/`.
- Эталонный репозиторий (`https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git`):
  `<путь к локальному клону>` — далее обозначается `<эталон>`: эталонный комплект — сам
  корень `<эталон>` (`brd/`, `srs/`, `glossary.md`, `traceability-matrix.md`).
- Репозиторий стандартов (`https://gitlab.gboteam.ru/ED/eco-techbook.git`): `<путь к клону стандартов>` —
  конвенция `standards/analytics/conventions.md`, нотация `standards/analytics/notation.md`.
- Репозиторий контрактов внешних сервисов (`https://gitlab.gboteam.ru/EAN/docs-external-contracts.git`): `<путь к контрактам внешних систем>` 
  (спецификации вызовов систем, внешних по отношению к Экосистеме).
- Сервис: `<название, например: Хранение файлов>`, service-id: `<kebab-case-код сервиса, например: file-storage>`.
  Источник истины для service-id — справочник сервисов `<канон>/services.json`: сервис
  заносится туда ДО старта промпта; введённый service-id сверь со справочником — нет
  в справочнике → остановись и запроси занесение (id не выдумывается и не выбирается
  из вариантов написания в источниках).
- Метка среза `version` для frontmatter всех документов комплекта:
  `<строка, например: prod-2026-08>` — задаёт команда; без неё гейт и матрица
  неоднозначны.
- Дедлайн миграции: `<дата, например: 2026-09-01>`. Кто акцептует план и приёмки этапов:
  `<роль и имя, например: лид аналитики сервиса — И. Соколов (@i.sokolov)>`.

### Рамка: что здесь главное

1. **Эталон — образец, гейт — судья.** Структуру, типы артефактов, frontmatter, стиль
   бери из эталонного комплекта и шаблонов `<канон>/templates/`. Соответствие
   подтверждается ТОЛЬКО прогоном инструмента проверки `<канон>/tools/selfcheck.py` —
   это единый язык всех команд. Любой этап плана считается закрытым только с прогоном
   гейта и его вердиктом в сдаче.
2. **Способ достижения — любой.** Скиллы `<канон>/skills/` и инструменты `<канон>/tools/` —
   строительные блоки и доноры: их можно использовать как есть, адаптировать под
   специфику сервиса или не использовать вовсе и преобразовывать исходники напрямую сильной моделью («в лоб»).
   Универсальность переработок не требуется — требуется результат, проходящий гейт.
   Правило окупаемости: повторяющаяся работа → инструмент/скилл; разовая → руками LLM.
3. **Асимметрия ошибок.** Молчаливая потеря требования хуже любого шума. Перенос —
   дословный, целиком, без пересказа; сокращения («и т. д.», «фрагмент», «см. выше»)
   запрещены; справочники и перечни переносятся полностью. Если фрагмент некуда
   положить — он кладётся как есть с открытым вопросом, но НЕ выбрасывается.
4. **Документ — карта пробелов.** Дыры аналитики не прячутся: отсутствующая цель ссылки
   — долг в матрице; неоднозначность — вопрос в реестре открытых вопросов (OQ);
   выдумывать содержимое, сигнатуры, идентификаторы запрещено.
5. **Минимальная гигиена — часть канона, не опция:** YAML-frontmatter каждого файла,
   матрица трассировки, реестр OQ (append-only), долги ссылок.
6. **Охват миграции.** Мигрирует SRS-слой из выгрузки. Типы, которых нет в
   выгрузке, — норма, а не дыра: их отсутствие фиксируется строкой в плане, карточки
   не выдумываются. BRD-слой, `glossary.md`, `service-vision.md` при отсутствии
   страниц-источников строятся ПОЗЖЕ отдельными заходами reverse-from-SRS (скиллы
   `create-brd`, `create-glossary`, `create-service-vision`) — в план миграции не
   входят. `docs/api/` (YAML из кода) — вне миграции. Вызовы внешних АС — оба
   контура обязательны: базовый контракт в docs-external-contracts + карточка вызова
   в комплекте (доступ к репозиторию контрактов у команд есть).
7. `confluence_page_id` во frontmatter и матрице — рабочая трассировка. Этот план
   создаёт baseline требований по ПРОМ-срезу; требования Confluence продолжают выводиться в ПРОМ, и изменения
   из него будут довозиться в созданную структуру позже, отдельными проработками —
   `page_id` и есть нить этой довозки. Поэтому: `page_id` проставляются штатно и
   **НЕ удаляются** — ни этапом этого плана, ни по своей инициативе; их зачистка
   произойдёт в рамках отдельного проекта по решению лида аналитики.

### Словарь

- **Заход** — одна порция работы LLM-исполнителя с проверяемым результатом.
- **Сдача** — отчёт исполнителя по заходу: что сделано, откуда взяты факты, полный
  вывод гейта и честный вердикт (включая «не готово»).
- **Приёмка** — проверка сдачи человеком с решением «принять / дозаход».
- **Дозаход** — прогон-актуализация по списку замечаний ревью. Скоуп дозахода задаёт не раздел выгрузки, а отчёт самопроверки.
- **Долг** — зафиксированная в матрице трассировки недостающая цель ссылки.
- **Baseline** — сохранённый отчёт гейта, против которого меряется дельта следующей
  сдачи.

### Шаг 1. Предпроверки (до любого планирования)

- Убедись, что `confluence/` читается; **опись страниц НЕ составляется
  вручную** — сгенерируй механический скелет инструментом:

  ```
  python <канон>/tools/source_inventory.py --sources confluence/ --out inventory.md
  ```

  Скелет (`inventory.md` в корне репозитория сервиса) содержит скриптовые
  колонки (page_id — ключ, title, родитель, req_type, строк) и две пустые
  колонки для тебя. Состав строк и скриптовые колонки НЕ изменяются — это
  проверяет валидатор. Строку «ИТОГО…» скелета перенеси в план дословно.
  Титулы с маркером `⋯` обрезаны экспортёром (известный дефект: ~150 байт,
  незакрытая YAML-кавычка) — при классификации опирайся на полное имя
  файла выгрузки; дубли title возможны из-за той же обрезки — страницы
  различай по page_id, по необъяснённым дублям — вопрос.
- Грепни выгрузку на CriticMarkup-маркеры (`{++`, `{--`, `{~~`, `{==`, `{>>`).
  Найдены → выпиши список страниц в предупреждение; эти страницы — стоп-зона плана,
  пока команда не доведёт их до чистового вида. Помощь в чистке не предполагается.
- Пометки `status: draft` в метаданных экспортёра — НЕ стоп-зона и не повод исключать
  страницы: выдай предупреждение со списком таких страниц и продолжай. Чистота
  ПРОМ-среза — ответственность команды; иное решение по draft-страницам принимает
  она сама.
- Сверь дерево выгрузки с типами эталона. Типы эталонного комплекта смотри по факту
  каталогов корня `<эталон>` и шаблонов `<канон>/templates/` (модель
  данных и справочники, контроли, экранные формы, функции по контурам, процессы и
  статусная модель, интеграции, RBAC, печатные формы, use-cases, глоссарий и т. п.).

### Шаг 2. Классификация по сигналам

Заполни в `inventory.md` ТОЛЬКО две колонки, построчно:

- **целевой тип (гипотеза)** — тип артефакта эталона/шаблонов (и целевой
  каталог, если он не очевиден из типа);
- **основание** — одно из: `сигналы согласны` (титул, родитель в дереве и
  `req_type` указывают на один тип — содержимое НЕ читается);
  `прочитано: <вывод>` (сигналы расходятся, `req_type: unknown`,
  страница-агрегат или обрезанный титул — прочитан фрагмент, вывод
  зафиксирован); `вопрос N` (чтение не сняло неоднозначность).

Правило чтения: содержимое открывается ТОЛЬКО у кандидатов
(рассогласование / unknown / агрегат / дубль / обрезанный титул).
Прочитанных ожидается меньшинство — если читаешь подряд, остановись и
перепроверь правило. Для страниц «методов» применяй определитель метода
из `<канон>/skills/create-artifact.md`.

По завершении прогони валидатор и приведи его строку в плане дословно
(вердикт не OK либо «без гипотезы» > 0 — план не сдаётся):

```
python <канон>/tools/source_inventory.py --sources confluence/ --check inventory.md
```

Отдельно выпиши:

- корневая страница-оглавление пространства (есть у каждого сервиса): если она несёт
  только дерево ссылок без содержимого — её `page_id` закрепляется за будущим
  `README.md` комплекта, в матрице — строка-долг; в `service-vision.md` её НЕ
  превращать (концепцию не выдумывать) и отдельным вопросом не поднимать;
- страницы, не попавшие ни в один тип эталона, — по каждой сформулируй вопрос
  пользователю (не угадывай);
- типы, для которых в эталоне нет образца, но у сервиса есть содержимое, — пометь
  «работа от шаблона <канон>/templates/ — образец внутри шаблона, примеры в других сервисах НЕ искать» и добавь вопрос держателю
  эталона;
- страницы-агрегаты (одна страница → несколько карточек) и составные документы
  (несколько страниц → один документ).

### Шаг 2а. Разметка подсервисов (только крупный сервис, ≳200 страниц)

Предложи таблицу разметки «подсервис / общая часть / core» — это
ПРЕДЛОЖЕНИЕ для профиля источников, утверждает аналитик:

- сигналы: префиксы тегов в титулах, верхнеуровневые ветви дерева,
  семантика (кросс-подсервисные списки и отчёты — кандидаты в общую
  часть ВОПРЕКИ тегам);
- формат: `тег/ветвь → подсервис <слаг kebab-case с групповым префиксом>
  | общая часть | core | вне Экосистемы`; спорные строки — вопросами;
- зона «вне Экосистемы» (иной контур исполнения: НФТ об исключении
  механизмов Экосистемы, PCI DSS, каналы другой системы) в `docs/` не
  размещается — мини-комплект рядом с паспортом границы; в плане —
  этап контроля охвата без карточек;
- страницы-«Копии», тестовые заготовки и черновики в комплект не
  мигрируют: точечный список page_id «вне SRS» в контроле охвата
  (с причиной по каждой), НЕ матчеры-зоны; копия, расходящаяся с
  актуальной страницей, — открытый вопрос владельцу о судьбе
  расхождения;
- однофайловые слоты уровня куска (`status-model.md`,
  `ntf-notification.md`) — по одному на кусок (conventions §3.1),
  агрегировать не требуется;
- план затем строится ПО КУСКАМ: общая часть → core-подсервисы →
  зависимые; внутри куска — этапы по типам.

**Материализация разметки:** после утверждения (шаг 3) внеси таблицу
в профиль источников src-репозитория (создай/дополни по шаблону
`<канон>/templates/sources-readme.md`) — источник истины для сторожа
разметки selfcheck — ПРОФИЛЬ; план несёт только её снимок. Дата среза
выгрузки в профиле — ФАКТИЧЕСКАЯ: не записана экспортёром —
восстанови по mtime файлов выгрузки (единая дата по всем файлам =
день экспорта; основание укажи рядом с датой); псевдоточность
(«формализация» вроде последнего числа месяца) запрещена — лучше
честное «дата не зафиксирована» с тем знанием, что есть.

Малому сервису этот шаг не нужен: план единым куском.

### Шаг 3. Вопросы пользователю

Собери ВСЕ вопросы шагов 1–2а в один нумерованный список с вариантами
ответа и своей рекомендацией по каждому. По страницам с основанием
«прочитано» допусти и содержательные вопросы (противоречия и дыры,
замеченные при чтении) — отдельным блоком, они улучшают план, но не
блокируют классификацию. Дождись ответов. Если ответ аналитика
ссылается на ПРАВКУ канона/конвенции (новые коммиты) — перечитай
названные файлы и перегенерируй оставшиеся вопросы: рекомендации,
сформированные до правки, устарели. План с открытыми вопросами
не генерируется.

### Шаг 4. Генерация плана

Выдай план как markdown-документ со структурой:

1. **Паспорт миграции** — сервис, service-id, объём по типам и кускам
   (сводки считаются механически по заполненному `inventory.md`; суммы
   обязаны сходиться со строкой «ИТОГО»), дедлайн, акцептующий.
2. **Строки гейтов дословно** — «ИТОГО…» скелета и «ПРОВЕРКА ОПИСИ…»
   валидатора (вердикт OK, без гипотезы 0). Опись в план НЕ копируется —
   план ссылается на `inventory.md`.
3. **Маппинг и расхождения** — таблица особых случаев из шага 2
   (страницы-агрегаты, составные документы, страницы вне типов эталона,
   типы без образца) с принятыми решениями по вопросам шага 3; для
   крупного сервиса — утверждённая разметка подсервисов (шаг 2а).
   Построчный маппинг НЕ дублируется — он живёт в `inventory.md`.
   Если план УТОЧНЯЕТ утверждённое решение (при генерации нашлись
   новые факты) — каждое отклонение отдельным примечанием с основанием
   из содержимого источников (что проверено, что найдено); отклонение
   без основания запрещено.
4. **Порядок этапов** по зависимостям типов. Базовый порядок (адаптируй под состав
   сервиса, независимые типы можно вести параллельно разными сессиями):
   модель данных + справочники → контроли → экранные формы → функции → процессы и
   статусная модель → интеграции → RBAC → остальные типы → финализация матрицы и OQ.
   Этапа «зачистка `confluence_page_id`» в плане НЕТ — page_id остаются (рамка, п. 6).
5. **Карточка каждого этапа:** вход (перечень page_id — строк описи), выход (каталог внутри
   `<выход>` и ожидаемые карточки), способ (скилл-донор / адаптация / «в лоб»), критерий
   приёмки — прогон `selfcheck.py --docs <выход>` с вердиктом и дельтой против baseline
   предыдущего этапа,
   политика долгов этапа (что оформляется долгом, что вопросом OQ). Этап закрыт,
   когда акцептующий дал approve и MR этапа слит в основную ветку — акцепт
   фиксируется в git-процессе, а не записью в плане.
   Карточка обязана быть САМОДОСТАТОЧНОЙ для сборки промпта захода
   подстановкой в шаблон §10 протокола `<канон>/tools/step-protocol.md`:
   вход перечнем с ожидаемым числом, выход, способ, скоуп-запреты,
   предусловия формулой «принято приёмкой владельца».
   НАРЕЗКА ПО ЁМКОСТИ ИСПОЛНИТЕЛЯ: вход одного захода — не более
   ~1500 строк источника (суммируй колонку «строк» описи; ≈15–18 тыс.
   токенов); страница крупнее порога делится по верхнеуровневым
   секциям, карточка типа собирается за несколько заходов (append).
   Этап с крупным входом несёт раздел «Заходы серии» — перечень
   входов каждого захода с прогоном гейта и сдачей после каждого. Замер: слабый
   исполнитель на входе ~90 тыс. токенов ушёл в генерирующий скрипт
   вместо пофайловой работы.
6. **Правила работы исполнителя-LLM** — в план дословно НЕ
   переписываются: исполнитель каждого захода обязан работать по
   нормативному протоколу `<канон>/tools/step-protocol.md` (preflight,
   git read-only, запрет изменяющих скриптов, baseline/журнал, лимит
   попыток, три исхода, формат сдачи) — план ссылается на протокол
   одной строкой. В плане остаются только два правила самого плана:
   долги фиксируются ТОЛЬКО канонным форматом строки матрицы «нет
   целевого артефакта … — требуется заход …», проверяемым link_debts;
   локальные обозначения плана — ярлыки политик, коды классов вроде
   `D-*` — допустимы только с расшифровкой при первом употреблении и
   пометкой «в артефакты комплекта не переносятся».
7. **Риски и обходы** — минимум: CriticMarkup в источнике; битые/сложные HTML-таблицы
   (rowspan, вложенность); страницы-свалки; потери при конвертации ячеек; перегрузка
   контекста LLM на больших страницах (лечится нарезкой захода).
8. **Календарная раскладка** этапов на дедлайн с явным критическим путём и точками,
   где возможна параллель.
9. **Идеи ускорения** — отдельным разделом предложи всё, что видишь по этому сервису
   (пакетная обработка однотипных страниц, параллельные сессии, донорские скилл-заготовки
   канона, механизация повторяющихся преобразований). Время критично — любые
   работающие идеи приветствуются.
10. **Промпты заходов** — для каждого этапа плана собери готовый промпт
   ПОДСТАНОВКОЙ его карточки в шаблон §10 протокола
   `<канон>/tools/step-protocol.md` и сохрани файлом
   `prompts/<ЭТАП>.md` в src-репозитории (приложение плана) И выведи
   полным текстом в ответ — человек видит промпт сразу, ревьюит и при
   необходимости правит; правки вносятся В ФАЙЛ (версионируются
   чекпоинтом стенда), не в буфер. Хэша канона в шаблоне нет
   конструкцией: свежесть сверяет сторож среза по строке «срез канона»
   профиля источников (строку ведёт владелец). Промпт передаётся в
   СВЕЖУЮ сессию исполнителя указанием на файл, не копипастом. Сочинение промпта сверх шаблона — дефект:
   всё инвариантное живёт в протоколе и скиллах, не в промпте.

### Ограничения

- Ты работаешь read-only по всем перечисленным репозиториям; изменяются
  только: `inventory.md` (две колонки LLM), профиль источников
  `README.md` src-репозитория (материализация утверждённой разметки,
  шаг 2а), файлы промптов `prompts/<ЭТАП>.md` (структура плана, п. 10)
  и создаваемый файл плана.
- Числа в плане — только из строк гейтов описи, не оценки «на глаз».
- Если входные данные неполны (нет выгрузки, нет эталона, не задан путь к клону
  docs-external-contracts, не назван service-id,
  service-id отсутствует в `<канон>/services.json`, не задана метка `version`,
  не заполнена дата дедлайна или не назван акцептующий) — остановись и запроси
  недостающее, не строй план на предположениях. Дедлайн не выводится и не
  предполагается — только явная дата от команды.
