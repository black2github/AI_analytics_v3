# [КК] Паспорт границы контуров: Экосистема ↔ Розница (операции с чувствительными данными карт)

Черновик страницы Confluence для раздела «Корпоративные Карты» (родитель —
по решению аналитика; ветки `[КК_Виджет_РЕКВ]`, `[КК_Виджет_ПИН]` и страница
«[КК_Виджет] Клиент: Метод обмена токенов» перевешиваются под эту страницу).
Предмет паспорта — ГРАНИЦА между контурами (двусторонняя: оба направления
пересечений); виджеты — модули, работающие через неё (раздел 6).
Все факты — дословно из аналитики сервиса; пробелы — в «Открытых вопросах».

---

## 1. Назначение

Страница фиксирует границу между контуром Экосистемы (ГПБ БОЛ) и
PCI DSS-контуром Розницы для операций с чувствительными данными
банковских карт (PAN, CVV2, ПИН-код) сервиса «Корпоративные Карты»:
где исполняются виджеты, по чьим каналам ходят данные, в каких точках
и в каких направлениях граница пересекается и почему к модулям за
границей не применяются механизмы Экосистемы. Страница — верхний узел
веток виджетов и опорный артефакт для ИБ / PCI DSS-аудита.

## 2. Контур исполнения и участники

- **Виджеты** — наборы скриптов, исполняемые на устройстве пользователя
  (браузер / мобильное приложение). Реализация — команда сервиса
  «Корпоративные Карты»; серверной части у виджетов нет.
- **Канал данных — Розница** (омни-платформа / ОКС): целевые эндпоинты
  «УС Реквизиты карты» (`omni-oks-requisites`) и «УС ПИН»
  (`omni-oks-pin`); аутентификация — ЕПАА («лёгкий токен»).
- **Процессинговый Центр (ПЦ)** — источник xPAN и открытого RSA-ключа,
  получатель ПИН-блока.
- **Экосистема (ГПБ БОЛ)** — только точка встраивания: пользователь
  инициирует операцию с экранных форм Экосистемы (например, кнопка
  «глаз» поля «Номер карты» на ЭФ «Детальная информация по карте»);
  дальнейшая работа виджета идёт вне её каналов. Последующее
  подтверждение операций (OTP) выполняется уже в Экосистеме после
  возврата управления.

Из нефункциональных требований раздела (дословно): модуль «является
частью системы работы с чувствительными данными банковской карты и, как
следствие, относится к списку систем, входящих в контур PCI DSS»;
требуется «минимизировать использование механизмов и/или библиотек,
относящихся к Экосистеме» и «исключить использование механизмов и/или
библиотек, передающих информацию в Экосистему, за исключением передачи
параметров, возвращаемых явно в результате вызова методов данного
виджета».

## 3. Поток данных

- PAN: виджет запрашивает у УС_РЕК недостающую часть номера
  (`partNum`) и склеивает её с маскированным номером на устройстве;
  полный PAN существует только на устройстве пользователя.
- CVV2: запрашивается у УС_РЕК, отображается на устройстве.
- ПИН: вводится пользователем в ЭФ виджета, шифруется НА УСТРОЙСТВЕ
  (ПИН-блок ISO 9564-1 & ANSI X9.8 format 0, Thales ‘01’; открытый
  RSA-ключ и фиктивный xPAN-«соль» — от ПЦ) и отправляется по каналу
  Розницы в ПЦ. Открытый ПИН канал не покидает устройство.
- Через каналы и хранилища Экосистемы PAN/CVV2/ПИН **не проходят и не
  сохраняются**. В Экосистему возвращаются только явные результаты
  методов (статусы, коды/сообщения ошибок).
- Права на просмотр CVV и антифрод-контроль (СМФТ) проверяются на
  стороне УС_РЕК (коды ошибок 02, 03 таблиц маппинга) — не механизмами
  привилегий Экосистемы.

## 4. Точки пересечения границы (их две)

**4.1. Обмен токена (Экосистема → Розница, вход в контур).**

Виджеты используют действующий токен пользователя Экосистемы (формат
UAA, ГПБ БОЛ) ОДНИМ способом — обменивая его на «лёгкий токен» / 
идентификатор сессии доступа формата ЕПАА через «[КК_Виджет] Клиент:
Метод обмена токенов» (общий метод обоих виджетов, «Библиотека модулей
Сервиса»): цепочка «аутентификация по IP (`/passport/gpb/authenticate`,
realm `/system/ip`) → интроспекция токена UAA в омни-платформе (realm
`b2c/legal/uaa`) → выдача токена ЕПАА». Обмен нестандартный
(вне RFC 8693 OAuth 2.0 Token Exchange) — осознанное решение из-за
единичности случая. Полученный токен ассоциируется с сессией текущего
пользователя; при ответе `needConfirm` (истечение сессии Розницы)
связь разрывается и обмен выполняется повторно.

**4.2. Авторизация операции (Розница → Экосистема, обратный вызов).**
Перед выдачей данных УС_РЕК обращается к собственному API-методу сервиса
«Корпоративные Карты» — «[КК_API] API Функция авторизации операции»
(логика авторизации операций по корпкартам v2, стратегия «Просмотр
реквизитов» / ViewRequisitesStrategy) — для проверки правомерности
запроса по конкретной карте. Чувствительные данные карт в этом вызове
не передаются. В целевой структуре метод оформляется штатно:
internal-contract (INTC) + функция метода в комплекте сервиса.
Сквозной сценарий четырёх участников (Экосистема-фронт → виджет →
УС_РЕК → Экосистема-бэк) — процесс-артефакт Экосистемы (комплект КК,
UML-диаграммы последовательностей в ветке «[КК_РЕК] Просмотр
реквизитов»).

## 5. Границы ответственности

| Зона | Ответственный |
|---|---|
| Скрипты виджетов, их методы и ЭФ | команда «Корпоративные Карты» |
| Эндпоинты УС_РЕК / УС_ПИН, ЕПАА, канал | Розница (омни-платформа/ОКС) |
| xPAN, RSA-ключи, приём ПИН-блока | Процессинговый Центр |
| Точки встраивания, возврат управления, OTP | Экосистема (комплект КК) |
| Авторизация операций по картам (метод API) | Экосистема (комплект КК) |

## 6. Виджеты и их методы

- **[КК_Виджет_РЕКВ] Просмотр реквизитов карты**: «Клиент: Скрипт
  получения PAN», «Клиент: Скрипт получения cvv».
- **[КК_Виджет_ПИН] Смена пин-кода**: «Клиент: Скрипт ввода ПИН-кода»
  (+ «Метод шифрации ПИН-кода»), «Клиент: Скрипт отправки ПИН-кода»;
  ЭФ виджета: первый ввод, повторный ввод, ПИН установлен/изменён,
  отказ в смене, ошибка авторизации, техническая ошибка.
- **Общий метод**: «[КК_Виджет] Клиент: Метод обмена токенов».

Спецификации целевых эндпоинтов (раздел «Реквизиты и ПИН для ГПБ
БОЛЛ»): УС ПИН — запрос на инициализацию, запрос на установку
ПИН-кода; УС Реквизиты карты — запрос части номера карты, запрос cvv2;
плюс эндпоинт(ы) обмена токена (см. открытый вопрос 4).

## 7. Что НЕ применяется к виджетам

Привилегии и ролевая модель Экосистемы (методы виджетов «общедоступны» /
«не зависят от роли»; правомерность запроса по конкретной карте
обеспечивается обратным вызовом авторизации — п. 4.2, а права на
просмотр CVV и антифрод — на стороне УС_РЕК/СМФТ); гейты и конвенции
комплекта Экосистемы (селфчек, CALL-модель); механизмы и библиотеки
Экосистемы (по НФТ раздела).

## 8. Открытые вопросы

1. Официальное реестровое наименование АС «Розницы» (омни-платформа /
   ОКС) и документ, подтверждающий её PCI DSS-сертификацию, — для
   ссылки из этого паспорта (сейчас утверждение опирается на НФТ
   аналитики сервиса).
2. Владелец (команда) эндпоинтов УС_РЕК/УС_ПИН и ЕПАА — контакт для
   изменений контракта.
3. Время жизни «лёгкого токена» ЕПАА и точное место его хранения
   «в ассоциации с сессией пользователя» (на устройстве / в сессии
   браузера?) — подтвердить, что токен Розницы не попадает в
   серверные компоненты Экосистемы.
4. Обмен токена специфицирован внутри страницы метода; отдельной
   страницы спецификации эндпоинтов обмена (как у УС_РЕК/УС_ПИН) нет —
   завести или явно принять текущее описание как достаточное.
5. Формулировки разделов 2–4 — на согласование ИБ.
