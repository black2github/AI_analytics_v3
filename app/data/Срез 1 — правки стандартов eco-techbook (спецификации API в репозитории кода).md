# Срез 1 — правки стандартов eco-techbook: спецификации API живут в репозитории кода

Основание: письмо «Спецификации API в репозиториях кода» и его решения — 1.В (`HEAD`
по умолчанию, явный `ref` как исключение), 2.В (два состояния сервиса: карточка `INTC` до перехода
на API First, поля YAML после), 3.Г (адрес спецификации чужого сервиса строится по коду сервиса),
4.В (генерация YAML — вне комплекта; в комплекте только то, что читает человек).

Файлы: `standards/analytics/conventions.md`, `standards/analytics/repo-topology.md` (ветка от
свежего `master` после вливания `analytics/lib-contract` и `analytics/named-entity-links`; MR —
владелец). Ниже — каждое место: где, что сейчас, что станет. Номера строк — по `master` на
2026-10-06. Формулировки «стало» — черновик на вычитку, не окончательный текст.

## Единая модель, на которую сводятся все места

- Спецификации OpenAPI и AsyncAPI сервиса живут в `api-specification/` репозитория кода
  (`ECO_BE/ms-<service-id>`). Копий YAML в комплекте документации нет; каталог `api/` в комплекте не
  создаётся.
- Связь операций с требованиями ведёт матрица трассировки, раздел «Покрытие: API ↔ SRS»: строка —
  операция, ссылка «Источник:» на файл спецификации через `HEAD` и имя операции (`operationId` /
  channel) текстом.
- Описание метода для людей — два состояния сервиса. До перехода на API First — карточка `INTC` в
  `srs/internal-contract/` (постановка из Confluence). Событие перехода — спецификация с
  заполненными `summary` и `description` опубликована в `api-specification/`. После — описание
  живёт в этих полях YAML, карточка снимается с пометкой в реестре, её текст — источник полей;
  матрица связывает в обоих состояниях. Слой `LIBC` не затрагивается.
- Потребитель находит спецификацию чужого сервиса по правилу: код сервиса из каталога канона →
  `https://gitlab.gboteam.ru/ECO_BE/ms-<code>/-/tree/HEAD/api-specification`. Правило требует, чтобы код
  сервиса совпадал с именем репозитория кода без префикса `ms-`; исключения (несколько репозиториев
  кода у сервиса, несколько сервисов в одном) — явным полем каталога.
- Ссылки в репозиторий кода — через `HEAD`. Явное имя `ref` допустимо только когда комплект
  описывает не основную линию кода; тогда `ref` называется один раз в шапке раздела «Покрытие: API ↔
  SRS» с причиной, и все ссылки раздела используют его. Прибор: любой явный `ref` — предупреждение;
  имена веток по умолчанию (`master`, `main`, `trunk`, `develop`) — брак в строгом профиле.
- Асинхронные контракты: YAML — тоже только в репозитории кода; для людей в комплекте остаётся
  реестр асинхронных операций в `internal-contract` без YAML (детали — срез 3, канон).

## Что в этом срезе не делается

- Канон (`_meta` docs-o2new) — срез 2, готовится параллельно и вливается сразу за срезом 1.
- Асинхронные контракты в каноне (`generate-async-contracts`, `_meta/asyncapi/`,
  `async-contract-card.md`) — срез 3.
- Живые комплекты `docs-sign`, `docs-file-storage` — срез 4, сообщение владельцам.
- Материалы API-First техбука (`api-first-async-analyst-howto.md`, версия AsyncAPI) — не наша зона;
  расхождение версий 3.1.0 / 3.0.0 снимается само: генерация из канона уходит.

## Открытые места для вычитки владельцем

1. T13 — формулировка о совпадении `service-id` с именем репозитория кода затрагивает §6, который
   ведёт другая команда (team-configs, манифесты). Предложение записано как правило для сервисов,
   зарегистрированных в каталоге канона; если руководитель хочет общего правила — формулировку
   усилить.
2. C10 — исключение для явного `ref` записано так, как в письме (не основная линия кода, причина в
   шапке раздела). Рекомендация внутри: предпочитать тег ветке.
3. C8 — уведомление потребителей при снятии карточки опирается на таблицу «Потребители» карточки
   `INTC`; если руководитель считает это обязанностью матрицы, а не карточки — поправить.
