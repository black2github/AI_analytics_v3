# Каталог сервисов `services.json`: что проверить в своих записях

**Кому:** коллегам, вносившим правки в каталог сервисов с 24.09 по 01.10: Андрей Дмитричев,
Алексей Трушин, Владислав Веревкин, Александр Шилов.
**От:** владелец канона. **Дата:** 02.10.2026.

## Зачем это письмо

Каталог сервисов (`_meta/services.json` в репозитории канона `EAS/docs-o2new`) — единственное
место, по которому сервисы находят друг друга после переезда из Confluence в Git. По полю `code`
ищут запись сервиса, по полю `repo` строят ссылки на чужой комплект требований. Ошибка в записи
не видна в самом каталоге, но ломает ссылки у всех, кто на этот сервис опирается.

С 29.09 каталог проверяет инструмент проверки комплектов `selfcheck`: в отчёте каждой команды
появились строки «каталог сервисов: …». Сейчас таких строк 14. На вердикт проверки они не влияют,
но видны всем командам при каждом прогоне, поэтому лучше убрать их до того, как начнутся вопросы.

Ниже: три правила записи, затем адресно — что поправить каждому, и как это сделать.

## Три правила записи

**1. Поле `repo` — адрес корня комплекта, без имени ветки и без хвостов.**
Корень репозитория пишется как есть. Каталог внутри репозитория — через `/-/tree/HEAD/<путь>`.

| | Адрес |
|---|---|
| Верно, комплект в корне репозитория | `https://gitlab.gboteam.ru/EAS/src-invite` |
| Верно, комплект в каталоге | `https://gitlab.gboteam.ru/EAS/src-common-dictionary/-/tree/HEAD/output/okfs/docs` |
| Неверно: имя ветки | `…/-/tree/master/output/okfs/docs` |
| Неверно: хвост из адресной строки браузера | `…/output/types_doc/docs?ref_type=heads` |

Почему `HEAD`, а не `master`: адрес с именем ветки перестаёт работать при её переименовании, а
`HEAD` всегда указывает на основную ветку. Хвост `?ref_type=heads` браузер добавляет сам, в
адрес комплекта он не входит и мешает достраивать путь к файлам.

**2. Поле `code` уникально.** По коду запись должна находиться однозначно.

**3. Код сервиса совпадает с `service` во frontmatter документов его комплекта** и пишется в
kebab-case (строчные латинские буквы, цифры, дефис). Менять код можно, но это переименование
сервиса для всех, кто на него ссылается: порядок — в разделе для Алексея и Владислава ниже.

Полное описание полей и правило смены кода — документ «Межсервисная адресация», раздел 4:
`_meta/migration/cross-service-addressing.md` в том же репозитории.

## Как внести правку

Основная ветка канона защищена, правка идёт веткой и запросом на слияние. `<клоны>` — каталог,
в котором лежат клоны репозиториев.

1. Обновить клон и создать ветку:

   ```powershell
   git -C <клоны>\docs-o2new switch master; git -C <клоны>\docs-o2new pull --ff-only; git -C <клоны>\docs-o2new switch -c meta/services-<ваш-сервис>
   ```

   Ожидание: `Switched to a new branch 'meta/services-…'`.

2. Исправить свои записи в файле `<клоны>\docs-o2new\_meta\services.json`. Чужие записи не
   трогать, порядок записей не менять.

3. Проверить каталог до отправки:

   ```powershell
   python <клоны>\docs-o2new\_meta\tools\selfcheck.py --docs <клоны>\docs-account-opening-request --out $env:TEMP\catalog-check.txt; Get-Content -Encoding UTF8 $env:TEMP\catalog-check.txt | Select-String "каталог сервисов"
   ```

   Ожидание: в выводе нет строк с кодами ваших сервисов. Строки про чужие записи исчезнут,
   когда их поправят авторы.

4. Закоммитить и отправить:

   ```powershell
   git -C <клоны>\docs-o2new add -- _meta/services.json; git -C <клоны>\docs-o2new commit -m "services.json: адрес repo по правилу адресации (<ваш сервис>)"; git -C <клоны>\docs-o2new push -u origin meta/services-<ваш-сервис>
   ```

   Ожидание: ссылка GitLab на создание запроса на слияние. Целевая ветка — `master`.

Вопросы по правилам каталога — владельцу канона.
