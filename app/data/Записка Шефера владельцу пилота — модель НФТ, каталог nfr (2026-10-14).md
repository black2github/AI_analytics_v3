## 2. Уже мигрированные комплекты (в т.ч. lk-mp)

**Правило по умолчанию:** существующие комплекты **не трогаем** до явного захода. Строка README `US / FR / NFR / RR` и НФТ внутри фич остаются как есть до следующей волны миграции.

**Для lk-mp до переноса в `docs-lk-mp`:** нужен явный заход `create-nfr` (`ingress: reverse` по страницам НФТ источника) + правка README/легенды под каталог; НФТ из фич вынести в `nfr/`, раздел `NFR-NN` убрать. Иначе паспорт покажет расхождение с каноном. Параллельно два формата в одном репозитории команды не держим.

## 3. НФТ вне 18 кодов каталога

Другие коды **не выдумываются**. Фрагмент без однозначного кода (`prf`…`mon`) помечается неоднозначностью / «вне типа» в **отчёте захода**, на страницу не пишется. Аналитик в HITL назначает код из таблицы или отклоняет как вне объёма / не-НФТ. Расширение каталога — только через изменение шаблона `nfr.md`, не локальным кодом сервиса.

## 4. Какие страницы Confluence — вход НФТ для планировщика

Признаки (`prompt-plan.md` / шаблон `nfr.md`):

- код источника **NFT**, идентификатор документа с **`NFT:`**, ветвь НФТ;
- содержание про качество, ограничение, профиль нагрузки, мониторинг или политику;
- префикс **`НФТ.`** в title **не обязателен** — его отсутствие не отправляет страницу в «неизвестный тип».

Роли входа: `navigation` | `content` | `reference-only` | `baseline` | `instruction`. Целевой документ — `nfr-<код>.md` в `output/<service>/nfr/`, скилл `create-nfr`, `ingress: reverse`. Не НФТ: каталог REST, процесс, функция, модель данных, инструкция/чек-лист методологии.
