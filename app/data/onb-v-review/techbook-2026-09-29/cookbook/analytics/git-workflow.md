Точные правила веток, коммитов, запросов на слияние и ревью для **docs-репозитория**
аналитики.

Это нормативные правила «можно / нельзя / когда вливать». Практика день за днём —
[руководство аналитика §4](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#4-типичный-рабочий-день).

Кратко по терминам (дальше — коротко):

* **`trunk`** — общая ветка docs-репо; в неё не пишут напрямую;
* **запрос на слияние (MR)** — просьба влить вашу ветку в `trunk` после проверки;
* **push** — отправка ветки на GitLab;
* **коммит** — сохранённый снимок правок с сообщением;
* **squash / squash-merge** — влить MR в `trunk` **одним коммитом** (в истории `trunk`
  не остаётся пачки мелких коммитов ветки). В docs так **предпочтительно**. Настройка —
  [gitlab-settings](gitlab-settings.md); термин —
  [terms.md](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/terms.md);
* **Approval rules** — именованные правила ролей в GitLab (Analyst / Backend / …).
  Для docs-репо **не используем**; обязательный approve — CODEOWNERS;
* **CODEOWNERS** — файл владельцев путей; при включённом Require code owner
  approval GitLab требует их approve. Роли ревью в шаблоне MR — чеклист автора,
  не GitLab rule;
* **SemVer** — схема версий в backend; из‑за неё там часто **запрещают** squash.
  У docs SemVer нет — squash ок.

## 2. Картина целиком

Одна общая ветка **`trunk`**. Работа — в короткой ветке → коммит → запрос на слияние
(MR) → проверка → вливание в `trunk`.

```text
своя ветка (docs/…/KEY-…)
        │
        ▼  MR + проверка + при необходимости совместное вливание с кодом
     trunk   ← единственная долгоживущая ветка docs-репо
```

Если правка описывает поведение, которое **реализуют в коде**, docs и код вливают
**согласованно** (одна Jira, два MR). Подробнее —
[Долгоживущие ветки — Trunk-Based Development (TBD)](#долгоживущие-ветки--trunk-based-development-tbd).

## 3. Общие правила

* Базовая ветка — **`trunk`**. Прямые коммиты в `trunk` запрещены.
* Одна логическая задача — одна ветка.
* Имена веток — **латиница**, **kebab-case** (строчные буквы, слова через дефис:
  `data-model-entities`). Сообщения коммитов — **русский**.
* Коммит и push агентом — **только по просьбе** аналитика.
* **ИИ не соавтор:** запрещены `Co-authored-by:` / `Signed-off-by:` от модели,
  «сгенерировано ИИ» и перечни моделей. Автор — человек (учётка команды).
* **Автор коммита** — `user.name` и `user.email` в Git (глобально, **рабочая** почта
  банка). Настройка —
  [environment-setup §2.1](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/environment-setup.md#автор-коммитов).

* В `<service-id>/` нет ссылок на Confluence, код и **src-репо**. Откуда взяты
  факты — в **коммите или MR**, не в тексте документа.
* **Целевой remote** docs-репо — состав по
  [repo-topology § состав](../../standards/analytics/repo-topology.md#3-состав-целевого-docs-репо)
  (единственный источник перечня): `<service-id>/` + инфра (`README.md`,
  `gpb-manifest.json`, `CODEOWNERS`, `.gitignore`). Сырьё, выгрузки Confluence,
  открытые вопросы (OQ) и отчёты — в **парном src-репо**, не в docs. Обёртки
  агентов не коммитить; `.gitignore` не ослаблять под сырьё и IDE.

## 4. JIRA и линковка с задачей

Выжимка — [conventions.md](../../standards/analytics/conventions.md) §7.

Ключ задачи: `<JIRA-PROJECT>-<номер>`. Проект разный у команд; **агент его не выбирает**.
Источник — человек / карточка; `jiraDevProject` в манифесте — только ориентир.
В примерах `KEY-12345` — условный ключ.

Ключ нужен в **трёх местах**: имя ветки, заголовок MR, тема **каждого** коммита.
Одного имени ветки мало.

| Где        | Правило                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------- |
| **Ветка**  | jiraid обязателен, если есть задача; без задачи — исключения (`fix/…`, иногда `meta/` / `chore/`) |
| **Коммит** | ключ в начале темы: `KEY-12345 Добавлены сущности…` (русский, прошедшее время; без `feat:`)       |
| **MR**     | `KEY-12345: …`; при squash — ключ в squash-сообщении                                              |

Без задачи — ветка и коммиты без ключа. Агент **не выдумывает** jiraid; нет ключа —
спросить.

## 5. Ветки

### Формат имени

```text
<prefix>/<topic>[/<jiraid>]
```

| Сегмент  | Описание                                             |
| -------- | ---------------------------------------------------- |
| `prefix` | Тип изменений (таблица ниже)                         |
| `topic`  | 2–5 слов, kebab-case (строчные, через дефис)         |
| `jiraid` | `<JIRA-PROJECT>-<номер>` — если у работы есть задача |

Примеры: `docs/data-model-entities/KEY-12345`, `meta/git-workflow/KEY-12345`;
без задачи: `fix/ent-005-signature-typo`.

### Префиксы

| Префикс | Когда                                                                                | Пример                                 |
| ------- | ------------------------------------------------------------------------------------ | -------------------------------------- |
| `docs`  | Изменения под `<service-id>/`                                                        | `docs/data-model-entities/KEY-12345`   |
| `src`   | Работа в **парном src-репо** (выгрузки, черновики, хронология); не папка внутри docs | `src/KEY-12345` (ветка **в src-репо**) |
| `meta`  | шаблоны, скиллы (правки в eco-techbook / eco-kb / toolkit или локально)              | `meta/git-workflow/KEY-12345`          |
| `fix`   | Опечатки, формат без смены смысла                                                    | `fix/ent-005-signature-typo`           |
| `chore` | README, .gitignore, CI                                                               | `chore/readme-structure`               |

### JIRA ID — действующие правила

* Есть задача → третий сегмент обязателен.
* Без задачи → `<prefix>/<topic>` только как согласованное исключение.
* JIRA ID указывает **только пользователь**; агент не подставляет placeholder.
* Если ключ дан явно — и в ветке, и в каждом коммите.

### Дополнительно

* Ветки по имени человека — только локальный черновик на своей машине; перед MR →
  `docs/…` или `meta/…`.
* Не смешивать в одной ветке несвязанные docs и methodology.

### Примеры: хорошо / плохо

| OK                                   | Не OK                                             |
| ------------------------------------ | ------------------------------------------------- |
| `docs/data-model-entities/KEY-12345` | `asudnitsin` (к merge)                            |
| `src/KEY-12345` (в src-репо)         | `Docs/DataModel/KEY-12345`                        |
| `fix/ent-005-signature-typo`         | `docs/stuff`; ветка без jiraid при наличии задачи |
| `meta/git-workflow/KEY-12345`        |                                                   |

### Долгоживущие ветки — Trunk-Based Development (TBD)

#### Что это значит

В docs-репо одна общая ветка **`trunk`** (чистовик `<service-id>/`). В неё не
пишут напрямую. Работа — в короткой ветке под задачу → MR → вливание в `trunk`.

Так же устроены BE/FE и org
([ADR-0017](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/architecture/adr/0017-trunk-based-development.md)).
Для обычной работы в docs достаточно `trunk` и feature-веток `docs/…` (или `meta/…`,
`fix/…`).

#### Что где лежит

| Что                                    | Где                                             |
| -------------------------------------- | ----------------------------------------------- |
| Чистовик требований                    | `trunk` docs-репо (`<service-id>/`)             |
| Текущая работа                         | Короткая feature → MR → `trunk`                 |
| Сырьё, выгрузки Confluence, хронология | Парный **`src-*`** (не docs)                    |
| Ревью разработки и QA                  | В **docs**; доступ к src — **только аналитики** |

В docs-репо **нет** долгоживущей ветки `history` и папки `sources/`. Git-процесс src
не нормируется так же жёстко, как docs. Мост src → чистовик — скилл / копирование
смысла, **не** git-merge между репо.

Подробнее:
[repo-topology § состав](../../standards/analytics/repo-topology.md#3-состав-целевого-docs-репо),
[§ доступ](../../standards/analytics/repo-topology.md#доступ-к-репо),
[roadmap миграции](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/roadmap-doc-as-code-migration.md).

#### Совместный merge с кодом

Если меняется поведение / контракт, которое **реализуют** в BE/FE:

1. Одна Jira, парные MR (docs + код). Автоматического «замка» между репо нет —
   дисциплина и чеклист в шаблоне MR.
2. Пока docs не в `trunk`, разработчик читает **открытый docs MR / ветку**. Срез
   «ещё не в проде» — матрица / Jira, не вторая git-линия.
3. **Сигнал к merge** — во всех репо с префиксом **`docs-*`** (сервисные, доменные и
   docs-external-contracts). Когда задача **поступает к QA**, тестировщик пишет
   аналитику в командный чат. Аналитик вливает MR в `trunk` (ревью закрыты;
   предпочтительно squash — одним коммитом).

Правило сигнала QA **не** действует для `src-*`, репозиториев общих норм
(eco-techbook, eco-kb, toolkit) и репо кода. Пошагово —
[кейс 4](#4-задача-поступила-к-qa--merge-в-docs-).

#### Когда можно без кода и без сигнала QA

Docs в `trunk` без парного кода (и без ожидания QA):

* `fix/…` — опечатки и мелкие правки текста;
* `meta/…` — методология / инфра docs;
* AS-IS без новой реализации;
* заглушки EXTINT / каркас ID, явно «ещё не в код».

#### Короткие feature

* Feature **короткоживущая**: в docs долгоживущая только `trunk`.
* Большую задачу дробить на несколько коротких MR, **если возможно**: тогда так же
  делят задачу Jira и срез передачи в разработку / релиз (один ключ — один
  согласованный кусок поставки).
* Пока ждут парный код, MR может жить дольше — в описании ссылка на парный MR.
* Вливание в docs предпочтительно **squash** (одним коммитом) — см. термины в начале
  файла. Feature toggles FE/BE в docs не переносим.
* Практика —
  [гайд §4](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#4-типичный-рабочий-день);
  разборы — [Операционные кейсы](#операционные-кейсы).

#### TBD: не делать

| Не делать                               | Почему                                               |
| --------------------------------------- | ---------------------------------------------------- |
| `dev` / `stage` / `develop`             | Docs не деплоятся по средам; цель вливания — `trunk` |
| Долгоживущая ветка на аналитика         | Нет общей утверждённой версии текста для команды     |
| `draft-trunk` под статусы               | Статусы — у MR/Jira                                  |
| Ветка `history` / сырьё внутри docs     | Летопись и выгрузки — в src-репо                     |
| Merge docs «вперёд» кода без исключения | Расходится с основной веткой кода                    |

Черновик / на ревью / принято — через **MR и акцепт в Jira**, не отдельной git-линией.

## 6. Коммиты

### Сообщение коммита

Сообщение коммита — по-русски, в прошедшем времени, одна мысль.
Префиксы вроде `feat:` и Conventional Commits / SemVer — **не** для docs (у backend —
свой контур).

### Язык и время

* Русский; тема — «Добавлена», «Обновлены», «Исправлена».
* Без английских префиксов (`feat:`, `fix:`, `docs:`).

### Тема (первая строка) — обязательна

```text
KEY-12345 <Что сделано в прошедшем времени>[, уточнение]
```

Одна мысль; мягкий лимит ~72 символа; без точки в конце. Ключ обязателен, если есть
задача.

### Тело — только когда темы недостаточно

По умолчанию тело не нужно. Добавьте, если:

| Ситуация                       | В теле                    |
| ------------------------------ | ------------------------- |
| Факты из src-репо              | **Откуда взяты факты:** … |
| Много файлов, из темы не видно | **Изменённые файлы:** …   |
| Из темы неясно зачем           | 1–2 предложения           |

#### Примеры

```text
KEY-12345 Исправлена опечатка в описании ENT-003
```

```text
KEY-12345 Добавлено описание сущности ENT-003 «Подпись»

Откуда взяты факты: Confluence «Подпись заявки» (pageId 6364xxx); архив ms-account-opening-domain.
```

### Коммиты: не делать

| Плохо                             | Как правильно                         |
| --------------------------------- | ------------------------------------- |
| `update`, `wip`                   | `Обновлены справочники модели данных` |
| `Добавить модель`                 | `Добавлена модель данных сервиса`     |
| `feat: добавлена модель`          | без английского префикса              |
| pageId внутри `<service-id>/*.md` | pageId — в теле коммита/MR            |
| `Co-authored-by:` от модели       | убрать                                |

| OK                                              | Не OK                  |
| ----------------------------------------------- | ---------------------- |
| `KEY-12345 Добавлены сущности ENT-001…ENT-005`  | `update`               |
| `KEY-12345 Исправлена обязательность branch_id` | `Добавить справочники` |

## 7. Merge Request

### Описание MR

Запрос на слияние (MR) — способ отдать работу на проверку и влить в `trunk`.
В описании — коротко: что сделано; какие артефакты; откуда факты (если из src);
что проверить. MR дополняет коммиты, не дублирует каждый.

Как вливать: в docs обычно **squash-merge** — все коммиты ветки схлопываются в
**один** коммит в `trunk` (см. термины в начале файла). В squash-сообщении нужен
ключ Jira, если задача есть.

Матрица при затронутых ID — **в том же MR** (conventions §5.3). К каждому MR —
[записка для команды](#записка-для-команды). Акцепт — через MR/Jira, не полем
`status` в файле.

### Шаблон описания MR

Ниже — чеклист для автора: что отметить, чтобы коллеги поняли объём и когда можно
вливать. Файл в репо: `.gitlab/merge_request_templates/Default.md` (или Default
description).

```markdown
## Что сделано

## Артефакты (пути / ID)

## Откуда взяты факты

## Роли ревью (автор отмечает нужные; GitLab требует approve владельцев путей)

* [ ] Analyst — полнота, ID, матрица
* [ ] Backend — API / данные / FUN
* [ ] Frontend — SCR, UI
* [ ] QA — проверяемость
* [ ] Methodology — шаблоны, conventions   <!-- только eco-techbook / eco-kb / toolkit -->

## Что проверить

* [ ] матрица в том же MR (если трогали ID)
* [ ] в `<service-id>/` нет ссылок на Confluence / код / src-репо
* [ ] в remote docs нет сырья (выгрузки, открытые вопросы, reports) — место в src-репо
* [ ] парный MR BE/FE **или** исключение совместного merge

## Перед merge

* [ ] Code Owners апрувнули затронутые пути (Require code owner approval)
* [ ] треды закрыты → squash-merge
* [ ] feature с реализацией в `docs-*`: есть сигнал QA (задача у тестирования)
      **или** исключение
```

Заголовок: `KEY-12345: …`. Соавторства ИИ в описании нет.

### Записка для команды

Короткий текст в чат (для тех, кто MR не открывает): что изменилось и что делать
коллегам.

* Первая строка — суть + ссылка на MR.
* 2–5 пунктов человеческим языком; мелочь — одним пунктом.
* Действия для команды — с ⚠️.
* Читается за полминуты. Агент готовит текст вместе с созданием MR. ИИ как автор
  не указывать.

## 8. Ревью

### Что делает аналитик

* Прямой push в `trunk` запрещён — только через MR.
* На проверку зовут не только аналитиков: при нужном составе — Backend, Frontend, QA
  ([роли ниже](#типы-approval-роли-ревью)).
* Перед вливанием: матрица при затронутых ID; способ вливания docs —
  **squash-merge** (одним коммитом; предпочтительно). У backend squash часто
  запрещён из‑за SemVer — у docs SemVer нет, squash ок (см. термины в начале файла).
* После merge feature-ветку удаляют. Автор себя не утверждает (не апрувит).
* Срок ревью: желательно **один рабочий день**. В замечании: причина + что сделать;
  блокирующее vs пожелание.

### Типы approval (роли ревью)

Зачем аналитику: понять, **кого отметить** в MR и кто должен нажать Approve.

Роли отмечает автор в шаблоне MR (чеклист ниже). GitLab требует approve владельцев
затронутых путей (`CODEOWNERS` + Require code owner approval). Именованные Approval
rules не заводим — [gitlab-settings.md](gitlab-settings.md#4-approval-rules).

#### Роли и на что смотрят

Forward-стиль — в docs нет ссылок на src, Confluence, код, общие репо норм.

| Роль            | Фокус                               | Когда нужен                                       |
| --------------- | ----------------------------------- | ------------------------------------------------- |
| **Analyst**     | Полнота, ID, матрица, forward-стиль | Почти всегда при изменениях в `<service-id>/`     |
| **Backend**     | Модель, FUN, API, EXTINT, статусы   | data-model, FUN, `docs/api`, EXTINT, status-model |
| **Frontend**    | SCR, UI, RBAC в интерфейсе          | screen-forms, клиентский путь, UI-тексты          |
| **QA**          | Проверяемость, ветки Если/то        | CTL, process, status-model, SCR с ошибками        |
| **Methodology** | Шаблоны, conventions, git-rules     | Только правки в eco-techbook / eco-kb / toolkit   |

Один человек может закрыть две роли, если смотрит оба фокуса.

#### Что обязательно до merge

| Состав MR                                       | Analyst | Backend    | Frontend   | QA         | Methodology                |
| ----------------------------------------------- | ------- | ---------- | ---------- | ---------- | -------------------------- |
| Только правки в eco-techbook / eco-kb / toolkit | —       | —          | —          | —          | **да**                     |
| BRD / glossary / vision                         | **да**  | по желанию | по желанию | по желанию | —                          |
| data-model, FUN, api, EXTINT                    | **да**  | **да**     | по желанию | по желанию | —                          |
| SCR, RBAC-UI                                    | **да**  | по желанию | **да**     | по желанию | —                          |
| CTL, process, status-model                      | **да**  | по желанию | по желанию | **да**     | —                          |
| Смешанный API+SCR+CTL                           | **да**  | **да**     | **да**     | **да**     | + если трогали общие нормы |

На пилоте в чеклисте MR Analyst обязателен; Backend / Frontend / QA — по желанию.
Цель после пилота — обязательные роли по «да» в таблице (дисциплина ревью, не GitLab
Approval rules).

**Критерий завершения пилота (единственное место определения):** пилот завершён,
когда одновременно: (1) все пилотные сервисы получили вердикт «готов к переносу в
GitLab» и слиты в `trunk`; (2) достигнута метрика качества: менее 5 % файлов требуют
критических правок; (3) руководитель управления утвердил итоговый отчёт пилота.
До этого действует пилотный режим ревью; переход к целевым правилам — тем же
решением руководителя.

### Настройка GitLab (кратко)

Детали UI — в [gitlab-settings](gitlab-settings.md). Для аналитика достаточно знать
цепочку:

1. `CODEOWNERS` + Require code owner approval (шаблон — в
   [gitlab-settings §4](gitlab-settings.md#4-approval-rules)).
2. Автор отмечает роли в шаблоне MR и назначает Reviewers.
3. GitLab блокирует merge, пока апрувнули владельцы затронутых путей.
4. **Merge** могут Developers и Maintainers
   ([protected branches](gitlab-settings.md#3-protected-branches)). Перед merge:
   approve Code Owners, **Prevent approval by author**, закрытые треды, при
   реализации —
   [совместный merge](#долгоживущие-ветки--trunk-based-development-tbd).
   Labels опциональны; истина — блок Approvals.

#### CODEOWNERS

**Пока CI нет** — `CODEOWNERS` кладёте сами по шаблону. Состав из
[team-configs](https://gitlab.gboteam.ru/TEAM/team-configs) (репо состава команд);
когда CI появится — файл приедет сам, руками не править. Смена
владельцев — MR в team-configs. До sync или без sync — положить файл по шаблону в
[gitlab-settings §4](gitlab-settings.md#4-approval-rules).

Роли Analyst / Backend / Frontend / QA / Methodology — чеклист в шаблоне MR (дисциплина
ревью). GitLab требует approve владельцев путей (`CODEOWNERS`). Пока файла нет —
Require code owner approval не включать. Манифест —
[repo-topology](../../standards/analytics/repo-topology.md#6-именование-репозиториев).

#### Чеклисты по ролям

**Analyst:** атомарность; ID и матрица; нет сырья и ссылок на src в `docs/`; нет
кросс-ссылок BRD↔SRS.
**Backend:** реализуемость; YAML согласован (парный MR).
**Frontend:** SCR достаточны для UI.
**QA:** ясно что проверить; негатив.
**Methodology:** шаблон; переносимость; git-правила.

## 9. Особые случаи

### Операционные кейсы

1. [Разработка началась](#1-разработка-началась--аналитику-надо-изменить)
2. [Баги](#2-изменения-по-багам)
3. [Конфликты в Git](#3-конфликты-в-git)
4. [Задача поступила к QA — merge в docs-*](#4-задача-поступила-к-qa--merge-в-docs-)
5. [Какую аналитику брать](#какую-аналитику-брать-в-работу)
6. [Git в docs-external-contracts](#git-в-docs-external-contracts)

Напоминание:

* «Готово к реализации» ≠ «уже в docs-`trunk`» — до совместного merge текст в
  **MR / feature**.
* Merge с реализацией —
  [совместный merge](#долгоживущие-ветки--trunk-based-development-tbd).

#### 1. Разработка началась — аналитику надо изменить

Что сделать сейчас:

1. Править в docs-feature (+ **парный** MR в BE/FE).
2. Если docs ещё не в `trunk` — править открытый MR.
3. Если требования уже влили в `trunk`, а код по ним ещё нет: откатите влитие
   (revert) или сделайте новый MR с уточнением текста; дальше меняйте docs и код
   согласованно.

Если правка ломает то, что разработчики уже пишут по старым требованиям: парные
MR (docs + код), одна Jira; в [записке](#записка-для-команды) пометьте ⚠️, что
именно пересмотреть в коде.

#### 2. Изменения по багам

1. Ошибка только в доках → `fix/…` или docs-only MR (**исключение**).
2. Баг продукта → правка требований → как кейс 1.
3. Уточнение смерженного текста без новой реализации → feature от `trunk`
   (docs-only). Отдельную bugfix-ветку не заводим.

#### 3. Конфликты в Git

Часто горят матрица, README, словари. Профилактика: короткие ветки; перед push —
подтянуть `trunk`.

1. Обновить `trunk`.
2. Merge или rebase в feature.
3. В матрице **не** брать целиком «только мою» версию файла при конфликте —
   свести строки вручную (свои и чужие ID).
4. Проверить ссылки; коммит с ключом Jira; push (force-with-lease только своей
   feature).

Не делать:

* принудительно переписывать историю общей ветки `trunk` или чужой ветки;
* в матрице при конфликте принимать целиком «свою» сторону файла;
* неделями не подтягивать `trunk` в свою feature-ветку.

#### 4. Задача поступила к QA — merge в docs-*

Только репо **`docs-*`** (включая docs-external-contracts); не `src-*` / код /
eco-techbook / eco-kb / toolkit.

1. Задача в Jira поступила к тестировщику.
2. QA пишет в командный чат: ключ Jira, ссылка на открытый docs MR; ⚠️ аналитику —
   влить MR.
3. Аналитик проверяет, что approve владельцев путей закрыты, и делает squash-merge в `trunk`.

Docs-only исключения — без этого шага
([совместный merge](#долгоживущие-ветки--trunk-based-development-tbd)).

#### Какую аналитику брать в работу

> **Merge docs в `trunk` ≠ очередь на реализацию.** Истина — Jira. До совместного
> merge читать **docs MR / ветку**.

1. Задача в статусе готовности к разработке.
2. В задаче — ID артефактов и ссылка на docs MR.
3. До merge feature — MR/ветка; после совместного merge — `trunk`.
4. Противоречия без скоупа — эскалация аналитику, не наугад.

#### Git в docs-external-contracts

Репо:
[docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts).

Общие правила (trunk, Jira, язык, записка, без ИИ-соавторства) — как выше. Карточки —
[conventions](../../standards/analytics/conventions.md) §5.1.1; топология —
[repo-topology](../../standards/analytics/repo-topology.md#9-репо-docs-external-contracts);
чеклисты —
[гайд](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#внешние-банковские-ас).

**Ветки:** `<prefix>/<topic>[/<jiraid>]`. Префикс **`docs/`** здесь не использовать.

| Префикс  | Когда                      | Пример                                 |
| -------- | -------------------------- | -------------------------------------- |
| `extint` | Карточки, examples, реестр | `extint/tessa-upload-params/KEY-12345` |
| `fix`    | Опечатки                   | `fix/bsk-typo-igk`                     |
| `chore`  | Инфра репо                 | `chore/readme-link-rules`              |

| Ситуация                                           | Что мержить                                                                         |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Новый потребитель существующего базового контракта | Раздел «как сервис вызывает» в docs сервиса **и** строка «Потребители» в общем репо |
| Новый контракт / АС                                | Сначала общее репо, затем вызов в сервисе                                           |
| Ломающее изменение базового контракта              | Общее репо + правки «как вызывает» у всех потребителей                              |
| AS-IS / заглушка «ещё не в код»                    | Общее репо без парного backend                                                      |
| Опечатка                                           | Общее репо без кода                                                                 |

Гейт «docs+код» — в **сервисном** контуре, не в общем репо внешних контрактов.
Ревью базового текста: обычно Analyst + Backend. Сигнал QA → merge аналитиком —
как у всех `docs-*` ([кейс 4](#4-задача-поступила-к-qa--merge-в-docs-)).
