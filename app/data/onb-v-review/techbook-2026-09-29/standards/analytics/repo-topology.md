Куда класть аналитику (markdown) и описание API в YAML (OpenAPI / AsyncAPI)
относительно кода.

Это карта репозиториев: **где что лежит** и **как называть**. Правила веток и
день за днём — в git-workflow и гайде аналитика.

Кратко по терминам (дальше — коротко):

* **docs-репо** (`docs-…`) — чистовик требований для людей;
* **src-репо** (`src-…`) — сырьё и выгрузки для reverse (восстановление
  документации из источников; не чистовик);
* **remote** — то, что лежит на GitLab (не локальные черновики IDE);
* **`trunk`** — общая ветка docs-репо (см. git-workflow);
* **MR** — запрос на слияние;
* **BRD / SRS** — бизнес-требования и системные требования (markdown-чистовик);
* **FUN / SCR** — функции и экраны в комплекте требований;
* **`gpb-manifest.json`** — паспорт репозитория (имя = имя GitLab);
* **CODEOWNERS** — кто владеет путями и кого звать на ревью;
* **`.gitignore`** — что Git не должен коммитить в этот репозиторий;
* **team-configs** — общий репозиторий с доменами и правилами регистрации проектов
  ([TEAM/team-configs](https://gitlab.gboteam.ru/TEAM/team-configs));
* **EXTINT** — базовый контракт внешней банковской АС: текст (общий для всех
  сервисов) лежит в репо docs-external-contracts; **как сервис его вызывает** —
  карточка `CALL` в docs сервиса (`srs/contract-call/`).

## 2. Какие репозитории есть

### Что это значит

Аналитика живёт **отдельно от кода**. Обычно рядом несколько репозиториев:

| Репозиторий                                              | Простыми словами                                                                                                                                                              |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Docs** (`docs-…`)                                      | Чистовик для людей (BRD, SRS, матрица, api md). На GitLab состав **ограничен** (§3). Пространство: **ECO Analytics** ([gitlab.gboteam.ru/EAN](https://gitlab.gboteam.ru/EAN)) |
| **Src** (`src-…`)                                        | Черновики, выгрузки, сырьё для reverse. Состав **не ограничен**. Пространство: **ECO Analytics Src** ([gitlab.gboteam.ru/EAS](https://gitlab.gboteam.ru/EAS))                 |
| **Общие нормы** (eco-techbook, eco-kb, канон docs-o2new) | Правила, гайд, скиллы. **Не** копируют в docs сервиса                                                                                                                         |
| **Backend**                                              | Код сервера и файлы API в YAML (OpenAPI / AsyncAPI)                                                                                                                           |
| **Frontend**                                             | Код UI                                                                                                                                                                        |
| **docs-external-contracts**                              | Общие базовые контракты с внешними банковскими АС                                                                                                                             |

```text
общие нормы        src-репо (*)          docs-репо              backend / frontend
────────          ──────────          ─────────              ─────────────────
правила ─────────► выгрузки AS-IS ───► BRD / SRS / api md
                   черновики, OQ        вызов внеш. АС ───────► YAML OpenAPI
                   (состав свободный)   матрица / SCR           код

docs-external-contracts (**) ◄──полн. URL── вызов внеш. АС

(*) парный к docs: сервис или домен; пространство EAS (https://gitlab.gboteam.ru/EAS)
(**) https://gitlab.gboteam.ru/EAN/docs-external-contracts
```

Исходные ограничения:

* фронт и бэкенд — отдельные репо;
* аналитика — markdown в Git;
* комплект **переносим** (без ссылок на eco-techbook / eco-kb / канон,
  src, Confluence, код) — правила переносимости чистовика:
  [conventions](conventions.md) §5.

## 3. Состав целевого docs-репо

### Минимальный remote

В **целевом** docs-репозитории на GitLab (remote) лежит только чистовик и
минимальная инфра. Сырьё и IDE-обёртки туда **не** пушат.

### Что можно в remote

<!-- markdownlint-disable MD013 -->
| Путь                    | Назначение                                                                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`<service-id>/`**     | Чистовик сервиса — комплект (brd, srs, api, матрица, README, service-vision, glossary). В репозитории одного сервиса папка `<service-id>/` не создаётся: комплект лежит в корне репозитория; в репозитории нескольких сервисов — у каждого своя папка `<service-id>/` |
| **`README.md`**         | Вход в репозиторий: что это за docs-репо и куда смотреть дальше                                                                                                                                                                                                       |
| **`gpb-manifest.json`** | Паспорт репо для учёта в организации: поле `name` = имя проекта на GitLab. Образец — [`gpb-manifest.json`](../../gpb-manifest.json); поля — [guideline](https://gitlab.gboteam.ru/TEAM/team-configs/-/blob/master/gpb_manifest_guideline_team_info.md)                |
| **`CODEOWNERS`**        | Кто владеет путями и кого GitLab зовёт на ревью (пока кладёте сами по шаблону gitlab-settings)                                                                                                                                                                        |
| **`.gitignore`**        | Список того, что **нельзя** коммитить в этот репо. Держит узкий состав выше: сырьё, выгрузки и IDE-обёртки в remote не попадают                                                                                                                                       |
<!-- markdownlint-enable MD013 -->

```text
Один сервис (docs-<service-id>):
├── README.md
├── gpb-manifest.json
├── CODEOWNERS
├── .gitignore
├── brd/
├── srs/
├── api/
└── ...

Несколько сервисов (docs-<domain-slug>):
├── README.md
├── gpb-manifest.json
├── CODEOWNERS
├── .gitignore
├── <service-id-1>/
│   ├── brd/
│   ├── srs/
│   └── api/
├── <service-id-2>/
│   ├── brd/
│   ├── srs/
│   └── api/
└── ...
```

### Чего нет в remote docs

В remote docs **нет** `output/` (не класть в remote; целевой путь
`<service-id>/`), `sources/`, соседних `open-questions.md` /
`reports/` и прочего сырья.

Выгрузки Confluence, черновики, клоны кода, реестры открытых вопросов (OQ) и
отчёты — в **парном src-репо** (`src-…`). Состав src **не нормируется**.

### Только локально (не пушить в docs remote)

Папки IDE (`.cursor/`, `.claude/`), корневые `AGENTS.md` / `CLAUDE.md`,
`examples/` и прочее рабочее остаются на машине аналитика. Скиллы агентов
ставят из
канона docs-o2new (`_meta/skills/`, аналитика) и
[drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit) (разработка, QA), а не
коммитят в docs.

Для reverse рядом клонируют **src-** и репо кода — отдельные клоны, не папки
внутри docs.

`.gitignore` как раз и не даёт случайно запушить сырьё и IDE-обёртки. Не
ослаблять его «под удобство». Полный шаблон файла — отдельная задача при
настройке целевого репо.

У парного **src-репо** правила **не требуют** `gpb-manifest.json`, `CODEOWNERS` и
регистрации в team-configs как у docs. Состав и инфра src свободны.

### Доступ к репо

| Репо         | Пространство                                                                   | Кто имеет доступ в GitLab                                                                    |
| ------------ | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| **`src-*`**  | **ECO Analytics Src** ([gitlab.gboteam.ru/EAS](https://gitlab.gboteam.ru/EAS)) | **Только аналитики.** Разработку и QA в список участников не включают                        |
| **`docs-*`** | **ECO Analytics** ([gitlab.gboteam.ru/EAN](https://gitlab.gboteam.ru/EAN))     | **Аналитики + разработка (backend/frontend) + тестирование (QA)** — чтение и ревью чистовика |

Как выставить права и правила одобрения MR —
[gitlab-settings](../../cookbook/analytics/gitlab-settings.md).

## 4. Где что живёт

### Таблица «где истина»

Одна таблица «где истина» — чтобы не искать файл не в том репозитории.

<!-- markdownlint-disable MD013 -->
| Что                                                                      | Где «истина»                                                                                                                                   | Комментарий                                                   |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Бизнес- и системные требования (markdown)                                | **Docs-репо**                                                                                                                                  | Другие владельцы и ритм, чем у кода                           |
| Выгрузки AS-IS, черновики, сырьё reverse                                 | **Src-репо**                                                                                                                                   | Состав свободный; в чистовик docs не переносится как есть     |
| Правила, шаблоны, скиллы                                                 | **Общие нормы** (§7)                                                                                                                           | В продукт / backend / remote docs-репо не переносится         |
| OpenAPI / AsyncAPI (**YAML**)                                            | **Backend**                                                                                                                                    | Адрес метода, поля, типы, что обязательно                     |
| Описание методов для людей                                               | **Docs** (`api/…`)                                                                                                                             | Зачем метод, связи с FUN/SCR; якорь — `operationId` / channel |
| Экраны (SCR)                                                             | **Docs**                                                                                                                                       | Фронт не владеет требованиями                                 |
| Базовый контракт внешней АС                                              | [docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts)                                                               | Протокол, примеры — [раздел](#9-репо-docs-external-contracts) |
| Как сервис вызывает чужой контракт                                       | **Docs** (`srs/contract-call/`, карточки `CALL` — схема: [conventions §5.1.1](conventions.md#511-слой-вызовов-чужих-контрактов-contract-call)) | На базовый контракт в чужом репо — полный GitLab URL          |
| Платформенные функции ЭКО (`PLT`; граница с `CALL` — conventions §5.1.2) | **Docs** (`srs/platform-functions.md`)                                                                                                         | Не в репо внешних интеграций                                  |
<!-- markdownlint-enable MD013 -->

| Вопрос про API                                          | Отвечает                           |
| ------------------------------------------------------- | ---------------------------------- |
| Какой адрес у метода, какие поля, типы, что обязательно | YAML в **backend**                 |
| Зачем метод, поведение, ошибки по смыслу                | Markdown в **docs**                |
| Связь с FUN/SCR                                         | **Матрица** трассировки требований |

Не копировать структуры данных из YAML в markdown —
[стыковка](#8-как-стыковать-yaml-в-backend-и-markdown-в-docs-репо).

## 5. Несколько docs-репо

### Гранулярность docs-репо

Можно завести **несколько** docs-репозиториев — по домену или по сервису.
**Гранулярность выбирает команда.**

В одном docs-репо может быть несколько сервисов: у каждого свой
`<service-id>/`. Парный src — той же крупности (`src-<service-id>` или
`src-<domain-slug>`).

### Когда несколько сервисов в одном docs-репо — нормально

Обязательно:

* Одна команда-владелец, общие права merge / ревью
  ([git-workflow §ревью](../../cookbook/analytics/git-workflow.md#8-ревью)).

Дополнительно (не обязательно): общая неделимая логика в документации — требования
нельзя разнести по двум комплектам, не разорвав смысл. Это ещё один повод держать
сервисы вместе, а не условие «иначе нельзя».

Нет общих владельцев или доступа — отдельные docs-репо.

Постоянно:

* При нескольких сервисах каждый — в своём `<service-id>/` (единица выноса и
  пространство ID). Папки не смешивают; это не запрет гиперссылок. При одном
  сервисе корень репозитория и есть корень комплекта, папка `<service-id>/`
  не создаётся ([§ состав](#3-состав-целевого-docs-репо)); вынос сервиса из
  общего репозитория — перенос содержимого его папки в корень нового.
* Ссылки на соседний комплект в **том же** docs-репо — относительные пути к
  `<service-id>/` допустимы. На **другой** docs-репо из чистовика не ссылаются
  (ни путём, ни GitLab URL). Стык с ECO-соседом из другого репо — карточка
  `CALL-INT` в `contract-call/internal/` своего комплекта, базовый контракт — в
  `internal-contract/` владельца (можно заглушку); Jira/MR соседа — в описании
  задачи, не в чистовике. Это не EXTINT: базовые контракты внешних банковских АС —
  [репо docs-external-contracts](#9-репо-docs-external-contracts).
* Общие нормы читают из eco-techbook / eco-kb / канона docs-o2new; в docs сервиса не копируют.

### Когда выносить сервис или домен в отдельный docs-репо

* Другая команда / доступ / compliance / ритм релизов.
* Репозиторий раздулся (часто из-за сырья, ошибочно закоммиченного в docs вместо
  src — [§ состав](#3-состав-целевого-docs-репо)).

Вынос: переносят `<service-id>/`. Относительные ссылки на бывших соседей по репо
переписать или заменить карточкой интеграции. Общие нормы остаются в §7. Дробить
«на всякий случай» не нужно.

### Чего не смешивать в одном репо «для удобства»

| Не делать                                                          | Почему                                                                                                            |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Класть несколько сервисов в один `docs/` без папки `<service-id>/` | Ломает перенос комплекта                                                                                          |
| Создавать промежуточный каталог `docs/` внутри `<service-id>/`     | Никогда не создаётся — файлы лежат напрямую в `<service-id>/` (один сервис) или в корне репо (несколько сервисов) |
| Коммитить сырьё и выгрузки в docs remote                           | Ломает ограниченный состав; место — src                                                                           |
| Держать общие ENT/FUN «на двоих» без владельца                     | Конфликты ID                                                                                                      |
| Класть docs сервиса A в backend-репо B                             | Путаница владельцев                                                                                               |

## 6. Именование репозиториев

### Шаблоны имён

Имена docs/src **не** копируют префиксы кода (`ms-`, `eco-`, `lib-api-`).

| Контур                | Шаблон               | Пример                   | Пространство                                                 |
| --------------------- | -------------------- | ------------------------ | ------------------------------------------------------------ |
| Backend               | `ms-<service>`       | `ms-uaa`                 | —                                                            |
| Frontend              | `eco-<service>`      | `eco-user`               | —                                                            |
| **Docs, один сервис** | `docs-<service-id>`  | `docs-open-add-account`  | **ECO Analytics** ([EAN](https://gitlab.gboteam.ru/EAN))     |
| **Docs, домен**       | `docs-<domain-slug>` | `docs-domain-onboarding` | **ECO Analytics** ([EAN](https://gitlab.gboteam.ru/EAN))     |
| **Src, один сервис**  | `src-<service-id>`   | `src-open-add-account`   | **ECO Analytics Src** ([EAS](https://gitlab.gboteam.ru/EAS)) |
| **Src, домен**        | `src-<domain-slug>`  | `src-domain-onboarding`  | **ECO Analytics Src** ([EAS](https://gitlab.gboteam.ru/EAS)) |

Только **kebab-case**: строчные латинские буквы, слова через дефис
(`open-add-account`, не `OpenAddAccount` и не `open_add_account`).

* `<service-id>` = поле **`jiraDevComponent`** из манифеста кода (не обязан
  совпадать с именем `ms-…`).
* `<domain-slug>` = поле `slug` из YAML домена в
  [team-configs/domain](https://gitlab.gboteam.ru/TEAM/team-configs/-/tree/master/domain).

Для **docs**: имя GitLab-репо = `gpb-manifest.name`.
Для **src**: имя = проект GitLab `src-…`; **`gpb-manifest.json` и `CODEOWNERS` не
обязательны**.

| Не делать                               | Почему                                        |
| --------------------------------------- | --------------------------------------------- |
| Называть аналитику как `ms-…`           | Путаница с кодом                              |
| У docs имя GitLab ≠ `gpb-manifest.name` | Ломает регистрацию в team-configs и CI        |
| Класть сырьё в `docs-…` «временно»      | Состав docs ограничен (§3); сырьё — в `src-…` |

### Откуда взять service-id и domain-slug

Источник имён и доменов — [team-configs](https://gitlab.gboteam.ru/TEAM/team-configs)
(репозиторий с YAML доменов и правилами манифестов).

**Домен** (`docs-<domain-slug>` / `src-<domain-slug>`):

1. Взять `slug` из
   [domain/*.yml](https://gitlab.gboteam.ru/TEAM/team-configs/-/tree/master/domain)
   как есть.
2. Имя репо = префикс + slug.
3. Нет домена — завести MR в team-configs, не выдумывать slug.
4. Внутри docs-репо у каждого сервиса свой `<service-id>/`.

**Сервис** (`docs-<service-id>` / `src-<service-id>`):

1. В репо кода открыть `gpb-manifest.json`.
2. Взять **`jiraDevComponent`**.
3. Имя репо = префикс + `jiraDevComponent`.
4. Не копировать имя `ms-…` / `eco-…`.

| Место                               | Пример                      |
| ----------------------------------- | --------------------------- |
| GitLab / `gpb-manifest.name` (docs) | `docs-open-add-account`     |
| GitLab (src, без манифеста)         | `src-open-add-account`      |
| Путь в docs                         | `open-add-account/`         |
| Frontmatter                         | `service: open-add-account` |

**Мини-алгоритм:**

* один сервис → `docs-<jiraDevComponent>` (+ парный `src-<jiraDevComponent>`);
* несколько сервисов одной команды (общие владельцы и доступ) →
  `docs-<domain-slug>` (+ парный `src-<domain-slug>`). Неделимая логика в
  документации — доп. повод, не обязательна.

**Манифест и CODEOWNERS — для docs:** образец
[`gpb-manifest.json`](../../gpb-manifest.json); шаблон владельцев путей — в
[gitlab-settings §4](../../cookbook/analytics/gitlab-settings.md#4-approval-rules);
поля манифеста —
[gpb_manifest_guideline](https://gitlab.gboteam.ru/TEAM/team-configs/-/blob/master/gpb_manifest_guideline_team_info.md).

Чеклист заведения docs —
[гайд](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#новый-docs-репозиторий);
src —
[гайд § новый src](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#новый-src-репозиторий).

Открытый вопрос про `projectType` для docs — [§11](#11-куда-смотреть-дальше).

## 8. Как стыковать YAML в backend и markdown в docs-репо

### Разделение YAML и markdown

Файл API в YAML (OpenAPI / AsyncAPI — для программ и генерации кода) и текст для
людей (markdown) живут в **разных** репо. Связь — через идентификатор операции
(`operationId` / channel) и **матрицу** трассировки.

Процесс **без файла-замка** между репо (не нужен общий `contracts.lock`):

* одна Jira, парные MR;
* при смене смысла — **согласованный merge**: docs в `trunk`, код — в default
  branch репо кода
  ([ADR-0017](../../architecture/adr/0017-trunk-based-development.md) — целевое имя
  `trunk`;
  [git-workflow TBD](../../cookbook/analytics/git-workflow.md#долгоживущие-ветки--trunk-based-development-tbd));
* расхождения ловят дисциплиной MR + ревью.

### Обязательные правила стыковки

* Утверждённая копия YAML — **backend**; смысл метода — **markdown в docs**;
  связь — `operationId` / channel и **матрица**. Не копировать схемы полей из
  YAML в md.
* Смена смысла API → парные MR docs + backend и совместный merge. Только транспорт
  при том же `operationId` → чаще только backend.
* В FUN/SCR не разбирать поля API — отсылка на карточку метода / матрицу, не на
  прямую ссылку на файл YAML в GitLab.
* Чеклист для backend —
  [гайд](https://gitlab.gboteam.ru/ED/eco-kb/-/blob/master/analytics/analyst-docs-guide.md#api-в-backend).

```text
docs-репо                              backend-репо
карточка метода (md) ──operationId──►  адрес и поля метода в YAML
матрица ──operationId──► FUN / SCR
парный MR / одна Jira / совместный merge
```

### Сценарии «кто что меняет»

| Ситуация                    | Backend  | Docs                                              |
| --------------------------- | -------- | ------------------------------------------------- |
| Новое поле, поведение то же | MR: YAML | описание не обязательно                           |
| Новое поведение / метод     | MR: YAML | карточка + матрица (парный MR + совместный merge) |
| Новая FUN без API           | —        | FUN + матрица; merge с кодом FUN — совместно      |
| Релиз кода                  | tag в BE | docs ради релиза не меняют                        |

## 10. Чего не делать

* Держать весь SRS только в backend; считать docs навсегда единственным местом
  для YAML API; держать две главные копии одного YAML.
* Считать поле `description:` в YAML заменой описанию метода для людей;
  копировать схемы полей из YAML в markdown.
* Ставить из комплекта ссылки на «сырой» файл в GitLab; связывать FUN/SCR с API
  «по памяти» без матрицы.
* Требовать общий файл-замок (`contracts.lock`) или версию пакета API в docs как
  обязательную связку состыковки.
* Коммитить в docs remote сырьё, выгрузки, обёртки агентов или прочее вне
  [состава](#3-состав-целевого-docs-репо); ослаблять `.gitignore`, чтобы пустить
  IDE-обёртки.
* Держать черновики и Confluence-выгрузки в `docs-…` вместо парного `src-…`.

### Временное vs целевое размещение api/

> **Направление пересматривается (2026-08-02):** обсуждается модель
> «спецификация — неотъемлемая часть комплекта сервиса + реестр опубликованных
> спецификаций экосистемы» (ссылки на операции из SRS, симметричная адресация).
> Цель «утверждённый YAML только в backend» до этого решения не исполнять;
> таблица ниже — прежняя гипотеза.

| Этап                    | YAML                                    | Описание методов  |
| ----------------------- | --------------------------------------- | ----------------- |
| Сейчас (восстановление) | Допустима временная копия в docs        | Частично          |
| Цель (пересматривается) | Утверждённый YAML **только в backend**  | Markdown в docs   |
| После переноса          | YAML из docs убрать / «истина: backend» | Markdown остаётся |
