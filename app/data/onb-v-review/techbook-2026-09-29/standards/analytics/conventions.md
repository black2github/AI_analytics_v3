## 1. Источники и их приоритет

Сырьё для reverse лежит в **src-репо** (или в локальных клонах кода рядом). В **docs remote** сырья нет
([repo-topology §3](repo-topology.md#3-состав-целевого-docs-репо)). Типичный приоритет при reverse:

<!-- markdownlint-disable MD013 -->
| Приоритет | Источник                           | Роль                                                                                                                                                                                                        |
| --------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1         | Выгрузка Confluence в **src-репо** | **Первичный источник SRS.** Какой срез актуален — в профиле src (§1.1); при новой выгрузке обновляют профиль и прогоняют изменившиеся разделы через `verify-vs-sources`                                     |
| 2         | Клоны репозиториев разработки      | Только выгрузка API-контрактов (`openapi.yaml`, `asyncapi.yaml`) для `docs/api/` (§5.1) и (временно) reverse data-model/rbac. Для остальных артефактов SRS код не используется. Список репо — в профиле src |
| 3         | Figma / UX-выгрузки в src          | Экраны и UX: состав полей, состояния, тексты                                                                                                                                                                |
| 4         | Сырые данные (raw) в src           | Staging до нормализации. **Не** источник фактов для SRS, пока материал не нормализован                                                                                                                      |
| —         | Прочие черновики в src             | Только как подсказка «где искать», не как источник фактов                                                                                                                                                   |
<!-- markdownlint-enable MD013 -->

Правила:

- Актуальна только выгрузка, указанная в профиле src (§1.1). Прочие срезы в src — устаревшие: факты из них **не берём**.
- Код: аналитик клонирует репозитории разработки локально (отдельные клоны рядом с docs/src); читать файлы напрямую из
  рабочего дерева. Zip-архивы и `unzip` **не используются**.
- Факты в чистовик `<service-id>/` не берутся из raw, пока материал не нормализован. Расхождение источников — в
  открытых вопросах (§6), реестр при необходимости ведут в **src**.
- Сырьё в src — **только чтение** для reverse (кроме обновления профиля и новых выгрузок по процессу команды). В
  **целевой docs remote** сырья нет.
- Расхождение между источниками — не повод выбирать «на глаз»: фиксируем как открытый вопрос (§6) и выносим на решение
  аналитика.
- Факт, которого нет ни в одном источнике, — не выдумываем. Фиксируем как открытый вопрос (§6).

**SRS адаптируется только из Confluence.** Содержимое страниц актуальной выгрузки переносится в формат комплекта без
сверки с кодом. Код используется единственным образом — как источник авто-выгруженных API-контрактов для `docs/api/`
(§5.1).

**Исключение (временное, до отдельного решения о границе логического и физического уровней):** при восстановлении
документации **существующего** сервиса модель данных и ролевая модель допускают reverse из кода (скиллы
`create-data-model`, `create-rbac`) — Confluence для этих артефактов исторически неполон. Для всех остальных артефактов
SRS код источником не является.

### 1.1. Профиль источников в src

**Назначение:** маршрутизатор источников сервиса в **src-репо** — пути выгрузок, метка `version`, таблица клонов кода,
фильтр legacy. Читается **до** reverse; в переносимый комплект не входит. Состав src не нормируется; профиль — удобный
ориентир (часто `README.md` в корне src). Шаблон — [`sources-readme.md`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/blob/master/_meta/templates/sources-readme.md) в каноне (адаптировать под src-репо).

Обязательные блоки профиля:

| Блок                       | Содержание                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| `service-id`               | Идентификатор сервиса                                                                     |
| Актуальная метка `version` | Необязательно: строка среза для YAML-шапки документов, если команда её ведёт              |
| SRS (Confluence)           | Путь к выгрузке в src, дата                                                               |
| Код                        | Таблица: GitLab URL, локальный путь клона, ветка/commit, назначение                       |
| Legacy-фильтр              | Признаки отсечения (§3)                                                                   |
| Разметка частей            | Только у сервиса с подсервисами (§3.1): тег/ветвь выгрузки → часть (код) / вне Экосистемы |
| Доп. источники             | Опционально                                                                               |

**Несколько сервисов** (доменный `src-<domain-slug>`): профиль каждого сервиса — секция `## Профиль: <service-id>` или
отдельный файл в src. Парный docs — [repo-topology.md](repo-topology.md) §5–§6.

**Когда создавать и обновлять:** до первого reverse; при новой выгрузке Confluence; при смене среза кода; при уточнении
legacy. Без заполненного профиля агент останавливается на шаге «собери источники» (`create-artifact`).

## 2. Версия и метка среза

Описываем **актуальную версию сервиса** по последней выгрузке Confluence, указанной в профиле src.

- Поле `version` во frontmatter (**метка среза** сервиса) — необязательное: в новых комплектах не
  используется, из шаблонов и профиля источников убрано; в ранее выпущенных комплектах остаётся как есть,
  волна удаления не проводится. Какая метка актуальна, какие устаревшие документы подлежат ревизии и какой
  срез кода соответствует актуальному Confluence — в профиле src (§1.1).
- В переносимом `README.md` корня комплекта актуальная метка и краткие границы версии фиксируются **самодостаточно** (без
  ссылок на eco-techbook / eco-kb / toolkit и профиль src).
- Не доверять API-контрактам в `api/`, если они выгружены из устаревшего среза кода: сверить с актуальным срезом из
  профиля src и перегенерировать при расхождении.

## 3. Границы контура сервиса

Документируем **один целевой контур** сервиса (`service-id` в пути `<service-id>/` и во frontmatter).

- Legacy / старый формат / параллельный устаревший сервис в том же пространстве источников **не переносим** в комплект.
- Признаки отсечения (типы документов, префиксы страниц, таблицы БД, ветки кода и т.п.) — в профиле src (§1.1), не в
  этих конвенциях.
- Если без упоминания legacy текст теряет смысл — фиксируем открытый вопрос (§6), а не тащим legacy в чистовик.
- Временно отключённые способности целевого контура описывают как «временно недоступна/отключена», не как «неактуальна».
  (§5.4)

### 3.1. Подсервисы крупного сервиса

Крупный сервис из слабосвязанных подсервисов с общей частью ведётся **одним комплектом**: одна запись каталога
сервисов, единые матрица трассировки, открытые вопросы и реестры ID. Часть сервиса кодируется в путях и в
идентификаторах — слот части, правила в «Схеме ID» (§5).

- **Путь.** Каталог части — сразу после `srs/`: `srs/<подсервис>/<тип>/…` (kebab-case слаг; для родственных частей —
  групповой префикс: `qr-c2b`, `onb-client`); общая часть — `srs/shared/`. Сервис без подсервисов (эталон) каталогов
  частей не имеет. Вложенность частей запрещена: иерархия «сервис → сервисы → подсервисы» раскладывается в плоский
  список частей с групповым префиксом слага, группы описываются в `service-vision.md`.
- **Коды частей** объявляются один раз таблицей в `README.md` корня комплекта (колонки «Код», «Каталог», название);
  код общей части — `SHR`. Идентификаторы артефактов части несут слот кода (`FUN-DS-SYS-01`, `ENT-SHR-001`),
  нумерация внутри слота своя. Документы уровня сервиса (`rbac.md`, `platform-functions.md`, `glossary.md`,
  `service-vision.md`, матрица трассировки, открытые вопросы) лежат в корне комплекта и слота не несут.
- **Однофайловые слоты уровня части** — по одному на часть, включая общую: `srs/<часть>/process/status-model.md`
  (`SM-<ЧАСТЬ>-000`), `srs/<часть>/ntf-notification.md` (`NTF-<ЧАСТЬ>-000`, записи `NTF-<ЧАСТЬ>-NN`). Агрегировать
  статусные модели частей в общий файл не требуется.
- **Разметка** «тег/ветвь выгрузки → часть (код) / вне Экосистемы» — декларация в профиле источников (§1.1):
  предлагает планировщик, утверждает аналитик; соответствия «источник → каталог части» и «слот → каталог» проверяет
  инструмент проверки. Зона «вне Экосистемы» (иной контур исполнения, например PCI DSS-виджеты) в комплект не
  входит — ведётся мини-комплектом рядом, паспорт границы обязателен.
- **Порядок миграции:** общая часть → базовые части → зависимые от них.

## 4. Язык и стиль

Детализация нотации записи — условия и чистота условия, `=`/`==`, стрелки, словарь UI-типов полей, скобки и кавычки,
многострочные ячейки — единый источник [notation.md](notation.md); правила ниже — базовые.

- Язык документов — **русский**. Технические идентификаторы (имена полей, статусы, эндпоинты) — как в коде, без
  перевода.
- **Литералы источника переносятся дословно.** Технические идентификаторы, коды статусов и ошибок, числовые значения,
  тексты-константы (названия форм и кнопок, тексты сообщений) переносятся буква в букву — вместе со служебными
  символами, если они отображаются пользователю. Такой литерал нельзя ни **изменять** (в том числе исправлять опечатку
  или приводить к «правильному» написанию), ни **заменять обобщённым описанием** («с ошибкой», «некорректно»,
  «прекращается»). Опечатка в источнике или два разных написания на разных страницах — это расхождение: фиксируется
  вопросом (§6) и решается аналитиком, а не правится молча. Исключение — **имена сущностей и атрибутов модели данных**:
  они берутся из модели (§5), а не из текста источника.
- **Язык — понятный бизнес-аналитику.** Читатель документов — аналитик, который раньше не погружался на физический
  уровень системы. Технические слои (API, взаимодействие фронт↔бэк, форматы данных) описываем так, чтобы их мог понять и
  отревьюить аналитик без опыта разработки: сначала смысл («что происходит и зачем»), потом техническая точность
  (эндпоинт, поля, коды). Жаргон без пояснения — не используем.
- Описываем **действия и порядок шагов** (глаголы, связи, условия), а не только статичные перечни. Критерий: другой
  человек или ИИ-агент воспроизведёт результат по описанию.
- **Логика — конструкцией Если/то/иначе (во всех документах комплекта).** Везде, где описывается поведение или условная
  логика — функции, экранные формы (события, кнопки), процессы («Детали шагов»), контроли (логика проверки), печатные
  формы (правила заполнения), нотификации и любой другой тип, — ветвления записываются словами **Если** / **то** /
  **иначе** / **иначе если**, выделенными жирным, каждое условие и исход с новой строки; многошаговый сценарий —
  нумерованными шагами. Исключение — компактные табличные форматы, где ветку задаёт колонка (например, «Далее: `условие
  → шаг`» в таблице шагов процесса): там прозаическая конструкция не требуется.
- **Вызовы смежных систем не сворачиваются (во всех документах).** Обращение к чужому контракту — ссылкой на
  карточку `CALL` с указанием передаваемых параметров запроса и обработки ответа; к платформенной функции/проверке
  ЭКО — ссылкой на запись `PLT` (`srs/platform-functions.md`); граница `CALL`/`PLT` — §5.1.2. Если карточки/записи нет (постановки нет в выгрузке) — упоминание
  цели по имени (без выдуманного ID) и долг: запись в открытых вопросах (§6) и строка в матрице трассировки. Файлы и
  записи чужих типов из чужого захода не создаются (границы скоупа `create-artifact`); карточку-минимум своего типа
  создаёт только заход этого типа (определение — §5).
- **Широкие текстовые колонки в таблицах.** Реестры и сводные таблицы (обзорные перечни с ID) — **без** широкой
  прозаической колонки: детальные правила и логика выносятся в подразделы или карточки. Таблицы дословного контента
  (тексты сообщений, подстановочные таблицы печатных форм, содержание шагов процесса) — **ровно одна** широкая колонка.
  Больше одной широкой колонки не бывает ни в одной таблице.
- Требования — **атомарные** (одно требование = одна проверяемая мысль) и **проверяемые** (понятно, как убедиться, что
  выполнено).
- Персональные и конфиденциальные данные в примерах — **обезличиваем** (вымышленные ИНН, ФИО, номера счетов).

## 5. Стандарт файла документа

**Корень комплекта.** Комплект сервиса — это каталог, в котором лежат
`README.md`, `service-vision.md`, `glossary.md`, `traceability-matrix.md` и
каталоги `brd/`, `srs/`, `api/`. В docs-репозитории одного сервиса корень
комплекта — корень репозитория; в репозитории нескольких сервисов — папка
`<service-id>/` ([repo-topology §3](repo-topology.md#3-состав-целевого-docs-репо)).
Все пути в этом документе даны от корня комплекта; обозначение `<service-id>/`
в путях означает корень комплекта. Промежуточный каталог `docs/` не создаётся.

**Инварианты комплекта** (проверяются ревью и инструментом проверки; исключений
нет):

- в корне комплекта обязательно лежат `service-vision.md` (`VIS-001`) и
  `glossary.md` (`GLO-001`) — входные документы обоих слоёв (§5.4);
- `service` во frontmatter и `<service-id>` в путях — только kebab-case и
  равен полю `jiraDevComponent` манифеста кода
  ([repo-topology §6](repo-topology.md#6-именование-репозиториев));
- базовые контракты внешних (смежных банковских) АС живут только в
  [docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts);
  в комплекте сервиса — только карточки вызова `CALL` (§5.1.1);
- слой `brd/` обязателен для продуктовых сервисов; для платформенных
  (`is_platform: true` в каталоге сервисов) его роль выполняет
  `service-vision.md` с перечнем потребителей и обязательств — см. §5.4.

Каждый документ комплекта начинается с YAML-шапки в начале файла (frontmatter):

<!-- markdownlint-disable MD013 -->
```yaml
---
id: <уникальный ID документа>       # см. схему ID ниже
title: '<наименование документа>'   # ОПЦИОНАЛЬНО, но в reverse обязателен к переносу: дословное наименование из title главной страницы-источника
type: data-model | process | agent | function | screen-form | print-form | control | notification | rbac | api-contract | glossary | vision | external-integration | internal-contract | platform-function | feature | use-case | business-rules
service: <service-id>
version: <метка-среза>             # ОПЦИОНАЛЬНО; в новых комплектах не используется (§2)
confluence_page_ids: ['<id>', …]    # ОПЦИОНАЛЬНО, только reverse: ID страниц-источников Confluence; ВСЕГДА список (даже из одной), главная страница — первой
---
```
<!-- markdownlint-enable MD013 -->

- **`title`** — собственное наименование документа в языке предметной области; **постоянный** атрибут (в отличие от
  `confluence_page_ids` к миграции не привязан и после переезда остаётся). В reverse переносится ДОСЛОВНО из `title`
  главной страницы-источника, включая сервис-префикс в квадратных скобках, — при переименовании файлов в слаги это
  единственный носитель исходного наименования; тихая потеря title = находка. В forward наименование задаёт аналитик.
  Для функций наименование отражается в ролевой модели — расхождение `title` и имени в RBAC является дефектом.
- **`confluence_page_ids`** — трассировка миграции: значения — из поля `confluence_page_id` frontmatter
  страниц-источников выгрузки. Всегда YAML-список (смешение «строка или список» ломает
  разбор скриптами);
  документ из нескольких страниц
  (файл функции + «Параметры вызова», реестры README, dictionaries) перечисляет все, главная первой; файлы-части одной
  страницы (вкладки ЭФ) несут одинаковый одиночный ID. В forward-режиме поле опускается; ID не выдумывать. Это поле —
  единственное допустимое упоминание источников в документе (служебные поля YAML-шапки,
  не текст; см. правило происхождения
  ниже).
- **`id` или `partOf` — ровно одно из двух.** Самостоятельный типизированный документ несёт `id`. Файл-часть составного
  документа (физическое продолжение документа, у которого уже есть корневой файл с `id`, — например `cards-<slug>.md`
  каталога `control/`) вместо `id` несёт `partOf: <id корневого документа>`; остальные поля
  (`type`/`service`/`version`) — те же, что у корневого файла. Собственных строк в реестре ID матрицы у файла-части нет.
- **Критерий выбора для файла-части: суб-ID или `partOf`.** Решается при заведении составного документа вопросом-тестом:
  «на что будут ссылаться извне этого документа?» **Если** на часть ссылаются извне **как на целое** — ссылка ведёт на
  файл части, и часть сама фигурирует единицей в других документах, матрице трассировки, задачах разработки или
  тест-кейсах (пример — вкладка экрана: функция открывает именно вкладку, у вкладки своя строка покрытия), **то** часть
  — самостоятельный документ-адресат: получает собственный суб-ID (`SCR-CL-NN.K`), frontmatter с `id` и строку в реестре
  ID. **Иначе** — то есть **если** извне ссылаются только на **отдельные записи внутри файла**, каждая из которых уже
  имеет собственный стабильный ID (карточка контроля `CTL-NNN`, операция `метод+путь`, термин-якорь глоссария), а на
  файл целиком не ссылается никто, — файл несёт `partOf`: это **физическая упаковка** записей, в реестрах регистрируется
  его содержимое, не файл. Следствия: при `partOf` перекладка записей между файлами не ломает ссылок (они ведут на ID
  записей), поэтому нарезка на файлы — вопрос удобства; при суб-ID файл сам адресат, его перенос или слияние — изменение
  документа. Пограничный случай — асимметрией: сначала проверить, нельзя ли адресовать конкретную запись; если
  адресат-целое действительно нужен — суб-ID давать сразу при заведении (добавить документный ID позже — правка реестра
  и переучивание внешних ссылок, лишний суб-ID почти ничего не стоит).
- **Поле `status` во frontmatter не используется.** Акцепт человеком (HITL) — через
  MR / Jira, не полем в файле. Кто пишет, кто ревьюит, кто акцептует — ведём
  вне документов; все требования комплекта считаются актуальными и реализованными. (Плановые/заглушечные строки, если
  нужны на этапе построения, фиксируются в матрице трассировки, §5.3, а не полем документа.) **Статус вычисляется из
  git:** артефакт **акцептован**, когда его MR прошёл approve и слит в `trunk`; в ветке — черновик. Иные статусные
  словари (`draft`, `план`, `review` и т. п.) не вводятся.
- **Заголовок документа (H1)** — название артефакта **без названия сервиса**: сервис задают frontmatter `service` и путь
  `<service-id>/` (например, «Статусная модель заявки», «Ролевая модель и доступ (RBAC)»). Исключений нет (решение
  2026-08-02): H1 существующих `service-vision.md`, `glossary.md`, `data-model/README.md` выравниваются ближайшим
  docs-MR.
- Имена файлов в `<service-id>/` — латиница, **kebab-case** (строчные латинские буквы, слова через
  дефис). **Нумерованный артефакт** (документ с ID из схемы ниже): имя =
  `<id-строчными>-<короткое-название>.md`, например `ent-001-request.md`,
  `fun-cl-06-sign-request.md`. **Реестры** (`dictionaries.md`, `traceability-matrix.md`), `README.md` и
  **однофайловые документы** (`rbac.md`, `process/status-model.md` — единственные в своём типе, см. схему ID) и файлы
  каталога `control/` (`README.md`, `cards-<slug>.md`) — фиксированные имена без ID-префикса (§5.3).
- Один документ — одна тема. Несколько связанных документов — папка.

**Комплект в forward-стиле (как будто написан до кода): без ссылок на сырьё.** Документы в
`<service-id>/` должны выглядеть так, будто написаны *до* появления кода:

- никаких ссылок на Confluence (pageId, URL), на файлы кода, классы, клоны репозиториев разработки и на **src-репо**;
- **комплект переносим**: комплект сервиса (SRS и API) целиком переносится в целевой репозиторий, поэтому ссылки и
  текстовые отсылки за пределы комплекта сервиса (на eco-techbook / eco-kb / toolkit, конвенции проекта, src-репо,
  README рабочего репозитория, другой docs-репо) не допускаются. Исключение: в одном docs-репо относительные ссылки
  на соседний `<service-id>/` допустимы; при выносе сервиса их переписывают или заменяют карточкой интеграции
  ([repo-topology §5](repo-topology.md#5-несколько-docs-репо)). Общие для комплекта ограничения (границы сервиса,
  версия) фиксируются самодостаточно в `README.md` корня комплекта;
- ссылки — на документы своего комплекта; в том же docs-репо — также относительные ссылки на соседний
  `<service-id>/`;
- **ссылки на модель данных (ENT/EXT) — единообразно во всём комплекте**: первое упоминание сущности в документе —
  полная ссылка `[ENT-NNN <название>](ent-…-….md)` (для платформенных — `[EXT-NNN <название>](dictionaries.md)`); все
  последующие упоминания — короткая ссылка `[ENT-NNN](…)`. Каждое упоминание — ссылкой, голый ID без ссылки не
  используется. **Атрибут сущности** — точечной нотацией: `[ENT-NNN](…).«Атрибут»` (название атрибута — как в модели
  данных); идентификатор в точечной нотации — всегда короткой ссылкой, в том числе в плотных перечислениях (формулы
  конкатенации, длинные таблицы, дословные тексты сообщений). Запись атрибута без идентификатора сущности (просто
  `«Атрибут»`) не используется;
- **ссылки на контроли, интеграции и платформенные функции — всегда ID + название**, во всех упоминаниях (не только в
  первом): контроль `[CTL-NNN <название>](…)`, группа контролей `[CTL-GRP-N <точка применения>](…)`, вызов чужого
  контракта `[CALL-EXT-NNN <название>](…)` / `[CALL-INT-NNN <название>](…)`, платформенная функция/проверка `[PLT-NNN <название>](…)`. Голый идентификатор без
  названия и без ссылки не используется. (Отличие от ENT/EXT, где повторные упоминания — короткой ссылкой: у
  CTL/CALL/PLT название несёт смысл проверки/вызова, важный читателю по месту.)
- артефакты реализации, которые не проектирует аналитик (имена классов, пути в коде), в SRS не включаются. Физическую
  модель (таблицы, имена и типы полей) аналитик **проектирует сам** — она в SRS остаётся;
- **технический журнал событий заявки (аудитный event-лог) в модель данных не включается**: сущность вида «События
  заявки» (таблица `*_event`, поля `event_type`/`params`/`parameters`, платформенный `EventEntity`) и связанный с ней
  справочник «Типы событий заявки» — техническая инфраструктура аудита, которую аналитик не проектирует. Такую сущность
  и её справочник не выгружать из кода и не описывать в SRS (историзация статусов, значимая для аналитики, ведётся
  отдельной сущностью «История изменений заявки»);
- происхождение содержимого (какие страницы/файлы выгрузки использованы) фиксируется в сообщениях коммитов и MR, а не в
  ТЕКСТЕ документов. Исключение — служебные поля YAML-шапки `confluence_page_ids` (§5,
  схема frontmatter): это
  трассировочный ключ, не ссылка; в теле документа упоминаний источников по-прежнему нет.
- комплект в forward-стиле (как будто написан до кода): документы в `<service-id>/` должны выглядеть так, будто написаны
  *до* появления кода — никаких ссылок на Confluence, на файлы кода, классы, клоны репозиториев и на **src-репо**;
  ссылки — на документы своего комплекта; в том же docs-репо — также относительные ссылки на соседний
  `<service-id>/`;

FMT-P3. Правила авторинга — в шаблонах и скиллах, не в README комплекта.
Полные правила формата (как оформлять таблицы шагов, диаграммы, событийную модель,
карточки контролей, реестры и т. п.) — **единый источник в шаблонах**
[`_meta/templates/`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/tree/master/_meta/templates) **и скиллах** [`_meta/skills/`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/tree/master/_meta/skills)
канона (репозиторий docs-o2new); в документах
комплекта они не дублируются. В `README.md` раздела комплекта (data-model,
control, contract-call, process, api и др.) помещается только **короткая
читательская легенда** — как читать раздел и его обозначения, а не как его писать.
README не делают «самодостаточным» переносом правил авторинга; при этом (см.
переносимость выше) README, как и любой документ комплекта, **не ссылается** на
репозитории общих норм (eco-techbook, eco-kb, канон docs-o2new) — легенда формулируется
своими словами внутри комплекта.

### Схема ID

Статус: **принята** (решение 2026-08-02); изменения — обычным MR в этот файл.

Формат: `<PREFIX>-<NNN>`, сквозная нумерация в рамках типа, ID стабильны (не переиспользуются после удаления).

**Выдача ID (единое правило; скиллы своих правил не вводят, только ссылаются сюда):**
следующий свободный номер в скоупе нумерации типа (скоуп — тип; для `FUN`/`SCR` —
контур; для `EXTINT`-base — папка АС) по **реестру выданных ID** матрицы
трассировки (§5.3). Каталог файлов и упоминания в текстах документов источником
выдачи НЕ являются. Выданные и погашенные номера не переиспользуются; погашение —
строка-примечание в реестре («выдан ошибочно, не переиспользовать»). ID выдаёт
только заход своего типа: упоминание ещё не созданного артефакта — по имени, без
ID (границы скоупа; инцидент file-storage 2026-08-11: EXT-002 «выдан» упоминанием
в тексте процесса без строки реестра — и два захода модели данных разрешили номер
по-разному).

| `BR-NN`                | Атомарное бизнес-правило (RuleSpeak), документ `brd/business-rules.md` (`BR-000` — сам документ)                       |
| `ТР-NN`                | Таблица решений (DMN) в `business-rules.md`                                                                            |
<!-- markdownlint-enable MD013 -->

**Слот части сервиса в идентификаторе.** У сервиса, который ведётся одним
комплектом из нескольких подсервисов (у каждого свой каталог `srs/<подсервис>/`,
общая часть — `srs/shared/`), идентификатор нумерованного артефакта несёт слот
части сразу после префикса: `<PREFIX>-<ЧАСТЬ>-…`, например `FUN-DS-SYS-01`,
`SCR-DS-CL-03`, `ENT-SHR-001`, `NTF-DS-000`. Правила:

- слот допустим только у сервиса с подсервисами; у сервиса без подсервисов
  идентификаторы без слота (`FUN-CL-01`);
- коды частей объявляются один раз таблицей в `README.md` корня комплекта:
  код — каталог подсервиса — название; код не длиннее четырёх латинских
  букв, код общей части — `SHR`;
- слот соответствует каталогу, в котором лежит артефакт, по этой таблице;
  инструмент проверки сверяет слот с каталогом и с таблицей;
- документы уровня сервиса (`VIS-001`, `GLO-001`, `rbac.md`,
  `platform-functions.md`, матрица) слота не несут;
- нумерация внутри слота своя (`FUN-DS-SYS-01` и `FUN-MB-SYS-01` — разные
  артефакты); при переносе артефакта между частями действует правило снятого ID.

Дополнительно для экранных форм и функций:

- **Экран с вкладками** — папка: `README.md` (ID экрана, обзор и перечень вкладок) + файл на каждую вкладку с суб-ID
  `SCR-…-NN.K` (имя файла `scr-…-nn.k-<название>.md`), например `scr-cl-03-request-edit/scr-cl-03.1-account.md`.
- **Внутренние идентификаторы экранной формы** (стабильны, для ссылок из задач и тест-кейсов, уникальны в пределах
  документа): `FLD-N` — правило поля, `EV-N` — событие, `B-N` — кнопка, `MSG-N` — сообщение. Нумерация источника (2.1.6
  и т.п.) в идентификаторы не переносится. Детали формата — [шаблон `screen-form.md`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/blob/master/_meta/templates/screen-form.md) в каноне.
- **Политика внутренних идентификаторов**: только латиница (`A–Z`, цифры, дефис, точка) — кириллица в ID запрещена;
  префикс — минимум два символа и не целиком из букв, совпадающих по начертанию с кириллическими (иначе
  опечатка-кириллица неотличима глазом и не ловится поиском); ID стабильны, не перенумеровываются и не переиспользуются.
  **Снятый ID (артефакт удалён или сменил тип) не удаляется из реестра ID матрицы** — строка остаётся с пометкой
  «снят <дата>: <причина/преемник>» и файлом «—»: только так ID занят навсегда и защищён сторожем дублей; удаление
  строки открывает переиспользование (прецедент 2026-08-30: SCR-CL-05 снят при смене типа на FUN-CL-01, строка
  удалена — следующий заход выдал SCR-CL-05 новой ЭФ, один ID стал значить разные артефакты в истории комплекта).
  Занятыми считаются и ID, упомянутые в трассировках («Бывшие группы: …» после консолидаций), даже если строки
  реестра у них никогда не было: новый артефакт с таким номером делает историческую пометку двусмысленной
  (прецедент 2026-08-31: STS-02 выдал новым группам CTL-GRP-19…21, значившиеся «бывшими» в трассировке GRP-15
  cc-card-issue; перенумерованы в 34…36). Новые ID выдаются из диапазона, свободного и от реестра, и от трассировок.
  Задокументированное исключение — `B-N` (кнопка): замена связана с судьбой раздела кнопок и выполняется вместе с ней. В
  ранее выпущенных комплектах до каскадной замены встречаются прежние `П-N`/`Е-N`/`М-N` — при доработке документа они не
  переименовываются точечно (только целиком с комплектом, чтобы не смешивать схемы в одном документе).
- **Функция — всегда один файл**: подстраницы источника «Параметры вызова …» переносятся разделами в файл функции.
- **Карточка-минимум** — файл или запись СВОЕГО типа, создаваемые заходом этого типа, когда постановка вне выгрузки:
  frontmatter и раздел «Назначение», содержательное описание впереди. Из чужого захода не создаётся — там вместо неё
  долг в открытых вопросах и матрице (границы скоупа `create-artifact`). Отдельного поля статуса нет; причина неполноты,
  если нужна, поясняется прозой в матрице трассировки (раздел «Артефакты вне трассировки»).

Детализация схемы (атрибуты, вложенность) — в шаблонах типов [`_meta/templates/`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/tree/master/_meta/templates) канона.

**Шаблоны** `_meta/templates/` **— не документы комплекта.** В них не оформляют рабочие markdown-ссылки
`[текст](путь)` — только указания, где ссылка понадобится в целевом документе `<service-id>/`: подсказка `<ссылка
[текст](путь)>`. Имена файлов без ссылки — в backticks (`dictionaries.md`, `entity-….md`).

## 5.1. Слои документации и API

- **SRS (**`srs/`**)** адаптируется из актуальной выгрузки Confluence (§1): содержимое страниц переносится в формат
  комплекта. С кодом не сверяется.
- **Маппинг на структуры данных API (модели запроса/ответа, DTO) и поля API не ведётся**:
  экранные формы не описывают
  вызовы методов и поля структур ответа/запроса API.
- `api/` — контракты, выгруженные из кода (read-only источник — локальные клоны разработки по таблице из профиля
  src; ориентир [`_meta/asyncapi/overrides-<service-id>.md`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/tree/master/_meta/asyncapi)):
  - REST: `api/rest/<module>.yaml` + реестр `api/rest/README.md`;
  - Async: `api/<module>-asyncapi.yaml` (AsyncAPI **3.1.0**, по одному файлу на микросервис/модуль) + реестр
    `api/async/README.md` + sequence `api/async/async-api-sequence.md`;
  - правила генерации AsyncAPI — [`_meta/asyncapi/generation-rules.md`](https://gitlab.gboteam.ru/EAS/docs-o2new/-/blob/master/_meta/asyncapi/generation-rules.md), сервисные
    фильтры — `_meta/asyncapi/overrides-<service-id>.md`;
  - устаревший единый `asyncapi.yaml` не используется.
  Контракты вручную не пишутся и не адаптируются (кроме явных правок через overrides и delta-режим скилла).
- **В телах документов SRS и в YAML API связей между слоями нет.** Трассировка API ↔ SRS — только в матрице (§5.3 п.7).

### 5.1.1. Слой вызовов чужих контрактов (`contract-call`)

Карточка вызова описывает обращение сервиса к ЛЮБОМУ контракту, которым он не владеет; карточка устроена одинаково,
различается только владелец базового контракта. Два уровня:

1. **Базовый контракт** — у владельца вызываемого интерфейса (протокол, параметры, ответы, примеры; не зависит от
   сервиса-потребителя — без ENT/EXT сервиса, без OQ, без относительных путей в чужой docs-репо):
   - внешняя (смежная банковская) АС — общий репозиторий
     `[docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts)` (`EXTINT-<AS>-NNN`);
   - другой сервис Экосистемы — `internal-contract/` его комплекта (`INTC-NNN`, §5.1.3);
   - платформенный метод с опубликованной спецификацией — документация платформы (без спецификации — `PLT`, §5.1.2).
2. **Как сервис вызывает (карточка вызова)** — `<service-id>/srs/contract-call/`: назначение вызова, процессы и
   шаги, маппинг ENT, транспорт, обработка ответов. Два подкаталога по владельцу базового контракта:
   `external/` — вызовы внешних АС (`CALL-EXT-NNN`, реестр `CALL-EXT-000`, файлы `call-ext-NNN-<slug>.md`);
   `internal/` — вызовы внутри Экосистемы: методы других сервисов и платформенные методы со спецификацией
   (`CALL-INT-NNN`, реестр `CALL-INT-000`, файлы `call-int-NNN-<slug>.md`). Нумерация подтипов независимая;
   общий README-реестр каталога — `CALL-000`. В шапке карточки — ссылка на базовый контракт.

Принципы:

- Ссылки **между** репо — только абсолютный GitLab URL; внутри репозитория базового контракта на `examples/` —
  относительные.
- Сопутствующие файлы (sidecar: JSON/XML/XSD/WSDL): только полезные данные обмена
  (payload); сценарий — в §5 карточки и в имени файла, не комментариями в sidecar.
- ID базового контракта внешней АС: `EXTINT-<AS>-NNN` (нумерация внутри папки АС); ID карточки вызова:
  `CALL-EXT-NNN` / `CALL-INT-NNN` (нумерация сервиса, независимая по подтипам). Frontmatter базового контракта —
  без `service`; карточка вызова — с `service: <service-id>`.
- Не включать в CALL: функции класса `PLT` (граница — §5.1.2), legacy, отсылки к OQ в комплекте.
- vs `glossary.md`: термины систем; в базовом контракте — **чем и как** обмениваемся; в карточке вызова — как это
  делает сервис.

Формат карточек, дерево репо, «Потребители», чек-листы — шаблон

### 5.1.2. Слой platform-functions

- **Путь:** `<service-id>/srs/platform-functions.md` — единый документ-реестр (`PLT-000`, `type:
  platform-function`). Функции и проверки **платформы ЭКО**, которые сервис вызывает, но реализует вне его контура
  (проверка сертификата ЭП, контроль доступности функций, онбординг, резервирование счёта, обновление сведений, проверка
  участия в маркетинговой кампании и т.п.).
- **ID:** префикс `PLT`; карточки — H3-подразделы `PLT-NNN. <название>` в том же файле (реестр-таблица + карточки с
  якорями для ссылок). Тип записи — из закрытого словаря: `функция` | `проверка` | `экран` (**экран** — универсальная
  платформенная ЭФ, переиспользуемая сервисом и единая для многих типов заявок ЭКО; собственной ЭФ сервиса не описывается).
- **Отграничение:** не `CALL` (вызов опубликованного контракта, §5.1.1: платформенный метод СО спецификацией — карточка
  `CALL-INT`; `PLT` — функциональность платформы БЕЗ опубликованной спецификации) и не `CTL` (проверки данных заявки внутри
  сервиса). Платформенный контроль доступа (например, доступность функций пользователю) — это `PLT`, а не `CTL`.
- **Записи — карточки-минимум** (назначение, где используется), пока постановка платформенной функции вне выгрузки;
  создаёт их только заход типа `platform-function` — из чужих заходов вместо записи остаётся долг (границы скоупа).
  Пробел — как открытый вопрос (§6).
- **Ссылки:** из экранов, функций, процессов — `[PLT-NNN <название>](platform-functions.md#…)` (всегда ID + название,
  §5).

### 5.1.3. Слой internal-contract (постановка контрактов собственных методов)

- **Семантика имён:** internal/external — относительно границы ЭКОСИСТЕМЫ ДБО, не сервиса. Все микросервисы ДБО —
  внутренний контур; «внешние» системы — за пределами Экосистемы (смежные АС банка и внешний мир).
- **Путь:** `<service-id>/srs/internal-contract/` — карточки контрактов методов, которыми ВЛАДЕЕТ сервис
  (README-реестр `INTC-000`, карточки `intc-NNN-<slug>.md`, sidecar-примеры в `examples/`).
- **Два уровня, граница как у модели данных:** internal-contract — ПОСТАНОВКА (из Confluence, зона аналитика);
  `api/` — РЕАЛИЗАЦИЯ (YAML авто-выгрузкой из кода, зона разработки, §5.1). Расхождение уровней — открытый
  вопрос команде; при переходе на api-first карточки — источник description-полей контракта, не конкурент YAML.
- **ID:** префикс `INTC` (схема ID §5). Ссылки SRS → `INTC-NNN` — штатные (процессы и функции ссылаются на карточку
  метода вместо текстового упоминания); карточка на процессы/функции не ссылается — трассировка «метод ↔ SRS» в
  матрице (§5.3 п.7: до появления YAML операции таблицы «API ↔ SRS» — карточки INTC).
- **Межсервисные вызовы внутри Экосистемы:** контракт — в internal-contract сервиса-ВЛАДЕЛЬЦА; потребление другим
  сервисом — карточка `CALL-INT-NNN` в `contract-call/internal/` его комплекта (§5.1.1; решение 2026-08-20, закрыло прежнее
  «в проработке»).
- **Шаблон и правила переноса** — [internal-contracts.md][intc-template].

## 5.2. Настраиваемые параметры

Настраиваемые параметры, которые использует сервис, фиксируются **вместе со значениями** в документации сервиса (раздел

## 5.3. Трассировка требований

Цель — комплект, читаемый ИИ-агентами: связи между артефактами собраны в одном месте
(удобном для скриптов и поиска), покрытие проверяемо.

**Матрица трассировки** — `<service-id>/traceability-matrix.md` (в корне комплекта сервиса, **общая для всего
комплекта — BRD, SRS, API**), служебный реестр комплекта.

Правила:

1. **Якорь трассировки — функция (**`FUN`**).** Строка матрицы — функция; в колонках — связанные экраны (`SCR`), данные
   (`ENT`/`EXT`), контроли (`CTL`), печатные формы (`PRN`).
2. **Источник связей — тела документов; матрица — единственный реестр связей.** Markdown-ссылка в теле фиксирует связь
   по месту её возникновения; матрица собирает все связи в одном месте (для скриптов и поиска) и производна от тел.
   Расхождение —
   дефект матрицы: она приводится в соответствие с документами.
3. **Матрица обновляется в том же MR**, что и добавление или изменение артефакта. Новый документ без строки/упоминания в
   матрице не проходит ревью.
4. **Реестр ID ведётся в матрице**: каждый выданный ID — строка реестра (ID, название, файл), включая корневые общие
   документы (`VIS-001`, `GLO-001`). Файлы-части составного документа (`partOf` вместо `id`, §5) собственных строк
   документного ID не имеют — их содержимое регистрируется своими ID (например, контроли `CTL-NNN` с файлом карточек).
   ID не переиспользуются после удаления документа.
5. **Плановые строки разрешены**: артефакт, который ещё не написан, получает ID и строку реестра (без поля статуса) —
   матрица работает как карта комплекта.
6. **Этап 2 (начинается решением по итогам пилота):** при детализации функций атомарные требования получают `REQ-ID`
   внутри документа функции и попадают в матрицу отдельными строками. До этого трассировка ведётся на уровне артефактов.
7. **Трассировка API ↔ SRS ведётся в матрице** (раздел «Покрытие: API ↔ SRS»): одна строка — операция контракта
   `api/` (REST OpenAPI и AsyncAPI), в колонке — задействованные артефакты SRS
   (`FUN`/`SCR`/`PROC`/`ENT`/`CALL`/`PRN`/`RBAC`). Назначение — обратная связь: при изменении артефакта SRS по этой
   таблице определяются контракты, которые нужно поправить. **Методы контрактов упоминаются только в матрице**, в телах
   документов SRS их нет (аналогично: контракт не ссылается на ID SRS). Таблица обновляется в том же MR, что и правка
   SRS или контракта; при построении/сверке допускается смотреть в код (контроллеры, каналы). Легаси-операции
   (`/request/`*) и платформенно-технические (`/i18n/*`) не трассируются.
8. **Трассировка BRD ↔ SRS ведётся в матрице** (см. §5.4 — слои не ссылаются
   друг на друга в телах). Секции:

    - **BRD → SRS (покрытие требований реализацией):** строка — фича/`US`,
      колонки — `FR`, `UC`, реализующие `FUN`/`SCR`/`CTL`/`PROC`/статусы/`PRN`.
      Это единственное место стыковки бизнес-требования с реализацией.
    - `BR` **→ фича/**`UC`; `UC` **→ фичи**; `PRN` **→ фича/сценарий** — каждая
      с гейтом «0 записей без связи».
    - **Разрывы и сироты** — счётчики гейтов достаточности (ниже); при значении
      ≠ 0 перечисляются незакрытые элементы.
9. **Гейты достаточности BRD** (комплект BRD полон, когда все = 0; проверка обратная — инвентарь SRS покрывается BRD):
   функции без `US` = 0; сценарные процессы без `UC` = 0; доменные политики без `BR` = 0 (форматные/крипто-проверки
   осознанно вне `BR`); печатные формы без связи = 0; сироты BRD (`F`/`US`/`FR`/`BR`/`UC` без связи с SRS) = 0.
   Инвентарь берётся из реестров `function/README.md`, `process/README.md`, `control/README.md`,
   `print-form/README.md`. Механизм и порядок — скилл `create-brd`.

Проверки при ревью (`review-artifact`): ID уникальны; имена файлов соответствуют правилу «ID + название» (§5); у каждой
функции заполнены связи; нет артефактов-сирот (документ есть, в матрице не упомянут); гейты достаточности BRD = 0.

## 5.4. Слои BRD и SRS: раздельность и запрет кросс-ссылок

Комплект разделён по ролям-владельцам (у платформенного сервиса слой BRD может отсутствовать — его роль выполняет `service-vision.md`, см. инварианты §5): **BRD** (`brd/`) — бизнес-аналитик (бизнес-правила, фичи, сценарии); **SRS**
(`srs/`) — системный аналитик (модель данных, процессы, экраны, функции, контроли, RBAC, интеграции, ПФ). **Общие
входные документы** комплекта лежат в корне комплекта: `service-vision.md` (концепция, VIS-001), `glossary.md` (термины),
`traceability-matrix.md` (сквозная трассировка) — ими пользуются оба слоя.

- **Документы BRD и SRS не ссылаются друг на друга в телах.** В BRD нет markdown-ссылок на `docs/srs/`**; в SRS нет
  ссылок на `brd/**`. Ссылки на `service-vision.md` / `glossary.md` из обоих слоёв допустимы (оба файла — в корне
  корне комплекта). Поведение в BRD описывается **бизнес-языком**: статусы — по бизнес-наименованию без ссылки; проверки —
  бизнес-условием или ссылкой на `BR-NN`; обращения к смежным системам в `UC` — как шаги бизнес-намерения без протокола.
- **Единственное место стыковки BRD и SRS — матрица трассировки** (§5.3, п. 8).
- **Внутри BRD ссылки допустимы:** фича → `BR-NN`/`UC-NN`, `business-rules` → фича, на глоссарий/концепцию — обычными
  markdown-ссылками (`../glossary.md`, `../service-vision.md`).
- **Реестр каталога BRD —** `README.md` (не `_index.md`), по общей конвенции реестров (§5): `brd/features/README.md`,
  `brd/use-cases/README.md`.
- **Границы охвата** (§2–§3) действуют и в BRD: только целевой контур сервиса; актуальная метка версии из профиля
  sources / `README.md` корня комплекта; временно отключённые способности — «временно недоступна/отключена», не «неактуальна».
- **Навигация для читателя:** `README.md` корня комплекта — вход в комплект. Обязательный состав
  и порядок разделов — шаблон [docs-readme.md][docs-readme];
  создание/синхронизация — скилл [create-docs-readme][create-docs-readme].
  В README: ссылка на Service Vision как точку входа, краткая таблица контуров CL/BNK
  (+ SYS), самодостаточная карта обозначений (без отсылок за пределы комплекта), дерево
  фактических разделов. Подробности «что за сервис» — только в `service-vision.md`.

## 6. Открытые вопросы и расхождения

Принцип: **документы в** `<service-id>/` **— чистовые.** Никаких inline-маркеров, TODO и черновых пометок в тексте
документов — их потом пришлось бы вычищать.

Порядок работы с пробелами и расхождениями:

1. **Лучший вариант — разрулить сразу:** задать вопрос аналитику в диалоге и внести согласованный результат в документ.
2. Если сразу нельзя — зафиксировать **открытый вопрос** вне целевого docs remote (удобно — в парном **src-репо**; состав
   src свободен). В docs remote отдельного `open-questions.md` **нет**. Пример формата записи в src:

   ```markdown
   ## OQ-001. <Краткая формулировка вопроса>
   - **Статус:** открыт | решён
   - **Затронутые документы:** data-model.md, …
   - **Суть:** что неясно / в чём расхождение источников
   - **Решение:** (заполняется при закрытии; кто решил, что решили)
   ```

3. **Реестр — append-only:** новая запись добавляется В КОНЕЦ файла, номер — следующий свободный `OQ-NNN`. Вставка в
   середину, перестановка записей и переиспользование номеров запрещены (порядок номеров = хронология обнаружения;
   инцидент file-storage 2026-08-11 — новые OQ вставлены после тематически близкой записи, нумерация утратила
   монотонность).
4. В самом документе спорное место описываем по **наиболее достоверному
   источнику** (по приоритету §1) — без пометок. **Отсылок к OQ в документах
   комплекта не делаем** (ни ссылок, ни упоминаний `OQ-NNN`) — связь «вопрос →
   документ» ведётся только во внешнем реестре (поле «Затронутые документы»).
5. MR в docs, затрагивающий документы со связанными открытыми вопросами, не сливается в
   `trunk`, пока эти вопросы не закрыты (акцепт вычисляется из git — §5).

Отчёты ревью и проверок (качество требований, сверка с источниками и т.п.) — тоже **не** в docs remote; при
необходимости — в src.

## 7. Git

Краткие правила (полная норма — `[git-workflow.md](../../cookbook/analytics/git-workflow.md)`):

- Работаем в **ветках**, в `trunk` напрямую не коммитим.
- Имя ветки: `<prefix>/<topic>[/<jiraid>]`. JIRA ID указывает только человек; без задачи — согласованные исключения
  (`fix/…`, иногда `meta/…` / `chore/…`).
- Сообщения коммитов — на **русском**, тема в **прошедшем времени** («Добавлена…», «Обновлены…»).
- Если факты брали из src / выгрузок — в теле коммита или MR строка **«Откуда взяты факты:»**.
- **Целевой remote** docs-репо — состав по `repo-topology.md` [§3](repo-topology.md#3-состав-целевого-docs-репо)
  (`<service-id>/` + инфра); сырьё и обёртки агентов не пушить.
- К каждому MR — **записка для чата команды** (формат в git-workflow).
