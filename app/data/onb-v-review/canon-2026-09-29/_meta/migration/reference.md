# Гид миграции сервиса: справочник

Справочник норм и ориентиров конвейера миграции — общий для обоих
треков (с координатором и без). Порядок действий — в инструкциях
треков (`track-manual.md`, `track-coordinator.md`), выбор трека —
в `README.md` этого каталога. Нормативный документ конвейера —
протокол `_meta/tools/step-protocol.md`; при расхождении прав он.

## Термины и обозначения

- **Прибор** — собирательное имя механических инструментов контроля и
  нормализации (`_meta/tools/normalize_tables.py`, `selfcheck.py`,
  `link_debts.py`); «отказ прибора», «калибровка прибора»,
  «дефект прибора» в гиде — о них.
- **§N** — раздел протокола этапа `_meta/tools/step-protocol.md`
  (например, §8 — форма сдачи, §10 — шаблон промпта), если явно не
  назван другой документ.
- **Гейт** — прогон `selfcheck.py` с вердиктом OK/БРАК (часть прибора).
- **Зона** — подсервис или общая часть сервиса по разметке профиля
  источников.
- **Акцептующий** — аналитик команды, акцептующий план и приёмки
  этапов (персона из «Входных данных» промпта генерации плана).
- **Трек** — вариант миграции: с ИИ-координатором или без него; выбор —
  `README.md` этого каталога.
- **ПРОМ-срез** — состояние требований, соответствующее продуктиву:
  основная ветка `master` репозитория сервиса (первичный срез миграции
  помечен тегом `src/PROM`). Миграция ведётся только с него.
- **Доводка выгрузки** — приведение выгрузки Confluence к чистовому
  виду до старта миграции: снятие CriticMarkup-разметки (утилиты
  `apply`/`reject` в составе `confluence-tree-exporter`) и флаги
  замороженных поддеревьев (`unapproved_jira`).
- **Техприёмка** — техническая приёмка сдачи: проверка по фактам
  репозитория (git-скоуп, отчёт гейта, дословность, ID, долги), а не по
  тексту сдачи. В треке с координатором её проводит координатор,
  решение остаётся за акцептующим.

Остальные термины конвейера (этап, заход, сдача, приёмка, дозаход,
долг, baseline, владелец канона) — словарь протокола
`_meta/tools/step-protocol.md`; он нормативен, при расхождении прав
протокол.

## Обозначения путей

Команда заполняет ТОЛЬКО два пути; остальные выводятся из них и
переопределяются лишь при нестандартном расположении:

| Обозначение | Что это | Значение по умолчанию |
|---|---|---|
| `<src>` | корень репозитория сервиса | заполняет команда |
| `<клоны>` | родительский каталог для клонов канона, эталона, стандартов, контрактов | заполняет команда |
| `<канон>` | клон `docs-o2new` | `<клоны>/docs-o2new` |
| `<эталон>` | клон `docs-account-opening-request` | `<клоны>/docs-account-opening-request` |
| `<стандарты>` | клон `eco-techbook` | `<клоны>/eco-techbook` |
| `<контракты>` | клон `docs-external-contracts` | `<клоны>/docs-external-contracts` |
| `<выход>` | корень создаваемого комплекта | `<src>/docs` |

Оба промпта (`prompt-plan.md`, `prompt-coordinator.md`) используют
эти обозначения; во «Входных данных» промптов указываются те же
значения.

## Структура репозитория сервиса

| Путь в `<src>` | Что лежит | Кто создаёт |
|---|---|---|
| `sources/raw/` | нетронутый архив выгрузки — только чтение | экспортёр |
| `sources/confluence/` | выгрузка после доводки — источник миграции, только чтение | экспортёр + доводка |
| `docs/` (= `<выход>`) | целевой комплект: `srs/`, `brd/`, `glossary.md`, `traceability-matrix.md` | исполнитель |
| `inventory.md` | опись страниц и приложений выгрузки | планировщик (инструментом) |
| `README.md` | профиль источников: маршрутизация зон, легенда, строки «Срез канона» и «Срез источника» (тег последней задачи, разнесённой в `docs/`) | планировщик, срезы — акцептующий |
| файл плана миграции (имя задаёт планировщик, например `migration-plan.md`) | план: этапы, реестр этапов, разметка | планировщик |
| `prompts/` | промпты этапов `prompts/<ЭТАП>.md` | планировщик |
| `sandbox/` | нормализованные копии, отчёты гейта, журнал гейта | исполнитель, гейт |
| `open-questions.md` | вопросы аналитику OQ-NN (append-only) | агенты |
| `feedback.md` | обратная связь владельцу канона FB-NN (append-only) | акцептующий |
| `coordination-log.md` | журнал координации (только трек с координатором) | координатор |

## Ветки и теги репозитория сервиса

| Ссылка | Что означает | Кто и когда меняет |
|---|---|---|
| ветка `master` | ПРОМ: требования, соответствующие эксплуатации; источник миграции и дельт | акцептующий — при вводе задачи в эксплуатацию и при новой выгрузке (`run-history` коммитит прямо в ветку; прямой push мейнтейнерам разрешён, MR в `src-*` не используется) |
| тег `src/PROM` | первичный ПРОМ-срез миграции: последний коммит `master` перед первым вводом задачи | ставится один раз; пока вводов нет, при исправлениях ПРОМ переносится на новый коммит |
| тег `src/<JIRA-ID>` | момент ввода задачи в эксплуатацию: коммит `master`, в котором она применена к `sources/confluence/`. Дельта задачи — дифф этого коммита; `docs/` в нём ещё не обновлён | `run-history` при вводе |
| коммит «Выгрузка: …» | событие выгрузки на обеих ветках: архив обновлён, ранее введённые (на `master`) или ранее нарезанные (на `future`) задачи применены заново. Дифф коммита — механическая разница двух выгрузок; тега нет | `run-history` сам, когда пересчитанное состояние отличается от вершины ветки |
| ветка `future` | хронология: цепочка событий «выгрузка → задача → задача…» по порядку дат первой записи истории; каждая задача — свой коммит с тегом. Вершина ветки — все задачи применены, прозрачный вид потенциального будущего. Для миграции не используется; «что поменяла задача» смотрят в GitLab по коммиту с тегом | `run-history` с `--tag-prefix hist/ --commit-prefix "Срез хронологии"`; старые коммиты и теги не перестраиваются |
| тег `hist/<JIRA-ID>` | вклад задачи в хронологию на момент своей выгрузки. Дополнения разметки, пришедшие позже, видны в коммите выгрузки, а не под тегом задачи | `run-history` на `future` |
| ветка `src/raw-import` | история появления архива `sources/raw/` | не меняется |

Ввод задачи в эксплуатацию — два коммита `master`, в этом порядке:

1. Акцептующий запускает `run-history` для введённой задачи; в файле
   задач только вводимые, введённые ранее скрипт видит по тегам. Скрипт
   пересобирает `sources/confluence/` из `raw/` (введённые ранее задачи
   и текущая применены, остальные отклонены), делает коммит и ставит
   тег `src/<JIRA-ID>`. Комплект `docs/` в этом коммите ещё соответствует
   предыдущему срезу.
2. Дельта-процесс: дифф коммита ввода по источнику раскладывается по
   `page_id` в комплект. До переноса комплекта в `docs-<сервис>` это
   `<src>/docs` и тот же коммит обновляет строку «Срез источника» в
   `README.md`; после переноса дельта идёт только в `docs-<сервис>`
   веткой `docs/<JIRA-ID>` через MR (роадмап, этап 5), а строку «Срез
   источника» в `<src>/README.md` обновляет отдельный коммит после
   принятия MR. Каталог `<src>/docs` после переноса удаляется: у
   комплекта один дом.

   ```powershell
   git -C <src> diff src/<JIRA-ID>~1 src/<JIRA-ID> -- sources/confluence
   ```

   Левая граница — родитель коммита ввода, тег для неё не нужен.
   Строку «Срез источника» акцептующий заводит по завершении миграции
   со значением `src/PROM`; планировщик и промпты о тегах не знают.

Пустой ввод штатен. Если страницы задачи целиком принадлежат другой,
ещё не введённой задаче (страничный флаг `unapproved_jira`), отклонение
непринятых опустошает их, и вклад задачи проявится только с вводом
владельца страницы. Коммит и тег ставятся всё равно, скрипт печатает
причину. Обратная сторона: дельта более позднего ввода может содержать
ранее введённые правки на страницах, которые появились этим вводом.

Порядок ввода задач произвольный и от номеров Jira не зависит:
состояние `master` определяется множеством введённых задач, а дельта
задачи — это изменение источника при добавлении её к уже введённым.
Список тегов `src/*` на `master` — реестр того, что уже в ПРОМ. Если
между двумя вводами дельта-процесс не запускался, разница берётся от
тега в строке «Срез источника» до `HEAD` (все накопившиеся задачи
разом) или по цепочке коммитов ввода, когда нужна атрибуция по задачам.

Новая выгрузка — событие на обеих ветках, полная пересборка не нужна:

1. На `master`: очистить `sources/raw/`, положить выгрузку целиком и
   закоммитить («Архив: выгрузка от <дата>»); `git add sources/raw`
   зафиксирует и удалённые страницы. Дифф этого коммита — всё, что
   изменилось в Confluence с прошлой выгрузки. Затем `run-history` без
   файла задач: он пересчитает «архив + введённые ранее» и зафиксирует
   коммит «Выгрузка: …». Вводить задачи в этом запуске нельзя, файл
   задач не передаётся.
2. На `future`: перенести архив с `master` командой `git restore` (она,
   в отличие от `git checkout -- sources/raw`, удаляет исчезнувшие файлы)
   и закоммитить, затем `run-history` со списком задач выгрузки
   (`migration-apply-order.md` из архива) и ключами хронологии. Уже
   нарезанные задачи скрипт пропустит по тегам, коммит выгрузки
   поставит сам, новые задачи нарежет по одной.

   ```powershell
   git -C <src> checkout future
   git -C <src> restore --source=master --staged --worktree sources/raw
   git -C <src> commit -m "Архив: выгрузка от <дата>"
   run-history.bat <src>\sources\raw <src> <src>\sources\raw\migration-apply-order.md --tag-prefix hist/ --commit-prefix "Срез хронологии" --base-dir <каталог вне репозитория>
   git -C <src> push origin future "refs/tags/hist/*"
   git -C <src> checkout master
   ```

## Роли

- **Аналитик команды** (в терминах протокола — «акцептующий») —
  владелец результата. Обязанности:
  - готовит выгрузку и утверждает план;
  - передаёт промпты агентам и даёт отмашки;
  - принимает сдачи (в треке с координатором техприёмку готовит
    координатор, решение — за аналитиком);
  - выполняет коммиты и push, накатывает решения в файлы.
  Все необратимые действия — только человеком.
- **Агент-планировщик (обязательно сильная LLM)** — строит план
  миграции (фаза A) и собирает промпты этапов подстановкой карточки
  этапа в шаблон §10 (фаза B). Промпт — файл в
  репо (в отличие от версии 1, где вы получали его только на экране), человек его ревьюит.
- **Агент-исполнитель** — выполняет этап заходами строго по протоколу;
  свежая/новая сессия на этап (§11). Для новой сессии рекомендуется сильная LLM. Для дозаходов - часто и слабая LLM дает приемлемый результат.
- **Гейт** (см. «Термины») — сверяет карточки
  с источниками после каждого захода; вердикт OK/БРАК не обсуждается с
  агентом, а чинится.
- **ИИ-координатор** (только трек с координатором) — ведёт процесс,
  проводит техприёмку сдач и оформляет решения акцептующего в файлы;
  роль и красные линии — `prompt-coordinator.md`, порядок —
  `track-coordinator.md`.

## Решения аналитика: как управлять конвейером

Правка описи, плана и файлов промптов — главный рычаг аналитика,
дающий воспроизводимый результат: решение,
внесённое в файл, версионируется коммитом и переживает сессии;
решение, сказанное агенту только в чате, — потерянное решение.

Куда вносить — по моменту принятия:

- **до сборки промпта этапа** — в опись (целевой тип, примечание) или
  в план-документ (строка реестра этапов, общая карточка типового
  этапа, примечания к этапу — отдельной «карточки этапа» как документа
  нет, см. инструкции треков, фаза A, пункт «План этапов»): планировщик
  подставит сам;
- **между сборкой и запуском** — правкой файла промпта (ревью
  промпта — штатная точка для этого);
- **между заходами бегущего этапа** — тоже правкой файла промпта,
  плюс явное указание в отмашке: «промпт обновлён, перечитай раздел
  такой-то»;
- **во время захода** промпт не правится (как и канон — не меняется
  под бегущим агентом).

Форма записи решения — пять элементов (по образцу промптов стенда):

1. **Утверждение, не условие** — «это режим той же формы», а не
   «если это режим…»: условная формулировка передаёт решение агенту.
2. **Маркер** «решение аналитика <дата>» — отделяет норму от
   описания и оставляет след.
3. **Обоснование фактами источника** (дословными) — без него агент,
   встретив в источнике противоречащее слово, вправе «пере-решить»;
   с фактами противоречие снято заранее.
4. **Операционное следствие** — что делать и чего не делать
   («третью вкладку не заводить; режим — видимостью блоков»).
5. **Согласованность всех мест**, где агент мог бы споткнуться
   (опись + план + промпт): рассогласованные документы — худший
   вход, агент либо встанет, либо тихо выберет сам.

Граница: аналитик правит опись, план и промпты СВОЕГО сервиса. Если
решение требует изменить канон (шаблон, скилл, сторож прибора) — это
не правка промпта, а обратная связь владельцу канона (см. «Обратная
связь»): промпт не может разрешить то, что канон запрещает.

### Доводки серии: промпт этапа как журнал

При серии заходов с доводками ведите промпт этапа как живой журнал
серии. Формат обкатан пилотом, образец — `prompts/ISS-03.md`
референс-стенда:

1. **Таблица «Заходы серии»** — по строке на заход: номер (zNN), тема,
   вход (page_id и строки), сумма строк, имя отчёта гейта. Дозаход
   добавляется НОВОЙ строкой с суффиксом (например, `z06-fix`),
   отметкой «без нового входа» и ссылкой на блок решения — история
   серии видна одним взглядом, нумерация заходов не путается, отчёт
   дозахода получает собственное имя.
2. **Блок «Решения аналитика по приёмке zNN»** под таблицей —
   датированный, по формуле пяти элементов (выше), с
   операционализацией до уровня файлов: какие карточки переделать,
   какие ID сменить (и как — через матрицу), какие ссылки
   перепривязать, что НЕ делать. Именно этот блок исполняет дозаход.
3. Решение, меняющее правила ОСТАВШИХСЯ заходов серии, вносится в
   раздел правил/особенностей заходов промпта (не в блок дозахода);
   отмашка несёт «промпт обновлён, перечитай раздел такой-то».

Когда применять: приёмка требует переделки уже сданного захода
(дозаход); решение меняет правила оставшихся заходов; вход
перекраивается между заходами; серия длинная или прерывалась —
журнал даёт исполнителю точку перепривязки после обрыва сессии
(проверено живым обрывом на пилоте).

Когда НЕ применять: этап в один заход — дозаход идёт простой отмашкой
с замечаниями, журнал не нужен; замечание не требует переделки уже
сданного — решение вносится в строку или правила СЛЕДУЮЩЕГО захода,
отдельный дозаход не открывается. Журнал окупается там, где серия
живёт дольше одной сессии; вести его ради формы не нужно.

## Постоянные правила (весь проект)

- Решения — только в файлы (опись, план, промпты): решение, сказанное
  агенту в чате, — потерянное решение.
- Вопросы агентов к источнику — записями OQ-NN в `open-questions.md`;
  вопрос без записи не существует.
- Дефект прибора не обходится молча: запись FB-NN в `feedback.md` +
  MR-тред владельцу канона; сроки его реакции — раздел «Обратная связь».
- Требование прибора, противоречащее протоколу или гиду, — отказ
  прибора, а не ручка: под него не подстраиваются (FB-03: гейт просил
  журнал в `sources/sandbox/`, исполнитель создал каталог — потом его
  пришлось убирать). Стоп только по затронутому участку — сдаче и базе
  дельты; содержание по шаблонам и скиллам продолжается, формат задают
  они, гейт только судит. Следы обхода, если успели появиться, убирает
  владелец канона ответом на FB: «лечение» по шагам либо «откат»
  (раздел «Откат участка к принятому коммиту»).
- Журналы репозитория: `open-questions.md` (вопросы), `feedback.md`
  (обратная связь); в треке с координатором — ещё
  `coordination-log.md` (координация).

- Поле `version` во frontmatter не используется: шаблоны канона и
  профиль источников его не несут, прибор не проверяет. В комплектах,
  выпущенных раньше, поле остаётся как есть, волна удаления не
  проводится (решение владельца канона 2026-09-28).
- Слой `brd/` обязателен для продуктового сервиса; у платформенного
  (`is_platform: true` в `services.json`) его роль выполняет
  `service-vision.md` с перечнем потребителей и обязательств платформы,
  каталог `brd/` не создаётся.
- Сервис из подсервисов: каждая часть в своём каталоге `srs/<часть>/`,
  общая часть — `srs/shared/`; идентификаторы нумерованных артефактов
  несут слот части сразу после префикса (`FUN-DS-SYS-01`, `ENT-SHR-001`),
  коды частей объявляются таблицей в `README.md` комплекта с колонками
  «Код» и «Каталог», прибор сверяет слот с каталогом. У сервиса без
  подсервисов слота нет. Инструкции и прочие документы вне требований в
  `srs/` не кладут — база знаний команды, раздел «Куда класть документы».

## Типовые ошибки

1. **Смешение сессий.** Планировщик и исполнитель (а в треке с
   координатором — и координатор) — **разные** агенты с разными
   промптами и правами; каждому — своя сессия.
2. **Экономия на модели** в первых заходах типа/зоны: слабая модель
   фабрикует содержимое — доказано контролируемым экспериментом
   (раздел «Правило моделей»).
3. **Старт по недолеченной выгрузке** — для большого сервиса самая
   дорогая ошибка (инструкции треков, шаг «окружение и выгрузка»).

## Куда класть документы

Не всякий полезный документ — требование. Комплект требований — карта
пробелов сервиса: всё, что в нём лежит, сверяется гейтом и попадает в
контекст ИИ-агентов при развитии аналитики. Инструкция «как
пользоваться модулем» рядом с требованием «что сервис обязан делать»
однажды заставит агента принять первое за второе. Поэтому дом (место хранения)
документа определяется не его типом (тип файла — не признак), а
ответами на четыре вопроса, за которыми стоит два принципа: 
1) полезность ≠ принадлежность (не потерять — обязательно, положить в требования —
нет); 
2) один факт — один дом (правило единого источника истины для
единицы содержания — каждый факт записан ровно в одном месте, все
остальные места на него ссылаются, а не копируют).

Правило чтения таблицы: задавайте вопросы по порядку; на первом
ответе «Да» дом определён. При ответе «Нет» переходите к следующему

### Пример разбора: самописная инструкция по работе с криптомодулем

*Вопрос 1. Обязывает ли документ систему?* Нет. Инструкция объясняет
разработчикам, как пользоваться внешним модулем; проверяемых
утверждений вида «сервис должен…» в ней нет. Переходим к вопросу 2.

*Вопрос 2. Опирается ли какое-то требование на этот документ как на
источник факта?* Ответ зависит от содержания требований сервиса. Если
ни одно требование не ссылается на свойства модуля — ответ «нет»,
переходим к вопросу 3. Если же требования опираются на факты о модуле
(например, «подпись формируется по ГОСТ Р 34.10-2012 через
криптомодуль» — требование использует поддерживаемый модулем
алгоритм), то ответ «да», и поступаем так: сам факт записывается в
карточку требования (функции или вызова), а источником факта
указывается документация вендора модуля, которая как документ
внешнего владельца хранится в `docs-external-contracts`. Источником
становится документация вендора, а не самописная инструкция:
инструкция лишь пересказывает вендора, и ссылаться на пересказ вместо
первоисточника нельзя.

*Вопрос 3. Это обоснование решения?* Для самой инструкции — нет. Но
если в ней записаны выводы из обсуждений («выбрали режим X, потому что
режим Y не поддерживает…»), эти выводы — обоснование решения, и они
выносятся в отдельную запись решения (ADR). Инструкция после этого
остаётся чистой инструкцией. Переходим к вопросу 4.

*Вопрос 4. Это полезно людям как инструкция, справка или обучение?*
Да. Инструкция помещается в базу знаний команды, в подкаталог
инструкций (`knowledge/how-to/`). Из карточек требований на неё можно
сослаться словами «см. также», но никогда — как на источник факта.

*Итог.* Один документ разложился на три дома: факты о модуле — в
карточки требований со ссылкой на документацию вендора; обоснования
выбора — в запись решения; сама инструкция — в базу знаний. В комплект
требований не попало ничего лишнего, и ничего не потерялось.

## Правило моделей (проверено контролируемым экспериментом)

Первые заходы нового типа или новой зоны — **только сильная модель**.
Слабая модель допустима на накатанных типах в "обжитой" зоне. Чистый
повтор одного этапа двумя моделями показал: слабая фабрикует
содержимое «по аналогии» (таблица атрибутов при источнике без таблиц),
нарушает протокол нормализации и не задаёт ни одного вопроса; сильная
на том же входе честно фиксирует пробел источника вопросами OQ.
Сторожа фабрикации в гейте есть, но они — последний рубеж, не замена
правилу.

## Паспорт производительности (числа с прогона, не обещания)

## Откат участка к принятому коммиту

Когда применять: владелец канона в ответе на FB выбрал «откат» вместо
«лечения» — обычно когда до остановки успели появиться побочные
следы обхода (каталоги и файлы не на месте, базовая линия с ложным ✗,
часть этого в коммите), а переделать участок дешевле, чем разбирать
следы по одному. Откат всегда по путям, не по всему дереву: работа,
сделанная легально по другим путям, остаётся. `reset --hard` и
`push --force` не используются.

Что пропадает: всё по указанным путям после принятого коммита, в том
числе `sandbox/journal.txt` и `sandbox/baseline.txt`, если они входят
в откатываемые пути. Для захода, чей гейт давал ложный ✗, это
приемлемо: такие журнал и базовая линия для дельты непригодны.

Принятый коммит и откатываемые пути называет владелец канона в поле
«Решение» записи FB. Ниже `<коммит>` — его хэш, `<пути>` — пути через
пробел, как в записи FB (например `sources/sandbox sources/README.md
sandbox`). Рецепт проверен живым прогоном на копии репозитория
сервиса.

1. Посмотреть, что по этим путям отличается от принятого коммита:

   ```powershell
   git -C <src> diff --name-status <коммит> -- <пути>
   git -C <src> status --short -- <пути>
   ```

   Ожидание: первая команда печатает учтённые файлы с буквой `M`
   (изменён), `A` (добавлен после принятого коммита) или `D` (удалён);
   вторая — неучтённые пути с пометкой `??` и незакоммиченные
   изменения. Если обе печатают пусто, откатывать нечего.

2. Вернуть учтённые файлы по этим путям к принятому коммиту в индексе
   git. Команда принимает любые пути, в том числе те, которых в
   принятом коммите нет:

   ```powershell
   git -C <src> reset -q <коммит> -- <пути>
   ```

   Ожидание: команда ничего не печатает.

3. Вернуть рабочие копии файлов. Команда `checkout` отказывает на
   путях, которых в принятом коммите нет, поэтому сначала спросить
   git, какие из путей там есть:

   ```powershell
   git -C <src> ls-tree --name-only <коммит> -- <пути>
   ```

   Ожидание: напечатан список путей, возможно короче исходного. Если
   список пуст, этот шаг закончен. Иначе выполнить `checkout` только
   для напечатанных путей:

   ```powershell
   git -C <src> checkout -- <пути, напечатанные ls-tree>
   ```

   Ожидание: команда ничего не печатает.

4. Удалить неучтённые файлы и каталоги только по этим путям:

   ```powershell
   git -C <src> clean -fd -- <пути>
   ```

   Ожидание: строки вида «Removing <путь>» для каждого удалённого,
   в том числе для файлов, добавленных после принятого коммита (после
   шага 2 они стали неучтёнными). Ничего за пределами названных путей
   команда не трогает.

5. Проверить результат и зафиксировать:

   ```powershell
   git -C <src> diff --stat <коммит> -- <пути>
   git -C <src> status --short -- <пути>
   ```

   Ожидание: первая команда печатает пусто (по путям состояние равно
   принятому коммиту). Если вторая печатает строки с `M` или `D` в
   первой колонке — это откат закоммиченных следов, его нужно
   закоммитить:

   ```powershell
   git -C <src> commit -m "Откат <пути> к принятому коммиту <коммит> (FB-NN)"
   ```

   Если вторая команда печатает пусто, коммит не нужен: следы были
   только в неучтённых файлах.

После отката заход по этому участку выполняется заново в свежей сессии
исполнителя (протокол §11), с исправленным прибором: сначала шаги
«обновить клон канона» и «принять срез» из ответа на FB, потом новая
базовая линия.

## Обратная связь

- Вопросы-находки по канону/прибору: MR-тред в ветку канона + запись
  `FB-NN` в `feedback.md` в корне вашего src-репо (append-only,
  сквозная нумерация). Формат записи:

  ```text
  ## FB-NN — <дата> — <краткий заголовок находки>
  - Где: <этап/заход, файл источника или карточки, команда прибора>
  - Что: <дословная диагностика — вывод прибора / цитата, не пересказ>
  - Ожидалось: <что по гиду/протоколу/шаблону должно было произойти>
  - Обход: <применён ли легальный обход и какой / работа остановлена>
  - Решение владельца канона: <заполняется ответом; дата, суть>
  ```

  Молча обходить дефект прибора не нужно — обход маскирует
  дефект и ломает следующую команду.
- **Обязательство владельца канона по скорости FB-цикла:** первичная
  реакция (триаж: дефект прибора / дефект использования / вопрос) — в
  течение рабочего дня; решение по подтверждённому дефекту прибора
  (калибровка с новым срезом канона ЛИБО явно санкционированный
  временный обход) — до двух рабочих дней; если дольше — в ответе на
  FB называется срок. Дисциплина «не обходить молча» работает только
  при быстром цикле починки — поэтому это обязательство, а не
  пожелание: затянутый ответ владельца канона легализует ваш обход
  через явный запрос.
- Решения по вашему сервису (типизация страниц, спорная нарезка) —
  ваши; канон фиксирует только общие правила.
