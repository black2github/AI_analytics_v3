# Скилл: создать экранную форму

Создать чистовой документ экранной формы (`SCR-CL-NN` / `SCR-BNK-NN`, при вкладках — папка с README и файлами вкладок `SCR-…-NN.K`) в `output/<service>/docs/srs/screen-form/<контур>/` по шаблону `_meta/templates/screen-form.md`. Результат: чистовой документ(ы), заведённые заглушки для отсутствующих вызовов, обновлённая матрица трассировки, список спорных мест для аналитика. Поле `status` во frontmatter не используется (`conventions.md` §5).

Всегда действуют: роль и принципы `AGENTS.md`, конвенции [conventions.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md), шаблон `_meta/templates/screen-form.md` (включая чек-лист). Формат — событийная модель (события EV-N, кнопки B-N, правила полей FLD-N, сообщения MSG-N), логика конструкцией **Если**/**то**/**иначе**.

## Вход

- Экранная форма (название или страница источника) и контур (Клиент/Банк).
- Режим: **reverse** (из sources) или **forward** (по требованиям).
- Экран с вкладками или без (определяется по источнику: несколько вкладок на одной странице → папка + README + файлы вкладок).

## Gate

- Описываем **экранную форму** (состав полей, поведение, кнопки, сообщения). Логику функций и процессов — в их артефактах (`create-function`, процессы); экран на них ссылается.
- Вызов внешней банковской АС — не в экране, а карточкой `CALL`; платформенная функция/проверка ЭКО без опубликованной спецификации — записью `PLT` в `platform-functions.md`.

## Порядок (reverse)

1. Прочитай шаблон `_meta/templates/screen-form.md` целиком, включая чек-лист.
2. Собери источники (актуальная выгрузка Confluence, conventions §1) — страница ЭФ обычно содержит вперемешку: **несколько вкладок**, «Дополнительные действия при открытии ЭФ», описания кнопок, боковую часть, «Функцию сохранения». Раздели их по структуре шаблона:
   - таблицы полей вкладок → реестр полей (§2) + правила FLD-N (§4): каждому полю присвой `FLD-N` (следующий свободный; существующие номера не перенумеровывай и не переиспользуй) — строка реестра и подраздел §4 связаны биекцией;
   - «Дополнительные действия при открытии» и реакции на изменение полей → события EV-N (§5);
   - кнопки → раздел B-N (§6);
   - «Функции формы» (именованные наборы шагов, работающие с полями ЭФ) → раздел FF-N (§8): шаги дословно, кнопки ссылаются якорями; в карточки FUN не выноси (нет входной сигнатуры — выдумывать нельзя), в кнопки не дублируй;
   - «Сообщения …» (информеры/блоккеры/плашки) → таблица MSG-N (§7);
   - боковая часть со статусом → подраздел «Боковая часть»;
   - «Функция сохранения» → колонка «Атрибут» в реестре + отдельная функция «Сохранить заявку» (`create-function`).
3. Сверь согласованность с комплектом: модель данных (атрибуты, куда сохраняются поля), справочники и настраиваемые параметры, статусная модель (маршрутизация по статусам), контроли (обязательность, бизнес-проверки).
4. **Вызовы, у которых нет карточки:**
   - внешняя АС без карточки вызова `CALL` → заведи карточку/заглушку (`create-contract-call`);
   - платформенная функция/проверка без записи → добавь `PLT` в `platform-functions.md` (заглушкой, если постановки нет);
   - зафиксируй пробел в `open-questions.md`.
5. Напиши документ строго по шаблону: обязательность полей — в реестре (источник истины — ЭФ); статика в FLD-подразделах — буллетами под жирными ярлыками словаря шаблона в фиксированном порядке (Тип → Формат → Способ заполнения → Обязательность → Видимость → Логика установки значения; дополнительные — после стандартных; голых условий без ярлыка не оставляй, неприменимые атрибуты опускай целиком — без прочерков); поля, замапленные на один атрибут, — представления одного элемента данных (расхождение их статики — спорное место); логика — **Если**/**то**/**иначе**; вызовы не сворачивай (параметры запроса + обработка ответа + ссылка на CALL/PLT); контроли — ID + название; идентификаторы FLD/EV/B/MSG/FF стабильны.
6. Обнови матрицу трассировки в том же изменении: реестр ID (экран `SCR-CL-NN` + строка на каждую вкладку `SCR-CL-NN.K`; новые CALL/PLT), покрытие функций (колонка SCR); индекс и дерево `docs/srs/README.md`.
7. Спорные места: сначала вопрос аналитику в диалоге; нерешённое — в `open-questions.md` (формат conventions §6). В документе — по наиболее достоверному источнику, без отсылок к OQ. Типовые пробелы ЭФ: страницы методов вне выгрузки; противоречия «текст ЭФ ↔ страница метода»; неполные условия видимости/активности.
8. Прогони чек-лист шаблона; исправь найденное (типовые дефекты: битые ссылки после переименований, широкая прозаическая колонка в реестре — её быть не должно, дубли текстов ошибок контролей).
9. Выведи аналитику: краткое резюме (что вошло) + спорные места, каждое в формате **вопрос / предположение / что проверить** с рекомендацией.
10. Коммит — только по просьбе аналитика; тема в прошедшем времени, в теле «Откуда взяты факты:».

## Порядок (forward)

1. Прочитай шаблон; собери вход: бизнес-требование, процесс, роли, состав данных (модель), связанные функции и контроли. Пробелы — списком вопросов аналитику до начала.
2. Спроектируй форму по шаблону (ID — по правилу выдачи `conventions.md` §5: скоуп — контур, по реестру матрицы; вкладки — если экран многошаговый); далее шаги 4–10 режима reverse (включая коммит-шаг).

## Правила обоих режимов

- Не выдумывай факты; предположения помечай и выноси аналитику.
- Идём по одной форме (или одной вкладке многотабного экрана) за итерацию: документ → отчёт аналитику → правки → следующая.
- Ссылки на макеты Figma переносятся живыми URL (единственное исключение из запрета внешних URL — иначе аналитику не соотнести с макетом; шаблон, раздел «Макеты Figma»). Zeplin, pageId, домены сред, кодовые имена платформенных интерфейсов — не переносятся.
- Артефакт акцептованным не помечаешь никогда — акцепт делает только человек, вне документа (`conventions.md` §5).

## Выход аналитику

Резюме (что описано, какие заглушки CALL/PLT заведены) + спорные места (вопрос / предположение / что проверить).
