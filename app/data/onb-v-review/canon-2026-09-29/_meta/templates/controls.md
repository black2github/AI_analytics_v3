# Шаблон: контроли (CTL)

Шаблон документа контролей сервиса — каталог `docs/srs/control/`. Общие правила — [conventions.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md); при противоречии истина в конвенциях.

## Идентификация и размещение

- **Один документ на сервис, несколько файлов**: каталог `docs/srs/control/`. `README.md` — реестр с ID `CTL-000` (разделы 1–4); карточки контролей — в файлах `cards-<slug>.md` рядом. Документ разбит на файлы, чтобы каждый оставался лёгким для preview; логически это один документ `CTL-000`: `id: CTL-000` несёт только `README.md`, карточные файлы вместо `id` несут `partOf: CTL-000` (conventions §5), остальные поля frontmatter (`type`/`service`) одинаковые у всех файлов каталога.
- **Файлы карточек — ОДИН ФАЙЛ НА СУЩНОСТЬ / НА ФОРМУ** (решение
  владельца 2026-08-31, заменяет «тематические блоки ≤200 строк» —
  прежняя нарезка по заходам чтения была артефактом конвейера и
  разбрасывала контроли одной сущности по файлам): BE-карточки — файл
  `cards-<слаг-сущности>.md` по сущности «Проверяемого атрибута»
  (`cards-ent-016-request.md`); FE-карточки — файл на экранную форму
  (`cards-scr-cl-01.md`). Frontmatter карточного файла несёт
  `entity: <ID сущности или формы>` — данные разметки, сторож сверяет
  «Проверяемый атрибут» каждой карточки с entity файла. Лимит размера
  файла СНЯТ — навигацию даёт реестр README; H1 файла — «Контроли
  <сущность/форма>», после H1 — строка-аннотация со ссылкой на
  `README.md`. Новый контроль получает следующий сквозной ID и
  добавляется В ФАЙЛ СВОЕЙ СУЩНОСТИ (диапазоны ID по файлам НЕ
  обязаны быть непрерывными). ID и якоря карточек стабильны; перенос
  карточки между файлами — только каноническим инструментом
  перепривязки (на якоря ссылаются другие документы).
- **Контроль** — атомарная проверка: ID `CTL-NNN`, сквозная нумерация из трёх цифр в рамках сервиса; ID стабильны, не переиспользуются после удаления.
- **Группа контролей** — именованная точка применения: ID `CTL-GRP-N` (номер без ведущих нулей). Группа отвечает на вопрос «когда выполняется набор проверок»: переход между вкладками по кнопке, подпись документа, приём заявки в банк. Внешние документы (экраны, функции, процессы) ссылаются на группу; ссылка на отдельный `CTL-NNN` допустима ровно в двух случаях — контроль вне групп, либо шаг обращается к конкретной проверке (например, интеграционной), а не к точке применения набора.
- **Подпроверки источника** (нумерация вида 18.1, 18.2) — отдельные контроли `CTL-NNN`: у каждой своя логика и/или своё сообщение об ошибке. Проверки обязательности и формата одного реквизита не сливаются в одну карточку.
- **Нумерация источника не сохраняется** (в ней пропуски и дубли); соответствие «№ строки источника → CTL-NNN» фиксируется в описании MR, не в документе.
- **Контроль вне групп** (запускается в собственной точке, а не в составе набора) — допустим: в карточке вместо поля «Группы» указывается поле «Точка вызова».
- **H1 `README.md`** — «Контроли заявки» (без названия сервиса; если объект проверок не заявка — «Контроли <объект>»).

## Frontmatter

`README.md` (корневой файл документа):

```yaml
---
id: CTL-000
title: '<дословное наименование из title главной страницы-источника>'
type: control
service: <service-id>
confluence_page_ids: [<ID страниц-источников, главная первой; только reverse>]
---
```

Каждый `cards-<slug>.md` (часть документа, без собственного `id` — conventions §5):

```yaml
---
partOf: CTL-000
type: control
service: <service-id>
confluence_page_ids: [<ID страниц-источников, главная первой; только reverse>]
---
```

## Структура документа

Разделы 1–4 — в `README.md`, порядок фиксированный; сами карточки — в файлах `cards-*.md`.

### 1. Назначение (обязательный)

1–2 абзаца: что проверяется (сущность — полной ссылкой `<ссылка [ENT-NNN <название>](…)>`), кто выполняет проверки (система, автоматически), что даёт результат (блокирует переход/подпись, показывает сообщение об ошибке).

### 2. Группы контролей (обязательный)

Таблица:

| ID | Контур | Точка применения/Привязка | Где используется |
|---|---|---|---|

Правила:

- **Контур** — `FE` или `BE`, проставляется явно (решение владельца
  2026-08-29: контур — данные разметки, не вывод из текста; сторож
  сверяет согласованность колонки с формулировкой привязки).
- **Точка применения/Привязка** — «Точка применения» — термин эталона
  (для FE он точен); для BE понятие обобщено до привязки (переход /
  операция), двойное имя колонки увязывает новую модель с эталоном.
  Содержимое зависит от контура:
  - `FE` — UI-событие пользовательским языком: «при нажатии кнопки
    „Продолжить“ на вкладке „…“», «при загрузке скана». Кодовые имена
    платформы не пишутся.
  - `BE` статусный — ПЕРЕХОД статусной модели: «переход
    `<ссылка [ENT-NNN](…)>` в статус `X`». Места инициирования
    (кнопки, экраны, интеграции) НЕ перечисляются: сервер валидирует
    переход и не знает, откуда пришёл запрос (API First); перечень
    триггеров заведомо неполон и молча устаревает. Связка
    «UI-событие → вызов перехода» живёт в карточках кнопок/функций.
  - `BE` нестатусный — серверная операция: «при выполнении
    `<ссылка [FUN-… …](…)>`» (импорт файла, сохранение вложения).
- Одно UI-событие двух контуров (нажатие ведёт и к FE-проверкам полей,
  и к вызову перехода с BE-проверками) — ДВЕ группы, по одной на
  контур; карточка кнопки ссылается на обе ступени по порядку.
- **Где используется** — ссылки на экраны, функции, процессы: `<ссылка [SCR-CL-NN …](…)>`, `<ссылка [FUN-CL-NN …](…)>`, ссылка на документ процесса. Это навигация для читателя; трассировка — в матрице. Имена ещё не мигрированных целей (ожидатели долгов матрицы) живут ЗДЕСЬ, не в привязке — иначе сторож долгов вынуждает возвращать перечни функций-инициаторов в BE-привязку (конфликт приёмки дозахода №3, 2026-08-29).
- Если источник задаёт общее для группы правило отображения результатов (например, «ошибки показываются под полями, переход блокируется»), оно описывается абзацем после таблицы, а не повторяется в каждой карточке (типовое различие контуров: FE — ошибка под полем, BE — списком по всей группе).

### 3. Реестр контролей (обязательный)

Сводная таблица-оглавление, без логики:

| ID | Проверяемый атрибут | Проверка | CTL-GRP-1 | CTL-GRP-2 | … |
|---|---|---|---|---|---|

- **ID** — ссылкой на карточку: файл карточек + якорь заголовка, например `cards-account.md#ctl-007-…`.
- Принадлежность группе — `✓` / `—`. Колонка на каждую группу из раздела 2; контроль вне групп получает `—` во всех колонках.
- Контроль, помеченный источником как неактуальный, получает в колонке «Проверка» пометку «(неактуален)» после названия.
- Реестр — сводка для обзора; истина о принадлежности группам — в карточках (поле «Группы»). Их совпадение — пункт чек-листа.

### 4. Карточки контролей (обязательный)

В `README.md` раздел 4 — таблица-оглавление файлов карточек: «Файл | Контроли | Тема». Сами карточки — в файлах `cards-*.md`.

Каждый контроль — H3-заголовок `CTL-NNN. <Название>`. Порядок карточек внутри файла — по возрастанию ID. Название уникально в документе и включает проверяемый объект: «<Реквизит/объект>: <название проверки>» (например, «БИК счёта для списания комиссии: обязательность заполнения») — иначе однотипные проверки разных полей дадут одинаковые заголовки и конфликт якорей.

Поля карточки (маркированный список; необязательные поля при отсутствии опускаются):

- **Проверяемый атрибут** (обязательное) — точечной нотацией `<ссылка [ENT-NNN](…)>.«Атрибут»`. Если проверяется обязательность полей вкладки в целом (контроль уровня формы; прежнее рабочее название «зонтичный») — карточка описывает **механизм** и ссылается на **якорь раздела «Реестр полей»** вкладки `<ссылка [SCR-…-NN.K …](…/screen-form/…)>` (источник истины об обязательности — экранная форма, не карточка контроля); в логике фиксируется, что проверяются **только отображаемые** поля. Состав полей в карточке не перечисляется.
- **Условие выполнения** (необязательное) — когда контроль вообще запускается («только если …»). Если запускается всегда — поле опускается.
- **Логика проверки** (обязательное) — конструкцией **Если** … **то** проверка пройдена, **иначе** ошибка (жирным, конвенции §4); условие — чистый предикат без логики получения значений и без реакций на исход ([notation.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/notation.md) §1 «Чистота условия»); многошаговая логика — нумерованными шагами. Данные — по правилу конвенций §5: атрибуты точечной нотацией, первое упоминание сущности в документе — полная ссылка. Обращение к внешней АС — ссылкой на карточку вызова `<ссылка [CALL-EXT-NNN <название>](…)>` (вызов внутри Экосистемы — `CALL-INT-NNN`; к платформенной функции/проверке без спецификации — `<ссылка [PLT-NNN <название>](…)>`); протокол и формат обмена не дублируются.
- **Сообщение об ошибке** (обязательное) — дословный текст в кавычках + способ отображения (под полем / информер / модальное окно). Подстановки в тексте — в угловых скобках с расшифровкой, откуда берётся значение. Модальное окно, описанное отдельным экраном сервиса, — ссылкой; платформенные экраны вне сервиса — текстом, без ссылок.
- **Неактуален** (необязательное) — для контроля, который источник помечает неактуальным (соответствующая функциональность недоступна в текущей версии сервиса): пометка с причиной по источнику. Неактуальные контроли из документа не исключаются — переносятся со всеми полями, которые задаёт источник; отсутствующие в источнике поля опускаются, пробел фиксируется в open-questions.
- **Группы** (обязательное для контролей в группах) — перечень ID групп через запятую: `CTL-GRP-1, CTL-GRP-3`. Внутри каталога `control/` ID групп и контролей пишутся без ссылок — документ сам является их реестром.
- **Точка вызова** (вместо «Группы» — для контроля вне групп) — откуда и когда вызывается, пользовательским языком. Если источник точку вызова не задаёт — поле опускается, вопрос фиксируется в open-questions.

## Ссылки на контроли из других документов

- **Всегда ID + название** (конвенции §5), во всех упоминаниях: группа `<ссылка [CTL-GRP-N <точка применения кратко>](…/control/README.md)>`, отдельный контроль `<ссылка [CTL-NNN <название>](…/control/cards-<slug>.md#…)>`. Голый ID без названия и без ссылки не используется.
- Экранная форма у кнопки/действия: «выполняются контроли группы `<ссылка [CTL-GRP-N <точка применения>](…)>`»; состав контролей не перечисляется.
- Функция или процесс: шаг поведения ссылается на группу; отдельный контроль указывается, когда шаг задействует именно его (например, интеграционную проверку).
- Ссылка на группу или документ в целом ведёт на `control/README.md`; ссылка на конкретный контроль — на файл карточек (`control/cards-<slug>.md`), якорь карточки допустим, но при переименовании карточки обновляются все якорные ссылки.

## Что не переносится из источника

- Нумерация источника, пустые строки-обрывки таблицы.
- Ссылки на макеты Figma, URL Confluence, pageId, домены сред, ссылки на sources.
- Черновые пометки, упоминания legacy-сервиса.

## Трассировка

- **Реестр ID матрицы**: строка на документ (`CTL-000`, файл `control/README.md`) + строка на каждую группу `CTL-GRP-N` (файл `control/README.md`) + строка на каждый контроль `CTL-NNN` (файл — его файл карточек `control/cards-<slug>.md`).
- **Покрытие (функции → артефакты)**: в колонке «Контроли (CTL)» у функции указываются **группы** `CTL-GRP-N`, которые функция запускает; отдельный `CTL-NNN` — только для контроля вне групп или когда функция задействует конкретный контроль, а не набор. Состав «группа → контроли» в матрице не разворачивается — он зафиксирован в `control/` (реестр + карточки) ровно один раз.
- **Этап 2 (REQ)**: контроль уже атомарное требование — `CTL-NNN` выполняет роль ID требования, перенумерация в `REQ-…` не планируется.

## Чек-лист самопроверки

1. Frontmatter полный: `README.md` — `id: CTL-000`; каждый `cards-*.md` — `partOf: CTL-000` без собственного `id` + `entity: <ID сущности/формы файла>`; `type`/`service` одинаковы во всех файлах каталога `docs/srs/control/`; каждая карточка лежит в файле своей сущности (сверяется по «Проверяемому атрибуту»).
2. ID групп и контролей уникальны; каждый зарегистрирован в реестре ID матрицы: группы — с файлом `control/README.md`, контроли — со своим файлом карточек.
3. Точки применения групп — пользовательским языком, без кодовых имён платформы; ссылки «Где используется» существуют.
4. Реестр (раздел 3) согласован с карточками (раздел 4): каждый CTL реестра имеет карточку и наоборот, принадлежность группам совпадает.
5. Названия карточек уникальны и включают проверяемый объект.
6. Атрибуты — точечной нотацией `[ENT-NNN](…).«Атрибут»`, голых атрибутов нет; первое упоминание сущности — полная ссылка.
7. Тексты сообщений — дословно, в кавычках, со способом отображения; подстановки расшифрованы.
8. Логика воспроизводима: условия, ветвления в форме **Если**/**то**/**иначе** (жирным), шаги; обращения к внешним АС — ссылками на CALL, к платформенным функциям/проверкам — на PLT.
9. Неактуальные контроли перенесены с пометкой «Неактуален» и причиной; пробелы источника (неопределённая точка вызова, отсутствующая логика) зафиксированы в open-questions.
10. Ссылки ведут только внутрь `docs/` и все существуют; в документе нет ссылок на sources/Confluence/Figma, inline-TODO, отсылок к OQ.
11. Матрица трассировки обновлена в том же изменении (реестр ID + колонка CTL в покрытии функций).
