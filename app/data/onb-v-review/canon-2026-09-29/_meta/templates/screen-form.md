# Шаблон: экранная форма (SCR)

Шаблон документа экранной формы в `docs/srs/[<подсервис>/]screen-form/<контур>/`. Общие правила — [conventions.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md); при противоречии истина в конвенциях.

Формат зафиксирован по итогам пилота вкладки «Открываемый счёт»: **событийная модель** — статика полей отделена от поведения, поведение описано событиями (триггер → шаги), логика — конструкцией **Если**/**то**/**иначе**, вызовы внешних систем и платформы не сворачиваются.

## Идентификация и размещение

- **ID по контурам, номер из двух цифр**: экраны Клиента — `SCR-CL-NN`, экраны Банка — `SCR-BNK-NN`. Сквозная нумерация в рамках контура; ID стабильны, не переиспользуются.
- **Экран из одной части** — один файл `scr-cl-NN-<короткое-название>.md` (латиница, kebab-case).
- **Экран из частей** — папка `scr-cl-NN-<короткое-название>/`. Часть —
  это вкладка UI **или** дочерняя страница-источник, делящая описание
  (решение 2026-08-17: источник может разносить одну форму без вкладок
  по дочерним страницам — «Документ → реквизиты»; называть такие части
  «вкладками» — приписывать форме несуществующий UI):
  Роли файлов группы (решения владельца 2026-08-30/31; принцип «один
  факт — один дом»: дублирование разделов между файлами запрещено):
  - `README.md` отвечает на вопрос «ГДЕ ЧТО ЛЕЖИТ». Чистое оглавление
    БЕЗ frontmatter (вне сверки, Р-9) и БЕЗ разделов карточки. Состав:
    H1 — ДОСЛОВНОЕ наименование источника, включая теги «[XX_YY]»
    (решение владельца 2026-08-31: реестр контура показывает полное имя
    — по клику читатель должен увидеть его же, иначе сомневается, туда
    ли попал; в карточках-требованиях H1 модифицирован суффиксами, там
    опущение тега приемлемо); одна строка-аннотация СВОИМИ словами со
    ссылкой («Оглавление
    экрана. Что экран делает и как ведёт себя как целое — в
    [главной карточке](scr-cl-NN-main.md); устройство разделов — в
    карточках частей.»); таблица «Части» (главная карточка первой
    строкой); «Макеты ЭФ» (ссылки Figma — только здесь). Разделов
    «Назначение» и «Как перейти» в README НЕТ — они дословные и живут
    в главной карточке.
  - `scr-cl-NN-main.md` — ГЛАВНАЯ КАРТОЧКА экрана, отвечает на вопрос
    «ЧТО ЭТО И КАК РАБОТАЕТ КАК ЦЕЛОЕ». Несёт ID ЭКРАНА
    (`id: SCR-CL-NN` — суб-ID .0 не используется) и
    `confluence_page_ids` главной страницы — вся сверка с источником
    здесь. H1 = H1 экрана + « — главная карточка». Состав: дословные
    «Назначение» и «Как перейти»; раздел «Структура экрана» (строка
    «UI-вкладок форма не имеет; деление — по страницам-источникам» для
    частей-не-вкладок; таблицы частей здесь НЕТ — она в README); FLD
    шапки/боковой панели, реестр полей уровня страницы, видимость
    блоков, шаги открытия/закрытия, события/кнопки/сообщения уровня
    страницы, таблица групп контролей уровня формы, определения,
    используемые ≥2 частями. В таблицу групп уровня формы НЕ входят
    группы, имеющие носителя на форме (поле/кнопку/событие) — они
    указываются у носителей; группы других форм и серверных
    переходов/операций в таблице не живут (их места держит «Где
    используется» реестра контролей). Если групп уровня формы нет —
    раздел опускается целиком (решение владельца 2026-08-31: сводная
    таблица всех групп дублировала носителей и противоречила
    собственному определению раздела). Каждый из перечисленных разделов —
    САМОСТОЯТЕЛЬНЫЙ H2 со сквозной нумерацией («## 2. Как перейти на
    ЭФ»), не подраздел «Назначения» (замечание владельца 2026-08-31:
    H3-вложение под Назначение — наследие старых README). Раздела
    «Макеты» в главной карточке НЕТ — ссылки Figma живут только в
    README; структурная сверка ячейки макетов прибором не выполняется
    (наличие ссылок в README держит сторож группы).
  - файл на каждую часть с суб-ID `SCR-CL-NN.K` отвечает на вопрос
    «КАК УСТРОЕН РАЗДЕЛ N». Имя `scr-cl-NN.K-<название>.md` — название
    СПЕЦИФИЧНОЕ по содержимому (`scr-cl-03.1-account.md`, не
    `…-main.md`: «main» зарезервировано за главной карточкой и как имя
    части ничего не говорит). Определение, используемое только одной
    частью, — в ней.
- **README всегда навигационный** (решение 2026-08-30; ранее README
  папки экрана был содержательной карточкой — модель отменена: читатель,
  ждущий оглавления, получал сотни строк алгоритмов). README-реестр
  каталога `docs/srs/screen-form/<контур>/` — как прежде: навигационный
  реестр форм контура (правила — docs-readme).
- **H1**: название экранной формы с контуром, без названия сервиса — «ЭФ Клиента «…»» / «ЭФ Банка «…»». Для вкладки UI — H1 родителя + « — вкладка «<название вкладки>»»; для части-страницы — H1 родителя + « — «<название части по источнику>»».
- **Заглушка** — файл с frontmatter, разделом «Назначение» и строкой «Документ-заглушка: …»; в реестре ID матрицы — пометка «заглушка» прозой (без поля статуса, conventions §5).

## Frontmatter

```yaml
---
id: SCR-CL-NN | SCR-CL-NN.K
title: '<дословное наименование из title главной страницы-источника>'
type: screen-form
service: <service-id>
confluence_page_ids: [<ID страниц-источников, главная первой; только reverse>]
---
```

## Структура документа

Порядок разделов фиксированный; необязательные разделы при отсутствии содержимого опускаются целиком. Счётное правило: §5 опускается, если у формы нет событий (реакций на открытие и изменение полей); §6 — если нет кнопок; §7 — если нет сообщений; §8 — если источник не описывает функций формы. Опущенный раздел не пересказывается «кратко» в §4 — поведение либо описано событием/кнопкой, либо его нет.

### 1. Назначение (обязательный)

1–2 предложения: что делает форма для пользователя. Для вкладки — её роль в экране, ссылка на `<ссылка [README](README.md)>` экрана и на функции, открывающие форму (`<ссылка [FUN-CL-NN …](…)>`).

### 2. Реестр полей (обязательный)

Таблица-обзор состава формы. **Одна широкая текстовая колонка не заводится** (конвенции §4: реестры — без широкой прозаической колонки) — детальные правила выносятся в §4 (FLD-N):

| № | Блок | Поле | Тип | Обяз. |
|---|---|---|---|---|
| 1 | — | FLD-1 «Заголовок» | Текст | — |
| 2 | Счёт | FLD-2 «Счёт списания» | Список | Да |

Правила:

- **№** — номер поля в порядке отображения: есть блоки (§3) — вложенная нумерация `2`, `2.1`; блоков нет — сквозная. Номер — не идентификатор (при вставке поля перенумеровывается); для ссылок на поле используется его `FLD-N`.
- **Поле** — `FLD-N «Название»`: **каждая строка реестра несёт стабильный ID поля** (образец — строки таблицы выше). N — следующий свободный номер в документе; ID не перенумеровываются и не переиспользуются, номер не обязан совпадать с позицией строки. Упоминание поля в тексте документа — всегда по `FLD-N` (имя без ID неуникально и не проверяется машинно).
- **Блок** — название блока-группы (тем же значением у всех полей блока); видимость блоков — §3.
- **Тип** — канонический UI-тип из словаря [notation.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/notation.md) §4 («Текст», «Список», «Переключатель», «Чекбокс»…); способ получения значения в тип не примешивается («текст, автоматически» — ошибка нормализации: тип «Текст», автозаполнение — в правиле поля).
- **Обяз.** — **источник истины об обязательности полей — экранная форма** (не карточка контроля): `Да` / `Нет` / «условно — `<ссылка [CTL-NNN <название>](…)>`» (когда обязательность зависит от условия и оформлена отдельным контролем). Зонтичный контроль «обязательность полей вкладки» описывает **механизм** и ссылается на якорь этого реестра, состав полей не перечисляет; проверяются только поля, отображаемые в момент проверки (в тексте документа такой контроль упоминается, как и любой другой, — ссылкой «ID + название»).
- **Сохранение (опционально):** если форма сохраняет данные в сущность, добавляется колонка «Атрибут» с точечной нотацией `<ссылка [ENT-NNN](…)>.«Атрибут»` — маппинг «поле → атрибут». Вычисляемые реквизиты (номер, дата, статус) и порождение записей/вложений выносятся в отдельную функцию «Сохранить заявку» (см. «Сохранение данных формы»).

Преамбула раздела: одной фразой — где проверяется обязательность (группа `<ссылка [CTL-GRP-N <точка применения>](…)>`) и указатель на разделы 3–7.

### 3. Видимость блоков (обязательный, если блоков больше одного)

**Отдельный раздел**, каждый блок — с новой строки маркированным списком: «<Блок> — <условие отображения>». Блок, видимый всегда, — «отображается всегда». Составное условие — вложенным списком (каждое подусловие с новой строки).

### 4. Правила полей (обязательный)

Статика полей — подразделы `### FLD-N. «<Поле>»` — **на каждое поле реестра** (биекция: каждая строка §2 имеет подраздел, каждый подраздел — строку §2; проверяется чек-листом машинно). Только **статика**: значения/источник списка, формат отображения, предзаполнение, видимость и доступность поля, подсказки, тексты-константы. Реакции на действия пользователя — **не здесь**, а в §5 (события).

Допущение-свёртка (чтобы биекция не плодила пустые подразделы): соседние **презентационные** поля (заголовки разделов, тексты-константы) с тривиальной статикой — видимость «всегда», без условий, умолчаний и источников — могут разделять один общий подраздел; все их `FLD-N` перечисляются в его заголовке через запятую, биекция при этом сохраняется (несколько строк реестра → один общий подраздел). Поле с условием видимости/доступности, умолчанием, источником списка или форматом — всегда отдельный подраздел. Образец свёрнутого подраздела:

```markdown
### FLD-1, FLD-5. Заголовки «Оплата комиссии», «Реквизиты»

- **Видимость:** всегда; тексты — константы макета.
```

**Атрибуты статики — нормированный словарь, фиксированный порядок**
(решение 2026-08-16, модель ЭФ этап 1; состав и порядок — из
событийного формата ЭФ, авторитет по структуре FLD): каждый факт
подраздела FLD-N — отдельный буллет, начинающийся ярлыком атрибута
**жирным** с двоеточием; голому условию без ярлыка в подразделе не
место (прецедент FLD-14 «Светофор»: условие видимости, записанное
просто абзацем, машинно неотличимо от пояснительного текста).
Стандартные атрибуты — строго в этом порядке; **неприменимый атрибут
опускается целиком** (строка не пишется; прочерк «—» вместо значения
запрещён — прочерки легальны только в ячейках таблиц-реестров);
отсутствие атрибута в источнике — не пробел и не спорное место.

1. **Тип:** — UI-тип из словаря нотации (тот же, что в реестре §2;
   способ заполнения в тип не примешивать).
2. **Формат:** — формат вывода, маска/шаблон ввода, пример,
   плейсхолдер; при различии представлений — под-ярлыки **В списке:**
   / **В поле:**.
3. **Способ заполнения:** — Вручную / Выбор из списка / Автоматически;
   здесь же редактируемость/доступность/блокировка поля, в т.ч.
   условная.
4. **Обязательность:** — Да / Нет / условная форма «Да, **если**
   <условие>; **иначе** — Нет» (свод «Обяз.» — в §2; критерий-тест:
   при невыполнении условия поле исчезает с формы — это видимость;
   остаётся, но требует заполнения — условная обязательность).
5. **Видимость:** — показ/скрытие поля и лейбла («всегда» — явно).
6. **Логика установки значения:** — откуда значение; внутри — ЗАКРЫТЫЙ
   реестр под-ярлыков: **Источник списка:** / **По умолчанию:**
   (предзаполнение) / **При открытии на редактирование:** /
   **Переформирование списка:**. Момент срабатывания пересчёта — шаг
   события §5, здесь только правило.

**Дополнительные атрибуты** — только после стандартных, из закрытого
реестра: **Сортировка:** / **Поиск:** / **Подсказка:** / **Действие:**
(что открывает нажатие на текст-ссылку) / **Особый случай:** (ссылка
на MSG-N) / **Заголовок:** (отображаемый лейбл поля/блока, когда он
отличается от наименования или вычисляется — «Ошибки»/«Предупреждения»
по типу ошибки; решение 2026-08-17). Новые ярлыки — правкой шаблона
(ревью канона), не самодеятельно в карточке. Маппинг на атрибут сущности — колонкой
«Атрибут» реестра §2 (структурное слияние с атрибутом «Элемент
данных:» событийного формата — отложено).

Образец подраздела (неприменимые атрибуты опущены, строк с прочерками
нет):

```markdown
### FLD-4. «Счёт списания»

- **Тип:** Список
- **Формат:** Маска номера счёта: 408XX…
- **Способ заполнения:** Выбор из списка
- **Обязательность:** Да, **если** в FLD-2 выбрано «Со счёта»; **иначе** — Нет
- **Видимость:** всегда
- **Логика установки значения:**<br>**Источник списка:**<br>счета Организации по `<ссылка [CALL-INT-NNN …](…)>`.<br><br>**По умолчанию:**<br>**Если** в списке один счёт, **то** поле заполняется им и блокируется.
```

**Атрибут = элемент данных.** Поля разных форм, замапленные на один
атрибут сущности (колонка «Атрибут» §2), — ПРЕДСТАВЛЕНИЯ одного
элемента данных. Статика представлений может расходиться (на одной
форме поле редактируемо, на другой — только чтение), но расхождение
должно быть сознательным: при переносе сверить подразделы FLD у форм с
тем же атрибутом; необъяснённое расхождение (разные маски, разные
источники списка) — спорное место, предмет ревью, а не молчаливый
перенос.

Данные — по конвенциям §5: первое упоминание сущности — полная ссылка `<ссылка [ENT-NNN <название>](…)>`, далее короткая; атрибут — `<ссылка [ENT-NNN](…)>.«Атрибут»`. Справочники и настраиваемые параметры — ссылками на `data-model/`.

### 5. События (обязательный для форм с логикой)

Сводная таблица + детализация. Сводка:

| ID | Триггер | Суть реакции |
|---|---|---|

Затем на каждое событие — подраздел `### EV-N. <Триггер>` с шагами. Правила:

- **Триггеры**: открытие формы; выбор/изменение конкретного поля; установка чекбокса. Нажатие кнопок — **не событие**, а раздел 6.
- **Логика — конструкцией Если/то/иначе**: слова **Если**, **то**, **иначе**, **иначе если** выделяются жирным; каждое условие и исход — с новой строки. Многошаговый сценарий — нумерованными шагами с переходами «— шаг N».
- **Вызовы внешних систем не сворачиваются** (см. «Вызовы …» ниже): ссылка на карточку `<ссылка [CALL-EXT-NNN <название>](…)>` (внутри Экосистемы — `CALL-INT-NNN`), какие параметры запроса передаются и как обрабатывается ответ.
- **Платформенные функции и проверки** — ссылкой `<ссылка [PLT-NNN <название>](…/platform-functions.md#…)>`.
- **Контроли** — ссылкой `<ссылка [CTL-NNN <название>](…)>` или группой `<ссылка [CTL-GRP-N <точка>](…)>` (всегда ID + название).
- **Статусы** — системными кодами (`DRAFT`, `NEW`…) со ссылкой на `<ссылка [справочник статусов](…/data-model/dictionaries.md)>` / `<ссылка [статусную модель](…/process/status-model.md)>`.
- **Сообщения** — по ID (MSG-N), тексты не дублируются (они в §7).
- Повторно используемый набор шагов описывается один раз; другие события ссылаются диапазоном «шаги N–M события EV-1».

### 6. Кнопки (обязательный, если на форме есть кнопки)

**Отдельный раздел**. Каждая кнопка — подраздел `### B-N. «<Название>» (<расположение>)` с полями: **Видимость**, **Активность** (если зависит от условий), **При нажатии** (шаги в той же логике Если/то/иначе; вызовы — по тем же правилам, что в §5). Контроли, запускаемые кнопкой, — ссылкой на группу.

### 7. Сообщения (обязательный, если форма показывает сообщения)

Таблица дословного контента — ровно одна широкая колонка «Содержание» (конвенции §4):

| ID | Тип | Показ | Содержание |
|---|---|---|---|

- **Тип** — «Информер», «Блоккер», «Плашка», «Модальное окно» (как в источнике).
- **Показ** — где определено условие отображения (шаг события EV-N или правило поля FLD-N).
- **Содержание** — заголовок, дословный текст в кавычках, кнопки и их действия (вызовы — ссылками на FUN/PLT). Подстановки — в угловых скобках с расшифровкой источника значения.
- **Тексты ошибок контролей не дублируются** — они в карточках CTL; сообщение ссылается на контроль.
- Указание на скрытие/блокировку полей при показе сообщения — здесь же.

### 8. Функции формы (обязательный, если источник их описывает)

Именованные повторно используемые наборы шагов ЭТОЙ формы («функции
формы» источника): работают с полями ЭФ напрямую, собственных страниц и
входных сигнатур не имеют — самостоятельными функциями FUN **не
являются**, в реестр функций и матрицу не попадают (решение
2026-08-17). Каждый набор — подраздел `### FF-N. «<Название из
источника>»`; шаги — дословно, с маркерами источника. Кнопки, события и
другие наборы ссылаются якорем `[FF-N «<название>»](#…)`; упоминание
функции формы словами без ссылки — дефект. Маппинг параметров вызова
настоящей функции (FUN/CALL/PLT) — при шаге вызова, по правилу
«вызовы не сворачиваются».

Два отклонённых искажения (не делать): выносить шаги в отдельную
карточку FUN — нельзя (пришлось бы выдумывать входную сигнатуру,
которой нет в источнике, — суррогат; шаги теряют контекст полей ЭФ);
дублировать шаги в тело каждой вызывающей кнопки — нельзя (набор
вызывается из многих мест, правка даёт лавинный дифф).

### Боковая часть (опционально)

Если форма имеет боковую часть с блоком «Статус» — описывается отдельным подразделом: бэйдж = отображаемое клиенту название статуса, текст-пояснение = колонка «Пояснение клиенту» справочника статусов (`<ссылка [справочник статусов](…/data-model/dictionaries.md)>`). Тексты пояснений живут в справочнике, форма на них ссылается (не дублирует).

## Внутренние идентификаторы

Стабильные идентификаторы для ссылок из задач разработки и тест-кейсов, уникальные в пределах документа:

- `FLD-N` — правило поля (раздел 4);
- `EV-N` — событие (раздел 5);
- `B-N` — кнопка (раздел 6);
- `MSG-N` — сообщение (раздел 7);
- `FF-N` — функция формы, именованный набор шагов (раздел 8).

Нумерация источника (2.1.6 и т.п.) в идентификаторы не переносится; соответствие фиксируется в описании MR, не в документе.

## Вызовы внешних систем, платформы и контролей

- **Внешняя банковская АС** (КНОСИС, ЕСК, ТЕССА, РКО Ф1, БСК) — карточка `CALL` в `contract-call/`. Если карточки нет (страница метода вне выгрузки) — **завести заглушку** (скилл `create-contract-call`), а не оставлять голый текст; пробел — в `open-questions.md`.
- **Платформенная функция или проверка ЭКО** (вне контура сервиса: проверка сертификата ЭП, контроль доступности функций, онбординг, резервирование, обновление сведений и т.п.) — запись `PLT` в `docs/srs/platform-functions.md`. Нет записи — добавить (заглушкой).
- **Контроль данных заявки** — `CTL` в `control/`; ссылка **всегда ID + название** (и на группу `CTL-GRP-N`, и на отдельный `CTL-NNN`).
- **Функция сервиса** — `FUN`; **процесс** — `PROC`.
- Платформенные UI-экраны вне сервиса и навигация (главная, сайт банка, тарифы) — текстом, без ссылок; кодовые имена платформенных интерфейсов не пишутся.

## Сохранение данных формы

Маппинг «поле → атрибут» — колонкой «Атрибут» в реестре полей (§2). Всё, что не сводится к прямому маппингу (вычисление номера/даты, **правило вычисления статуса**, порождение печатных форм и вложений, запись связанных сущностей), — в отдельной функции `FUN-CL-NN` «Сохранить заявку» (шаблон `function.md`); форма в шагах событий/кнопок ссылается на неё словами «сохранение заявки» → ссылка на функцию. Это правило — о СЕРВЕРНОЙ логике сохранения (у неё есть или будет своя карточка функции); клиентская оркестрация формы вокруг вызова (обновление полей после ответа, диалоги ошибок, предварительное сохранение перед печатью) — «функция формы», раздел 8 (FF-N).

## Чек-лист самопроверки

1. Frontmatter полный; `id` соответствует контуру и не занят (реестр ID матрицы); имя файла = `<id строчными>-<название>.md`, экран из частей — папка + навигационный README (БЕЗ frontmatter, без разделов карточки) + главная карточка `scr-…-nn-main.md` (id экрана) + файлы частей со специфичными названиями; части-не-вкладки не названы «вкладками» (главная карточка несёт строку «UI-вкладок форма не имеет» в «Структуре экрана»).
2. H1 без названия сервиса, с контуром; вкладка — H1 родителя + «— вкладка «…»»; часть-страница — H1 родителя + «— «…»».
3. Реестр полей без широкой прозаической колонки; **каждая строка несёт `FLD-N`**; обязательность проставлена в реестре (`Да`/`Нет`/условно — CTL); контроль УРОВНЯ ФОРМЫ (применяется к форме целиком в момент её события, а не к отдельному полю — термин 2026-08-29, прежнее рабочее название «зонтичный») ссылается на якорь реестра, а не наоборот.
3a. **Биекция реестр ↔ подразделы §4**: каждая строка §2 имеет подраздел FLD-N (или входит в общий свёрнутый подраздел презентационных — её ID в его заголовке), каждый подраздел — строку §2; полей-фантомов (упомянут в тексте, нет в реестре) нет.
4. Видимость блоков — отдельным разделом, каждый блок с новой строки.
5. §4 — только статика; реакции на действия — в §5/§6. Каждый факт FLD-подраздела — буллетом под жирным ярлыком словаря в фиксированном порядке (Тип → Формат → Способ заполнения → Обязательность → Видимость → Логика установки значения; дополнительные — после); голых условий без ярлыка нет; неприменимые атрибуты опущены (строк с прочерками нет); расхождения статики полей с одним атрибутом — осознаны (проверены против других форм).
6. Логика везде в форме **Если**/**то**/**иначе** (жирным, с новой строки).
7. Вызовы внешних АС — ссылками на CALL с параметрами запроса и обработкой ответа; отсутствующие карточки заведены заглушками. Платформенные функции/проверки — ссылками на PLT; отсутствующие заведены.
8. Ссылки на контроли — всегда ID + название (контроль и группа).
