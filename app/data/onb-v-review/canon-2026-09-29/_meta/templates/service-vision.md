# Шаблон: концепция сервиса (Service Vision)

Как устроен документ концепции сервиса и по какому формату он пишется. Назначение — **верхнеуровневая рамка сервиса**: зачем он, для кого, что в охвате и на каких условиях доступен. Это входная точка комплекта SRS: из неё читатель (человек или ИИ-агент) понимает границы прежде, чем углубляться в функции, экраны и процессы.

## Состав комплекта

```
docs/
└── service-vision.md      # единственный файл концепции сервиса (корень docs/, рядом с glossary.md)
```

Правила:

- **Один файл** `service-vision.md` в корне `docs/` (на уровне `glossary.md` и `traceability-matrix.md`); отдельную папку не создаём. Не класть в `brd/` или `srs/`. Это **входная точка комплекта**: из неё читатель понимает, что за сервис и что у него есть клиентская и банковская части.
- **H1 сохраняет название сервиса** — концепция в списке исключений `conventions.md` §5 (наравне с `glossary.md` и `data-model/README.md`).
- **Верхнеуровневый, не дублирующий.** Концепция даёт рамку и смысл; детали живут в профильных документах: функции — в `srs/function/`, экраны — в `srs/screen-form/`, процессы и статусы — в `srs/process/`, контроли — в `srs/control/`, роли — в `srs/rbac.md`, термины — в `glossary.md`. В концепции — **что и зачем**, со ссылкой-делегированием на детали. Перечни ID (FUN/SCR/CTL/CALL) в концепцию не переносим.
- **Клиентская и банковская части — обязательный раздел** (после «Акторы»): кратко, таблицей — кто работает в каждом контуре и какова роль в жизненном цикле; суффиксы CL / BNK / SYS делегировать в README комплекта (`README.md#условные-обозначения`). После существенного обновления концепции актуализируй `docs/README.md` (скилл `create-docs-readme`).
- **Условия доступности — обязательный раздел.** Кому и при каких условиях сервис доступен (статус клиента, договоры, полномочия пользователя) — фиксируется здесь бизнес-языком; вычислимые проверки делегируются контролям.
- **Не выдумывать.** Факт, не раскрытый в источнике/комплекте, — не сочиняем: пробел в `output/<service>/open-questions.md` (вне `docs/`, `conventions.md` §6). Отсылок к OQ в документе нет.
- **Язык — бизнес-аналитика, не технический** (`conventions.md` §4): смысл «что и зачем»; без имён процессов, тегов, кодов и жаргона платформы. Технический термин — только с бизнес-расшифровкой.
- **Ссылки** (как в целевом документе): только внутри `docs/` (`conventions.md` §5, переносимость) — на `glossary.md`, `srs/control/README.md`, реестры разделов, `README.md`. Голых ID и ссылок за пределы `docs/` нет.
- **Весь файл шаблона** — без markdown-ссылок `[текст](путь)`; места, где в целевом документе нужна ссылка, помечаются `<ссылка […](…)>`. Имена файлов без ссылки — в backticks: `glossary.md`, `srs/control/README.md`.

## Три режима наполнения

### Режим A — reverse (восстановление из источников)
Базовый поток — `create-artifact` с типом `vision`. Рамка сервиса — из актуальной выгрузки Confluence (`conventions.md` §1): страницы продукта, процесса, ролевой модели, смежных систем. Фильтр: только новый сервис (§3), актуальная версия, включая QR/СБП (§2). Нераскрытое — в open-questions (§6).

### Режим B — forward (проектирование по требованиям)
Если концепция проектируется без AS-IS источников, агент задаёт аналитику: назначение и целевая группа; акторы и смежные системы; что в охвате / вне охвата; условия доступности (сценарии, договоры, полномочия); измеримые бизнес-цели.

### Режим C — sync (сборка из готового комплекта SRS)
Когда SRS-документы сервиса уже написаны, а концепция отстаёт или её нет: источник — **сам комплект** `docs/srs/`, не `sources/`. Порядок:

1. Собери рамку из комплекта:
   - акторы, роли, доступ — `srs/rbac.md`, `glossary.md` (роли и акторы); клиентская/банковская части — по каталогам `client/` / `bank/` в функциях и экранах;
   - смежные системы и сервисы экосистемы — `glossary.md` (смежные системы), `srs/contract-call/`, `srs/platform-functions.md`;
   - ключевые возможности — реестр `srs/function/README.md` и `traceability-matrix.md`;
   - типы объектов домена и их доступность (в т. ч. временно отключённые) — `glossary.md`, `srs/data-model/`, `srs/control/` (пометки «временно отключён»);
   - **условия доступности** — `glossary.md` (термины «Доступность сервиса», «Полномочие») и `srs/control/` (контроль наличия рамочного договора и контроль полномочий уполномоченного лица);
   - границы (что вне охвата, legacy) — `glossary.md`, `traceability-matrix.md` («вне трассировки»).
2. Сопоставь с текущей концепцией: чего не хватает, что расходится с комплектом.
3. Внеси/уточни разделы строго по шаблону; детали делегируй ссылками; нераскрытое — в open-questions.
4. Прогони чек-лист самопроверки; исправь найденное.

Команда для этого режима — скилл `create-service-vision` (режим `sync`), при необходимости обёрнутый в `/goal` с ограничением итераций.

## Чек-лист самопроверки (критерии приёмки; до отправки MR на ревью)

### Формальное соответствие (conventions §5)
- [ ] Frontmatter заполнен: `id: VIS-001`, `type: vision`, `service`. **Поля `status` нет.**
- [ ] Имя файла — фиксированное `service-vision.md`; H1 сохраняет название сервиса (разрешённое исключение).
- [ ] Присутствуют разделы: Назначение, Целевая группа, Акторы, Клиентская и банковская части, Потребности, Ключевые возможности, Границы (в охвате / вне охвата), Условия доступности сервиса, Бизнес-цели, Контекстная диаграмма — и все содержательны.

### Переносимость и ссылки (conventions §5)
- [ ] Нет ссылок за пределы `docs/`: ни на `sources/*`, ни на Confluence (pageId/URL), ни на `_meta/*`, ни на пути/классы кода.
- [ ] Все ссылки ведут на существующие документы комплекта; битых ссылок нет.
- [ ] Нет inline-TODO, черновых пометок и отсылок к OQ (`OQ-NNN`).

### Границы охвата (conventions §1–3)
- [ ] Только новый сервис; старый продукт — «вне охвата» (например, доступен только просмотр прежних заявок).
- [ ] Временно отключённые типы объектов помечены «временно недоступен / не предлагается», а не «неактуально».
- [ ] Если версия актуальная — отражён шаг оплаты комиссии по QR/СБП, и формулировка «вне охвата» ему не противоречит.
- [ ] Нет удалённых из объёма веток (для О2+ — счета ДУ / специальные транзитные счета).

### Условия доступности (обязательный раздел)
- [ ] Для каждого сценария доступа закрыты пять вопросов: статус клиента; нужен ли рамочный договор; нужно ли ещё соглашение; по какому соглашению пользователь — УЛ; руководитель (ЕИО) и/или какая доверенность.
- [ ] Базовое условие статуса клиента указано явно (действующий / потенциальный).
- [ ] Связка условий полномочий (**И** / **ИЛИ**) соответствует источнику/комплекту; вычислимые проверки делегированы контролям, не дублируются.
- [ ] Названия договоров и доверенностей — бизнес-термин + официальное название в скобках; термины есть в `glossary.md`.

### Согласованность с комплектом
- [ ] Названия смежных систем и сервисов экосистемы совпадают с `glossary.md`.
- [ ] Акторы согласованы с `rbac.md` и функциями.
- [ ] Каждая ключевая возможность покрыта артефактом комплекта (функцией/процессом).
- [ ] Контекстная диаграмма (mermaid) корректно рендерится, её состав совпадает с разделом «Акторы».

### Бизнес-цели и стиль (conventions §4)
- [ ] Каждая бизнес-цель — исход с измерителем (метрикой); отсутствие целевого значения указано явно («Целевое значение — не задано»).
- [ ] Язык русский, бизнесовый, не технический; жаргон и коды платформы не используются либо расшифрованы.
