# Шаблон: docs/README.md (вход в комплект сервиса)

Как устроен корневой `docs/README.md` сервиса. Назначение — **навигация по комплекту**: с чего начать, кратко про клиентскую и банковскую части, карта условных обозначений (CL / BNK / SYS и префиксы ID), границы комплекта, дерево разделов. Подробности «что за сервис» — только в `service-vision.md`.

Живой пример — `docs/README.md` любого готового комплекта.

## Где искать методологию (вне комплекта)

Сам `docs/README.md` **переносим**: в нём нет ссылок на org-канон, `_meta`, `sources/`, Confluence. Автору комплекта нормы и гайд искать **вне** `docs/`:

| Что нужно | Куда |
| --- | --- |
| Conventions, notation, repo-topology | [eco-techbook / standards/analytics](https://gitlab.gboteam.ru/ED/eco-techbook/-/tree/master/standards/analytics) |
| Git-workflow, gitlab-settings, API First howto | [eco-techbook / cookbook/analytics](https://gitlab.gboteam.ru/ED/eco-techbook/-/tree/master/cookbook/analytics) |
| Гайд аналитика, git-start, terms, окружение ПО | [eco-kb / analytics](https://gitlab.gboteam.ru/ED/eco-kb/-/tree/master/analytics) |
| Скиллы и шаблоны артефактов | пока `_meta/skills/`, `_meta/templates/` в пилоте; целевой дом — [drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit) |

В тексте комплекта фразу вроде «полная схема ID — в конвенциях проекта» оставляй **без** markdown-ссылки наружу (читатель комплекта не зависит от org-репо).

## Состав комплекта

```
docs/
└── README.md      # входная навигация комплекта (этот файл)
```

Правила:

- **Один файл** `docs/README.md` на сервис; frontmatter **не используется** (навигационный README, не нумерованный артефакт).
- **Не дублировать Service Vision.** Абзац «О сервисе (кратко)» — 2–4 предложения + таблица контуров; детали — ссылкой на `service-vision.md`.
- **Обязательные разделы** (порядок фиксирован): заголовок + «С чего начать»; «О сервисе (кратко)»; «О комплекте»; «Как читать»; «Условные обозначения»; «Границы комплекта»; «Разделы»; «Дерево».
- **Переносимость** (`conventions.md` §5): без ссылок и отсылок за пределы `docs/` (нет `_meta/`, `sources/`, pageId, URL Confluence). Легенда обозначений **самодостаточна** в этом файле.
- **Дерево и таблица «Разделы»** отражают **фактический** состав каталога сервиса (отсутствующие слои не рисуем как существующие).
- **Весь файл шаблона** — без markdown-ссылок `[текст](путь)`; в целевом документе — обычные относительные ссылки внутри `docs/`.

## Шаблон docs/README.md

````markdown
# <Краткое название сервиса>

Документация сервиса **«<полное название>»** (кодовое имя <код>) — одного из сервисов АС Экосистема.

**С чего начать.** Что из себя представляет сервис, кому он нужен, какие у него границы и как устроены клиентская и банковская части — в <ссылка [концепции сервиса (Service Vision)](service-vision.md)>. Термины и смежные системы — в <ссылка [глоссарии](glossary.md)>.

## О сервисе (кратко)

<2–4 предложения: что делает сервис для пользователя и какой результат даёт. Без перечней ID.>

У сервиса два пользовательских контура:

| Контур | Кто | Что делает |
|--------|-----|------------|
| **Клиентский (CL)** | <актор клиента> | <кратко: основные действия> |
| **Банковский (BNK)** | <актор банка> | <кратко: основные действия> |

Между ними работает автоматическая обработка (<системный актор / **SYS**>). Подробнее — в <ссылка [Service Vision](service-vision.md#клиентская-и-банковская-части)>.

## О комплекте

Это чистовой комплект аналитической документации. Он самодостаточен: описывает поведение системы на уровне требований, не ссылаясь на внешние источники.

- **Формат** — Markdown, docs-as-code: документы дробятся на карточки с устойчивыми идентификаторами (`ENT-`, `SCR-`, `FUN-`, `CTL-`, `PRN-`, `CALL-`, `PROC-`), связанными сквозными ссылками.
- **Идентификаторы и трассировка.** Каждый артефакт имеет стабильный ID; сквозные связи сведены в <ссылка [матрицу трассировки](traceability-matrix.md)> — она общая для всего комплекта (BRD, SRS, API).
- **Навигация.** В каждом каталоге есть `README.md` — обзор раздела и реестр его артефактов.

## Как читать

Рекомендуемый порядок для первого знакомства:

1. <ссылка [Service Vision](service-vision.md)> — зачем сервис, кому, клиентская и банковская части, границы.
2. <ссылка [Глоссарий](glossary.md)> — термины и смежные системы.
3. <ссылка [Бизнес-требования (BRD)](brd/README.md)> — бизнес-правила, фичи и сквозные сценарии (если слой есть).
4. <ссылка [Процессы](srs/process/README.md)> — жизненный цикл (если слой есть).
5. <ссылка [Модель данных](srs/data-model/README.md)> — какие данные хранит сервис (если слой есть).
6. <ссылка [Экранные формы](srs/screen-form/README.md)> и <ссылка [Функции](srs/function/README.md)> — что видит и делает пользователь (если слой есть).
7. Контроли, печатные формы, внешние интеграции — по наличию в комплекте.
8. <ссылка [API](api/README.md)> — контракты (если слой есть).

В списке оставляй только пункты для разделов, которые реально есть в `docs/` сервиса; нумерацию пересобери подряд.

## Условные обозначения

Карта префиксов и суффиксов в идентификаторах комплекта (полная схема ID — в конвенциях проекта / org-стандартах аналитики; ниже — рабочий набор для читателя комплекта).

### Контуры (суффиксы в ID)

| Код | Значение | Где встречается |
|-----|----------|-----------------|
| **CL** | Клиентский контур | `F-CL-*`, `FUN-CL-*`, `SCR-CL-*`; каталоги `client/` |
| **BNK** | Банковский контур | `F-BNK-*`, `FUN-BNK-*`, `SCR-BNK-*`; каталоги `bank/` |
| **SYS** | Системные функции (без пользовательского UI) | `FUN-SYS-*`; каталог `function/system/` |

### Типы артефактов (префиксы ID)

| Префикс | Что обозначает | Где лежит |
|---------|----------------|-----------|
| **VIS** | Концепция сервиса | `service-vision.md` |
| **F-CL / F-BNK** | Спецификация фичи (BRD) | `brd/features/` |
| **US / FR / NFR / RR** | User Story, функциональное / нефункциональное / регуляторное требование | внутри фич |
| **UC** | Сквозной сценарий (use case) | `brd/use-cases/` |
| **BR / ТР** | Бизнес-правило / таблица решений | `brd/business-rules.md` |
| **PROC** | Процесс | `srs/process/` |
| **ENT** | Сущность модели данных | `srs/data-model/` |
| **EXT** | Справочник / сущность платформы (вне сервиса) | `srs/data-model/dictionaries.md` |
| **FUN** | Функция системы | `srs/function/` |
| **SCR** | Экранная форма | `srs/screen-form/` |
| **CTL / CTL-GRP** | Контроль / группа контролей | `srs/control/` |
| **PRN** | Печатная форма | `srs/print-form/` |
| **CALL** | Вызов чужого контракта (внешняя АС, другой сервис Экосистемы, платформенный метод со спецификацией) | `srs/contract-call/` |
| **PLT** | Платформенная функция ЭКО | `srs/platform-functions.md` |
| **RBAC** | Ролевая модель сервиса | `srs/rbac.md` |

Внутри экранных форм дополнительно: **FLD-N** — правило поля, **EV-N** — событие, **B-N** — кнопка, **MSG-N** — сообщение.

Таблицу префиксов можно сузить до тех типов, которые уже есть в комплекте; контуры CL / BNK / SYS оставляй всегда.
````
