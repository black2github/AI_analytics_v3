# Протокол исполнителя захода миграции

Нормативный документ конвейера миграции. Промпт захода НЕ пересказывает
эти правила — он ссылается сюда, а исполнитель читает протокол целиком
до начала работы. Отклонение от протокола — брак захода независимо от
качества содержимого.

Дом на период обкатки — `_meta/tools/` (правится циклом калибровок
инструментов); целевой дом после обкатки — eco-techbook
`cookbook/analytics/`.

## Словарь

- **Заход** — порция работы исполнителя с проверяемым результатом;
  крупный этап делится на СЕРИЮ заходов (нарезка по ёмкости).
- **Дозаход** — правка ранее сданного захода по списку замечаний
  приёмки; скоуп задают замечания, счётчики попыток гейта не
  открываются.
- **Сдача** — отчёт по §8 с полным выводом гейта и честным вердиктом.
- **Приёмка** — решение акцептующего по сдаче.
- **Baseline** — принятый владельцем отчёт гейта, точка отсчёта дельты.
- **Долг** — недостающая цель ссылки, зафиксированная в матрице.
- **OQ (запись OQ-NN)** — открытый вопрос аналитику: append-only
  запись в `open-questions.md` src-репозитория со сквозной нумерацией
  (формат: вопрос → варианты → рекомендация → что проверить, §8
  п. 12). Вопрос, не записанный в файл, не существует.
- **Акцептующий** — аналитик команды сервиса: приёмки и baseline,
  строка среза канона в профиле, отмашки, решения по `--force` и
  вопросам своего сервиса.
- **Владелец канона** — держатель инструментов, шаблонов и скиллов:
  калибровки прибора, дефекты нормализатора, правки протокола.
- **Владелец** (без уточнения) — читается по контексту: стенд и
  приёмки — акцептующий; прибор и канон — владелец канона (в пилоте
  роли совпадали).

## 1. Preflight (до любых изменений)

Выполни и сохрани ДОСЛОВНЫЕ выводы:

1. `git -C <src-репо> branch --show-current`
2. `git -C <src-репо> status`
3. `git -C <src-репо> diff -- docs`
4. `git -C <канон> rev-parse --short HEAD`

Условия продолжения:

- свежесть канона: источник истины — строка «срез канона: `<hash>`» в
  профиле источников src-репозитория; гейт (selfcheck) сверяет её с
  фактическим HEAD канона автоматически при каждом прогоне. Промпт
  захода хэш НЕ несёт. Вывод `rev-parse` сохрани в сдачу; ✗ среза у
  гейта — стоп, решение владельца (обновить клон канона либо строку
  профиля — строку меняет только владелец, одной командой:
  `python <канон>/_meta/tools/accept_canon.py --profile <профиль>
  [--reason "<что принято>"]` — правка строки + точечный коммит
  профиля; без --reason основание собирается из тем принимаемых
  коммитов канона; исполнителю утилита запрещена §3);
- baseline предыдущего этапа существует и ПРИНЯТ акцептующим.
  Предусловие формулируется «принято приёмкой акцептующего» — НЕ
  требованием конкретных строк в файлах отчётов: формат отчётов
  эволюционирует вместе с прибором;
- неожиданных изменений рабочего дерева нет; ничего не восстанавливай —
  остановись и сообщи.

Спорная проверка доказывается только дословным выводом команды,
не вердиктом своими словами.

## 2. Запреты Git

Git — только для чтения состояния. Разрешены: `status`, `diff`, `log`,
`show`, `branch --show-current`, `rev-parse`.

Запрещены любые команды, меняющие рабочее дерево, индекс, refs или
remote: `restore`, `checkout`, `switch`, `reset`, `stash` (все
подкоманды), `clean`, `add`, `commit`, `push`, `pull`, `fetch`,
`merge`, `rebase`, `cherry-pick`, `revert`, `apply`, `am`, `rm`, `mv`,
`tag`, операции с ветками и worktree.

Не пытайся «восстановить стенд» средствами Git даже при обнаружении
неожиданных изменений. Чекпоинт-коммиты стенда делает владелец после
приёмки.

## 3. Запрет изменяющих скриптов

Запрещено создавать или запускать скрипты (Python/PowerShell/Bash/…),
которые создают, копируют, форматируют или массово изменяют файлы
комплекта и служебные артефакты. Каждый целевой файл редактируется
непосредственно и пофайлово.

Исключения:

1. канонический `selfcheck.py` — пишет отчёты и журнал только в
   `sandbox/`;
2. канонический `normalize_tables.py` — только на точечных копиях в
   `sandbox/normalized/`, с `--sidecar`; запуск на `confluence/` или
   `docs/` запрещён;
3. read-only диагностика, ничего не изменяющая.

Фоновые агенты, «полные сборки» и генерация по манифесту — те же
запрещённые скрипты: карточки пишутся по одной, руками, с сохранением
после каждой. Разрешённая read-only диагностика выполняется БЕЗ
сохранения скрипт-файлов в src-репозитории (файл диагностики,
оставленный в стенде, роняет чужие прогоны сторожем §3).

Shell-редиректы (`>`, `Out-File`) запрещены — PowerShell пишет UTF-16.
`--force` нормализатора — только по явному решению владельца.

## 4. Baseline и журнал

Фиксированные имена (дрейф имён = расщепление дельты и журнала):

- журнал: `sandbox/journal.txt` — единый append-only на весь стенд;
  вручную не редактируется; самодельные имена журналов запрещены —
  сторож гейта аннулирует прогон с посторонним `--journal`;
- первый заход стенда: baseline `sandbox/baseline.txt` создаётся ДО
  первого изменения файлов и далее не перезаписывается;
- отчёт захода: `sandbox/selfcheck-<ЭТАП>.txt`; для этапа из серии
  заходов — `sandbox/selfcheck-<ЭТАП>-zNN.txt`, где zNN — номер
  захода из таблицы «Заходы серии» промпта этапа; повторные ПРОГОНЫ —
  суффикс `-retry-N` к имени отчёта (N — номер прогона; лимит
  §6 считается по каждому ✗ отдельно и подтверждается сдачей,
  retry-3+ — сигнал приёмке проверить квалификацию);
- baseline следующего этапа — финальный ПРИНЯТЫЙ отчёт текущего
  (с учётом retry); самостоятельно baseline не сдвигается.

Каждый прогон гейта обязан нести одновременно: `--baseline <принятый>`,
`--journal sandbox/journal.txt`, отдельный `--out`.

## 5. Нормализация таблиц источника

Готовые markdown-таблицы переносятся напрямую. Сырые HTML-таблицы —
только через канонический нормализатор на точечной копии в
`sandbox/normalized/`; для каждой целевой таблицы сверяются строки,
колонки, порядок, rowspan/colspan, вложенность, комментарии по sidecar.
Потеря строки, колонки или смыслового фрагмента блокирует приёмку.

При отказе нормализатора: не писать собственный парсер, не переносить
таблицу «на глаз», не использовать `--force` — зафиксировать блокер
владельцу канона с дословной диагностикой. Дефект прибора чинит
владелец; после калибровки владелец сообщает новый ожидаемый хэш
канона решением по блокеру.

## 6. Лимит попыток

На каждый обнаруженный ✗ — не более ДВУХ циклов «правка конкретной
причины → повторный прогон». Счётчик ведётся НА КАЖДЫЙ ✗ отдельно;
baseline и первый прогон сдачи попытками не считаются. Для
подтверждённого внешнего блокера (нужны решение владельца, правка
канона, источника или чужого этапа) бессмысленные retry не выполняются.

### Серия заходов этапа

В этапе из нескольких заходов следующий заход начинается ТОЛЬКО после
исхода OK текущего и отмашки акцептующего (§11). БРАК с блокерами или
СТОП по лимиту останавливают серию до решения акцептующего.

### Серия заходов одной страницы

Крупная страница переносится серией заходов по срезам владельца.
Гейт сверяет страницу ЦЕЛИКОМ против всех её карточек, поэтому OK
промежуточного захода недостижим по построению. Правило серии:
промежуточный исход «БРАК», в котором ВСЕ ✗ относятся к переносимой
странице, не останавливает серию; критерий продолжения — счётчик
недостающих литералов УБЫВАЕТ от захода к заходу и новых классов
✗ нет. На закрывающем заходе страницы правило не действует: исход
обязан быть OK, остаток литералов — настоящие потери.

## 7. Три допустимых исхода

Бинарные статусы («ГОТОВО/НЕ ГОТОВО») не используются.

- **OK** — только если: финальный прогон завершился кодом 0, ✗
  отсутствуют, дельта против baseline присутствует, изменения — строго
  в scope захода, все входные единицы учтены.
- **БРАК с блокерами** — есть ✗ или расхождение, неисправимое в scope
  без решения владельца / правки канона / источника / чужого этапа /
  разрушения чужих правок. Для каждого блокера: дословный ✗, причина,
  что проверено, почему вне scope, владелец решения, следующее
  действие.
- **СТОП по лимиту** — тот же ✗ остался после двух циклов: дословный ✗,
  обе правки, результаты обоих прогонов, что требуется от человека.

Ошибка гейта не может быть переименована в предупреждение или
«ожидаемый долг». Каждый непогашенный ✗ — блокер.

### Пульс

Первое сообщение исполнителя — краткий статус сразу после preflight;
далее краткий статус после КАЖДОГО сохранённого файла. Тихая работа
дольше нескольких минут неотличима от смерти сессии; молчаливых фаз
у захода нет.

## 8. Формат сдачи

1. Этап.
2. Git preflight: команды и дословные выводы; commit канона;
   подтверждение отсутствия изменяющих команд.
3. Baseline: путь, дословный итог, подтверждение неизменности.
4. Механическая проверка входа: каждая входная единица против описи,
   разметки профиля и файлов источника; ожидаемое число единиц.
5. Созданные и изменённые файлы.
6. Соответствие вход → целевой артефакт/раздел; выданные ID с моментом
   регистрации в матрице.
7. Нормализация: источник → копия → sidecar → сверка.
8. Все прогоны гейта: команда, номер попытки, код возврата, ПОЛНЫЙ
   дословный вывод (без сокращений и пересказа), путь отчёта.
9. Дельта финального прогона — дословно.
10. Таблица непогашенных ✗: дословный ✗, счётчик попыток, блокер,
    владелец решения, следующее действие.
11. Итоговый исход — ровно один из трёх (§7).
12. Вопросы аналитику: СНАЧАЛА каждый вопрос записывается в
    `open-questions.md` (append-only, следующий номер OQ-NN: вопрос →
    варианты → рекомендация → что проверить), ПОТОМ в сдаче
    перечисляются только номера и заголовки записанных OQ. Вопрос,
    которого нет в файле, не существует: текст вопроса в сдаче без
    записи OQ — потеря вопроса (прецеденты пилота).
13. Подтверждения: изменяющие скрипты не использовались; запрещённые
    git-команды не выполнялись; commit/push не выполнялись; чужие
    этапы и типы не затронуты; baseline не сдвигался.

## 9. Правила качества

- Малый заход с человеческой приёмкой; следующий этап не начинается
  до приёмки текущего.
- Перенос дословный; асимметрия ошибок: молчаливая потеря хуже шума.
  Ссылка на справочник ДОПОЛНЯЕТ исходный текст ячейки, не заменяет.
- Факт без источника не добавляется; неоднозначность — вопрос или
  блокер, не догадка.
- Заглушки чужих типов не создаются — долг в матрице.
- ID выдаются через реестр матрицы непосредственно перед созданием
  реального артефакта; авансовые ID запрещены.
- Открытые вопросы — append-only в `open-questions.md` src-репозитория
  (conventions §6); в docs отсылок к OQ нет.
- В docs запрещены: TODO и заглушки, номера OQ, локальные коды плана,
  пути `confluence/`/`sources/`/`sandbox/`/`_meta/`, ссылки на
  Confluence и канон, имена классов и пути к коду, факты эталона.
- Требования, чьё поведение предписано шаблоном или скиллом,
  исполняются по канону; конфликт задания с каноном — стоп и дословные
  цитаты обеих сторон (не молчаливый выбор).

## 10. Шаблон промпта захода (для планировщика)

Промпт захода собирается ПОДСТАНОВКОЙ карточки этапа в шаблон — не
сочинением. Всё, что не входит в шаблон, живёт в этом протоколе,
скиллах и шаблонах канона.

```text
Ты выполняешь только этап <ЭТАП> миграции SRS сервиса «<СЕРВИС>»:
<название этапа из карточки плана>.

Работай СТРОГО по протоколу <канон>/_meta/tools/step-protocol.md —
прочитай его целиком до начала. Способ — скилл <скилл-донор карточки>;
обязательное чтение: AGENTS.md канона, conventions.md (§3.1 при
подсервисах), профиль источников, шаблон типа, карточка этапа в плане.

Рабочие пути: <src-репо, источник, комплект docs, канон, эталон,
техбук — из плана>.
Свежесть канона сверяет гейт по строке «срез канона» профиля
источников; ✗ среза — стоп, решение владельца.
Параметры: <service-id, version, режим, зона, тип, целевой путь>.
Предусловия: <этапы, принятые приёмкой акцептующего>; baseline —
<принятый отчёт предыдущего этапа>.

Вход: <точечный перечень единиц из карточки этапа с ожидаемым числом>.
Скоуп: разрешено изменять <список из карточки>; запрещено <список из
карточки>. <Особые решения владельца, если есть.>

Сдача — по §8 протокола. Не начинай другие этапы.
Жёсткие якоря (полный текст — в протоколе): скрипты, создающие или
изменяющие файлы, НЕ писать и НЕ запускать; фоновые агенты и «полные
сборки» — те же скрипты, карточки по одной с сохранением после каждой;
попыток исправления на каждый ✗ — не более двух; git — только чтение;
журнал — только sandbox/journal.txt; неожиданные изменения стенда —
СТОП и сообщение владельцу, ничего не откатывать; пульс — статус
после preflight и после каждого файла.
```

Правила для планировщика:

- **Самодостаточность карточки.** Карточка этапа обязана быть
  самодостаточной для этой подстановки (вход перечнем, выход, способ,
  критерий приёмки, скоуп). Карточка может быть факторизована в плане
  (общая карточка типового этапа + строка реестра этапов + правило
  механического отбора входа из описи) — тогда самодостаточной обязана
  быть композиция, а вход перечнем планировщик вычисляет отбором при
  сборке промпта.
- **Скоуп чужих документов.** Скоуп каждого этапа несёт ровно ДВЕ
  разрешённые категории правок чужих документов (прочие — запрещены):
  (1) обернуть дословные имена появившихся карточек ссылками в
  ожидателях (матрица, «Где используется» реестров); (2) дописать свою
  новую карточку потребителем в «Где используется» реестра
  платформенных функций — append-only: чужие записи не менять,
  раскладка существующих строк — только по срабатыванию сторожа
  (прецедент пилота: без категории 2 реверс-индекс потребителей
  молчаливо неполнеет с каждой новой ЭФ).
- **Нарезка по ёмкости** (замер пилота: слабый исполнитель на входе
  ~90 тыс. токенов ушёл в генерирующий скрипт): вход одного захода —
  не более ~1500 строк источника (числа строк — из колонки «строк»
  описи; ≈15–18 тыс. токенов); страница крупнее порога делится по
  верхнеуровневым секциям (у контролей — группы), карточка типа
  собирается за несколько заходов (append). Промпт этапа с крупным
  входом несёт раздел «Заходы серии»: перечень входов каждого захода
  (номера zNN) и требование прогона гейта со сдачей после каждого.
- **Промпт — файл.** Промпт этапа сохраняется файлом в src-репо
  (`prompts/<ЭТАП>.md`) И выводится полным текстом в ответ — человек
  видит его сразу, ревьюит и при необходимости правит; правки вносятся
  В ФАЙЛ (версионируются чекпоинтом стенда), не в буфер копипаста.
  В сессию исполнителя передаётся указание на файл, не копипаст
  (инцидент: копипастом в сессию ушёл промпт чужого этапа).
- **Без хэша канона.** Хэш канона в шаблоне отсутствует
  конструкцией — свежесть держит сторож среза по строке «срез канона»
  профиля (обновляет акцептующий при приёмке правок канона).

Живучесть сессии планировщика — те же якоря, что у исполнителя:
источники, опись и план читать по АБСОЛЮТНЫМ путям; отказ чтения пути
со [скобками] или кириллицей не означает отсутствия файла — перечитать
через терминал; пульс — короткий статус после каждого шага сборки
(вход прочитан / заходы нарезаны / файл промпта записан). Молчание
дольше одного шага — тихая смерть сессии, а не «долго думает»
(инцидент: пересборка промпта этапа встала на чтении путей и ожила по
формуле «абсолютные пути + терминал-фолбэк + пульс»).

## 11. Роли сессий

- Исполнителю — СВЕЖАЯ сессия на каждый этап: самодостаточность
  промпта проверяется только чистым контекстом.
- Планировщику — продолжение его сессии (накопленный контекст плана).
- Дозаход по замечаниям приёмки — продолжение сессии исполнителя,
  если она не деградировала; замечания приёмки не открывают счётчики
  попыток гейта.
- Отмашка между заходами серии — стандартная формула; её пишет тот,
  кто акцептует приёмки этапов (персона из «Входных данных» плана
  миграции), самостоятельно — участие владельца канона/методолога
  для отмашки не требуется:

  ```text
  Сдача zNN принята акцептующим, изменения закоммичены. Продолжай по
  промпту <путь к файлу этапа>.
  ```

  zNN — номер захода серии из промпта этапа (§4); для этапа без серии
  формула начинается «Сдача этапа <ЭТАП> принята…».
  Отмашка несёт только невыводимое из промпта: факт приёмки и
  коммита, плюс вопросы/замечания приёмки, если есть. Детали промпта
  (вход захода, baseline, ограничения) в отмашке НЕ дублируются:
  дублирование маскирует неполноту промпта — если исполнителю
  отмашки не хватает, это дефект промпта и чинится в файле промпта.
