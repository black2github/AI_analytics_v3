# Шаблон: процесс

Как устроен комплект процессов сервиса и по какому формату описывается каждый процесс (оркестратор и подпроцессы). Живой пример — каталог `docs/srs/process/` любого готового комплекта. При подсервисной структуре (conventions §3.1) каталог типа лежит в `docs/srs/<подсервис>/process/` — структура внутри неизменна.

## Состав комплекта

```
docs/srs/process/
├── README.md              # обзор: назначение, реестр процессов, связи, короткая читательская легенда (FMT-P3)
├── proc-001-<имя>.md       # оркестратор (сквозной процесс)
├── proc-002-<имя>.md       # подпроцессы (PROC-002, PROC-003 …)
├── …
└── status-model.md        # статусная модель заявки (SM-000)
```

Правила:

- **Процесс — это маршрут и клей комплекта**: он задаёт порядок шагов, условия переходов и указывает на артефакты с деталями (функции `FUN`, экраны `SCR`, вызовы чужих контрактов `CALL`, контроли `CTL`, данные `ENT`). Детали в процессе **не пересказываются** — на них ссылаются.
- **Смена статуса и сохранение реквизитов — эффекты шага**, а не отдельные шаги. Шаг — действие, событие или решение пользователя, названное глаголом.
- **Один процесс — один файл.** Имя файла: `proc-<NNN>-<короткое-имя-латиницей>.md` (ID строчными + название, conventions §5); нумерация сквозная, ID стабильны.
- **Ошибки интеграций, ожидающие вмешательства банка, — не исходы**: процесс остаётся в цикле «зафиксировать ошибку → информировать → обработать ошибку (Пользователь Банка)» и возобновляется функцией повторения выгрузки либо завершается по решению пользователя. Исход заводится только для терминальных состояний, которые считывает оркестратор.
- Статусы заявки — только коды из справочника статусов; каждый переход, вытекающий из шагов, должен существовать в `status-model.md` (сверка трёх слоёв: справочник ↔ модель ↔ процессы).
- Спорные места (расхождение источников) — не решаем молча: вопрос аналитику или реестр `open-questions.md`; в документ — по приоритету источников (conventions §1, §6).

## Таблица шагов

Таблица `№ | Шаг | Содержание` — всё о шаге в одной строке; единственная широкая колонка «Содержание» (таблица дословного контента, конвенции §4) не сжимается в узких превью. Блоки внутри ячейки разделяются `<br>`.

- **Шаг** — действие, событие или решение пользователя, названное глаголом.
- **Нумерация в reverse — ДОСЛОВНО из источника**, включая подшаги
  (`1.1`, `1.29`, `Шаг №2` — какая система есть): номера шагов — литералы,
  их нельзя перенумеровывать, сливать и «упаковывать» (инцидент src-locks
  2026-08-14: 29 шагов источника сжаты в 22 своих — смысл переходов
  «Далее» пришлось синтезировать). Механический сторож — полнота маркеров
  шагов в `--check --source`. Сквозная `1..N` без подшагов — правило
  ТОЛЬКО для forward-проектирования с нуля; завершающие события —
  отдельные нумерованные шаги.
- **Источник без таблицы шагов** (страница-обзор со ссылкой на диаграмму
  или вложение): шаги НЕ синтезировать — ни из диаграммы-картинки, ни из
  страниц других разделов; карточка-минимум (назначение, роль, ссылки на
  дочерние процессы) + открытый вопрос с `confluence_page_id` источника
  недостающих шагов.
- **Исполнитель** по умолчанию — Система (фиксируется в преамбуле раздела); иной исполнитель помечается в названии шага: «Обработать ошибку — *Пользователь Банка*».
- **Содержание** — 1–4 предложения: суть, входные данные, ссылки на артефакты; затем строки «Статус =» и «Далее» через `<br>`. Условия и присвоения — атрибутной нотацией `[ENT-NNN](…).«Атрибут»`. Развёрнутые правила — в «Детали шагов» по якорю.
- **Перечисление альтернатив** (ожидаемых событий, действий пользователя, вариантов условия) — маркированным списком внутри ячейки: каждый вариант с новой строки — `<br>• вариант — описание;`, после последнего — точка; продолжение общего текста — с новой строки `<br>`.
- **Несколько присвоений или последовательных сохранений** в одном шаге — каждое с новой строки `<br>` (без маркера).
- **Статус =** — код статуса, в который шаг переводит заявку (с уточнением ветки, если статус ставится не всегда); у шага без смены статуса строка опускается.
- **Далее** — все переходы шага в виде `условие → номер шага` с короткими метками условий; у безусловного перехода — `→ N`; у терминального шага — `конец`. Строка обязательна для каждого шага.
- Шаг, выполняемый через функцию, экран, вызов чужого контракта или платформенную функцию, **обязан** ссылаться на соответствующий артефакт (`FUN-…`, `SCR-…`, `CALL-…`, `PLT-…`); шаг ожидания сообщений — на карточку вызова с форматами сообщений.

## Диаграмма (PlantUML activity)

- Обязательная шапка:

  ```
  skinparam ActivityBackgroundColor #F5F5F5
  skinparam ActivityBorderColor #333333
  ```

- При двух и более исполнителях — дорожки `|Исполнитель|`.
- Узлы-действия нумеруются номерами шагов таблицы; ромбы (`if` / `switch`) собственных номеров не имеют — условие и ветки заданы в строке «Далее» шага-источника.
- Смена статуса — в подписи узла: `(статус = КОД)`; для веток — на метках стрелок.
- Шлюзы с 3+ ветками — `switch/case/endswitch`, с двумя — `if/else` (детали — скилл `_meta/skills/generate-activity-diagram.md`).
- Общий обработчик ошибок из нескольких веток — приём «пустая ветка проваливается на общий блок»; терминальный узел, достижимый из независимых веток, допускается дублировать (один шаг таблицы — несколько одинаковых узлов), это оговаривается в преамбуле схемы.
- Цикл «ожидание действий пользователя после ошибки» — `repeat … repeat while (Решение пользователя?)`; если из цикла нет выхода вперёд (единственная ветка — повтор), после `repeat while` ставится `detach`.

## Исходы и стыковка с оркестратором

- Каждый терминальный шаг возвращает именованный исход; таблица «Исходы процесса» — единственное место, где расписаны статус на выходе и шаг продолжения в оркестраторе.
- Название исхода совпадает с меткой ветки в строке «Далее» шага-вызова оркестратора **дословно**.
- В оркестраторе шаг-вызов подпроцесса — одна строка: «Вызывается подпроцесс <ссылка>…» + «Далее» с ветками-исходами; шлюзы данных между подпроцессами — шаг-решение с условиями в «Детали шагов».

## Приложенные артефакты (при наличии)

Если у страницы-источника есть не-markdown приложения (типично —
VSD/VSDX-диаграмма процесса в BPMN) — карточка несёт блок
«Приложенные артефакты» по `attachments-block.md`: файл в `files/`
рядом с карточкой, ссылка обязательна, роль «авторская диаграмма
процесса (BPMN)» — на миграции первоисточник для сверки (содержание
переносится текстом карточки; невыписанное в тексте → OQ), после
перехода на forward-режим — архив.

## Чек-лист самопроверки (до отправки MR на ревью)

- [ ] Frontmatter заполнен (id, type, service); `id` соответствует имени файла и схеме `PROC-NNN`.
- [ ] Нет ссылок на Confluence, код и `sources/*` (conventions §5); ссылки — только на документы комплекта.
- [ ] «Назначение» содержит паспорт: оркестратор (шаг вызова), инициатор, исполнители, предусловие, исходы.
- [ ] Диаграмма имеет шапку `skinparam`; номера узлов совпадают с таблицей; дублированные терминальные узлы оговорены.
- [ ] Каждый шаг таблицы имеет строку «Далее»; все ветки перечислены; смены статусов — в «Статус =», отдельных статусных шагов нет.
- [ ] Перечисления альтернатив — буллетами `<br>• `; несколько присвоений — по строкам.
- [ ] Шаг ссылается якорем на «Детали шагов», если содержит больше одного **Если** либо больше трёх строк содержимого; прочие шаги на «Детали» не ссылаются.
- [ ] Названия исходов дословно совпадают с метками веток шага-вызова оркестратора.
- [ ] Статусы — только из справочника статусов; каждый переход, вытекающий из шагов, есть в `status-model.md`; свод «Статусы заявки в процессе» совпадает со справочником по отображениям.
- [ ] Ссылки на функции, экраны, интеграции, контроли — по месту использования; связи отражены в `traceability-matrix.md` в том же MR.
- [ ] Атрибуты старого сервиса не попали (conventions §3); ПД в примерах обезличены.
- [ ] Спорные места переданы аналитику или зафиксированы в `open-questions.md`.
