# Шаблон: контракты собственных методов сервиса (internal-contracts)

Постановочный уровень контрактов методов, которыми ВЛАДЕЕТ документируемый
сервис. «Internal» — относительно границы ЭКОСИСТЕМЫ ДБО, не сервиса:
здесь интерфейсы внутреннего контура Экосистемы; интерфейсы систем ВНЕ
Экосистемы — в репозитории
[docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts)
(шаблон [`contract-call.md`](contract-call.md)).

**Два состояния описания метода (решение 2026-10-06):**

- **До перехода сервиса на API First** — карточка `INTC` в
  `docs/srs/internal-contract/` (этот шаблон): что метод должен делать,
  семантика и состав параметров дословно из требований; зона аналитика,
  источник — Confluence.
- **После перехода** — описание метода живёт в полях `summary` и
  `description` операции в контракте `api-specification/` репозитория
  кода (зона разработки; conventions §5.1, §5.1.3). Событие перехода —
  контракт с заполненными полями опубликован. Карточка снимается (см.
  «Снятие карточки при переходе на API First»), её текст — источник
  полей. Описание в двух местах не держат.
- Копий YAML в комплекте нет, каталог `api/` не создаётся; этот шаблон в
  репозиторий кода ничего не пишет. Трассировка «метод ↔ SRS» в обоих
  состояниях — матрица (conventions §5.3 п. 7).

## Состав каталога

```
docs/srs/internal-contract/
├── README.md                  # INTC-000: реестр методов сервиса
├── client/                    # контуры — по тем же правилам, что function/
│   └── intc-NNN-<slug>.md     #   Авторизация: Bearer token, роль Клиента
├── bank/
│   └── intc-NNN-<slug>.md     #   Авторизация: Bearer token, роль Банка
├── system/
│   └── intc-NNN-<slug>.md     #   Авторизация: Basic authorization (ТУЗ)
└── examples/
    └── intc-NNN-<сценарий>.<ext>   # sidecar: только машинный payload
```

Контур карточки определяется строкой паспорта «Авторизация:» (см. §1):
`Bearer token` → подкаталог по контуру роли (client/bank),
`Basic authorization` → system. Карточка INTC заводится ТОЛЬКО для
метода с признаками собственного эндпоинта (REST/URL/MQ); «метод» без
эндпоинта — библиотечная процедура (FUN-SYS, см. определитель
create-artifact): если её вызывают только функции своего комплекта,
контракт ей не заводится; если её подключают другие сервисы (код
исполняется в их контуре) — это библиотечный контракт `LIBC`, шаблон
[`lib-contract.md`](lib-contract.md).

- **ID:** `INTC-NNN` (по правилу выдачи ID conventions §5, реестр —
  матрица трассировки). Frontmatter: `id`, `type: internal-contract`,
  `service`, `confluence_page_ids`.
- Ссылки артефактов SRS (процессы, функции) НА карточку `INTC-NNN` —
  штатные (метод получает целевой артефакт вместо текстового упоминания).
  Карточка на процессы/функции НЕ ссылается: поведение — их предмет,
  трассировка «метод ↔ SRS» — в матрице (conventions §5.3 п. 7; до
  перехода сервиса на API First строки таблицы «API ↔ SRS» — карточки
  INTC, после — операции контракта в `api-specification/` репозитория
  кода).
  Ссылки на сущности и справочники в правилах заполнения — по
  конвенциям §5 (точечная нотация ENT/EXT).

## Асинхронные операции (MQ / Kafka)

Асинхронный обмен сервиса описывается теми же карточками `INTC`, по
одной на операцию: отправка (`send`) и приём (`receive`) одной очереди —
две карточки, склеивать их в одну запрещено (парная операция
указывается в паспорте). Контракт AsyncAPI, как и OpenAPI, живёт в
`api-specification/` репозитория кода; в комплекте YAML нет, скилла
генерации в каноне нет (решение 2026-10-06). Переход на API First — тот
же, что для REST («Снятие карточки при переходе на API First»): после
публикации контракта с `summary`/`description` карточка снимается,
строка матрицы ссылается на операцию (`operationId` / channel).

Отличия карточки асинхронной операции от REST-метода:

- подкаталог — `system/`; строка паспорта «Авторизация:» — `—
  (асинхронный обмен)`, вместо неё в паспорте обязательны строки
  **«Транспорт:»** (`MQ` / `Kafka`, интеграционная платформа, если обмен
  через неё), **«Канал:»** (очередь / топик дословно из источника),
  **«Действие:»** (`send` / `receive`) и **«Парная операция:»** (ссылка
  на карточку ответа / запроса либо «—»);
- §2/§3 — состав сообщения (отправляемого для `send`, принимаемого для
  `receive`) в канонических колонках параметров; §4 — обработка ошибок
  и повторной доставки, если источник их описывает;
- **имя операции** для реестра и матрицы строится по правилу
  `<Система, с которой идёт обмен>_<Интеграционная платформа, если есть>_<Протокол>_<Название интеграции>`,
  например `Модуль процессинга О2+_Очередь сообщений_MQ_Выгрузка заявки в процессинг`,
  `СБП_Очередь сообщений_Kafka_Уведомление о финальном статусе QR-кода`.
  «Система» — адресат очереди или источник сообщения, а не свой
  микросервис; для `receive`, парного чужому `send`, «Система» берётся
  из парного `send`. Слово «команда» в названии не используется —
  формулировки по Confluence («выгрузка заявки», «обработка ответа»).
  Имя операции — `title` карточки и строка реестра; `operationId` из
  контракта, если он уже есть, пишется в паспорте.

Sequence-диаграмма жизненного цикла обмена в каталог контрактов не
кладётся: это поведение, его дом — карточка процесса, который
оркестрирует обмен (шаблон `process.md`, блок авторской диаграммы);
реестр `INTC-000` на неё ссылается. Подписи стрелок на диаграмме —
имена операций из реестра дословно.

## Правила переноса (общие с базовыми контрактами)

Действуют дословно правила шаблона `contract-call.md` (контур A):
состав колонок таблиц §2/§3, разбор сырых HTML-таблиц нормализатором
(`--sidecar`), дословность §1 (лейблы паспорта ИСТОЧНИКА), секционные
строки, справочники целиком, замена ссылок источника на страницы
Confluence (три случая; целевые карточки ищутся и в этом каталоге, и в
`contract-call/`), сдача с ДОСЛОВНЫМ вердиктом
`--check --source` и эскалацией «НЕ ГОТОВО». Ключевые: «Код параметра» —
полный технический путь (XML — через `/`, JSON — через `.`), ТОЛЬКО
технические имена ИЗ ИСТОЧНИКА (склейка с бизнес-названием — брак);
каждый параметр источника — строка таблицы. **Источник технического
имени не даёт** (только «№» и русские наименования, либо плейсхолдер
вида `<ID "Клиент Банка">`): «Код параметра» остаётся ПУСТЫМ (валидатор
пустое допускает) + спорное место «технические имена появятся из
реализации/делта-захода»; номера строк, транслитерации и синтетические
пути (`1`, `3.1`, `ID.КлиентБанка`) НЕ выдумывать — суррогат хуже
пустоты (инцидент src-locks 2026-08-15); дословный плейсхолдер
источника переносится в «Наименование параметра».

## Снятие карточки при переходе на API First

Когда контракт сервиса с заполненными `summary` и `description`
опубликован в `api-specification/` репозитория кода:

1. В реестре `INTC-000` строка карточки получает пометку «снята
   <дата>: перешла в контракт, операция `<operationId>`» (ID не
   переиспользуется — conventions §5), файл карточки удаляется
   отдельным коммитом; текст карточки остаётся в истории и служит
   источником полей контракта.
2. Строки матрицы «Покрытие: API ↔ SRS» переводятся с `INTC-NNN` на
   операцию: «Источник:» — ссылка на файл контракта через `HEAD` и имя
   операции текстом.
3. Потребителям из таблицы «Потребители» карточки владелец сообщает о
   снятии: их карточки вызова меняют цель в шапке на файл контракта и
   операцию (шаблон `contract-call.md`); до этого ссылка на снятую
   карточку — долг у потребителя.
4. Новые методы после перехода карточками `INTC` не описываются:
   описание — в контракте, связь с SRS — строкой матрицы.

## Чек-лист самопроверки

- [ ] Frontmatter заполнен; `confluence_page_ids` — из источника, не выдуманы.
- [ ] §1 — дословные лейблы паспорта источника; «Документация»-ссылки не потеряны.
