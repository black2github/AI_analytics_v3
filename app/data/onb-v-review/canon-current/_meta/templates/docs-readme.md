# Шаблон: docs/README.md (вход в комплект сервиса)

Как устроен корневой `docs/README.md` сервиса. Назначение — **навигация по комплекту**: с чего начать, кратко про клиентскую и банковскую части, карта условных обозначений (CL / BNK / SYS и префиксы ID), границы комплекта, дерево разделов. Подробности «что за сервис» — только в `service-vision.md`.

Живой пример — `docs/README.md` любого готового комплекта.

## Где искать методологию (вне комплекта)

Сам `docs/README.md` **переносим**: в нём нет ссылок на org-канон, `_meta`, `sources/`, Confluence. Автору комплекта нормы и гайд искать **вне** `docs/`:

| Что нужно | Куда |
| --- | --- |
| Conventions, notation, repo-topology | [eco-techbook / standards/analytics](https://gitlab.gboteam.ru/ED/eco-techbook/-/tree/master/standards/analytics) |

| Гайд аналитика, git-start, terms, окружение ПО | [eco-kb / analytics](https://gitlab.gboteam.ru/ED/eco-kb/-/tree/master/analytics) |
| Скиллы и шаблоны артефактов | пока `_meta/skills/`, `_meta/templates/` в пилоте; целевой дом — [drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit) |

В тексте комплекта фразу вроде «полная схема ID — в конвенциях проекта» оставляй **без** markdown-ссылки наружу (читатель комплекта не зависит от org-репо).

## Состав комплекта

```
docs/
└── README.md      # входная навигация комплекта (этот файл)
```

Правила:

- **Один файл** `docs/README.md` на сервис; frontmatter **не используется** (навигационный README, не нумерованный артефакт).
- **Не дублировать Service Vision.** Абзац «О сервисе (кратко)» — 2–4 предложения + таблица контуров; детали — ссылкой на `service-vision.md`.
- **Обязательные разделы** (порядок фиксирован): заголовок + «С чего начать»; «О сервисе (кратко)»; «О комплекте»; «Как читать»; «Условные обозначения»; «Границы комплекта»; «Разделы»; «Дерево».
- **Переносимость** (`conventions.md` §5): без ссылок и отсылок за пределы `docs/` (нет `_meta/`, `sources/`, pageId, URL Confluence). Единственное исключение — ссылка `../nfr/README.md`, и только когда каталог `output/<service>/nfr/` есть. Легенда обозначений **самодостаточна** в этом файле.
- **Дерево и таблица «Разделы»** отражают **фактический** состав каталога сервиса (отсутствующие слои не рисуем как существующие).
- Каталог НФТ — `output/<service>/nfr/`, рядом с `docs/`, не внутри `brd/`. В «Как читать», «Разделы» и «Дерево» он появляется только если каталог есть; ссылка из `docs/README.md` — `../nfr/README.md`.
- **Весь файл шаблона** — без markdown-ссылок `[текст](путь)`; в целевом документе — обычные относительные ссылки внутри `docs/`.

## Шаблон docs/README.md

````markdown
# <Краткое название сервиса>

Документация сервиса **«<полное название>»** (кодовое имя <код>) — одного из сервисов АС Экосистема.

**С чего начать.** Что из себя представляет сервис, кому он нужен, какие у него границы и как устроены клиентская и банковская части — в <ссылка [концепции сервиса (Service Vision)](service-vision.md)>. Термины и смежные системы — в <ссылка [глоссарии](glossary.md)>.

## О сервисе (кратко)

<2–4 предложения: что делает сервис для пользователя и какой результат даёт. Без перечней ID.>

У сервиса два пользовательских контура:

| Контур | Кто | Что делает |
|--------|-----|------------|
| **Клиентский (CL)** | <актор клиента> | <кратко: основные действия> |
| **Банковский (BNK)** | <актор банка> | <кратко: основные действия> |

Между ними работает автоматическая обработка (<системный актор / **SYS**>). Подробнее — в <ссылка [Service Vision](service-vision.md#клиентская-и-банковская-части)>.

## О комплекте

Это чистовой комплект аналитической документации. Он самодостаточен: описывает поведение системы на уровне требований, не ссылаясь на внешние источники.

- **Формат** — Markdown, docs-as-code: документы дробятся на карточки с устойчивыми идентификаторами (`ENT-`, `SCR-`, `FUN-`, `CTL-`, `PRN-`, `CALL-`, `PROC-`), связанными сквозными ссылками.
- **Идентификаторы и трассировка.** Каждый артефакт имеет стабильный ID; сквозные связи сведены в <ссылка [матрицу трассировки](traceability-matrix.md)> — она общая для всего комплекта (BRD, SRS, API).
- **Навигация.** В каждом каталоге есть `README.md` — обзор раздела и реестр его артефактов.

## Условные обозначения

Самоописание комплекта: контуры, части, префиксы идентификаторов, статусная модель и поля frontmatter — всё, что нужно читателю, чтобы разобрать любой идентификатор и любую карточку комплекта, не заглядывая в стандарты (полная схема ID — в конвенциях проекта / org-стандартах аналитики). Раздел читают и инструменты, и агенты вне комплекта: имена подразделов ниже не меняй.

### Контуры (суффиксы в ID)

| Код | Значение | Где встречается |
|-----|----------|-----------------|
| **CL** | Клиентский контур | `F-CL-*`, `FUN-CL-*`, `SCR-CL-*`; каталоги `client/` |
| **BNK** | Банковский контур | `F-BNK-*`, `FUN-BNK-*`, `SCR-BNK-*`; каталоги `bank/` |
| **SYS** | Системные функции (без пользовательского UI) | `FUN-SYS-*`; каталог `function/system/` |

### Подсервисы

Только у сервиса из частей (подсервисов): код части стоит в идентификаторе сразу после префикса (`FUN-DS-SYS-01`, `ENT-SHR-001`), каталог части — `srs/<каталог>/`, общая часть — `srs/shared/` с кодом `SHR`. У сервиса без частей подраздел не включается, слота в идентификаторах нет.

| Код | Каталог | Название |
|-----|---------|----------|
| **SHR** | `shared` | Общая часть |
| **<КОД>** | `<каталог>` | <Название части> |

### Сервис домена

Только у комплекта в доменном репозитории: «Сервис домена `<domain-slug>`, код в идентификаторах `<СЕРВИС>` — стоит сразу после префикса (`FUN-<СЕРВИС>-CL-01`), у сервиса с частями перед слотом части (`ENT-<СЕРВИС>-SHR-001`); таблица сервисов и рамка домена — в корневом `README.md` репозитория, термины домена — в корневом `glossary.md`». Если сервис включён в домен без перенумерации (в таблице сервисов «Слот: нет») — так и написать.

### Долги по ссылкам

Только если в матрице трассировки есть раздел «Долги по ссылкам». Имя раздела историческое: раздел содержит все долги комплекта. Каждая его строка — открытое поручение по комплекту, не дефект. Строки двух форматов:

- **долг по ссылке** — в тексте документа оставлено дословное имя цели, которой в комплекте нет: `| FROM-ID | — | нет целевого артефакта <тип> «<имя>» [у владельца <service-id>] — требуется заход <скилл> |`;
- **долг без отсутствующей цели** — `| FROM-ID | — | долг <вид>: «<формулировка>» — причина: <…>; ответственный: <кто>; ограничение: <какое поведение нельзя разрабатывать до закрытия>; закрытие: <условие>[; источник: OQ-NNN либо T-<JIRA-ID>] |`, где вид — один из: открытый вопрос, противоречие, правило на изображении, источник недоступен.

Как читать строку:

| Поле поручения | Откуда берётся |
|----------------|----------------|
| Формулировка (`statement`) | текст строки долга целиком; у долга без цели — формулировка в «ёлочках» и причина |
| Основание (`basis`) | карточка `FROM-ID` — документ, в котором цель упомянута дословно либо в котором обнаружена проблема |
| Адресат (`addressee`) | сервис-владелец из «у владельца <service-id>» (межсервисный долг: закрывается публикацией владельца, в этом комплекте не решается); у долга без цели — поле «ответственный»; без них — аналитик этого сервиса |
| Приоритет (`priority`) | `IMPORTANT`: работа по сервису продолжается, цель или ответ дописывается отдельным заходом |
| Область действия | весь комплект, не одна задача: долг действует до закрытия; объём API или задачи не определяет |
| Затронуто | карточка `FROM-ID` и карточки, которые ссылаются на неё относительной ссылкой (матрица и README-реестры не считаются); перечень считает прибор миграции и выводит в реестр долгов отчёта гейта переноса |
| Условие закрытия | по виду долга (таблица ниже); поле «закрытие» строки без цели уточняет его для конкретного долга |

Долг ограничивает использование затронутых карточек — `FROM-ID` и ссылающихся на неё: их поведение опирается на отсутствующую цель или на нерешённую проблему. Пока долг не закрыт, задача, которая реализует или изменяет поведение этих карточек, допускается к разработке только по записанному решению владельца документации; задачи, не затрагивающие их, долгом не ограничены. Долг из открытого вопроса журнала миграции несёт вопрос целиком — формулировку, причину, ответственного, ограничение, условие закрытия и номер источника (`OQ-NNN`): журнал в этот репозиторий не переносится, и ссылки на него недостаточно.

Условие закрытия по виду долга; закрытый долг снимается из матрицы:

| Вид долга | Условие закрытия |
|---|---|
| долг по ссылке (нет цели) | цель появилась, дословное имя заменено ссылкой, содержание цели проверено (не заглушка) |
| открытый вопрос | ответ записан ответственным в карточке `FROM-ID` |
| противоречие | осталась одна формулировка, вторая исправлена ответственным |
| правило на изображении | правило записано текстом в карточке по подтверждению владельца |
| источник недоступен | доступ получен либо материал перенесён с указанием источника |

Временный снимок контракта в карточке вызова (`CALL-INT`), сделанный для метода владельца без опубликованного описания, долг «у владельца» не отменяет: долг закрывается заменой снимка на ссылку, когда описание у владельца появляется.

Строка `| FROM-ID | — | «<текст>» |` — названный пробел нормы. Текст в кавычках дословно стоит в колонке «Не задано», в таблице применимости или в свидетельстве страницы `FROM-ID`. Это не отсутствующий артефакт. Строка снимается, когда аналитик заполняет пробел.
````

## Корневой README домена

Только у доменного docs-репозитория (стандарт `repo-topology` §3, `conventions` §3.2). Корень домена — не комплект: у него нет матрицы, открытых вопросов и записи в каталоге сервисов; его README — карта домена. Frontmatter не используется. Обязательные разделы: заголовок с названием домена и абзац «что за домен»; «Документы домена» (`domain-vision.md`, `glossary.md`); «Сервисы домена» — ТАБЛИЦА СЕРВИСОВ (её читает инструмент проверки: колонки `service-id` — каталог комплекта — и «Слот» — слот сервиса в идентификаторах либо «нет»; у домена «Цифрового рубля» колонка слота названа «Код в ID», прибор принимает оба имени); строка режима глоссария «Глоссарий: доменный» либо «Глоссарий: доменный + указатели» (шаблон `glossary.md`, правило «Домен»); «Идентификаторы»; «Как читать».

````markdown
# <Название домена>

Доменный репозиторий документации **«<название домена>»** (Doc-as-Code). В корне — рамка домена; комплекты сервисов лежат в папках `<service-id>/`, общие для сервисов модули — в `shared/`.

## Документы домена

| Документ | Назначение |
|----------|------------|
| `domain-vision.md` | Концепция домена: зачем он, карта сервисов, границы (`VIS-000`) |
| `glossary.md` | Глоссарий домена (`GLO-000`); режим — строкой ниже |

Глоссарий: доменный <либо «доменный + указатели» — тогда в каждом комплекте `glossary.md` с терминами только своего сервиса>

## Сервисы домена

| service-id | Слот | Название | Вход |
|------------|------|----------|------|
| `shared` | SHR | Общие модули домена | `shared/README.md` |
| `<service-id>` | <СЕРВИС> | <Название сервиса> | `<service-id>/README.md` |
| `<service-id-2>` | нет | <Сервис, включённый без перенумерации> | `<service-id-2>/README.md` |

## Идентификаторы

- `service-id` — имя каталога комплекта и код записи в каталоге сервисов; слот сервиса — 2–4 латинские буквы в идентификаторах артефактов комплекта.
- Документы домена без слотов: `VIS-000`, `GLO-000`; в матрицы комплектов не входят.
- Артефакты комплекта несут слот сервиса сразу после префикса: `FUN-<СЕРВИС>-CL-01`, `ENT-<СЕРВИС>-001`; у сервиса с частями следом — слот части: `FUN-<СЕРВИС>-<ЧАСТЬ>-CL-01` (коды частей — в README комплекта). «Слот: нет» — идентификаторы сервиса без слота сервиса.
- Уникальность идентификатора — в комплекте; слот сервиса делает её сквозной в домене.

## Как читать

1. `domain-vision.md` — зачем домен, карта сервисов.
2. `glossary.md` — термины домена.
3. README нужного сервиса — дальше по его правилам.
````

## Режимы наполнения

### reverse / forward / sync

Источник смысла для блоков «О сервисе», таблицы контуров и «Границы» — `service-vision.md` (и при его отсутствии — выгрузка Confluence / требования, затем vision). Состав дерева и «Как читать» — по фактическому содержимому `output/<service>/docs/`.

## Чек-лист самопроверки

- [ ] Нет frontmatter.
