# Шаблон: платформенные функции и проверки (PLT)

Единый документ-реестр `docs/srs/platform-functions.md` (`PLT-000`) — функции,
проверки и универсальные экраны **платформы ЭКО**, которые сервис вызывает, но
не реализует сам (принадлежат платформе, вне контура микросервиса). Общие
правила — [conventions.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md)
§5.1.2; при противоречии истина в конвенциях.

## Идентификация и границы

- **ID**: `PLT-NNN`, сквозная нумерация по сервису; записи — H3-подразделы
  `### PLT-NNN. <название>` в этом же файле (отдельные файлы не создаются).
  Ссылки извне — `[PLT-NNN <название>](platform-functions.md#…)`, всегда
  ID + название (conventions §5).
- **Граница с `CALL-INT`** (conventions §5.1.2): платформенный метод СО
  опубликованной спецификацией — карточка вызова `CALL-INT` в
  `contract-call/internal/`; функциональность платформы БЕЗ опубликованной
  спецификации — запись `PLT` здесь.
- **Не `CTL`**: контроли (`control/`) проверяют данные заявки внутри сервиса;
  PLT-проверки выполняет платформа (доступ, полномочия, сертификат ЭП).
  Платформенный контроль доступа — всегда `PLT`, не `CTL`.
- **Не `FUN`**: функции сервиса реализует сам микросервис; PLT сервис только
  вызывает.
- Реестр охватывает и **универсальные платформенные экранные формы**,
  переиспользуемые сервисом (единые для многих типов заявок ЭКО), — они не
  описываются как собственные ЭФ сервиса.
- **Записи-заглушки легальны и ожидаемы**: сервис знает точку и цель вызова,
  а постановка платформенной функции ведётся вне его выгрузки. Создаёт записи
  только заход типа `platform-function`; из чужих заходов вместо записи —
  долг (границы скоупа). Пробел постановки — открытый вопрос (§6 конвенции).

## Структура документа

### 1. Назначение

Кратко: что это за реестр и зачем (ссылки по стабильному ID из экранов,
функций, процессов; трассировка). Отграничения от смежных артефактов —
тремя пунктами (не CALL — граница §5.1.2; не CTL; не FUN), ссылками на
реестры соседних типов комплекта.

### 2. Реестр

| ID | Название | Тип | Где используется |
|---|---|---|---|
| [PLT-NNN](#якорь-карточки) | <название> | функция \| проверка \| экран | <ссылки на SCR/FUN/PROC> |

Строка на каждую запись; «Тип» — из закрытого словаря
`функция` / `проверка` / `экран`.

### 3. Карточки

```markdown
### PLT-NNN. <Название>

- **Тип:** функция | проверка | экран (платформа).
- **Назначение:** <что делает и зачем сервису — по источнику, 1–3 предложения>.
- **Где используется:** <ссылки на экраны/функции/процессы с местом вызова
  (событие, шаг); входные данные и результат — если известны из источника>.
- **Статус:** заглушка (постановка платформенной функции вне выгрузки) |
  <ссылка на постановку платформы, когда появится>.
```

По мере появления платформенной постановки запись дополняется параметрами
вызова и обработкой результата (или переезжает в `CALL-INT`, если платформа
опубликовала спецификацию, — переезд фиксируется решением аналитика, ссылки
обновляются в том же изменении).

## Чек-лист

- [ ] Frontmatter `id: PLT-000`, `type: platform-function`; отдельных файлов
  записей нет — только H3 в этом документе.
- [ ] Каждая запись — в реестре §2 и карточкой §3; якоря ссылок работают.
- [ ] «Тип» каждой записи — из словаря функция/проверка/экран.
- [ ] Ни одна запись не дублирует `CALL-INT` (есть спецификация → карточка
  вызова, не PLT) и не описывает контроль данных заявки (`CTL`).
- [ ] Реестр ID матрицы: строка `PLT-000` + строка на каждую запись `PLT-NNN`
  (файл — `platform-functions.md`).
- [ ] Ссылки из SCR/FUN/PROC — «ID + название» на якорь записи.
