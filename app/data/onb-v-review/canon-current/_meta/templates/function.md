# Шаблон: функция системы (FUN)

Шаблон документа функции в `docs/srs/[<подсервис>/]function/<контур>/`. Общие правила — [conventions.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md); при противоречии истина в конвенциях.

## Идентификация и размещение

- **ID по контурам, номер из двух цифр**: функции Клиента — `FUN-CL-NN`, функции Банка — `FUN-BNK-NN`, системные функции (без пользовательского контура, вызываются платформой или процессами) — `FUN-SYS-NN`. Сквозная нумерация в рамках контура; ID стабильны, не переиспользуются.
- **Файл**: `fun-cl-NN-<короткое-название>.md` в `function/client/`, `fun-bnk-NN-<короткое-название>.md` в `function/bank/`, `fun-sys-NN-<короткое-название>.md` в `function/system/` (латиница, kebab-case).
- **Системная функция**: H1 — как в источнике, без приставки контура; в «Доступности» — «Системная функция» (без роли и привилегии) и условие доступности, если задано источником; разделы «Входящие/Исходящие параметры» — таблицами.
- **Один файл на функцию.** Подстраницы источника «Параметры вызова …» не выделяются в отдельные документы — переносятся разделом в файл функции (см. структуру ниже).
- **H1** — название функции с контуром, без названия сервиса: «Клиент: Функция …» / «Банк: Функция …».

## Frontmatter

```yaml
---
id: FUN-CL-NN | FUN-BNK-NN
title: '<дословное наименование из title главной страницы-источника>'
type: function
kind: navigation | operation
service: <service-id>
confluence_page_ids: [<ID страниц-источников, главная первой; только reverse>]
---
```

`kind` — характер функции (решение владельца 2026-08-30, логический
уровень): **navigation** — навигационная: результат — экранное
представление, функция ведёт клиентский путь (открытие ЭФ, переходы);
**operation** — операционная: результат — данные/статус (OK, ошибки,
структуры), экранов не порождает; именно операционные функции лягут в
операции OpenAPI-спецификаций и несут привязку BE-групп контролей.
Критерий — РЕЗУЛЬТАТ функции, не место исполнения (контур — уровень
реализации, «Клиент:»/«Банк:» в имени — привилегия доступа, не
характер). Обёртывать операционную функцию в карточку экранной формы
запрещено (прецедент SCR-CL-05 «Процедура сохранения заявки», z06:
фиктивное поле «Видимость: не отображается» — натяжка типа).

## Структура документа

Порядок разделов фиксированный; необязательные разделы при отсутствии содержимого опускаются целиком.

### 1. Назначение (обязательный)

1–2 предложения: что функция делает для пользователя и зачем. Без технических деталей.

### 2. Доступность (обязательный)

Вызов клиентской/банковской функции ВСЕГДА идёт по токену доступа с
проверкой привилегий пользователя — поэтому для `FUN-CL`/`FUN-BNK`
упоминание привилегий/прав доступа в «Доступности» ОБЯЗАТЕЛЬНО;
источник без привилегий — недоработка аналитика источника: переносится
как есть + открытый вопрос владельцу (механический сторож даёт
предупреждение). Для `FUN-SYS` — фиксированная формула: «Системная
функция; вызов с ТУЗ; роли и привилегии не применяются» — пишется
ОБЫЧНЫМ шрифтом, не жирным (решение аналитика 2026-08-19: жирная
формула визуально спорит с ярлыками-атрибутами). Библиотечная
процедура (FUN-SYS с пометкой «библиотечная процедура; вызывается
только из шагов функций комплекта») — та же формула, эндпоинта и
авторизации у неё нет по определению. Функция, которую подключают
ДРУГИЕ сервисы (код исполняется в их контуре), публикуется библиотечным
контрактом `LIBC-NNN` (шаблон `lib-contract.md`): в разделе «Вызов
функции» — строка «подключается другими сервисами по библиотечному
контракту `<ссылка [LIBC-NNN <название>](../lib-contract/…)>`»,
потребители перечисляются в карточке контракта, не в функции; параметры
— как у функции метода, ссылкой на контракт.

Два пункта списка:

- **Роль и привилегия.** Код привилегии в backticks + `<ссылка [ролевая модель](…/rbac.md)>`. Код берётся **из каталога rbac.md комплекта** (не со страницы функции источника — написания привилегий на страницах Confluence расходятся; расхождение фиксируется в open-questions, в документе используется код rbac.md).
- **Зависимость от статуса заявки** — только для сервисов с заявочной/статусной моделью (есть статусная модель или справочник статусов в комплекте либо статусы в источнике); у сервиса без понятия заявки пункт ОПУСКАЕТСЯ целиком (не писать «не зависит от статуса» — фраза в никуда). Статусы — **системными кодами** (`DRAFT`, `SIGNED`…), не отображаемыми названиями Клиента/Банка. Канонная формулировка: «Функция доступна во всех статусах заявки, кроме `…`, `…` (краткое пояснение почему)». Если перечень разрешённых статусов короче перечня исключений (посчитать оба) — наоборот: «Функция доступна только в статусах … (пояснение); в остальных недоступна». Если статус не влияет: «Функция не зависит от статуса обработки заявки». В конце — `<ссылка [справочник статусов](…/data-model/dictionaries.md)>` (только при существующем файле справочника).

Источник доступности по статусам — обзорные таблицы «Функции Клиента» / «Функции Банка» (колонки статусов); отображаемые названия колонок переводятся в коды по справочнику статусов.

### 3. Вызов функции (обязательный)

Маркированный список: **каждая точка вызова — отдельный пункт**, несколько экранов в одном пункте не группируются. Формат пункта: «кнопкой „<название>“ на <экран>», «двойным кликом по записи списка на <экран>», «при выборе пункта навигационного меню „…“ в …».

Правила:

- **Пользовательский язык**: конкретный элемент UI (кнопка, пункт меню, виджет) + экран, где он расположен, в терминах пользователя. Кодовые имена платформенных интерфейсов («ГС 2.0», «ГС» и т.п.) не пишутся.
- Экраны сервиса — ссылками с ID: `<ссылка [SCR-CL-NN ЭФ … «…»](…/screen-form/…)>`.
- Платформенные экраны вне сервиса — текстом, без ссылок; после списка одной строкой пометка: «Кроме …, перечисленные экраны — платформенные, вне сервиса».
- Функция без своего элемента UI (вызывается процессом или другой функцией) — описать словами: каким шагом какого процесса вызывается, после какой функции; что это значит для пользователя.
- Маркетинговые/deep-ссылки: фиксируется относительный путь и параметры (`/path?param=<…>`); домены тестового и промышленного контуров не переносятся.

### 4. Входящие параметры (необязательный)

Только если параметры есть на странице источника. **Функция метода**
(FUN-SYS по алгоритму из паспорта метода, у которого есть карточка
internal-contract): таблицы параметров НЕ дублировать — раздел заменяется
строкой «Входные и исходящие параметры — по контракту
`<ссылка [INTC-NNN <название>](../internal-contract/…)>`»; в карточке
INTC — встречная ссылка на функцию. **ЕДИНЫЙ канонический состав
колонок** (тот же, что у internal-contracts; лишние колонки не
добавлять; пустые значения источника оставлять пустыми, не выдумывать):

| Код параметра | Наименование параметра | Тип | Обяз. | Кратность | Правила заполнения / Описание |
|---|---|---|---|---|---|
| `body.system` | Системные параметры | Структура | Да | [1] |  |
| `body.system.user_id` | ID «Пользователь» | GUID | Да | [1] | литералы источника дословно |

Правила единого формата (решения 2026-08-16, Э-10/Э-11; синтетическая
нумерация строк ОТКЛОНЕНА — вставка параметра в середину не должна
перенумеровывать таблицу):

- **Иерархию несёт «Код параметра»** — путь (JSON — через точку,
  массивы `[]`; XML — через `/`): вложенность читается из кода
  родителя. Собственная колонка номеров ИСТОЧНИКА, если он её ведёт, —
  переносится дословно как его данные (её стабильность — забота
  источника). Лесенка «колонок-уровней» источника (и её протяжка в
  сетке нормализатора — повторённые заголовки и продублированные
  ячейки) в карточку НЕ переносится: уровни сводятся в ОДНУ колонку
  «Наименование параметра», дублей заголовков в шапке быть не должно
  (механический сторож). При ПУСТЫХ кодах порядок строк сохраняет
  порядок источника (секция — строка перед своими полями).
- **«Код параметра»** ведётся ВСЕГДА и остаётся ПУСТЫМ, если источник
  технических имён не даёт (появятся из реализации/OpenAPI; суррогаты
  не выдумывать). Номера строк источника — НЕ код (механический
  сторож). Образец для случая «источник ведёт только № и русские
  названия» (лесенка «1 / 1.1»):

  | № | Код параметра | Наименование параметра | Тип | Обяз. | Кратность | Правила заполнения / Описание |
  |---|---|---|---|---|---|---|
  | 1 |  | Системные параметры | Структура | Да | [1] |  |
  | 1.1 |  | ID «Пользователь» | GUID | Да | [1] | = "Входящие параметры". <ID «Пользователь»> |

  — «№» здесь — дословная колонка ИСТОЧНИКА (его данные), «Код
  параметра» пуст; писать `1`, `1.1` в «Код параметра» — брак.
- **Динамический набор** («Все значения бизнес-полей шаблона, для
  которых …») — это ПРАВИЛО, не параметр: строка с пустым «Кодом» и
  пометкой «правило:» в начале «Правил заполнения».

Типы, кратность и пояснения переносятся ИЗ ИСТОЧНИКА дословно (потеря типов и
кратности — инцидент file-storage, прогоны 1–2, 2026-08-10). Исходящие
параметры — та же таблица. Если источник даёт только имя и обязательность —
остальные колонки пустые (не удалять колонки).

Для параметров, извлекаемых из URL, — отдельная таблица (Параметр URL | Содержимое | Обязательность) с указанием условности блока.

### 5. Поведение (обязательный)

Нумерованные шаги; ветвления — конструкцией **Если** / **то** / **иначе** / **иначе если** (жирным, каждое условие и исход с новой строки; конвенции §4). Правила:

- **Вложенность шагов переносится структурой, а не только текстом.**
  Маркеры шагов — ДОСЛОВНО из источника (какая бы система ни была:
  `1.1)`, `A)`, `Шаг №2`, включая знак после номера и жирность);
  уровень вложенности шага в источнике (вложенный список или визуальный
  отступ страницы) выражается уровнем вложенности списка в карточке.
  Выпрямление вложенного **Если**/**иначе** в плоский список меняет
  смысл ветвления — это потеря.
- **Каждый шаг — элемент markdown-СПИСКА, иначе рендер склеит шаги в
  плоский абзац.** Составные маркеры источника (`1.1)`, `А.2`) — НЕ
  валидные маркеры markdown: строка с таким маркером и отступом
  становится продолжением абзаца, а не пунктом. Поэтому пункт создаёт
  маркер `-`, а дословный маркер источника пишется ТЕКСТОМ сразу после
  него. Образец двухуровневого ветвления (маркеры условные — в карточке
  всегда дословные из источника):

  ```markdown
  - **1)** **Если** «Тип» = "Критичное", **то:**
    - **1.1)** Определить максимальный номер в очереди
    - **1.2)** **Если** очередь пуста, **то:**
      - **1.2.1)** Разместить объект первым
      - **иначе:**
      - **1.2.2)** Разместить объект следом
    - **иначе:**
    - **1.3)** Вернуть отказ
  - **2)** Завершение работы функции
  ```

- Смена статуса — кодом, с названием перехода и `<ссылка [статусная модель](…/process/status-model.md)>`.
- **Вызовы смежных систем не сворачиваются** (конвенции §4): обращение к чужому контракту (внешняя АС, другой сервис Экосистемы, платформенный метод со спецификацией) — ссылкой на карточку `<ссылка [CALL-EXT-NNN <название>](…/contract-call/external/…)>` (вызов внутри Экосистемы — `CALL-INT-NNN`, `…/contract-call/internal/…`) с передаваемыми параметрами запроса и обработкой ответа; к платформенной функции/проверке ЭКО без спецификации — ссылкой на `<ссылка [PLT-NNN <название>](…/platform-functions.md#…)>`. Нет карточки/записи — НЕ создавать (границы скоупа `create-artifact`): ссылка по имени без файла + долг в open-questions («нет целевого артефакта … — требуется заход <скилл>»).
- Данные — по правилу конвенций §5: первое упоминание сущности — полная ссылка `<ссылка [ENT-NNN <название>](…)>`, последующие — короткая `<ссылка [ENT-NNN](…)>` либо в связном тексте ссылка с названием без ID `<ссылка [название](…)>` (только ENT; для EXT — всегда с ID); атрибут — точечной нотацией `<ссылка [ENT-NNN](…)>.«Атрибут»` (название атрибута — как в модели данных). Та же запись — в плотных формулах и дословных текстах: идентификатор всегда короткой ссылкой; атрибут без идентификатора сущности не пишется.
- Тексты сообщений, диалогов, snackbar — в кавычках, дословно по источнику.
- Экраны — ссылками с ID (как в «Вызове функции»).
- Детали экрана (состав полей, кнопок) не дублируются — «Состав полей и действий экрана — в описании экранной формы».

### 6. Дополнительные разделы (необязательные)

Технические подразделы функции, в источнике вынесенные в подстраницы, — отдельными H2 в том же файле. Типовой случай — «Параметры вызова универсальной функции подписи»: таблица параметров (№ | Параметр | Значение | Тип | Обяз. | Кратность) + правила формирования составных значений подразделами H3. Пометки источника «На усм. арх.» не переносятся (тип не указывается, факт — в open-questions).

## Что не переносится из источника

- Страницы-заготовки под будущие версии (помеченные источником как «будет использоваться при переходе на …»).
- Домены сред (тест/пром), URL Confluence, pageId, ссылки на sources.
- Примеры с артефактами распознавания/OCR.
- Черновые пометки («На усм. арх.», TODO), упоминания legacy-сервиса.

## Трассировка и спорные места

- В том же изменении обновляется матрица трассировки: строка покрытия (функция → SCR, ENT/EXT, CTL, PRN) и строка реестра ID.
- Экран, на который ссылается функция, но который ещё не описан, — НЕ создаётся (границы скоупа): упоминание по имени + долг в open-questions.
- Расхождения источников и пробелы: сначала вопрос аналитику в диалоге; нерешённое — в `open-questions.md` сервиса. В документе спорное место описывается по наиболее достоверному источнику, без отсылок к OQ.

## Чек-лист самопроверки

1. Frontmatter полный, `id` соответствует контуру и не занят (проверить по реестру ID матрицы).
2. Имя файла = `<id строчными>-<короткое-название>.md`, файл в папке своего контура.
3. H1 без названия сервиса, с контуром («Клиент: …» / «Банк: …»).
4. Привилегия — код из rbac.md; расхождение со страницей источника зафиксировано в open-questions.
5. Статусы — кодами; формулировка доступности канонная («во всех, кроме …» или короткий позитивный перечень).
6. Каждая точка вызова — отдельный пункт; без кодовых имён платформы; пометка о платформенных экранах есть.
7. Ссылки ведут только внутрь `docs/`; ссылка на несуществующий артефакт — по имени (без пути) с долгом в open-questions, битых путей нет.
8. Поведение воспроизводимо: шаги, ветвления в форме **Если**/**то**/**иначе** (жирным), дословные тексты сообщений, коды статусов с переходами; вызовы смежных систем — ссылками на CALL/PLT с параметрами и обработкой ответа.
9. Матрица трассировки обновлена (покрытие + реестр) в том же изменении.
10. В документе нет: ссылок на sources/Confluence/код, inline-TODO, отсылок к OQ, доменов сред, «На усм. арх.».
