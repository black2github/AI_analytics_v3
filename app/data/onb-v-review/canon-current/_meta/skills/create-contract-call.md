# Скилл: создать карточки вызова чужих контрактов (contract-call)

Создать или доработать **карточку вызова** (`CALL`) в `output/<service>/docs/srs/contract-call/` и — для внешних АС — **базовый контракт** во внешнем репо. Карточка вызова описывает обращение сервиса к любому контракту, которым он не владеет: внешняя АС, метод другого сервиса Экосистемы, платформенный метод с опубликованной спецификацией.

**Канон репо базовых контрактов:** [https://gitlab.gboteam.ru/EAN/docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts)

Ссылки между этим репо и комплектом сервиса — **только абсолютные** GitLab URL через `HEAD`; имя ветки в адресе не пишется (в репозитории контрактов основная ветка `trunk`, ветки `master` нет):

- карточка: `https://gitlab.gboteam.ru/EAN/docs-external-contracts/-/blob/HEAD/<as>/extint-<as>-NNN-<slug>.md`
- examples: `https://gitlab.gboteam.ru/EAN/docs-external-contracts/-/tree/HEAD/<as>/examples`

Всегда: `AGENTS.md`, [`conventions.md`](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md) §5.1.1, шаблон [`contract-call.md`](../templates/contract-call.md), поток [`create-artifact`](create-artifact.md).

## Вход

- **Контур:** `base` | `call` | `both` (по умолчанию для нового обмена с внешней АС — `both`; для вызова
  сервиса Экосистемы или платформенного метода — только `call`) — КУДА пишем
  (внешний репо / комплект сервиса / оба). Не путать с режимом.
- **Сервис** (для `call`/`both`): `<service-id>`.
- **Внешняя АС** (для `base`/`both`): код папки (`knosis`, `esk`, `tessa`, `f1`, `bsk`, `sbp`, …).
- **Режим `reverse`|`forward` и версия** — как во «Входе» `create-artifact` (ОТКУДА данные).

## Gate

Кто владелец вызываемого контракта?

- **Сам сервис** — это НЕ вызов чужого контракта: собственные методы — тип `internal-contract` (`docs/srs/internal-contract/`, conventions §5.1.3).
- **Внешняя АС** (за границей Экосистемы) — карточка вызова + базовый контракт во внешнем репо (контуры `base`/`both`).
- **Другой сервис Экосистемы** — карточка вызова со ссылкой на `internal-contract/` владельца (если владелец перешёл на API First — на файл контракта в `api-specification/` его репозитория кода по адресу из кода сервиса: документ адресации §5.2); базовый контракт НЕ создаётся из этого захода (им владеет чужой комплект): комплекта владельца нет — дословное имя + межсервисный долг с указанием владельца (`… у владельца <service-id> …`, формат — create-artifact «Недостающая цель ссылки»).
- **Платформа ЭКО**: метод С опубликованной спецификацией — карточка вызова со ссылкой на документацию платформы; функция/проверка БЕЗ спецификации — НЕ этот скилл (запись `PLT` в `platform-functions.md`, conventions §5.1.2).

## Внешний репо недоступен или запрещён окружением

VPN-контур или изоляция прогона могут закрывать доступ к
[docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts).
В этом случае:

1. **Остановись и сообщи аналитику** — не решай молча. Назови, что именно
   нужно из/во внешнего репо (папка АС, свободный `NNN`, строка «Потребители»,
   обновление корневого README).
2. Дальше — по решению аналитика:
   - **(а)** аналитик обеспечивает доступ (переключает VPN, выполняет
     команды, возвращает результат) — продолжаешь штатно;
   - **(б)** аналитик разрешает подготовить base-черновик в
     `sandbox/extint-base-draft/<as>/` (карточка + `examples/`) — тогда
     `NNN` помечается предположительным (свободный номер без репо не виден),
     долг переноса — в `open-questions.md` и в матрицу трассировки.
3. Вариант (б) без явного разрешения аналитика не выбираешь.

## Контур `base`

1. Выбери/создай папку `<as>/` в [docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts); `NNN` — по правилу выдачи ID `conventions.md` §5 (скоуп — папка АС, по реестру внешнего репо). Номер выдаётся по реестру `README.md` СВЕЖЕЙ основной ветки: до выдачи акцептующий обновляет клон контрактов (`git -C <контракты> pull --ff-only` на `trunk`); номер, выданный по отставшему клону, — коллизия с чужим контрактом и перенумерация задним числом.
2. §1–§5 — внешний контракт без ENT/EXT сервиса; sidecar в `<as>/examples/`; §5 — относительные ссылки `examples/…` (внутри репо).
3. **Sidecar (JSON, XML, XSD, WSDL):** только машинный payload/контракт. Комментарии сценария внутрь файла **не** добавлять (`# …`, `<!-- EXTINT-… -->`). Сценарий — в таблице §5 и в имени файла `extint-<as>-NNN-<сценарий>.<ext>`.
4. Раздел **«Потребители»** — таблица (может быть пустой до первой карточки вызова); при известном потребителе — сразу **абсолютный** URL на его карточку вызова.
5. Обнови корневой `README.md` внешнего репо.
6. Frontmatter **без** `service:`.
7. **Публикация — веткой и MR.** Изменения в репозитории контрактов попадают в `trunk` только запросом на слияние: ветка от свежего `trunk` → push ветки → MR. Коммитов в `trunk` не делать: ветка защищена, локальный коммит останется незамеченным и разойдётся с сервером. Публикацию выполняет акцептующий; исполнитель готовит файлы в рабочей копии клона контрактов и перечисляет их в сдаче.

## Контур `call`

1. Назначь локальный ID по подкаталогу — `CALL-EXT-NNN` (внешняя АС, `external/`) или `CALL-INT-NNN` (внутри Экосистемы, `internal/`); нумерация подтипов независимая. В шапке — ссылка на базовый контракт:
   внешняя АС — абсолютные URL на base и `<as>/examples` (см. канон выше); другой
   сервис Экосистемы — его `internal-contract/` (`INTC-NNN`; этот же репозиторий —
   относительная ссылка, другой — абсолютный URL) либо, если владелец перешёл
   на API First, файл контракта `https://gitlab.gboteam.ru/ECO_BE/ms-<code>/-/blob/HEAD/api-specification/<файл>.yaml`
   и операция текстом (`<code>` — код владельца из каталога; поле `api`
   каталога — только для исключений); комплекта владельца нет и контракта
   нет — дословное имя + межсервисный долг с владельцем `<service-id>`);
   состав запроса и ответа нужен потребителю до публикации владельцем — раздел
   «Временный снимок контракта» с источником и датой по шаблону; долг при этом
   остаётся, снимок без источника не заводится;
   платформенный метод — документация платформы.
2. Раздел «Назначение» — ОБЯЗАТЕЛЕН (шаблон, контур B): владелец вызываемого,
   направление обмена (кто кого вызывает), что делает и зачем сервису; 1–3
   предложения по источнику. Карточка вызова читается автономно — читатель
   комплекта не обязан ходить в базовый контракт, чтобы понять суть метода.
3. Раздел «Использование в сервисе …» — процессы, транспорт и две **полные**
   таблицы: чем сервис заполняет исходящие параметры и куда кладёт входящие
   (маппинг ENT). Каждый параметр контракта — строкой, незаполняемый —
   прочерком; имя параметра — полный путь от корня, как в базовой карточке
   (правило волны extint-o2 2026-08-16, сохранено при слиянии с моделью CALL).
4. Обнови README сервиса (реестр: локальный ID | вызываемый контракт (владелец) | базовый контракт | процесс).
5. **Обязательно для внешней АС:** строка в «Потребители» базовой карточки: сервис — `code` из каталога `_meta/services.json`, адрес карточки вызова — от корня комплекта по каталогу (поле `repo`) через `/-/blob/HEAD/<путь>`. Вносится в репозиторий контрактов веткой и MR (контур `base`, п. 7).
6. Трассировка: `docs/traceability-matrix.md` сервиса; ссылки из FUN/SCR/PROC — на **локальный** `CALL-EXT-NNN`/`CALL-INT-NNN`.
7. **Не** создавать `examples/` в комплекте сервиса.

## Контур `both`

Сначала `base`, затем `call` (+ строка «Потребители»).

## Reverse / forward

- **Reverse base:** постановка интеграции → §1–§5 + sidecar во внешнем репо; OQ — в open-questions **потребителя** или methodology-задаче внешнего репо (без OQ в тексте карточки).
- **Сырые HTML-таблицы источника (проход 1 — обязателен ДО анализа).** Таблицы параметров в выгрузке — сырой HTML с rowspan/colspan; читать их напрямую нельзя (теряются строки и иерархия). Порядок по [`source-parsing.md`](../tools/source-parsing.md):
  1. запусти нормализатор из состава методологии: скопируй файл-источник в `sandbox/normalized/` и выполни `python _meta/tools/normalize_tables.py <копия> --profile _meta/tools/table-profiles/<профиль>.json --sidecar` — утилита сама запишет `<копия>.tables.md` рядом в UTF-8 (для ЕСК-обменов профиль `esk-xml-blocks.json`; в `sources/` не писать — только чтение; shell-редирект `>` ЗАПРЕЩЁН — PowerShell пишет UTF-16, инцидент 2026-08-11). Собственный парсер таблиц НЕ писать — утилита уже решает протяжку rowspan/colspan, лесенку путей и сохранение форматирования, самописный разбор теряет их (проверено итерацией 6);
  2. утилита сама проверяет качество по колонкам; при отказе («ниже порога») — сними `--sample`, разметь роли колонок и создай профиль, повтори;
  3. таблицы §2/§3 строй ПО ВЫХОДУ утилиты (полные пути, кратность, форматирование правил — жирные **Если**/**то**/**иначе** и отступы вложенности сохранены); текст вне таблиц бери из источника напрямую; **каждый параметр источника — строка §2/§3, включая узловые элементы**, число строк сверь с выходом утилиты до сдачи;
  4. **ячейки правил/комментариев переноси ИЗ выхода утилиты КАК ЕСТЬ** — с разметкой (`**жирный**`, `&nbsp;`-отступы, `~~зачёркнутое~~`, `<u>`), ссылками и токенами в угловых скобках (`<GUID клиента в ЕСК>`); пересказ ячейки своими словами снимает разметку и теряет токены (проверено итерацией 6-тер). Таблицы, которые утилита вывела «сеткой без сборки путей» (коды отказов, свойства обмена), — тоже переноси с их колонками как есть.
  5. **готовые markdown-таблицы источника** (вне сырого HTML — например «Коды банковских продуктов») утилита не обрабатывает: переноси их в карточку напрямую, ЦЕЛИКОМ и как есть: все колонки и строки, содержимое и порядок колонок — как в источнике; перед сдачей сверь ЧИСЛО таблиц — HTML-таблицы из выхода утилиты + markdown-таблицы источника = таблицы карточки. Потеря таблицы или её колонок = потеря требований (замечание итерации 6-секст: «Коды банковских продуктов» ужалась до одной колонки без пояснений).
  6. **разнесение названий (семантика — твоя работа, прохода 2), НЕЗАВИСИМО от того, заполнены ли остальные колонки строки:** колонка «Наименование параметра» несёт ТОЛЬКО ИМЯ параметра. Всё остальное из ячейки названия источника — пояснения в скобках («(допускается передача…)»), вторые абзацы («Проверка ЕИО … выполняется всегда», «Время должно быть указано…»), описания назначения («Секция для связи блока…», «ссылка на блок…»), правила-присвоения («=Код должности…») — переноси ДОСЛОВНО в «Правила заполнения» той же строки (в конец, после существующего текста, через <br>). Ничего не выбрасывай. Отчёт утилиты помечает часть таких строк «⚠ подозрительных названий» — это ПОДСКАЗКА, а не полный список: решай по смыслу для каждой строки. Перенос строки внутри ячейки таблицы — ВСЕГДА `<br>`, никогда не настоящий перенос (ломает таблицу; --check это брак).
- **Reverse call:** колонка целевого сервиса в Confluence → раздел использования; не дублировать полный контракт.
- **Forward:** base → call → потребители.

## Режим C — change (изменение по постановке)

Типовые задачи: новый вызов внешней АС, другого сервиса Экосистемы или
платформенного метода из функции или процесса; изменение правил заполнения
сообщения или обработки ответов; новая операция существующего контракта.
Исполняй шаги режима C `create-artifact`; ниже — карта и вопросы.

**Карта затронутых карточек:**

- **Карточка вызова** `CALL-EXT-NNN` / `CALL-INT-NNN`: назначение,
  использование (процессы, функции), транспорт, правила заполнения
  исходящего сообщения, обработка входящих ответов.
- **Базовый контракт** в режиме C НЕ создаётся: внешняя АС — репозиторий
  `docs-external-contracts` (`EXTINT`), сервис Экосистемы — `INTC`/`LIBC`
  владельца. Описания нет — строка долга «у владельца <service-id>» в
  матрице; состав запроса и ответа нужен сейчас — раздел «Временный снимок
  контракта» только с источником и датой (шаблон), долг не отменяет.
- **README-реестры** `CALL-000`, `CALL-EXT-000`, `CALL-INT-000`.
- **Функция или процесс**: шаг со ссылкой на `CALL` (ID + название);
  **модель данных**: атрибуты, которые уходят и приходят; **ошибки**: коды
  отказа → сообщения формы или статусы.
- **Матрица**: строка реестра на новую `CALL`, покрытие «функция → CALL»,
  долг у владельца.

**Обязательные вопросы при пробеле:**

1. Какая система или сервис и какой метод (имя дословно); владелец
   (`service-id` по справочнику сервисов).
2. Есть ли опубликованный контракт и где (репозиторий, страница); нет —
   долг и источник для снимка.
3. Направление и транспорт (синхронный вызов, очередь, файл).
4. Какие данные уходят и откуда берутся (атрибуты, поля); что приходит.
5. Что делать с ответом и ошибками: повторы, таймаут, статус, сообщение
   пользователю.

**Идентификаторы:** `CALL-<EXT|INT>-NNN` — по реестру матрицы; снимок без
источника запрещён; платформенный метод без спецификации — `PLT`-реестр,
не `CALL`.

Пробел, который аналитик оставил сознательно, — строка долга вида «открытый вопрос»
в матрице; у каждого нового факта — происхождение (режим C, шаг 6); отчёт дельты — в
описание MR.

## Самопроверка

1. Чек-лист шаблона (секции A/B).
2. Grep base (§1–§5): нет `ENT-|data-model/|open-questions|service:|confluence\.` (последнее — живые URL Confluence: заменяются ссылками на карточки репо по `confluence_page_ids`, правило шаблона; поле frontmatter `confluence_page_ids` под греп не попадает — в нём нет точки после «confluence»).
2a-title. **`title` базовой карточки:** дословно из title главной страницы-источника; ведущий маркер контура-потребителя
(`[O2+NEW]`, `[ОНБ_2021]`, `[КК_ВК]`, `[ББ_РЕГ]`, `[ГЭП]`, `[РЭП]`) снимается — базовый контракт общий для потребителей;
имя системы в скобках сохраняется. Шаблон, раздел A.
2a. **Дословность и полнота (инциденты итерации 5):** «Протокол взаимодействия» в §1 перенесён целиком (канал, сигнатура, упаковка, формат ответа, общий канал); перечень допустимых кодов отказов источника — таблицей в §4; в «Правилах заполнения» сохранены жирные **Если**/**то**/**иначе** и отступы вложенности (`&nbsp;`).
2b. **Таблицы §2/§3**: состав колонок канонический (`Код параметра | Наименование параметра | Тип | Обяз. | Кратность | Правила заполнения`); пути **полные от корня** (XML — через `/`, JSON — через `.`); в «Коде параметра» — только технические имена, склейка с бизнес-названием (`upload_token/Токен загрузки`) — брак; секционные строки источника («Заголовок запроса», «Тело запроса», взаимоисключающие блоки) — строками таблицы; узловые элементы-контейнеры присутствуют строками; **число параметров сверено с источником** (потерянных нет); названия и литералы — дословно, без сокращений.
2d. **Справочники источника без сокращений:** в base-карточке нет слов «фрагмент», «и т.д.», «см. источник» внутри таблиц-справочников; каждый справочник — все колонки и все строки (образец — шаблон §2.N; инцидент 6-секст/6-септ).
2c. **Механическая проверка готовой base-карточки:** `python _meta/tools/normalize_tables.py <карточка.md> --check --source <файл-источник>` — должна закончиться `OK` (код 0). Ключ `--source` обязателен: он сверяет карточку с источником — каждая готовая markdown-таблица источника (справочники) должна присутствовать значениями ВСЕХ колонок, дословно (сокращение формулировок — тоже брак). `БРАК` (код 2) = литералы якорных колонок переписаны при переносе (кратность `[1]` → `1`, обязательность произвольным текстом — инцидент итерации 6-кватер); исправь по выходу утилиты и прогони проверку снова. Литерал, дословно совпадающий с ячейкой той же колонки источника (например авторское `[1]` в обязательности), утилита принимает сама с пометкой «дословно из источника — принято» — подгонять такие значения под словарь ролей ЗАПРЕЩЕНО (дословность сильнее словаря; инцидент file-storage, заход external-integrations 2026-08-10). **Сдача:** в отчёте аналитику для КАЖДОЙ base-карточки приводится ПОСЛЕДНЯЯ строка вывода `--check` ДОСЛОВНО (`# OK: …` / `# БРАК: …`); пересказ и переименование вердикта («предупреждение», «замечание», «особенность») запрещены — вердикт цитируется, не описывается. Не доведён до `OK` за две итерации исправлений — СТОП, не зацикливайся и не переименовывай: карточка сдаётся с явным статусом «НЕ ГОТОВО», дословный вывод гейта + причина — в спорные места; решение о приёме с `БРАК` принимает только аналитик. (Инцидент 2026-08-12: девять карточек с `БРАК` сданы как «предупреждения» — у правила не было ветки честного выхода.)
3. Sidecar в `<as>/examples/`: нет префиксных `# EXTINT` / `<!-- EXTINT` (только payload).
4. Карточка вызова внешней АС: в шапке есть URL, начинающиеся с `https://gitlab.gboteam.ru/EAN/docs-external-contracts/`; вызова сервиса Экосистемы — ссылка на `internal-contract/` владельца, на файл контракта в `api-specification/` его репозитория кода (через `HEAD`, операция текстом) либо дословное имя + долг; нет локального `examples/`.
5. В base «Потребители» — абсолютный URL на карточку вызова (если она уже есть).
