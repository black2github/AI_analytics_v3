# Скилл: собрать комплект BRD (ассемблер + проверка достаточности)

Собрать или актуализировать полный комплект бизнес-требований `output/<service>/docs/brd/` по готовому комплекту SRS этого же сервиса (**reverse-from-SRS**) и доказать его **достаточность** механизмом покрытия. Слой BRD (бизнес-аналитик). Оркеструет скиллы [`create-feature`](create-feature.md), [`create-use-case`](create-use-case.md), [`create-business-rules`](create-business-rules.md). Необязательный каталог НФТ `output/<service>/nfr/` собирает [`create-nfr`](create-nfr.md) и в `docs/brd/` не вкладывается. `docs/service-vision.md` и `docs/glossary.md` (корень `docs/`, не внутри `brd/`) — не трогает (у них свои скиллы).

Всегда действуют: `AGENTS.md`, `conventions.md`. Шаблоны — [`feature-spec`](../templates/feature-spec.md), [`use-case`](../templates/use-case.md), [`business-rules`](../templates/business-rules.md). Коммит/push — [git-workflow.md](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md).

## Вход

- `service`.
- Готовый (или частичный) комплект `output/<service>/docs/srs/`.
- Режим: **сборка** (BRD ещё нет / неполон) или **сверка достаточности** (BRD есть, проверить покрытие).
- Необязательно: `nfr_sources` — список md-страниц уже написанных НФТ. Пустой список шаг НФТ пропускает. `ingress: forward` этот скилл не запускает.

## Границы

- **Пометка происхождения (обязательна для документов, кроме `type: nfr`).** Каждый такой документ, собранный этим
  скиллом, несёт в frontmatter `origin: reconstructed-from-srs` и первой
  строкой преамбулы: *«Реконструкция по комплекту SRS (reverse-from-SRS);
  не является требованиями заказчика. Трассировка на этот документ ловит
  рассинхроны последующих изменений; исходные ошибки SRS она не выявляет —
  документ выведен из него же.»* Валидирующий лид обязан видеть, что перед
  ним реконструкция. Документы `type: nfr` от `origin` и этой преамбулы освобождены. Образец frontmatter:

  ```yaml
  ---
  id: US-01
  type: feature
  service: <service-id>
  origin: reconstructed-from-srs
  ---
  ```
- Реконструкция запускается ТОЛЬКО по готовому (или осознанно частичному)
  SRS — досрочная сборка из одного типа артефактов даёт кривой BRD и запрещена
  правилом скоупа `create-artifact` (§ «Границы скоупа»).
- BRD и SRS **не ссылаются друг на друга** в телах документов (`conventions.md` §5.4). Вся связь BRD↔SRS — в матрице трассировки `docs/traceability-matrix.md`.
- Реестры каталогов — `README.md` (не `_index.md`).
- Схема ID слоя BRD — таблица в `conventions.md` §5 (единственный источник; здесь не перечисляется).

## Порядок сборки

1. **Инвентарь SRS.** Собери из комплекта (эффективно — параллельными под-агентами по поддеревьям, каждому передай текущее состояние BRD, чтобы возвращали структурированный материал, а не пересказ):
   - функции — `function/` (клиент/банк/системные): назначение, актор, поведение, ветвления, статусы, контроли;
   - процессы — `process/` (+ `status-model.md`): сквозные сценарии, исходы, статусы;
   - контроли — `control/`: кандидаты в `BR`/`ТР` через фильтр «что не бизнес-правило»;
   - печатные формы — `print-form/`, роли — `rbac.md`, уведомления — `ntf-notification.md` (либо `notification/` при нарезке), статусы/справочники — `data-model/`.
2. **Бизнес-правила.** Собери `business-rules.md` (скилл `create-business-rules`).
3. **Фичи.** Сгруппируй функции в способности по актору → фичи (скилл `create-feature`), сквозная нумерация `US-NN`; обнови `features/README.md`.
4. **Use Cases.** Сведи процессы к бизнес-UC (скилл `create-use-case`); обнови `use-cases/README.md`.
5. **НФТ.** Если `nfr_sources` непуст — вызови [`create-nfr`](create-nfr.md) с `ingress: reverse` после фич и UC, до навигации и трассировки. Пустой список — шаг пропускается. Секцию BRD-6 не смешивай с гейтами достаточности BRD-1…BRD-5.
6. **Навигация.** Обнови `docs/brd/README.md` (разделы business-rules / features / use-cases; каталог НФТ сюда не вкладывается). Актуализируй корневой `docs/README.md` скиллом [`create-docs-readme`](create-docs-readme.md) (режим `sync`) — дерево, «Как читать» и таблица разделов должны отражать появившийся BRD и, если каталог есть, `output/<service>/nfr/`; легенду CL/BNK и вход через Service Vision не ломай.
7. **Трассировка.** Заполни BRD-секции матрицы (см. ниже) и прогони гейты. BRD-6 заполняет `create-nfr`, если каталог НФТ создан.

## Механизм проверки достаточности (гейты покрытия)

Комплект BRD **достаточен**, когда все счётчики ниже равны **0**. Проверка обратная: инвентарь SRS → покрытие в BRD, доказывается матрицей трассировки `docs/traceability-matrix.md`.

**Перечень гейтов достаточности и секций матрицы — единственный источник:
`conventions.md` §5.3 п. 8–9** (здесь не дублируется). Скилл исполняет их
механику: инвентарь SRS из реестров разделов → заполнение секций BRD-матрицы →
подсчёт каждого гейта; при значении ≠ 0 — перечислить незакрытые элементы.

Инвентарь SRS для гейтов бери из реестров: `function/README.md`, `process/README.md`, `control/README.md`, `print-form/README.md`.

## Самопроверка

1. Прогони чек-листы шаблонов `feature-spec` / `use-case` / `business-rules` по каждому документу.
2. Прогони гейты покрытия (все = 0). Незакрытое из-за пробела источника — в `output/<service>/open-questions.md`.
3. Grep-антирегрессия по `docs/brd/**` (ожидание: нет совпадений ВНЕ frontmatter; строка `confluence_page_ids:` во frontmatter — законное поле): `OQ-|TODO|sources/|pageId|confluence|_meta/|REJ-` и ссылок в SRS (`\]\([^)]*srs/`).

## Выход аналитику

Отчёт: (1) что собрано (перечень фич/UC/BR); (2) таблица гейтов со значениями счётчиков; (3) спорные места (**вопрос / предположение / что проверить**); (4) пробелы, вынесенные в open-questions.
