# Инструменты методологии

## Порядок правок инструментов

Утилиты этого каталога (`*.py`) живут в репозитории прибора
`requirements-analyzer-v3` (`app/scripts/CI/`, тесты — `tests/test_*.py`);
здесь — синхронизируемые копии, байт в байт с точностью до переносов строк.
Слияние в канон тесты прибора не запускает, поэтому ошибка в копии остаётся
незамеченной до прогона на комплекте.

1. **Правка утилиты — в репозитории прибора, с тестами.** Оттуда владелец
   прибора переносит копию в канон своим срезом. Если доступа к репозиторию
   прибора нет, к MR в канон прикладываются сценарии проверки (вход →
   ожидаемые строки отчёта); тесты по ним пишет владелец прибора, он же
   сливает.
2. **Конфликт в `_meta/tools/*.py` при слиянии не разрешается
   самостоятельно.** Разрешение «в пользу своей ветки» молча откатывает
   чужие правки: так 2026-10-14 из `link_debts.py` на `master` выпал формат
   долга без цели. При конфликте — перечень своих правок прибора владельцу
   прибора; он объединяет в репозитории прибора и обновляет копию.
3. **Перед MR, который трогает `_meta/tools/`:** `git fetch`, затем
   `git log --oneline master..origin/master -- _meta/tools/`. Непустой вывод —
   сначала п. 2, потом MR. Сторож структурных фактов
   (`python _meta/tools/structural_facts.py --repo .`) должен быть чист.
   Владелец канона перед вливанием чужого MR и после появления чужих
   коммитов на `master` смотрит дельту среза (`canon_delta.py`, ниже).
4. Правки `_meta/skills`, `_meta/templates`, `_meta/migration` и прочих
   текстов канона этим порядком не ограничены — обычная ветка и MR.

Копии сверяет владелец прибора перед каждым своим срезом (сравнение с
репозиторием прибора без учёта переносов строк); `accept_canon.py` копии не
сверяет — он принимает срез как есть.

## normalize_tables.py — проход 1 разбора сырых HTML-таблиц

Раскрывает rowspan/colspan в сетку, собирает иерархию в полные пути,
сохраняет форматирование правил (жирные **Если**/**то**/**иначе**,
`&nbsp;`-отступы), проверяет качество по колонкам и ОТКАЗЫВАЕТСЯ отдавать
брак (порог `--min-valid`, по умолчанию 95 %). Правила применения —
[source-parsing.md](./source-parsing.md), раздел «Два прохода».

Запуск (из корня репозитория; выход — вне `sources/`):

```text
python _meta/tools/normalize_tables.py <файл.md> --profile _meta/tools/table-profiles/<профиль>.json --sidecar
```

Ключ `--sidecar` пишет `<файл>.tables.md` рядом в UTF-8. Редирект `>` в PowerShell **запрещён**: PowerShell пишет UTF-16.

Разметка нового макета: `--sample` выдаёт шапку и строки-образцы; по ним
создаётся JSON-профиль в `table-profiles/` (см. формат в шапке утилиты).

Зависимости: Python 3.8+ (любой современный; версия 3.12 обязательна только в закрытом контуре — под неё собраны
offline-колёса бандла экспортёра) и пакет beautifulsoup4 (`pip install beautifulsoup4`).
Правки — по разделу «Порядок правок инструментов».

## transfer_gate.py — гейт переноса комплекта src → docs

Проверяет, что комплект `docs/` рабочего репозитория `src-<service-id>` технически
пригоден к переносу в `docs-<service-id>`: собирает его в целевой раскладке (корень без
`docs/`, без служебных файлов миграции), прогоняет прибор (`selfcheck` с источниками),
валидатор платформы AI Factory (копия в `platform/`) и условия переноса (открытых
вопросов нет, раздел «Покрытие: API ↔ SRS» в матрице, нет `api/`, есть README). Отчёт — таблица
«Статус | Критерий | Проверка | Результат» (блокеры → предупреждения → к сведению → пройдено;
критерии — чек-лист DoR, раздел «Технологическая совместимость»; `TRF-01…05` — предложенный
блок «Условия переноса», служебные метки ПРИБОР и ВАЛИДАТОР поясняются легендой под таблицей),
итог — `READY` / `NOT READY`; `--log` — журнал в порядке проверок, `--report <файл.md>` — отчёт
с шапкой (вид допуска, коммит src, срез канона), таблицей, реестром долгов и ручной частью
протокола до подключения — приложение к протоколу. Открытый вопрос журнала блокирует перенос,
если не переведён в строку долга матрицы со ссылкой на `OQ-NNN` и владельцем. Полное описание,
ключи и ограничители — в шапке утилиты.

```text
python _meta/tools/transfer_gate.py --src <клон src-репозитория>
python _meta/tools/transfer_gate.py --src <клон src> --out <клон docs-репозитория>
```

При `READY` и ключе `--out` комплект копируется в клон docs-репозитория; коммит и MR —
человек. Зависимости: PyYAML (для валидатора платформы), git в PATH.

**Журнал открытых вопросов.** Гейт ищет `open-questions.md` по порядку: `--questions <файл>`,
каталог комплекта, корень src, рядом с выгрузкой (родитель каталога `confluence/` из
`--sources`), `sources/<имя комплекта>/` — последнее для общего репозитория нескольких
комплектов, где комплект лежит в `output/<service-id>/`. Журнал не найден — блокер CORE-20
(открытые вопросы не проверены, READY подтвердить нельзя), в сообщении перечислены
проверенные места; в режиме репозитория документации журнал не ожидается.

**Режим репозитория документации.** Если `--src` — целевой `docs-<service-id>` (комплект в
корне, `docs/` нет, матрица трассировки в корне), гейт включает режим сам (явно — `--docs .`)
и проверяет комплект на месте: строка `РЕЖИМ` в отчёте, `CODEOWNERS` и `gpb-manifest.json` —
в самом репозитории, журнал вопросов не ожидается (вопросы комплекта — строки долга вида
«открытый вопрос» в матрице), служебные файлы миграции в корне — блокер, `--out` отклоняется.
Такой отчёт — расстояние комплекта до действующего стандарта, а не проверка переноса.

```text
python _meta/tools/transfer_gate.py --src <клон docs-репозитория> --report <файл.md>
```

Сторож forward: при `--out` в репозиторий назначения, где уже есть каталог `tasks/`
(постановки режима C — change), гейт отвечает ✗ TRF-02 и не копирует — после закрытия миграции
правки делаются в docs-репозитории, повторный перенос поверх затёр бы их.

## delta_report.py — отчёт дельты режима C (change, изменение по постановке)

Собирает детерминированную часть отчёта дельты (шаблон `_meta/templates/delta-report.md`) по
изменениям рабочего дерева репозитория документации относительно базы: изменённые, созданные и
снятые файлы с их карточками; новые и снятые ID со сверкой по реестру матрицы (дубли, карточка вне
реестра, ID без файла — замечания); добавленные и снятые строки реестра, связей и долгов матрицы
(обе формы строки долга); затронутые карточки — ссылающиеся на изменённые; заготовка таблицы
фактов из добавленных строк диффа (колонку «Происхождение» дописывает агент); открытые вопросы
постановки `tasks/<JIRA-ID>.md` и долги вида «открытый вопрос». Read-only; замечания не роняют
сборку (блок «Замечания прибора», код 0); код 2 — только когда отчёт собрать нельзя (не
git-репозиторий, нет матрицы, постановка в дельте неоднозначна). Зависимости — стандартная
библиотека и git.

```text
python _meta/tools/delta_report.py --repo <корень клона docs-репозитория> --task <JIRA-ID> --out <файл.md>
python _meta/tools/delta_report.py --repo <корень> --base <ref> --json
```

Без `--task` задача берётся из единственной постановки в дельте; `--base` по умолчанию `master`,
иначе `main`, иначе `trunk`, иначе рабочее дерево против `HEAD`. Отчёт — в описание MR, не в
репозиторий.

## passport_sync.py — паспорт раскладки ЭКО для платформы AI Factory

Паспорт проекта ЭКО у платформы (`docs-kit-layout.md` для ролей, `.yaml` для скриптов) —
производное от стандарта ЭКО и канона миграции. Утилита собирает машинную часть из домов
фактов канона (таблица типов шаблона README, формы `id:` шаблонов, документ адресации,
каталог сервисов, репозиторий базовых контрактов) и сверяет прозаическую часть паспорта
платформы с теми же домами: место AsyncAPI, реф ссылки на код, префиксы, набор `type`,
поля frontmatter, имена разделов README и матрицы, путь → навык, коды внешних АС. Описание,
ключи и ограничители — в шапке утилиты.

```text
python _meta/tools/passport_sync.py --build <выход>/docs-kit-layout.yaml --contracts <клон docs-external-contracts>
python _meta/tools/passport_sync.py --check <каталог паспорта платформы> --contracts <клон docs-external-contracts>
```

Выход проверки — markdown-таблица «Статус | Тема | В паспорте платформы | В стандарте ЭКО и
каноне миграции | Дом факта», сгруппированная: расхождения, объявленные отличия
reverse-комплектов, совпадения; итоговая строка со счётом; код возврата 1 при расхождениях.
Зависимость: PyYAML.

## canon_delta.py — дельта среза канона для ревью (утилита владельца)

Печатает между двумя ревизиями канона по зоне `_meta/`, `AGENTS.md`, `README.md`,
`.cursor/`, `.claude/`: удалённые, переименованные, добавленные и изменённые файлы;
удалённые заголовки разделов в изменённых `.md` — отдельно разделы документа и отдельно
структура образца в блоках кода (тело карточки шаблона в ````markdown); изменённые утилиты
`_meta/tools/*.py` с числом строк; итог «к ревью». Это не вердикт: удаление может быть верным
(раздел переехал в другой дом), но увидеть его нужно до вливания, а не после жалобы команды.
Повод — слияние 2026-10-14, снявшее раздел шаблона и формат долга прибора незаметно для всех.

```text
python _meta/tools/canon_delta.py --repo <клон канона> <старая ревизия> [<новая, по умолчанию HEAD>] [--strict]
python _meta/tools/canon_delta.py --repo <клон канона> origin/master <ветка MR>
```

Ревизии — любые ссылки git (хэш среза из профиля стенда, `origin/master`, ветка MR); сетевых
команд утилита не выполняет, `git fetch` — отдельно. `--strict` — код возврата 1, если есть
удаления или правки утилит. Командам и координаторам утилита не нужна: приём среза остаётся
`accept_canon.py` с контрактом «одна строка ✓ и три строки сторожа».
