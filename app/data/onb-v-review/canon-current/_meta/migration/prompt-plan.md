# Промпт генерации плана миграции сервиса к эталону

Универсальный промпт для команд сервисов Экосистемы (ДБО юрлиц).

## История изменений

**Версия 2.2 (2026-08-27) — выдаётся команде в раннем доступе.**
Существенное расширение против v1.x, отсюда мажорная версия.
Дополнение 2026-09-03: портированы нормы v1.2 — атрибут `repo`
справочника сервисов (межсервисная адресация), «репозитории чужих
сервисов только из справочника», межсервисный долг «у владельца»,
стоп-условие на незаполненный `repo`. Линия v1 ЗАМОРОЖЕНА (решение
владельца): новые нормы вносятся только в этот файл.
Дополнение 2026-09-08: в инструкцию команде (шаг 3) добавлено
переключение репозитория сервиса на ПРОМ-срез (тег `src/PROM`, ветка
`prom`) перед стартом — после восстановления хронологии основная
ветка стоит на последнем срезе, где применены все незавершённые
задачи; план с неё выглядел бы правильным, но описывал бы не ПРОМ.
Дополнение 2026-09-10 (заменяет процедуру от 2026-09-08): основная
ветка `master` репозитория сервиса = ПРОМ (решение владельца), поэтому
шаг 3 — проверка актуальности `master`; отдельная ветка `prom` больше
не нужна. Устройство веток и тегов — гид, «Ветки и теги репозитория
сервиса».

Изменения 2.2 (по пилоту исполнения ступени 7: PRE-00…ISS-01 на
Корпоративных Картах, журнал SANDBOX.md): правила исполнителя ВЫНЕСЕНЫ
из плана в нормативный протокол канона `_meta/tools/step-protocol.md` —
план и промпты на него ссылаются, а не пересказывают (измерено: в
самодостаточных промптах ~55% объёма — дрейфующий пересказ протокола,
~15% — пересказ скиллов); карточка этапа сделана самодостаточной для
сборки промпта этапа подстановкой в шаблон §10 протокола; сборка
промптов этапов переведена на режим «по одному, перед этапом» (норма —
п. 10 шага 4); хэш канона исключён из промптов в пользу сторожа среза
(дважды за пилот хэш из промпта устаревал между генерацией и
запуском); предусловия этапов переведены на формулу «принято приёмкой
акцептующего» вместо требований к формату строк отчётов прошлых
этапов (формат эволюционирует с прибором).

Изменения 2.1 (по обкатке плана Корпоративных Карт на подсервисном
каноне, журнал SANDBOX.md песочницы): материализация утверждённой
разметки в ПРОФИЛЬ источников (источник истины для сторожа — профиль,
не план); фактическая дата среза выгрузки без псевдоточности; судьба
копий/тестов/черновиков — точечные page_id-списки «вне SRS» с
причинами, расхождение копии с актуальной — OQ; перечитка канона при
его правке посреди Q&A; локальные обозначения плана — только с
расшифровкой и запретом переноса в артефакты; отклонение от
утверждённой разметки — только с основанием фактами; однофайловые
слоты уровня куска — по conventions §3.1.

Изменения 2.0 (по A/B-эксперименту на срезе «Корпоративные Карты», ~630
файлов, песочница ext-sandbox, журнал SANDBOX.md): постраничная опись
строится МЕХАНИЧЕСКИ инструментом `source_inventory.py` — в контрольном
прогоне v1 опись «чтением всего» на 457 страницах выродилась в агрегаты
по веткам (суммы сходились, но 90% страниц потеряли пофайловую
идентификацию молча) при ×4 времени; классификация — по сигналам с
точечным чтением; полнота плана — инструментальным гейтом, строка
которого обязана попасть в сдачу; для крупных сервисов (≳200 страниц) —
декомпозиция по подсервисам.

## Как пользоваться (инструкция команде сервиса)

Обозначения путей: `<src>` — корень репозитория сервиса, `<клоны>` —
родительский каталог клонов (`<клоны>\docs-o2new` и т. д.); подставляйте
свои значения. Полная таблица — гид `reference.md`, «Обозначения
путей». Команды — PowerShell; после каждой указано, какой вывод
подтверждает выполнение шага.

0. Проверьте окружение: git настроен (авторство коммитов миграции
   персональное; акцепт этапов фиксируется НЕ локальными данными git, а
   approve и слиянием MR в основную ветку), Python 3 доступен в PATH,
   установлены пакеты `beautifulsoup4` (инструменты проверки:
   `_meta/tools/selfcheck.py`, нормализатор таблиц) и `pyyaml` (валидатор
   платформы в гейте переноса `_meta/tools/transfer_gate.py`); полный
   список зависимостей — `_meta/tools/requirements.txt` в клоне канона.
   Установка: `python -m pip install -r <канон>\_meta\tools\requirements.txt`.
   В закрытом контуре — офлайн: на машине с доступом `python -m pip
   download -r <канон>\_meta\tools\requirements.txt -d <каталог>`
   (скачаются wheel: beautifulsoup4, soupsieve, PyYAML), перенести каталог и
   выполнить `python -m pip install --no-index --find-links <каталог> -r
   <канон>\_meta\tools\requirements.txt`. Ставьте пакеты тем же
   интерпретатором, которым будете запускать инструменты (`python -m
   pip`, не голый `pip`). Валидатор платформы скачивать не нужно — он
   входит в клон канона (`_meta/tools/platform/`).

   ```powershell
   git config --global user.name; git config --global user.email
   python --version
   python -c "import bs4; print(bs4.__version__)"
   ```

   Ожидание: две непустые строки (имя и почта), `Python 3.x` и номер
   версии bs4 (ошибка `ModuleNotFoundError` означает, что пакет не
   установлен в этот интерпретатор).
1. Подготовьте репозиторий сервиса `<src>`: структура каталогов — гид,
   «Структура репозитория сервиса». Выгрузка ПРОМ-среза требований
   утилитой confluence-tree-exporter лежит в `<src>\sources\confluence\`
   (рядом `<src>\sources\raw\` — нетронутый архив выгрузки, только для
   чтения).

   ```powershell
   Get-ChildItem <src>\sources\confluence -Recurse -Filter *.md | Measure-Object
   ```

   Ожидание: `Count` больше нуля.
2. Убедитесь, что выгрузка доведена до чистового вида — БЕЗ
   CriticMarkup-разметки; если разметка есть — сначала доведите
   аналитику до чистового вида (доводка — ваша зона ответственности).
   Замороженные поддеревья несут frontmatter-флаг `unapproved_jira`
   (см. гид, «Термины», «Доводка выгрузки»).

   ```powershell
   Get-ChildItem <src>\sources\confluence -Recurse -Filter *.md | Select-String -Pattern '\{\+\+|\{--|\{~~|\{==|\{>>' | Measure-Object
   ```

   Ожидание: `Count` равен 0.
3. Убедитесь, что репозиторий сервиса стоит на актуальной основной
   ветке `master` — она содержит ПРОМ-срез требований (устройство веток
   и тегов репозитория — гид, «Ветки и теги репозитория сервиса»).
   Планировщик ветку не проверяет: план, построенный с другой ветки,
   будет выглядеть правильным, но опишет не ПРОМ.

   ```powershell
   git -C <src> checkout master
   git -C <src> pull origin master
   git -C <src> branch --show-current
   ```

   Ожидание: третья команда отвечает `master`.
4. Склонируйте репозиторий канона (единый для всех команд), основная
   ветка `master`. Канон лежит в каталоге `_meta/`: шаблоны
   `_meta/templates/`, скиллы `_meta/skills/`, инструменты
   `_meta/tools/`; входная точка — `_meta/migration/README.md`.

   ```powershell
   git clone https://gitlab.gboteam.ru/EAS/docs-o2new.git <клоны>\docs-o2new
   git -C <клоны>\docs-o2new branch --show-current
   ```

   Ожидание: `master`.

   Шаги 5–8 можно выполнить одной командой из каталога `<клоны>`:
   `docs-o2new\_meta\migration\clone-workspace.bat [URL репозитория сервиса]`.
   Он клонирует недостающие репозитории, обновляет существующие,
   переключает на нужные ветки, проверяет их и наличие
   beautifulsoup4. Повторный запуск безопасен. Команды ниже — то же
   самое по шагам.
5. Склонируйте репозиторий эталона (единый для всех команд) —
   эталонный комплект лежит в корне репозитория (`brd/`, `srs/`,
   `glossary.md`, `traceability-matrix.md` и т. д.).

   ```powershell
   git clone https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git <клоны>\docs-account-opening-request
   git -C <клоны>\docs-account-opening-request branch --show-current
   ```

   Ожидание: `trunk`.
6. Склонируйте репозиторий стандартов, основная ветка `master`. Нужны
   конвенция `standards/analytics/conventions.md` (политика ID,
   подсервисы §3.1, слот части) и нотация
   `standards/analytics/notation.md`; на них опираются шаблоны и
   инструмент проверки. Репозиторий большой (сотни МБ), из него нужны
   два каталога — клонируйте частично (нужен git не ниже 2.26; обычный
   полный клон тоже допустим). `cookbook/analytics` — git-процесс
   docs-репозиториев (MR, ревью), на него ссылаются стандарты;
   `git pull` в таком клоне работает как обычно.

   ```powershell
   git clone --filter=blob:none --sparse https://gitlab.gboteam.ru/ED/eco-techbook.git <клоны>\eco-techbook
   git -C <клоны>\eco-techbook sparse-checkout set standards/analytics cookbook/analytics
   git -C <клоны>\eco-techbook branch --show-current
   ```

   Ожидание: `master`.
7. Склонируйте репозиторий спецификаций/контрактов внешних АС (единый
   для всех команд).

   ```powershell
   git clone https://gitlab.gboteam.ru/EAN/docs-external-contracts.git <клоны>\docs-external-contracts
   git -C <клоны>\docs-external-contracts branch --show-current
   ```

   Ожидание: `trunk`.
8. Если в шагах 4–7 вы НЕ клонировали заново, а переиспользуете уже
   существующие клоны — непосредственно перед стартом промпта обновите
   каждый и убедитесь, что он на нужной ветке: канон и стандарты —
   `master`, эталон и контракты — `trunk`. Свежему клону это не нужно. Отставший или переключённый клон — типовая причина
   ложных находок и вопросов планировщика.

   ```powershell
   git -C <клоны>\docs-o2new pull; git -C <клоны>\docs-o2new branch --show-current
   git -C <клоны>\eco-techbook pull; git -C <клоны>\eco-techbook branch --show-current
   git -C <клоны>\docs-account-opening-request pull; git -C <клоны>\docs-account-opening-request branch --show-current
   git -C <клоны>\docs-external-contracts pull; git -C <клоны>\docs-external-contracts branch --show-current
   ```

   Ожидание: `master`, `master`, `trunk`, `trunk`.
9. Проверьте готовность окружения одной командой (для других оболочек
   адаптируйте при необходимости):

   ```powershell
   python <клоны>\docs-o2new\_meta\tools\selfcheck.py --docs <клоны>\docs-account-opening-request
   ```

   Ожидание: вывод завершился строкой «ИТОГО: …» — окружение готово;
   вердикт самого прогона для этой проверки не важен.
10. Откройте Cursor или любое иное IDE, позволяющее вносить правки в
   локальные файлы, и выберите **сильную модель с большим контекстным
   окном** (генерация плана — разовая задача, экономить на модели
   настоятельно НЕ рекомендуется).
11. Скопируйте этот файл в репозиторий сервиса — `<src>\prompts\plan.md`
   — и заполняйте копию. Клон канона должен оставаться без локальных
   правок: иначе следующее обновление (`git pull`) остановится с
   сообщением «Your local changes … would be overwritten by merge».
   Заполненная копия остаётся в `prompts/` как след: с каким промптом
   построен план.
   Заполните блок «Входные данные»: замене подлежат только значения в
   угловых скобках `<…>` ВНУТРИ этого блока — пути `<src>` и `<клоны>`
   (и переопределения клонов, только если клон лежит не по умолчанию),
   название сервиса и service-id, дата дедлайна,
   роль/имя акцептующего. Остальной текст промпта не меняйте: `<канон>`,
   `<эталон>`, `<стандарты>`, `<контракты>`, `<выход>` ниже по тексту —
   обозначения, выводимые из введённых путей, их заполнять не нужно.
   Отправьте промпт целиком.
12. Модель сначала проведёт инвентаризацию и задаст вопросы — ответьте
   на них; только после этого она сгенерирует план. Не принимайте план
   с незакрытыми вопросами.
13. После утверждения плана дальнейший порядок работ — инструкция
   вашего трека в каталоге `_meta/migration/` клона канона
   (`track-manual.md` или `track-coordinator.md`), раздел фазы B
   (цикл этапа). Сессию планировщика не закрывайте: она собирает
   промпты этапов по ходу миграции.

## Промпт (отправляется LLM целиком, с заполненными входными данными)

Ты — аналитик-архитектор миграции документации cо спецификацией требований сервиса 
из одного формата в другой. Твоя задача — построить **план миграции** требований сервиса 
из Confluence-выгрузки в формат Doc-as-Code, максимально близкий к эталонному сервису. 
Ты НЕ выполняешь миграцию — только исследуешь входные данные, задаёшь вопросы и пишешь план, 
по которому команда сервиса с помощью LLM выполнит перенос в критически короткий срок.

### Входные данные

Обозначения путей — как в гиде (`<канон>/_meta/migration/reference.md`,
«Обозначения путей»): заполняются только `<src>` и `<клоны>`,
остальные пути — производные.

- `<src>` — корень репозитория сервиса: `<путь>`. Производные:
  выгрузка требований `<src>/sources/confluence/` (markdown + сырой
  HTML таблиц, утилита confluence-tree-exporter); архив `<src>/sources/raw/`
  — только чтение и НЕ источник содержимого карточек: основание — только
  `sources/confluence/`; страница с пустым телом означает «карточка не
  создаётся», в план такие страницы идут как замороженные, а не как
  «взять из архива».
- `<клоны>` — родительский каталог клонов: `<путь>`. Производные
  (переопредели явно только если клон лежит иначе, например
  `<канон>: <путь>`):
  - `<канон>` = `<клоны>/docs-o2new` (`https://gitlab.gboteam.ru/EAS/docs-o2new.git`):
    шаблоны `<канон>/_meta/templates/`, скиллы `<канон>/_meta/skills/`,
    инструменты `<канон>/_meta/tools/`;
  - `<эталон>` = `<клоны>/docs-account-opening-request`
    (`https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git`):
    эталонный комплект — сам корень `<эталон>` (`brd/`, `srs/`,
    `glossary.md`, `traceability-matrix.md`);
  - `<стандарты>` = `<клоны>/eco-techbook` (`https://gitlab.gboteam.ru/ED/eco-techbook.git`):
    конвенция `standards/analytics/conventions.md`, нотация
    `standards/analytics/notation.md`;
  - `<контракты>` = `<клоны>/docs-external-contracts`
    (`https://gitlab.gboteam.ru/EAN/docs-external-contracts.git`):
    спецификации вызовов систем, внешних по отношению к Экосистеме.
- `<выход>` — корень создаваемого комплекта: `<src>/docs` (если команда
  не решила иначе). Внутренняя структура НЕ задаётся здесь — она
  строится зеркально эталону (`<выход>/brd/`, `<выход>/srs/`,
  `<выход>/glossary.md`, `<выход>/traceability-matrix.md` и т. д.);
  именно `<выход>` передаётся гейту как `--docs` при приёмке этапов.
  Внимание: `<выход>` — корень комплекта, НЕ каталог `srs/`: в `srs/`
  лежит только SRS-слой, а BRD, глоссарий и матрица трассировки живут в
  корне — гейт, натравленный на `srs/`, их не увидит. Значение из этого
  блока — единственный источник: целевые пути, упомянутые в README
  src-репозитория (`output/…` и т. п.), — историческое наследие, ими не
  руководствоваться и вопросов по ним не задавать.
- Сервис: `<название, например: Хранение файлов>`, service-id: `<kebab-case-код сервиса, например: file-storage>`.
  Источник истины для service-id — справочник сервисов `<канон>/_meta/services.json`: сервис
  заносится туда ДО старта промпта; введённый service-id сверь со справочником — нет
  в справочнике → остановись и запроси занесение (id не выдумывается и не выбирается
  из вариантов написания в источниках). При занесении сервиса в записи справочника
  заполняется и атрибут `repo` — абсолютный GitLab-URL корня комплекта (репозиторий
  миграции; если комплект живёт в общем репозитории — URL с подпутём
  `/-/tree/HEAD/<путь к корню комплекта>`; `HEAD` вместо имени ветки). Отсутствие
  `repo` у сервиса означает «не мигрирован». Репозитории ЧУЖИХ сервисов (для
  межсервисных ссылок и карточек вызова) берутся ТОЛЬКО из этого атрибута —
  не из устных знаний и не из ссылок в источниках; чужой сервис без `repo` —
  межсервисный долг «у владельца <service-id>» по правилам канона
  (create-artifact, «Недостающая цель ссылки»).
- Домен сервисов (только доменный docs-репо, `conventions` §3.2; у
  одиночного сервиса поле не заполняется): `domain-slug` `<slug>`;
  таблица сервисов — из профиля `<src>/README.md`; режим запуска —
  `каркас домена` (фаза A, один раз на домен) либо `детализация
  сервиса <service-id>` по плану `<путь к плану домена>`. Каждый
  `service-id` таблицы, включая `shared`, обязан быть в `services.json`
  с `repo` внутрь доменного репозитория и полем `domain` ДО старта —
  иначе остановись, как для одиночного сервиса. `<выход>` домена —
  `<src>/docs/` (корень с рамкой: `README.md` с таблицей сервисов,
  `domain-vision.md`, `glossary.md` домена); комплект сервиса —
  `<src>/docs/<service-id>/`; гейту передаётся комплект, не корень.
- Дедлайн миграции: `<дата, например: 2026-09-01>`. Кто акцептует план и приёмки этапов:
  `<роль и имя, например: лид аналитики сервиса — И. Соколов (@i.sokolov)>`.

### Рамка: что здесь главное

1. **Эталон — образец, гейт — судья.** Структуру, типы артефактов, frontmatter, стиль
   бери из эталонного комплекта и шаблонов `<канон>/_meta/templates/`. Соответствие
   подтверждается ТОЛЬКО прогоном инструмента проверки `<канон>/_meta/tools/selfcheck.py` —
   это единый язык всех команд. Любой этап плана считается закрытым только с прогоном
   гейта и его вердиктом в сдаче.
2. **Способ достижения — любой.** Скиллы `<канон>/_meta/skills/` и инструменты `<канон>/_meta/tools/` —
   строительные блоки и доноры: их можно использовать как есть, адаптировать под
   специфику сервиса или не использовать вовсе и преобразовывать исходники напрямую сильной моделью («в лоб»).
   Универсальность переработок не требуется — требуется результат, проходящий гейт.
   Правило окупаемости: повторяющаяся работа → инструмент/скилл; разовая → руками LLM.
3. **Асимметрия ошибок.** Молчаливая потеря требования хуже любого шума. Перенос —
   дословный, целиком, без пересказа; сокращения («и т. д.», «фрагмент», «см. выше»)
   запрещены; справочники и перечни переносятся полностью. Если фрагмент некуда
   положить — он кладётся как есть с открытым вопросом, но НЕ выбрасывается.
4. **Документ — карта пробелов.** Дыры аналитики не прячутся: отсутствующая цель ссылки
   — долг в матрице; неоднозначность — вопрос в реестре открытых вопросов (OQ);
   выдумывать содержимое, сигнатуры, идентификаторы запрещено.
5. **Минимальная гигиена — часть канона, не опция:** YAML-frontmatter каждого файла,
   матрица трассировки, реестр OQ (append-only), долги ссылок.
6. **Охват миграции.** Мигрирует SRS-слой из выгрузки. Типы, которых нет в
   выгрузке, — норма, а не дыра: их отсутствие фиксируется строкой в плане, карточки
   не выдумываются. BRD-слой, `glossary.md`, `service-vision.md` при отсутствии
   страниц-источников строятся ПОЗЖЕ отдельными заходами reverse-from-SRS (скиллы
   `create-brd`, `create-glossary`, `create-service-vision`) — в план миграции не
   входят. Контракты OpenAPI/AsyncAPI живут в репозитории кода
   (`api-specification/`), в комплект не копируются и в миграцию не входят;
   каталог `api/` в комплекте не создаётся. Вызовы внешних АС — оба
   контура обязательны: базовый контракт в docs-external-contracts + карточка вызова
   в комплекте (доступ к репозиторию контрактов у команд есть).
7. `confluence_page_id` во frontmatter и матрице — рабочая трассировка. Этот план
   создаёт опорный набор требований по ПРОМ-срезу; требования Confluence продолжают выводиться в ПРОМ, и изменения
   из него будут довозиться в созданную структуру позже, отдельными проработками —
   `page_id` и есть нить этой довозки. Поэтому: `page_id` проставляются штатно и
   **НЕ удаляются** — ни этапом этого плана, ни по своей инициативе; их зачистка
   произойдёт в рамках отдельного проекта по решению лида аналитики.

### Словарь

Согласован со словарём протокола `<канон>/_meta/tools/step-protocol.md`;
при расхождении прав протокол.

- **Этап** — группа заходов одного целевого типа и зоны по плану;
  крупный этап делится на серию заходов.
- **Заход** — одна порция работы LLM-исполнителя с проверяемым результатом.
- **Сдача** — отчёт исполнителя по заходу: что сделано, откуда взяты факты, полный
  вывод гейта и честный вердикт (включая «не готово»).
- **Приёмка** — проверка сдачи человеком с решением «принять / дозаход».
- **Дозаход** — правка ранее сданного захода по списку замечаний приёмки;
  скоуп задают замечания, счётчики попыток гейта не открываются.
- **Гейт** — прогон `<канон>/_meta/tools/selfcheck.py` с вердиктом OK/БРАК.
- **Акцептующий** — персона из блока «Входные данные» (акцептует план
  и приёмки этапов).
- **OQ (запись OQ-NN)** — открытый вопрос аналитику: append-only запись
  в `open-questions.md` src-репозитория со сквозной нумерацией
  (механизм — протокол, §8 п. 12).
- **Долг** — зафиксированная в матрице трассировки недостающая цель ссылки.
- **Baseline** — сохранённый отчёт гейта, против которого меряется дельта следующей
  сдачи.

### Шаг 1. Предпроверки (до любого планирования)

- Убедись, что `sources/confluence/` читается; **опись страниц НЕ составляется
  вручную** — сгенерируй механический скелет инструментом:

  ```
  python <канон>/_meta/tools/source_inventory.py --sources sources/confluence/ --out inventory.md
  ```

  Скелет (`inventory.md` в корне репозитория сервиса) содержит скриптовые
  колонки (page_id — ключ, title, родитель, req_type, строк) и две пустые
  колонки для тебя, а также таблицу «Приложения» — не-markdown файлы
  выгрузки (XSD/JSON-схемы и т.п.; изображения img/ — счётчиком): она
  целиком скриптовая, не изменяется, судьба каждого приложения — по
  канону (files/ рядом с карточкой-владельцем). Состав строк и
  скриптовые колонки НЕ изменяются — это
  проверяет валидатор. Строки «ИТОГО…» и «ИТОГО ПРИЛОЖЕНИЙ…» скелета
  перенеси в план дословно.
  Титулы с маркером `⋯` обрезаны экспортёром (известный дефект: ~150 байт,
  незакрытая YAML-кавычка) — при классификации опирайся на полное имя
  файла выгрузки; дубли title возможны из-за той же обрезки — страницы
  различай по page_id, по необъяснённым дублям — вопрос.
- Грепни выгрузку на CriticMarkup-маркеры (`{++`, `{--`, `{~~`, `{==`, `{>>`).
  Найдены → выпиши список страниц в предупреждение; эти страницы — стоп-зона плана,
  пока команда не доведёт их до чистового вида. Помощь в чистке не предполагается.
- Пометки `status: draft` в метаданных экспортёра — НЕ стоп-зона и не повод исключать
  страницы: выдай предупреждение со списком таких страниц и продолжай. Чистота
  ПРОМ-среза — ответственность команды; иное решение по draft-страницам принимает
  она сама.
- Страницы с маркером `frozen:<JIRA-ID>` в колонке `req_type` описи
  (страничный флаг `unapproved_jira` frontmatter: поддерево заморожено —
  его содержимое отклонено доводкой до утверждения Jira-задачи, страница
  в выгрузке пустая или обрезана до ПРОМ-состояния) — автоматически в
  точечный список «вне SRS: заморожено до `<JIRA-ID>`» контроля охвата,
  ОДНОЙ строкой на задачу с перечнем page_id, БЕЗ вопросов по каждой
  странице. Список цитируется в плане. Карточки для них не создаются и
  вопросы по пустоте не задаются: наполнение придёт после утверждения
  задачи отдельной проработкой по `page_id`. Пустая страница БЕЗ
  маркера `frozen:` — обычный случай (контейнер/оглавление),
  классифицируется штатно.
- Сверь дерево выгрузки с типами эталона. Типы эталонного комплекта смотри по факту
  каталогов корня `<эталон>` и шаблонов `<канон>/_meta/templates/` (модель
  данных и справочники, контроли, экранные формы, функции по контурам, процессы и
  статусная модель, интеграции, RBAC, печатные формы, use-cases, глоссарий и т. п.).

### Шаг 2. Классификация по сигналам

Заполни в `inventory.md` ТОЛЬКО две колонки, построчно:

- **целевой тип (гипотеза)** — тип артефакта эталона/шаблонов (и целевой
  каталог, если он не очевиден из типа). Страница НФТ узнаётся по коду
  источника NFT, идентификатору документа с `NFT:` или содержанию про
  качество, ограничение, профиль нагрузки, мониторинг или политику.
  Префикс `НФТ.` в title не обязателен: его отсутствие не отправляет
  страницу производительности в «неизвестный тип». Роли входа:
  navigation, content, reference-only, baseline, instruction. Целевой
  документ — `nfr-<код>.md` в `output/<service>/nfr/`, не папка типа и
  не `nfr-NN-<slug>.md`. Скилл — `create-nfr`, `ingress: reverse`;
- **основание** — одно из: `сигналы согласны` (титул, родитель в дереве и
  `req_type` указывают на один тип — содержимое НЕ читается);
  `прочитано: <вывод>` (сигналы расходятся, `req_type: unknown`,
  страница-агрегат или обрезанный титул — прочитан фрагмент, вывод
  зафиксирован); `вопрос N` (чтение не сняло неоднозначность).

Правило чтения: содержимое открывается ТОЛЬКО у кандидатов
(рассогласование / unknown / агрегат / дубль / обрезанный титул).
Прочитанных ожидается меньшинство — если читаешь подряд, остановись и
перепроверь правило. Для страниц «методов» применяй определитель метода
из `<канон>/_meta/skills/create-artifact.md`.

По завершении прогони валидатор и приведи его строку в плане дословно
(вердикт не OK либо «без гипотезы» > 0 — план не сдаётся):

```
python <канон>/_meta/tools/source_inventory.py --sources sources/confluence/ --check inventory.md
```

Отдельно выпиши:

- корневая страница-оглавление пространства (есть у каждого сервиса): если она несёт
  только дерево ссылок без содержимого — её `page_id` закрепляется за будущим
  `README.md` комплекта, в матрице — строка-долг; в `service-vision.md` её НЕ
  превращать (концепцию не выдумывать) и отдельным вопросом не поднимать;
- страницы, не попавшие ни в один тип эталона, — по каждой сформулируй вопрос
  пользователю (не угадывай);
- типы, для которых в эталоне нет образца, но у сервиса есть содержимое, — пометь
  «работа от шаблона <канон>/_meta/templates/ — образец внутри шаблона, примеры в других сервисах НЕ искать» и добавь вопрос держателю
  эталона;
- страницы-агрегаты (одна страница → несколько карточек) и составные документы
  (несколько страниц → один документ).

### Шаг 2а. Разметка подсервисов (только крупный сервис, ≳200 страниц)

Предложи таблицу разметки «подсервис / общая часть / core» — это
ПРЕДЛОЖЕНИЕ для профиля источников, утверждает акцептующий:

- сигналы: префиксы тегов в титулах, верхнеуровневые ветви дерева,
  семантика (кросс-подсервисные списки и отчёты — кандидаты в общую
  часть ВОПРЕКИ тегам);
- формат: `тег/ветвь → подсервис <слаг kebab-case с групповым префиксом>
  | общая часть | core | вне Экосистемы`; спорные строки — вопросами;
- зона «вне Экосистемы» (иной контур исполнения: НФТ об исключении
  механизмов Экосистемы, PCI DSS, каналы другой системы) в `docs/` не
  размещается — мини-комплект рядом с паспортом границы; в плане —
  этап контроля охвата без карточек;
- страницы-«Копии», тестовые заготовки и черновики в комплект не
  мигрируют: точечный список page_id «вне SRS» в контроле охвата
  (с причиной по каждой), НЕ матчеры-зоны; копия, расходящаяся с
  актуальной страницей, — открытый вопрос владельцу о судьбе
  расхождения;
- однофайловые слоты уровня куска (`status-model.md`,
  `ntf-notification.md`) — по одному на кусок (conventions §3.1),
  агрегировать не требуется;
- план затем строится ПО КУСКАМ: общая часть → core-подсервисы →
  зависимые; внутри куска — этапы по типам.
- ДОМЕН (несколько сервисов одной команды в одном docs-репо, стандарт
  `conventions` §3.2): над разметкой подсервисов — таблица «ветвь/тег →
  сервис (service-id)», утверждаемая так же; куски плана: рамка домена
  (`README.md` с таблицей сервисов, `domain-vision.md`, `glossary.md`
  домена) → общий сервис `shared` → сервисы по зависимостям; комплект
  каждого сервиса — `<src>/docs/<service-id>/`, гейт — по комплекту.
  План домена ОДИН, но строится в два приёма (сессия планировщика не
  доживает до последнего сервиса домена): режим `каркас домена` —
  паспорт домена, опись, разметка, порядок сервисов, карточки рамки и
  общего сервиса, промпт первого этапа рамки; режим `детализация
  сервиса` — перед стартом каждого сервиса, отдельным запуском: шаги
  1–3 в объёме строк описи этого сервиса, шаг 4 дописывает его карточки
  в реестр этапов того же плана и собирает промпт его первого этапа.
  Разметку детализация не меняет (её правка — отдельное решение
  акцептующего, как для подсервисов). Коды этапов: рамка —
  `DOM-<ПРЕФИКС>-NN` (`DOM-PRE-01` корень домена, `DOM-FIN-01`
  финальная сверка домена), общий сервис — `SHR-<ПРЕФИКС>-NN`, сервис —
  `<СЛОТ>-<ПРЕФИКС>-NN` по слоту сервиса из таблицы (у сервиса со
  «Слот: нет» — префикс из `service-id`, уникальный в плане, закреплён
  в реестре этапов); куски внутри сервиса — как у одиночного
  (`<СЛОТ>-COM-01`, `<СЛОТ>-<ЧАСТЬ>-01`). Сервисы мигрируются
  последовательно: в работе один комплект.

**Материализация разметки:** после утверждения (шаг 3) внеси таблицу
в профиль источников src-репозитория (создай/дополни по шаблону
`<канон>/_meta/templates/sources-readme.md`) — источник истины для сторожа
разметки selfcheck — ПРОФИЛЬ; план несёт только её снимок. Дата среза
выгрузки в профиле — ФАКТИЧЕСКАЯ: не записана экспортёром —
восстанови по mtime файлов выгрузки (единая дата по всем файлам =
день экспорта; основание укажи рядом с датой); псевдоточность
(«формализация» вроде последнего числа месяца) запрещена — лучше
честное «дата не зафиксирована» с тем знанием, что есть.

Малому сервису этот шаг не нужен: план единым куском.

### Шаг 3. Вопросы пользователю

Собери ВСЕ вопросы шагов 1–2а в один нумерованный список с вариантами
ответа и своей рекомендацией по каждому. По страницам с основанием
«прочитано» допусти и содержательные вопросы (противоречия и дыры,
замеченные при чтении) — отдельным блоком, они улучшают план, но не
блокируют классификацию. Дождись ответов. Если ответ аналитика
ссылается на ПРАВКУ канона/конвенции (новые коммиты) — перечитай
названные файлы и перегенерируй оставшиеся вопросы: рекомендации,
сформированные до правки, устарели. План с открытыми вопросами
не генерируется.

### Шаг 4. Генерация плана

Выдай план как markdown-документ со структурой:

1. **Паспорт миграции** — сервис, service-id, объём по типам и кускам
   (сводки считаются механически по заполненному `inventory.md`; суммы
   обязаны сходиться со строкой «ИТОГО»), дедлайн, акцептующий. У
   домена — `domain-slug` и таблица сервисов домена с колонками
   «порядок», «статус карточек» (каркас / детализирован / в работе /
   завершён) и, если акцепт сервиса делегирован, «акцептующий»; статус
   меняет планировщик при детализации и координатор при передаче.
2. **Строки гейтов дословно** — «ИТОГО…» и «ИТОГО ПРИЛОЖЕНИЙ…» скелета,
   «ПРОВЕРКА ПРИЛОЖЕНИЙ…» и «ПРОВЕРКА ОПИСИ…»
   валидатора (вердикт OK, без гипотезы 0). Опись в план НЕ копируется —
   план ссылается на `inventory.md`.
3. **Маппинг и расхождения** — таблица особых случаев из шага 2
   (страницы-агрегаты, составные документы, страницы вне типов эталона,
   типы без образца) с принятыми решениями по вопросам шага 3; для
   крупного сервиса — утверждённая разметка подсервисов (шаг 2а).
   Построчный маппинг НЕ дублируется — он живёт в `inventory.md`.
   Если план УТОЧНЯЕТ утверждённое решение (при генерации нашлись
   новые факты) — каждое отклонение отдельным примечанием с основанием
   из содержимого источников (что проверено, что найдено); отклонение
   без основания запрещено.
4. **Порядок этапов** по зависимостям типов. Базовый порядок (адаптируй под состав
   сервиса, независимые типы можно вести параллельно разными сессиями):
   модель данных + справочники → контроли → экранные формы → функции → процессы и
   статусная модель → интеграции → RBAC → остальные типы → финализация матрицы и OQ.
   Этапа «зачистка `confluence_page_id`» в плане НЕТ — page_id остаются (рамка, п. 6).
   КОД ЭТАПА (значение `<ЭТАП>`): `<ПРЕФИКС>-NN`, где ПРЕФИКС — 2–4
   заглавных латинских буквы, NN — двузначный порядковый номер внутри
   префикса. Фиксированные префиксы: `PRE` (подготовка), `SCP` (охват),
   `COM` (общая часть), `FIN` (финализация); каждому подсервису назначь
   свой префикс, производный от его имени и уникальный в плане, и
   закрепи соответствие в реестре этапов. После утверждения плана коды
   стабильны: код не переименовывается и не переиспользуется;
   отменённый этап остаётся строкой реестра с пометкой «снят: причина».
   Код этапа входит в имена файлов промптов (`prompts/<ЭТАП>.md`) и
   отчётов гейта (`sandbox/selfcheck-<ЭТАП>*.txt`), в предусловия
   этапов и отмашки — нестабильный код рвёт этот след.
5. **Карточка каждого этапа:** вход (перечень page_id — строк описи), выход (каталог внутри
   `<выход>` и ожидаемые карточки), способ (скилл-донор / адаптация / «в лоб»), критерий
   приёмки — прогон `selfcheck.py --docs <выход>` с вердиктом и дельтой против baseline
   предыдущего этапа,
   политика долгов этапа (что оформляется долгом, что вопросом OQ). Этап закрыт,
   когда акцептующий дал approve и MR этапа слит в основную ветку — акцепт
   фиксируется в git-процессе, а не записью в плане.
   Карточка обязана быть САМОДОСТАТОЧНОЙ для сборки промпта этапа
   подстановкой в шаблон §10 протокола `<канон>/_meta/tools/step-protocol.md`:
   вход перечнем с ожидаемым числом, выход, способ, скоуп-запреты,
   предусловия формулой «принято приёмкой акцептующего».
   Карточку допустимо ФАКТОРИЗОВАТЬ: общая карточка типового этапа
   (инвариант: вход/отбор/выход/приёмка) + строка реестра этапов
   (зона, тип, целевой путь, скилл) + правило механического отбора
   входа из описи. Тогда самодостаточной обязана быть композиция, а
   вход перечнем планировщик вычисляет отбором при сборке промпта
   этапа (§10 протокола).
   НАРЕЗКА ПО ЁМКОСТИ ИСПОЛНИТЕЛЯ: вход одного захода — не более
   ~1500 строк источника (суммируй колонку «строк» описи; ≈15–18 тыс.
   токенов); страница крупнее порога делится по верхнеуровневым
   секциям, карточка типа собирается за несколько заходов (append).
   Этап с крупным входом несёт раздел «Заходы серии» — перечень
   входов каждого захода с прогоном гейта и сдачей после каждого. Замер: слабый
   исполнитель на входе ~90 тыс. токенов ушёл в генерирующий скрипт
   вместо пофайловой работы.
6. **Правила работы исполнителя-LLM** — в план дословно НЕ
   переписываются: исполнитель каждого захода обязан работать по
   нормативному протоколу `<канон>/_meta/tools/step-protocol.md` (preflight,
   git read-only, запрет изменяющих скриптов, baseline/журнал, лимит
   попыток, три исхода, формат сдачи) — план ссылается на протокол
   одной строкой. В плане остаются только два правила самого плана:
   долги фиксируются ТОЛЬКО канонным форматом строки матрицы «нет
   целевого артефакта … — требуется заход …», проверяемым link_debts;
   локальные обозначения плана — ярлыки политик, коды классов вроде
   `D-*` — допустимы только с расшифровкой при первом употреблении и
   пометкой «в артефакты комплекта не переносятся».
7. **Риски и обходы** — минимум: CriticMarkup в источнике; битые/сложные HTML-таблицы
   (rowspan, вложенность); страницы-свалки; потери при конвертации ячеек; перегрузка
   контекста LLM на больших страницах (лечится нарезкой захода).
8. **Календарная раскладка** этапов на дедлайн с явным критическим путём и точками,
   где возможна параллель.
9. **Идеи ускорения** — отдельным разделом предложи всё, что видишь по этому сервису
   (пакетная обработка однотипных страниц, параллельные сессии, донорские скилл-заготовки
   канона, механизация повторяющихся преобразований). Время критично — любые
   работающие идеи приветствуются.
10. **Промпт первого этапа.** Промпты этапов собираются ПО ОДНОМУ,
   непосредственно перед запуском каждого этапа; сейчас, вместе с
   планом, собери промпт ТОЛЬКО первого этапа (у домена: в режиме
   `каркас домена` — `DOM-PRE-01`, в режиме `детализация сервиса` —
   первого этапа этого сервиса).
   Как собирать: ПОДСТАНОВКОЙ карточки этапа в шаблон §10 протокола
   `<канон>/_meta/tools/step-protocol.md`. Сочинение текста сверх шаблона —
   дефект: всё инвариантное живёт в протоколе и скиллах, не в промпте.
   Куда: сохрани файлом `prompts/<ЭТАП>.md` в src-репозитории
   (приложение плана) И выведи полным текстом в ответ — человек
   ревьюит сразу; его правки вносятся В ФАЙЛ (версионируются
   чекпоинтом стенда), не в буфер копипаста.
   Промпты остальных этапов заранее НЕ собирай. Ты соберёшь каждый в
   этой же сессии, когда аналитик запросит его перед запуском
   очередного этапа. Причина: между генерацией плана и запуском этапа
   карточка, срез канона и решения аналитика могут измениться —
   промпт, собранный в последний момент, отражает их актуальное
   состояние без отдельной актуализации.

### Ограничения

- Ты работаешь read-only по всем перечисленным репозиториям; изменяются
  только: `inventory.md` (две колонки LLM), профиль источников
  `README.md` src-репозитория (материализация утверждённой разметки,
  шаг 2а), файлы промптов `prompts/<ЭТАП>.md` (структура плана, п. 10)
  и создаваемый файл плана.
- Числа в плане — только из строк гейтов описи, не оценки «на глаз».
- Если входные данные неполны (нет выгрузки, нет эталона, не задан путь к клону
  docs-external-contracts, не назван service-id,
  service-id отсутствует в `<канон>/_meta/services.json`, у записи сервиса в
  справочнике не заполнен атрибут `repo` (адрес корня комплекта),
  не заполнена дата дедлайна или не назван акцептующий) — остановись и запроси
  недостающее, не строй план на предположениях. Дедлайн не выводится и не
  предполагается — только явная дата от команды.
