# Порядок действий: трек без координатора

Эта инструкция описывает порядок действий команды, которая выполняет
миграцию требований сервиса по плану миграции без ИИ-координатора:
акцептующий сам принимает сдачи и управляет процессом.
Выбор трека — `README.md` этого каталога; нормы — гид
(`reference.md`) и протокол (`_meta/tools/step-protocol.md`), при
расхождении правы они. Обозначения путей (`<src>`, `<клоны>`,
`<канон>` и другие) — гид, раздел «Обозначения путей».

## Шаг 0 — подготовительный

1. Назначьте **акцептующего** — лида-аналитика сервиса (см.
   `prompt-plan.md`, «Входные данные»): приёмки, коммиты, push,
   отмашки; все необратимые действия — только он.
2. Проверьте комплект выдачи: ссылки на канон docs-o2new (в нём
   каталог `_meta/migration/` с этой инструкцией и промптами) и на
   стандарты eco-techbook; оба — основная ветка `master`. Копия
   референс-стенда `src-business-cards` передаётся владельцем канона по
   запросу.

## Какие документы определяют порядок каждой фазы

Порядок фазы A (подготовка) определён в файле `prompt-plan.md`: его
раздел «Как пользоваться» содержит команды подготовки окружения (с
ветками обкатки) и проверки их выполнения. Порядок фазы B (цикл этапа)
определён в этой инструкции и в протоколе `step-protocol.md` (§8 —
формат сдачи, §10 — промпты этапов, §11 — роли сессий и отмашка).
Порядок обратной связи определён в гиде (`reference.md`), раздел
«Обратная связь».

## Фаза A — подготовка (один раз на сервис)

1. **Репозиторий сервиса** (`<src>`): структура каталогов — гид,
   раздел «Структура репозитория сервиса». Референс структуры — стенд
   `src-business-cards`.
2. **Выгрузка Confluence** — утилитой `confluence-tree-exporter`
   (порядок и проверки — `prompt-plan.md`, «Как пользоваться»,
   пп. 1–3); дерево страниц зеркалом в `<src>/sources/confluence/`;
   каждая страница обязана нести `confluence_page_id` (гейт сверяет по
   нему).
3. **Опись** — файл `<src>/inventory.md` (генерируется инструментом
   `_meta/tools/source_inventory.py`): page_id, название, родитель,
   сигналы типа, строки, целевой тип. Генерирует и заполняет
   ПЛАНИРОВЩИК внутри план-сессии (шаги 1–2 промпта генерации плана);
   ваша роль — ответить на его вопросы. Спорные целевые типы
   решает аналитик правкой описи (прецедент: «Процедура сохранения» в
   разделе экранных форм сервиса Корпкарт — это `function`, не
   экранная форма).
4. **Профиль источников** — `<src>/README.md`: маршрутизация страниц
   по зонам, легенда каталогов, строка «Срез канона». Материализует
   планировщик после утверждения вами разметки (шаг 2а промпта
   генерации плана).
5. **Срез канона** — строка профиля с хэшем принятого HEAD канона;
   гейт останавливает работу при расхождении с HEAD. Внесение
   изменений в канон — НЕ ваша ответственность, но обновление строки
   среза после обновления клона канона — действие вашего акцептующего
   (`_meta/tools/accept_canon.py`, §1 протокола).
6. **План этапов** — строит агент-планировщик по `prompt-plan.md`,
   человек ревьюит. «Карточка этапа» в плане факторизована, отдельного
   документа на этап НЕТ: общая карточка типового этапа
   (вход/отбор/выход/приёмка — инвариант, один на все этапы) + строка
   реестра этапов (зона, тип, целевой путь, скилл) + вход перечнем
   страниц, который ВЫЧИСЛЯЕТСЯ механическим отбором из описи (зона +
   целевой тип) при сборке промпта. Нарезка этапа на заходы — по
   ёмкости, вход захода ≤ ~1500 строк источника (§10 протокола) —
   защита от переполнения контекста агента-исполнителя.
   На этой фазе создаются план, реестр этапов и промпт ПЕРВОГО этапа;
   промпты остальных этапов — по одному, перед каждым этапом.
7. **Домен сервисов** (`conventions` §3.2) — фаза A строит каркас
   домена (профиль с таблицей сервисов и разметкой «ветвь → сервис →
   зона», записи каталога на все комплекты, план с карточками `DOM-*`
   и `SHR-*`, промпт `DOM-PRE-01`); карточки каждого сервиса
   дописываются в тот же план перед его стартом запуском планировщика в
   режиме «детализация сервиса». Выход: `<src>/docs/` — корень домена
   с рамкой, `<src>/docs/<service-id>/` — комплекты; сервисы мигрируются
   последовательно (рамка → `shared` → сервисы по плану), гейт — по
   комплекту в работе; состояние, журнал, `open-questions.md` и
   `feedback.md` — одни на домен.

Проверка результата фазы A — в `<src>` существуют: файл плана,
`inventory.md` с вердиктом валидатора OK, `README.md` со строкой
«Срез канона», `prompts/<первый этап>.md`.

## Фаза B — цикл этапа (повторяется, пока план не исчерпан)

1. **Промпт этапа**: планировщик (продолжение его сессии, §11
   протокола) собирает промпт ОДНОГО этапа в шаблон §10 из композиции
   «общая карточка типового этапа × строка реестра этапов × вход,
   вычисленный отбором из описи» → файл `prompts/<ЭТАП>.md`; аналитик
   ревьюит файл. Инвариант: на момент запуска промпт обязан быть
   актуален — соответствовать карточке, текущему срезу канона и
   решениям аналитика, принятым после сборки (решения вносятся правкой
   файла промпта: аналитиком руками или планировщиком по его
   поручению). Собирать промпты впрок допустимо, но тогда актуализация
   перед запуском обязательна; сборка непосредственно перед этапом
   даёт актуальность бесплатно.
2. **Запуск**: свежая сессия исполнителя, в сессию — указание на файл
   промпта, не копипаст (§10 протокола). Один промпт обслуживает все
   заходы этапа.
3. **Заходы**: после каждого — гейт и сдача по §8 протокола
   (13 пунктов); приёмку сдачи делает аналитик; отмашка следующего
   захода — стандартная формула §11, её пишет сам акцептующий. Вопросы
   к источнику агент пишет в `open-questions.md` (append-only / только
   добавление, сквозная нумерация OQ-NN), не решает сам.
4. **Финал этапа**: сдача последнего захода = сдача этапа; приёмка,
   коммит человеком и отправка `git -C <src> push origin master` (после
   каждого коммита, не только в конце этапа); следующий этап — снова с
   шага 1. Комплект ведётся в ветке `master` репозитория сервиса,
   отдельная ветка под миграцию не создаётся.

## Постоянные правила и типовые ошибки

Общие для обоих треков — в гиде (`reference.md`), разделы
«Постоянные правила» и «Типовые ошибки»; прочитайте их до старта.
Отдельно, до первого запуска гейта: правило «требование прибора,
противоречащее протоколу, — отказ прибора, под него не подстраиваются»
(там же, «Постоянные правила») и раздел «Откат участка к принятому
коммиту» — что делать, если следы обхода уже появились.

## Первые три действия

1. Назначить акцептующего.
2. Подготовить окружение и выгрузку (`prompt-plan.md`, «Как
   пользоваться», пп. 0–9).
3. Открыть сессию планировщика с промптом плана — дальше фаза A,
   затем цикл фазы B.
