# Задание: разбор реестра замечаний команды ОНБ-В к методологии

Дата постановки: 2026-10-15. Заказчик — владелец пилота Doc-as-Code. Исполнитель — агент
(облачная или локальная сессия). Все входы лежат в этом каталоге, сеть и клоны репозиториев не
нужны и недоступны.

## Входы

- `../Замечания команды ОНБ-В к методологии — methodology-defect-fixes (29.09.2026, получено 15.10).md`
  — реестр коллег: 42 класса замечаний (ЗК-01…ЗК-42) и 39 предложений (ПР-01…ПР-39) со
  ссылками «файл:строка» на версии от 29.09.2026.
- `canon-2026-09-29/`, `techbook-2026-09-29/`, `eco-kb-2026-09-29/` — файлы, на которые
  ссылается реестр, в версиях на 29.09.2026 (ревизии в `MANIFEST.md`). Ссылки «файл:строка»
  реестра указывают на ЭТИ версии; номера строк проверены по пяти точкам, совпадают.
- `team-configs-2026-09-29/`, `team-configs-current/` — регламент паспорта репозитория
  и схемы (ЗК-33, ЗК-34).
- `canon-current/`, `techbook-current/`, `eco-kb-current/` — те же файлы на текущих срезах
  (канон `12ee0e0` от 15.10, техбук `1325b48`, eco-kb `origin/master`).
- `src-onb-v/` — репозиторий команды ОНБ-В как есть (без выгрузки Confluence): комплект в
  корне (brd/, srs/, glossary, service-vision, traceability-matrix, README), `sources/README.md`
  (профиль), `open-questions.md` (38 вопросов), `sandbox/gate/E1…E16` (журналы гейта по этапам),
  `sandbox/review/` (ревью 08.09), `sandbox/normalized/`. Каталога `prompts/`, журналов
  координации и файла плана миграции в репозитории нет.
- `registry.md` — реестр судьбы замечаний: заполняется по ходу работ (см. ниже).

## Контекст, который нужно учитывать (ограничения заказчика)

- **О1. Реестр коллег — не источник истины.** У автора может быть своя концепция, неполное
  понимание принципов канона или целей. Причина замечания — либо наша недоработка, либо
  несовпадение взглядов, либо дефект исполнения на стороне команды. По каждому классу нужно
  назвать, что это, с обоснованием по текстам канона.
- **О2. Реестр действий.** Каждому замечанию и предложению присвоен идентификатор
  (ЗК-NN, ПР-NN) в `registry.md`; все оценки, решения и позже коммиты исправлений пишутся туда,
  чтобы в конце собрать отчёт «замечание → как исправлено → коммит».
- **О3. Условия работы команды.** Команда шла по плану миграции версии 1, без координатора.
  Модель исполнителя — по их словам GLM 5.3 (в реестре: «хватает, если работает контроль»);
  соблюдались ли рекомендации канона о силе модели — неизвестно. Часть замечаний может быть
  следствием слабой модели или устаревшего плана, а не методологии. Комплект ОНБ-В небольшой:
  19 страниц выгрузки, 10 страниц требований, около 37 карточек (заказчик считал его большим —
  это стоит отметить).
- **Принципы канона, против которых сверять замечания:** асимметрия ошибок (молчаливая потеря
  требования хуже лишнего вопроса или шума); один нормативный дом у факта, остальные —
  потребители; дословность переноса; открытый вопрос вместо выдумки; реестр структурных фактов
  со сторожем; прибор (утилиты `_meta/tools`) живёт в репозитории прибора с тестами, в каноне —
  копии; стандарты ЭКО (техбук) выше канона миграции, канон выше шаблонов, образец в шаблоне —
  не норма (это утверждение само проверить: записано ли оно где-то, см. ЗК-09/ПР-13).

## Что сделать

### A. План исправления (основной результат)

Файл `plan.md`. Для каждого класса ЗК-NN:

1. **Локализация на 29.09**: подтвердить или опровергнуть ссылку коллег (цитата 1–2 строки из
   файла среза 29.09).
2. **Состояние сейчас**: исправлено ли на текущем срезе (цитата из `*-current/`), частично,
   или не исправлено. Если исправлено — чем (по тексту, без догадок о коммитах).
3. **Оценка обоснованности** (О1): наша недоработка / несовпадение концепции / дефект
   исполнения команды (модель, план v1, нет координатора) / смешанное. Обоснование по текстам.
4. **Критичность** для пилота по шкале: К1 — теряются требования или ломается гейт
   (асимметрия ошибок); К2 — ухудшает качество комплектов систематически; К3 — неудобство или
   косметика; К0 — не замечание к методологии.
5. **Сложность исправления**: С1 — текст одного дома канона; С2 — несколько домов и/или
   шаблоны + скиллы (структурное изменение, нужен реестр фактов); С3 — прибор (утилита +
   тесты + копия) ; С4 — стандарт ЭКО (техбук, MR другой команде) или правила репозитория;
   что тянет за собой (какие файлы/дома, какие комплекты уже сделаны по старому правилу).
6. **Рекомендация**: принять / принять частично (как именно) / отклонить (почему) /
   уже исправлено / неясно.

Затем сводка: очередь исправлений, упорядоченная по критичности, сгруппированная по
предложениям ПР-NN (одно предложение закрывает несколько классов) и по домам (техбук, канон,
шаблоны/скиллы, прибор, правила репозитория). Отдельно — предложения, которые противоречат
принципам канона (например, ПР-01 «перестать браковать карточку, чья страница вне выгрузки»
против асимметрии ошибок) с аргументацией.

### B. Неясные замечания

Раздел `plan.md` «Требуют уточнения»: классы, где суть не ясна или ссылка не подтверждается,
с конкретным вопросом автору (один вопрос на класс, формулировка для передачи коллеге).

### C. Корневые причины

Раздел `plan.md` «Корневые причины»: группировка классов по причинам более высокого уровня
(например: нет записанного старшинства правил; шаблоны несут образцы, воспринимаемые как
норма; проверки заявлены, но не внедрены; план v1 без координатора; нет правила «источник
молчит»; дом факта размыт по GitLab-ссылкам и локальным файлам). Для каждой — какие классы
закрывает, что даст её устранение, оценка «устранить / смягчить».

### Правила оформления

- Русский язык, терминология канона. Цитаты короткие, с путём файла и номером строки.
- `registry.md`: у каждого ЗК-NN заполнить колонки Статус (РАЗОБРАНО / УЖЕ ИСПРАВЛЕНО /
  НЕЯСНО), Критичность, Сложность, Наша оценка причины, Решение (рекомендация). У ПР-NN —
  Статус (ПРИНЯТЬ / ЧАСТИЧНО / ОТКЛОНИТЬ / УЖЕ ЕСТЬ / НЕЯСНО) и краткое решение. Коммиты
  исправлений добавит владелец позже.
- Не править файлы входов. Не выдумывать содержимое файлов, которых нет в пакете: если для
  оценки нужен файл вне пакета — записать это в раздел «Не хватает входов».
- Результат: `plan.md`, заполненный `registry.md`, при необходимости `questions.md` (вопросы
  автору реестра одним списком для передачи).
