# Пакет решений на утверждение: методология doc-as-code (ядро скиллов)

Подготовил: Сень А. Дата: 02.08.2026.

**Контекст.** В рамках подготовки пилота проведён полный аудит методологического
комплекта `_meta` (репозиторий docs-o2new): три независимых проверки по слоям
(правила / шаблоны / скиллы) плюс механические проверки ссылок. **ОСНОВНОЕ:** Найденные дефекты
исправлены восемью волнами правок в ветках `meta/*` — каждая волна отдельным
коммитом, всё пройдет стандартный путь MR → ревью → merge. Ниже — решения,
требующие утверждения (№ 1–2), решения, принятые в рамках переработки, чтобы не тормозить процесс, 
и направляемые для утверждения списком (№ 3), и рабочие решения для
сведения (№ 4).

## 1. Уровень представления модели данных в SRS (главное решение)

**Сегодня в `_meta`:** модель данных SRS ведётся на физическом уровне — карточка
сущности содержит таблицу БД, физические имена и типы колонок; стабильный
идентификатор атрибута — физическое имя колонки; в модель включаются только
физически хранимые атрибуты; при восстановлении модель строится из кода
(Liquibase-миграции, JPA-классы).

**Предлагаемое решение** (соответствует задаче 1.6 плана пилота):

> Разделить два вопроса. **Источник восстановления** для существующего сервиса —
> код допустим (для живой системы код точнее устаревшего Confluence; это факты
> о том, «что фактически хранится»). **Уровень представления в SRS** — только
> логический: сущности и атрибуты с бизнес-именами; физическая реализация
> (таблицы, имена и типы колонок, стратегия наследования) — зона разработки;
> физические имена сохраняются как атрибут прослеживаемости, не как канон.

**Обоснование:**

1. **Понятие дефекта.** Дефект — расхождение реализации с требованием. Если
   модель данных SRS выводится из кода и кодом же определяется, реализация
   становится эталоном самой себя: дефект «код не соответствует аналитике по
   данным» невозможно даже сформулировать.
2. **Свобода реализации.** Одна логическая модель имеет несколько корректных
   физических воплощений (например, наследование в реляционной БД — минимум три стратегии).
   Выбор — инженерная оптимизация разработчика; физика в SRS либо отнимает эту
   свободу, либо делает SRS ложным.
3. **Действующая норма управления (до перехода на API First, как минимум).** См. «Правила оформления аналитики ДБО»:
   описание аналитики — на логическом уровне, без привязки к реализации, везде,
   где возможно. Физическая модель в SRS противоречит этому принципу.
4. **Хрупкость ссылок.** Пока стабильный ID атрибута — имя колонки БД, любой
   рефакторинг схемы рвёт ссылки по всей документации (либо запрещает
   рефакторинг). Логический якорь (бизнес-имя) эту зависимость снимает.
5. **Полнота.** Правило «только физически хранимые атрибуты» лишает места в
   модели вводимые и вычисляемые реквизиты — их контролям не к чему
   трассироваться (пример: контроль формата индекса при хранении адреса одной
   строкой).
6. **API First.** Физика — за контрактом; аналитик и потребители работают с
   логическим уровнем и контрактами.

**Что меняется при принятии:** шаблон модели данных (бизнес-имена — канон,
физимя — колонка прослеживаемости; допускаются вводимые/вычисляемые реквизиты),
правило стабильного ID атрибута, порядок reverse в скилле (код — источник фактов,
представление — логическое). Эскиз переработанного шаблона и пример «как есть /
как будет» на одной сущности o2plus готовится как приложение к решению.

**Временная мера уже действует:** в конвенции внесено помеченное исключение
(reverse модели данных и RBAC из кода — допустим до этого решения); до принятия
решения массовая генерация моделей данных для новых сервисов пилота не
запускается.

## 2. Критерий завершения пилота

Правила ревью GitLab (approval) сегодня определены «на пилоте …, после пилота …»
без определения конца пилота. Предлагаемый критерий — (из черновика плана пилота)
(п. 6.8, Приложение 2, распределение ролей):

> Пилот завершён, когда одновременно: (1) все пилотные сервисы получили вердикт
> «готов к переносу в GitLab» и слиты в master; (2) метрика качества достигнута:
> менее 5 % файлов требуют критических правок; (3) руководитель управления
> утвердил итоговый отчёт пилота. Переход к целевым approval-правилам — тем же
> решением руководителя.

## 4. Рабочие решения — для сведения (действуют в ветках, возражения — до merge)

- **Статус документа вычисляется из git:** акцептован = MR прошёл approve и слит
  в master; поле статуса и статусные словари в документах не вводятся. Гейт:
  MR с открытыми вопросами по затронутым документам не сливается.
- **Источник связей трассировки — тела документов** (ссылка по месту
  использования); матрица — единственный реестр, производный от тел;
  расхождение — дефект матрицы.
- **Единая нотация** (новый файл правил): присваивание `=` / сравнение `==`,
  дисциплина стрелок, закрытый словарь UI-типов полей, «чистота условия»
  контролей, правило кавычек «один смысл на позицию», единое правило широких
  колонок таблиц.
- **Гигиена комплекта:** починено ~40 битых ссылок нормативного слоя; примеры
  шаблонов приведены к правилам собственных файлов; скиллы освобождены от
  привязки к конкретному сервису (предпосылка тиражирования на пилотные
  сервисы); устранены дубли норм («правило — в одном месте, остальное — ссылки»).

## 5. Межсервисная адресация и каталог сервисов (дополнение от 04.08.2026)

До расселения сервисов по репозиториям нужно зафиксировать, как сервисы
находят и адресуют друг друга: после расселения смена этих правил потребует
скоординированной правки всех команд (класс «потом почти неремонтируемо»).
Проработано предложение со сквозным примером на реальных сервисах
(«Каталог сервисов и межсервисная адресация» + «…— пример»); аналитический
уровень закрыт, на утверждение выносятся три вопроса организационного уровня:

**5.1. Репозиторий-хаб (требует решения).** Завести единый репозиторий
«контрактного хаба»: таблица-каталог пилотных сервисов + публикуемые CI-шагом
спецификации и карточки (устройство — по образцу docs-external-integrations).
Физический выбор GitLab-группы — совместно с DevOps.

**5.2. Роль «владелец платформенной документации» (требует решения).**
Платформенные функции (проверка подписи, доступность функций, онбординг)
сегодня описываются заглушками в каждом сервисе-потребителе с разными ID —
дубли растут с числом сервисов. Предлагается базовый реестр платформенных
функций с глобальными ID (наполняют команды платформы) + локальные
usage-карточки в сервисах. Нужна роль владельца: кто отвечает за базовый
реестр и кто генерирует его первичное наполнение, если платформенных
постановок не существует (reverse из Confluence платформы / заглушки
с закреплённым владельцем).

**5.3. Для сведения — правила адресации приняты на рабочем уровне**
(возражения — до старта обкатки): ссылка на чужой сервис всегда двухзвенная
(локальная карточка потребителя + стабильный адрес контракта в хабе; прямые
ссылки в чужой docs/-комплект запрещены); публикация версий срезами с
diff-отчётом; CI-гейт — срез не удаляется, пока на него есть фиксации
потребителей; карточка поставщика — на операцию; регистрация потребителя —
самообслуживанием (строку вносит потребитель, поставщик уведомляется — как
действующие обратные ссылки в Confluence).
