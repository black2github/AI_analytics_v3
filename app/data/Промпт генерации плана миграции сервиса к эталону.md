# Промпт генерации плана миграции сервиса к эталону

Универсальный промпт для команд сервисов Экосистемы (ДБО юрлиц). Версия 1 (2026-08-20), обкатка — на
первых пилотных сервисах; промпт будет уточняться по инсайтам обкатки.

## Как пользоваться (инструкция команде сервиса)

0. Подготовьте окружение:
   - git настроен (`user.name`, `user.email`) — авторство коммитов миграции должно
     быть персональным; акцепт этапов при этом фиксируется НЕ локальными данными git,
     а approve и слиянием MR в основную ветку (статус вычисляется из git);
   - Python 3 доступен в PATH — инструмент проверки `_meta/tools/selfcheck.py` из
     репозитория канона работает на стандартной библиотеке.
1. Подготовьте репозиторий сервиса (src-<сервис>) с каталогом `confluence/` — полной выгрузкой
   ПРОМ-среза требований сервиса утилитой confluence-tree-exporter.
   Выгрузка должна быть БЕЗ CriticMarkup-разметки; если разметка есть — сначала доведите
   аналитику до чистового вида, это ваша зона ответственности.
2. Склонируйте репозиторий канона `https://gitlab.gboteam.ru/EAN/docs-o2new.git`
   (единый для всех команд) — канон лежит в его каталоге `_meta/`: шаблоны
   `_meta/templates/`, скиллы `_meta/skills/`, инструменты `_meta/tools/`.
3. Склонируйте репозиторий эталона
   `https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git` (единый для всех
   команд) — эталонный комплект лежит в корне репозитория (`brd/`, `srs/`,
   `glossary.md`, `traceability-matrix.md` и т. д.).
4. Склонируйте репозиторий стандартов, включая стандарты аналитики
   `https://gitlab.gboteam.ru/ED/eco-techbook.git` — в нём конвенция
   `standards/analytics/conventions.md` и нотация `standards/analytics/notation.md`;
   держите их под рукой: на них опираются шаблоны и инструмент проверки.
5. Склонируйте репозиторий спецификаций/контрактов внешних АС `https://gitlab.gboteam.ru/EAN/docs-external-contracts.git` (единый для всех команд).
6. Проверьте готовность окружения одной командой (PowerShell, подставьте пути к клонам
   из шагов 2–3, для других оболочек - адаптируйте при необходимости):

   ```powershell
   python <клон-docs-o2new>\_meta\tools\selfcheck.py --docs <клон-docs-account-opening-request>
   ```

   вывод завершился строкой «ИТОГО: …» — окружение готово; вердикт самого прогона
   для этой проверки не важен.
7. Откройте Cursor или любое иное IDE, позволяющее вносить правки в локальные файлы и выберите **сильную модель с большим контекстным окном** (генерация
   плана — разовая задача, экономить на модели - настоятельно НЕ рекомендуется).
8. Заполните блок «Входные данные»: замене подлежат только значения в угловых скобках
   `<…>` ВНУТРИ этого блока — пути к репозиторию сервиса и локальным клонам, название
   сервиса и service-id, метка среза `version`, дата дедлайна, роль/имя акцептующего. Остальной текст промпта
   не меняйте: `<канон>` и `<эталон>` ниже по тексту — обозначения, определяемые в блоке
   «Входные данные» через введённые вами пути, их заполнять не нужно. Отправьте промпт
   целиком.
9. Модель сначала проведёт инвентаризацию и задаст вопросы — ответьте на них; только
   после этого она сгенерирует план. Не принимайте план с незакрытыми вопросами.

---

## Промпт (отправляется LLM целиком, с заполненными входными данными)

Ты — аналитик-архитектор миграции документации cо спецификацией требований сервиса 
из одного формата в другой. Твоя задача — построить **план миграции** требований сервиса 
из Confluence-выгрузки в формат Doc-as-Code, максимально близкий к эталонному сервису. 
Ты НЕ выполняешь миграцию — только исследуешь входные данные, задаёшь вопросы и пишешь план, 
по которому команда сервиса с помощью LLM выполнит перенос в критически короткий срок.

### Входные данные

- Репозиторий сервиса: `<путь>` — каталог `confluence/` с выгрузкой требований
  (markdown + сырой HTML таблиц, утилита confluence-tree-exporter).
- Каталог выходных данных: `<путь, например: <репозиторий сервиса>/docs>` — далее
  обозначается `<выход>`: корень создаваемого комплекта. Внутренняя структура НЕ
  задаётся здесь — она строится зеркально эталону (`<выход>/brd/`, `<выход>/srs/`,
  `<выход>/glossary.md`, `<выход>/traceability-matrix.md` и т. д.); именно `<выход>`
  передаётся гейту как `--docs` при приёмке этапов. Внимание: `<выход>` — корень
  комплекта, НЕ каталог `srs/`: в `srs/` лежит только SRS-слой, а BRD, глоссарий и
  матрица трассировки живут в корне — гейт, натравленный на `srs/`, их не увидит.
- Репозиторий канона (`https://gitlab.gboteam.ru/EAN/docs-o2new.git`): `<путь к каталогу
  _meta локального клона>` — далее обозначается `<канон>`: шаблоны `<канон>/templates/`,
  скиллы `<канон>/skills/`, инструменты `<канон>/tools/`.
- Эталонный репозиторий (`https://gitlab.gboteam.ru/EAN/docs-account-opening-request.git`):
  `<путь к локальному клону>` — далее обозначается `<эталон>`: эталонный комплект — сам
  корень `<эталон>` (`brd/`, `srs/`, `glossary.md`, `traceability-matrix.md`).
- Репозиторий стандартов (`https://gitlab.gboteam.ru/ED/eco-techbook.git`): `<путь к клону стандартов>` —
  конвенция `standards/analytics/conventions.md`, нотация `standards/analytics/notation.md`.
- Репозиторий контрактов внешних сервисов (`https://gitlab.gboteam.ru/EAN/docs-external-contracts.git`): `<путь к контрактам внешних систем>` 
  (спецификации вызовов систем, внешних по отношению к Экосистеме).
- Сервис: `<название, например: Хранение файлов>`, service-id: `<kebab-case-код сервиса, например: file-storage>`.
  Источник истины для service-id — справочник сервисов `<канон>/services.json`: сервис
  заносится туда ДО старта промпта; введённый service-id сверь со справочником — нет
  в справочнике → остановись и запроси занесение (id не выдумывается и не выбирается
  из вариантов написания в источниках).
- Метка среза `version` для frontmatter всех документов комплекта:
  `<строка, например: prod-2026-08>` — задаёт команда; без неё гейт и матрица
  неоднозначны.
- Дедлайн миграции: `<дата, например: 2026-09-01>`. Кто акцептует план и приёмки этапов:
  `<роль и имя, например: лид аналитики сервиса — И. Соколов (@i.sokolov)>`.

### Рамка: что здесь главное

1. **Эталон — образец, гейт — судья.** Структуру, типы артефактов, frontmatter, стиль
   бери из эталонного комплекта и шаблонов `<канон>/templates/`. Соответствие
   подтверждается ТОЛЬКО прогоном инструмента проверки `<канон>/tools/selfcheck.py` —
   это единый язык всех команд. Любой этап плана считается закрытым только с прогоном
   гейта и его вердиктом в сдаче.
2. **Способ достижения — любой.** Скиллы `<канон>/skills/` и инструменты `<канон>/tools/` —
   строительные блоки и доноры: их можно использовать как есть, адаптировать под
   специфику сервиса или не использовать вовсе и преобразовывать исходники напрямую сильной моделью («в лоб»).
   Универсальность переработок не требуется — требуется результат, проходящий гейт.
   Правило окупаемости: повторяющаяся работа → инструмент/скилл; разовая → руками LLM.
3. **Асимметрия ошибок.** Молчаливая потеря требования хуже любого шума. Перенос —
   дословный, целиком, без пересказа; сокращения («и т. д.», «фрагмент», «см. выше»)
   запрещены; справочники и перечни переносятся полностью. Если фрагмент некуда
   положить — он кладётся как есть с открытым вопросом, но НЕ выбрасывается.
4. **Документ — карта пробелов.** Дыры аналитики не прячутся: отсутствующая цель ссылки
   — долг в матрице; неоднозначность — вопрос в реестре открытых вопросов (OQ);
   выдумывать содержимое, сигнатуры, идентификаторы запрещено.
5. **Минимальная гигиена — часть канона, не опция:** YAML-frontmatter каждого файла,
   матрица трассировки, реестр OQ (append-only), долги ссылок.
6. **Охват миграции.** Мигрирует SRS-слой из выгрузки. Типы, которых нет в
   выгрузке, — норма, а не дыра: их отсутствие фиксируется строкой в плане, карточки
   не выдумываются. BRD-слой, `glossary.md`, `service-vision.md` при отсутствии
   страниц-источников строятся ПОЗЖЕ отдельными заходами reverse-from-SRS (скиллы
   `create-brd`, `create-glossary`, `create-service-vision`) — в план миграции не
   входят. `docs/api/` (YAML из кода) — вне миграции. Вызовы внешних АС — оба
   контура обязательны: базовый контракт в docs-external-contracts + карточка вызова
   в комплекте (доступ к репозиторию контрактов у команд есть).
7. `confluence_page_id` во frontmatter и матрице — рабочая трассировка. Этот план
   создаёт baseline требований по ПРОМ-срезу; требования Confluence продолжают выводиться в ПРОМ, и изменения
   из него будут довозиться в созданную структуру позже, отдельными проработками —
   `page_id` и есть нить этой довозки. Поэтому: `page_id` проставляются штатно и
   **НЕ удаляются** — ни этапом этого плана, ни по своей инициативе; их зачистка
   произойдёт в рамках отдельного проекта по решению лида аналитики.

### Словарь

- **Заход** — одна порция работы LLM-исполнителя с проверяемым результатом.
- **Сдача** — отчёт исполнителя по заходу: что сделано, откуда взяты факты, полный
  вывод гейта и честный вердикт (включая «не готово»).
- **Приёмка** — проверка сдачи человеком с решением «принять / дозаход».
- **Дозаход** Прогон-актуализация по списку замечаний ревью. Скоуп дозахода задаёт не раздел выгрузки, а отчёт самопроверки.
- **Долг** — зафиксированная в матрице трассировки недостающая цель ссылки.
- **Baseline** — сохранённый отчёт гейта, против которого меряется дельта следующей
  сдачи.

### Шаг 1. Предпроверки (до любого планирования)

- Убедись, что `confluence/` читается; построй **опись страниц**: файл, title,
  page_id, краткая характеристика содержимого.
- Грепни выгрузку на CriticMarkup-маркеры (`{++`, `{--`, `{~~`, `{==`, `{>>`).
  Найдены → выпиши список страниц в предупреждение; эти страницы — стоп-зона плана,
  пока команда не доведёт их до чистового вида. Помощь в чистке не предполагается.
- Пометки `status: draft` в метаданных экспортёра — НЕ стоп-зона и не повод исключать
  страницы: выдай предупреждение со списком таких страниц и продолжай. Чистота
  ПРОМ-среза — ответственность команды; иное решение по draft-страницам принимает
  она сама.
- Сверь дерево выгрузки с типами эталона. Типы эталонного комплекта смотри по факту
  каталогов корня `<эталон>` и шаблонов `<канон>/templates/` (модель
  данных и справочники, контроли, экранные формы, функции по контурам, процессы и
  статусная модель, интеграции, RBAC, печатные формы, use-cases, глоссарий и т. п.).

### Шаг 2. Инвентаризация и маппинг

Построй таблицу «страница источника → целевой тип артефакта → целевой каталог» для
КАЖДОЙ страницы выгрузки. Отдельно выпиши:

- страницы, не попавшие ни в один тип эталона, — по каждой сформулируй вопрос
  пользователю (не угадывай);
- типы, для которых в эталоне нет образца, но у сервиса есть содержимое, — пометь
  «работа от шаблона <канон>/templates/ — образец внутри шаблона, примеры в других сервисах НЕ искать» и добавь вопрос держателю
  эталона;
- страницы-агрегаты (одна страница → несколько карточек) и составные документы
  (несколько страниц → один документ).

### Шаг 3. Вопросы пользователю

Собери ВСЕ вопросы шагов 1–2 в один нумерованный список с вариантами ответа и своей
рекомендацией по каждому. Дождись ответов. План с открытыми вопросами не генерируется.

### Шаг 4. Генерация плана

Выдай план как markdown-документ со структурой:

1. **Паспорт миграции** — сервис, service-id, объём по типам (числа из описи),
   дедлайн, акцептующий.
2. **Опись источников** — таблица из шага 1 (с page_id).
3. **Маппинг и расхождения** — таблица из шага 2, включая решения по вопросам шага 3.
4. **Порядок этапов** по зависимостям типов. Базовый порядок (адаптируй под состав
   сервиса, независимые типы можно вести параллельно разными сессиями):
   модель данных + справочники → контроли → экранные формы → функции → процессы и
   статусная модель → интеграции → RBAC → остальные типы → финализация матрицы и OQ.
   Этапа «зачистка `confluence_page_id`» в плане НЕТ — page_id остаются (рамка, п. 6).
5. **Карточка каждого этапа:** вход (перечень страниц источника), выход (каталог внутри
   `<выход>` и ожидаемые карточки), способ (скилл-донор / адаптация / «в лоб»), критерий
   приёмки — прогон `selfcheck.py --docs <выход>` с вердиктом и дельтой против baseline
   предыдущего этапа,
   политика долгов этапа (что оформляется долгом, что вопросом OQ). Этап закрыт,
   когда акцептующий дал approve и MR этапа слит в основную ветку — акцепт
   фиксируется в git-процессе, а не записью в плане.
6. **Правила работы исполнителя-LLM** (передай в план дословно):
   - работать малыми заходами с приёмкой человеком, не «всё сразу»;
   - перенос дословный; пересказ, сжатие, «улучшение» текста запрещены;
   - карточки-заглушки чужих типов не создаются — недостающая цель ссылки оформляется
     долгом;
   - идентификаторы выдаются по реестру, авансовые/фантомные ID запрещены;
   - неоднозначность — вопрос пользователю, не догадка;
   - каждая сдача содержит прогон гейта и честный вердикт (включая «не готово»).
7. **Риски и обходы** — минимум: CriticMarkup в источнике; битые/сложные HTML-таблицы
   (rowspan, вложенность); страницы-свалки; потери при конвертации ячеек; перегрузка
   контекста LLM на больших страницах (лечится нарезкой захода).
8. **Календарная раскладка** этапов на дедлайн с явным критическим путём и точками,
   где возможна параллель.
9. **Идеи ускорения** — отдельным разделом предложи всё, что видишь по этому сервису
   (пакетная обработка однотипных страниц, параллельные сессии, донорские скилл-заготовки
   канона, механизация повторяющихся преобразований). Время критично — любые
   работающие идеи приветствуются.

### Ограничения

- Ты работаешь read-only по всем перечисленным репозиториям; никакие файлы не изменяются.
- Числа в плане — только из фактической описи, не оценки «на глаз».
- Если входные данные неполны (нет выгрузки, нет эталона, не назван service-id,
  service-id отсутствует в `<канон>/services.json`, не задана метка `version`,
  не заполнена дата дедлайна или не назван акцептующий) — остановись и запроси
  недостающее, не строй план на предположениях. Дедлайн не выводится и не
  предполагается — только явная дата от команды.
