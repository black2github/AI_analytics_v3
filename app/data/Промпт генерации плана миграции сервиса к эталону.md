# Промпт генерации плана миграции сервиса к эталону

Универсальный промпт для команд сервисов ДБО. Версия 1 (2026-08-20), обкатка — на
первых пилотных сервисах; промпт будет уточняться по инсайтам обкатки.

## Как пользоваться (инструкция команде сервиса)

1. Подготовьте репозиторий сервиса (хронология src-<сервис>) с каталогом `confluence/` — полной выгрузкой
   ПРОМ-среза требований сервиса утилитой confluence-tree-exporter.
   Выгрузка должна быть БЕЗ CriticMarkup-разметки; если разметка есть — сначала доведите
   аналитику до чистового вида, это ваша зона ответственности.
2. Склонируйте эталонный репозиторий (комплект `output/open-add-account` + канон `_meta`).
3. Склонируйте репозиторий стандартов аналитики
   `https://gitlab.gboteam.ru/ED/eco-techbook.git` — в нём конвенция
   `standards/analytics/conventions.md` и нотация `standards/analytics/notation.md`;
   держите их под рукой: на них опираются шаблоны и инструмент проверки.
4. Откройте Cursor, выберите **сильную модель с большим контекстным окном** (генерация
   плана — разовая задача, экономить на модели - настоятельно НЕ рекомендуется).
5. Подставьте значения в блок «Входные данные» и отправьте промпт целиком.
6. Модель сначала проведёт инвентаризацию и задаст вопросы — ответьте на них; только
   после этого она сгенерирует план. Не принимайте план с незакрытыми вопросами.

---

## Промпт (отправляется LLM целиком, с заполненными входными данными)

Ты — аналитик-архитектор миграции документации cо спецификацией требований. Твоя задача — построить **план
миграции** требований сервиса из Confluence-выгрузки в формат Doc-as-Code, максимально
близкий к эталонному сервису. Ты НЕ выполняешь миграцию — только исследуешь входные
данные, задаёшь вопросы и пишешь план, по которому команда с помощью LLM выполнит
перенос в критически короткий срок.

### Входные данные

- Репозиторий сервиса: `<путь>` — каталог `confluence/` с выгрузкой требований
  (markdown + сырой HTML таблиц, утилита confluence-tree-exporter).
- Эталонный репозиторий: `<путь>` — эталонный комплект `output/open-add-account/docs/`
  и канон `_meta/` (конвенция, нотация, шаблоны, скиллы, инструменты).
- Сервис: `<название>`, service-id: `<kebab-case-код сервиса>`.
- Дедлайн миграции: `<дата>`. Кто акцептует план и приёмки этапов: `<роль/имя>`.

### Рамка: что здесь главное

1. **Эталон — образец, гейт — судья.** Структуру, типы артефактов, frontmatter, стиль
   бери из эталонного комплекта и шаблонов `_meta/templates/`. Соответствие
   подтверждается ТОЛЬКО прогоном инструмента проверки `_meta/tools/selfcheck.py` —
   это единый язык всех команд. Любой этап плана считается закрытым только с прогоном
   гейта и его вердиктом в сдаче.
2. **Способ достижения — любой.** Скиллы `_meta/skills/` и инструменты `_meta/tools/` —
   строительные блоки и доноры: их можно использовать как есть, адаптировать под
   специфику сервиса или не использовать вовсе и работать «в лоб» сильной моделью.
   Универсальность переработок не требуется — требуется результат, проходящий гейт.
   Правило окупаемости: повторяющаяся работа → инструмент/скилл; разовая → руками LLM.
3. **Асимметрия ошибок.** Молчаливая потеря требования хуже любого шума. Перенос —
   дословный, целиком, без пересказа; сокращения («и т. д.», «фрагмент», «см. выше»)
   запрещены; справочники и перечни переносятся полностью. Если фрагмент некуда
   положить — он кладётся как есть с открытым вопросом, но НЕ выбрасывается.
4. **Документ — карта пробелов.** Дыры аналитики не прячутся: отсутствующая цель ссылки
   — долг в матрице; неоднозначность — вопрос в реестре открытых вопросов (OQ);
   выдумывать содержимое, сигнатуры, идентификаторы запрещено.
5. **Минимальная гигиена — часть канона, не опция:** YAML-frontmatter каждого файла,
   матрица трассировки, реестр OQ (append-only), долги ссылок. `confluence_page_id`
   во frontmatter и матрице — рабочая трассировка на время миграции; её зачистка —
   отдельный финальный этап плана.

### Шаг 1. Предпроверки (до любого планирования)

- Убедись, что `confluence/` читается; построй **опись страниц**: файл, title,
  page_id, краткая характеристика содержимого.
- Грепни выгрузку на CriticMarkup-маркеры (`{++`, `{--`, `{~~`, `{==`, `{>>`).
  Найдены → выпиши список страниц в предупреждение; эти страницы — стоп-зона плана,
  пока команда не доведёт их до чистового вида. Помощь в чистке не предполагается.
- Сверь дерево выгрузки с типами эталона. Типы эталонного комплекта смотри по факту
  каталогов `output/open-add-account/docs/` и шаблонов `_meta/templates/` (модель
  данных и справочники, контроли, экранные формы, функции по контурам, процессы и
  статусная модель, интеграции, RBAC, печатные формы, use-cases, глоссарий и т. п.).

### Шаг 2. Инвентаризация и маппинг

Построй таблицу «страница источника → целевой тип артефакта → целевой каталог» для
КАЖДОЙ страницы выгрузки. Отдельно выпиши:

- страницы, не попавшие ни в один тип эталона, — по каждой сформулируй вопрос
  пользователю (не угадывай);
- типы, для которых в эталоне нет образца, но у сервиса есть содержимое, — пометь
  «работа от шаблона `_meta/templates/`, образца нет» и добавь вопрос держателю
  эталона;
- страницы-агрегаты (одна страница → несколько карточек) и составные документы
  (несколько страниц → один документ).

### Шаг 3. Вопросы пользователю

Собери ВСЕ вопросы шагов 1–2 в один нумерованный список с вариантами ответа и своей
рекомендацией по каждому. Дождись ответов. План с открытыми вопросами не генерируется.

### Шаг 4. Генерация плана

Выдай план как markdown-документ со структурой:

1. **Паспорт миграции** — сервис, service-id, объём по типам (числа из описи),
   дедлайн, акцептующий.
2. **Опись источников** — таблица из шага 1 (с page_id).
3. **Маппинг и расхождения** — таблица из шага 2, включая решения по вопросам шага 3.
4. **Порядок этапов** по зависимостям типов. Базовый порядок (адаптируй под состав
   сервиса, независимые типы можно вести параллельно разными сессиями):
   модель данных + справочники → контроли → экранные формы → функции → процессы и
   статусная модель → интеграции → RBAC → остальные типы → финализация матрицы и OQ →
   зачистка `confluence_page_id`.
5. **Карточка каждого этапа:** вход (перечень страниц источника), выход (каталог и
   ожидаемые карточки), способ (скилл-донор / адаптация / «в лоб»), критерий приёмки —
   прогон `selfcheck.py` с вердиктом и дельтой против baseline предыдущего этапа,
   политика долгов этапа (что оформляется долгом, что вопросом OQ).
6. **Правила работы исполнителя-LLM** (передай в план дословно):
   - работать малыми заходами с приёмкой человеком, не «всё сразу»;
   - перенос дословный; пересказ, сжатие, «улучшение» текста запрещены;
   - карточки-заглушки чужих типов не создаются — недостающая цель ссылки оформляется
     долгом;
   - идентификаторы выдаются по реестру, авансовые/фантомные ID запрещены;
   - неоднозначность — вопрос пользователю, не догадка;
   - каждая сдача содержит прогон гейта и честный вердикт (включая «не готово»).
7. **Риски и обходы** — минимум: CriticMarkup в источнике; битые/сложные HTML-таблицы
   (rowspan, вложенность); страницы-свалки; потери при конвертации ячеек; перегрузка
   контекста LLM на больших страницах (лечится нарезкой захода).
8. **Календарная раскладка** этапов на дедлайн с явным критическим путём и точками,
   где возможна параллель.
9. **Идеи ускорения** — отдельным разделом предложи всё, что видишь по этому сервису
   (пакетная обработка однотипных страниц, параллельные сессии, донорские скилл-заготовки
   эталона, механизация повторяющихся преобразований). Время критично — любые
   работающие идеи приветствуются.

### Ограничения

- Ты работаешь read-only по обоим репозиториям; никакие файлы не изменяются.
- Числа в плане — только из фактической описи, не оценки «на глаз».
- Если входные данные неполны (нет выгрузки, нет эталона, не назван service-id) —
  остановись и запроси недостающее, не строй план на предположениях.
