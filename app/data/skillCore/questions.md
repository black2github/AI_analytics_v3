# Журнал вопросов облачной сессии (трек skillCore)

Формат (SC-07): номер решения, к которому относится вопрос; вопрос; варианты; рекомендация. Пустое поле «Решение

## Q-01. SC-07 / README «Проверки после каждого среза» — baseline selfcheck собран в Windows, байтовое сравнение в Linux невыполнимо (срез 0, 2026-10-29)

- **Вопрос.** Условие приёмки «оба selfcheck байт в байт как в `skillCore/baseline/`» в среде сессии (Linux) не
  выполняется уже на нетронутом `main` (коммит `2ac6034`, до правок): baseline собран `build_mirror.py` в Windows —
  разделители путей `\` против `/`, другой порядок строк обхода каталогов, CRLF против LF, и у полигона строка
  `✗ корень репозитория: посторонние файлы ×7 (app, canon, …)` — прибор ищет корень по ближайшему `.git`
  (`selfcheck.py:257`), в клоне зеркала это корень зеркала, а при сборке baseline каталог ещё не был репозиторием.
  Какую проверку считать условием «комплекты не задеты» для этого и следующих срезов?
- **Что сделано в срезе 0.** (1) Байтовое сравнение прогонов до и после правок в одной среде — оба `--out` и оба
  консольных вывода совпадают (`cmp` без отличий). (2) Нормализованное сравнение с baseline (`CRLF→LF`, `\→/`,
  `sort`): эталон совпадает полностью; полигон — единственное отличие та самая строка о корне. (3) Строк, зависящих
  от даты, нет (ПРОСРОЧЕН — 0, сводка OQ одинакова). Подробности — сдача среза 0, раздел 5.
- **Варианты.**
  - (а) Принять эквивалентную проверку: байтовое сравнение с прогоном на `main` в среде сессии плюс нормализованное
    сравнение с Windows-baseline с перечислением отличий в сдаче. Baseline не пересобирается.
  - (б) Пересобрать baseline в Linux (владелец или сессия по отмашке: те же четыре команды на `main`, результат —
    коммит по `skillCore/baseline/` в `main`); дальше — байт в байт, как написано.
  - (в) Оставить условие как есть — тогда ни один срез в этой среде принят быть не может.
- **Рекомендация.** (б) как целевое состояние (условие README остаётся буквальным), (а) — для среза 0 и до
  пересборки. Сессия baseline в `main` сама не меняет (SC-12: `main` правят локальные сессии и владелец), но может
  положить Linux-прогон на `main` в ветку по отмашке.
- **Решение владельца (2026-10-29):** для среза 0 принята эквивалентная проверка (а) — четыре `cmp` до/после в одной
  среде достаточны. Целевое состояние — (б): Linux-baseline собираешь ты в этой же ветке (те же четыре команды README на
  текущем состоянии ветки; файлы `skillCore/baseline/` заменить, имена прежние; строка о корне полигона входит в
  baseline; коммит по `skillCore/`). Условие SC-07 уточнено в файле решений. Вместе с этим — доработка среза 0 по
  файлу `skillCore/Разбор сдачи среза 0 …(2026-10-29).md`, раздел «Что передаётся сессии»: чтение шаблона — пункт
  общего `## Вход`, «Порядок» 1…7, в каркасе и образце; повторная сдача разделом в том же файле сдачи, патч заново.

## Q-02. SC-05 / SC-07 — пара A/B P1: расхождение в размахе повторов при равенстве по классам сторожей, ID и файлам (срез 1, 2026-10-29)

- **Вопрос.** По правилу SC-05 пара P1 провалена: размах повторов «после» больше размаха «до» по метрикам 4 (строки
  диффа к эталону: 32/31 против 8/7), 5 (счётчики вхождений литералов) и 6 (число вопросов: 20/18 против 20/20);
  по метрике 4 повтор «после-1» выше обоих «до» (214/104 против 174/72 и 182/79). Разложение (сдача среза 1,
  раздел 10.3): превышение целиком в файле постановки `tasks/TEAMTB-4567890.md` (119/66 против 81/34 — иная форма
  записи постановки), по карточкам, матрице и README «после» внутри размаха «до»; новых классов ✗/⚠ нет, ожидаемые
  ID, файлы дельты и состав разделов — равны. Считать ли это провалом переворота диспетчера?
- **Варианты.** (а) принять пару по разложенным метрикам (строки диффа — без `tasks/`; литералы — присутствие, не
  счётчик; число вопросов — информационно), записав уточнение в SC-05; (б) провал как есть, срез стоит, диспетчер
  возвращается к старой структуре; (в) третий повтор на плечо (3×3) и оценка по медиане и размаху трёх.
- **Рекомендация.** (а): два повтора ловят дисперсию модели в свободном тексте, а не различие структуры скилла —
  по всем механическим признакам результата (сторожа, ID, файлы, разделы) плечи равны. Повторные прогоны «до
  зелёного» сессия не делала (SC-07).
- **Решение владельца (2026-10-29):** вариант (а). Уточнение SC-05 записано в файле решений: метрики делятся на
  решающие (selfcheck, ID, файлы дельты, matrix_sync, состав разделов, присутствие и размещение литералов; критерий «не
  хуже худшего из „до“», новый класс ✗/⚠ — провал) и информационные (строки диффа, счётчики вхождений, число вопросов);
  правило размаха снято, третий повтор не добавляется. Пара P1 принята. Допиши в сдачу раздел «Решение по Q-02 и
  итоговый вердикт» (таблица 10.3 с колонкой «решающая / информационная», вывод, вердикт ГОТОВО) без новых прогонов;
  reverse-плечо PRC-002 не делать. Разбор — `skillCore/Разбор сдачи среза 1 …(2026-10-29).md`.

## Q-03. SC-02 / SC-01 — `create-nfr`: каркас с режимами не даёт ответа без переписывания (срез 2, 2026-10-29)

- **Вопрос.** У `create-nfr` два полных параллельных списка шагов: «Шаги `ingress: reverse` и `ingress: update` по
  переносу» (1–15) и «Шаги `ingress: forward`» (1–9). Общие действия (собрать строки по шаблону типа, назначить
  номера, записать 18 страниц, обновить реестр и BRD-6, долги матрицы, самопроверка, отчёт) есть в обоих списках,
  но записаны разными словами и с режимными деталями внутри (reverse: `ingress` страницы `reverse`, `title` из
  каталога, `confluence_page_ids` — шаг 10; forward: `source_artifacts` не ставить, `ingress` становится `mixed`,
  гейты BRD-6.5 — шаги 6–8; forward-шаг 7 ссылается «как в шаге 13 reverse»). Ни один шаг не совпадает текстуально.
  Норма каркаса «общие шаги один раз, в „Порядке“ — ничего, что зависит от режима» выполнима только одним из двух
  запрещённых в срезе способов: выбрать одну формулировку и снять другую (сокращение) или слить две в одну с
  оговорками (переписывание). Как поступить с `create-nfr`?
- **Варианты.** (а) В срезе 2 `create-nfr` не трогать: его вводный абзац уже несёт общую для всех `ingress` норму
  (прочитать индекс, `_common.md`, `glossary.md` с диска), `Gate` не зависит от режима, списки шагов ключуются
  значением `ingress`; записать исключение из SC-01 («структура по значениям `ingress`, каркас не применяется до
  отдельного решения»). (б) Применить каркас формально: «Вход reverse (режим A; `ingress: reverse`, `update`)» —
  шаги 2–6 reverse, «Вход forward (режим B; `ingress: forward`)» — шаги 2–4 forward, «Порядок» — шаги 7–15 reverse
  дословно, а forward-шаги 5–9 оставить в подразделе «Вход forward» как его продолжение. Итог: «Порядок» с
  reverse-оговорками, которые forward обязан игнорировать, и второй, дублирующий порядок внутри «Входа forward» —
  нарушены обе нормы каркаса, читатель получит два порядка вместо одного. (в) Владелец задаёт текст объединённого
  «Порядка» (как SC-04 задаёт forward-входы группы 3): общие шаги одной формулировкой, режимные детали — оговорками
  «при `ingress: reverse`/`update` …», «при `ingress: forward` …»; сессия применяет дословно в отдельном срезе или
  в срезе 4.
- **Рекомендация.** (а) сейчас, (в) как отдельное решение после среза 2: это единственный скилл объёма, где
  переворот — содержательная правка, а не перестановка; остальные пять скиллов группы 2 легли на каркас без
  переписывания (коммит по `canon/` в ветке). Заголовки подразделов с `ingress` в скобках (по постановке среза 2)
  применимы при (б) и (в).
- **Решение владельца:** (а) — принято (владелец, 2026-10-29). В срезе 2 `create-nfr` не трогать; в SC-01 записано
  исключение: «`create-nfr` — структура по значениям `ingress`, каркас не применяется до отдельного решения».
  Объединённый «Порядок» (вариант (в)) — отдельное решение: текст готовит сессия analyzer файлом на утверждение
  владельцу (таблица «шаг reverse ↔ шаг forward → общая формулировка / оговорка»), применяется дословно отдельным
  срезом после группы 3. Заголовки подразделов с `ingress` в скобках — по постановке среза 2, при применении.
  Разбор владельца: пять скиллов перевёрнуты верно (механическая сверка: десять связок + заголовки), срез 2
  принимается после итогового вердикта.

## Q-04. SC-05 / SC-07 — пара P2: ✗ сторожа имён параметров по карточке у обоих «после» (срез 2, 2026-10-29)

- **Вопрос.** По решающей метрике 1 оба повтора «после» хуже обоих «до»: по файлу карточки FUN-CL-02 — 1 ✗
  против 0, новый класс ✗ против базы «HTML-таблицы источника: в карточке отсутствуют N имён параметров — пример
  потери: `CLIENT_CONTRACT_VIEW`». Все остальные решающие метрики (карточка против эталона, матрица, `matrix_sync`,
  литералы и размещение, закрытые битые ссылки) равны. Источник ✗ — конфликт внутри канона: шаблон функции берёт
  код привилегии из `rbac.md` (`CLIENT.CONTRACT_VIEW`, как в эталоне; расхождение с источником закрыто OQ-023), а
  сторож selfcheck требует дословного `CLIENT_CONTRACT_VIEW` со страницы, потому что строка «Код привилегии» паспорта
  распознана как сетка параметров; эталон под этот сторож не попадал (без `confluence_page_ids`). «до» прошли сторож,
  дописав в карточку «(в реализации — константа `CLIENT_CONTRACT_VIEW`)» (прецедент FUN-CL-03 комплекта); «после»
  оставили код по шаблону и сдали «НЕ ГОТОВО по сторожу» с OQ-069, ссылаясь на правило `create-artifact` «гейт
  закрывается переносом данных, а не упоминанием». Считать ли это провалом переворота `create-function`?
- **Варианты.** (а) Признать ✗ конфликтом сторожа и шаблона, не поведением скилла: метрику 1 по карточке считать
  по классам без этого класса (или по карточке без `confluence_page_ids`, как у эталона) — тогда «не хуже» по всем
  решающим, пара принята; конфликт — отдельный вопрос владельцу канона (сторож исключает строку «Код привилегии» /
  коды привилегий из сетки параметров, либо шаблон разрешает пометку написания источника). (б) Провал как есть:
  срез стоит, пять скиллов группы 2 возвращаются к прежней структуре. (в) Третий повтор на плечо — при 2 : 2 по
  одному бинарному выбору исход решит один прогон; дорого (четыре прогона — 207–227 тыс. токенов исполнителя
  каждый). (г) Признать выбор «после» правильным по канону (правило о гейте — норма диспетчера), а приём «до» —
  маскировкой; тогда метрика 1 трактуется как «хуже» у «до» — но это оценка содержания, которую SC-05 не
  предусматривает.
- **Рекомендация.** (а), с записью в SC-05: класс ✗, вызванный расхождением сторожа и шаблона (подтверждённым
  записью OQ комплекта), в метрику 1 не входит до решения по конфликту; конфликт сторожа «имена параметров» с
  кодами привилегий — вопрос владельцу канона (прибор, `_meta/tools`), вне этого трека.
- **Решение владельца:** (а) — принято (владелец, 2026-10-29). ✗ «HTML-таблицы источника: имена параметров» по
  карточке FUN-CL-02 — ложное срабатывание сторожа `html_param_names` на таблице-паспорте источника (строка «Код
  привилегии»), подтверждено по коду прибора; шаблон `function.md` и OQ-023 требуют кода из `rbac.md`, правило
  диспетчера запрещает вписывать имя источника ради гейта. Плечо «после» действовало по канону; «до» прошло гейт
  приёмом, который канон называет маскировкой («прецедент FUN-CL-03» в эталоне отсутствует). Уточнение SC-05: класс
  ✗/⚠, вызванный подтверждённым расхождением сторожа и шаблона, в решающую метрику 1 не входит до решения по
  конфликту. По остальным строкам метрики 1 и метрикам 2–4 «после» не хуже — **пара P2 принята**. Конфликт сторожа
  передан владельцем в сессию прибора (постановка от 2026-10-29), вне этого трека. Сессии: дописать в сдачу раздел
  «12. Решения по Q-03 и Q-04, итоговый вердикт» (таблица 10.2 с пометкой у строк «✗ по файлу карточки» и «новых
  классов» — «класс конфликта сторожа и шаблона, в метрику не входит»; вывод «не хуже по всем решающим»; вердикт
  ГОТОВО), новых прогонов не делать, патч `2/0001` не пересобирать; коммит по `skillCore/`, push ветки.
