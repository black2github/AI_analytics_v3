## SC-02. Целевой каркас скилла

- Вопрос: единый порядок разделов после переворота.
- Предложение (записывается в `create-skill.md`, раздел «Каркас», как норма; существующие скиллы приводятся к нему):

```
# Скилл: <название>
## Вход                       что нужно на входе в любом режиме; строка «Режим: reverse / forward / change»
### Вход reverse (режим A)    сбор источников: бывшие шаги 2–4 режима A / «Порядок (reverse)» пп. 2–3 — только то,
                              что относится к выгрузке (где искать страницы, обзорные таблицы, подстраницы,
                              спорные места источника, запреты вроде Confluence-dump)
### Вход forward (режим B)    разбор требований/постановки: бывшие шаги 2–3 режима B; для группы 3 — новый текст по SC-04
## Порядок                    общие шаги, один раз: шаблон типа целиком → документ строго по шаблону → матрица
                              трассировки (matrix_sync) → чек-лист шаблона → самопроверка selfcheck → отчёт аналитику
                              → коммит по просьбе. Нумерация сквозная 1…N
## Режим C — change           как есть; ссылки «правила режима A действуют…» → «порядок и правила всех режимов действуют…»
## Границы скоупа / Специфика типа   как есть
## Правила всех режимов       как есть
## Самопроверка / Выход аналитику    как есть (где были)
```

  Буквы режимов A/B сохраняются в заголовках подразделов «Вход», чтобы внешние упоминания («режим A (reverse)» в
  `_meta/rules/defaults.md`, режим C в гиде) остались верными без правок. Для скиллов, где общие шаги были в
  «Порядок (reverse)» (группа 2), общий порядок — это их шаги с первого, не относящегося к сбору источников, и до конца.
- Решение владельца: принято (владелец, 2026-10-29); названия подразделов «Вход reverse (режим A)» / «Вход forward (режим B)» приняты
- Уточнение владельца (2026-10-29, по сдаче среза 0): чтение шаблона типа — пункт общего раздела `## Вход`
  (предусловие любого режима, до сбора входа), не шаг «Порядка». «Порядок»: документ строго по шаблону → матрица →
  спорные места → чек-лист → selfcheck → отчёт → коммит (1…7). Основание: в исходных скиллах и в `create-artifact`
  шаблон читается первым шагом в обоих режимах; переворот поведение менять не должен.
- Как применяет сессия: срез 0 — каркас в `create-skill.md` и образец на одном скилле (`create-function`) без
  вливания, для сверки владельцем; дальше по срезам.

## SC-04. Forward-«Вход» для группы 3 (новый текст)

Общий принцип предложений: вход forward — это документы постановки, уже существующие в комплекте или присланные
аналитиком; скилл называет, откуда брать факты и что делать при их отсутствии (вопрос аналитику по
`_meta/rules/questions.md`, умолчания `DFR-NNN` только в режиме C). Раздел шаблона «Проектирование с нуля» остаётся
домом правил проектирования; подраздел скилла — только о входе, без дублирования шаблона.

| Тип | Предложение текста «Вход forward» (5–10 строк) | Решение владельца |
| --- | --- | --- |
| `create-data-model` | Вход: бизнес-требования и use-case (какие данные создаются и меняются), процесс (шаги, порождающие или меняющие данные), экранные формы (поля → атрибуты), печатные формы (поля документа), справочники и сущности платформы (`EXT-NNN` по реестру `dictionaries.md`). Правила проектирования — шаблон, раздел «Проектирование с нуля». Физ. имена не задаются. Пробелы — вопросами аналитику, не домыслом | принято (владелец, 2026-10-29) |
| `create-contract-call` | Вход: спецификация контракта внешней системы (карточка в `docs-external-contracts/` или документ владельца АС), точка вызова (шаг процесса или функция), параметры из модели данных. Нет спецификации — карточка не создаётся (запрет заглушек), регистрируется долг и вопрос аналитику | принято (владелец, 2026-10-29) |
| `create-controls` | Вход: бизнес-правила и условия постановки, реестр полей экранной формы и атрибуты модели (к чему привязан контроль), тексты сообщений об ошибке из постановки дословно; текст не задан — «в постановке не задано» (прецедент), не сочинять | принято (владелец, 2026-10-29) |

| `create-print-form` | Вход: макет документа (docx с нумерацией полей или его описание), точки формирования (функция, шаг процесса, роль), правила заполнения полей из постановки (пять вопросов шаблона); нет макета — вопрос, карточка не заводится | принято (владелец, 2026-10-29) |

## SC-05. Протокол A/B

- Вопрос: как доказать, что переворот не изменил поведение агента.
- Предложение:
  - **Пары.** P1 — `create-artifact` в режиме C на полигоне: вход `polygon-ref/tasks/TEAMTB-4567890.md`, эталон
    сравнения — принятый результат той же задачи (`polygon-ref/`). P2 — `create-function`, reverse на эталонном
    комплекте: карточка `FUN-CL-02` («Клиент: Функция просмотра заявки»), источник — страница из
    `canon/sources/confluence/o2plus/` (сопоставление карточка → страница сессия устанавливает в срезе 0 по
    `index.md` и фиксирует в сдаче). P3 — `create-data-model`, reverse: `ENT-001` («Заявка»), источник —
    `o2plus/Модель-данных/Заявка-на-открытие-доп-счета-и-заключение-ДБС.md`. Для `create-artifact` в reverse —
    `PRC-002` (процесс), если срез 1 укладывается в бюджет; иначе P1 достаточно.
  - **Плечи и повторы.** Плечо «до» — скиллы базового среза (`canon-base`), плечо «после» — скиллы среза. По два
    повтора на плечо: четыре прогона на пару, двенадцать на три пары.
  - **Исполнитель.** Отдельный подагент с чистым контекстом на каждый прогон; промпт — «выполни скилл <имя> для
    <вход> в комплекте <путь>; режим <A|C>», без слов «эксперимент», «сравнение», «до/после». Та же модель. Выход
    исполнитель пишет в копию комплекта (`skillCore/ab/<пара>/<плечо>-<повтор>/`), исходный `canon/output` и
    `polygon/` не трогает.
  - **Метрики (только механические).** (1) строки selfcheck по созданной/изменённой карточке: вердикт, число ✗/⚠,
    классы сторожей; (2) дословность: `title`, кавычечные литералы, значения таблиц источника — доли «на месте»
    из selfcheck; (3) дифф к принятой карточке: строк добавлено/удалено, число разделов шаблона с отличиями;
    (4) матрица: строки реестра и покрытия через `matrix_sync`; (5) число записанных OQ и вопросов постановки;
    для P1 — отчёт дельты режима C (`delta_report`): затронутые файлы и ID против эталонного результата.
  - **Критерий приёмки.** Плечо «после» не хуже плеча «до» по каждой метрике в обоих повторах, и размах между
    повторами «после» не больше размаха «до». Любое новое ✗ класса, которого не было в «до», — провал пары.
  - **Форма результата.** Таблица «метрика × (до-1, до-2, после-1, после-2)» на пару, ссылки на каталоги
    прогонов; вывод словами только «не хуже / хуже по метрикам …», без оценок «похоже».
- Решение владельца: принято (владелец, 2026-10-29): пары P1–P3, два повтора на плечо, метрики и критерий как предложено
- Уточнение владельца (2026-10-29, ответ на Q-02, действует с пары P1 и на P2/P3): метрики делятся на **решающие** —
  selfcheck (вердикт, ✗/⚠ всего и по затронутым файлам, классы; новый класс ✗/⚠ — провал), ожидаемые ID и новые ID
  реестра, файлы дельты против эталона («нет» и «сверх»), `matrix_sync --check`, состав разделов второго уровня,
  присутствие литералов постановки (из N), файлы размещения литералов (новое место у «после», которого нет ни у «до», ни
  у эталона, — в сдачу с оценкой, само по себе не провал) — критерий «не хуже худшего из „до“ в обоих повторах»; и
  **информационные** — строки диффа к эталону (всего и по группам файлов, `tasks/` отдельно), счётчики вхождений
  литералов, число вопросов и записей OQ — в таблицу, на исход не влияют. Правило размаха повторов снято: при двух
  повторах оно не отличает дисперсию модели от различия скиллов; третий повтор не добавляется. Пара P1 по этому правилу
  принята.
- Уточнение владельца 2 (2026-10-29, ответ на Q-04, действует с пары P2): класс ✗/⚠, вызванный подтверждённым
  расхождением сторожа прибора и шаблона (запись OQ комплекта со ссылкой на правило шаблона, подтверждение владельца в
  ответе на вопрос), в решающую метрику 1 не входит до решения по конфликту; сам конфликт — задача прибора, вне трека.
  Пара P2 по этому правилу принята (по остальным строкам метрики 1 и метрикам 2–4 «после» не хуже).
- Как применяет сессия: провал пары — остановка среза с таблицей, без повторных попыток «до зелёного».

## SC-07. Правила остановки

- Нет решения в поле «Решение владельца» → вопрос в `skillCore/questions.md` (формат: номер SC, вопрос, варианты,
  рекомендация), срез стоит.
- Сторож SF ⚠ по сигнатуре, которую сессия не меняла намеренно → остановка (значит, задет чужой текст).
- Selfcheck эталона или полигона отличается от базового байт в байт → остановка (задет комплект).
  Уточнение владельца (2026-10-29, ответ на Q-01): «базовый» = прогон в среде сессии на состоянии, от которого
  ветвится срез; сравниваются `--out` и консоль байт в байт. Baseline в `skillCore/baseline/` пересобирается сессией в
  Linux в ветке среза 0 (те же четыре команды, коммит по `skillCore/`), строка о корне полигона входит в baseline;
  после этого сравнение с baseline байт в байт. Строки, зависящие от даты, перечисляются в сдаче отдельно.
- Тесты: новое падение против базового списка → остановка.
- Провал пары A/B по SC-05 → остановка с таблицей.
- Дифф содержит файл вне объёма SC-01 → остановка.
- Остановка — это сдача «НЕ ГОТОВО» с причиной, не тихий откат и не обход.
