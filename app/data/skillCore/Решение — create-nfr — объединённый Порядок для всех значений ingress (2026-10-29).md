# Решение: `create-nfr` — объединённый «Порядок» для всех значений `ingress`

Дата: 2026-10-29. Контекст: Q-03 среза 2 — у `create-nfr` две полные параллельные процедуры («Шаги `ingress: reverse` и
`ingress: update` по переносу» 1–15; «Шаги `ingress: forward`» 1–9), общие действия записаны разными словами с режимными
деталями внутри. Решение владельца по Q-03: вариант (а) сейчас (исключение в SC-01), объединённый «Порядок» — отдельным
решением с текстом на утверждение. Этот файл — такой текст. После утверждения применяется облачной сессией дословно
(срезом 4 или отдельным срезом), с проверками как у любого среза.

## 1. Принцип слияния

- Каждый шаг каждого из двух списков имеет ровно одно место в новой структуре: либо «Вход reverse», либо «Вход forward»,
  либо шаг «Порядка» (сам или оговоркой «при `ingress: …`»). Таблица соответствия — раздел 3; шагов без места нет.
- Общая формулировка берётся из reverse-списка (он полнее); forward-специфика добавляется оговорками «при
  `ingress: forward`: …» в тот же шаг. Формулировки оговорок — дословно из forward-шагов.
- Значения `ingress` (`reverse`, `update`, `forward`, `mixed`) — поле шапки НФТ, не переименовываются; в заголовках
  подразделов «Вход» остаются в скобках.
- Абзацы, не являющиеся шагами (роли файлов, `baseline` по флагу, «человек в цикле», `update` после Forward), получают
  дом рядом с тем режимом, к которому относятся.

## 2. Целевая структура файла

```
# Скилл: создать нефункциональные требования         (как есть)
<вводный абзац>                                        (как есть)
## Вход                                                (как есть + пункт чтения шаблона — см. 4.1)
### Вход reverse (режим A; ingress: reverse, update по страницам переноса)
### Вход forward (режим B; ingress: forward, update после Forward)
## Gate                                                (как есть, место — после подразделов «Вход»)
## Порядок                                             (новый, 1…9 — см. 4.2)
## Самопроверка                                        (как есть)
## Выход аналитику                                     (как есть)
```

## 4. Текст (дословно к применению)

### 4.1. Дополнение к `## Вход`

В конец списка «Вход» (перед «Недостающее — спроси до начала.»):

```
- Прочитай индекс `_meta/templates/nfr.md`, `_meta/templates/nfr/_common.md` и `_meta/templates/nfr/glossary.md` с диска; по мере записи каждой страницы — соответствующий `_meta/templates/nfr/nfr-<код>.md`.
```

### Вход reverse (режим A; `ingress: reverse`, `update` по страницам переноса)

```
1. Классифицировать каждый файл: `navigation`, `content`, `reference-only`, `baseline`, `instruction`, `not-nfr`.
2. Прочитать frontmatter источника. HTML-таблицы нормализовать в `sandbox/` средством `_meta/tools/normalize_tables.py`, если оно уже применяется к другим типам. Развернуть объединение по вертикали, сохранить смысл объединения по горизонтали.
3. Учесть фразы над таблицами.
4. Собрать исходящие ссылки и владельцев значений.
5. Разметить фрагменты: норма, ссылка, пробел, результат оценки, навигация, вне типа, ненормативный замер. Каждому нормативному фрагменту назначить код каталога и H2/колонки шаблона типа (по [`glossary.md`](../templates/nfr/glossary.md) и `nfr-<код>.md`) или пометить неоднозначность. Ненормативный замер и неоднозначность — в отчёт, не в чистовую страницу. Раздела «Текущее состояние и свидетельства» не создавать.

Инструкция и `not-nfr` файл сами по себе страниц не наполняют, но при наличии хотя бы одной контентной/навигационной страницы захода полный каталог создаётся. `reference-only` нормы не создаёт (тип остаётся скелетом). `baseline` обрабатывается только при флаге. Черновик единых НФТ без явной команды — сообщение в отчёте, не документ сервиса.
```

### Вход forward (режим B; `ingress: forward`, `update` после Forward)

```
1. Проверить, что передан ровно один содержательный вход. БТ прочитать в переданном формате, включая Word, без перевода в Markdown до захода. Постановку прочитать как файл аналитика. Зафиксировать путь этого входа. Оба входа или ни одного — остановиться и спросить, каталог не создавать.
2. Выделить кандидаты: ограничение качества, порог, политика, ненормативный замер, функциональное требование, вне объёма. Ненормативный замер на страницу не писать — только в отчёт.
3. Назначить код каталога по глоссарию составляющих или пометить неоднозначность. Неоднозначное на страницу не писать как норму.

Человек в цикле обязателен. Скилл оставляет черновик и не мержит. Аналитик подтверждает неоднозначности и не добавляет чисел, которых не было во входе. Ревьюер сверяет BRD-6.5 с входами.

`ingress: update` после Forward перечитывает тот же содержательный вход, сохраняет номера, не меняет `ingress` страницы и дополняет отсутствующие типы скелетом.
```

### 4.2. `## Порядок`

```
1. Собрать строки и пункты **по** `_meta/templates/nfr/nfr-<код>.md`. Материал одного кода сложить в один файл. При `ingress: forward`: функциональный критерий — решение «отклонено»; число без оператора не дополнять выдуманным оператором; показатель и значение — только из переданного входа.
2. Назначить номера: новые фрагменты получают следующий свободный. При `update`, а также при дописывании уже существующей страницы типа, уже выданные номера сохранить.
3. Для **каждого** из 18 кодов: если материала нет — записать страницу-скелет по шаблону типа (обязательные H2/строки/пункты, ячейки `не выявлено` / `требует уточнения`, ID у каждой строки/пункта). Если материал частичный — заполненные группы из входа, недостающие обязательные группы — скелетом. Если страница типа уже есть — дописать строки, недостающие группы — скелетом; совпадение объекта, показателя и значения — вопрос в отчёте, не вторая строка.
4. Записать страницы байтами с LF. У **каждой** страницы типа `title` и H1 — русское имя типа из каталога (как `nfr_type`), не title страницы-источника. Поле `ingress` страницы: `reverse`, пока на ней нет строк генерации; если при `ingress: forward` на странице уже есть строки переноса — `mixed`. При `ingress: reverse`/`update` по страницам переноса: `confluence_page_ids` — страницы захода. При `ingress: forward`: поле `source_artifacts` не ставить.
5. Каждую ячейку/пункт с `не выявлено` или `требует уточнения` записать долгом матрицы; цитата — дословно со страницы: `| nfr-<код> | — | «не выявлено» |` или `| nfr-<код> | — | «<заголовок H2>» |`. В `open-questions.md` пробел не пишется. Ссылку `OQ-` на странице не ставить.
6. Ссылки и долги — по шаблону, затем `python _meta/tools/link_debts.py --matrix <матрица> --docs <docs>`.
7. Обновить реестр `output/<service>/nfr/README.md` (все 18 строк + статус `заполнено` / `частично` / `не выявлено`) и матрицу BRD-6 (включая строки скелета в BRD-6.2; при `ingress: forward` — также BRD-6.5 с видом `скелет` для строк скелета). При заполнении BRD-6.2 для каждой строки **однозначно** сопоставить объект с существующей FUN по правилам шаблона (раздел BRD-6.2): один кандидат — ссылка в `SRS-реализация`; ноль или несколько — `—`, неоднозначности в отчёт. Функции не создавать. `BRD-связь` не угадывать. В `docs/brd/README.md` каталог НФТ не вкладывается. Корневой `docs/README.md`: если файла нет — [`create-docs-readme`](create-docs-readme.md) в режиме `create`. Если файл есть, полный `sync` не вызывать: дописать ветку `nfr` в «Как читать», таблицу префиксов, «Разделы» и «Дерево», и подраздел «Долги по ссылкам», когда в матрице есть долги. Местные разделы README не пересобирать.
8. Самопроверка ниже; при `ingress: forward` — также гейты BRD-6.5 из шаблона.
9. Отчёт аналитику: резюме до 10 строк и спорные места в форме «вопрос / предположение / что проверить», счётчики `заполнено` / `частично` / `скелет`; связи BRD-6.2 с FUN (связанных / без связи / неоднозначных). При переносе (`reverse`/`update` по страницам) дополнительно: число входных страниц по ролям; все 18 `nfr-<код>` и статус наполнения; число строк и пунктов; отложенные ненормативные замеры (не на странице); ссылки и долги; пробелы скелета; разрезанные составные ячейки; склеенные входы; неоднозначности типа; новые долги пробелов; гейты BRD-6; изменённые файлы; сохранённые и вновь выданные номера. При `ingress: forward` дополнительно: созданные ID, статусы 18 типов, отклонённые кандидаты, пробелы, вопросы по дублям и типам, что проверить человеку. Длиннее контракта выхода `create-artifact` отчёт не пишется.
```

## 5. Развилки для владельца

- **Р-1 — `link_debts.py` для forward.** В forward-списке шага «Ссылки и долги — по шаблону, затем `link_debts.py`» не было;
  в объединённом «Порядке» он общий (шаг 6). Для forward это добавление поведения — положительное (сторож долгов
  прогоняется всегда) и безопасное (утилита только проверяет). Рекомендация: оставить общим; альтернатива — оговорка «при
  переносе» (сохраняет forward как было).
- **Р-2 — абзац «`update` после Forward».** Предложен дом «Вход forward» (вход тот же содержательный документ). Альтернатива
  — отдельный абзац после подразделов «Вход» (режим `update` как третий). Рекомендация: «Вход forward».
- **Р-3 — проверка применения.** Пары A/B для `create-nfr` в SC-05 нет; предложение: без пары, приёмка по таблице раздела 3
  (каждая строка исходных списков имеет место, оговорки дословны) + штатные проверки среза (SF, selfcheck, pytest, SC-03).
  Альтернатива — один сухой прогон forward на полигоне с БТ: дорого и без плеча «до» неинформативно.
- **Р-4 — когда применять.** Рекомендация: в срезе 4 (`skill-core/4-docs`) отдельным коммитом по `canon/` — до
  окончательной редакции `create-skill.md`, чтобы исключение в SC-01 снять в том же срезе. Альтернатива — отдельный срез 3а
  между 3 и 4.

**Утверждено владельцем 2026-10-29: да по Р-1…Р-4.** Текст раздела 4 уходит в постановку среза 4 (применение дословно,
связки — только те, что в таблице раздела 3); исключение `create-nfr` в SC-01 снимается по сдаче среза 4.
