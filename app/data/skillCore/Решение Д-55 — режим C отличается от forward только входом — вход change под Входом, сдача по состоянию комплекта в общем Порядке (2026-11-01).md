**Статус:** РЕШЕНИЕ ВЛАДЕЛЬЦА 01.11 («Вариант 2»). ИСПОЛНЕНО В КАНОНЕ 01.11 (срезы 1–2: коммит `14d5226`,
master `2b0f93e`; прибор analyzer `8b2ae51f`); остаток — копия прибора в канон (MR), прогон полигона, сообщение командам,
закрытие трека. Исполнение — трек «change-input»
(`План трека change-input — вход change, общий Порядок, потребители номеров шагов (2026-11-01).md`,
этот каталог). Запись по правилам Д-26: сценарии жизненного цикла — до правок, один дом у факта.
В канон идентификатор Д-55 не вписывается, формулировки самодостаточны.

## Контекст и проблема (канон master `3e65918`)

Диспетчер `_meta/skills/create-artifact.md` после переворота структуры (п. 1 предложения 28.10, трек skillCore)
устроен так: «Вход» с подразделами «Вход reverse (режим A)» и «Вход forward (режим B)» → общий «Порядок»
(5 шагов, 13 строк) → раздел «Режим C — change (изменение по постановке)» (8 шагов, 135 строк) → «Повторный
заход» → «Границы скоупа» → «Правила всех режимов». Вопросы владельца 01.11 вскрыли три расхождения текста с
замыслом «режимы различаются только входом, артефакт и выход одинаковы»:

1. **Асимметрия формы.** Пункт «Режим:» во «Входе» перечисляет три равноправных режима, но у третьего нет
   подраздела входа — «см. ниже», и его вход (постановка, разбор по домам, вопросы) описан внутри раздела C.
2. **Две параллельные процедуры.** Шаги 4–8 раздела C (правки, матрица, происхождение, самопроверка с гейтом,
   отчёт дельты) — собственный порядок режима, совпадающий с общим «Порядком» в шагах «документ по шаблону» и
   «матрица». Преамбула C говорит «„Порядок“ и правила всех режимов действуют, кроме сверки с выгрузкой» — это
   неточно: шаги 3–5 «Порядка» (чек-лист, резюме, коммит) в C заменены. Процедуры уже разошлись: в C нет шага
   «чек-лист шаблона», в «Порядке» нет шага «самопроверка и гейт».
3. **Форма сдачи приписана режиму, а вытекает из состояния комплекта.** Отчёт дельты в описании MR нужен потому,
   что комплект уже принят и правится через MR; то же уместно при forward-правке принятого комплекта и при
   reverse-правке по свежей выгрузке после переноса (гид, раздел «Изменение по постановке»: «правки по новым
   выгрузкам тоже делаются в `docs-*`, reverse-скиллами с источником из архива»). Сегодня текст не говорит, чем
   сдавать такие заходы.

Что из различий C действительно следует из входа (подтверждено владельцем 01.11): вопросы до правок, а не после
(когда дано «что именно править», неясности снимаются до работы); происхождение каждого факта (постановка хранится
дословно строками `T-<JIRA-ID>-NN`, на которые можно сослаться).

## Решение

1. **Подраздел `### Вход change (режим C)` под «Входом»** — рядом с A и B. Содержимое — нынешние шаги 1–3 раздела
   C дословно (постановка в `tasks/<JIRA-ID>.md` и подтверждение; разбор постановки по домам и затронутые карточки;
   вопросы до правок). Завершается строкой «Далее — „Порядок“ целиком», как у forward.
2. **Общий «Порядок» — один линейный список для всех трёх режимов.** Шаги, различающиеся по состоянию комплекта,
   ветвятся ВНУТРИ шага по проверяемому признаку, а не выносятся в отдельные разделы. Состав после правки:
   документ строго по шаблону (сюда — «каждый факт только в своём доме из „Фактов по домам“», ID по реестру без
   перенумерации, frontmatter без `confluence_page_ids` у карточек без источника, удаление только по явному
   действию — нынешний шаг 4 режима C) → матрица трассировки (как сейчас) → чек-лист шаблона (как сейчас; в режиме
   C восстанавливается) → самопроверка перед сдачей: `selfcheck`, `link_debts`, гейт (`transfer_gate` — режим
   репозитория документации включается сам; `NOT READY` — не сдаётся; нынешний шаг 7 режима C, в каркасе
   `create-skill` этот шаг уже есть) → сдача: **новый комплект** — резюме до 10 строк и спорные места (как сейчас);
   **принятый комплект, правка через MR** — отчёт дельты по шаблону `delta-report.md` в описание MR, строгий порядок
   сдачи и сторож `--check`, у каждого нового факта происхождение (нынешние шаги 6 и 8 режима C дословно; при
   заходе по постановке — из `T-<JIRA-ID>-NN`, при заходе по выгрузке — страница источника) → коммит только по
   просьбе; при MR approve = акцепт.
   Признак «принятый комплект» (Р-1, рекомендация): репозиторий документации `docs-<service-id>` — матрица
   трассировки в корне, каталога `docs/` нет (тот же признак, что у гейта и правила слоёв); наличие
   `tasks/<JIRA-ID>.md` уточняет источник происхождения, но не включает отчёт дельты сам по себе.
3. **Раздел `## Режим C — change (изменение по постановке)` сохраняется** — заголовок остаётся точкой входа
   скилла `/change` для Cursor и строк «Исполняй шаги режима C» в надстройках типов. Содержимое сжимается до:
   когда применяется (комплект перенесён в `docs-*`, `src-*` заморожен, задачу ставит аналитик — ЧТО и ЗАЧЕМ,
   агент — КАК); состав захода одной строкой — «Вход change» → «Порядок» целиком → надстройка «Режим C» скилла
   типа; запреты режима (как сейчас); признак начатого forward (`tasks/`) и ссылка на гид. Порядка 20 строк
   вместо 135. Старые копии `.cursor/` у команд продолжают работать: они открывают этот раздел и видят состав.
4. **Ссылки на номера шагов режима C становятся именованными.** Сегодня «режим C, шаг 2» — `_meta/rules/questions.md`
   :13, `_meta/templates/task.md` :54 и :73, `_meta/tools/delta_report.py` :83, :968, :1325 (два комментария и одно
   сообщение пользователю); «режим C, шаг 6» — 13 скиллов типов (одна и та же строка «у каждого нового факта —
   происхождение (режим C, шаг 6)»). После правки: «„Вход change“, шаг „Разбор постановки“» и «„Порядок“, шаг сдачи
   (происхождение факта)». Номера шагов в ссылках больше не используются — образец уже есть в create-artifact
   («как в „Порядке“, шаг матрицы трассировки»).
5. **Каркас в `create-skill.md`** получает подраздел `### Вход change (режим C)`, в «Порядке» каркаса — ветвь сдачи
   по состоянию комплекта; строка таблицы разделов `## Режим C — change` и пункт чек-листа скилла — по новому
   составу. Надстройки типов (типовые задачи, карта затронутых карточек, обязательные вопросы, идентификаторы)
   по содержанию не меняются — только строка-ссылка п. 4.
6. **Потребители вне диспетчера:** скилл Cursor `_meta/templates/cursor/skills/change/SKILL.md` п. 1 — «раздел
   „Вход change (режим C)“, затем „Порядок“ целиком и „Режим C — change“ (состав и запреты)», п. 2 — перечень
   скиллов типов дополняется до 14; гид `_meta/migration/reference.md`, раздел «Изменение по постановке» — фраза
   «Порядок захода — скилл `create-artifact`, режим C» → «вход change и общий „Порядок“ скилла `create-artifact`».
   Копии `.cursor/` у команд обновляются командой установки из README шаблона — сообщение командам.

## Развилки владельцу (рекомендации — первыми)

**Решение владельца 01.11: «по развилкам — рекомендации»** — Р-1 (а) раскладка `docs-*`, Р-2 (а) долг прибору,
Р-3 заголовок сохранить. Трек запущен 01.11 (срезы 1–2 и `delta_report.py` — сессия «Правки прибора, акцепт и рутина», по очереди; отдельная сессия переноса не заводится — решение владельца).

- **Р-1. Признак «принятый комплект» для ветви сдачи.** (а) репозиторий документации `docs-*` (матрица в корне,
  `docs/` нет) — рекомендую: один признак с гейтом и правилом слоёв, проверяется раскладкой; (б) наличие
  `tasks/<JIRA-ID>.md` — покрывает только режим C, сценарий «reverse по свежей выгрузке» остаётся без формы сдачи.
- **Р-2. Отчёт дельты без постановки** (сценарий reverse на `docs-*`): если `delta_report.py` требует `--task`,
  вариант (а) долг прибору «отчёт дельты без `--task`: происхождение — страница источника», до закрытия —
  резюме плюс ссылка на дельту git; (б) постановка-заглушка `tasks/<JIRA-ID>.md` «перенос изменений страницы N» —
  не рекомендую: постановки аналитика нет, файл будет выдуман.
- **Р-3. Заголовок раздела C.** Сохранить дословно (рекомендую: точка входа Cursor и 13 надстроек) или
  переименовать в «Режим C — change: состав и запреты» с правкой всех ссылок.

6. Фраза «Коммит и MR — человек; approve = акцепт» — один дом, шаг коммита «Порядка».
