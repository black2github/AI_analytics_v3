# Постановка для облачной сессии: `delta_report.py` и сторож `tasks/` в гейте (срез С2 трека «Forward без платформы»)

Дата: 2026-10-15. Репозиторий: `https://github.com/black2github/AI_analytics_v3.git`, работать в
ветке **`cloud/delta-report`** от `main` (в `main` не коммитить: его правят локальные сессии).
Результат — ветка с коммитами, готовая к слиянию; слияние, копия утилиты в канон и живой прогон на
комплектах делаются локально, вне облака. Эта постановка самодостаточна: ничего за пределами
репозитория не нужно.

## 0. Контекст в трёх абзацах

Канон миграции аналитики Экосистемы (Doc-as-Code) описывает сервис комплектом markdown-карточек с
устойчивыми идентификаторами (`ENT-001`, `SCR-CL-02`, `CTL-AGR-012`, `FUN-SYS-03`…) и матрицей
трассировки `traceability-matrix.md` (реестр ID, связи, раздел долгов «Долги по ссылкам»). Прибор —
каталог `app/scripts/CI/` этого репозитория: `selfcheck.py` (сверка карточек), `link_debts.py`
(долги матрицы), `transfer_gate.py` (гейт готовности комплекта к подключению к платформе), тесты в
`tests/test_*.py`.

Решение владельца 2026-10-15 (реестр решений, запись Д-43, файл
`app/data/Реестр решений по ядру скиллов.md`, раздел «## Д-43.»): после миграции комплект в целевом
репозитории `docs-<service-id>` (комплект лежит в корне: `README.md`, `traceability-matrix.md`,
`srs/…`) развивается задачами аналитика без платформы, режим «изменение по постановке»: аналитик
ставит задачу, агент правит карточки по правилам. Постановка хранится в `tasks/<JIRA-ID>.md`
(frontmatter `type: task`, `task: <JIRA-ID>`; строки `T-<JIRA-ID>-NN`). Объект акцепта — **отчёт
дельты** в описании MR. Его и должен собирать прибор: детерминированную часть (файлы, ID, матрица,
затронутые карточки, проверки), а агент дописывает только происхождение фактов.

Форма отчёта зафиксирована шаблоном канона (копия ниже, раздел 3). Вторая, маленькая задача —
сторож в гейте: после первого forward-захода повторный перенос комплекта поверх `docs-*`
запрещён, признак начатого forward — каталог `tasks/` в репозитории назначения.

## 1. Задача A — утилита `app/scripts/CI/delta_report.py`

Назначение: по изменениям рабочего дерева репозитория документации относительно базы (по умолчанию
`master`, иначе `--base <ref>`) собрать отчёт дельты в markdown по шаблону раздела 3. Read-only:
ничего в репозитории не меняет, пишет отчёт в stdout и/или в файл `--out`. Зависимости — только
стандартная библиотека и `git` в PATH (закрытый контур: новых пакетов не вводить). Кодировка —
`encoding="utf-8"` везде явно, пути через `pathlib`, переводы строк в выходном файле — `\n`.

Ключи:

```
python app/scripts/CI/delta_report.py --repo <корень клона docs-репозитория> [--base master]
      [--task <JIRA-ID>] [--out <файл.md>] [--json]
```

- `--repo` — корень репозитория документации; комплект в корне (`traceability-matrix.md` там же).
  Если каталог `docs/` есть, а матрицы в корне нет (рабочий репозиторий миграции) — корень
  комплекта `docs/`; поддержать оба случая так же, как `transfer_gate.detect_layout`.
- `--base` — ref, относительно которого считается дельта (`git diff --name-status <base>` плюс
  незакоммиченные изменения и неотслеживаемые файлы: `git status --porcelain`); по умолчанию
  `master`, если его нет — `main`, если нет и его — только рабочее дерево против `HEAD`.
- `--task` — `JIRA-ID`; если не задан, берётся из единственного изменённого или нового файла
  `tasks/*.md`; если таких несколько и ключ не задан — сообщение и код 2.
- `--out` — записать отчёт в файл; `--json` — дополнительно напечатать данные в JSON.
- Код выхода: 0 — отчёт собран; 2 — отчёт собрать нельзя (не git-репозиторий, матрицы нет,
  неоднозначная задача). Отчёт с замечаниями (дубли ID, карточка вне реестра) — всё равно код 0:
  это вход для человека, не гейт; замечания — отдельным блоком «Замечания прибора» в конце.

Что считать и как (переиспользовать существующее, не дублировать):

1. **Изменённые файлы.** Из `git diff --name-status` и `git status --porcelain`: статус создан /
   изменён / снят / переименован. Для каждого `.md` с frontmatter — `id` или `partOf` и `type`
   через `selfcheck.read_frontmatter(path)` (возвращает плоский словарь строк; `{}` — frontmatter
   нет, `None` — битый). Для файлов `tasks/*.md` — отдельная строка «постановка», в таблицу
   карточек не включать; `selfcheck.is_task_file(path, docs_root)` уже есть.
2. **Идентификаторы.** Новые ID — `id` из frontmatter созданных карточек плюс новые строки реестра
   матрицы; снятые — ID удалённых карточек. Реестр читать через `link_debts.parse_matrix(text)`:
   возвращает `(registry, debts)`, где `registry: {ID: (тип, файл)}`, `debts: [(from_ids, тип,
   имя|None, владелец|None, строка)]`. Сверка: каждый новый ID карточки есть в реестре (иначе
   замечание «карточка вне реестра»), дублей ID в реестре нет, ID из реестра, которого нет на
   диске, — замечание. Для внутренних идентификаторов карточек (`FLD-N`, `EV-N`, `B-N`, `MSG-N`,
   `CTL-NNN` внутри файлов контролей) — считать добавленные заголовки `### <ID>.` в диффе
   изменённых карточек: регулярное выражение по строкам `+### ` диффа.
3. **Матрица трассировки.** Из диффа `traceability-matrix.md` (текущее против базы): добавленные и
   снятые строки реестра ID, строки других разделов (связи), строки раздела «Долги по ссылкам»
   (две формы строки: «нет целевого артефакта …» и «долг <вид>: «…» — …»; разобрать через
   `link_debts.parse_matrix` по тексту добавленных строк, вид долга — `link_debts.issue_fields(row)`
   для второй формы).
4. **Затронуто.** Карточки, которые ссылаются относительной ссылкой на изменённые или созданные
   карточки, — через `transfer_gate.card_referrers(root)` (возвращает `{ID: [ID…]}`, матрица и
   README не считаются). Для каждой изменённой карточки — список ссылающихся и пометка, изменена
   ли ссылающаяся в этой же дельте.
5. **Факты и происхождение.** Прибор заполняет только колонки «Факт» и «Где» заготовкой:
   добавленные строки диффа изменённых карточек, которые выглядят как факт (строки таблиц `| … |`,
   пункты списков `- **…**`, заголовки `### `), с указанием файла и ID; колонка «Происхождение» —
   пустая, её дописывает агент. Строки без смысла (пустые, разделители таблиц, frontmatter) не
   включать. Ограничить 200 строками с пометкой «…ещё N».
6. **Открытые вопросы.** Из файла постановки `tasks/<JIRA-ID>.md`: строки таблицы раздела «Вопросы
   и ответы» с ответом `—` и строки долгов вида «открытый вопрос» из п. 3.
7. **Проверки.** Запустить не нужно; в отчёте — блок-заглушка «Проверки: selfcheck …; link_debts …;
   гейт …» с пустыми местами для результатов (их вписывает агент после прогона). Прибор только
   проверяет, что файл постановки существует и его frontmatter содержит `type: task` и `task:`
   с тем же `JIRA-ID`; иначе замечание.

Заголовок файла утилиты — как у `link_debts.py`: комментарий с назначением, ключами и
ограничителями (по-русски, в стиле соседних утилит; см. первые 40 строк `link_debts.py` и
`transfer_gate.py`). Функции с докстрингами, читаемые имена; `main()` с `argparse`, русские
подсказки; `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` перед печатью (как в
`transfer_gate.main`). Импорт соседей — как в `selfcheck.py`:
`sys.path.insert(0, str(Path(__file__).resolve().parent))`, затем `import link_debts as ld`,
`import selfcheck as sc`, `import transfer_gate as tg`.

## 2. Задача B — сторож `tasks/` для `--out` в `transfer_gate.py`

В `run_gate` (файл `app/scripts/CI/transfer_gate.py`) при заданном `--out`, если каталог
`<out>/tasks` существует, — добавить строку гейта `✗ [TRF-02] в репозитории назначения есть
каталог tasks/ — forward-развитие уже начато, повторный перенос поверх запрещён (правило:
после закрытия миграции правки делаются в docs-репозитории)` через `gate.add("✗", "TRF-02", …,

Проверку делать там, где сейчас проверяется `check_target_repo` (для режима рабочего репозитория;
в режиме репозитория документации `--out` и так отклоняется). Существующие тесты
`tests/test_transfer_gate.py` должны остаться зелёными.

## 3. Форма отчёта дельты (копия шаблона канона `_meta/templates/delta-report.md`)

```markdown
# Отчёт дельты: <JIRA-ID> — <имя задачи>

Постановка: `tasks/<JIRA-ID>.md`, строки `T-<JIRA-ID>-01…NN`. Комплект
`<service-id>`, ветка `<ветка>`, база `<коммит целевой ветки>`.

## Изменённые файлы

| Файл | Действие | Карточка |
|---|---|---|
| `srs/screen-form/…` | изменён | `SCR-…` |
| `srs/control/…` | создан | `CTL-…` |

## Идентификаторы

Новые: `<ID>, …` (по реестру матрицы, дублей и пропусков нет). Снятые: `—`.

## Матрица трассировки

Новые строки реестра: … Связи: … Долги: … (строки долга вида «открытый
вопрос» — по вопросам без ответа).

## Затронуто

<Карточки, которые ссылаются на изменённые; меняются ли они и почему нет.>

## Факты и происхождение

| Факт (что записано) | Где | Происхождение |
|---|---|---|
| <поле «…», обязательное, формат …> | `SCR-…`, FLD-N | T-<JIRA-ID>-01 |
| <тип атрибута …> | `ENT-…` | `ENT-…` (комплект) |
| <текст сообщения …> | `CTL-…` | вопрос 1 → T-<JIRA-ID>-02 |

Происхождение — одно из четырёх: `T-NN` (постановка), ID карточки (комплект),
адрес внешнего доказательства (репозиторий, SHA, файл — пока не используется),
номер вопроса. Строк без происхождения в таблице быть не должно.

## Открытые вопросы

<Вопросы без ответа и заведённые по ним долги; «нет» — если нет.>

## Проверки

`selfcheck`: …; `link_debts`: …; гейт переноса (режим репозитория
документации): `READY` / `NOT READY` — отчёт приложен.
```

Имя задачи — из заголовка `# <JIRA-ID>. <имя>` файла постановки; `<service-id>` — из frontmatter
`service` постановки или любой карточки; ветка и база — из git (`rev-parse --abbrev-ref HEAD`,
`rev-parse --short <base>`). Блок «Замечания прибора» добавляется после «Проверки», только если
замечания есть.

Образец формата строк долга (для разбора и для фикстур):

```
| FUN-CL-01 | — | нет целевого артефакта process «Выпуск» — требуется заход create-process |
| FUN-CL-01 | — | нет целевого артефакта data-model «Карта» у владельца cards — требуется заход create-data-model |
| PROC-AGR-005 | — | долг открытый вопрос: «Что такое сегмент» — причина: определения нет; ответственный: аналитик lk-mp; ограничение: шаги доступа к сегменту; закрытие: определение в глоссарии; источник: OQ-033 |
```

## 4. Тесты — `tests/test_delta_report.py` (новый) и дополнение `tests/test_transfer_gate.py`

Запуск (локальная машина; в облаке — обычный `python -m pytest`):

```
PYTHONPATH="$PWD" PYTHONIOENCODING=utf-8 python -m pytest tests/test_delta_report.py tests/test_transfer_gate.py -q -o addopts=""
```

Фикстура: временный git-репозиторий (`git init`, `user.name`/`user.email` через `git -c`, ветка
`master`), в нём комплект в корне: `README.md`, `traceability-matrix.md` с реестром (`| ID | Тип |
Наименование | Файл |`, строки `| SCR-CL-02 | screen-form | Форма | srs/screen-form/scr-cl-02.md |`
и т. п.), две-три карточки с frontmatter (`id`, `type`, `service`, `title`), базовый коммит; затем
рабочие изменения: правка карточки (новый `### FLD-3. …`), новая карточка с новой строкой реестра,
новая строка долга «открытый вопрос», файл `tasks/ECO-123.md`. Образцы фикстур и стиля — `make()` и
`setup_docs()` в `tests/test_link_debts.py`, `make_src()`/`make_docs_repo()`/`_w()` в
`tests/test_transfer_gate.py` (`_run` там вызывает `run_gate` с `no_validator=True`).

Обязательные тесты, каждый — на срабатывание и на НЕсрабатывание, где есть обе стороны:

1. изменённые файлы: созданная, изменённая, снятая карточка и постановка попадают в нужные строки;
   файл `tasks/` в таблице карточек отсутствует;
2. идентификаторы: новый ID есть в реестре — без замечаний; новый ID без строки реестра —
   замечание «карточка вне реестра»; дубль ID в реестре — замечание; внутренний `### FLD-3`
   добавленной строкой диффа — в списке новых внутренних идентификаторов;
3. матрица: добавленные строки реестра, связей и долгов разнесены по трём группам; долг второй
   формы распознан как «открытый вопрос» с ответственным;
4. затронуто: карточка, ссылающаяся на изменённую, перечислена; ссылающаяся и сама изменённая —
   с пометкой; матрица и README не считаются;
5. факты: заготовка содержит добавленную строку таблицы и пункт списка из диффа карточки,
   колонка происхождения пуста; строки frontmatter и разделители таблиц не попали;
6. открытые вопросы: вопрос с ответом `—` из постановки и долг «открытый вопрос» перечислены;
   вопрос с ответом `T-ECO-123-02` — нет;
7. `--task` не задан, одна постановка в дельте — определяется сама; две постановки — код 2 и
   понятное сообщение; постановка без `type: task` — замечание;
8. `--base` отсутствует в репозитории (`master` нет, есть `main`) — отчёт строится от `main`;
   не git-репозиторий — код 2;
9. `--out` пишет файл в UTF-8 с `\n`, содержимое начинается с `# Отчёт дельты: ECO-123`; `--json`
   содержит ключи `files`, `ids`, `matrix`, `affected`, `facts`, `questions`, `notes`;
10. задача B: `--out` в каталог с `tasks/` — строка `✗ [TRF-02] … tasks/ …`, копирования нет
    (`NOT READY`); без `tasks/` — поведение прежнее (существующие тесты `test_out_only_when_ready`,
    `test_out_target_without_codeowners_blocks` зелёные).

## 5. Ограничители и стиль

- Асимметрия ошибок: лучше лишняя строка в отчёте или замечание, чем молчаливый пропуск. Файл,
  который не удалось прочитать или разобрать, — строка в «Замечаниях прибора», не исключение.
- Не трогать `link_debts.py`, `selfcheck.py` и логику `transfer_gate.py` вне задачи B; не менять
  существующие тесты, кроме добавления новых.
- Комментарии в коде — по-русски, в стиле соседних файлов; о следе источника писать «происхождение», не калькой с английского provenance. Переводы строк в исходниках — `\n`.
- Коммиты в ветке `cloud/delta-report`: один на утилиту с тестами, один на задачу B с тестами;
  сообщение коммита — по-русски, первая строка — что сделано; в конец сообщения добавить строку
  `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- Сдача — текст в ответе сессии: число тестов passed/failed по команде из раздела 4 (весь набор
  `tests/`), список файлов ветки, известные ограничения утилиты, если есть.
