# Цикл обратной связи команд сервиса по сгенерированному AI-aware комплекту

> ВАЖНО: это временный подход на время пилота. Вытаскивание аналитики из хронологии легко сломает 
> эту картину. Поэтому здесь играемся на ПРОМ-срезе и потом переезжаем в рабочий репозиторий. 
> Только после этого можно будет без последствий вытаскивать аналитику по задачам по мере реализации.

Рабочий инструмент пилота. Канал замечаний — двухпоточный: 
- **основной — инлайн-треды MR в GitLab** (привязка к строкам, статусы resolve,
переживают перегенерацию); 
- **запасной — `feedback.md`** в ветке отдачи
(для замечаний «вне строк» и участников, не работающих в MR).
Единая источник правды о судьбе замечаний — сам комплект (правки +
`open-questions.md`); треды MR и `feedback.md` — только каналы приёма
замечаний, состояние в них не хранится дольше цикла прогона.

> Команды ниже даны для PowerShell.

## Роли и права (фиксируются при старте)

- **Аналитик-эксперт (владелец конвейера):** генерирует и правит комплект
  `docs/` целиком (карточки, реестры, матрицу трассировки
  `docs/traceability-matrix.md`) и реестр `open-questions.md` в корне
  репозитория; ставит статус «исправлено» замечаниям.
- **Команда сервиса:** пишет инлайн-комменты в MR и записи в
  `feedback.md`; в ветке отдачи правит ТОЛЬКО `feedback.md`;
  ставит resolve тредам и статус «принято»/«отклонение согласовано».
- Эксперименты аналитика живут в отдельных ветках и в цикл не попадают:
  команда видит только ветку отдачи и её MR.

## Фаза 0. Разовая настройка (до первого цикла)

- **Один раз на группу GitLab:** создать групповую метку
  `analytics-review` (группа EAN → Manage → Labels → New label).
  Групповая — потому что видна во всех src-репозиториях; метка,
  созданная внутри одного проекта, сквозной фильтр по сервисам не даст.
- **Один раз на репозиторий сервиса:** `.gitattributes` с `* text=auto`
  первым коммитом ветки отдачи (диффы перегонов не шумят CRLF/LF).
- **Один раз для аналитика:** включить уведомления. Терминология
  GitLab: «проект» = один репозиторий, объединяет их «группа» —
  создавать отдельный контейнер под пилот не нужно, репозитории уже
  лежат в группе. Watch ставится либо на ГРУППЕ (колокольчик страницы
  группы → Watch — разом все её репозитории; удобно, если группа
  преимущественно пилотная), либо точечно на каждом src-репозитории.
  Плюс GitLab сам уведомляет участников MR независимо от Watch.

## Фаза A. Генерация и отдача (аналитик-эксперт, см. план проекта пилота)

1. **Ветка отдачи — ДО генерации** (единообразно `<svc>-runN`):

   ```powershell
   git -C C:\doc-as-code\EAN\src-<svc> checkout -b <svc>-run1 origin/trunk
   ```

2. **Генерация комплекта** заходами по канону; каждая приёмка —
   точечный коммит в ветку (`git add -- docs open-questions.md ...`,
   никогда `git add .`).

3. **Предотдаточная подготовка** (один коммит):
   - финальная самопроверка комплекта `selfcheck --out sandbox/selfcheck.txt`, вердикт OK или
     задокументированные ✗;
   - чистка служебного каталога: `git rm -r sandbox` (рабочая зона агентов — не часть комплекта);
   - `feedback.md` в КОРНЕ репозитория (рядом с `open-questions.md`, вне `docs/`) из шаблона ниже;

   ```powershell
   git -C C:\doc-as-code\EAN\src-<svc> add -- feedback.md
   git -C C:\doc-as-code\EAN\src-<svc> commit -m "Комплект к ревью: selfcheck OK, feedback.md заведён"
   ```

4. **Push ветки отдачи:**

   ```powershell
   git -C C:\doc-as-code\EAN\src-<svc> push -u origin <svc>-run1
   ```

5. **MR в GitLab** (web UI: Merge requests → New): source `<svc>-run1`
   → target `trunk`. Заголовок «Аналитика <сервис>: комплект docs/
   (прогон 1/2/3...)». В описании: состав комплекта, ссылка на правила записи
   замечаний (этот документ), вердикт selfcheck. Reviewers — команда
   сервиса; метка `analytics-review` — поле Labels формы MR (или
   сайдбар MR → Labels; сама метка — групповая, создана в Фазе 0).
   «Delete source branch» — СНЯТЬ. Draft не ставить. **MR создаётся,
   но НЕ вливается !!!** — он остаётся открытым на весь цикл ревью (иначе
   исправления перестанут обновлять его дифф); merge — только в фазе D
   по Approve, это и есть акт акцепта снапшота. Если MR влит
   преждевременно: замечания принимаются в нём же (треды в merged MR
   работают), исправления оформляются follow-up MR-ом из той же ветки.

## Фаза B. Ревью (команда сервиса)

6. Команда смотрит комплект **в MR, вкладка Changes** (переключаться
   на ветку локально не обязательно — GitLab показывает все файлы;
   локально: `git fetch; git switch <svc>-run1` — только читать).

7. Если **Замечание к конкретному месту** — инлайн-коммент в MR: Changes →
   строка → «Start a review» → …→ «Submit review» (пачка замечаний
   уходит одним уведомлением). Если **Замечание вне строк** (архитектурное,
   к комплекту целиком, от участника без привычки к MR) — записывать
   `FB-NN` в `feedback.md` и коммит в ту же ветку (команды ниже для последнего случая).
   `FB-NN` — идентификатор записи файла feedback.md (FB = feedback),
   по аналогии с `OQ-NN` реестра открытых вопросов; используется в
   сообщениях коммитов и ответах, чтобы судьба каждого замечания
   прослеживалась по истории:

   ```powershell
   git -C ...\src-<svc> switch <svc>-run1
   git -C ...\src-<svc> pull
   # правка feedback.md (append-only, шаблон ниже)
   git -C ...\src-<svc> add -- feedback.md
   git -C ...\src-<svc> commit -m "FB-03..FB-05: замечания по функциям"
   git -C ...\src-<svc> push
   ```

8. **Сигнал «ревью завершено»**: Submit review + итоговый коммент в MR
   «Ревью завершено: N инлайн-замечаний, M записей в feedback.md».
   Уведомление аналитику GitLab шлёт сам (участник MR); дополнительно
   аналитик держит Watch на проекте (колокольчик проекта → Watch).

## Фаза C. Обработка (аналитик-эксперт)

9. **Получение**: уведомление GitLab → треды читаются в MR;
   `feedback.md` приезжает обычным `git pull` по ветке отдачи.
   (Массовая выгрузка тредов при необходимости — GitLab API
   `/merge_requests/:iid/discussions`, токен с правом read_api.)

10. **Каждое замечание получает одну из трёх судеб:**
    - **правка** — мини-дозаход LLM-исполнителем: замечания команды
      включаются в промпт дозахода как легитимные ВНЕШНИЕ решения
      (это не «подсказки сверки» — это законные требования владельца сервиса);
      перегенерация затронутых карточек → selfcheck → приёмка-коммит
      «Замечания ревью run1: FB-03, тред !1#note_…» → push. MR
      обновляется сам, треды сохраняются (устаревшие строки GitLab
      помечает outdated, тред живёт);
    - **отклонение** — ответ в треде / статус в FB-записи с
      обоснованием; resolve НЕ ставим — его ставит автор замечания;
    - **вопрос к владельцу страницы Confluence** — запись в
      `open-questions.md` комплекта, в треде/FB — ссылка на OQ-NN.
    В тред исправленного замечания — ответ «исправлено в `<hash>`»;
    в FB-запись — статус `исправлено (<hash>)`.

## Фаза D. Подтверждение и закрытие (команда → обе стороны)

11. Команда проверяет исправления: тред → **Resolve**; FB-запись →
    статус `принято`. Цикл B→C→D повторяется, пока есть открытое.
12. **Закрытие прогона**: все треды resolved, все FB в терминальных
    статусах → команда ставит **Approve**, аналитик делает **Merge в
    trunk** (акцептованный снапшот комплекта; исходная ветка не
    удаляется — история прогона). Чистовая перегенерация в рабочий
    AI-aware репозиторий стартует от этого снапшота, и цикл там
    повторяется в той же модели (MR + `feedback.md`).

## Новый прогон и эксперименты

- Новый прогон = `<svc>-run2` от `trunk` + НОВЫЙ MR; `feedback.md`
  начинается пустым — несогласованный остаток run1 к этому моменту уже
  живёт в комплекте записями OQ (правда переезжает с комплектом; треды
  и feedback-файл прошлого прогона не копируются — остаются историей
  своего MR и ветки).
- Ветки экспериментов аналитика-эксперта (`<svc>-exp-*`) в GitLab не
  ревьюируются и командой не отслеживаются — цикл обратной связи они
  не рвут.

## Обновление исходной аналитики (один репозиторий, до переезда на два)

Пока источник и AI-aware выход живут в одном src-репозитории, это две
оси эволюции с направленным потоком:

- **`trunk` — ось источника**: исправления исходной аналитики команда
  ведёт ветками от `trunk` (`fix-analytics-*`) → MR → merge в `trunk`,
  В ЛЮБОЙ момент — нас это не блокирует и ничего не ломает (в этих
  ветках нет `docs/`);
- **`<svc>-runN` — ось выхода**: источник + комплект; `docs/` правится
  только заходами;
- переключение веток НЕ уничтожает закоммиченное — комплект живёт в
  своей ветке; единственное теряемое — незакоммиченные правки, поэтому
  перед любым `switch` рабочее дерево должно быть чистым.

**Правило: один прогон == один срез источника.** Докатка нового среза в
ось выхода происходит на ГРАНИЦЕ прогонов: цикл закрыт (Approve →
merge MR) → `<svc>-runN+1` создаётся от свежего `trunk` — ветка
рождается уже совмещённой (акцептованный комплект + новый срез, merge
руками не нужен) → на старте прогона selfcheck против нового среза
сам подсвечивает устаревшие карточки (✗ по изменённым страницам,
coverage — по новым/исчезнувшим) — это готовая карта делта-дозаходов →
делта-дозаходы → новый MR.
> В целом **принцип** прост: Approve для MR подтверждает НЕ то, что аналитика корректна, 
> а то, что AI-aware аналитика (в каталоге `docs/`) **соответствует** поданной на 
> вход аналитике (в каталоге `confluence/`).  

Внутрицикловая докатка среза (merge `trunk` → `<svc>-runN` при
открытом MR) — ИСКЛЮЧЕНИЕ по явному решению обеих сторон, когда правка
источника нужна для самого текущего ревью; обязательное объявление в
MR: «срез обновлён, карточки такие-то перегенерированы». Причины, по
которым это не норма: плывёт предмет ревью (треды уходят в outdated не
из-за замечаний), Approve теряет однозначность («принят к какому
срезу?»), коммиты по-замечаниям и по-срезу мешаются в истории.

Чего не делать никогда: `rebase` ветки отдачи на новый `trunk`
(перепишет хеши — сломает MR и ссылки); правки `sources/` в ветке
отдачи (зона команды там — только `feedback.md`); смешивание правок
источника и выхода в одном коммите. При переезде на два репозитория
(roadmap v6) протокол сохраняется — «докатка среза» становится свежей
выгрузкой, остальное без изменений.

## Параллельные сервисы

Один сервис = один репозиторий + одна ветка отдачи + один открытый MR
с меткой `analytics-review`. Сводка по всем сервисам: GitLab → Merge
requests → фильтр по метке (открытые = активные циклы). Кандидат на
автоматизацию: агрегатор открытых тредов/FB-статусов по списку репо из
services.json (утилита класса selfcheck, после пилота).

## Шаблон feedback.md

```markdown
# Замечания команды <сервис> — прогон run1

Правила: записи append-only (новая — В КОНЕЦ, номер следующий);
статусы правятся на месте; в ветке отдачи команда правит только этот
файл. Точечные замечания к строкам — предпочтительно инлайн в MR.

## FB-01. <файл или раздел комплекта>: <суть одним предложением>

- **Замечание:** <что не так / чего не хватает, со ссылкой на карточку>
- **Автор, дата:** <кто, когда>
- **Статус:** новое | в работе | исправлено (<hash>) | принято |
  отклонено (<обоснование/ссылка на тред>)
```

Дисциплина файла — клон реестра открытых вопросов (append-only,
статусы правятся на месте). Механический контроль: в инструментарии
самопроверки (`_meta/tools/link_debts.py`, вызывается selfcheck) уже
есть сторож порядка реестра OQ — номера записей обязаны монотонно
возрастать, вставка в середину/перемещение = брак (проверка
`check_oq_order`. Поскольку feedback.md устроен той же дисциплиной, сторож
обобщается на `FB-NN`.
