# Постановка: transfer_gate — актуализация проверок переноса (матрица трассировки, слой BRD, покрытие API ↔ SRS, объявление типов, внешние вызовы, версия комплекта)

Дата: 2026-11-19. Для сессии «Правки прибора, акцепт и рутина». Коммит analyzer — по слову владельца; ветка
канона — по его командам (отдельное рабочее дерево, в общем клоне канона только fetch).

## Проблема

Гейт переноса проверяет комплект перед выкладкой в репозиторий документации. С 15.10 его собственные
проверки матрицы не менялись: наличие раздела «Покрытие: API ↔ SRS» и долги. Остальное он берёт из
`selfcheck`, и там три дыры, из-за которых гейт пропускает комплект, непригодный к переносу.

1. **Матрица.** Сверка выводимых разделов матрицы с документами (`matrix_sync`) в `selfcheck` на вердикт не
   влияет (`Check("matrix_sync", …, affects_verdict=False)`, решение 17–18.10). Если матрица не по шаблону,
   обёртка `selfcheck._matrix_sync_report` сверку пропускает одной строкой «i … сверка пропущена». Комплект
   с такой матрицей гейт проходит без единой строки о связях.
2. **Слой BRD.** Стандарт требует `brd/` у продуктовых сервисов и нулевые гейты достаточности
   (`conventions.md` §5 «инварианты», §5.3 п. 8–9). Гейт не проверяет ни наличие слоя, ни секции
   `BRD-1…5` матрицы, ни счётчики. Прибор знает только секцию НФТ (`nfr.py`, BRD-6).
3. **Раздел API.** Пустой раздел при наличии карточек методов даёт ⚠, не ✗; полнота раздела не проверяется.

Замер 19.11 (`matrix_sync.py --docs <комплект>`):

| Комплект | Структура матрицы | Сверка разделов |
|---|---|---|
| `EAN/docs-business-cards` | по шаблону, секции `BRD-1…5` есть | совпадает |
| `EAN/docs-account-opening-request` (эталон) | 9 отклонений: два раздела вне шаблона, нет «Источников миграции» и «Долгов по ссылкам», порядок, колонки трёх разделов, две таблицы в реестре | расходится: 84 ID без строки реестра, связи покрытий |
| `EAS/src-lk-mp` | 4 отклонения: нет «Источников миграции», порядок, колонки обоих покрытий (поправка сессии прибора 19.11: в первой редакции стояло «по шаблону» — прочитан был только хвост вывода) | расходится: 39 связей покрытий не отражены; слоя BRD нет |

Заголовки секций бизнес-слоя у комплектов различаются («BRD-5. Разрывы и сироты: гейты достаточности BRD»,
«BRD-5. Достаточность BRD: гейты покрытия», у `docs-file-storage-service` — нумерованные «7. Гейты
достаточности BRD»). Общий признак — префикс заголовка `## BRD-<N>`. Значение счётчика в таблице гейтов
начинается с целого числа, дальше свободный текст («0 из 128: …», «0 (…)», «2 фичи (…)»).

## Решения владельца 19.11.2026

1. Порядок шести разделов матрицы — предупреждение гейта, не отказ; остальные отклонения структуры — отказ.
   Сверка связей выполняется при любом порядке разделов.
2. Слой BRD отсутствует у продуктового сервиса — отказ; отсрочка — явным ключом с основанием, ответственным и
   сроком, которые попадают в отчёт.
3. Коды критериев остаются по DoR v1.2. Драфт платформы от 20.10 (75 проверок) до его согласования в гейт не
   переносится: ни коды, ни упоминание в шапке отчёта; шапка отчёта в части критериев не меняется.
4. Устаревшие описания гейта в каноне исправляются попутно, тем же срезом (пункт Т1).
5. Остальные проверки — по перечню ниже.

## Принцип правила

Все признаки — по форме и структуре, слов источника нет:

- раздел матрицы — по ключу заголовка шаблона (`matrix_sync.TEMPLATE`); секция бизнес-слоя — по префиксу
  заголовка `## BRD-<N>`, не по названию;
- тип документа — поле `type` шапки; принадлежность слою — каталог `brd/` или `srs/`;
- продуктовый или платформенный сервис — признак `is_platform` записи сервиса в `_meta/services.json`;
- значение счётчика — ведущее целое число ячейки «Значение»;
- связь — markdown-ссылка между файлами.

Имена строк таблицы гейтов («Функции без US» и другие) — термины нормы (`conventions.md` §5.3 п. 9), не слова
источника. Новых словарных эвристик постановка не вводит; если при исполнении понадобится признак по слову —
остановиться и вернуть вопрос постановщику.

## Где живут проверки

- Проверки комплекта (матрица, BRD, типы, внешние вызовы) — модули `kitcheck/checks/` (`matrix.py`, новый
  `brd.py`, по теме), слой «ядро»: работают без выгрузки. В реестре `KIT_CHECKS` — с
  `affects_verdict=False`: вердикт `selfcheck` у команд на каждом заходе не меняется, строки печатаются как ⚠.
- Гейт переноса в полном режиме повышает перечисленные строки до ✗ по закрытому списку; в режиме
  `--after-step` они остаются ⚠ (закрытый список понижений в шапке гейта дополняется).
- Гейт вызывает сверку матрицы сам (`matrix_sync.check`), а не через обёртку `selfcheck`, которая пропускает
  сверку при отклонении структуры.

## Что сделать

Целевое состояние по каждой проверке: строка отчёта гейта с критерием, знаком и текстом.

**П1. Структура матрицы (SDLC-04).** `matrix_sync.structure_issues` возвращает отклонения с классом:

- блокирующие — нет раздела шаблона, раздел повторён, имя раздела не по шаблону, колонки выводимого раздела не
  по шаблону, в выводимом разделе не одна таблица, раздел вне шаблона, приложение до раздела шаблона → ✗, в
  тексте — перечень и подсказка («раздел вне шаблона переносится в приложение `## Приложение. …`»);
- только порядок шести разделов при верном составе → ⚠ «порядок разделов не по шаблону: …»; сверка разделов
  при этом выполняется.

`matrix_sync --write` при отклонении только порядка работает и порядок разделов сохраняет как есть; при
блокирующем отклонении — отказ, как сейчас.

**П2. Реестр ID (SDLC-09).** Строки `check_registry`: «нет строки для ID из документов», «строка без
документа», «снятый ID снова в документах», «файл расходится» → ✗ с числом и первыми ID. «ID только
упоминается в тексте» → ⚠.

**П3. Покрытия функций и процессов (SDLC-04).** Любое расхождение разделов «Покрытие: функции → артефакты» и
«Покрытие: процессы → артефакты» с документами → ✗ с числом по видам и командой пересборки
`matrix_sync.py --docs <комплект> --write`. Раздел «Источники миграции» → ⚠ (происхождение, не связи).

**П4. Пустой раздел API (SDLC-04).** Раздел пуст, а в комплекте есть карточки `type: internal-contract` в
контуре Экосистемы (карточки части вне контура, канал `js-api`, не считаются — правило шаблона матрицы) → ✗.
Пустой раздел допустим в двух случаях: карточек методов нет — ✓ «пуст — собственных методов нет»; причина
записана в шапке раздела (текст между заголовком и таблицей) — ✓ с цитатой причины. Форму оговорки причины
в шаблон матрицы вносит постановщик отдельной правкой нормы; до неё — любая непустая шапка раздела.

**П5. Полнота раздела API (SDLC-04).** Каждая карточка `type: internal-contract` в контуре Экосистемы
названа своим ID в разделе «Покрытие: API ↔ SRS» (строкой-операцией либо в колонке «Артефакты SRS») → иначе ✗
с перечнем ID (`conventions.md` §5.3 п. 7: до перехода на API First строка раздела — карточка `INTC`).

**П6. Слой BRD (SDLC-06).** Сервис комплекта — по полю `service` шапок; запись в `_meta/services.json`:

- `is_platform: true` → i «не применяется: платформенный сервис, роль слоя выполняет `service-vision.md`»;
- продуктовый либо не найден в каталоге (сомнение — в сторону отказа) и в комплекте нет каталога `brd/` с
  документами, имеющими `id`, → ✗ «слой BRD обязателен для продуктового сервиса (conventions §5)»;
- ключ `--brd-deferred "<основание>; ответственный: <кто>; срок: <ГГГГ-ММ-ДД>"` → вместо ✗ строка ⚠ с
  текстом ключа; текст попадает в шапку отчёта и в «Ручную часть протокола до подключения»; значение без
  ответственного или срока → ✗ с названием недостающего поля.

**П7. Секции и гейты BRD (SDLC-06).** Только при наличии слоя `brd/`:

- секции `## BRD-1` … `## BRD-5` есть (по префиксу заголовка) → иначе ✗ с перечнем отсутствующих;
- в секции `BRD-5` таблица «Гейт | Значение»; у каждой строки ведущее целое число ячейки «Значение» равно 0 →
  иначе ✗ с именем гейта и значением; ведущего числа нет → ✗ «значение гейта не читается»;
- пересчёт трёх счётчиков по комплекту: функции без `US` (функции реестров функций, которых нет в `BRD-1`),
  печатные формы без связи (формы реестров, которых нет в `BRD-4`), сироты BRD (документы `brd/` с `id`,
  которых нет в `BRD-1…3`). Расхождение пересчёта с заявленным нулём — в этом срезе ⚠ с перечнем; повышение
  до ✗ — отдельным словом владельца после замера (см. «Ограничители»);
- счётчики «сценарные процессы без UC» и «доменные политики без BR» механически не выводятся: читаются из
  таблицы, строка ✓ помечается «по заявленному значению».

Секция `BRD-6` (НФТ) остаётся за существующей проверкой `nfr_catalog`.

**П8. Слои не ссылаются друг на друга (SDLC-01).** Markdown-ссылка из файла `brd/**` на файл `srs/**` или
обратно (`conventions.md` §5.4) → целевой знак ✗ с числом и первыми парами. Включается после замера (см.
«Ограничители»).

**П9. Типы объявлены (TRF-04).** Тип документа вне закрытого набора платформы, которого нет в таблице типов
README («Условные обозначения»), → ✗ (сейчас i). Тип вне набора, описанный в README, → i «исключение к
согласованию», как сейчас. Тип из набора платформы, не описанный в README, → ⚠.

**П10. README как точка входа (SDLC-08).** В README комплекта нет ссылки на `traceability-matrix.md` → ⚠.
Подраздел «Долги по ссылкам» при непустом разделе долгов уже проверяется (CORE-20), не трогать.

**П11. Внешний вызов ведёт к контракту (SDLC-02).** Карточка внешнего вызова (`CALL-EXT-…`) содержит ссылку
на базовый контракт репозитория `docs-external-contracts` либо является `FROM-ID` строки долга матрицы →
иначе целевой знак ✗ с перечнем. Включается после замера (см. «Ограничители»).

**П12. Перенос только из зафиксированной версии (CORE-05).** При `--out` и незакоммиченных изменениях в
каталоге комплекта → ✗ «перенос из рабочего дерева: версию комплекта нельзя получить повторно»; без `--out`
— ⚠ и пометка в шапке, как сейчас.

**Отчёт.** `_SELFCHECK_CRITERIA` дополнить ключами новых строк. В `_MANUAL_BEFORE_CONNECT` — пункт SDLC-06:
«независимая сверка BRD с карточками (`verify-brd-vs-srs`) выполнена, отчёт приложен» — механически не
проверяется. Шапка `--report` в части критериев не меняется (решение 3).

**Т1. Устаревшие описания гейта в каноне** (решение 4; то же рабочее дерево канона). Исправляются независимо
от судьбы проверок П1–П12: если часть проверок вернётся на доработку, Т1 сдаётся всё равно.

| Где | Сейчас | Целевой текст |
|---|---|---|
| `_meta/migration/reference.md`, строка 234, раздел «Перенос комплекта в docs-репозиторий» | «…легенда служебных меток (ПЕРЕНОС — условия самого переноса, ПРИБОР — прибор миграции, ВАЛИДАТОР — валидатор платформы)» | метки, которые гейт печатает на самом деле: `TRF-01…05` — условия переноса, ПРИБОР, ВАЛИДАТОР, РЕЖИМ; метки «ПЕРЕНОС» в отчёте нет с 13.10 |

## Ограничители

- **Вердикт `selfcheck` не меняется**: число ✗ `selfcheck` на золотых комплектах до и после — одинаково;
  новые строки приходят как ⚠.
- **Замер перед включением ✗ для П8 и П11.** Прогнать на `docs-business-cards`, эталоне и `src-lk-mp`,
  привести числа и классы срабатываний. Есть класс, похожий на ложный, — в этом срезе оставить ⚠ и вернуть
  разбор постановщику; предположение «так везде» без замера не принимается.
- **Замер пересчёта П7** на `docs-business-cards`: ожидание — расхождений нет при заявленных нулях
  (в таблице гейтов этого комплекта реестры частей и не сценарные процессы названы поимённо). Расхождения —
  в сдачу с разбором, знак остаётся ⚠.
- **Тесты** (`tests/test_transfer_gate*.py`, `tests/test_matrix_sync*.py`, новый файл для BRD), на каждую
  проверку срабатывание и несрабатывание: порядок при верном составе — ⚠ и сверка выполнена; блокирующее
  отклонение структуры — ✗; `--write` при ином порядке сохраняет порядок; пустой раздел API без карточек
  методов — ✓, с карточками — ✗, с причиной в шапке — ✓; карточка части вне контура не требует строки API;
  платформенный сервис без `brd/` — i; продуктовый без `brd/` — ✗; `--brd-deferred` полный — ⚠, без срока —
  ✗; гейт «2 фичи (…)» — ✗, «0 из 128: …» — ✓; `--after-step` — все новые строки ⚠; `--out` на грязном
  дереве — ✗.
- **Живые прогоны** гейта с `--report`: `EAN/docs-business-cards` (с описью и выгрузкой из src по гиду),
  `EAN/docs-account-opening-request`, `EAS/src-lk-mp`. В сдачу — итог, число ✗ по новым критериям, было и
  стало. Отчёты содержат данные команд: в analyzer не коммитить.
- Быстрый уровень тестов (`-m "not chain" -n 4`) перед сдачей; `structural_facts.py --repo <рабочее дерево
  канона> --strict` — итог в сдачу.
- Сообщение коммита канона — для всех команд: сначала проблема (гейт пропускал комплект с матрицей,
  расходящейся с документами, и без слоя BRD), потом что меняется в отчёте.

справочники (SDLC-03); оценка содержания BRD. Сообщения командам (команде-поводу с числами и всем без чисел)
готовит постановщик после сдачи по числам живых прогонов.
