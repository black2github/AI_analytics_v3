# Реестр решений по ядру скиллов

Рабочий документ обсуждения расхождений между двумя корпусами методологии:

- **«Принципы»** — `app/data/Принципы проработки силлов.md` (15 принципов) + скиллы
  `.claude/skills/` (control-split, screen-form-restructure, event-driven-screen-form-design,
  `_shared`), обкатаны на сервисах КК и o2Plus;
- **`_meta`** — `C:\doc-as-code\EAN\docs-o2new\_meta` (AGENTS.md, rules/conventions.md,
  templates/, skills/) + образец комплекта `output/open-add-account`.

Назначение: зафиксировать развилки, накопить решения, стать входом для доработки `_meta`
и для «конституции ядра». Конституция пишется **после** закрытия Д-1, Д-2, Д-8 —
до этого нормативный текст не формулируется однозначно.

Порядок работы: обсуждение → заполнение поля «Решение» (кто, когда, что) → пункт
получает статус «решён» → поле «Следствия для _meta» превращается в план правок.
Новые вопросы и замечания добавляются новыми пунктами Д-N (нумерация сквозная,
не переиспользуется). Пункты не удаляются и не переписываются задним числом;
пересмотр решения — новым абзацем в «Решении» с датой.

Контекст фаз (сквозная рамка, через которую смотрят все пункты): корпус «Принципов»
оптимизирован под **миграцию** (преобразование недоверенного исходника без потерь),
`_meta` — под **целевое состояние** (чистовой переносимый комплект forward-стиля).
Кандидат в объединяющий принцип — **двухфазная модель**: рабочая фаза допускает
маркеры/прослеживаемость/промежуточные артефакты; гейт чистовости — механический
(grep/счётный) — не пускает их в master.

**Стратегия внедрения (зафиксирована 2026-08-02, пользователь):** сроки пилота
ограничены, обсуждение каждого изменения с командой/руководителем дорого. Ставка —
на демонстрацию результатом: если документация, сформированная с изменениями из
рабочей ветки, однозначно качественнее документации без них — предмет для споров
исчезает. Полномочия «попробовать» и ответственность за риски — у пользователя
(эксперт-аналитик, дорабатывающий скиллы). Следствие для реестра: пункты двигаются
реализацией в ветке и проверкой на пилотных документах, а не предварительным
согласованием каждого; обсуждению подлежит готовый измеримый результат.

## Д-1. Политика неуверенности: inline-маркер vs чистовой документ

- **Статус:** открыт
- **Критичность:** высшая — расхождение переворачивает асимметрию ошибок.
- **Суть.** «Принципы» п. 1: «тихая потеря — худшее; явная пометка — приемлемо»,
  маркер `[НЕ РАСПОЗНАНО: <дословно>]` прямо в артефакте. `_meta` (conventions §6,
  AGENTS.md): «документы чистовые», inline-маркеры запрещены, спорное пишется «по
  наиболее достоверному источнику — без пометок», отсылки к OQ из документов запрещены;
  связь «вопрос → место» живёт только в поле «Затронутые документы» реестра
  `open-questions.md`. Для слабой LLM дефолт `_meta` опасен: лучшая догадка вписывается
  чистовым текстом, неотличимым от факта, а заполнение OQ-реестра — отдельное действие,
  которое слабая модель систематически пропускает. Тихое сглаживание становится штатным
  режимом отказа.
- **Варианты:**
  - **(а) — рекомендация.** Двухфазная политика: в рабочей ветке inline-маркеры
    (`[НЕ РАСПОЗНАНО: …]`, `уточняется`) разрешены; гейт чистовости — grep-паттерн
    в антирегрессии (механизм в `_meta` уже есть) блокирует merge, пока маркер не
    разобран в OQ или с аналитиком. Маркер живёт в ветке, в master не доезжает.
  - (б) Принять политику `_meta` как есть, компенсировав обязательным шагом скилла
    «каждая догадка → строка OQ» + чеклист-пункт. Риск: у слабых моделей шаг
    выпадает, контроль только ревью человеком.
  - (в) Принять политику «Принципов» как есть (маркеры в чистовых документах).
    Ломает переносимость комплекта и его читаемость как «канона».
- **Решение:** —
- **Следствия для _meta (при варианте а):** conventions §6 — раздел о рабочей фазе;
  grep-антирегрессии скиллов (create-controls «Самопроверка» п. 3, create-data-model
  п. 2 и далее по всем create-*) — добавить паттерн `НЕ РАСПОЗНАНО|уточняется|TODO`
  как gate перед MR, а не как тотальный запрет в ветке; AGENTS.md — «Документы —
  чистовые» переформулировать с оговоркой о фазе.

## Д-2. Прослеживаемость к источнику: в артефакте vs в описании MR

- **Статус:** открыт
- **Критичность:** высокая.
- **Суть.** «Принципы» п. 11: каждый производный элемент несёт связь с исходным
  (колонка «Ориг.» с исходным №, дефекты исходной нумерации сохраняются в поле
  прослеживаемости). `_meta`: forward-стиль запрещает любые следы источника в
  документе; «нумерация источника не сохраняется», соответствие «№ источника →
  CTL-NNN» — в описании MR (шаблон контролей, create-controls). Описание MR —
  эфемерный, не машиночитаемый носитель: сверка результата с исходником (главный
  инструмент контроля качества слабой модели) требует git-археологии на каждый
  элемент; функция п. 11 «сверять, откатывать и чистить первоисточник» теряется,
  пока Confluence жив.
- **Варианты:**
  - **(а) — рекомендация.** Sidecar-файл прослеживаемости на уровне сервиса **вне**
    переносимого `docs/` — по прецеденту `open-questions.md`: `trace-map.md`
    (таблица «исходник/№ → целевой ID», машиночитаемо). Комплект остаётся чистым,
    соответствие живёт в git.
  - (б) Колонка «Ориг.» в документах рабочей фазы, механически удаляемая скриптом
    при финализации (двухфазная модель). Требует скрипта и дисциплины запуска.
  - (в) Оставить как в `_meta` (MR-описание). Дешевле всего, но сверка дорожает
    именно там, где слабой модели нужен контроль.
- **Решение:** —
- **Следствия для _meta (при варианте а):** conventions §5.3 — новый подраздел о
  trace-map (уровень сервиса, вне docs/, в целевой репозиторий не переносится);
  create-controls, create-screen-form, create-data-model — шаг «обнови trace-map
  в том же изменении»; чеклисты шаблонов — пункт сверки.

## Д-3. Инструкционный стек: самодостаточность скилла для рабочей модели

- **Статус:** открыт
- **Критичность:** высокая для использования слабыми LLM.
- **Суть.** `ai-sdlc.md` требует самодостаточности документов («опенсорсные LLM слабее
  фронтирных: документ должен читаться без большого внешнего контекста»), но не
  применяет это к самим инструкциям: рабочий контекст агента собирается по цепочке
  AGENTS.md → conventions.md (304 строки) → create-artifact → create-<тип> →
  templates/<тип>.md → git-workflow.md (5–6 прыжков). Слабые модели теряют дальние
  ограничения первыми; по «Принципам» п. 15 сильная модель это молча компенсирует,
  скрывая недосказанность. Наши скиллы устроены обратно: самодостаточный SKILL.md +
  прогрессивное раскрытие references с явными пометками «авторитет».
- **Варианты:**
  - **(а) — рекомендация.** Сохранить нормализацию `_meta` (единый источник — верно),
    добавить **сборку**: «компилированный» скилл (skill + шаблон + релевантные выдержки
    конвенций одним файлом) как генерируемый артефакт для рабочей модели. Это п. 4
    «Принципов»: выводимое не ведётся вручную. Компиляция — скриптом или скиллом.
  - (б) Денормализовать вручную: перенести ключевые правила конвенций в каждый скилл.
    Рассинхронизируется (ровно то, от чего защищается FMT-P3).
  - (в) Оставить как есть, положившись на способность моделей ходить по ссылкам.
    Проверяемо экспериментом Д-5(б), до него — риск.
- **Решение:** —
- **Следствия для _meta (при варианте а):** новый скилл `compile-skill` (или скрипт);
  правило в create-skill.md: компилят — build-артефакт, правится только источник;
  место хранения компилятов (напр. `_meta/compiled/`, в git или генерация на лету).

## Д-4. Оценочные границы в шаблонах — заменить счётными

- **Статус:** открыт
- **Критичность:** средняя-высокая (дрейф на сотнях применений).
- **Суть.** «Принципы» п. 3: многократно применяемая граница — механическая
  (посчитать), не оценочная. В `_meta` есть оценочные: «поле со **значимой логикой**»
  (заводить ли П-N, templates/screen-form §4), «**тематически подходящий** файл»
  карточек (templates/controls), «**простые** экраны» (разделы 5–7 можно опустить,
  templates/screen-form), «когда речь **именно о нём**» (ссылка на CTL vs группу).
  В наших скиллах аналоги счётные: критерий выноса видимости (ветвление / разделяемость /
  внешнее состояние — «посчитать "если", посчитать владельцев, все ли участники — поля
  формы»), field/rule («можно ли проверить, глядя на одно поле»), порядконезависимость
  кандидата в контроль.
- **Варианты:**
  - **(а) — рекомендация.** Точечно заимствовать счётные формулировки в шаблоны `_meta`.
    Например, П-N заводится, если у поля есть хотя бы одно из: условие видимости или
    доступности, предзаполнение, источник списка, формат с ограничением; иначе не
    заводится. Аналогично для «простых экранов» (нет событий и кнопок → §5–6
    опускаются) и ссылки CTL vs группа (по одиночной точке вызова).
  - (б) Оставить оценочные, компенсировать ревью человеком. Не масштабируется.
- **Решение:** —
- **Следствия для _meta (при варианте а):** templates/screen-form.md §4, §«Структура»;
  templates/controls.md §«Файлы карточек», §«Ссылки»; чеклисты шаблонов — пункты
  проверки по счётному критерию.

## Д-5. Петля «ошибка → правило» и приёмка на рабочей модели

- **Статус:** открыт
- **Критичность:** средняя (растёт с масштабом пилота).
- **Суть.** «Принципы» п. 14: обнаруженная ошибка исправляется правкой скилла
  (правило + пункт чеклиста), не заплаткой в файле. П. 15: валидация чистым сигналом
  на сильной модели, приёмка — на рабочей; расхождение → недосказанность скилла.
  В `_meta` петли нет: create-skill.md не требует закреплять находки, ревью-скиллы
  складывают отчёты в `reports/` — цепочка обрывается; методология целится в опенсорсные
  LLM (ai-sdlc.md), но обкатана на фронтирных (Cursor/Claude) — реальная недосказанность
  шаблонов не измерена.
- **Варианты:**
  - **(а) — рекомендация.** Два дополнения: (1) раздел «Петля ошибок» в create-skill.md
    и норма в AGENTS.md — системная находка ревью обязана порождать MR в `_meta`
    (правило + пункт чеклиста); (2) до масштабирования на группу сервисов — пилотный
    прогон 2–3 шаблонов (screen-form, controls) на целевой опенсорс-модели, расхождения
    с фронтирной моделью разбираются как список недосказанностей.
  - (б) Только петля ошибок, без прогона. Дешевле, но целевой стек останется непроверенным.
- **Решение:** —
- **Следствия для _meta (при варианте а):** create-skill.md — раздел «Петля ошибок»;
  AGENTS.md — базовый принцип; план пилота — пункт «прогон на рабочей модели» с
  критерием (счётным) приёмки.

## Д-6. Один разбор — согласованный набор vs поартефактная нарезка

- **Статус:** открыт
- **Критичность:** средняя.
- **Суть.** «Принципы» п. 7: интерпретация неструктурированного текста — самая дорогая
  операция, за неё платят один раз; производные рождаются согласованным набором.
  В `_meta` одну страницу-исходник (вкладки + кнопки + «Функция сохранения» вперемешку)
  независимо парсят create-screen-form, create-function, create-controls; согласованность
  держится шагом «сверь с комплектом» и матрицей — то есть способностью модели. Слабая
  модель при повторной интерпретации даст разночтения между SCR, FUN и CTL.
- **Варианты:**
  - **(а) — рекомендация.** Фиксированный порядок конвейера + промежуточный структурный
    экстракт как рабочий артефакт вне `docs/` (аналог прохода 2a скилла
    screen-form-restructure: `источник / ось / целевая_строка / текст`); производные
    скиллы строят из экстракта, не из сырого исходника.
  - (б) Оставить поартефактно, усилить шаг сверки чеклистами перекрёстных инвариантов
    (по образцу 18 машинных инвариантов event-driven-скилла). Частично закрывает риск.
- **Решение:** —
- **Следствия для _meta (при варианте а):** create-artifact — понятие экстракта и
  порядок конвейера; место хранения экстрактов (уровень сервиса, вне docs/);
  create-screen-form/function/controls — вход из экстракта при его наличии.

## Д-7. Стратегия миграции: полная пересборка vs минимальная правка

- **Статус:** открыт — **решение по группам сервисов, не единое**
- **Критичность:** стратегическая развилка (не дефект одной из сторон).
- **Суть.** «Принципы» п. 10: артефакты узнаваемы, имена из оригинальных минимальной
  правкой, новое точечно — дешёвое ревью, сохранение навигации. `_meta`: сознательная
  полная пересборка forward-стиля («как будто написано до кода»: новые имена
  латиницей, новая нумерация, новая структура). Корреляция с типологией сервисов:
  для «музейной» реструктуризации (o2Plus — исходник дальше не живёт) пересборка
  честнее; для сервисов с активной разработкой (КК) эволюционный путь дешевле и
  сохраняет навигацию команды. Пересборка требует более сильной модели; эволюционная
  правка оставляет меньше степеней свободы.
- **Варианты:**
  - **(а) — рекомендация.** Решить явно и по-разному для групп пилота: критерий выбора
    зафиксировать счётно (например: исходник продолжает править команда → эволюционный
    путь; исходник замораживается → пересборка). Ядро скиллов должно поддерживать оба
    режима (наши — эволюционный, `_meta` — пересборку; это и есть кандидат в
    специализацию поверх ядра).
  - (б) Единая стратегия для всех групп. Проще управлять, но один из классов сервисов
    получит неподходящий режим.
- **Решение:** —
- **Следствия для _meta:** зависит от решения; при (а) — create-artifact получает
  режимы, а выбор фиксируется в параметрах сервиса (frontmatter/README комплекта).

## Д-8. Нотация внутренних ID: омоним FR, кириллица, стабильность шагов

- **Статус:** в работе — кандидат решения зафиксирован, остались подвопросы
- **Кандидат решения (2026-08-01):** `app/data/Политика идентификаторов.md`, вариант A
  (пользователь: «в идеале хочется поддержать эти принципы»). Политика проверена по
  фактам репозитория `_meta`:
  - рассинхрон `PROC`/`PRC` **подтверждён**, причём внутри самого conventions.md
    (строка 106 объявляет `PROC`; строки 219/253/255 и все живые файлы/ID —
    `PRC-NNN`) → унификация на `PRC` фиксирует факт, а не меняет его;
  - `ТР-NN` в conventions §5 — **кириллица на уровне байтов** (d0a2 d0a0),
    нарушение алфавита политики; замена — `DT-NN` (decision table);
  - кириллические локальные ID в живом комплекте: 138×`П-N`, 23×`Е-N`, `М-N`
    в таблицах §7, плюс 54×`B-N` — объём миграции 11 документов ЭФ, механизируется
    скриптом;
  - анти-омоглифный фильтр политики корректен: все префиксы схемы проходят,
    кроме признанного исключения `EXT` (⚠️ задокументировано) и найденных ниже.
- **Подвопросы к закрытию:**
  - (а) **`B-N` (кнопки) не покрыт таблицей замены** — однобуквенный префикс
    (запрещён п. 2) и омоглиф `В`. Варианты: `BTN-N`, либо модель событийного
    скилла (кнопка = событие `EV-N`) — второе выходит за рамки нотации, см. (в).
  - (б) **Коллизия `FR` остаётся**: 63 живых `FR-NN.M` (EARS) в BRD o2plus против
    `FR-N` (правило поля) в размеченных документах КК. Смягчения реальны: разные
    форматы (`NN.M` vs `N`), слои BRD/SRS не ссылаются друг на друга (conventions
    §5.4), локальный ID вне документа — только полным адресом. Решение: явное
    правило дизамбигуации в политике либо переименование одной из сторон.
  - (в) **Кнопки: `B-N`-раздел (_meta) vs кнопка-как-событие (event-driven)** —
    расхождение моделей документа ЭФ, не нотации; разруливается при слиянии
    шаблонов (связано с Д-4/Д-6, при необходимости — отдельный Д-пункт).
  - (г) **`F-CL-NN`/`F-BNK-NN` (фичи BRD)** — однобуквенный префикс, живые файлы

## Д-10. Модель данных: логический якорь vs физика; реестр элементов данных (DE)

- **Статус:** в работе — кандидат решения зафиксирован, остались интеграционные решения
- **Кандидат решения (2026-08-01):** `app/data/Реестр модели данных (DE).md` — реестр
  `DE-NNN` (бизнес-реквизит клиентского пути) + составной адрес `SCR-…/FR-N`; обкатан
  на пилоте (22 DE, 2 вкладки, двусторонняя автосверка поймала расхождение до ревью).
- **Суть.** Критика «модель `_meta` идёт от физики» **подтверждена проверкой, причём
  жёстче, чем заявлено** (templates/data-model.md):
  1. «**Только физически хранимые атрибуты**» — вычисляемое и вводимое-но-не-хранимое
     из модели исключено правилом; контролю формата «Индекса» не к чему трассироваться;
  2. «Стабильный ID атрибута — `ENT-001.doc_number` (ID сущности + **физическое имя
     поля**)» — стабильность требований подвешена на самый нестабильный слой
     (рефакторинг колонки БД рвёт ссылки), прямое противоречие API First и принципу 5
     политики ID;
  3. маппинг «поле → атрибут» в реестре полей ЭФ — колонка 1:1, N:M невыразимо
     (код+наименование; номер+дата контракта).
  Для reverse-контекста o2plus физический якорь объясним (документируется существующая
  БД), но в ядро наследоваться не должен. Вопрос «кто проектирует физическую модель»

  незыблемым, коллизии из-за него фиксируются явно и работу не блокируют.
- **Матрицу трассировки предложение НЕ ломает** — оно следует её же паттерну:
  «состав "группа → контроли" в матрице не разворачивается — зафиксирован в controls/
  ровно один раз» (templates/controls.md). Аналогично: состав «DE → представления»

  этап 2 (REQ-строки) может добавить колонку DE — аддитивно.
- **Интеграционные решения к закрытию:**
  - (а) **Carve-out реестра ID матрицы**: по букве §5.3 п.4 («каждый выданный ID —
    строка реестра») 22 DE-NNN дали бы 22 строки-дубля. Прецедент есть: коды

    правил матрицы, не сущностная проблема предложения. Ссылочность от статуса
    «локальный» не страдает: контроль ссылается на `DE-NNN` обычной markdown-ссылкой
    на якорь реестра, наличие строки в реестре ID матрицы для этого не требуется

    нужно правило выбора якоря контроля: BE-контроль якорится на атрибут (как

    атрибут» карточки CTL. Стандартная оговорка о стабильности якорей при расщеплении

  - (б) **Судьба колонки «Атрибут» в реестре полей ЭФ** (templates/screen-form §2):
    при цепочке «поле → DE → Хранение» прямой маппинг 1:1 становится дублем

    *Направление решения (2026-08-02):* пользователь склоняется к **проекции** —

  - (в) **Якорь «Хранения» без полной переделки модели**: точечная нотация

## Д-11. Кто проектирует физическую модель: граница ответственности аналитик/разработка

- **Статус:** открыт — на обосновании; согласование с руководителем управления
  готовит пользователь
- **Суть.** Конвенции `_meta` (§5) фиксируют: «физическую модель (таблицы, имена и
  типы полей) аналитик проектирует сам — она в SRS остаётся». Это противоречит
  разграничению ответственности аналитиков и разработки по API First (физика — зона
  разработки за контрактом; аналитик — логический уровень). Пользователь намерен
  обосновать исключение этого принципа из методологии и согласовать с руководителем
  управления.
- **Рабочее правило до решения (зафиксировано 2026-08-02):** принцип `_meta` не
  считается незыблемым; он не блокирует проработку остальных пунктов. Каждый
  вопрос, противоречие или двусмысленность, возникающие из-за него, **явно
  фиксируются** (здесь или в OQ-реестре соответствующего репозитория) — накопленный
  список станет частью обоснования.
- **Уже накопленные коллизии** (материал для обоснования):
  1. стабильный ID атрибута = физическое имя колонки ([[Д-10]] суть, п. 2) —
     устойчивость документации подвешена на схему БД;
  2. «только физически хранимые атрибуты» — вводимые/вычисляемые реквизиты не имеют
     места в модели, их контролям не к чему трассироваться ([[Д-10]] суть, п. 1);
  3. reverse-порядок create-data-model начинается с кода (`@Entity`, liquibase) —
     источник модели фактически физический, Confluence вторичен;
  4. конфликт доменов при ведении «Хранения» реестра DE ([[Д-10]] п. (г)).
- **Принципиальные аргументы (пользователь, 2026-08-02):**
  5. **Эпистемологический.** Дефект по определению — расхождение реализации с
     входным требованием. Если модель данных SRS выводится из кода, реализация
     становится эталоном самой себя: класс дефектов «код не соответствует
     аналитике по данным» делается **невыразимым** — его негде зафиксировать.
  6. **Свобода физической реализации.** Одна логическая модель имеет несколько
     легальных физических воплощений (наследование в реляционной БД — минимум
     три стратегии: single table / joined / table-per-class); выбор — инженерная
     оптимизация разработчика, не предмет аналитики. Физика в SRS отнимает у
     разработки эту свободу либо делает SRS ложным при её использовании.
  7. **Норма организации уже существует**: «Правила оформления аналитики ДБО» —
     «описание аналитики выполняется на логическом уровне, без привязки к
     реализации, везде, где возможно». Физическая модель в SRS противоречит
     действующему орг-документу, а не только API First.
- **Уточняющее различение (2026-08-02, к обоснованию):** в `_meta` склеены два
  независимых решения — (1) **источник восстановления** при reverse существующего
  сервиса (код как источник фактов «что фактически хранится» — защитимо: для
  живой системы код точнее устаревшего Confluence) и (2) **уровень представления
  в SRS** (физический — спорно, против пп. 5–7). Можно уступить (1), выиграв (2):
  reverse извлекает факты из кода, но SRS обязан представить их логической
  моделью; физимена — прослеживаемость (свойство/сайдкар), не канон. Это
  усиливает переговорную позицию: спор не «код vs Confluence», а «уровень
  представления результата».
- **Решение по рамке (2026-08-02, пользователь): различение принято** — линия
  обоснования: «уступить источник (1), выиграть уровень представления (2)».
  Принят гибридный путь: дочистить механические волны; параллельно подготовить
  эскиз логической модели (переработанный шаблон data-model + одна сущность
  o2plus «как есть / как будет») как материал обоснования; до закрытия Д-11
  массовая генерация моделей данных для новых сервисов пилота не запускается
  (строка в план пилота — за пользователем). Итоговое решение по принципу — ждёт
  согласования с руководителем.
- **Решение:** —
- **Следствия для _meta (при исключении принципа):** conventions §5 (два места),
  templates/data-model.md (колонки «Физ. имя»/«Тип»/«Ограничения БД» → к разработке
  или в отдельный несервисный артефакт; правило стабильного ID атрибута → бизнес-имя),
  create-data-model.md (reverse-порядок: Confluence первичен); связь с Д-10 (в) —

## Д-12. Режим «detailed calls»: инициализация параметров вызовов с заземлением в OpenAPI

- **Статус:** открыт — на обсуждении (кандидат-вклад из `.claude/_shared/function-calls.md`)
- **Суть.** Наше правило: вызов функции/метода записывается с инициализацией входных
  параметров (`<параметр> = <поле>`); состав дополняется по логическому описанию
  функции (приоритет) и OpenAPI; источник значения каждого параметра — поле формы либо
  `[НЕ РАСПОЗНАНО]`/`уточняется`; граница — маппинг параметра в атрибут сущности =
  API-слой, вне объёма. В `_meta` этому противостоят **два жёстких правила**:
  conventions §5.1 «маппинг на DTO и поля API не ведётся; экранные формы не описывают
  вызовы методов» и §5.3 п. 7 «методы контрактов упоминаются только в матрице».
  Зазор меньше, чем кажется: шаблон ЭФ `_meta` **уже требует** «вызовы не сворачиваются:
  какие параметры запроса передаются и как обрабатывается ответ» (для EXTINT/PLT,
  в бизнес-терминах); у функций параметры — в самом документе FUN. Конфликт сводится
  к двум точкам: (1) `operationId`/имена методов в телах SRS; (2) OpenAPI как источник
  полноты состава (их принцип — «SRS с кодом не сверяется»).
- **Содержательный вопрос:** «поле → параметр вызова» — требование или реализация?
  Позиция наших скиллов: состав и источники значений — требование (несут
  бизнес-семантику), маппинг в атрибут/DTO — реализация. Аргумент «за» — AI SDLC
  этапы 2–3: агенту-генератору нужна эта связь; аргумент «против» — двухканальная
  модель `_meta` (SRS из Confluence, контракты из кода, связь только в матрице)
  позволяет перегенерировать контракты без правки SRS.
- **Варианты:**
  - **(а) — рекомендация.** Опциональный режим «detailed calls» (флаг сервиса) с
    ограничителями: параметры — бизнес-именами; `operationId` — не в телах SRS, а
    в углублённом разделе матрицы §5.3 п. 7 (параметрный уровень) либо в sidecar;
    OpenAPI — read-only справка полноты, расхождение = OQ, не правка. Пилот на одном
    сервисе с регуляторной потребностью.
  - (б) Ослабить §5.1/§5.3 п. 7 глобально. Ломает слоистость `_meta` — не рекомендую.
  - (в) Не вносить; связь поле→параметр остаётся зоной разработки. Теряется
    трассируемость для генерации и регуляторики.
- **Позиция пользователя (2026-08-02):** двухканальная модель `_meta` спорна —
  противоречит API First; спецификация сервиса — его неразрывная часть, ссылка на
  эндпоинт своего сервиса не отличается от ссылки на любой файл комплекта; единый
  репозиторий спецификаций (`C:\doc-as-code\all-bundle`) — больше плюс, чем минус.
- **Анализ (2026-08-02), подтверждает и уточняет позицию:**
  1. **Правило `_meta` — защита, согласованная с Code First, а не с API First.**
     Их конвейер по собственному описанию Code First: «контракты вручную не пишутся,
     выгружаются из кода» — спека = нестабильная производная кода, запрет ссылок
     из SRS рационально защищает от гниения ссылок. Под API First спека —
     проектируемый артефакт с управляемой стабильностью, объект защиты исчезает.
     Симметрия с Д-10/Д-11: SRS изолируется от нестабильного слоя; вопрос лишь в том,
     что нестабильно — под Code First спека, под API First код.
  2. **Аномалия собственных правил `_meta`:** спеки уже лежат внутри переносимого
     комплекта (`docs/api/`), SRS может ссылаться на любой файл `docs/` (ENT, CTL,
     EXTINT — ссылками), кроме единственного — `api/`. Общее правило §5.3 п. 2
     («ссылки в телах — навигация, не источник трассировки») уже покрывает нужную
     семантику; приведение API к нему снимает аномалию, а не ломает систему.
  3. **Матрица не ломается — системное решение:** раздел «API ↔ SRS» остаётся
     единственным источником трассировки уровня операций, но становится
     **генерируемой проекцией** из ссылок в телах + спек, с двусторонней CI-сверкой
     (инвариант Д-13: операция в теле ⇔ строка в матрице). Прецеденты уже приняты:
     DE «Представления», проекция «Атрибут» Д-10 (б). Гранулярность: матрица —
     операции; параметрный уровень — в телах у вызова (detailed calls).
  4. **Асимметрия свой/чужой решается прецедентом EXTINT** (base в общем репо +
     usage локально, абсолютные URL): all-bundle — готовый базовый каталог контрактов
     экосистемы, нужен нормативный статус + правило ссылок. Заодно закрывается дыра
     `_meta`: вызовы соседних микросервисов экосистемы (не внешних АС и не платформы)
     сейчас не имеют слоя вообще (EXTINT — внешние АС, PLT — платформа).
  5. **Предусловие стабильности — проверено по all-bundle (184 сервиса, 179 с
     paths/):** operationId есть у 162, но стиль нестабилен — `update`, `create`
     (глобально неуникальны), `generateDigest_2` (авто-суффикс дедупликации
     springdoc, плывёт при регенерации). Стабильны: `METHOD + путь` и файлы
     сплит-формы (paths/, components/schemas/<домен>/<Dto>.yaml — адресация,
     созданная скиллом split-openapi-spec). → Якорь ссылок: метод+путь либо файл
     сплит-формы; operationId — после введения governance (стабильные имена как
     требование к разработке); diff-гейт на спеки в CI (breaking-change check)
     превращает «постулат стабильности» в управляемое свойство.
  6. Прецедент в нашем корпусе уже работает: control-split проецирует BE-контроли
     в спеку через `x-controls` (source-ссылка + group) — связь SRS ↔ OpenAPI
     уже часть целевого формата пилота КК.
- **Уточнения по вопросам пользователя (2026-08-02):**
  1. **Назначение «обратной связи» (§5.3 п. 7) при генерации сохраняется полностью**:
     таблица остаётся той же формы (операция → задействованные артефакты), lookup
     «изменился FUN → какие контракты править» работает идентично — меняется способ
     наполнения, не назначение. Достоверность растёт (ручная таблица может лгать,
     проекция — нет); появляется новая функция — механическая проверка покрытия
     «каждая операция спеки упомянута хотя бы одним требованием» (сироты спеки
     всплывают гейтом, а не при разборе инцидента). Акт фиксации связи переезжает
     из матрицы в тело по месту вызова — туда, где связь семантически живёт.
     Гибрид для связей, не выразимых ссылками в телах (колонка ENT у операции):
     ведутся вручную отдельной колонкой, пока не станут выводимыми через цепочку
     DE (Д-10) / detailed calls; сверка линтером — только генерируемой части.
  2. **x-controls — не альтернатива матрице, а ещё одна сверяемая проекция.**
     Источник истины привязки «контроль ↔ операция» — BE-документ контролей;
     x-controls — транспорт этой привязки внутрь контракта (потребитель спеки и
     генератор видят валидационную семантику без чтения SRS); матрица — единственный
     универсальный реестр связей всех осей. Инвариант линтера (Д-13): x-controls
     в спеке ⇔ привязка в документе контролей ⇔ строка матрицы. Оси не конкурируют:
     x-controls покрывает одну ось в одной спеке, матрица — все оси комплекта.
- **Решение:** —
- **Связи:** Д-10 (DE снимает часть потребности: тождество реквизита ↔ параметры),
  Д-13 (линтер — страховка режима и сверка проекций), Д-1 (маркеры в

- **Решение:** 2026-08-02 — принят порядок внедрения вкладов **Д-14 → Д-13 → Д-12**

## Д-15. Межсервисные вызовы экосистемы: реестр опубликованных спек + карточка потребителя

- **Статус:** открыт — на обсуждении
- **Суть.** В `_meta` нет слоя для вызовов соседних микросервисов экосистемы
  (EXTINT — внешние банковские АС, PLT — платформа) — межсервисные вызовы сироты.
  Целевое состояние по пользователю: каждый сервис ведёт свою спеку, переход на
  API First идёт с разной скоростью; all-bundle собран вручную для удобства.
- **Предлагаемая конструкция — две части:**
  1. **Реестр опубликованных спецификаций экосистемы** — спека как релизный
    артефакт: сервис публикует её в реестр CI-шагом при релизе (Code First сервисы —
    сгенерированную, API First — спроектированную; скорость перехода не мешает).
    all-bundle — ручной прототип этого реестра. Восстанавливает **симметрию
    адресации**: на операцию любого сервиса можно сослаться стабильным адресом
    (метод+путь / файл сплит-формы, см. Д-12 п. 5).
  2. **Интеграционная карточка на стороне потребителя** (по образцу usage-карточек
    EXTINT): семантика использования — какие параметры шлём, как обрабатываем
    ответы и ошибки в наших сценариях, пин версии/совместимости.
- **Асимметрия «свой/чужой» — честная, а не дефект.** Для своих вызовов карточка
  не нужна: семантика уже в собственном SRS (FUN, DE, контроли), спека и ссылки
  меняются одним MR атомарно. Чужой сервис — другой репозиторий и другой релизный
  цикл: атомарности нет, чужой SRS-контекст недоступен. Карточка = локальная
  проекция недоступного чужого контекста + точка пина версии. Симметрия существует
  на уровне принципа «семантика использования всегда задокументирована рядом с
  потребителем»; симметричная нотация без карточки лишь спрятала бы реальную
  асимметрию управляемости изменений.
- **Тип карточки:** по принципу 4 политики ID (ось классификации — не в ID) — не
  новый префикс, а свойство существующей интеграционной карточки

  внешней АС в экосистему) не ломает ссылки.

    имеют; их содержимое регистрируется своими ID (CTL-NNN).
  Обе модели осмысленны (вкладка — цель внешних ссылок; cards-файл —
  физическое продолжение, адресуются карточки, не файл), но **критерий выбора
  нигде не сформулирован**. Третий составной тип (многофайловая модель данных,
  многостраничный процесс) вынудит решать заново.
- **Эскиз критерия (кандидат):** часть получает суб-ID, если на неё ссылаются
  извне как на целое (вкладка из функции/задачи); часть получает `partOf`,
  если внешние ссылки идут только на её содержимое (карточки CTL) — файл
  тогда лишь физическая упаковка.
- **Решение:** —
- **Связи:** Д-8 (политика ID), Д-16 (вкладки ЭФ), Д-13 (инвариант
  «id/partOf — ровно одно из двух» — в пуле линтера).
