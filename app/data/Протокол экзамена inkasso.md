Правила (подтверждены 2026-08-16): канон ЗАМОРОЖЕН (методология
75aecb9; поздние коммиты — только данные/прибор); заходы по разделам

чинятся сразу с пометкой — их шум кумулятивен и портит все следующие
измерения; приёмка заходов — коммитами на exam-run1, допускается
«принят с задокументированным остатком» решением аналитика.
Продукт экзамена — этот список, не документация.

## Стратегия сэмплирования (решение аналитика 2026-08-16, после захода 5)

Метрика экзамена — находки на страницу, не страницы на комплект.
Принцип: сэмплирование по осям разнообразия «тип × команда × стиль
вёрстки»; сплошное покрытие оси — только пока она даёт находки
(функции насытились к заходу 5: К-2…К-5/Э-4/Э-5 пришли с первых
партий, дальше — случайные особенности страниц). Интеграционные
классы (дозакрытия, межтиповые связи, покрытие) сохраняются финальным
заходом vision+README на СОЗНАТЕЛЬНО неполном покрытии («отложено
экзаменом» — документированная судьба страниц, сам по себе новый
класс проверки). Пересобранный план: микро-дозаход fun-bnk-04 →
ЭФ партия 1 (1–2 формы из 38 стр.) → контроли (2) → интеграция+методы
(6+2) → агенты-сэмпл (1 из 12) → ПФ-сэмпл (2) → vision+README.
ОТЛОЖЕНО: функции партия 3б (27 стр.), хвосты ЭФ/агентов/ПФ (~50 стр.)
— возврат только если пакет волн изменит соответствующий канон.
**Правило выборки партии (Парето-стратификация; решение аналитика
2026-08-16, после захода 5).** Статистика экзамена: находко-несущих
страниц ~8–25% по типам (function — 5 из 65), и они предсказуемы:
первые страницы типа + АНОМАЛИИ по дешёвым метрикам (critic/draft,
экстремальный размер, глубина дочерних, нестандартные таблицы).
Правило: для типа с N>5 страниц — стратифицированный сэмпл 3–6
страниц (по представителю каждого структурного класса типа + все
аномалии по метрикам, считаемым до прогона: wc, grep critic, глубина,
число таблиц); расширение партии — только если предыдущая дала ≥1
новую находку; тип насыщен при нуле новых классов. Оговорка:
интеграционные классы (дозакрытия, покрытие, матрица) проявляются на
связях — финальный заход и механика «отложено экзаменом» обязательны.

Межкомандное разнообразие — принцип отбора сервисов для фазы тиража
после пилота. Уточнение (аналитик, 2026-08-16): ось «команда» — это не
только вёрстка, а ИНТЕРПРЕТАЦИЯ шаблонов при формально одинаковых
шаблонах типов: стиль изложения и структурирования, варианты выноса
служебного в дочерние страницы, имена колонок, оформление заголовков.
Подтверждено пилотом: file-storage → locks → inkasso — каждый сервис
дал свою порцию калибровок. Норма процесса тиража: первый сервис
каждой новой команды — калибровочный (ожидаемые К-находки и шаблонные
дыры — свойство процесса, не дефект канона); словари и профили
сторожей держать расширяемыми данными, не кодом.

## Инструментальные калибровки (прибор, не методология)

- **К-1** (заход 1): сторож маркеров шагов сделан тип-зависимым
  (process/agent/function/notification; тип не распознан — применяется)
  — на страницах сущностей МД составные номера 1.1… — нумерация секций,
  не шаги; ложные «отсутствуют 72 из 72» (ent-001/007/008). Analyzer +
  синк; тесты (162).
- **К-2** (заход 3): обрезки ТЕКСТОВОГО CriticMarkup («++}», «{++») в
  ячейках таблиц источника исключены из требуемых значений — разметка
  правок, не содержимое (fun-bnk-04: пайп внутри `{++…++}` породил
  ячейку-обрезок «++}»); содержимое внутри правок сторожится как
  прежде (тест на НЕсрабатывание).
- **К-3** (заход 3): `_title_suspicious` бракует «чистый тип» только
  по словарю типов — одиночный латинский идентификатор (TraceID,
  SessionID) — легитимное имя параметра, generic-латиница ложно
  бракавала имена (fun-bnk-04). Тесты (166).
- **К-4** (заход 4): колонные роли параметрических таблиц не
  применяются к README-реестрам (навигационные таблицы) — колонка
  «Краткое название формы (элемент…)» реестра ЭФ ложно распознана
  ролью «путь» (75% → брак трёх названий форм). Полноту реестра
  держит сверка значений источника. Тесты (168).
- **К-5** (заход 5): гейты сверяют ЦЕЛЕВОЙ текст источника —
  `apply_critic` применяет правки CriticMarkup обеих форм (добавления —
  содержимым без маркеров и префикса задачи, удаления выпадают,
  замены — новым текстом) до всех сверок. Двусторонний инцидент:
  старый гейт ПРОВОЦИРОВАЛ перенос разметки в чистовик (fun-sys-08:
  «markup сохранён для прохождения гейта») и ПРОЩАЛ выброс содержимого
  вставок (fun-bnk-04: вставка «Доступность функции проверяется в
  соответствии с [ЦРМ]…» выброшена целиком — вскрыто сразу после
  К-5). Тесты (172, включая НЕсрабатывание: целевое содержимое
  добавлений обязано присутствовать).
- **К-9** (заход 7): история изменений источника (HTML-таблицы с шапкой
  «Дата»/«Автор») вырезается препроцессором strip_history до ВСЕХ
  сверок — её кавычечные литералы («исключен реквизит "Наименование
  клиента"») ложно требовались в карточках; md-историю режет фильтр
  check_source_tables (ретро-волна). На странице контролей: потерь
  литералов 6→3 (остаток — настоящие примечания правил). Тесты (178).

Журнал (продолжение): дозаход по сторожам захода 7 — ПРИНЯТ:
примечания ФЛК досóбраны дословно (включая опечатку источника
«Максимальные значение»), оба параметра заведены в dictionaries с

легитимен только скоуп-пункт о предсуществующем фоне. Шаблон

- **К-6** (заход 6): ячейки-изображения (`<img …>` — скриншоты/эскизы)
  исключены из требуемых значений — шаблоны запрещают перенос

- **К-7** (заход 6, по находке аналитика): отсылки к страницам

  «совпадает с источником Confluence»), locks ×1 (pageId в прозе

  чинится с будущим data-model-дозаходом locks), file-storage ×2

## Находки методологии (копятся до конца экзамена)

- **Э-1. Lifecycle-паспорт сущности** (ent-003, ent-005; заход 1).
  Страницы МД ведут паспорт-таблицу «Назначение / Использование
  сущности / Когда создается запись / Когда изменяется запись» со
  ссылками на функции-создатели. Шаблон data-model про неё молчит →
  агент не перенёс, гейт таблиц требует. Вопросы к волне: куда
  переносится (карточка сущности? связи в функции при их заходе —
  межтиповое?); «Когда создается…» — это готовые связи ENT↔FUN.
- **Э-2. Таблица маппинга БД** (ent-002; заход 1). Источник даёт
  готовый маппинг «Наименование поля ↔ Наименование поля в БД»
  (13 строк); канон: «физическую модель аналитик проектирует сам»,
  но правила про ГОТОВЫЙ маппинг источника нет — агент не перенёс,
  гейт требует.
- **Э-4. Исправление подозреваемой опечатки источника вместо
  дословного переноса + OQ** (prc-002 шаг 14; заход 2). Источник
  (без critic-разметки): «Изменить статус документа на "SIGNED_2"» в
  шаге удаления — очевидная копипаста-опечатка; агент перенёс своё
  предположение `DELETED` и лишь задокументировал спорным местом.
  Канон-прецедент обратный (locks «шаг №1.3»: дословно + OQ), но
  ЯВНОГО правила в create-process/шаблоне нет. Гейт литералов не
  ловит: литерал "SIGNED_2" присутствует в карточке в других шагах
  (сторож ищет по всей карточке, не по месту). Волна-кандидат: правило
  «подозрение на опечатку — переносить дословно + OQ» в create-artifact
  (общее для reverse) + подумать о месте-чувствительности сторожа.
- **Э-5. Сжатие длинного алгоритма невидимо механике** (fun-cl-10;
  заход 4). Источник «Функция подписи документа» — 370 строк, ~100
  шагов с ОДИНОЧНОЙ нумерацией; карточка — 58 строк, агент сам
  задокументировал сжатие спорным местом. Сторож маркеров сознательно
  не собирает одиночные номера (шум счётчиков) — нашлись только
  100.1–100.3; 17 литералов уцелели в сжатом тексте → все гейты ✓.
  Кандидаты волны: сборщик одиночных номеров при длинной
  последовательности (1..N, N≥5, strong/первые колонки); правило
  «алгоритм переносится целиком» уже подразумевается — нужна механика.
  Карточка fun-cl-10 требует пере-заноса при пакете волн.
- **Э-7. Отсылка вместо переноса** (scr-cl-02.1; заход 6; находка
  аналитика). Содержимое полей («статика и источники значений»)
  заменено 40 отсылками «по таблице полей источника page NNN» —
  потеря большого объёма + запрещённые ссылки на источник; словарь
  маркеров сокращения класс не покрывал (нет буквального «см.
  источник»). Механизировано К-7; содержательный пере-занос полей —
  дозаходом. Кандидат волны: правило «отсылка к источнику не заменяет
  перенос» явно в create-artifact.
- **Э-8. Судьба page_id-таблиц матрицы** (обсуждение аналитика,
  заход 6; сверено с Д-18-копилкой; ИТОГ — таблицы ОСТАЮТСЯ).
  Исходное предложение «убрать, чтобы не провоцировать отсылки»
  отклонено после разбора: (1) множественность «одна страница →
  несколько карточек» ЛЕГИТИМНА и системна (вкладки ЭФ, control-split
  FE/BE, межтиповые страницы, группы data-model) — правило
  единственности главной связало бы руки; (2) по Д-18 таблица
  «page_id → покрывающий ID» — авторитет разрешения владельца для
  резолвера миграционного связывания; (3) провокация агентов снята
  К-7 (тела карточек сторожатся; матрица и frontmatter — единственные
  легальные носители page_id). Кандидат волны сужен: канонизировать
  формат таблицы «Источники Confluence» в правилах матрицы
  (create-artifact §6) как служебный реестр соответствий — сейчас это
  стихийная практика агентов.
- **Э-9. Линия глубокой модели ЭФ не влита в _meta** (scr-cl-02.1;
  заход 6 + разбор аналитика; КРУПНЕЙШАЯ находка экзамена). Карточки
  структурно верны (FLD-статика с биекцией, EV — влиты ранее), но
  семантический слой проработанной модели отсутствует в каноне _meta:
  элемент данных/представления (Д-10), нормированный словарь
  статик-атрибутов (видимость, формат, предзаполнение, подсказка,
  поиск, сортировка, доступность, логика установки), межформенные
  связи представлений, кнопки (Д-16), выделение контролей R/V (модель
  ЭФ v2 analyzer-скиллов). Этапность внедрения (решение аналитика
  2026-08-16, контроли ОТЛОЖЕНЫ — команды не готовы, связка не
  неразрывна: R/V — надстройка над статикой):
  Живой пример нужды этапа 1 (аналитик, свежая версия карточки):
  FLD-14 «Светофор» — условие «Если настройка … ≠ „Не отображать“, то

  «Видимость:» — читатель гадает, к какому атрибуту относится текст.

- **Э-10. Таблицы параметров функций: сетка нормализатора как формат +
  состав колонок не канонизирован** (fun-cl-03/18/20, партия 2;
  находки аналитика, заход 8). Три дефекта одного корня: (1) тройная
  шапка «Название параметра» — протяжка colspan-лесенки уровней из
  sidecar-сетки перенесена как формат карточки; (2) колонки «Код

  кодов не даёт, суррогаты не выдумывать — симметрия с INTC);
  (3) корень: шаблон function НЕ фиксирует состав колонок таблицы
  параметров — форматы плавают по комплектам (locks vs exam vs INTC).
  Волна-кандидат: канонизировать единый состав «№ | Код параметра |
  Название параметра | Тип | Обяз. | Кратность | Правила/Описание» с
  номерной вложенностью уровней (1, 1.1) для function И
  internal-contracts; механизация — К-10 (сторож дублей шапки).
- **Э-12. Классификация методов и модель авторизации** (заход 8;
  семантический разбор с аналитиком, решения 2026-08-16). «Метод» в
  до-AI аналитике — три разных сущности; дерево-определитель для
  канона (create-artifact/диспетчер):
  1) страница в разделе Интеграций / формат интеграционного шаблона /
     внешняя АС → ИНТЕГРАЦИОННЫЙ метод: контракт →
     docs-external-contracts, вызов → contract-calls; асинхронные (MQ)
     — оба направления сообщений; идеал реализации — подкаталог
     asyncapi/ рядом с api/ (generate-async-contracts);
  2) раздел «Методы» на ВЕРХНЕМ уровне каталога сервиса (рядом с
     Функции, Контроли, Модель данных, Процессы, Нотификации,
     Интеграции, Агенты) ИЛИ признаки настоящего эндпоинта
     (REST/URL/MQ) с ТУЗ → метод-как-СИСТЕМНАЯ-функция: FUN-SYS
     (поведение) + INTC (контракт) — INTC заводится ТОЛЬКО при
     признаках эндпоинта;
  3) вызывается из шагов функций, эндпоинта/авторизации нет (в т.ч.
     «Методы» как ПОДкаталог Функций) → БИБЛИОТЕЧНАЯ процедура:
     FUN-SYS с пометкой «библиотечная процедура; вызывается только из
     шагов функций комплекта» (решение (а) — обратимо: пометка
     механически выявляема, миграция в отдельный тип позже);
     параметры — единым форматом таблиц (Э-10/Э-11), БЕЗ «Авторизации»;
  4) не подпадает → открытый вопрос (человеческий фактор легален).
  Модель авторизации: «Авторизация:» — обязательная строка паспорта
  КОНТРАКТОВ, ровно одно значение: Bearer token (CL/BNK) XOR Basic
  authorization (ТУЗ/системные); оба сразу — НИКОГДА (безопасность:
  финансовые операции по логину-паролю недопустимы). Reverse при
  молчании источника: выводить по контексту вызова МОЖНО, но всегда +
  OQ для ручного разбора. «Доступность» для FUN-CL/BNK ОБЯЗАНА
  упоминать привилегии/права (вызов всегда по токену с проверкой);
  формула SYS: «Системная функция; вызов с ТУЗ; роли и привилегии не
  применяются». Определение контура: привилегии упомянуты → CL/BNK;
  нет привилегий и нет «Клиент:»/«Банк:» в title → кандидат SYS;
  нет привилегий при «Клиент:»/«Банк:» в title → OQ.
  Механизация: сторож «FUN-CL/BNK без привилегий в Доступности» —
  WARNING (не брак; подсветит существующие комплекты — принято как
