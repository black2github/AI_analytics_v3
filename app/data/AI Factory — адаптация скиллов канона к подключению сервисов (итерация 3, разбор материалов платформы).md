## 1. Принципиальный уровень

### 1.1. Платформа — не потребитель нашего канона, а второй канон той же родословной

Главный факт. У платформы есть собственный «Канон комплекта документов аналитики»
(`docs-kit-canon.md`), раскладка (общая по умолчанию + паспорт проекта ЭКО, md + yaml), нотация и
20 навыков аналитика — по одному на тип документа с тем же набором типов и тех же схем
идентификаторов, что у нас: `FUN`, `SCR`, `CTL`/`CTL-GRP`, `ENT`/`EXT`, `PROC`, `SM`, `PRN`,
`CALL-EXT`/`CALL-INT`, `EXTINT`, `NTF`, `RBAC`, `F`/`UC`/`BR`/`ТР`, `VIS`/`GLO`. Совпадают не только
имена — совпадают решения, которые мы принимали на пилоте: карточки контролей в `cards-<slug>.md` с
`partOf: CTL-000`, `dictionaries.md` с `partOf: ENT-000`, событийная модель экранов `FLD/EV/B/MSG`,
«внешние вызовы не сворачиваются», реестры разделов `<ПРЕФИКС>-000`, статус через git, «факт без
источника не выдумывается», нотация — прямая копия `eco-techbook standards/analytics/notation.md`
(платформа это и пишет: «источник нотации — методология Экосистемы»).

Расхождения тоже есть (реестр — раздел 3). Но вывод принципиальный: задача «адаптировать скиллы
канона к платформе» — это не задача адаптации, а задача **двух канонов одной родословной, у которых
нет общего дома**. Ровно принцип 3 итерации 2 (один дом у факта), только на уровне двух
организаций: сегодня одни и те же нормы записаны в eco-techbook, в `_meta` канона и в
`analytics-docs-kit` платформы тремя редакциями, и расходятся они уже сейчас (HEAD/ветка, место
AsyncAPI, семантика `CALL-INT`, `title`).

### 1.2. Трёхслойная модель норм — главное, что стоит заимствовать

Платформа разделила то, что у нас смешано:

| Слой | Что содержит | Как переопределяется |
|---|---|---|
| Канон (`docs-kit-canon.md`) | **правила**: слои, форма ID, выдача ID, маршрутизация интеграций, кросс-ссылки, frontmatter | не переопределяется; «расхождение навыка с каноном — дефект навыка» |
| Раскладка (`docs-kit-layout.md` + `.yaml`) | **значения проекта**: репозитории и пространства, дерево, сегменты ID (контуры), имя матрицы и разделов, где живут базовые контракты, закрытый набор `type` | проект заменяет файл целиком по тому же пути (ЭКО так и сделал) |
| README комплекта | **значения сервиса**: контуры, части («Подсервисы»), «Условные обозначения», объявленные отличия | «объявленное отличие — не дефект; необъяснённое — вопрос человеку, а не исправление» |

Плюс навык = «как изготовить документ своего типа», и ничего о слоях и ID («здесь, и только
здесь»). Это и есть компилируемая доставка из итерации 2: параметр проекта — один файл-оверлей, а
не правка двадцати навыков. Наши `conventions.md` и `_meta` держат правила и значения ЭКО вместе
(контуры `CL/BNK/SYS` прописаны в правилах выдачи ID), поэтому любое значение у нас размножено.

Следствие: наш eco-techbook — естественный **источник** для паспорта раскладки ЭКО, а не его
конкурент. Сегодня паспорт написан руками и уже отстал на две недели.

### 1.3. Проверка: где платформа детерминирована, а где вероятностна

Платформенный гейт трёхступенчатый: детерминированный валидатор → независимый AI-ревьюер фазы
(до двух раундов с автодоработкой) → строгий HITL (на аналитических фазах человек обязан ответить
на каждый открытый вопрос). Валидатор проверяет только структуру: UTF-8, frontmatter, `id|partOf`,
уникальность ID, локальные ссылки, YAML/JSON, `$ref`, `operationId`, матрица в корне комплекта,
запрет обёртки `docs/`. **Содержание проверяет ревьюер-LLM** — по чек-листам навыков и 15 проверкам
согласованности `artifact-consistency`, то есть вероятностно.

Это зеркально нашей ситуации: наш прибор силён именно в содержании (дословность, полнота таблиц,
литералы, шаги — потому что есть источник), а по структуре слабее их валидатора (у нас нет
проверки `$ref`, `operationId`, обёртки). У платформы нет источника в нашем смысле — поэтому
содержательная сверка отдана ревьюеру. Принцип 1 (проверка строже порождения) у них выполнен для
формы и не выполнен для содержания; у нас — наоборот для forward. Две системы дополняют друг друга,
и это аргумент за общий набор сторожей, а не за два.

### 1.4. Источник для forward у платформы есть — это план и доказательства

Ответ на вопрос итерации 1 «что такое вход forward». Планировщик аналитики производит
`analytics_plan` (работы `BA-NN`/`SA-NN`: ровно одно действие и один документ, без «либо») и
`analytics_evidence` (строки `E-NN`: репозиторий, ветка, полный SHA, документ, проверяемый вывод,
вердикт `новое / есть частично / уже есть / противоречит`, краткое доказательство). BA и SA правят
только документы из строк плана; факт берут из evidence, постановки или ответа человека; всё
остальное — запись реестра. Это и есть «профиль входа» из P-01, уже реализованный: вход имеет
адрес (SHA), ID элементов (`E-NN`, `BA-NN`) и правило «нет факта — вопрос». Наш reverse отличается
только типом источника (страница выгрузки вместо `E-NN`).

### 1.5. Квантование неопределённости — реестр рана вне git

Реестр OQ/AS/HO платформы — то, что в итерации 2 названо P-12 (реестр решений как артефакт):
идентификаторы выдаёт оркестратор, типы разведены по оси «кто резолвит», два теста перед вопросом
(ценность, риск), темы «обязан спросить» (деньги, доступы, регуляторика, поведение без аналога,
противоречие источников), приоритеты, маршрутизация, строгий гейт, права ревьюера (только
опрокинуть допущение), правило «ответ человека применяется буквально, не закрывший вопрос ответ —
уточняющий OQ». Решения человека — высший источник, выше AI-ревьюера.

Два отличия от нашей модели, оба принципиальные:

- реестр живёт **вне git**, в оркестраторе, с областью **ран** (одна задача); в документы вопросы
  не пишутся, `open-questions.md` создавать запрещено. У нас реестр — файлы `open-questions.md` и
  `feedback.md` в src-репозитории с областью **комплект** (вся миграция, месяцы);
- у платформы решение человека фиксируется в реестре и в `work_report`, у нас — в промпте этапа
  (прецедент FB-08: решение в промпте исполнилось буквально).

Это не конфликт по существу: платформа работает с docs-репозиториями, наш `open-questions.md` лежит
в src. Но при подключении мигрированного сервиса накопленные OQ и долги не видны платформе ни в
каком виде — это разрыв, который надо закрывать (раздел 4, P-06 и P-12 переформулированы).

## 2. Что меняет наше понимание

1. **Forward у канона не нужен.** Платформа — это и есть forward-система для BRD/SRS, с планом как
   источником. Писать forward-разделы в семь наших шаблонов (P-03) значит завести третью редакцию
   тех же правил. Снимается в пользу общего дома норм.
2. **Канон — спецификация reverse, не спецификация агента платформы.** Роль канона после
   переезда сервиса — миграция и нормы ЭКО; роль навыков платформы — развитие. Граница проходит по
   источнику: выгрузка Confluence → канон; план и постановка → платформа. Общее — нормы комплекта,
   и у них должен быть один дом.
3. **DoR подключения уже существует — неявно, в каноне и валидаторе платформы.** Комплект пригоден,
   если: корень без обёртки `docs/`; матрица в корне с разделами «реестр выданных ID», «Реестр ID
   бизнес-слоя», гейты BRD, «Покрытие: API ↔ SRS»; README комплекта с «Условными обозначениями»
   (контуры, «Подсервисы»); frontmatter `id|partOf`, `type`, `service`; реестры `<ПРЕФИКС>-000`;
   нет `api/`; в телах нет ссылок на Confluence и код; типы вне закрытого набора читаются «как
   документ без навыка» и не правятся. Паспорт готовности (P-02) теперь можно не придумывать, а
   списать и, главное, **частично прогнать их же валидатором на наших комплектах** [проверить —
   скрипты на реальном комплекте не запускались].
4. **Мигрированный комплект платформа трогать не будет там, где он отличается.** Правило
   «существующий комплект не перестраивай; расхождение — OQ» защищает миграцию: наши `INTC`,
   `LIBC`, `PLT`, `agent`, `instruction` платформа читает как источник и не создаёт. Но и не
   развивает: собственные методы сервиса у неё — API-слой, карточки `INTC` для них она не заведёт.
   Это согласуется с нашим решением о двух состояниях (`INTC` до API First, YAML после), но
   переходное состояние платформе неизвестно.
5. **Руководитель принёс нам решения платформы.** «API-артефактов в docs-репозиториях НЕТ»,
   «покрытие API ↔ SRS только в матрице», «ссылка `Источник:` на файл спецификации» — это дословно
   канон платформы. Мы исполнили это срезами 1–3. Но по двум пунктам наши решения с каноном
   платформы разошлись (ветка в ссылке на код, место AsyncAPI) — раздел 3.
6. **Асинхронные контракты у платформы пишет SA в репозитории кода** (`api-asyncapi`, AsyncAPI 3.0,
   без генерации кода) — наше снятие генерации из канона (срез 3) этому соответствует; реестр
   операций для людей в `internal-contract` платформа не ведёт, но и не запрещает (документ без
   навыка).

## 5а. Уточнение процесса (владелец, 2026-10-07) — что оно меняет в разборе

Роадмап миграции: основа комплекта создаётся в рабочем репозитории `src-<service-id>` (EAS) →
валидация (приёмка акцептующим, отсутствие незакрытых вопросов в `open-questions.md`) → перенос
комплекта в целевой репозиторий `docs-<service-id>` (EAN); служебные файлы миграции (промпты,
`sandbox/`, журналы, `open-questions.md`) в целевой репозиторий не переносятся. Руководитель —
участник развития платформы и периодически снимает копии текущего канона; отсюда отставание
паспорта ЭКО.

- **R-07, R-08 — не разрывы, а устройство.** Платформа видит комплект только после переноса: без
  обёртки `docs/`, без `open-questions.md`, с закрытыми вопросами. Поэтому отсутствие OQ в
  платформе не пробел, а следствие гейта переноса. Мост реестров (P-18) сужается до долгов
  матрицы, которые переживают перенос (межсервисные «у владельца»), — вопросы не переезжают по
  построению.
- **P-02 получает место в процессе: это гейт переноса.** Паспорт готовности = проверка перед
  переносом: вопросы закрыты, комплект в корне (без `docs/`), служебные файлы отфильтрованы,
  валидатор платформы на результате чистый, README комплекта несёт «Условные обозначения» в форме
  платформы. Пять дефектов КК из замера (три невалидных JSON, две битые ссылки) — то, что гейт
  переноса должен ловить до переезда.
- **P-17 — не переговоры двух организаций, а один владелец и процедура.** «Один дом норм» решается
  предложением руководителю: паспорт ЭКО собирать из стандартов и каталога инструментом (сборщик
  делаем мы). Это снимает с него ручное копирование — выигрыш обеим сторонам.
- **Приоритет — скорость переезда без переделок.** Контекст (сервисы должны быстро начать
  развиваться в платформе, за этим следит руководство) смещает веса: выше всего то, что гарантирует
  первым мигрированным сервисам чистый вход в платформу — гейт переноса (P-02), два сторожа из
  валидатора (P-20), README в форме платформы (P-19), сборка паспорта (P-11); ниже —
  архитектурные расхождения, не мешающие первому прогону (R-03 снимок `CALL-INT`, P-14 ID
  инструментом). Записка руководителю по R-01/R-02 переформулирована: это согласование двух
  редакций у одного владельца, а не спор сторон.
