## 1. Что сегодня не определено (разрыв между эскизом и промптами)

1. **Единица плана.** `prompt-plan.md` исходит из одного сервиса: входные данные — «Сервис / service-id», `<выход>` = `<src>/docs`, паспорт миграции на сервис. Для домена пункт ДОМЕН шага 2а говорит о «кусках плана», но не говорит, один ли это документ, как он утверждается и переживает ли сессия планировщика домен в 1500 страниц (ЦР — 1539).
2. **Раскладка `<выход>`.** Прибор узнаёт домен по таблице сервисов в README *родителя* комплекта. Для миграции в `src` это означает `<src>/docs/` = корень домена (рамка), `<src>/docs/<service-id>/` = комплекты. Промпт этого не задаёт; `transfer_gate` переносит `<src>/docs` как один комплект.
3. **Координатор.** Состояние и журнал — «два файла в корне src-репо», шаблон состояния — «Состояние координации — <сервис>» с одним этапом и одним базлайном. У домена одновременно живут несколько комплектов, несколько базлайнов и, возможно, несколько сессий.
4. **OQ, feedback, акцептующий.** Протокол знает один `open-questions.md`, один `feedback.md`, одного акцептующего. ЦР де-факто ведёт OQ по файлу на сервис.
5. **Рамка домена как объект миграции.** Этапы рамки (`README.md` корня, `domain-vision.md`, `glossary.md` домена) ни один промпт не описывает; гейт корень домена не проверяет (прибор включает доменные правила только из комплекта).

Рекомендация — **В**. Это и есть практика ЦР, выраженная правилом: их план (`plans/план-миграции.md`) строился сервис за сервисом, этапы 0–2 (домен, lib) — сразу, этапы 3–7 (сервисы) — по мере готовности, 9–12 (домен) — в конце.

**Правила варианта В:**

- Паспорт плана домена: таблица сервисов домена (из профиля) с колонками «порядок», «статус карточек» (каркас / детализирован / в работе / завершён), «акцептующий» (если делегирован).
- Коды этапов: рамка — `DOM-<ПРЕФИКС>-NN` (`DOM-PRE-01` корень и инфраструктура, `DOM-FIN-01` финальная сверка домена); общий сервис — `SHR-<ПРЕФИКС>-NN`; сервисы — `<СЛОТ>-<ПРЕФИКС>-NN`, где СЛОТ — слот сервиса из таблицы, у сервиса со «Слот: нет» — первые буквы `service-id` по правилу префиксов (уникальность в плане, закрепляется в реестре этапов). Куски внутри сервиса — как у одиночного (`<СЛОТ>-COM-01`, `<СЛОТ>-<ЧАСТЬ>-01`).
- Детализация сервиса — тот же `prompt-plan.md`, блок входных данных получает поле «Режим: детализация сервиса `<service-id>` по плану `<путь>`»; шаги 1–3 выполняются только в объёме строк описи этого сервиса; шаг 4 дописывает карточки в реестр плана и собирает промпт первого этапа сервиса. Утверждает акцептующий сервиса.
- Разметка «ветвь → сервис» утверждается один раз в фазе A вместе с каркасом; детализация её не меняет (изменение — правка профиля отдельным решением, как сейчас для подсервисов).

### 5.2. Раскладка `<выход>` и перенос

Решение, вытекающее из прибора: `<выход домена>` = `<src>/docs/` — корень домена с рамкой; комплект сервиса — `<src>/docs/<service-id>/`; гейт этапа — `selfcheck.py --docs <src>/docs/<service-id>`. Перенос в `docs-<domain-slug>` — по комплектам (`transfer_gate` на каждый `<service-id>`) плюс рамка корня. Нужна доработка прибора:

- `selfcheck.py --docs <корень домена>`: распознать корень (таблица сервисов в собственном README) и проверить рамку — наличие `domain-vision.md` (`VIS-000`, тип `domain-vision`, раздел «Карта сервисов домена», состав совпадает с таблицей), `glossary.md` (`GLO-000`), строка режима глоссария, каталоги таблицы существуют; комплекты при этом не сканируются (у каждого свой гейт);
- `transfer_gate.py`: режим домена — `--docs docs/<service-id>` с проверкой, что корень `docs/` несёт рамку, и отдельная проверка рамки при переносе корня.

Это срез прибора C2, без него план домена исполнять можно, но рамку гейт не судит.

### 5.3. Что ещё меняется в `prompt-plan.md`

- Входные данные: «Сервис» → «Сервис либо домен»: для домена — `domain-slug`, таблица сервисов из профиля; каждый `service-id` таблицы (включая `shared`) обязан быть в `services.json` с `repo` внутрь доменного репо и полем `domain` до старта — иначе стоп, как сейчас для одиночного сервиса.
- Шаг 2а: пункт ДОМЕН дополняется ссылкой на 5.1 (каркас/детализация) и 5.2 (раскладка).
- Шаг 4: паспорт домена; п. 10 «Промпт первого этапа» — первого этапа каркаса (`DOM-PRE-01`); для каждого сервиса промпт первого этапа собирается при детализации.
- Нарезка по ёмкости и факторизация карточек — без изменений (уже работают на масштабе КК).

## 7. Решения владельца (2026-10-13)

Критерий выбора — устойчивость и простота для акцептующего: миграция домена — редкое событие,
предсказуемость важнее календарного выигрыша. Принят **последовательный вариант**: домен
мигрируется как цепочка одиночных сервисов, в каждый момент времени в работе один комплект.

| Развилка | Решение |
| -------- | ------- |
| 5.1 единица плана | **В**: один план домена; в фазе A утверждается каркас (паспорт домена, опись, разметка «ветвь → сервис → зона», порядок сервисов, карточки `DOM-*` и `SHR-*`, промпт `DOM-PRE-01`); карточки каждого сервиса дописываются в тот же план отдельным запуском планировщика в режиме «детализация сервиса» перед его стартом. Детализация нужна не ради параллели, а потому что сессия планировщика не доживает до последнего сервиса |
| 5.2 выход | `<src>/docs/` — корень домена с рамкой, `<src>/docs/<service-id>/` — комплекты, гейт на каждый. Срез прибора C2 (гейт корня домена, режим домена в переносе) **отложен до первого нового домена**; до него рамку принимает акцептующий по чек-листу шаблона `domain-vision.md` |
| 6.1 сессии, журнал, состояние | **А**: одно состояние и один журнал на домен; в состоянии строка «сервис в работе», записи журнала с префиксом `[<service-id>]` либо `[DOM]`; сессия координатора привязана к сервису в работе, смена сервиса — передача, как смена этапа |
| 6.2 OQ, feedback, акцептующий | **А**: один `open-questions.md` со сквозной нумерацией и колонкой «Сервис», один `feedback.md`, один акцептующий; делегирование по сервису — строка паспорта, если понадобится |
| Параллель | по сессиям и клонам — не нормируется; параллель исполнителей под одним координатором в одном клоне допускается без отдельной нормы (таблица активных сервисов в состоянии вместо строки) — к ней возвращаемся по первой реальной нужде |
| Срезы | A2 — канон: `prompt-plan.md`, `prompt-coordinator.md`, `track-coordinator.md`, `track-manual.md`, `templates/coordination-state.md`, `reference.md`, SF-03; стандарт — одна фраза в `conventions` §3.2 «Порядок миграции» (после A2); C2 — отложен |

Что это означает для акцептующего сверх трека одиночного сервиса: два момента — фаза A
утверждает каркас домена, перед каждым сервисом один запуск планировщика «детализируй
сервис X». Один клон, одно состояние, один журнал, один OQ, один accept, один исполнитель
за раз; гейт, протокол и координатор работают без изменений.
