Термины. **Платформа** в этом документе — AI Factory, платформа forward-разработки сервисов

## Как проверить комплект

1. Записать, какой сервис, какую версию и какие возможности проверяем. Указать, для какого состояния сервиса написана документация: существующее поведение или согласованное изменение. Для будущего изменения зафиксировать границы отдельно.
2. Составить перечни проверяемых объектов: возможностей, сценариев, данных, состояний, действий с ограничением доступа, операций API, обменов, формируемых документов и уведомлений. Перечни могут быть в существующих документах; создавать отдельные файлы не требуется. Если полноту перечня нельзя установить, результаты, зависящие от этой полноты, остаются «Не проверено».
3. Записать исключенные возможности, причину исключения и кто подтвердил границы проверки. Нельзя исключить часть сценария, без которой не определен его результат. Проверка части сервиса дает заключение только об этой части.
4. Пройти раздел 1 по отчёту прибора миграции и валидатора платформы; пройти раздел 2 по основному блоку и выбрать дополнительные пункты по возможностям сервиса. Для каждого PASS указать перечень проверенных объектов и ссылку на доказательство. Для FAIL достаточно одного подтвержденного нарушения; его место и исправление записываются в протоколе.
5. Повторить проверку исправленных положений и связанных описаний на новой версии документации. Название «эталон», наличие файла или закрытие вопроса без отражения решения в документах не дают PASS.

| Результат | Условия оценки |
|---|---|
| PASS — выполнено | Все относящиеся к критерию объекты выбранного объема проверены; есть ссылки на подтверждающее содержание. |
| FAIL — не выполнено | Найдено отсутствующее обязательное описание, противоречие или неверный материал. Указан конкретный пример. |
| N/A — неприменимо | Такой возможности или свойства нет в выбранном объеме. Причина записана; отсутствие нужной документации не является причиной N/A. |
| Не проверено | Объекты проверены не полностью, источник недоступен проверяющему или данных для вывода недостаточно. Такой результат не считается PASS. |

Выборочная проверка позволяет найти нарушение, но не подтверждает выполнение критерия для всего перечня. Недоступность внешнего источника из-за отсутствия прав у проверяющего означает «Не проверено»; подтвержденный неверный адрес или отсутствие нужного документа означает FAIL.

Галочка означает PASS. Для раздела 2 формат документов свободный. Для раздела 1 обязательны структура и материалы, требования к которым определяются зафиксированными версиями эталона и скиллов. Наличие OpenAPI само по себе не является обязательным, если его не требует согласованный стандарт платформы.

# Раздел 1. Технологическая совместимость мигрируемого сервиса с платформой

Необходимое условие подключения. Критерии этого раздела проверяются автоматически там, где
проверка реализована: прибором миграции при переносе комплекта из рабочего репозитория
`src-<service-id>` в `docs-<service-id>` и валидатором платформы (`validate_analytics_docs.py`),
одной командой — гейт переноса `transfer_gate.py`. Строки отчёта гейта прилагаются к протоколу как
доказательство. Критерии без автоматической проверки (отмечены в колонке «Проверка»; гейт
перечисляет их в отчёте) проверяются вручную с доказательством — отсутствие инструмента проверку
не отменяет.

До проверки нужно зафиксировать адрес и версию действующего эталона, перечень и версии применяемых скиллов, а также требования платформы к конфигурационным файлам. Обновление эталона — отдельная задача владельца стандарта. Пока нужный эталон, скилл или правило конфигурации не определены, соответствующий критерий имеет результат «Не проверено»; считать структуру подходящей по предположению нельзя.

## Готовность подключения к AI SDLC — 8 критериев

Под двусторонней связью понимается следующее: документ сервиса ведет к используемому контракту или справочнику, а его описание использования ведет обратно к конкретному документу сервиса или записи матрицы. Обратная связь может находиться в реестре потребителей рядом с общим материалом. Изменять спецификацию внешнего поставщика ради такой ссылки не требуется. Обе стороны связи должны однозначно разрешаться.

Служебные каталоги без документации проверяются только там, где README требует эталон. | README комплекта и реестры разделов; битые ссылки — валидатор платформы; дополнительно требование платформы: раздел «Условные обозначения» с таблицами контуров и подсервисов и объявленные отличия комплекта — единственный способ, которым платформа узнаёт об отличиях |
| SDLC-09 | [ ] Каждая страница документации имеет код и название и включена в матрицу трассировки. | Код и название указаны способом, предусмотренным эталоном. Код однозначен в пределах сервиса; для общего комплекта контекст сервиса снимает совпадения кодов разных модулей. Страница доступна из матрицы и имеет предусмотренные для ее типа связи. Неиндексированные страницы и ссылки на другой документ вместо заявленного не допускаются. | frontmatter `id|partOf`, `type`, `service`; реестр ID матрицы — прибор миграции и валидатор платформы |

Репозиторий внешних контрактов: [EAN/docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts). Для проверки его содержимого используются конкретные версии, а не только адрес изменяемой ветки.

## Условия переноса — 5 критериев (предложение, коды предварительные)

Условия, которых в v1.1 нет, но которые требует канон миграции и валидатор платформы. Платформа
предложила подтверждённые условия добавить в критерии явно; коды `TRF-NN` — до решения рабочей группы (возможна
нумерация в составе блока SDLC как `SDLC-12…16`). Все пять проверяются гейтом переноса.

| ID | Критерий | Что должно быть для PASS | Проверка |
|---|---|---|---|
| TRF-01 | [ ] Комплект лежит в корне репозитория документации без обёртки `docs/`. | Корень содержит `README.md`, `traceability-matrix.md`, `srs/` (и `brd/`, если есть); каталога `docs/` нет ни в корне, ни внутри комплекта. | гейт переноса: сборка в целевой раскладке; валидатор платформы `E_KIT_DOCS_WRAPPER` |
| TRF-02 | [ ] Служебные файлы миграции в комплект не перенесены. | В репозитории документации нет `open-questions.md`, `feedback.md`, журналов координации, `prompts/`, `sandbox/`, `sources/`, нормализованных копий `*.tables.md`, заполненных промптов `*.filled.md`. | гейт переноса: фильтр при сборке, строка «служебных файлов миграции не перенесено: N» |
| TRF-03 | [ ] Контрактов OpenAPI/AsyncAPI в комплекте нет. | Нет каталога `api/` и YAML с `openapi:`/`asyncapi:`; связь операций с требованиями — только раздел «Покрытие: API ↔ SRS» матрицы со ссылками на репозиторий кода. | гейт переноса; прибор `selfcheck` (контракты в комплекте) |
| TRF-04 | [ ] Типы документов комплекта объявлены. | Каждый `type` из frontmatter либо входит в закрытый набор платформы, либо описан в README комплекта («Условные обозначения», таблица типов) с назначением и каталогом; типы вне набора перечислены в отчёте гейта как исключения к согласованию (SDLC-01). | гейт переноса (строки TRF-04); прибор: сторож самоописания README |
| TRF-05 | [ ] Межрепозиторные ссылки — по действующему стандарту. | Ссылки внутри docs-контура (базовые контракты, другие комплекты) — через `HEAD`; ссылки в репозиторий кода — по правилу стандарта ЭКО (сегодня `HEAD`; вопрос 1 письма платформе); имя ветки docs-репозитория в ссылки не подставляется. | прибор `selfcheck`: сторож ссылок матрицы «API ↔ SRS»; сторож ссылок на `docs-external-contracts` — добавить |

Перед переносом открытые вопросы журнала `open-questions.md` либо закрыты, либо переведены в строки
долга матрицы. Строка несёт вопрос целиком — формулировку, причину, ответственного, ограничение на
разработку, условие закрытия и номер источника (`OQ-NNN`), потому что журнал в репозиторий
документации не переносится. Если
ответ на вопрос — отсутствующий документ, допустима строка долга по ссылке с упоминанием `OQ-NNN`.
Гейт блокирует открытый вопрос без строки и строку с неполными полями (CORE-20). Раздел матрицы
«Долги по ссылкам» содержит все долги комплекта, не только отсутствующие ссылки: виды — долг по
ссылке, открытый вопрос, противоречие, правило на изображении, источник недоступен (имя раздела
историческое, переименование — в v1.3). Долг ограничивает использование затронутых карточек —
`FROM-ID` и карточек, ссылающихся на неё (перечень считает прибор); пока долг не закрыт, задача,
реализующая или изменяющая их поведение, допускается к разработке только по записанному решению
владельца документации. Условие закрытия — по виду долга; у строки без цели поле «закрытие» уточняет
его (комментарии платформы к CORE-08, CORE-14, CORE-17, CORE-20, SDLC-10).

# Раздел 2. Качество аналитики

Гигиенический минимум качества самих требований. В процессе миграции аналитика не лечится: дефекты
источника переносятся как есть и фиксируются как долги. Раздел проверяется отдельным шагом после
переноса и до подключения; исполнитель — аналитик сервиса, выборочно — ревьюер; для дельты после
подключения — навыки платформы (`requirements-quality-review`, `artifact-consistency`).

## Основной блок — 12 критериев

| ID | Критерий | Что должно быть для PASS |
|---|---|---|
| CORE-01 | [ ] Указано, какую задачу решает сервис и для кого. | Названы сервис, целевой пользователь или система и результат использования. Фразы «обработка данных» без объяснения задачи недостаточно. |
| CORE-02 | [ ] Перечислены возможности, которые входят в проверку. | Для каждой возможности определено, что делает сервис и что делает внешняя система. Будущие и исключенные возможности отмечены отдельно; причины исключения записаны. |
| CORE-03 | [ ] Для действий сценария указан исполнитель. | Пользовательская роль, сервис или внешняя система названы в самом шаге либо однозначно определены для всего сценария. Слова «пользователь» недостаточно, если действуют разные роли с разными правами. |
| CORE-10 | [ ] Термины, от которых зависит поведение, имеют одно определенное значение. | Определены сущности, роли, статусы и предметные сокращения. Если один термин используется в разных значениях, указан контекст каждого значения. Общеупотребительные слова отдельно определять не требуется. |
| CORE-11 | [ ] Для каждого требования можно определить, выполнено оно или нет. | Задано наблюдаемое действие или результат. Слова «корректно», «быстро», «при необходимости» раскрыты проверяемым условием там, где от них зависит решение. |
| CORE-12 | [ ] Для каждой возможности описан полный успешный сценарий. | Указаны исходное состояние, запуск, исполнитель, шаги и результат. Для каждой развилки известен следующий шаг; событие создания документа или отправки сообщения связано с соответствующим описанием. |
| CORE-13 | [ ] Для каждого применимого сбоя или отказа описано, что произойдет дальше. | Для каждого сценария проверен перечень случаев из правил проверки. Для применимого случая указаны результат, состояние данных и последующее действие; для неприменимого — причина. Рецензенту не нужно придумывать реакцию. |
| CORE-14 | [ ] Правила выбора, запрета и расчета дают однозначный результат. | Заданы условия и результат каждого правила. Если условия могут выполниться одновременно, понятен приоритет. Формулы определяют единицы и округление, когда они влияют на результат. |
| CORE-15 | [ ] Для используемых полей можно определить допустимое значение. | Заданы смысл, тип или формат, обязательность и применимые ограничения. Для сумм и дат указаны единицы, точность или часовой пояс, если без этого значение трактуется по-разному. Допустимые справочные значения доступны по указанному источнику. |
| CORE-16 | [ ] Для объектов с состояниями описано, когда состояние меняется. | Известны все используемые состояния и их смысл. Для перехода определены исходное состояние, событие или условие и новое состояние. Понятно, как определяется допустимость перехода. |
| CORE-17 | [ ] Для действий с ограничением доступа описано, кому они разрешены. | Определены роль или субъект и дополнительные условия: принадлежность организации, владение объектом или другие ограничения, если они предусмотрены. Условие доступа определено для самой операции; видимость кнопки его не заменяет. |
| CORE-19 | [ ] Описания одного действия не противоречат друг другу. | Для одной версии и одного контекста совпадают результаты, ограничения данных, права, переходы состояний и условия обмена. Отличия между версиями или окружениями явно обозначены. |

Основной блок используется для любого комплекта. Для CORE-16 допускается N/A, если объекты не имеют состояний и переходов; для CORE-17 — если действия не имеют ограничений доступа. Для другой неприменимости также нужна конкретная причина. «Описание не найдено» означает FAIL, если известно, что оно необходимо; если это еще не установлено — «Не проверено».

## Дополнительные блоки — только по применимости

### API и сообщения — 3 критерия

Применяется, если сервис предоставляет интерфейс или принимает/публикует сообщения. Критерии проверяются для всех операций и типов сообщений выбранного объема.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| API-01 | [ ] Указано, как обратиться к каждой операции или передать каждый тип сообщения. | Для HTTP указаны метод и путь; для другого интерфейса — его способ обращения. Для сообщений определены тип и канал обмена. Указаны применяемая версия и связанный сценарий. |
| API-02 | [ ] По документации можно составить допустимый вход каждой операции. | Перечислены параметры, поля, применимые заголовки, их смысл и ограничения. Условия передачи данных указаны; отсутствие входных данных обозначено явно. Один пример без правил заполнения недостаточен. |
| API-03 | [ ] По документации можно понять каждый предусмотренный результат операции. | Описаны успешный ответ и виды ошибок, способ их различения и смысл возвращаемых полей. Для асинхронного обмена понятна связь ответа с запросом. Отсутствие ответа обозначено явно. |

### Зависимости и обмен со смежными системами — 1 критерий

Применяется при использовании внешних систем, общих функций или асинхронного обмена. Реакции на результаты обмена, таймауты и недоступность проверяются в CORE-12/13, доступность схем — в CORE-09.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| INT-01 | [ ] Для каждого обмена указан согласованный контракт, по которому он выполняется. | Определены отправитель, получатель или способ его выбора и владелец контракта. Доступен подтвержденный источник с применяемой версией или ревизией. Структура очереди или общего вызова не восстанавливается по догадке. |

### Источники данных и расчеты — 1 критерий

Применяется, если сервис получает или формирует значения, в том числе вычисляет их локально. Отсутствие внешних интеграций не делает этот пункт неприменимым. ID INT-02 сохранен.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| INT-02 | [ ] Для каждого получаемого или формируемого значения указан источник или расчет. | Указано конкретное поле источника, константа, ввод пользователя или формула. Если значение может отсутствовать, определен результат этого случая. Формулировки «из системы» или «по аналогии» без уточнения недостаточны. |

### Пользовательский интерфейс — 2 критерия

Применяется при наличии пользовательского интерфейса. Результаты действий проверяются в CORE-12/13; условная доступность элементов — по CORE-14/17 в применимом контексте.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| UI-01 | [ ] Для каждого поля ввода указано, какое значение пользователь может ввести. | Определены обязательность, ее условия и проверки значения. Если поле показывается или доступно только при определенном условии, это условие указано. Возможна ссылка на общие правила данных. |
| UI-02 | [ ] Заданы тексты сообщений, которые влияют на действия пользователя. | Указаны ошибки, предупреждения, подтверждения и сообщения о результате операции, событие показа и подстановки. Для выбора действия указаны доступные варианты и их последствия. |

### Формируемые документы — 2 критерия

Применяется при генерации печатных форм или других документов. Момент формирования проверяется в соответствующем сценарии по CORE-12.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| DOC-01 | [ ] Указано, какой документ должен быть сформирован. | Доступен действующий макет или описание структуры. Если существуют варианты, определено условие выбора; в сценарии указано событие формирования. |
| DOC-02 | [ ] Для каждого поля документа указано, как получить его значение. | Определены источник или расчет, формат вывода и результат при отсутствии исходных данных, если такой случай возможен. |

### Исходящие уведомления — 2 критерия

Применяется при отправке уведомлений пользователям или подразделениям. Прием входящего события сам по себе не означает наличие исходящего пользовательского уведомления.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| NTF-01 | [ ] Для каждого уведомления указано, когда, кому и по какому каналу его отправляют. | Определены событие, правило выбора получателя, канал и предусмотренные условия, при которых отправка не выполняется. |
| NTF-02 | [ ] Текст каждого уведомления можно получить по описанному шаблону. | Для каждого используемого канала задан текст; у каждой подстановки есть источник и правило обработки отсутствующего значения, если оно может отсутствовать. |

### Нефункциональные требования — 1 критерий

Применяется к заявленным или известным обязательным требованиям производительности, доступности, надежности, безопасности и другим характеристикам. Перед N/A нужно подтвердить, что таких требований нет в выбранном объеме. Неизвестная применимость означает «Не проверено». Не заданный показатель бизнес-цели сам по себе не является дефектом НФТ.

| ID | Критерий | Чем подтвердить |
|---|---|---|
| NFR-01 | [ ] Для каждого НФТ задан способ определить, выполнено оно или нет. | Для числового требования указаны метрика, предел и условия измерения. Для требования без числового показателя указан проверяемый результат, например запрет доступа определенной роли. Совместимость с поведением проверяется в CORE-19. |

## Готовность подключения к AI SDLC — 3 критерия

| ID | Критерий | Что должно быть для PASS |
|---|---|---|
| SDLC-06 | [ ] Состав BRD определен с учетом типа сервиса. | Для бизнес-сервиса BRD восстановлен по SRS: связи прослеживаются, противоречий между слоями нет, восстановленный материал явно обозначен и подтвержден владельцем документации. Для технического или платформенного сервиса отсутствие BRD допускается при записанном обосновании и подтверждении владельцем документации. Для смешанного комплекта решение определяется по входящим сервисам или возможностям. |
| SDLC-10 | [ ] Проведена проверка качества и согласованности требований. | Есть отчет на зафиксированной версии документации с объемом проверки, результатами применимых критериев основного и дополнительных блоков и доказательствами. Нарушения, препятствующие READY по качеству, исправлены и проверены повторно. Незавершенные проверки не скрыты за общим положительным выводом. Для выполнения можно использовать существующего агента проверки качества. |
| SDLC-11 | [ ] Перед подключением документация сопоставлена с кодом сервиса. | Есть отчет с версиями документации и кода, проверенным объемом и найденными расхождениями. Для каждого расхождения определены причина и решение владельца; необходимые исправления внесены и проверены. Существующее поведение и согласованные будущие изменения разделены. Не осталось неопределенности, какое поведение описывается и используется платформой. Непроверенные компоненты отмечены и не считаются подтвержденными. |

Для SDLC-06 отсутствие BRD у технического или платформенного сервиса является предусмотренным вариантом выполнения критерия, а не пропуском проверки («платформенный» здесь — признак `is_platform` сервиса Экосистемы, не отношение к AI Factory). SDLC-10 фиксирует результат проверки качества; повторно создавать отдельные дефекты для тех же нарушений не требуется. SDLC-10 — это итог самого раздела 2: отчёт по его критериям на зафиксированной версии.

Сверка с кодом не означает, что текст автоматически переписывается под реализацию. Ошибка может быть в коде, документации или выбранной версии сравнения. Решение фиксируется явно. Само наличие отчета без разбора и проверки необходимых исправлений не дает PASS по SDLC-11. Критерии описывают требуемые результаты проверок; инструкция по работе агентов здесь не задается.

Три критерия этого подраздела расходятся с действующими решениями миграции и ждут решения
рабочей группы: SDLC-06 — BRD до подключения или первая задача бизнес-аналитика на платформе;
SDLC-10 — READY по качеству как условие подключения или перечень доработок; SDLC-11 — сверка с
кодом как часть DoR или отдельная работа после подключения (стандарт ЭКО: SRS адаптируется из
Confluence без сверки с кодом). Формулировки критериев до решений не меняются.

Для каждого применимого критерия записать результат. Для раздела 1 результат берётся из отчёта сторожей: строка отчёта — доказательство, отсутствие сторожа у критерия — ручная проверка с пометкой. Для неприменимого блока достаточно одной записи с причиной N/A на весь блок, если она одинакова для всех его пунктов. В подразделах «Готовность подключения к AI SDLC» неприменимость оценивается отдельно по пунктам.

|---|---|---|---|---|---|
| CORE-… / API-… / SDLC-… / … | PASS / FAIL / N/A / Не проверено | | | | |

**Технологическая совместимость — READY:** все применимые критерии раздела 1 имеют PASS по отчёту прибора миграции и валидатора платформы; неприменимость остальных обоснована результатом N/A. Это необходимое условие подключения, но не достаточное.

**Качество аналитики — READY:** все применимые критерии раздела 2 имеют PASS; неприменимость остальных обоснована результатом N/A. Положительная оценка одного раздела не подтверждает другой.

**NOT READY — готовность не подтверждена:** в соответствующем разделе есть применимый FAIL или непроверенный критерий. В заключении отдельно указать нарушения и незавершенные проверки. Если раздел не проверялся, записать «Раздел не оценивался». Каждый итог относится только к записанному объему и версиям.

Для DoD измененной документации проверяются измененные положения и связанные описания; найденные ранее незакрытые дефекты сохраняются. При первичной подготовке комплекта проверяется весь применимый объем.

Не каждый недостаток оформления блокирует готовность. Он влияет на DoR, если мешает однозначно определить действие, условие, данные, доступ, результат или нужный источник. Такой недостаток получает FAIL по соответствующему критерию. Замечание о стиле без такого влияния записывается отдельно и не превращается в FAIL.
