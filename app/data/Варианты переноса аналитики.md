# Термины и определения

*Оригинальный markdown файл* - markdown файл с требованиями, полученный конвертацией из конкретной страницы Confluence внутреннего контура с сохранением информации о нереализованных требованиях со ссылками на идентификаторы Jira задач и перенесенный из внутреннего контура на внешний (конвертация с помощью **migrate_confluence_tree.py** с параметром **—task**) 

*Завершение миграции* - завершение процесса переноса требований из Confluence в markdown и затем в GitLab и завершение реализации тех требований, которые на момент миграции в markdown оставались нереализованными. Он же - момент, когда разработка требований начинает идти по целевому процессу Doc-as-Code (создание в GitLab ветки с ID → commit → MR → согласование MR → вливание в ветку main по реализации).

MR - merge request (понятие Git процессов). Запрос на вливание в базовую ветку репозитория набора изменений, выполненных в рамках другой ветки.

`legacy/` - каталог с оригинальными markdown файлами на внешнем контуре.

`critic.py` - утилита для отметки либо того, что требование с конкретным идентификатором реализован, либо исключению конкретного требования из состава требований.   

# Описание проблемы

На текущий момент при конвертации требований из Confluence внутреннего контура в markdown можно конвертировать либо срез ПРОМа, либо весь набор требований, который будет включать и нереализованные, и отложенные и т.д. Версионность по текущим процессам поддерживается в Confluence цветом и отражением в Истории изменений какой цвет какой задаче Jira соответствует. 

При вливании в GitLab по целевому процессу должно происходить по такой последовательности: создание в GitLab ветки с ID → изменение требований → commit → MR → согласование MR → вливание в ветку main по реализации.

Таким образом, сразу после конвертации Confluence страниц и переноса на внешний контур нет возможности как-либо перенести информацию о составе требований в привязке к конкретной задаче (например, в Jira). Информация потеряна. Доступны либо ПРОМ срез, либо текущий срез. Что приводит к проблемам:

1. И текущий срез и срез требований ПРОМа требуют отдельного переноса из закрытого контура. То есть требуется два переноса близких по смыслу требований. Это длительная процедура и требующая достаточного времени аналитики (работает только при логине во внутренний контур)
2. После вливания в Git ПРОМ-среза требований нужно каким-то образом по оставшейся части требований (текущий срез) пройти и проставить отметки, что реализовано, а что нет. То, что текущий сре может быть влит в репозиторий отдельной веткой проблемы НЕ решает. Так как такая разметка - это и большой ручной труд и источник большого числа ошибок. Ко всему прочему - сам процесс такого разделения пока не ясен, а при развитии сервиса нужно на что-то опираться. 

Таким образом, даже оперативно переехав во внешний контур и markdown формат команды НЕ получат возможности развивать сервис. Вместо ускорения и решения текущих проблем мы получим замедление на достаточно длительный срок.

# Предлагаемое решение

**Кратко суть:** **конвертация атрибуции из markdown текста требований в историю Git.**

**Подробности**:

Использовать текущую цветовую разметку в Confluence как основу расширения markdown разметки для того, чтобы включить в нее “цвет” требований, выраженный в виде специальных отметок, а-ля CriticMarkup, используемых Git для фиксации изменений. Git работает по принципу создания отметок вида {++текст1 текст2++}, {—текст 3 —}, {~~текст 4 > текст 5~~} и т.д.

При конвертации из Confluence в markdown в текст требований вставляются ссылки специального вида:  {++ID:…++} и т.д. для чистого markdown и  `<span class="critic-ins" data-task="ID">...</span>` для сырого HTML. В качестве ID выступает идентификатор задачи Jira строки таблицы “История изменений”, указанной тем же цветом, что и требование. 

Таким образом, “цвет” требований преобразуется в идентификатор задачи Jira и переезжает на внешний контур без отрыва от самого требования.

На внешнем контуре выполняется специальное преобразование, которое позволяет достать ПРОМ-срез + вариант требований в привязке к конкретной задаче Jira.

С учетом того, что задачи Jira в конечном итоге привязаны к одной бизнесовой задаче/эпику, собрав список задач Jira в привязке к эпику мы получим набор идентификаторов Jira конкретной версии сервиса. Именно это по сути и является полным эквивалентом “ветки” для репозитория GitLab.  Безусловно, это не отменяет необходимость последующих преобразований требований AI-агентами, но в таком раскладе задача не потерять актуальный статус реализации требований станет на порядок легче (во всяком случае для сервисов, для которых существует значительный “хвост” из нереализованных требований не несколько месяцев)  

Утилиты конвертации Confluence в markdown с CriticMarkup разметкой и обратным преобразованием - созданы (PoC завершен), что переводит вопрос полностью в практическую область: 

- каков порядок шагов (включая предварительные шаги по наведению порядка в аналитике)?
- какие ограничения возникают?
- пределы применимости подхода?
- и т.д.

### + Отдельно: скиллы на критическом пути

Стабильность скиллов как «отдельный важный момент» — она важнее выбора процесса. Любая схема с повторным прогоном агента по одному материалу требует, чтобы скилл давал воспроизводимый результат.

Это проверяется относительно быстро, до всех процессных решений: взять один реальный файл, прогнать скилл пять раз, посмотреть попарные diff. Если расхождения структурные — варианты A и A′ отпадают автоматически, остаются C и D, где каждый файл проходит через агента однократно. Если расхождения косметические — A′ жизнеспособен. Этот эксперимент стоит сделать первым.

# Варианты реализаций (специфика сервисов?)

## Вариант A - дельта

**Предлагаемый порядок действий таков**:

1. Создать с помощью AI-Агента и более-менее стабильных скиллов (это отдельный важный момент) новую/целевую версию документации и обязательно в другом каталоге - каталог AI-агента (не изменяя оригинальной markdown документации ) на основе “critic.py reject-all” вывода, то есть используя срез промышленной эксплуатации (ПРОМа).
2. Влить в git в main ветку каталог AI-агента.
3. После реализации очередной задачи, которая была в разработке на момент старта миграции,  по каталогу с оригинальной markdown документацией снимается criticMarkup метка конкретных задач. То есть выполняется:
    1. Сначала “critic.py apply ID”, где ID - реализованная задача (или набор задач)
    2. Затем снова “critic.py reject-all” - получение ПРОМ среза с учетом реализованной задачи 
    3. После чего запускается агент, **НО с жестким ограничением**: он получает инструкцию не «сгенерируй документацию заново из нового PROM-среза», а три входа:
        1. текущий файл в новой структуре (каталог агента);
        2. diff, который дал `critic.py apply GBO-12345` в `legacy/`;
        3. скилл-инструкцию «размести эту дельту в новой структуре».
        
        Упрощенно, задача агента сжимается с «перестрой документы» до «положи два абзаца туда, где им место». Выход привязан к существующему файлу (в каталоге Агента), поэтому посторонний дрейф структурно невозможен: агент физически не переписывает то, чего не касается дельты.
        
        > **Что теряется:** корпус (набор сгенеренной аналитики) перестаёт быть гарантированно консистентным с текущей версией скиллов (которые допиливаются). Решается разделением операций — полная регенерация становится **редким осознанным рефакторингом** со своим MR, не привязанным ни к какой задаче Jira, а посадки задач идут инкрементально.
        > 
4. Затем, все изменения по каталогу Агента вливаются в ветку GitLab с идентификатором, содержащим ID реализованной задачи (и прогоняется полный цикл через MR до вливания в main).

В результате в GitLab получается новый набор файлов, созданных AI-агентом с привязкой изменений по версиям. Это и есть эквивалент переноса истории изменений из внутреннего контура во внешний. 

> **Важно учитывать**, что часть информации все же будет утеряна для случая, когда одни цветные изменения в Confluence вносились поверх других цветных изменений (эвристика для этого есть, но это отдельная тема). В этом случае требуется принять такое несовершенство, либо “ручками” пройти по тем файлам, по которым были конфликты (это будет доступно в журнале миграции) и выполнить “critic.py apply ID” с указанием того ID из набора идентификаторов, который приводит к меньшим разрешениям/переделкам.
> 

Так продолжается до тех пор, пока все требования в оригинальных markdown файлах не будут реализованы в ПРОМ. После чего весь каталог с оригинальными markdown файлами архивируется и больше не участвует в изменении требований.

## Вариант B - перенос маркеров через реструктуризацию

Агент реструктурирует документ **вместе с маркерами**, с жёсткой инструкцией сохранять атрибуцию при переносе и переформулировке  (жесткие инструкции AI-агенту, что он не имеет права разрывать информацию, не обрамив ее criticMarkup отметками. С учетом, что  при переносе в чистый markdown обрамление должно происходит по принципу  {++GBO-12345: текст1++}, а при переносе в HTML таблицу в виде `<span class="critic-ins" data-task="GBO-12345">текст 1</span>` и т.д.).

Правило атрибуции формулируется просто: любой фрагмент, происходящий из размеченного текста, сохраняет метку своей задачи, в скольких бы местах он ни оказался; связь многие-ко-многим допустима. `apply` после такой реструктуризации работает корректно — так как нужно лишь снять “обёртки”.

Ломается другое, и это решающее: **`reject` перестаёт быть достоверным.** Левая часть замены и содержимое `{--…--}` ссылаются на текст ПРОМ, который после переформулировки дословно не существует. Значит представление «текущий ПРОМ» — то, что читают разработка и тестирование, — становится ненадёжным ровно в тот период, когда оно нужнее всего.

Плюс риск односторонний: это одна большая необратимая операция вместо серии малых.

Годится в одном частном случае — если реструктуризация чисто механическая (перенос без переформулировки, например разбиение таблицы полей на отдельные блоки один-к-одному). Тогда границы фрагментов сохраняются точно и `reject` остаётся корректным.

Есть ли кандидаты-сервисы для такого случая?

## Вариант C - заморозка хвоста

Не реструктурировать ничего, пока в `legacy/` есть маркеры. Новые задачи в это время ведутся штатным Doc-as-Code в старой структуре. Работа агента начинается после исчерпания хвоста.

**Плюсы:** проблема исчезает целиком. Один корпус, ноль взаимодействия агента с разметкой, ноль вопросов у аналитиков. Освободившееся время уходит на стабилизацию скиллов — а это, как вы сами отметили, отдельный важный вопрос, и он на критическом пути.

**Минусы:** ожидание, и старая структура (гигантские таблицы полей) продолжает мешать параллельной работе всё это время.

**Вариант оценивается численно, а не мнением.** Из `migration-manifest.yaml` берутся: сколько задач в хвосте, какая доля файлов содержит маркеры, за какой срок хвост исторически рассасывается. Если это 5–10 задач и 3–4 месяца — заморозка почти наверняка выгоднее любой схемы с двумя корпусами. Если 30 задач и полтора года — не годится.

По всей видимости, может подойти “замороженным”/стабильным сервисам, изменения по которым давно не вносились. Ответственным командам - проверить.

## Вариант D - послойный переход по файлам

Единица перехода — файл, а не корпус (весь набор аналитики сервиса).

- Файл без маркеров реструктурируется агентом **сразу** и переезжает в новый корпус навсегда.
- Файл с маркерами остаётся в старой структуре и обрабатывается штатно: правки внутри маркеров, `apply` при посадке задачи.
- Когда последний маркер файла снят, файл «выпускается»: агент реструктурирует его один раз, файл переезжает.

Ключевое отличие от Варианта А - **файл в каждый момент существует ровно в одном месте.** Нет двойного сопровождения, нет цикла регенерации, нет вопроса о детерминизме — каждый файл проходит через агента один раз в жизни.

**Плюсы:** аналитик получает выигрыш от новой структуры немедленно на большинстве файлов (обычно доля файлов с маркерами невелика); процесс монотонный и измеримый; объяснение помещается в три предложения.

**Минусы:** во время перехода корпус разнородный — часть файлов в старой структуре, часть в новой; сквозные вещи (матрица трассировки) неполны, пока переход не завершён; кросс-файловые преобразования блокируются, если хотя бы один участвующий файл «грязный». [Может оказаться существенно для случая  `control-split` скилла, который порождает FE- и BE-документы из одного источника: единицей выпуска становится не файл, а группа связанных файлов.]

### Сломается ли трассировка требований?

#### Суть опасений

Не имеет ли данный вариант ограниченное применение? Если взаимосвязь между файлами требований высока, то, возможно, сложно поддержать трассировку требований (или она становится неполной). Например, перенести модель данных в новую структуру - да, вполне возможно. Но использование AI-агента обычно сразу приводит к созданию матрицы трассировки требований. Она выполняется по новой структуре, где у каждого требования есть свой ID, в отличие от того, что будет получено из Confluence, где роль ID совмещена с ролью wiki ссылки. Опасения, что матрица трассировки будет усеченной. 

### Ответ

**Кратко**: матрица трассировки будет не усеченной, а грубой

**Подробно**: 

#### Матрице трассировки нужны ID, а не новая структура

Не путаем две вещи, которые агент делает одновременно, но которые имеют противоположную оптимальную гранулярность:

| Операция | Естественная единица | Стоимость | Семантический риск |
| --- | --- | --- | --- |
| Присвоение стабильных ID + построение трассировки | весь корпус сразу | низкая, механическая | нет |
| Реструктуризация (разбиение таблиц полей, `control-split` на FE/BE) | файл или кластер | высокая | есть |

Если вникнуть подробней, то матрица трассировки требует от корпуса ровно одного: чтобы каждое требование было адресуемо стабильным идентификатором. Она **не требует**, чтобы поля экранной формы были декомпозированы на атрибуты. Это разные свойства, и они разделяются.

**Если присвоить ID всему корпусу сразу — до и независимо от какой-либо реструктуризации — матрица становится полной с первого дня, а реструктуризация идёт файлами или кластерами, не влияя на её полноту.** Опасение исчезает не за счёт компромисса, а за счёт того, что операции перестают быть одной операцией.

#### Начинаем не с нуля

С одной стороны в Confluence роль ID совмещена с ролью wiki-ссылки. Это верно, но после миграции эта роль перешла к смарт-ссылкам `{{сервис:элемент}}` (смотри markdown файлы после конвертации) — а значит **пространство имён адресуемых сущностей у нас уже есть**, и резолвер к нему написан.

Не хватает двух вещей: гранулярности (сегодня адресуются элементы и сущности, а не отдельные требования) и стабильности при переформулировке. Обе добираются механически, без агента и без изменения структуры:

- заголовок раздела → ID;
- строка таблицы контролей → ID (у контролей он у вас уже есть);
- строка таблицы полей → ID.

Но это ровно та гранулярность, которая в “старой” структуре и так существует. Грубая, но стабильная и адресуемая.

#### Что это даёт сверх полноты матрицы

**Проверяемый инвариант на работу агента.** Реструктуризация обязана сохранять ID: каждый ID, присутствовавший до, присутствует после — либо явно отражён в таблице расщепления (`REQ-042` → `REQ-042.1`, `.2`, `.3`) или слияния.

Это механически проверяется в CI (обсудить с Суднициным). И это частично закрывает вопрос недетерминированности, который поднимался раньше: воспроизводимость прозы проверить нельзя, а воспроизводимость множества ID — можно. Диф ветки перестаёт быть неотсматриваемым: если набор ID сохранён, изменения структурны и локальны по построению.

**Трассировка покрывает и незавершённые задачи.** Требование, существующее пока только внутри маркера, тоже получает ID и попадает в матрицу. Когда маркер снимается, ID остаётся. Статус реализации и идентичность требования оказываются ортогональны — как и должно быть.

#### Чем платим

Присвоенные грубым единицам старой структуры, дают матрицу, **полную по связности, но неравномерную по гранулярности**. Ребро из декомпозированного требования новой структуры может вести в строку таблицы, за которой стоят три разных требования.

Это ощутимо хуже, чем целевое состояние. Но качественно лучше, чем усечённая матрица: провал в точности локален и виден, провал в связности — нет. И он сам рассасывается по мере реструктуризации, тогда как отсутствующие рёбра не восстанавливаются никогда, потому что о них никто не узнает.

#### Насколько D вообще применим — это измеряется, а не оценивается!

Риск высокой связность файлов. Проверить это можно на существующем коде: резолвер смарт-ссылок уже вычисляет граф зависимостей между файлами. Построить граф зависимостей между файлами, найти компоненты связности, посмотрите распределение размеров?

Три исхода, и каждый даёт однозначное решение:

- **есть естественные кластеры** (по сущности, по экранной форме, по агрегату) размером в единицы-десятки файлов → D работает, единица выпуска = кластер, вычисляется автоматически;
- **одна компонента покрывает большую часть корпуса** → D вырождается в C (заморозка), и это не плохо, а численный ответ: инкрементальность в таком корпусе недостижима в принципе, любой вариант будет иметь ту же проблему;
- **промежуточный случай** → выпускать крупные кластеры, мелкую периферию доводить отдельно.

Требуется оценка, сколько времени на это нужно. Оценка ответит не только на вопрос про D — размер компонент связности определяет и то, насколько вообще осмысленно `control-split` и подобные преобразования применять к отдельным файлам.

#### Итого к рекомендации?

То есть присвоение ID и построение трассировки уходят вперёд, до выбора между C и D:

1. измерить граф связности существующим резолвером;
2. присвоить ID всему корпусу механически, построить матрицу — она полная сразу, независимо от дальнейшего (перестаёт быть дорогим, если отделить присвоение ID от переписывания текста и делать только первое);
3. зафиксировать сохранение ID как обязательный инвариант скиллов реструктуризации, с проверкой в CI (обсудить с руководителем подразделения);
4. и только затем выбирать C или D — причём после шагов 1–3 цена этого выбора заметно ниже, потому что главный корпусный артефакт от него больше не зависит.
