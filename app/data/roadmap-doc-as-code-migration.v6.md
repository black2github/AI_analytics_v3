# Переезд аналитики в Git (Doc-as-Code): карта маршрута

**Для кого:** аналитик сервиса, который переносит спецификацию требований из Confluence в
GitLab. Опыт работы с Git не обязателен: нужные понятия объяснены по месту,
при выполнении нижеперечисленных команд текст из командной строки копируется как есть.

**Что здесь есть:** суть переезда (4 предложения), карта из 5 этапов,
мини-словарь и сами этапы с шагами. Технические стандарты и правила вынесены в конец.

---

## Суть в четырёх предложениях

У сервиса появляются два хранилища (репозитория): **хронология**
`src-<сервис>` — туда попадает выгрузка из Confluence и восстанавливается
история изменений требований «как было», и **рабочее пространство**
`docs-<сервис>` — там живёт аналитика в AI-aware формате, удобном и людям, и
AI-агентам. В хронологию добавляются обновления требований из Confluence пока с ним 
идет работа. После того, как Confluence будет закрыт на редактирование и будет реализована 
последняя задача из списка не реализованных на момент переезда, хронология перестанет пополнятся.
Друг в друга они никогда не копируются средствами Git — перенос делается
**преобразованием**: скилл переводит изменения задачи из текущего формата в новый.
Поэтому изменения, вносимые в хронологию, ничего не могут сломать в рабочем пространстве: 
они физически в разных местах.

## Карта маршрута

```text
Confluence ──1──> markdown ──2──> внешний контур ──3──> src-<сервис>
 (внутренний контур)                                    (архив + чистый ПРОМ)
                                                            │
                                                            4  хронология:
                                                            │  задача за задачей,
                                                            ▼  срез за срезом
                                                       src-<сервис>
                                                            ┆
                                                            5  преобразование
                                                            ┆  (скилл, не Git!)
                                                            ▼
                                                       docs-<сервис>
                                                       (AI-aware формат)
```

| Этап                  | Что получится | Где | Инструмент                                                         |
|-----------------------|---|---|--------------------------------------------------------------------|
| 1. Выгрузка           | папка markdown-файлов с разметкой задач | внутренний контур (VDI) | confluence-tree-exporter                                           |
| 2. Перенос            | та же папка на внешнем контуре | оба контура | (способ переноса необходимо уточнить у лида по аналитике команды) |
| 3. Архив              | репозиторий `src-<сервис>`: нетронутая копия + «чистый ПРОМ» | внешний | GitLab                                                             |
| 4. Хронология | история изменений по задачам, срез за срезом | внешний | critic + GitLab                                                    |
| 5. Новый формат       | AI-aware аналитика в `docs-<сервис>` | внешний | Cursor + скиллы                                                    |

Этапы 1–4 проходит каждый сервис. **Этап 5 — решение команды** (см.
«Развилка» после этапа 4).

## Шесть слов, которые понадобятся

- **Репозиторий** — хранилище файлов в GitLab с полной историей их изменений.
- **Ветка** — черновик изменений: правки копятся в ней и не видны остальным,
  пока черновик не принят.
- **Основная ветка** — содержит все принятые правки.
- **MR** (merge request) — «предложение изменений»: просьба принять ветку,
  с обсуждением и проверкой коллегой.
- **Тег** — именованная закладка на состоянии репозитория; по ней это
  состояние можно открыть в любой момент.
- **Срез** — состояние всех требований на момент завершения одной задачи.
- **ПРОМ-срез** — только требования, установленные в ПРОМ на момент переезда.

---

## Этап 1. Выгрузка из Confluence

**Что получится:** папка markdown-файлов со всеми требованиями и разметкой,
какая правка к какой задаче Jira относится.

**Где:** внутренний контур (VDI). **Инструмент:** confluence-tree-exporter.

> Видео установки и использования: <https://disk.yandex.ru/i/4vZvS0dJiukLKw>.
> Предварительно рекомендуется попробовать установить confluence-tree-exporter самостоятельно
> согласно инструкций в пакете — скорее всего вы справитесь самостоятельно и сэкономите время.

**Готово, когда:**

- папка с markdown-файлами (и картинками) лежит на диске внутреннего контура (VDI);
- в отчёте выгрузки нет отметок `UNKNOWN-#XXXXXX` — все правки привязались
  к задачам.

## Этап 2. Перенос на внешний контур

**Что получится:** та же папка файлов на внешнем контуре.

**Где:** внутренний (VDI) → внешний. **Инструмент:** специализированное ПО (инструментарий для переноса можно уточнить у лида по аналитике команды).

**Готово, когда:** папка с выгрузкой доступна на внешнем контуре.

> ⚠ Переносите папку файлов как есть, не упаковывая её в ZIP «навсегда»:
> следующему этапу нужны именно файлы.

## Этап 3. Архив: создается `src-<сервис>`

**Что получится:** репозиторий-хроника с двумя папками: `sources/raw/` —
нетронутая копия выгрузки (страховка: с неё всегда можно начать заново) и
`sources/confluence/` — «чистый ПРОМ», то есть только реализованные в ПРОМ
требования.

**Где:** внешний контур. **Инструменты:** Git, GitLab.

**Шаги:**

1. Завести репозиторий `src-<сервис>` (как — см. пошаговую инструкцию в
   [analyst-docs-guide § Новый src-репозиторий](analyst-docs-guide.md#новый-src-репозиторий)).
   Репозиторий `docs-<сервис>` на этом этапе **не нужен** — он появится на
   этапе 5, если команда туда пойдёт.
2. Положить выгрузку в папку `sources/raw/` и влить в основную ветку
   (через MR).
   > ⚠ С этого момента `sources/raw/` — только чтение, навсегда. Это
   > страховочная копия: в неё не вносят правок ни при каких условиях.
3. Скопировать `sources/raw/` в `sources/confluence/` и убрать все
   нереализованные в ПРОМе правки, выполняя команду ниже:

   ```
   run-critic.bat reject-all --path .
   ```

   (запускается по папке `sources/confluence/`).
4. Влить результат (через MR) и поставить закладку (тег) **`src/PROM`** —
   это «точка отсчёта»: утверждённое состояние аналитики, соответствующей ПРОМу на момент переезда.

**Готово, когда:** в `src-<сервис>` лежат `sources/raw/` (копия как есть)
и `sources/confluence/` (чистый ПРОМ с тегом `src/PROM`).

## Этап 4. Хронология: история изменений по задачам

**Что получится:** в `src-<сервис>` — история требований «как было»: каждая
задача Jira представлена своим срезом с закладкой-тегом. Любое прошлое
состояние открывается по тегу; чем задача изменила требования — видно в
сравнении соседних срезов.

**Где:** внешний контур. **Инструменты:** critic (в составе
confluence-tree-exporter), Git, GitLab.

**Шаги** (повторяются для каждой ещё не реализованной задачи; ветка на задачу):

1. Скопировать архив из `sources/raw/` в `sources/confluence/` заново
   (да, каждый раз заново — так задумано).
2. Добавить Jira-номер задачи к накопительному списку «реализованных»
   (список растёт с каждым шагом — это нормально).
3. Принять все задачи списка — по каждому номеру, выполняя команду ниже:

   ```
   run-critic.bat apply <JIRA-ID> --path .
   ```

4. Запомнить «хвост» — список задач, которые ещё остались, выполняя команду ниже:

   ```
   run-critic.bat list --path .
   ```

5. Убрать «хвост» из текущей копии, выполняя команду ниже:

   ```
   run-critic.bat reject-all --path .
   ```

6. Зафиксировать срез: ветка `src/<JIRA-ID>`, MR в основную ветку
   `src-<сервис>`, после принятия — тег `src/<JIRA-ID>`.
7. «Хвост» не пуст → повторить с шага 1 для следующей задачи.

> ⚠ Все действия по выполнению команд выполняются только в папке `sources/confluence/`;
> `sources/raw/` — только чтение.

Пока команды продолжают работать в Confluence, свежие выгрузки дописывают
хронологию теми же шагами: этап 4 не «закрывается», а живёт параллельно
этапу 5.

**Готово, когда:** каждая не реализованная на ПРОМ задача видна в
`src-<сервис>` срезом с тегом `src/<JIRA-ID>`.

## Этап 5. AI-aware формат: создается `docs-<сервис>`

**Что получится:** аналитика в AI-aware формате — структура, в которой
совместно работают аналитик и AI-агент: карточки требований, реестры,
трассировка.

**Где:** внешний контур. **Инструменты:** Cursor / VS Code, Git, скиллы
([drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit)).

**Шаги:**

1. Создать репозиторий `docs-<сервис>`
   ([analyst-docs-guide § Новый docs-репозиторий](analyst-docs-guide.md#новый-docs-репозиторий)).
2. Преобразовать скиллом чистый ПРОМ (тег `src/PROM`
   в `src-<сервис>`) в AI-aware комплект; результат — ветка от `master` в
   `docs-<сервис>`, MR, принятие.
3. По мере реализации очередной задачи взять её
   изменения из хронологии (сравнение тега `src/<JIRA-ID>` с предыдущим
   срезом), преобразовать скиллом и оформить веткой `docs/<JIRA-ID>` от
   `master`; в MR указать тег-источник — так сохраняется прослеживаемость
   «откуда взяты факты».
   > Перенос изменений между репозиториями — **только преобразованием
   > через скилл**. Копирование файлов или слияние средствами Git из
   > `src-<сервис>` в `docs-<сервис>` запрещено — это стоп-сигнал на ревью.
4. Способ конверсии выбирает команда: по одной задаче, заморозив "хвост", или
   послойно по файлам — правила веток от этого не меняются.

**Готово, когда:** каждая прошедшая посадку задача влита в ветку `master`
`docs-<сервис>` через MR со ссылкой на тег-источник, и команда подтвердила
готовность сопровождать аналитику в AI-aware формате.

## Завершение переезда

«Хвост» пуст (`run-critic.bat list` ничего не показывает), команда
подтвердила переход: хронология останавливается. Репозиторий `src-<сервис>`
с тегами остаётся навсегда как архив прослеживаемости — его не удаляют.
Новые задачи идут только по целевому процессу: ветка `docs/<JIRA-ID>` от
`master` → MR → согласование → принятие.

---

## Почему это работает (для тех, кто хочет углубиться)

Конфликт «история затёрла новую аналитику» невозможен по построению:

- прошлое и настоящее живут в **разных репозиториях** — у них нет общей
  git-истории, случайное слияние исключено самой топологией;
- единственный канал между ними — преобразование скиллом, а оно всегда
  оформляется отдельным MR в `docs-<сервис>` и проходит ревью;
- рабочие ветки растут только от `master` docs-репозитория; теги хронологии
  открывают только для чтения и сравнения;
- связь линий держится не на git-истории, а на прослеживаемости:
  тег среза в `src-<сервис>` ↔ MR конверсии в `docs-<сервис>`.

## Технические стандарты и правила

- состав и права репозиториев:
  [repo-topology](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/repo-topology.md)
  — `docs-*`: ограниченный состав (`<service-id>/docs/` + инфраструктура:
  README, gpb-manifest, CODEOWNERS), доступ аналитика+разработка+QA;
  `src-*`: технический архив, доступ по решению команды;
- процесс веток и ревью описан здесь:
  [git-workflow](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md)
  (именование `docs/<topic>/<JIRA-ID>` — §5; критерии завершения пилота
  ревью — §8; парный MR с backend/frontend при смене API — раздел TBD);
- конвенции комплекта описаны здесь:
  [conventions §1](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md);
- пошаговое создание репозиториев описано здесь: [analyst-docs-guide](analyst-docs-guide.md).

Неизменные условия, которые проверяет ревьюер (все уже встречались по тексту выше рядом со
своими шагами):

1. `sources/raw/` — только чтение.
2. Хронология меняет только `sources/confluence/`; AI-aware ветки — только
   `<service-id>/docs/` (+ инфраструктура).
3. Между `src-*` и `docs-*` нет git-слияний и копирования файлов — только
   преобразование скиллом через MR.
4. Прямых коммитов в `master` docs-репозитория нет: MR → ревью → squash.
5. У каждого MR конверсии — ссылка на тег-источник `src/<JIRA-ID>`.
6. В комплекте `docs-*` нет ссылок на Confluence и на `sources/`
   (прослеживаемость живёт в MR, не в тексте требований).
