# Переезд аналитики в Git (Doc-as-Code): карта маршрута

**Для кого:** аналитик сервиса, который переносит спецификацию требований из Confluence в
GitLab. Опыт работы с Git не обязателен: нужные понятия объяснены по месту,
при выполнении нижеперечисленных команд текст из командной строки копируется как есть.

**Что здесь есть:** суть переезда (4 предложения), карта из 5 этапов,
мини-словарь и сами этапы с шагами. Технические стандарты и правила вынесены в конец.

---

## Суть в четырёх предложениях

У сервиса появляются два хранилища (репозитория): **источник**
`src-<сервис>` — туда попадает выгрузка из Confluence, там лежит текущее
состояние требований ПРОМ и хронология задач, и **рабочее пространство**
`docs-<сервис>` — там живёт аналитика в формате, удобном и людям, и
AI-агентам. Пока с Confluence идёт работа, в источник поступают новые
выгрузки, а каждая задача, вышедшая в ПРОМ, вводится в него отдельным
коммитом. После того как Confluence закрыт на редактирование и введена
последняя задача из числа нереализованных на момент переезда, источник
перестаёт пополняться. Друг в друга хранилища никогда не копируются
средствами Git. Перенос делается **преобразованием**: скилл переводит
изменения задачи из текущего формата в новый. Поэтому изменения в
источнике ничего не могут сломать в рабочем пространстве: они физически
в разных местах.

## Карта маршрута

```text
Confluence ──1──> markdown ──2──> внешний контур ──3──> src-<сервис>
 (внутренний контур)                                    (архив + чистый ПРОМ)
                                                            │
                                                            4  ввод в ПРОМ
                                                            │  и хронология:
                                                            ▼  событие за событием
                                                       src-<сервис>
                                                            ┆
                                                            5  преобразование
                                                            ┆  (скилл, не Git!)
                                                            ▼
                                                       docs-<сервис>
                                                       (формат для людей и AI-агентов)
```

| Этап                  | Что получится | Где | Инструмент                                                        |
|-----------------------|---|---|-------------------------------------------------------------------|
| 1. Выгрузка           | папка markdown-файлов с разметкой задач | внутренний контур (VDI) | confluence-tree-exporter                                          |
| 2. Перенос            | та же папка на внешнем контуре | оба контура | (способ переноса необходимо уточнить у лида по аналитике команды) |
| 3. Архив              | репозиторий `src-<сервис>`: нетронутая копия + «чистый ПРОМ» | внешний | GitLab                                                            |
| 4. Ввод в ПРОМ и хронология | ПРОМ обновляется вводом задач (коммит + тег на задачу); хронология задач на отдельной ветке | внешний | run-history + GitLab                                              |
| 5. Новый формат       | AI-aware аналитика в `docs-<сервис>` | внешний | GLM + скиллы                                            |

Этапы 1–4 проходит каждый сервис. **Этап 5 — решение команды**.

## Шесть слов, которые понадобятся

- **Репозиторий** — хранилище файлов в GitLab с полной историей их изменений.
- **Ветка** — черновик изменений: правки копятся в ней и не видны остальным,
  пока черновик не принят.
- **Основная ветка** — содержит все принятые правки (в docs — `trunk`).
- **MR** (merge request) — «предложение изменений»: просьба принять ветку,
  с обсуждением и проверкой коллегой.
- **Тег** — именованная закладка на состоянии репозитория; по ней это
  состояние можно открыть в любой момент.
- **Срез** — состояние всех требований на момент одного события: ввода
  задачи в ПРОМ или новой выгрузки.
- **ПРОМ-срез** — только требования, установленные в ПРОМ (все страницы
  Confluence, где нереализованное опустошено и помечено флагом). На момент
  переезда — тег `src/PROM`; дальше ПРОМ живёт в основной ветке `master`
  и растёт вводами задач.

---

## Этап 1. Выгрузка из Confluence

**Что получится:** папка с файлами в markdown-формате со всеми требованиями и разметкой,
какая правка к какой задаче Jira относится.

**Где:** внутренний контур (VDI). **Инструмент:** confluence-tree-exporter.

> Видео установки и использования: <https://disk.yandex.ru/i/4vZvS0dJiukLKw>.
> Предварительно рекомендуется попробовать установить confluence-tree-exporter самостоятельно
> согласно инструкций в пакете — скорее всего вы справитесь самостоятельно и сэкономите время.

**Готово, когда:**

- папка с файлами в markdown-формате (и картинками) лежит на диске внутреннего контура (VDI);
- в отчёте выгрузки нет отметок `UNKNOWN-#XXXXXX` — все правки привязались
  к задачам.

## Этап 2. Перенос на внешний контур

**Что получится:** папка с файлами, полученная на этапе 1, на внешнем контуре.

**Где:** внутренний (VDI) → внешний. **Инструмент:** специализированное ПО (инструментарий для переноса можно уточнить у лида по аналитике команды).

**Готово, когда:** папка с выгрузкой доступна на внешнем контуре.

> ⚠ Переносите папку файлов как есть, не упаковывая её в ZIP «навсегда»:
> следующему этапу нужны именно файлы.

## Этап 3. Архив: создается `src-<сервис>`

**Что получится:** репозиторий-хроника с двумя папками: `sources/raw/` —
нетронутая копия выгрузки (страховка: с неё всегда можно начать заново) и
`sources/confluence/` — «чистый ПРОМ», то есть только реализованные в ПРОМ
требования.

**Где:** внешний контур. **Инструменты:** Git, GitLab.

**Шаги:**

1. Завести репозиторий `src-<сервис>` (как — см. пошаговую инструкцию в
   [analyst-docs-guide § Новый src-репозиторий](analyst-docs-guide.md#новый-src-репозиторий)).
   Репозиторий `docs-<сервис>` на этом этапе **не нужен** — он появится на
   этапе 5, если команда туда пойдёт.
2. Положить выгрузку в папку `sources/raw/` и влить в основную ветку
   (через MR).

   > ⚠ **До первого `git add`** создайте в корне репозитория файл
   > `.gitattributes` со строкой `sources/** -text`. Иначе git (при обычной для
   > Windows настройке `core.autocrlf=true`) заменит в выгрузке переводы строк,
   > и архив перестанет быть побайтной копией — при том, что весь смысл
   > `sources/raw/` именно в этом. Правило лежит в репозитории, поэтому
   > действует и у коллег, и в CI, в отличие от локальной настройки git.
   > Проверка перед коммитом: `git diff --cached --name-only --diff-filter=M`
   > не должна показывать файлы, которых вы не меняли.

   ```
   git checkout -b src/raw-import
   git commit -m "Архив выгрузки Confluence: sources/raw как есть, без конверсии переводов строк"
   git push -u origin src/raw-import
   ```

   > ⚠ С этого момента `sources/raw/` — только чтение, навсегда. Это
   > страховочная копия: в неё не вносят правок ни при каких условиях.
3. Собрать «чистый ПРОМ» одной командой `run-history.bat` из состава
   confluence-tree-exporter, без файла задач:

   ```
   run-history.bat <репозиторий>\sources\raw <репозиторий> --base-dir <каталог вне репозитория>
   ```

   Утилита копирует архив в `sources/confluence/` без служебных файлов
   выгрузки (`migration-*`), отклоняет все нереализованные правки
   (`reject-all`) и делает коммит «ПРОМ-срез: …». Рабочее дерево
   репозитория перед запуском должно быть чистым (`git status` пуст).
   Ключ `--base-dir` задаёт каталог для рабочей копии архива: укажите
   место вне репозитория и вне проверки антивируса.
4. Влить результат (через MR) и поставить закладку (тег) **`src/PROM`** —
   это «точка отсчёта»: утверждённое состояние аналитики, соответствующей
   ПРОМу на момент переезда. Если до первого ввода задачи ПРОМ пришлось
   исправить (например, вернуть потерянную страницу), тег переносится на
   новый коммит: `git tag -f src/PROM master`, затем `git push -f origin src/PROM`.

**Готово, когда:** в `src-<сервис>` лежат `sources/raw/` (копия как есть)
и `sources/confluence/` (чистый ПРОМ в основной ветке `master`, тег `src/PROM`).

## Этап 4. Ввод в ПРОМ и хронология задач

**Что получится:** в `src-<сервис>` две ветки с разной ролью.

- Основная ветка `master` — всегда текущий ПРОМ. Каждая задача, вышедшая в
  ПРОМ, вводится отдельным коммитом с тегом `src/<JIRA-ID>`; дифф этого
  коммита — ровно то, что задача изменила в требованиях. Именно отсюда
  этап 5 берёт изменения для преобразования.
- Ветка `future` — хронология: все задачи из отчёта выгрузки применены по
  одной, в порядке дат первой записи «Истории изменений», каждая своим
  коммитом с тегом `hist/<JIRA-ID>`. Вершина ветки — «все задачи
  приняты», прозрачный вид будущего. Что поменяла ещё не введённая задача,
  смотрят здесь: в GitLab открыть коммит с её тегом.

Обе ветки — цепочки событий двух видов: «задача» и «выгрузка». Новая
выгрузка не перестраивает ничего: она добавляет коммит «Выгрузка: …», дифф
которого — всё, что изменилось в Confluence с прошлого раза, а дальше
цепочка продолжается новыми задачами. Старые теги остаются на месте.

**Где:** внешний контур. **Инструменты:** `run-history.bat` (в составе
confluence-tree-exporter), Git, GitLab. Push утилита не делает: после
прогона просмотрите историю и отправьте ветку с тегами сами.

**Как делается.**

*Ввод задачи в ПРОМ* — когда задача установлена в ПРОМ (факт из Jira или
релиза; из Confluence утилита его вывести не может, список введённых даёт
команда):

```
run-history.bat <репозиторий>\sources\raw <репозиторий> <файл с JIRA-ID> --base-dir <каталог вне репозитория> --dry-run
run-history.bat <репозиторий>\sources\raw <репозиторий> <файл с JIRA-ID> --base-dir <каталог вне репозитория>
git push
git push origin "refs/tags/src/*"
```

В файле — только вводимые задачи, по одной в строке; введённые ранее
утилита видит по тегам `src/*` на ветке и повторно не вводит. `--dry-run`
показывает введённые ранее, план и ошибки проверок, ничего не меняя.
Порядок ввода произвольный: состояние `master` определяется множеством
введённых задач, а не их номерами.

Что делает утилита на каждую задачу: применяет её в рабочую копию
«архив + введённые ранее», заменяет `sources/confluence/` этой копией,
отклоняет все ещё не введённые правки, делает коммит «Ввод в эксплуатацию:
<JIRA-ID> …» и ставит тег `src/<JIRA-ID>`. Задача, не изменившая ни одного
файла, тоже получает коммит и тег — для прослеживаемости. Так бывает,
когда её страницы целиком принадлежат другой, ещё не введённой задаче
(страничный флаг): их содержимое появится с вводом той задачи, утилита
печатает причину. В конце утилита печатает хвост «не введено N из M» по
манифесту выгрузки.

*Хронология на `future`* — один раз после этапа 3, список задач берётся
прямо из отчёта выгрузки:

```
git checkout -b future master
run-history.bat <репозиторий>\sources\raw <репозиторий> <репозиторий>\sources\raw\migration-apply-order.md --tag-prefix hist/ --commit-prefix "Срез хронологии" --base-dir <каталог вне репозитория>
git push -u origin future "refs/tags/hist/*"
git checkout master
```

На сотню задач это десятки минут; предупреждения о строках без JIRA-ID и о
дублях при чтении отчёта штатны (в отчёте задачи перечислены дважды:
таблицей и блоком команд). Ожидание в конце: «не введено 0 из N».

*Новая выгрузка* — пока команда работает в Confluence, выгрузки повторяются
(этапы 1–2), и каждая становится событием на обеих ветках:

```
git checkout master
<положить новую выгрузку в sources\raw как есть>
git add sources/raw
git commit -m "Архив: выгрузка от <дата>"
run-history.bat <репозиторий>\sources\raw <репозиторий> --base-dir <каталог вне репозитория>
git push
git checkout future
git checkout master -- sources/raw
git commit -m "Архив: выгрузка от <дата>"
run-history.bat <репозиторий>\sources\raw <репозиторий> <репозиторий>\sources\raw\migration-apply-order.md --tag-prefix hist/ --commit-prefix "Срез хронологии" --base-dir <каталог вне репозитория>
git push origin future "refs/tags/hist/*"
git checkout master
```

На `master` запуск без файла задач только пересчитывает ПРОМ по новому
архиву и фиксирует коммит «Выгрузка: …»; вводить задачи этим запуском
нельзя. На `future` утилита пропустит уже нарезанные задачи по тегам, сама
поставит коммит выгрузки и нарежет только новые. Дополнения разметки уже
нарезанной задачи видны в коммите выгрузки, а не под её тегом.

> ⚠ `sources/raw/` — только чтение между выгрузками: в него кладут новую
> выгрузку целиком и никогда не правят руками. Рабочая копия утилиты живёт
> вне репозитория (`--base-dir`).

Этап 4 не «закрывается»: вводы и выгрузки продолжаются параллельно
этапу 5, пока Confluence не закрыт.

**Готово, когда:** `master` помечен тегом `src/PROM` и растёт только
вводами задач (коммит + тег `src/<JIRA-ID>` на каждую); на `future` у
каждой задачи отчёта выгрузки есть тег `hist/<JIRA-ID>`; последний прогон
на `future` печатает «не введено 0 из N».

## Этап 5. AI-aware формат: создается `docs-<сервис>`

**Что получится:** аналитика в AI-aware формате — структура, в которой
совместно работают аналитик и AI-агент: карточки требований, реестры,
трассировка.

**Где:** внешний контур. **Инструменты:** VS Code / другие IDE, Git, скиллы
([drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit)).

**Шаги:**

1. Создать с помощью LLM план миграции аналитики ПРОМа (основная ветка `master` в `src-<сервис>`) в AI-aware формат (запросить у лида аналитики "Промпт генерации плана миграции сервиса к эталону.md").
2. Преобразовать аналитику в AI-aware комплект, действуя по плану с предыдущего шага.
3. Проверить качество комплекта аналитики с помощью скилла `review-requirements-quality` и устранить замечания.
4. Создать репозиторий `docs-<сервис>`. ([analyst-docs-guide § Новый docs-репозиторий](analyst-docs-guide.md#новый-docs-репозиторий)).
5. Перенести AI-aware комплект в `docs-<сервис>`; результат — ветка от `trunk` в
   `docs-<сервис>`, созданный MR, принятие.
6. Влить аналитику в рабочий репозиторий. После принятия MR удалить
   каталог `docs/` из `master` репозитория `src-<сервис>` одним коммитом
   («Комплект переехал в docs-<сервис>»): у комплекта один дом. Профиль
   источников `README.md`, опись, план и промпты в `src-<сервис>` остаются —
   это документы миграции, а не комплекта.
7. По мере ввода очередной задачи в ПРОМ (этап 4) взять её изменения из
   коммита ввода в `src-<сервис>` (дифф коммита с тегом `src/<JIRA-ID>`;
   заранее посмотреть, что принесёт задача, можно по тегу `hist/<JIRA-ID>`
   на ветке `future`), преобразовать с помощью LLM к заданной ПРОМ-срезом
   структуре, проверить качество скиллом `review-requirements-quality` и
   оформить веткой `docs/<JIRA-ID>` от `trunk`; в MR указать тег-источник —
   так сохраняется прослеживаемость «откуда взяты факты». После принятия
   MR обновить строку «Срез источника» в профиле `README.md` репозитория
   `src-<сервис>` (тег последней разнесённой задачи) отдельным коммитом:
   по ней видно, с какого ввода брать следующую дельту.
8. Способ конверсии выбирает команда: по одной задаче, заморозив "хвост", или
   послойно по файлам — правила веток от этого не меняются.

**Готово, когда:** каждая прошедшая посадку задача влита в ветку `trunk`
`docs-<сервис>` через MR со ссылкой на тег-источник, и команда подтвердила
готовность сопровождать аналитику в AI-aware формате.

## Завершение переезда

Хвост пуст (последний прогон `run-history.bat` на `master` печатает
«не введено 0 из N»), Confluence закрыт, команда подтвердила переход:
вводы и выгрузки останавливаются. Репозиторий `src-<сервис>` с тегами
остаётся навсегда как архив прослеживаемости — его не удаляют.
Новые задачи идут только по целевому процессу: ветка `docs/<JIRA-ID>` от
`trunk` → MR → согласование → принятие.

---

## Почему это работает (для тех, кто хочет углубиться)

Конфликт «история затёрла новую аналитику» невозможен по построению:

- прошлое и настоящее живут в **разных репозиториях** — у них нет общей
  git-истории, случайное слияние исключено самой топологией;
- единственный канал между ними — преобразование скиллом, а оно всегда
  оформляется отдельным MR в `docs-<сервис>` и проходит ревью;
- рабочие ветки растут только от `trunk` docs-репозитория; теги хронологии
  открывают только для чтения и сравнения;
- связь линий держится не на git-истории, а на прослеживаемости:
  коммит ввода (тег `src/<JIRA-ID>`) в `src-<сервис>` ↔ MR конверсии в `docs-<сервис>`.

## Технические стандарты и правила

- состав и права репозиториев:
  [repo-topology](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/repo-topology.md)
  — `docs-*`: ограниченный состав (`<service-id>/docs/` + инфраструктура:
  README, gpb-manifest, CODEOWNERS), доступ аналитика+разработка+QA;
  `src-*`: технический архив, доступ по решению команды;
- процесс веток и ревью описан здесь:
  [git-workflow](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md)
  (именование `docs/<topic>/<JIRA-ID>` — §5; критерии завершения пилота
  ревью — §8; парный MR с backend/frontend при смене API — раздел TBD);
- конвенции комплекта описаны здесь:
  [conventions §1](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md);
- пошаговое создание репозиториев описано здесь: [analyst-docs-guide](analyst-docs-guide.md).

Неизменные условия, которые проверяет ревьюер (все уже встречались по тексту выше рядом со
своими шагами):

1. `sources/raw/` — только чтение.
2. Ввод задач и хронология меняют только `sources/confluence/`, новая
   выгрузка — `sources/raw/` целиком; AI-aware ветки — только
   `<service-id>/docs/` (+ инфраструктура).
3. Между `src-*` и `docs-*` нет git-слияний и копирования файлов — только
   преобразование скиллом через MR.
4. Прямых коммитов в `trunk` docs-репозитория нет: MR → ревью → squash.
5. У каждого MR конверсии — ссылка на тег-источник `src/<JIRA-ID>`.
6. В комплекте `docs-*` нет ссылок на Confluence и на `sources/`
   (прослеживаемость живёт в MR, не в тексте требований).
