# Матрица трассировки — разделы комплектов и их природа — решено 2026-10-16

Дата: 2026-10-16. Пакет 2, задача 10, шаг 1: анализ без кода. Поправка П2: выводимые разделы
собирает утилита, ручные ведёт аналитик, генерация матрицы целиком отклонена. Шаг 2 (шаблон и
`matrix_sync.py`) не начат. Решения по этому файлу приняты 16.10, см. последний раздел.

## Вывод

1. **Реестр ID выводим почти целиком.** Строки берутся из шапок документов и из заголовков
   тел (внутренние ID контролей, полей, событий). Ручная часть — только снятые ID с пометкой
   «снят: …»: их нет ни в одном теле.
2. **Покрытие функций и процессов выводимо из ссылок в обе стороны**, но не везде. В КК,
   стенде и эталоне часть строк матрицы называет ID, на которые нет ссылки ни из тела, ни
   в тело. Пересборка такие связи потеряет. Это главный риск шага 2.
3. **Долги по ссылкам — ручной раздел.** Его ведёт аналитик, проверяет `link_debts.py`.
4. **Разделы источников смешанные.** Перечень страниц выводим из выгрузки и
   `confluence_page_ids`, категория и основание — ручные.
5. **Комплекты расходятся в составе, порядке, названиях и колонках разделов.** Шаблон шага 2
   должен закрепить одно имя, один порядок и один набор колонок на раздел.

## Расхождения формы между комплектами

- **Порядок.** КК, lk-mp и УЛ начинают с реестра. Стенд и эталон начинают с покрытия.
- **Имена.** «Покрытие — функции (FUN)» в КК и «Покрытие: функции → артефакты» в остальных.
  У эталона три раздела с номером «4.»: реестр, артефакты вне трассировки, связи интеграций.
- **Колонки реестра.** В КК есть колонка «Тип», в остальных комплектах — «ID | Название | Файл».
- **Колонки покрытия функций.** В КК «Назначение» и коды типов, в эталоне ещё «Роль».
- **Колонки покрытия процессов.** В КК есть «CALL», в стенде и эталоне есть «Вызывает» и
  «Интеграции», в lk-mp нет «Название».
- **Долги.** Шапка «FROM | — | Долг» в КК, «Откуда | — | Долг» в lk-mp, «Откуда | Цель | Долг»
  в УЛ, «Артефакт | Цель | Причина» в стенде.

## Что нужно решить

1. **Связи только в матрице.** Пересборка их потеряет. Рекомендация: `--check` перечисляет
   их как ⚠ «связь есть в матрице, нет в документах», а `--write` отказывается работать,
   пока перечень не пуст. Тогда аналитик либо добавит ссылку в документ, либо снимет связь.
   Альтернатива — `--write` сохраняет объединение, но тогда матрица остаётся вторым домом факта.
2. **Внутренние ID реестра.** Рекомендация: выводить из заголовков тел, где ID стоит в начале
   заголовка. Упоминания в тексте не выводить: часть из них ссылается на чужой ID.
   Расхождение по ним `--check` показывает как ⚠.
3. **Снятые ID.** Рекомендация: отдельный ручной подраздел «Снятые ID» с колонками
   «ID | Причина и дата | Преемник». Утилита его не трогает и проверяет, что снятый ID не
   выдан снова.
4. **Покрытие API ↔ SRS.** Перечень операций живёт в спецификации репозитория кода, вне
   комплекта. Рекомендация: раздел ручной, проверку оставить сторожам `selfcheck` и
   `passport_sync`.
5. **Разделы источников.** Рекомендация: перечень страниц и целевых артефактов выводить из
   `confluence_page_ids` и выгрузки, как в `source_coverage.py`. Категория и основание для
   страниц вне SRS ведутся вручную в отдельной колонке, которую утилита переносит без правки.
6. **Бизнес-слой эталона (BRD-1…BRD-5).** Есть только в эталоне. Рекомендация: в шаг 2 не
   включать, шаблон помечает эти разделы как «по наличию слоя brd/».
7. **Порядок, имена и колонки.** Рекомендация: порядок «Реестр ID → Покрытие функций →
   Покрытие процессов → Покрытие API ↔ SRS → Источники → Долги по ссылкам». Имена — как в
   `passport_sync.py`: «Реестр ID», «Покрытие: API ↔ SRS», «Долги по ссылкам». Колонки —
   по стенду, с колонкой «Вызовы» в покрытии процессов. Переход комплектов на новый порядок
   и колонки — отдельным заходом по каждому комплекту.

## Решения владельца (2026-10-16)

Все семь рекомендаций раздела «Что нужно решить» приняты без изменений. Это основание шага 2:

1. Связи только в матрице: `--check` перечисляет их как ⚠, `--write` не работает, пока
   перечень не пуст.
2. Внутренние ID реестра выводятся из заголовков тел, где ID стоит в начале заголовка.
   Упоминания в тексте не выводятся, расхождение по ним — ⚠ в `--check`.
3. Снятые ID — ручной подраздел «Снятые ID» с колонками «ID | Причина и дата | Преемник».
   Утилита его не трогает и проверяет, что снятый ID не выдан снова.
4. Покрытие API ↔ SRS — ручной раздел, проверка остаётся за `selfcheck` и `passport_sync`.
5. Разделы источников: перечень страниц и целевых артефактов выводится из
   `confluence_page_ids` и выгрузки. Категория и основание ведутся вручную в отдельной колонке,
   утилита переносит её без правки.
6. Бизнес-слой эталона (BRD-1…BRD-5) в шаг 2 не входит, шаблон помечает эти разделы «по
   наличию слоя brd/».
7. Порядок «Реестр ID → Покрытие функций → Покрытие процессов → Покрытие API ↔ SRS →
   Источники → Долги по ссылкам», имена как в `passport_sync.py`, колонки по стенду с колонкой
   «Вызовы» в покрытии процессов. Перевод комплектов — отдельным заходом по каждому.
