## OQ-NNN — <дата> — Зона виджетов: владелец эндпоинтов УС_РЕК / УС_ПИН и ЕПАА (контакт для изменений контракта)

- Вопрос: модуль `modules/widgets-rtl/` (Д-46) вызывает эндпоинты чужого контура — «УС Реквизиты
  карты» (`omni-oks-requisites`), «УС ПИН» (`omni-oks-pin`) и ЕПАА (`confirm_ip`, `tokenExchange`).
  Их базовые контракты заводятся в `docs-external-contracts`, у каждого должен быть владелец —
  команда, которая сообщает об изменениях контракта и подтверждает трактовку. Паспорт границы
  контуров (`2495516676`, §8 п. 1) оставил этот вопрос открытым. В выгруженных спецификациях Розницы
  владелец не назван.
- Варианты:
  1. Назвать команду-владельца для каждого из трёх (Розница — омни-платформа / ОКС; ЕПАА) с
     контактом; владельцы вносятся в README папок АС `docs-external-contracts` (`rtl/`, `epaa/`) и в
     паспорт мини-комплекта.
  2. Владелец Розницы известен, ЕПАА — нет (или наоборот): контракты заводятся, у неизвестного
     владельца — строка «владелец не установлен» в README папки АС и этот OQ остаётся открытым по
     нему.
  3. Владельцев установить нельзя — контракты заводятся как трактовка команды КК по выгрузкам 21.10
     с пометкой происхождения; при изменении эндпоинта сигнал не придёт. Это риск для виджетов
     (PCI DSS).
- Рекомендация: вариант 1. Без владельца базовый контракт чужого контура стареет без сигнала,
  а изменения эндпоинтов Розницы и ЕПАА напрямую ломают виджеты.
- Что проверить: страницы-родители спецификаций в пространствах Розницы и ЕПАА — поля «Владелец» /
  «Ответственный»; README папки `epaa/` в `docs-external-contracts` — там уже есть `EXTINT-EPAA-001`,
  владелец ЕПАА мог быть указан при его заведении.
- Статус: открыт

## OQ-NNN — <дата> — Зона виджетов: покрывает ли «Системный токен ЕПАА (internal)» часть обмена токена виджета

- Вопрос: в выгрузке раздела ЕПАА «system/ip» есть страница `118237030` «Системный токен ЕПАА
  (internal)». Метод обмена токенов виджета на неё не ссылается, но она описывает токен того же
  realm `/system/ip`, что и шаг 0 метода (`confirm_ip`). Нужно ли описывать её базовым контрактом в
  `epaa/` как часть цепочки виджета?
- Варианты:
  1. Не относится к виджету: токен «исключительно для межсистемных вызовов», его «не должно быть
     возможности получить путём стандартного механизма вызова авторизации», к нему «не должны
     применяться никакие правила, применимые для токена system/ip (confirm_ip)» — всё дословно со
     страницы. Виджет работает от токена пользователя UAA. Контракт не заводится в рамках зоны
     виджетов; страница — справочно в README папки `epaa/`.
  2. Относится: системный токен используется на стороне Розницы или ЕПАА в цепочке обработки
     запросов виджета — тогда контракт `epaa/` и ссылка из паспорта мини-комплекта.
- Рекомендация: вариант 1 — по тексту страницы токен межсистемный и правила `confirm_ip` к нему
  прямо не применяются, а метод виджета на него не ссылается.
- Что проверить: «Матрица покрытия (system/ip)» `1428824259` — кто потребители системного токена;
  ответ владельца ЕПАА (OQ о владельце выше).
- Статус: открыт
