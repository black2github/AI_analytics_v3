# Принципы работы с требованиями в целевом репозитории при довозке хвостов из Confluence

Рабочий документ команды. Редакция 0 (проект, 2026-11-08) — к обсуждению; правится по мере обкатки.
Решение, из которого он вырос, — проект Д-63 в реестре решений по ядру скиллов.

## 1. Для кого и зачем

Для аналитиков команды сервиса, который переехал в целевой репозиторий (`EAN/docs-<сервис>`),
но у которого часть требований ещё вводится в ПРОМ в Confluence и будет довозиться позже
(«хвосты»). Документ отвечает на один вопрос: **как одновременно править требования в
репозитории и довозить хвосты из Confluence так, чтобы конфликты слияния были редкими,
локальными и разрешимыми аналитиком за минуты, а не днями.**

Другим командам документ подходит без изменений — в нём нет ничего специфичного для КК,
кроме примеров.

## 2. Термины

| Термин | Что это |
|---|---|
| **Источник** | Страница Confluence в состоянии ПРОМ (всё введённое, без неподтверждённых правок). |
| **Выгрузка** | Снимок дерева Confluence экспортёром; хранится в src-репозитории как коммит цепочки (`hist/<ID>`, тег `src/<ID>` — «задача введена в ПРОМ»). |
| **Карточка** | Файл требований в целевом репозитории (функция, контракт, ЭФ, сущность…), сделанный из источника и несущий его след (`page_id`, выгрузка). |
| **Хвост** | Изменения источника между двумя выгрузками, перенесённые в карточки целевого репозитория. |
| **Хозяин карточки** | Кто сейчас вправе менять её содержание: Confluence (изменение приедет хвостом) или репозиторий (команда правит напрямую). |
| **Долг захода** | Запись гейта переноса «требуется заход»: страница ещё не доведена до карточек или будет введена в ПРОМ позже. |
| **Режим C (change)** | Режим скилла `create-artifact`: правка существующей карточки по постановке «что именно изменить» — тот же forward, но вход — дельта, а не цель. |

## 3. Принципы

Каждый принцип — одно правило, почему оно нужно и пример. Нумерация постоянная, чтобы на
принципы можно было ссылаться.

### П-1. Хвост — это дельта источника, а не новая карточка

**Правило.** Хвост переносится как разница между двумя выгрузками страницы, наложенная на
существующую карточку режимом C. Карточка никогда не делается заново по новой выгрузке, пока
она существует.

**Почему.** Повторная генерация карточки по той же странице даёт другой текст там, где источник
не менялся: скилл недетерминирован. Такие различия выглядят как конфликты и их сотни — процесс
останавливается. Дельта трогает только то, что действительно изменилось.

**Пример.** В ТЗ п. 4.5.2 изменили срок с 3 до 5 дней. Хвост: в выгрузке N−1 → N по странице
изменилась одна строка; в карточке FUN-SYS-07 режимом C меняется одно условие. Всё остальное в
карточке — как было, включая правки команды в других пунктах.

### П-2. У карточки один хозяин

**Правило.** В каждый момент карточку меняет либо Confluence (через хвост), либо команда в
репозитории — не оба. Карточка с открытым долгом захода принадлежит Confluence. Передача
хозяина — явное событие: долг закрыт → хозяин репозиторий; страница Confluence с этого момента
только запись ПРОМ.

**Почему.** Конфликт возникает только там, где одно место правят с двух сторон. Карта владения
сводит такие места к нулю, пока её соблюдают, и к понятному списку, когда её нарушили
осознанно.

**Пример.** Страница «Лимиты по карте» имеет долг захода (TEAMTB-4620 ещё не введена в ПРОМ).
Аналитику нужно поправить описание лимита. Правильно: правка в Confluence в рамках задачи,
ввод в ПРОМ, хвост. Неправильно: правка карточки в репозитории — при хвосте она столкнётся с
дельтой источника.

### П-3. Если очень нужно править карточку, которая ещё ведётся в Confluence

**Правило.** Можно, но правящий берёт на себя слияние хвоста по этой карточке и записывает долг
«расхождение с ПРОМ» (страница, карточка, что изменено, почему не через Confluence). Долг
закрывается тем хвостом, который принесёт ту же правку из источника, или решением владельца.

**Почему.** Запрет без выхода нарушают молча; выход с записью оставляет след и назначает
ответственного за слияние заранее.

### П-4. ID и нарезка после вливания не меняются

**Правило.** После первого вливания карточки в целевой репозиторий её ID (FUN-, CALL-, CTL-,
SCR-, ENT-…) и разбиение страницы на карточки не меняются ни в хвосте, ни в правке команды.
Структурное изменение — отдельное решение владельца канона и отдельный MR, до или после хвоста.

**Почему.** Git не видит «переименовано и изменено» как одно действие: при перенумерации или
перенарезке хвост ляжет на старые файлы, а правки команды — на новые. Такой конфликт не
разрешается, а переделывается руками.

**Пример.** Страницу «Блокировка карты» решили разбить на две карточки. Это делается отдельным
MR «структура», в котором нет ни хвоста, ни правок содержания; хвост по этой странице идёт
следующим MR уже на новую нарезку.

### П-5. Хвосты маленькие и частые

**Правило.** Хвост делается по готовности группы страниц (задача введена в ПРОМ — есть тег
`src/<ID>`), а не накоплением «раз в квартал». Состав выгрузки определяется до выгрузки; версия
экспортёра на период хвостов заморожена.

**Почему.** Объём конфликтов растёт с временем между хвостами и с числом пересекающихся правок.
Пять страниц раз в две недели сливаются за час; пятьдесят раз в квартал — не сливаются.
Канал выгрузки медленный (архив через DLP), поэтому состав — заранее, повторные выгрузки
недопустимы.

### П-6. Один гейт на обе стороны

**Правило.** MR хвоста и MR команды проходят один и тот же гейт прибора: ссылки, ID, реестры,
долги, срез канона. Версия канона закреплена на репозиторий; накат новой версии — отдельный MR
«одним приёмом», во время которого хвосты и правки не вливаются.

**Почему.** Прибор ловит невидимые для git последствия слияния (битая ссылка после правки
соседней карточки, долг без цели, ID вне реестра). Расхождение версий канона между хвостом и
репозиторием даёт «конфликты формы», которые не относятся ни к источнику, ни к команде.

### П-7. При содержательном конфликте побеждает источник ПРОМ (проект, развилка Р-2)

**Правило.** Если команда и источник изменили одно и то же место по-разному, в карточку входит
текст источника (он введён в ПРОМ), а правка команды переносится поверх отдельным коммитом с
указанием причины — либо снимается, если источник её уже учёл.

**Почему.** ПРОМ — зафиксированное требование; правка в репозитории без ввода в ПРОМ — ещё
нет. Умолчание нужно, чтобы аналитик не решал каждый раз заново; отклонение от умолчания —
осознанно и со следом.

### П-8. Приёмка — у команды, структура — у владельца канона

**Правило.** MR хвоста и MR команды апрувит аналитик команды. К владельцу канона идут только
структурные изменения (П-4), накат канона (П-6) и конфликты, которые команда не может решить
сама.

**Почему.** Один апрувер на все шаги всех команд — узкое место через неделю параллельной
работы.

## 4. Порядок хвоста (шаги)

1. **Состав.** Список страниц с тегом `src/<ID>` после прошлого хвоста; для каждой — карточки,
   куда она разложена (карта «страница → карточки» из описи). Пересечение с правками команды
   за период — по `git log` целевого репозитория по этим карточкам: это кандидаты на конфликт,
   они известны до выгрузки.
2. **Выгрузка** только состава; коммит в цепочке src-репо; дельта по каждой странице
   (выгрузка N−1 → N).
3. **Перенос** дельт в карточки режимом C на ветке `tail/<дата>` от `main`; на пересекающихся
   карточках — трёхстороннее слияние по П-7.
4. **Гейт** прибора по П-6; долги захода по перенесённым страницам закрываются; хозяин →
   репозиторий (П-2).
5. **MR** в `main`; апрув команды (П-8); после вливания — сообщение команде: какие страницы
   переехали, какие карточки изменились, где было слияние.

## 5. Правила правки в репозитории (памятка аналитику)

- Перед правкой карточки — посмотреть, нет ли по ней долга захода. Есть — П-2/П-3.
- Не переименовывать файлы, не менять ID, не делить и не сливать карточки — П-4.
- Правка содержания и правка структуры — в разных MR.
- В MR — только свои файлы; «выводимые» разделы (реестры, матрицы) — только утилитой.
- После слияния любой ветки — гейт прибора до пуша.

## 6. Что делать при конфликте (памятка)

| Ситуация | Действие |
|---|---|
| Хвост и правка команды в разных местах одной карточки | git сливает сам; проверить глазами, прогнать гейт. |
| Одно место, разные правки | П-7: текст источника в карточку, правка команды поверх отдельным коммитом с причиной или снимается. |
| Хвост ложится на карточку, которую переименовали/перенарезали | Нарушение П-4: откатить структурное изменение в отдельный MR, повторить хвост. |
| Прибор после слияния даёт ✗ по форме | Проверить срез канона у хвоста и репозитория (П-6); расхождение — накат канона отдельным MR, затем хвост. |
| Правка нужна срочно, а карточка у Confluence | П-3: правка + долг «расхождение с ПРОМ» + ответственность за слияние. |

## 7. Роли

| Роль | Делает |
|---|---|
| Аналитик команды | Правит карточки-«репозиторий»; вводит задачи в ПРОМ; апрувит MR; решает конфликты по П-7. |
| Координатор (исполнитель хвоста) | Состав, выгрузка, перенос режимом C, гейт, MR хвоста, сообщение команде. |
| Владелец канона | Структурные решения (П-4), накат канона (П-6), спорные конфликты, развитие этого документа. |

## 8. Что в этом документе ещё не решено

Вопросы к обсуждению с владельцем (рекомендация владельца канона — в скобках; решения записывать сюда с датой):

- Р-1. Где живёт карта владения: опись долгов захода или отдельный реестр в комплекте. (Рекомендация — опись долгов захода: ничего нового не заводится, долг «требуется заход» и есть признак «хозяин — Confluence».)
- Р-2. Умолчание П-7 «источник ПРОМ побеждает, правка команды поверх отдельным коммитом» или «решает аналитик без умолчания». (Рекомендация — умолчание: ПРОМ есть введённое требование; без умолчания каждый конфликт решается заново.)
- Р-3. Эксперимент: один реальный хвост КК (6 страниц итерации 2) режимом C на копии целевого репозитория с искусственной правкой «команды» по пересекающейся странице; замер настоящих / ложных / невидимых конфликтов — до переезда или на первом боевом хвосте. (Рекомендация — до переезда: ответ на «насколько сложно» числами, а не оценкой.)
- Р-4. Апрувер MR хвоста — команда или владелец канона. (Рекомендация — команда; владелец канона по запросу.)
- Р-5. Нужен ли обратный поток «репозиторий → Confluence» для страниц, у которых хозяин уже репозиторий, пока Confluence читают смежные команды. (Рекомендация — нет: Confluence после передачи хозяина — архив ПРОМ с пометкой «актуально в репозитории»; иначе два источника правды.)
- Р-6. Как команда узнаёт, что страница «ведётся в Confluence»: по описи долгов (Р-1) или по пометке в самой карточке. (Рекомендация — по описи; пометку в карточке даёт прибор строкой i при гейте, руками не ставить.)
