# Этап 1: Выгрузка аналитики из Confluence в markdown формат

**Цель**: выгрузка требований аналитики в markdown формат в привязке к задачам Jira

**Контур**: внутренний (VDI)

**Инструмент**: confluence-tree-exporter

**DoD**: 

- каталог выгруженных требований в виде markdown файлов и связанных файлов (например, картинок) на файловой системе.
- в случае привязки требований к задачам - отсутствие UNKNOWN-#XXXXXX отметок в отчете по цветовой привязке требований.

# Этап 2: Перенос аналитики между контурами

**Цель**: получение файлов с аналитикой в markdown формате на внешнем контуре

**Контур**: внутренний (VDI) + внешний

**Инструмент**: onix_ft

**DoD:** 

- каталог требований в markdown формате на файловой системе во внешнем контуре.

# Этап 3: Сохранение аналитики в архив

**Цель**: сохранение в Git репозиторий архива аналитики в markdown + формате (с разметкой привязки к задачам, если требуется) для возможности восстановления в любое время (точка отсчета).

**Контур**: внешний

**Инструмент**: Git

**DoD**: 

- все файлы требований влиты в GitLab репозиторий внешнего контура с привязкой к сервису в рамках базовой ветки. (путь к репозиторию…).

# Этап 4: Восстановление истории изменения аналитики

**Цель:** воссоздание в Git репозитории истории изменения требований в markdown формате в их оригинальном составе. Формальное начало Doc-as-Code фазы.

**Контур**: внешний

**Инструменты:** Critic, Git

**DoD**: 

- в Git репозитории созданы ветки с уникальными идентификаторами под каждую бизнесовую задачу, по которой еще не завершена реализация. (Путь к репозиторию: doc-as-code\EAN\<service-code>\sources\confluence…)
- все нереализованные на ПРОМе изменения аналитики (в markdown формате) связаны с веткой репозитория, относящейся к бизнесовой (или ее эквиваленту) задаче.

**Шаги**:

1. Влить в репозиторий ПРОМ срез (critic —reject-all)
2. Определить список задач очередного эпика
3. Принять все задачи эпика в качестве “реализованных” (critic —apply ID)
4. Исключить весь “хвост” нереализованных задач (critic —reject-all)
5. Создать новую ветку под эпик.
6. Влить в ветку репозитория весь набор требований (в ветку попадет diff двух веток)
7. Если “хвост” еще остался, то перейти к шагу 2. 

# Этап 5: Миграция аналитики в AI-aware формат

**Цель**: переход на полу/автоматизированное создание и сопровождение аналитики, при котором AI-агент и человек-аналитик работают совместно. 

**Контур**: внешний

**Инструменты**: Cursor / VS Code, Git

**DoD:** 

- в Git репозитории созданы ветки с  уникальными идентификаторами под каждую бизнесовую задачу, по которой еще не завершена реализация.
- Идентификаторы веток отличны от веток Этапа 4.
- с веткой репозитория связаны все изменения аналитики оформленные в  AI-aware формате и относящиеся к бизнесовой задаче.
- Подтверждение команды сервиса о готовности сопровождения аналитики в выбранном формате.

**Шаги**:

1. Пилот по переходу части сервисов на AI-aware формат
2. Тиражирование принятых подходов, шаблонов и инструментов на все сервисы Экосистемы.
3. Переход на этап развития аналитики совместно AI-агентами
