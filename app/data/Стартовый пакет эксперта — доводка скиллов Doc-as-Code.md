# Стартовый пакет эксперта: доводка единых скиллов Doc-as-Code

Для аналитика-эксперта, подключающегося к фазе 4 пилота перехода на doc-as-code (доводка единых скиллов
на пилотных сервисах). 
Версия: 2026-08-12.

---

## 1. Роль и цель

Вы дорабатываете ЕДИНЫЕ скиллы, а не документацию конкретного сервиса.

- **Продукт итерации — скилл** (правило в каноне `_meta`), который генерит
  корректный и полный выход из исходников. Готовые документы сервиса —
  побочный продукт и материал проверки.
- Ищем **системные ошибки** (воспроизведутся на любом сервисе), а не
  специфику источников. Специфика (ошибки постановки, дыры источника) —
  в open-questions сервиса, командам.
- Если выход неполон — не дочинивать руками молча: найти корневую
  причину, поправить канон, перегнать заново. Ручная правка выхода
  допустима только как санкционированный «дозаход по замечаниям ревью».

## 2. Что прочитать до первого прогона (по порядку)

1. «Принципы проработки скиллов» (этот репозиторий, `app/data/`) —
   базовые инварианты; при любом неочевидном решении сверяйтесь с ними.
2. План работ фазы 4 (документ руководителя) — роли, метод, Приложения
   2–3 (чек-лист валидации, классификация ошибок).
3. Канон `_meta` (репо docs-o2new, ветка master ПОСЛЕ вливания
   meta/phase4-scope-rule): `AGENTS.md`, `rules/conventions.md`,
   `rules/terms.md` — целиком; скиллы и шаблоны — по мере типов.
4. «Протокол фазы 4 — file-storage (прогон 1)» (`app/data/`) — образец
   ведения протокола и реестр находок С-1…С-20: КАЖДАЯ находка там —
   грабли, на которые вы иначе наступите заново.

## 3. Терминология (обязательный минимум)

| Термин | Значение                                                                                                                       |
|---|--------------------------------------------------------------------------------------------------------------------------------|
| **тип артефакта** | Вид документа (`type` во frontmatter): data-model, process, function, controls… Заход работает с ОДНИМ типом |
| **заход** | Одна задача агенту: создать/актуализировать артефакты одного типа                                                              |
| **прогон** | Конкретный запуск агента (новый чат) по заходу                                                                                 |
| **волна** | Правка канона `_meta` по итогам разбора находки                                                                                |
| **перегон** | Повторный прогон после волны — проверка, что правка доехала                                                                    |
| **дозаход** | Прогон-актуализация по списку замечаний ревью                                                                                  |
| **находка (С-NN)** | Зафиксированный дефект/класс с корневой причиной                                                                               |
| **долг** | Ссылка на ещё не созданный артефакт: имя без ID + запись в open-questions + строка в матрице (файлы чужих типов НЕ создаются)  |
| **base / usage** | Контракт внешней АС (репо docs-external-contracts) / вызовы контракта сервисом (`docs/srs/contract-calls/`)                    |

Запрещённый сленг в каноне и документах: «жанр» (говорите «тип
артефакта»), внутренние номера решений (Д-NN) — формулировки только
самодостаточные.

## 4. Рабочий цикл итерации

1. **Предсказания ДО запуска** — что, по-вашему, сломается (журнал
   предсказаний в протоколе). Дисциплинирует сверку.
2. **Прогон** — строго по регламенту (§5).
3. **Сверка**: сначала механика (§6), затем глазами — семантика.
   Механика стабильна от прогона к прогону; семантические находки — нет,
   их ловит только человек.
4. **Корневой разбор** каждой находки: не «агент ошибся», а ЧТО в
   каноне/процедуре позволило или заставило ошибиться. Перед разбором —
   поиск по реестру находок: класс мог быть уже открыт.
5. **Заявка на волну** владельцу канона (§7). Канон напрямую не правим.
6. **Перегон** после волны — новый чат, тот же заход.
7. **Коммит проверенного** — сразу после приёма итерации, ДО следующего
   запуска (незакоммиченный проверенный выход был потерян перезаписью —
   урок пилота).
8. Протокол сервиса ведётся непрерывно (по образцу протокола
   file-storage): контекст, предсказания, журнал находок, журнал
   прогонов, чекпоинты.

## 5. Регламент прогона (нарушение = прогон не засчитывается)

- **Каждый прогон — НОВЫЙ чат агента.** Контекст диалога переигрывает
  обновлённые шаблоны: агент воспроизводит свои старые структуры и даже
  «восстанавливает» удалённые файлы из истории (находки С-9, С-14).
- **Промпт — стандартный, из трёх блоков + задача** (шаблон ниже).
  В блоке изоляции — АКТУАЛЬНАЯ ветка (устаревшая ветка в промпте —
  инцидент С-12: агент сам переключил репозиторий).
- **Выход агента принимается только с дословными вердиктами гейтов**
  (`# OK` / `# БРАК` построчно). «Предупреждения», «замечания» вместо
  вердикта — эвфемизация гейта (С-18), прогон на доверии не принимается.
- Правки канона во время чужого прогона не вносятся (агент читает файлы
  с диска).

Шаблон промпта (замените ветку, репо, задачу):

```
Методология (скиллы, правила, шаблоны, утилиты): C:\...\docs-o2new\_meta\ — все пути вида _meta/... отсчитывай от корня docs-o2new. Рабочий репозиторий сервиса: C:\...\docs-<service>\ — источники в sources\, выходы в output\<service-id>\, служебные файлы — в sandbox\.

Изоляция: работай на ТЕКУЩЕЙ ветке репозитория (git branch --show-current, должна быть <ветка>); ветки не переключай — если текущая ветка выглядит не той, остановись и спроси. В master и другие ветки не заглядывай, их содержимое не используй. Сеть и remote (fetch/pull/push) не используй.

Прогон с нуля: единственный источник данных — sources/ и текущее состояние диска (git status). Память диалога и история редактора источником не являются: если в твоём плане появляются слова «предыдущий прогон», «восстановлю», «как в прошлый раз» — остановись и сообщи аналитику.

Задача: по скиллу _meta/skills/<скилл>.md создай или актуализируй <тип артефакта> сервиса <service-id> (тип <тип>, режим reverse, объём — <...>). Источник — <раздел выгрузки>.
```

**«Объём»** — параметр входа скилла: какая часть комплекта типа входит в
заход. Примеры: «весь комплект» (все сущности + справочники + README),
«одна функция — Функция загрузки файла», «только реестр functions/README»,
«внешняя АС MFlash (9 методов)», «только dictionaries.md». Идти можно и
по одному артефакту за итерацию — на незнакомом типе так и рекомендуется
(«одна функция → отчёт → правки → следующая», порядок скилла).

## 6. Механические гейты сверки

| Проверка | Как |
|---|---|
| Скоуп захода | `git status --porcelain`: новые/изменённые файлы только в каталоге запрошенного типа, `sandbox/`, `open-questions.md`, матрице. Чужие файлы не тронуты |
| Полнота и дословность карточек контрактов | `python _meta/tools/normalize_tables.py <карточка> --check --source <страница-источника>` → `# OK` (код 0). Проверяет колонки, значения markdown-таблиц источника, ИМЕНА параметров HTML-таблиц |
| Разбор сырых HTML-таблиц | нормализатор с `--sidecar` (пишет UTF-8 сам); shell-редирект `>` запрещён — PowerShell даёт UTF-16 |
| Счётные сверки | строк/колонок таблиц против источника; число статусов; число страниц раздела против числа артефактов |
| Чистота документов | греп по `sources/|confluence|OQ-|TODO` в тексте (frontmatter `confluence_page_ids` — законное поле) |

Механика ловит потери и структуру. Семантику (перепутанные ветки
успех/ошибка, дыры безопасности, противоречия названий) — только вы.

## 7. Формат находки (заявка на волну)

```
С-NN. <короткое имя>
Тип артефакта / сервис / прогон: ...
Симптом: что не так в выходе (с примером, путь+строка).
Корневая причина: что в каноне/процедуре это позволило или заставило
  (конфликт указаний? дыра правила? образец переиграл текст? тупик без
  ветки выхода?).
Системная? да/нет (воспроизведётся ли на другом сервисе).
Предлагаемая правка: файл канона, формулировка.
```

Правила волн: заявки — владельцу канона, он арбитр; правки общего слоя
(conventions, схема ID, frontmatter, нотация) — только через него;
формулировки в каноне самодостаточные (без сленга и внутренних номеров);
причину и дату инцидента вписывать прямо в правило.

## 8. Законы доставки правил (выведены экспериментально — не спорьте с ними, используйте)

1. **Образец в месте письма сильнее любой инструкции.** Слабая LLM
   копирует пример из шаблона, а не текст правила. Меняете правило —
   меняйте образец.
2. **Имя сильнее инструкции.** Точное имя колонки/каталога устраняет
  класс ошибок, который не лечился абзацами текста.
3. **Два текстовых неисполнения → механический гейт.** Не пишите третью
   формулировку — стройте проверку содержимого.
4. **Сторожить содержимое, а не слова** — включая ОТЧЁТ агента: вердикты
   гейтов цитируются дословно, статусы не пересказываются.
5. **У каждого запрета — ветка честного выхода.** Правило-тупик («нельзя»
   без «а если не получилось — делай так») порождает эвфемизмы и обходы.
6. **Изоляция без снапшота внешних зависимостей порождает слепые дубли.**
   Перед заходом, зависящим от внешнего репо, — согласуйте read-only
   срез или явное разрешение на черновики в sandbox.
7. **Тихая потеря хуже шумного отказа.** Любая эвристика, способная
   отбросить содержимое, обязана иметь ограничитель и тест на
   НЕсрабатывание.

## 9. Git-дисциплина

- Рабочая ветка прогонов сервиса: `ab-<service>-runN` от актуального
  master; канон — короткие ветки `meta/<волна>` (создаёт владелец канона).
- `git add -- <точный перечень>`; никогда `git add .` / `-A`.
- Коммит — по готовности проверенной итерации; тема в прошедшем времени;
  в теле «Откуда взяты факты:» с перечнем страниц источника.
- Пуш/MR — по git-workflow канона; записка для команды к MR.
- Чужие файлы в репо (комплекты других аналитиков, архивные копии в
  sandbox) не редактируются — замечания владельцу.

## 10. Чек-лист старта на новом сервисе

1. Есть локальная копия docs-репо сервиса (`git clone`, если ещё нет —
   клон нужен любому работающему, независимо от числа экспертов); создана
   рабочая ветка прогонов `ab-<service>-run1` (наши фактические примеры:
   `ab-fs-run1…run3` в docs-file-storage, `ab-esk-run1…run6l` в репо
   контрактов; номер N растёт при аннулировании линии — см. журнал
   прогонов протокола).
2. **Проверен профиль sources** (`sources/README.md` — назначение и
   обязательные блоки описаны в conventions §1.1, шаблон —
   `_meta/templates/sources-readme.md`): пути существуют, выгрузка
   актуальна (битый профиль уводит агента не туда — находка В-1).
   Целевая топология источников — по roadmap (v6): репо-хроника
   `src-<сервис>` (`sources/raw/` — нетронутая копия, ТОЛЬКО чтение;
   `sources/confluence/` — «чистый ПРОМ» от тега `src/PROM`, хронология
   задач) + комплект `docs-<сервис>`; замечание: пилот file-storage исторически
   держит sources и output в одном репо — на новых сервисах следуйте
   roadmap.
3. Инвентарь разделов выгрузки → таблица «раздел → тип(ы) артефактов →
   скилл → порядок» (образец — в протоколе file-storage). Ключевое
   правило инвентаря — принцип 2 «классификация по природе, а не по
   месту записи»: тип назначается по СОДЕРЖИМОМУ страниц, а не по имени
   раздела, и маппинг «раздел → тип» может быть 1:N. Как именно раздел
   распадается — специфика каждого сервиса; примеры пилота: раздел
   «Методы» дал три природы (контракты API сервиса + поведенческая
   «логика методов» + контракты чужой АС MFlash), раздел «Процессы»
   содержал справочник статусов (ушёл в модель данных) и статусную
   модель, раздел «МД» — сущности и отдельный справочник. Симптом ошибки
   инвентаря: артефакт «не лезет» в шаблон типа — остановитесь и
   переклассифицируйте, не дожимайте шаблоном.
4. Предсказания записаны.
5. Порядок типов — **по убыванию независимости** (сначала типы с
   наименьшими входными зависимостями, чтобы последующие ссылались на
   уже существующие артефакты, а не копили долги):
   **модель данных → функции → процессы (+статусная модель) →
   вызовы контрактов → контроли/экраны → BRD** (только финальным заходом
   `create-brd` по готовому SRS). Взаимные ссылки соседних типов
   (функции↔процессы) дают долги в одну сторону — это нормально, долг
   снимается следующим заходом.
6. Протокол сервиса заведён.

## 11. Куда нести вопросы

- Классы находок и спорные волны — владельцу канона (координатор фазы).
- Разбор находок командой — на регулярном коротком синке; реестр
  находок — общий, перед новым разбором ищите свой класс в нём.
