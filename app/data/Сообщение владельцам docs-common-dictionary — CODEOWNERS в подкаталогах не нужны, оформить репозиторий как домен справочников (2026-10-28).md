# Владельцам репозитория docs-common-dictionary: CODEOWNERS в подкаталогах не нужны; репозиторий — домен справочников, предлагаю оформить его как домен

Дата: 2026-10-28. От владельца канона. Повод — вопрос при прогоне гейта переноса (`transfer_gate.py`) по
`EAN/docs-common-dictionary` (trunk `999325d`): гейт требует `CODEOWNERS` в каталоге каждого справочника.

## 1. Ответ на вопрос: файл в каждом справочнике создавать не нужно

GitLab читает `CODEOWNERS` только из трёх мест: корень репозитория, `docs/CODEOWNERS`, `.gitlab/CODEOWNERS`.
Файл внутри подкаталога (например `branches/CODEOWNERS`) для GitLab не существует и владельцев не назначает.
Ваш корневой `CODEOWNERS` устроен правильно: секция `[Analytics]` с правилом на каждый каталог справочника —
именно так назначается владелец комплекта в репозитории с несколькими комплектами. Чек-лист платформы
(SDLC-07) требует файлы «в месте, предусмотренном стандартом платформы», то есть в корне репозитория; CORE-04
требует лишь, чтобы ответственный был назван.

Красный CORE-04 — дефект гейта, не репозитория: режим репозитория документации исходил из «один комплект =
один репозиторий» и ищет `CODEOWNERS` в корне комплекта. Исправление поставлено прибору: гейт будет искать
`CODEOWNERS` и `gpb-manifest.json` в корне домена (а без домена — в корне git-репозитория), засчитывать ✓ при
правиле на каталог комплекта и предупреждать, если комплект покрыт только правилом по умолчанию `*`. Срез
канона с исправлением сообщу. До него ✗ CORE-04 по вашим справочникам — известное ложное срабатывание,
заводить файлы ради него не нужно.

## 2. Что поправить в репозитории сейчас

1. **Корневой `CODEOWNERS`:** у трёх справочников, добавленных последним коммитом, строки нет, и они попадают
   под правило по умолчанию `* @eshefer` с одним владельцем. Добавить в секцию `[Analytics]` строки для
   `/currency/`, `/fatf/`, `/swift/` с владельцами, как у остальных.
2. **Подкаталожные `CODEOWNERS` удалить** — их пятнадцать: `bank-client`, `branch-services-classifier`,
   `branches`, `countries`, `country-call-codes`, `document-type`, `error-message`, `goz-activity-type`,
   `mobile-app`, `okfs`, `okopf`, `services`, `short-link`, `types-doc`, `types-doc-eco`. Они мёртвые
   (GitLab их не читает) и создают иллюзию назначения; после исправления гейт будет на них указывать
   строкой «можно удалить».
3. **`gpb-manifest.json` в подкаталогах** (15 из 20) не трогать: нужен ли платформе манифест на каждый комплект
   внутри репозитория — вопрос к платформе AI Factory, гейт их требовать не будет, корневой манифест печатает
   как сейчас.

## 3. Предложение: оформить репозиторий как домен справочников

По норме канона (гид адресации, раздел «Подсервисы и домены») домен — несколько сервисов одной команды в
одном docs-репозитории с рамкой домена в корне: комплекты сервисов в подкаталогах, в каталоге сервисов
запись на каждый сервис с полем `repo` внутрь репозитория и полем `domain`, записи самого домена нет.
docs-common-dictionary — ровно это, и это первый живой доменный репозиторий в Экосистеме: 20 комплектов по
подкаталогам, у части справочников уже свои записи в каталоге, один `CODEOWNERS` с правилами по каталогам.
Не хватает рамки домена, по которой прибор и читатели распознают домен; сегодня прибор считает каждый
справочник одиночным сервисом — отсюда и ложный CORE-04.

Что нужно (заход команды по шаблонам канона, правок канона не требует):

1. **Корневой `README.md` в доменной форме** — шаблон `_meta/templates/docs-readme.md`, раздел «Корневой
   README домена»: название домена, раздел «Документы домена» (`domain-vision.md`, `glossary.md`, строка
   режима глоссария), раздел «Сервисы домена» — таблица с шапкой по шаблону: `service-id | Слот | Название | Вход`
   (service-id — каталог комплекта). Прибор распознаёт домен именно по этой таблице в README родителя комплекта. Нынешняя таблица справочников
   (колонки «Справочник, Комплект SRS, Кратко») — хороший материал для неё, но колонки и шапка должны быть
   по шаблону. Формулировку «документация сервиса common-dictionary» убрать: домен — не сервис, записи
   «common-dictionary» в каталоге нет и не будет.
2. **Колонка «Слот» = «нет»** для всех справочников. Тогда идентификаторы артефактов (`ENT-001`, `FUN-BNK-01`)
   остаются как есть — перенумерация комплектов не нужна. Слот нужен только там, где ID должны различаться
   между сервисами домена в одном тексте.
3. **`domain-vision.md`** (`VIS-000`) по шаблону `_meta/templates/domain-vision.md`: зачем справочники вместе,
   карта сервисов (совпадает с таблицей README), что общее. Рамка, не сумма концепций: концепции справочников
   остаются в их `service-vision.md`.
4. **`glossary.md` домена** (`GLO-000`) и выбранный режим в README: «доменный» (один файл, в комплектах
   глоссария нет) либо «доменный + указатели» (в каждом комплекте указатель на термины домена).
5. **Общий сервис `shared/`** — только если у справочников есть общее (общие сущности, общие функции). По вашему
   README общего нет — тогда каталог не заводится.
6. **Каталог сервисов `_meta/services.json` канона** — MR в канон от вашей команды: у каждой записи
   справочника поле `domain: "common-dictionary"` и `repo` на каталог комплекта вида
   `https://gitlab.gboteam.ru/EAN/docs-common-dictionary/-/tree/HEAD/<каталог>`. Текущее состояние по
   trunk `999325d`:

   | `countries` | `country-directory` | docs-common-dictionary/countries | добавить `domain` |

7. **Проверка:** после приведения README `selfcheck.py --docs <каталог справочника>` должен печатать строку
   «i домен: корень docs-common-dictionary, сервис <каталог>…», а гейт после исправления — ✓ CORE-04 по
   корневому `CODEOWNERS`.
