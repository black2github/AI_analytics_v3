# Контекст

## Экосистема

Система дистанционного банковского обслуживания юридических лиц (Экосистема) состоит из большого набора микросервисов (или просто сервисов). Часть микросервисов относятся к платформенным или системным (такие как авторизация, формирование подписи, системные справочники и т.д.) и используются остальными микросервисами, ориентированными на бизнес.

В настоящее время (что планируется изменить в близкой перспективе и подробности - далее) по аналитике, каждый микросервис, включая платформенные микросервисы, состоит из большого числа страниц Confluence, описывающих взаимосвязанные требования. 

Каждому типу требований (процессы, диаграммы состояний, модели данных, функции, интеграционные методы, экранные формы, печатные формы, контроли, нотификации, агенты, информационная безопасность) соответствует свой шаблон, определяющий правила оформления страницы с требованиями. Такие шаблоны описаны в виде Confluence страниц.

## Текущие процессы производства

Каждый микросервис закреплен за одной командой, включающей технического лида, лида-аналитика и 2 аналитика, разработку (2 бэкэнд разработчика, 2 фронтэнд разработчика) и тестирование (2 тестировщика).

Одна команда может сопровождать несколько микросервисов. Для платформенных сервисов используются отдельные команды, построенные на аналогичных принципах. То есть существует некоторая специализация в плане того, какими типами сервисов занимается команда.

Работа аналитиков строится согласно документа “`Правила оформления аналитики ДБО` ”. 

**Важно:** Описание аналитики выполняется на логическом уровне, без привязки к реализации (физическому уровню) везде, где это возможно.  

При поступлении запроса или новой постановки от представителей бизнеса, она отражается в Jira в виде эпика. В рамках выполнения работ происходит декомпозиция запроса на отдельные подзадачи, которые так же отражаются в Jira в виде записей типа story (истории), привязанных к эпику. Далее номер истории в Jira используется как идентификатор задачи Jira, с которым и связывается очередной набор измененных требований. То есть подзадача по факту (история) часто называется задачей для упрощения коммуникаций внутри команды, если это не создает недопонимания. 

## Планы

Управлением аналитики принято решение по переходу на принципы создания аналитики по Doc-as-Code. Разработка и тестирование уже используют в работе GitLab, для них это стандартный режим работы. 
Инструменты для конвертации страниц Confluence в markdown мы с тобой проработали (migrate-confluence-tree.py, critic.py). Это техническая основа.

Прорабатывается план пилотного проекта по миграции на doc-as-code первой группы сервисов. В рамках проекта предполагается и некоторое изменение структуры формирования требований, чтобы использовать преимущества doc-as-code. 

В максимальном варианте хочется перейти на автоматизацию создания требований AI-агентом с проведением ревью человеком-аналитиком. В минимальном варианте - реструктурировать описание требований, чтобы их можно было сопровождать и развивать в markdown формате, ориентируясь на API First подход разграничения ответственности аналитиков и разработки.

Так же важно исключение использования большого числа вложенных таблиц. Наличие большого числа вложенных таблиц является следствием удобства работы в Confluence и легкости и удобства создания там таблиц, включая вложенные, что, в свою очередь, для markdown формата и работе с Git является серьезной помехой или неудобством. 

Ограничение: Сейчас работа аналитиков в Confluence ведется в закрытом контуре, без доступа в интернет. Предполагается:

- конвертация требований в markdown формат с атрибуцией требований информацией об идентификаторах задач Jira (с помощью migrate-confluence-tree).
- Перенос markdown файлов на внешний контур с доступом в интернет
- Вливание в репозиторий GitLab внешнего контура c созданием веток, каждая из которых связана с группой задач (эпиком).

Дальнейшая работа будет идти во внешнем контуре.

Примерный план пилотного проекта - здесь https://docs.google.com/document/d/11pNM890aXV_kyzu5UjfzXGar3ApVygpJ2XpGv9YvtG4/edit?tab=t.0#heading=h.p7o1wmdujxhk.

Предполагается, что я буду выступать в роли эксперта-аналитика и с твоей помощью мы доработаем централизованный набор скиллов, который подойдет для нескольких разных по типу сервисов (платежные сервисы, типа РКО; заявочные неплатежные сервисы, типа корпоративные карты или сервис открытия счета; системные сервисы типа авторизации или передачи файлов и т.д.).

**Важная особенность**:  Не смотря на то, что все сервисы должны были бы быть описаны по единым правилам/шаблонам, их существенная специфика нашла свое отражение в том, что описание сервисов все же существенно рознится. Например: в расчетных сервисах для описания требований часто используется шаблонизация, которая покрывает набор документов конкретного типа (платежное требование, платежное поручение, валютный перевод и т.д.). Заявочные сервисы (нерасчетные бизнес-сервисы) ближе всего к “каноническому” описанию согласно шаблонов документов по типам. Системные сервисы часто нарушают границы логического описания, так как детали физической / низкоуровневой реализации становятся важным предметом согласования/проработки.    

В настоящее время уже создан предварительный набор скиллов (на примере сервиса “открытие второго счета” c кодом сервиса o2Plus). Сервис является классическим заявочным сервисом. Набор скиллов предназначен для того, чтобы с помощью AI-агентов преобразовывать требования, выгруженные из Confluence в markdown в некоторый “целевой” формат представления. Строго говоря, этот формат пока нельзя назвать “целевым”, так как это только предложение и целевой формат должен быть уточнен в результате пилотного проекта параллельно доработки скиллов.

Полной уверенности, что получится доработать единый набор скиллов в ограниченное время проекта - еще нет ввиду различий групп сервисов. Это интересная и амбициозная задача. Но, здравый смысл и опыт подсказывает, что можно будет, как минимум,  выделить “ядро” скиллов для преобразования аналитики, а затем, в зависимости от того, к какой категории принадлежит конкретный сервис (расчетный, заявочный, системный) использовать те или иные специализированные скиллы или части скиллов. То есть в процессе проекта и доработки скиллов такой вариант так же является одним из возможных. В целом, надеюсь, что ты сможешь предложить и еще варианты, чтобы с одной стороны - поддержать централизацию скиллов, с другой - учесть структурную специфику сервисов, а с третьей - по-прежнему поддержать формат получаемых документов, приемлемый и для ручного развития “человеком” и для развития с помощью AI-агентов.  

Описание правил преобразования описано в каталоге `C:\doc-as-code\EAN\docs-o2new\_meta`. Не смотря на его множество достоинств по сравнению с текущим описанием в Confluence, в текущем формате и скиллах есть недостатки и недоработки.
