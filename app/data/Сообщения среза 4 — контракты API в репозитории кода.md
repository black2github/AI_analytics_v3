## 1. Владельцам комплектов с каталогом `api/` — docs-sign и docs-file-storage

> Коллеги, решение руководителя от 2026-10-06 по спецификациям API: контракты OpenAPI и AsyncAPI
> живут только в каталоге `api-specification/` репозитория кода сервиса; копий YAML в комплекте
> документации нет, каталог `api/` в комплекте не создаётся. Стандарты (`conventions.md` §5.1,
> `repo-topology.md` §3, §4, §8, §10) и канон обновлены: eco-techbook `10a7b26`, канон
> `5f377e7`.
>
> Что это значит для вашего комплекта. В нём есть каталог с контрактами:
> — docs-sign: `srs/dst-management/api/` (3 файла);
> — docs-file-storage: `docs/api/` (2 файла).
> Инструмент проверки комплекта после обновления канона показывает его строкой
> `⚠ контракты в комплекте: каталог …/api/ (N файлов) — …`. Это предупреждение, не брак: вердикт
> не меняется, срочности нет.
>
> Что нужно сделать при ближайшей правке комплекта, одним коммитом:
> 1. Убедиться, что содержимое каталога есть в `api-specification/` репозитория кода сервиса (если
>    нет — передать разработке, это их зона; в комплекте файлы при этом всё равно не остаются).
> 2. Удалить каталог из комплекта:
>    `git -C <клон комплекта> rm -r -- <путь к каталогу api>` → в выводе строки `rm '…'` по
>    каждому файлу.
> 3. Если в `README.md` комплекта есть пункт или строка таблицы «API — контракты: `api/`» —
>    убрать (шаблон `docs-readme.md` их больше не содержит).
> 4. Строки раздела матрицы «Покрытие: API ↔ SRS», которые ссылались на файлы в `api/`, перевести
>    на файл контракта в репозитории кода: ссылка через `HEAD` и имя операции текстом, например
>    `Источник: https://gitlab.gboteam.ru/ECO_BE/ms-<код сервиса>/-/blob/HEAD/api-specification/<файл>.yaml, операция <operationId>`.
>    Имя ветки (`master`, `trunk`) в ссылке не пишется.
> 5. Прогнать проверку комплекта — строка `⚠ контракты в комплекте` должна исчезнуть.
>
> Вопросы и расхождения — записью в `feedback.md` вашего репозитория либо мне напрямую.

## 2. Координатору КК

> Канон обновлён до среза `0999e86` (включает `5f377e7`). Акцептующему: обновить клон канона и принять срез
> (`accept_canon.py`); ожидаемая строка гейта — `✓ срез канона: профиль 0999e86 = HEAD канона 0999e86`.
>
> Суть срезов: контракты OpenAPI/AsyncAPI живут в `api-specification/` репозитория кода, в
> комплект не копируются, каталог `api/` не создаётся (решение руководителя 2026-10-06); скилл
> генерации AsyncAPI из канона снят. На текущую работу это не влияет: заходы в `api/` не пишут,
> ваш комплект каталога `api/` не содержит, скилл генерации вами не использовался.
> Ожидаемый эффект на гейте — нулевой: новых строк быть не должно.
>
> Что меняется для будущих заходов:
> 1. Карточки вызова методов других сервисов (`CALL-INT`): если владелец уже перешёл на API First
>    (его контракт с `summary`/`description` опубликован в `api-specification/`), цель ссылки в
>    шапке — файл контракта по адресу `https://gitlab.gboteam.ru/ECO_BE/ms-<код владельца>/-/blob/HEAD/api-specification/<файл>.yaml`
>    и операция текстом; код владельца — из каталога сервисов. Пока владелец не перешёл — как
>    раньше, карточка `INTC` владельца. Дерево выбора — документ адресации §5.2 и §10.
> 2. Собственные методы сервиса: карточки `INTC` создаются как раньше, пока «Корпоративные карты»
>    не перешли на API First; порядок снятия карточек при переходе — шаблон `internal-contracts.md`,
>    раздел «Снятие карточки при переходе на API First». Для текущей миграции это не действует.
> 3. Матрица, раздел «Покрытие: API ↔ SRS»: ссылки на файлы в репозитории кода — только через
>    `HEAD`; прибор предупреждает о явном имени ветки.
> 4. Асинхронные обмены (MQ / Kafka), если встретятся в выгрузке: описываются карточками `INTC`
>    по разделу «Асинхронные операции» шаблона `internal-contracts.md` — одна карточка на операцию
>    (`send` и `receive` раздельно), имя операции по правилу `<Система>_<Платформа>_<Протокол>_<Название>`;
>    контракт AsyncAPI в комплект не пишется, sequence-диаграмма — в карточке процесса.
>
> Промпты этапов менять не нужно.

## 3. Жукову Илье (библиотечные контракты)

> Илья, по решению руководителя от 2026-10-06 контракты OpenAPI/AsyncAPI живут только в
> `api-specification/` репозитория кода, в комплектах документации YAML нет. Слой библиотечных
> контрактов `LIBC` (`srs/lib-contract/`) это не затрагивает: у библиотеки контракта в
> `api-specification/` нет, это код, исполняемый в контуре потребителя, карточки `LIBC` остаются в
> комплекте как были. Формулировка §5.1.4 конвенций уточнена именно в этом смысле (eco-techbook
> `10a7b26`). Для MR 104/198 ничего менять не нужно.
