# Быстрый старт: миграция сервиса с ИИ-координатором (быстрый трек)

Один лист для команды, стартующей миграцию большого сервиса по плану
(промпт плана v2.x) и с ИИ-координатором (см. промпт координатора v1.0, далее - "координатор").
Быстрый старт — только порядок действий; нормы живут в гиде миграции
(`_meta/migration-guide.md` клона канона, далее - "гид") и протоколе миграции
(`_meta/tools/step-protocol.md`, далее - "протокол") — при расхождении правы они.

Комплект быстрого трека — три файла, передаются вместе:
- этот быстрый старт, 
- «Промпт генерации плана миграции сервиса к эталону» (v2.x), 
- «Промпт координатора миграции сервиса» (v1.0).

## Шаг 0 — решения до техники (полчаса)

1. Назначьте **акцептующего** — лида-аналитика сервиса: приёмки,
   коммиты, push, отмашки; все необратимые действия — только он.
2. Осознанно выберите трек (вариант миграции). Быстрый: координатор с отмашки
   акцептующего сам правит файлы вашего репозитория (промпты, опись,
   план). Не готовы к этому — работайте по гиду без координатора:
   треки равноправны, переход возможен в любой момент, журналы
   остаются.
3. Проверьте комплект выдачи: ссылки на ветки **`ext/extension-points`**
   (канон docs-o2new и стандарты eco-techbook), два промпта, копия
   референс-стенда (`src-business-cards`).

## Шаг 1 — окружение и выгрузка (человек)

По инструкции «Как пользоваться» промпта плана, пп. 0–7: git и Python;
репозиторий сервиса `src-<сервис>`; клоны четырёх репозиториев ПО
ВЕТКАМ обкатки; смок-проверка `selfcheck.py` по эталону («ИТОГО…» =
окружение готово).

Самый содержательный пункт для большого сервиса — **выгрузка
ПРОМ-среза** утилитой `confluence-tree-exporter`:

- выгрузка обязана быть доведена до чистового вида — БЕЗ
  CriticMarkup-разметки (доводка — ваша зона ответственности);
- замороженные поддеревья (содержимое ждёт неутверждённых Jira-задач)
  обязаны нести frontmatter-флаг `unapproved_jira: <JIRA-ID>` — тогда
  опись пометит их `frozen:<ID>`, а план автоматически отложит до
  утверждения задачи. Флаг без истории изменений на странице ставится
  вручную (`--flag-page` конвейера доводки).

Дефект выгрузки у большого сервиса размазывается по всем этапам —
не экономьте на этом шаге.

## Шаг 2 — сессия координатора (первое действие после окружения)

Откройте агентную сессию в IDE (сильная LLM, доступ к репозиториям и
терминалу) и отправьте промпт координатора целиком с заполненными
входными данными (план: «ещё не создан»). Координатор определит
текущую фазу по состоянию репозитория и поведёт вас дальше (будет направлять вас).

С этого момента вопрос «что дальше?» задаётся координатору. Сессия координатора —
**ОДНА на всю миграцию**, но РАСХОДНАЯ: якорь — журнал
`coordination-log.md`; при обрыве/сбое - просто откройте новую сессию тем же промптом,
она поднимется с журнала.

## Шаг 3 — фаза A: план (под руководством координатора)

1. По подсказке координатора откройте ОТДЕЛЬНУЮ сессию планировщика:
   промпт плана v2.x целиком, сильная LLM.
2. Планировщик проведёт инвентаризацию и задаст вопросы — ответьте на
   все; план с открытыми вопросами не принимается.
3. Для большого сервиса (≳200 страниц) ключевой вопрос —
   **разметка подсервисов** (шаг 2а промпта плана): утверждает
   акцептующий, порядок кусков — общая часть → core → зависимые.
4. Результат: план + опись + профиль источников + промпт ПЕРВОГО
   этапа. Акцептующий ревьюит и утверждает.
5. Сессию планировщика НЕ закрывайте: промпты остальных этапов она
   собирает по одному, перед каждым этапом, весь проект.

## Шаг 4 — фаза B: цикл этапа (повторяется до конца плана)

1. **Прогноз**: координатор пишет в журнал ожидание результата, риски
   и первоочередные проверки — ДО запуска (см. далее).
2. **Запуск**: акцептующий открывает СВЕЖУЮ (НОВУЮ) сессию исполнителя,
   передаёт указание на файл промпта этапа (не копипаст). Первые
   заходы нового типа или зоны — только сильная модель.
3. **Заходы**: после каждого — гейт и сдача; техприёмку сдачи делает
   координатор (чек-лист по фактам стенда + сверка с прогнозом) и даёт
   рекомендацию акцептующему «принять / дозаход / вопросы».
4. **Решение и коммит — акцептующий.** Отмашка следующего захода —
   стандартной формулой (черновик готовит координатор, отправляет
   акцептующий).
5. Промпт следующего этапа получаете через запрос к планировщику (в его сессии);
   актуальные решения доезжают до промпта правкой файла, то есть фиксируются в самом файле промпта (окна
   внесения — гид, «Решения аналитика»).

## Постоянные правила (весь проект)

- Решения — только в файлы (опись, план, промпты): решение, сказанное
  агенту в чате, — потерянное решение.
- Вопросы агентов к источнику — записями OQ-NN в `open-questions.md`;
  вопрос без записи не существует.
- Дефект прибора (см. термины в других файлах) не обходится молча: запись FB-NN в `feedback.md` +
  MR-тред владельцу канона; сроки его реакции — гид, «Обратная связь».
- Три журнала репозитория: `coordination-log.md` (координация),
  `open-questions.md` (вопросы), `feedback.md` (обратная связь).

## Три типовые ошибки

1. **Смешение сессий.** Координатор, планировщик и исполнитель — ТРИ
   **разных** агента с разными промптами и правами; каждому — своя сессия.
2. **Экономия на модели** в первых заходах типа/зоны: слабая модель
   фабрикует содержимое — доказано контролируемым экспериментом
   (гид, «Правило моделей»).
3. **Старт по недолеченной выгрузке** — для большого сервиса самая
   дорогая ошибка (см. шаг 1).

## Первые три действия буквально

Назначить акцептующего → выгрузка и окружение (пп. 0–7 промпта
плана) → открыть сессию координатора. Дальнейшее диктует координатор.
