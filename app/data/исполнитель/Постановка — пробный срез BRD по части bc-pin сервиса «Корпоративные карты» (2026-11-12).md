# Постановка — пробный срез слоя BRD по части bc-pin сервиса «Корпоративные карты» (2026-11-12)

Состояние: к исполнению (слово владельца канона на запуск — 12.11.2026). Постановщик и приёмка норм — сессия «Точки расширения эталона». Подтверждающий аналитик по содержанию — владелец канона (его решение 12.11.2026).

## 1. Зачем срез

Слой бизнес-требований у сервиса «Корпоративные карты» не собирался. Решение владельца 10.11.2026: слой собирается скиллом `create-brd` из готового комплекта SRS; страницы бизнес-требований из выгрузки Confluence служат только для сверки, в текст BRD не попадают.

Полный инвентарь сервиса — 129 функций, 50 процессов, 22 контроля, 12 печатных форм (замер 10.11, перед полной сборкой пересчитать). Прежде чем собирать его целиком, проверяем метод на одной небольшой части и получаем три ответа:

1. что прибор говорит о каталоге `docs/brd/` — на этом сервисе слой прибором не мерился;
2. сколько времени занимает сборка на единицу инвентаря — для оценки полной сборки;
3. читается ли результат подтверждающим аналитиком как бизнес-требования, а не как пересказ SRS (прецедент другого сервиса, сентябрь 2026: BRD пересказывал SRS неточно).

Срез — проба метода. В `master` он вливается только отдельным словом владельца после его чтения.

## 3. Охват

Инвентарь берётся только из реестров части `docs/srs/bc-pin/` (на `649036a8`):

Вне охвата: остальные части сервиса; `docs/service-vision.md` и `docs/glossary.md` (скилл их не трогает); каталог НФТ (вход `nfr_sources` пуст, шаг 5 скилла пропускается); корневой `docs/README.md` — в пробном срезе не обновляется (шаг 6 скилла выполняется только в части `docs/brd/README.md`), чтобы навигация комплекта не обещала слой, которого в `master` нет.

## 4. Что получается на выходе

Целевое состояние ветки:

1. **`docs/brd/`** содержит `README.md`, `business-rules.md`, `features/` с реестром, `use-cases/` с реестром — по шаблонам канона. В каждом документе — пометка происхождения по скиллу: `origin: reconstructed-from-srs` во frontmatter и первая строка преамбулы дословно из скилла.
2. **Идентификаторы** — сквозные по сервису, без кода части (конвенции §5): фичи `F-CL-NN` / `F-BNK-NN`, истории `US-NN`, требования `FR-NN.M`, сценарии `UC-NN`, правила `BR-NN`. Срез занимает номера с первого. В `docs/brd/README.md` отдельной строкой сказано: собрана часть «Установка ПИН-кода», остальные части сервиса не собраны, номера при полной сборке могут быть пересчитаны.
3. **Рабочая таблица «утверждение → идентификатор и раздел SRS»** лежит в `sandbox/brd-pilot-bc-pin-claims.md`. Каждое утверждение документов BRD имеет в ней строку до того, как попало в документ; строк без места в SRS — ноль (шаг 1 порядка сборки, самопроверка п. 3 скилла).
4. **Матрица** `docs/traceability-matrix.md` получает секции слоя BRD (конвенции §5.3 п. 8) только для собранного: «BRD → SRS», «BR → фича/UC», «UC → фичи». Существующие строки матрицы не меняются. Исправление постановщика по итогам приёмки 12.11: раздел «Реестр ID» получает строки документов слоя (конвенции §5.3 п. 4 — каждый выданный ID имеет строку реестра) — их добавляет `matrix_sync.py --docs docs --write`, руками они не пишутся; к трём секциям добавляется секция счётчиков гейтов достаточности (конвенции §5.3 п. 8–9) по инвентарю части. Первая редакция этого пункта запрещала любые изменения существующих разделов и тем самым запрещала строки реестра — это была ошибка постановки, а не исполнителя.
5. **Тела документов BRD не ссылаются на SRS** и наоборот (конвенции §5.4): статусы — бизнес-наименованием, проверки — словами правила. Стыковка — только в матрице.
6. **Сверка со страницами бизнес-требований.** Вход `brd_reference` — две страницы выгрузки этой части: `1026987183` «[КК_ПИН] Установка ПИН-кода» и `2166861763` «[КК_ПИН] Бизнес-требования» (опись `inventory.md`, метка `brd`, reference-only). После сборки страницы читаются и сверяются с собранным; каждое расхождение записывается в `sandbox/brd-pilot-bc-pin-reference-diff.md`: что на странице, что в BRD, где в SRS. В текст BRD со страниц ничего не переносится.
7. **Журнал открытых вопросов `open-questions.md` в ветке не меняется.** Журнал только дополняется, номера идут по порядку, и в него параллельно пишут конвейер координатора и сессия «Вопросы КК». Новые вопросы среза — файлом `sandbox/brd-pilot-bc-pin-questions.md` без номеров, в форме записи журнала; номера присваивает координатор КК при вливании.

## 5. Гейты достаточности для среза

Гейты считаются по инвентарю части, а не сервиса (конвенции §5.3 п. 9):

| Гейт | Ожидание на срезе |
|---|---|
| функции без `US` | 0 из 6 |
| сценарные процессы без `UC` | 0; какой из трёх процессов сценарный, а какой нет (PROC-042 — родительская минимальная карточка, PROC-043 — диаграмма последовательностей) — решение записывается в отчёте с основанием |
| доменные политики без `BR` | 0; CTL-414 проходит фильтр «что не бизнес-правило» скилла `create-business-rules`, результат фильтра — в отчёте |
| печатные формы без связи | не применимо, форм нет |
| сироты BRD (`F`/`US`/`FR`/`BR`/`UC` без связи с SRS) | 0 |

Функция, которой нет бизнес-смысла для заказчика (системная FUN-SYS-34 — библиотечная процедура), всё равно получает место: либо входит в историю, которая её использует, либо в отчёте стоит как осознанно не покрытая с основанием. Молча не пропускается.

Ожидание: число ✗ по файлам вне `docs/brd/` и вне новых секций матрицы — как на `origin/master` (базовый прогон того же запуска на чистом дереве сделать до первой правки и сохранить в `sandbox/selfcheck-brd-pilot-base.txt`; на 12.11 полный прогон даёт ✗ 0). Запуск без `--sources` и `--raw` для сравнения не годится: на чистом состоянии он даёт 34 ошибки и вердикт «БРАК» — это свойство облегчённого запуска.

```
C:\Python312\python.exe C:\doc-as-code\EAN\docs-o2new-kk-c3385b1\_meta\tools\matrix_sync.py --docs docs --check
C:\Python312\python.exe C:\doc-as-code\EAN\docs-o2new-kk-c3385b1\_meta\tools\link_debts.py --matrix docs\traceability-matrix.md --docs docs --strict
```

**Каждое замечание прибора по `docs/brd/` и по секциям BRD матрицы записывается в отчёт дословно.** Замечание, которое исполнитель считает ложным (прибор не знает слой), не обходится правкой документа под прибор и не гасится исключением — оно идёт постановщику списком: это и есть первый ответ, ради которого срез делается.

## 7. Границы и остановки

- Пересказ вместо реконструкции — брак: утверждение без строки в рабочей таблице в документ не вносится.
- Пробел или противоречие в SRS, найденные при сборке, в SRS не исправляются: карточки `docs/srs/**` в ветке не меняются. Находка — в файл вопросов (п. 4.7).
- Дефект источника не лечится формулировкой BRD: бизнес-требование записывается так, как следует из SRS, расхождение со страницей бизнес-требований — в файл сверки.
- Остановиться и написать постановщику, если: реестры части разошлись с таблицей раздела 3; шаблон канона не даёт места факту из SRS; прибор падает (а не выдаёт замечания); для покрытия функции части нужна карточка другой части сервиса.

## 8. Сдача

Одним сообщением сессии «Точки расширения эталона»:

1. хеш вершины `exec/brd-pilot-bc-pin` и число коммитов;
2. перечень собранного: фичи, истории, сценарии, правила — идентификатор и название;
3. таблица гейтов раздела 5 со значениями и основаниями решений;
4. числа обоих прогонов `selfcheck` (базовый и итоговый) и список замечаний прибора по слою дословно;
5. число строк рабочей таблицы и число строк без места в SRS (ожидание — ноль);
6. число расхождений со страницами бизнес-требований и число новых вопросов;
7. затраченное время по шагам порядка сборки — для оценки полной сборки;
8. спорные места в форме «вопрос / предположение / что проверить».

Приёмка: постановщик проверяет нормы и повторяет прогоны прибора; затем владелец канона читает `docs/brd/` как подтверждающий аналитик. Решение о полной сборке и о судьбе ветки — его отдельным словом.
