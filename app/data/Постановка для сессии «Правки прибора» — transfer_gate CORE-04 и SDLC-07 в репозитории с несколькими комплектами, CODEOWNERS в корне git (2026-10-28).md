# Постановка: transfer_gate — CODEOWNERS и gpb-manifest.json искать в корне git-репозитория, а не в корне комплекта (CORE-04, SDLC-07)

Дата: 2026-10-28. Для сессии «Правки прибора, акцепт и рутина». Коммит analyzer — по слову владельца; ветка канона — по его командам.

## Проблема

Гейт переноса в режиме репозитория документации (`--src <комплект>`, `docs/` нет, матрица в корне) проверяет
`CODEOWNERS` и `gpb-manifest.json` в корне комплекта (`check_target_repo`, `in_place=True`, `transfer_gate.py`
около строки 919). Предположение прибора: один комплект = один репозиторий. В репозитории общих
справочников `EAN/docs-common-dictionary` (trunk 999325d) комплектов двадцать, по подкаталогу на справочник
(`branches/`, `countries/`, `currency/`…), а `CODEOWNERS` один, в корне репозитория, с секциями по
подкаталогам (`/branches/ @atrushin @eshefer @admitrichev`). Гейт по `--src <repo>/currency` даёт
✗ CORE-04 «CODEOWNERS отсутствует», хотя владельцы назначены там, где их читает GitLab.

GitLab читает `CODEOWNERS` только из трёх мест: корень репозитория, `docs/CODEOWNERS`, `.gitlab/CODEOWNERS`.
Файл `CODEOWNERS` внутри подкаталога комплекта для GitLab не существует. Десять таких файлов в подкаталогах
справочников (например `branches/CODEOWNERS` со строкой `* @atrushin …`) появились, видимо, ради гейта — это
мёртвые файлы, они владельцев не назначают. Гейт не должен подталкивать команды их заводить.

## Что сделать

1. **CORE-04 в режиме `in_place`:** корень для поиска — сначала корень домена по правилу прибора
   (`kitcheck.checks._common.domain_context`: родитель комплекта с README, в таблице сервисов которого есть
   каталог комплекта — тот же признак, по которому selfcheck пишет «i домен: корень …»); если домена нет —
   вершина git-репозитория (`git -C <src> rev-parse --show-toplevel`; git недоступен — подъём по родителям до
   каталога с `.git`). Это и есть отложенный «срез прибора по первому домену» для гейта: docs-common-dictionary —
   первый живой доменный репозиторий (20 комплектов), пока его README не в доменной форме — работает запасной
   путь через корень git, после приведения README — доменный.
   Файл ищется по правилам GitLab: `CODEOWNERS`, `docs/CODEOWNERS`, `.gitlab/CODEOWNERS` в этом корне —
   первый найденный непустой (строки без `#`).
   - Комплект совпадает с корнем репозитория — поведение прежнее.
   - Комплект в подкаталоге: ✓ CORE-04, если в файле есть правило, покрывающее путь комплекта относительно
     корня, кроме правила по умолчанию `*`: шаблон вида `/branches/`, `/branches/**`, `branches/` или более
     общий префикс пути (сравнение по правилам gitignore-паттернов GitLab в упрощённом виде: ведущий `/` —
     от корня, завершающий `/` — каталог и всё под ним). В тексте строки ✓ — какое правило покрывает и кто
     владельцы.
   - Файл есть, но комплект покрыт только правилом `*` (или секцией `[Default]`) — ⚠ CORE-04: «владельцы
     комплекта `<путь>` назначены только правилом по умолчанию `* <кто>` — добавить строку для каталога
     комплекта в `CODEOWNERS` корня репозитория». Не ✗: владелец формально назначен.
   - Файла нет нигде из трёх мест или он пуст — ✗ как сейчас, с перечислением трёх мест, где его ждёт GitLab.
   - `CODEOWNERS` внутри подкаталога комплекта при наличии корневого — i-строка: «`<путь>/CODEOWNERS` GitLab не
     читает (владельцев назначает только файл в корне репозитория, `docs/` или `.gitlab/`) — можно удалить».
     Без корневого файла подкаталожный не засчитывается (иначе ✗ CORE-04 маскируется мёртвым файлом).
2. **SDLC-07 `gpb-manifest.json`:** тот же корень git-репозитория. Манифест корня репозитория печатается как
   сейчас (поля — для ручной сверки); манифест в подкаталоге комплекта, если есть, печатается отдельной
   i-строкой «манифест комплекта `<путь>/gpb-manifest.json`: name=…, title=…» без требования и без ⚠: нужен ли
   платформе манифест на комплект внутри репозитория — вопрос к платформе, гейт его не решает. Манифеста нет
   ни в корне, ни в комплекте — ⚠ как сейчас.
3. **Режим `--out`** (перенос в отдельный docs-репозиторий) не меняется: там `--out` и есть корень репозитория.
4. **README прибора и гид reference** (раздел о режиме репозитория документации, около строки 284): одна фраза —
   «`CODEOWNERS` и манифест ищутся в корне git-репозитория (как их читает GitLab), комплект может лежать в его
   подкаталоге; файл `CODEOWNERS` в подкаталоге комплекта GitLab не читает».

## Ограничители

- Golden-прогон гейта на одиночных репозиториях (`docs-lk-mp`, стенд, полигон `docs-account-opening-request`,
  `--out`-сценарии в тестах) — построчно без изменений: там корень комплекта и корень git совпадают.
- Тесты (`tests/test_transfer_gate.py`): (а) комплект в подкаталоге, корневой `CODEOWNERS` с правилом на
  каталог — ✓; (б) правило только `*` — ⚠ с текстом про правило по умолчанию; (в) только
  `<комплект>/CODEOWNERS`, корневого нет — ✗ (мёртвый файл не засчитывается); (г) `.gitlab/CODEOWNERS` —
  засчитывается; (д) корневой и подкаталожный вместе — ✓ плюс i-строка «можно удалить»; (е) манифест
  в подкаталоге — i-строка, манифест корня печатается; (ж) без git (tmp_path без `.git`) — подъём по
  родителям останавливается на `--src`, поведение прежнее.
- Живой прогон: `transfer_gate.py --src C:\doc-as-code\EAN\docs-common-dictionary\branches` (корневое правило
  есть, подкаталожный файл есть → ✓ + i) и `--src …\currency` (в корневом файле строки для `currency/`
  нет → ⚠ «только правило по умолчанию»). Отчёты обоих — в сдачу.
- Сообщение коммита канона — для всех команд: сначала проблема (репозиторий с несколькими комплектами,
  CODEOWNERS читается GitLab только из корня), потом что меняется.
