# Общие правила показа сообщений экранных форм — варианты решения для обсуждения с командой

Дата: 2026-11-18. Подготовлено сессией «Точки расширения эталона» по слову владельца канона: сохранить варианты, обсудить с командой, вернуться к вопросу отдельно. Решение не принято.

## 1. Вопрос

В источнике сервиса «Корпоративные карты» есть страница «[КК] Правила информирования пользователя Клиента об ошибках» (2166861183). Она задаёт для всего клиентского интерфейса сервиса, каким способом показывается сообщение в каждой типовой ситуации. Карточки у страницы нет, в комплекте этих требований нет. Нужно решить, где и в какой форме такие требования живут в комплекте — так, чтобы правило было записано один раз, а человек и AI-агент, читающие карточку одной экранной формы, его находили.

Вопрос общий: в других сервисах единого описания показа ошибок может не быть, и решение не должно создавать им замечаний.

## 3. Что уже говорит канон

- Шаблон контролей: текст сообщения — в карточке контроля; способ и место показа (под полем, информер, модальное окно) в контролях не пишутся, их дом — раздел 7 «Сообщения» экранной формы, которая вызывает группу (решение владельца 15.10.2026).
- Шаблон экранной формы, раздел 7: колонка «Тип» — закрытый словарь способов показа: «Информер», «Блоккер», «Плашка», «Модальное окно», «Под полем»; новый способ — правкой шаблона.
- README каталога экранных форм — навигационный, без шапки и без идентификатора; в каждом подсервисе свой.

Отсюда: способ, место и вид сообщения — характеристика представления, то есть экранных форм. Перенос страницы в документ контролей (первое предложение «Точек») отклонён владельцем как противоречащий этому принципу; README каталога форм не подходит, потому что он навигационный и не единственный.

## 4. Варианты

| | Вариант | За | Против |
|---|---|---|---|
| А | Разложить правило по формам: в разделе «Сообщения» каждой формы с вводом — свои строки | форма самодостаточна, ссылка не нужна | стандартные тексты копируются в десятки форм; правка правила — правка всех форм; таблица источника как целое пропадает |
| Б | Одна карточка в общей части сервиса плюс ссылка из раздела «Сообщения» каждой формы с вводом | один дом, текст источника дословно, заход малый | нужна ссылка в каждой форме и проверка её наличия; у карточки нет полей — нужно дополнение шаблона |
| В | Вынести правило на уровень платформы, комплекты сервисов только ссылаются | верно, если правило общее для всех сервисов | общность не подтверждена; решение не на стороне одной команды |

Предварительная позиция владельца (18.11): вариант Б предпочтителен. Рекомендация «Точек» — тоже Б.

### Вариант Б подробнее

- **Дом.** Каталог экранных форм общей части сервиса (в КК — `bc-component/screen-form/client`): правило относится к представлению, а общая часть — единственный подсервис, общий для всех форм.
- **Содержание.** Назначение и реестр типовых сообщений с постоянными идентификаторами строк: тип показа, ситуация, содержание. Таблица источника ложится в форму раздела «Сообщения» почти без переделки.
- **Привязка.** Одна фраза шаблона в начале раздела «Сообщения» каждой формы с вводом: ошибки контролей и интеграций показываются по общей карточке (ссылка с идентификатором и названием); отличия формы — строками ниже. Текст сообщения контроля остаётся в карточке контроля.

## 5. Условность правила и проверки

Замечание владельца (18.11): единое описание показа ошибок принято не во всех сервисах, поэтому требование ссылки не должно давать ни ошибок, ни предупреждений там, где общей карточки нет.

Как это выполняется:

- **Шаблон.** Общая карточка необязательна: заводится, только если источник сервиса задаёт общее правило показа сообщений. Фраза-привязка обязательна только в комплекте, где такая карточка есть.
- **Прибор.** Сторож сначала ищет в комплекте общую карточку. Карточки нет — молчит полностью. Карточка есть — форма с вводом без ссылки на неё получает предупреждение; это не брак и не блокер гейта.
- **Контур.** Карточка для пользователя Клиента проверяет только формы Клиента; банковские формы — когда появится своя карточка.
- **Что не покрыто.** Общая страница в источнике есть, а карточки нет: это ловит учёт покрытия источника, а не этот сторож. В КК он не сработал — опись отнесла страницу к «правилам ведения документации».

## 6. Словарь способов показа

Решение владельца (18.11): «Информер» и Snackbar — разные элементы, закрытый словарь расширяется.

На странице есть ещё один способ вне словаря — «На странице ЭФ» (сообщение о недоступности сервиса). Предложение «Точек»: добавить оба значения, написанием как в источнике. По второму значению решения нет.

## 7. Практики, на которые опираются предложения

1. **Одно правило — один нормативный дом.** Сквозное поведение интерфейса описывают один раз, как стандарт интерфейса сервиса; в стандартах на спецификации требований (ISO/IEC/IEEE 29148) правила показа сообщений об ошибках входят в требования к пользовательскому интерфейсу.
2. **Умолчание, привязка, исключение.** Общий документ задаёт умолчание по классу ситуации; форма называет, какие её события к какому классу относятся, и описывает только отличия.
3. **Связь не зависит от внимательности читателя.** Агент, работающий с одной карточкой, читает её и то, на что она явно ссылается. Поэтому ссылка стоит в фиксированном месте каждой формы одной и той же фразой шаблона, идентификаторы строк общей карточки позволяют сослаться на конкретный образец, а наличие ссылки проверяет прибор.

## 8. Вопросы к обсуждению с командой

1. Вариант А, Б или В. Есть ли у других сервисов такие же правила и не общие ли они для всей Экосистемы (тогда В).
2. При Б — вид карточки: Б-1 или Б-2.
3. Достаточно ли одной фразы-привязки в разделе «Сообщения», чтобы агент, работающий с формой, применил общее правило; нужна ли привязка строк сообщений формы к строкам общей карточки.
4. Нужна ли отдельная общая карточка для банковских форм.
5. Словарь: значение «На странице ЭФ»; написание Snackbar.
6. Что делать формам сервиса, у которого общего правила в источнике нет: оставлять способ показа в каждой форме, как сейчас.
