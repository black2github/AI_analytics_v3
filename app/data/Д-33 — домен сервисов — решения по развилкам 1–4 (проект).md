# Домен сервисов: решения по развилкам 1–4 (проект на утверждение владельца)

Постановка — реестр решений, Д-33 (2026-10-09). Здесь: модель, четыре развилки с вариантами и
рекомендацией, сценарии жизненного цикла (требование Д-26 — до правок канона), перечень домов
фактов, которые изменятся. Правки канона и прибора начинаются только после решений по этому
документу.

## 0. Что показал осмотр, чего не было в постановке

- Комплекты ЦР ссылаются друг на друга **напрямую относительными ссылками**, тысячами:
  `payment → shared` 1 412, `payment → registration` 317, `ascr-transport → registration` 428,
  `shared → payment` 311. Карточек `CALL-INT` внутри домена — 0. То есть домен в ЦР ведётся как
  один большой комплект с пятью реестрами, а не как пять сервисов, связанных контрактами.
- Базовые контракты внешних АС домена (ПЦР-Коннект, пакеты АС ЦР, криптомодуль) ведутся внутри
  `shared/srs/integrations/` (`EXTINT-KM-*`), а не в `docs-external-contracts`: «потому что
  ПлЦР использует только этот домен».
- Стандарт уже допускает доменный docs-репо (`repo-topology` §5: один владелец; `<service-id>/`
  — единица выноса и пространство ID; относительные ссылки на соседа по репо допустимы) и
  доменный `src-<domain-slug>` с профилем на сервис (`conventions` §1.1). Чего в стандарте и
  каноне нет: рамки домена (корневые документы), правила общего сервиса, схемы ID с кодом
  сервиса, разметки «сервис → часть» в профиле, поведения прибора на корне домена.
- Глоссарий ЦР: корневой `glossary.md` (`GLO-001`) — канон терминов домена; в комплектах
  сервисов глоссария нет вовсе (31 ссылка `../glossary.md`). README домена и README `shared`
  противоречат друг другу о том, нужен ли указатель в комплекте.

## 0а. Развилка 0 — что такое сервисы домена физически (вопрос разработке ЦР)

Поставлена владельцем 2026-10-09 при обсуждении развилки 3: может выясниться, что сервисы ЦР
разделяют одну кодовую базу. От ответа зависит, домен ли ЦР вообще.

| Факт о кодовой базе | Что это по канону | Прямые ссылки между комплектами | Уровень «домен» |
|---|---|---|---|
| **Раздельные деплоируемые сервисы** (у каждого свой `ms-<service-id>`; план ЦР берёт `service-id` из `team-configs` как «repo-slug без `ECO_BE/ms-`», что указывает на этот случай) | сервисы Экосистемы | вызов — карточка `CALL-INT`: цель `INTC` при сетевом вызове, `LIBC` там, где потребитель реально линкует код владельца (например, UI-оболочка из `shared`); прямая ссылка из тела документа в чужой комплект — долг | настоящий: уровень над сервисами, развилки 1–4 нужны целиком |
| **Одна кодовая база** (один деплой, модули) | один сервис с частями — случай «Корпоративных карт»; стандарт §3.1 запрещает вложенность частей и раскладывает «сервис → сервисы → подсервисы» в плоский список частей с групповым префиксом | законны, как между частями одного комплекта | домена нет: «ЦР» — сервис, `digital-ruble-payment` — группа частей `pay-*`; слот сервиса в ID и записи каталога на каждый «сервис» не нужны |

Почему LIBC не заменяет этот ответ. Библиотечный контракт меняет вид контракта (код исполняется в
контуре потребителя вместо сетевого вызова), но не способ ссылки: у владельца — карточка `LIBC`
с таблицей «Потребители», у потребителя — карточка вызова со ссылкой из шапки; ссылок из тел
`FUN`/`SCR`/`PROC` в чужой комплект он не разрешает, функция владельца целью ссылки не бывает.
Применить его ко всем прямым ссылкам ЦР нельзя и по существу: заметная их часть ведёт на
сущности (`ENT`) соседнего сервиса, а у раздельных сервисов чужая сущность — не вызов, у
потребителя либо своя сущность, либо данные приходят через контракт.

Следствие для документа: решение по развилке 3 записывается условно (см. §4); при ответе «одна
кодовая база» развилки 2–4 сворачиваются до правил подсервисов, а трек ЦР становится
«перепроектирование в сервис с группами частей», не «возврат домена под канон».

## 1. Модель

Рекурсия из трёх уровней, каждый опционален и вырождается в предыдущий:

```
домен            корень docs-репо: domain-vision.md, glossary.md, README (таблица сервисов)
└── сервис       <service-id>/ — комплект: service-vision, матрица, brd/, srs/
    └── часть    srs/<часть>/ — подсервис; srs/shared/ — общая часть сервиса
общий сервис     <domain>/shared/ — комплект, потребители которого — сервисы домена
```

Инварианты, которые модель наследует от подсервисов и не нарушает:
комплект — единица выноса и пространство реестров (матрица, OQ, FB); код в ID объявляется
таблицей и проверяется прибором по каталогу; без домена и без частей структура и ID совпадают с
эталоном.

глобальной в домене автоматически).

## 4. Развилка 3 — каталог и адресация

| Вопрос | Рекомендация |
|---|---|
| Записи каталога | одна запись на **каждый** сервис домена, включая `shared`; `repo` = `…/docs-<domain>/-/tree/HEAD/<service-id>` (формат уже допускает, прецедент — `src-common-dictionary` с подкаталогами); код сервиса в каталоге = `service-id` из `team-configs`; поле `domain` (slug домена) — необязательное, для группировки |
| Домен в каталоге | записи самого домена нет: извне адресуются сервисы; домен — свойство записей |
| Ссылки внутри домена | **условно по развилке 0.** Раздельные сервисы: относительные ссылки между комплектами одного репо допустимы (стандарт §5), но только на те же цели, что и снаружи — карточки `INTC`/`LIBC` владельца из шапки карточки вызова, реестры и README; прямые ссылки из тел FUN/SCR/PROC в чужой комплект — долг, как для внешнего сервиса (ЦР этого не соблюдает — тысячи ссылок, развилка 7). Одна кодовая база: домена нет, ссылки между частями одного комплекта законны |
| Вызовы между сервисами домена | карточка `CALL-INT` у потребителя как для любого сервиса Экосистемы; относительная ссылка на `../<service-id>/srs/internal-contract/…` |
| Прибор | сторож каталога: `repo` разных сервисов могут указывать внутрь одного репозитория — норма; сторож ссылок-названий и долгов — без изменений |

| Что | Сейчас | Нужно |

| Реестры OQ/FB | один файл на комплект | без изменений: `open-questions.md` и `feedback.md` в каждом комплекте (ЦР ведёт `open-questions/` по сервисам в src — развилка 5, не здесь) |

## 6. Сценарии жизненного цикла (Д-26)

1. **Новая миграция домена с нуля.** Профиль src с секциями по сервисам и разметкой «ветвь →
   сервис → зона»; план по кускам: рамка домена → `shared` → сервисы по зависимостям; каждый
   сервис — отдельный план и координатор, журнал общий на домен (развилка 6). Гейт — по
   комплектам; accept — один.
2. **Одиночный сервис становится частью домена.** Комплект переносится в `<service-id>/`
   доменного репо; ID получают слот сервиса? — нет: слот сервиса вводится только для
   артефактов, создаваемых после переноса? Это даст смесь. Решение: при включении в домен
   перенумерация со слотом сервиса — отдельное изменение «переименование», как смена кода
   сервиса (документ адресации §4.1), с сообщением потребителям. Либо сервис остаётся без
   слота — допустимо, если корневая таблица помечает его «без слота» (колонка «Слот: нет»).
   Рекомендация: допустить оба, сторож читает колонку.
3. **Вынос сервиса из домена в свой репо.** Каталог: `repo` меняется на новый корень; ID не
   меняются (слот остаётся историческим кодом — сторож допускает слот сервиса при таблице с
   одной строкой «этот сервис»); относительные ссылки на бывших соседей → карточки вызова
   или абсолютные адреса по каталогу (стандарт §5 это уже предписывает).
4. **Потребитель вне домена ссылается на сервис домена.** По каталогу: `repo` сервиса →
   карточка `INTC`/`LIBC`; домен для него невидим — как подсервисы для внешнего потребителя.
5. **Сервис домена потребляет `shared`.** Карточка `CALL-INT` у потребителя, цель —
   `../shared/srs/internal-contract/…` (или `lib-contract`); у `shared` — таблица
   «Потребители». Прямые ссылки из тел документов в `shared` — долг.
6. **Термин домена и термин сервиса.** Термин, нужный двум и более сервисам, — в доменном
   глоссарии; указатель комплекта ссылается на него; термин одного сервиса — в указателе
   комплекта. Перенос термина между уровнями — правка двух файлов, ID терминов нет.
7. **Переход сервиса домена на API First.** Как для любого сервиса (Д-32): адрес контрактов
   по коду сервиса из каталога; домен не участвует.
8. **Возврат ЦР под канон.** Отдельный трек (развилка 7): перенумерация не нужна при варианте
   2.Б; нужны — kebab-case вертикалей (`srs/identify_request` → `srs/identify-request`),
   указатели глоссария в комплектах, перенос `EXTINT` в `docs-external-contracts`, замена
   прямых межкомплектных ссылок на карточки вызова или долги, прохождение гейта. Объём
   большой; делать срезами по сервисам, начиная с `shared`.
