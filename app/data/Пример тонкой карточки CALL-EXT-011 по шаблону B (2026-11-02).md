# CALL-EXT-011. ЕСК. Проверка полномочий пользователя на подпись заявки на выпуск карты [КК_ВК]

**Базовый контракт:** [EXTINT-ESK-003. Проверка полномочий пользователя на подпись документа в АС ЕСК](https://gitlab.gboteam.ru/EAN/docs-external-contracts/-/blob/HEAD/esk/extint-esk-003-signing-authority.md) — внешняя АС ЕСК (ЦФТ ГО)
**Примеры обмена:** [esk/examples/](https://gitlab.gboteam.ru/EAN/docs-external-contracts/-/tree/HEAD/esk/examples)

## Назначение

Подсервис выпуска карт сервиса «Корпоративные карты» через онлайн-адаптер ЕСК вызывает процедуру `Repr_Auth_Check(p_request clob) return clob` АС ЕСК (ЦФТ ГО), чтобы проверить наличие у пользователя клиента полномочий на подпись «[КК_ВК] Заявка на выпуск карты» от имени организации. Владелец вызываемого контракта — АС ЕСК. Направление обмена: запрос XML в CLOB → ЕСК; ответ ← ЕСК сообщением типа ИО `Receipt` в CLOB. Вызов выполняет общая функция сервиса FUN-SYS-10; вариант проверки (имя процесса `ProcessName`) и состав проверяемых полномочий выбираются по условиям заявки. Результат управляет доступностью кнопки «Подписать и отправить».

### Где используется

Данный запрос используется в:

- проверки полномочий пользователя на подпись заявок в [FUN-SYS-10 Функция проверки в ЕСК наличия полномочий пользователя на подпись документа](../../../bc-component/function/system/fun-sys-10-esk-auth-check.md).

Наличие полномочий определяется с помощью Функции проверки в ЕСК наличия полномочий пользователя на подпись документа, вызываемой с параметрами, определяемыми следующим образом (SCR-CL-20, кнопка B-2 «Подписать и отправить», «Видимость»).

## Примечания составителя (в карточку не входят)

1. **Что изменилось против версии 3.** Две карточки (общая часть в bc-component + привязка к заявке в bc-issue) слиты в одну карточку подсервиса: общие параметры (конверт, SessionID, реквизиты организации и пользователя) и зависящие от заявки (вариант 10.1/10.2, наборы полномочий) — в одной таблице правил заполнения; сопоставление входящего сообщения — целиком здесь, без ссылки на «общую часть». Карточка в bc-component не остаётся: CALL-EXT-011 переезжает в `bc-issue/contract-call/external/` с тем же ID (страницы-источники те же, история и долг матрицы не рвутся). Слово «тег» в ячейках заменено на «параметр»; присвоения через «=»; условия «Если/то/иначе» сохранены там, где условие — условие значения (вариант заполнения идентификатора). Атрибуты «Клиент Банка» привязаны к EXT-002 (у EXT-002 в реестре КК этих атрибутов нет — долг матрицы на атрибуты, не правка реестра).
2. **Откуда правила подсервиса.** Для [КК_ВК] они есть на странице самого подсервиса: SCR-CL-20 (2166860206), видимость кнопки «Подписать и отправить», с условием по ENT-007 и парами «полномочие + продукт». Таблица FUN-SYS-10 шага 1 даёт для 10.2 те же значения без пар («PROD_EXEC_WRNT / PROD_AGR_WRNT», «='CORP_CARDS' / ='RKO'»); SCR-CL-20 точнее, взят он, FUN-SYS-10 — как источник условий выбора и колонки «Проверки в ЕСК». Общие параметры — из колонки «Логика заполнения …» страницы-копии метода (2464250512). Строки 10.1 и 10.2 в одной карточке — допустимо: один подсервис, одна функция, одна версия.
3. **Аналоги для bc-status и bc-limits.** [КК_БК]: SCR-CL-17 (2166860586) ссылается на FUN-SYS-10 без параметров, PROC-016 шаг 5 вызывает функцию; значения 10.2 для «[КК_БК] Заявка на изменение статуса карты» есть только в строке 10.2 FUN-SYS-10 («- новое»). [КК_ЛК]: FUN-CL-21 шаг 1 и PROC-007 шаг 5, значения — та же строка 10.2. Карточки CALL-EXT-036 (bc-status) и CALL-EXT-037 (bc-limits) строятся по форме этой карточки с источниками своих подсервисов плюс страница-копия метода и строка 10.2; общие строки таблицы повторяются в них дословно (цена одной карточки на потребителя: изменение общего правила — правка трёх карточек; в API First карточки заменяются ссылкой на контракт и повтор исчезает); у них только вариант 10.2, «Вариант заполнения идентификатора заявителя» и PRESET — «в постановке не задано».
4. **FUN-SYS-10 после переиздания.** Шаг 1: текст шага по срезу, ссылка на карточку вызова подсервиса заявки (CALL-EXT-011 для [КК_ВК], 036 для [КК_БК], 037 для [КК_ЛК]) вместо пометки «(нет целевого артефакта contract-call …)», таблица 10.1/10.2 заменяется этими ссылками и колонкой «Заявки»; колонка «Проверки в ЕСК» остаётся в функции — это поведение ЕСК, описанное в источнике функции, не правило заполнения. Алгоритм вызова и обработки ответа (шаги 2–5) — только в функции. Один дом у факта: пары «полномочие + продукт» живут только в карточках подсервисов.
5. **Что ушло в базовый контракт.** Паспорт поставщика, «Документация», таблицы запроса и ответа с типами и кратностями, «Коды банковских продуктов», коды отказов EIO1–EIO5, «Пример вызова». После !74 базовый EXTINT-ESK-003 — сводка; долг «базовый контракт — сводка» на CALL-EXT-011 восстанавливается в матрице (держатель — карточка в bc-issue).
6. **Развилки для владельца.**
   - **Р-4. Title карточки подсервиса.** По шаблону title = дословное наименование главной страницы-источника; главной взята страница подсервиса SCR-CL-20 (она задаёт параметры и несёт маркер контура), страница-копия метода и FUN-SYS-10 — дополнительные. Прибор примет title ЭФ (равенство title главной). Альтернатива — главная = страница-копия метода «Копия [КК] ЕСК_ОА_…» с одинаковым title у трёх карточек подсервисов и без маркера контура. В примере взят title ЭФ.
   - **Р-5. Класс вызова.** SCR-CL-20 называет метод `/sign/signature/v2/check-authority`: это похоже на REST-метод сервиса Экосистемы (подпись), который сам обращается в ЕСК. Если так, вызов КК — внутренний (CALL-INT → контракт сервиса подписи), а ЕСК вызывает тот сервис. Класс карточки — решение владельца, как по 007–009; до решения карточки остаются CALL-EXT с базовым ESK-003, а наблюдение — вопрос аналитику.
   - **Р-1 из постановки — решена владельцем 02.11 (вариант а):** страница-копия метода общая для нескольких сервисов, их специфика (ветки по чужим `ProcessName`, точки вызова из чужих процессов) не является требованием КК и в карточку не переносится; «ничего не терять» относится к требованиям самого сервиса. В примере: ветки `GPB_ReprRegCert_Auth_Check` и абзац «Обновления сведений» свёрнуты до результата для КК; из «Где используется» сняты процессы [ГЭП], [РЭП] и [БРК_ОБГ] (версия 4 до этого решения переносила их дословно). Скобка «(формируется только для сервиса «Обновление сведений» …)» у `SKIP_CONTROL_DUL` снята по замечанию координатора — та же чужая специфика.
7. **Сторожа прибора.** Освобождение тонкой карточки (28)/(28-доп) по смыслу остаётся; литералы колонки правил источника (`"Active"`, `GPB_…`, `PROD_EXEC_WRNT`, `RKO`, `CORP_CARDS`) теперь обязаны быть в карточках — их сверку вернуть отдельным правилом «литералы колонки правил заполнения требуются у тонкой карточки», в очередь прибора.
