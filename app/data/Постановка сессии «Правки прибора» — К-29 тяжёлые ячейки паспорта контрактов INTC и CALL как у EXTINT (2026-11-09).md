# Постановка сессии «Правки прибора, акцепт и рутина» — К-29: тяжёлая ячейка паспорта карточек контрактов (INTC, CALL) остаётся строкой таблицы, как у базовых контрактов внешних АС (2026-11-09)

От: «Точки расширения эталона». Слово владельца дано 09.11 («Даю слово, ставь после К-17»). Очередь: ПОСЛЕ сдачи К-17 (постановка от 09.11), отдельной веткой.

## Проблема

Решение владельца 2026-11-08 (шаблон `contract-call.md`, строки 127–129): «Ячейки §1 в подразделы ради прибора не выводятся: тяжёлая ячейка остаётся строкой таблицы, ложный ✗ сторожа тяжёлых ячеек разбирается при приёмке». Гейт переноса считает READY только при нуле ✗, поэтому любой контракт с тяжёлой ячейкой паспорта делает гейт красным, и «разобрать при приёмке» на деле означает «вливать с NOT READY». Пример — КК, волна С3: `docs/srs/widgets-rtl/internal-contract/client/intc-015-pin-send.md`, ячейка «Как вызывается» (список ЭФ через `<br>`) дословно в одной строке двухколоночной таблицы → ✗ К-29 «тяжёлая ячейка источника расплющена», единственный блокер MR.

Исключение под это решение в приборе уже есть, но только для базовых контрактов внешних АС: `card_run.py:823` — `passport_rows_ok = (type == "external-integration")`; `card_passport.check_heavy_cells` (строки 105–176): при `passport_rows_ok` расплющивание в строке таблицы из ДВУХ колонок — i-строка, в таблицах из трёх и более колонок — ✗.

## Что сделать

1. `card_run.py` (строка 823): `passport_rows_ok` — истина для типов шапки `external-integration` (как сейчас), `internal-contract` и `contract-call` (тонкие карточки вызова CALL-EXT/INT/MOD). Признак структурный — тип карточки в шапке; ширина таблицы проверяется внутри `check_heavy_cells`, как сейчас. Словарных признаков не вводить.
2. Текст i-строки — как у EXTINT, с указанием типа: «i тяжёлая ячейка паспорта остаётся строкой двухколоночной таблицы (решение 2026-11-08, контур A шаблона contract-call; тип <type>)». Для таблиц из трёх и более колонок (параметры, коды ошибок) — ✗ без изменений.
3. `_meta/tools/README.md`: абзац К-29 — перечислить три типа; таблица «Слои прибора» — слой прежний (ядро/сверка с источником — как сейчас у К-29).
4. Тесты парные: INTC с тяжёлой ячейкой в двухколоночной таблице §1 → i, не ✗; та же ячейка расплющена в таблице §2 (три колонки) → ✗; тип `function` с тем же текстом → ✗ (исключение не расползается); contract-call — как INTC. Тест на НЕсрабатывание: эталон `C:\tmp\tool-golden` побайтно; КК на ветке С3 после вливания (или на `exec/c3-widgets-rtl`) — ✗ INTC-015 → i, других изменений ИТОГО нет; число ушедших ✗ по всем комплектам стенда назвать (если у других сервисов были такие ✗ — они тоже уйдут, это ожидаемо и является целью).
