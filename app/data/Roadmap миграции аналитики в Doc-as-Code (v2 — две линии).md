# Roadmap миграции аналитики в Doc-as-Code

Версия 2: добавлена модель двух линий и единая политика веток Git.
Решаемый изъян v1 — конфликт между воссозданием истории изменений и
вливанием AI-aware аналитики (подробности — в разделе «Почему это работает»).

---

# Модель двух линий (прочитать до этапов)

После миграции в репозитории сервиса живут **две линии времени с разной
природой**:

- **Линия настоящего — ветка `main`.** AI-aware аналитика (каталог `docs/`),
  движется только вперёд. Здесь работают аналитики и AI-агенты, отсюда
  создаются все рабочие ветки.
- **Линия прошлого — ветка `history`.** Реконструкция истории изменений
  требований в их оригинальном составе (каталог `sources/confluence/`):
  срез за срезом, задача за задачей — летопись того, как аналитика менялась
  в Confluence. Пополняется, пока сервис живёт двойным ведением; в прошлое
  не вносят правок — его дописывают.

Каждая линия владеет своими каталогами, поэтому их изменения **не
пересекаются по путям**:

| Каталог | Владелец | Режим |
|---|---|---|
| `sources/raw/` | архив (этап 3) | только чтение — навсегда |
| `sources/confluence/` | линия `history` | меняется только в ветках летописи |
| `docs/` | линия `main` | меняется только в AI-aware ветках |

**Мост между линиями — не git-merge, а преобразование**: скилл берёт срез
задачи из летописи (тег) и оформляет её изменения в AI-aware формате
отдельной веткой от `main`. Git-слияний между линиями не существует.

## Политика веток (правила без исключений)

1. **Рабочие ветки создаются только от `main`.** От веток и тегов летописи
   рабочие ветки не создаются — теги летописи открывают только для чтения
   и сравнения (просмотр среза, diff).
2. **`history` никогда не мержится в `main`; `main` — в `history`.**
3. Ветка летописи изменяет только `sources/confluence/`; AI-aware ветка —
   только `docs/` (и связанные реестры комплекта). Нарушение — стоп-сигнал
   на ревью.
4. **Имена веток разводят линии**: летопись — `src/<JIRA-ID>`, AI-aware —
   `docs/<JIRA-ID>`. У одной задачи Jira законно существуют обе ветки —
   это разные представления одной задачи, а не дубли.
5. Каждый срез летописи помечается тегом **`src/<JIRA-ID>`** (первый —
   `src/PROM`). Тег — точка чтения, не точка роста.
6. **Прослеживаемость**: MR ветки `docs/<JIRA-ID>` ссылается на тег
   `src/<JIRA-ID>`, из которого взята дельта.
7. `sources/confluence/` в `main` заморожен на точке отсчёта (ПРОМ-срез
   момента миграции) и не обновляется: актуальная летопись — это `history`.

Схема:

```
main     ──A──P──●───────────●──────────●──→   docs/ (AI-aware, настоящее)
               \        MR docs/GBO-2     MR docs/GBO-5
                \                ↑ конверсия дельты (скилл), не merge
history          └──С1────С2────С3──→          sources/confluence/ (летопись)
                    │      │
                 src/PROM  src/GBO-2  (теги срезов)

A — архив в sources/raw/;  P — ПРОМ-срез (точка отсчёта)
```

# Этап 1: Выгрузка аналитики из Confluence в markdown формат

**Цель**: выгрузка требований аналитики в markdown формат в привязке к задачам Jira

**Контур**: внутренний (VDI)

**Инструмент**: confluence-tree-exporter
> Видео о том, как установить и использовать: https://disk.yandex.ru/i/4vZvS0dJiukLKw.
> Рекомендуется до просмотра попробовать сразу по инструкции внутри пакета, скорей всего сразу получится.

**DoD**:

- каталог выгруженных требований в виде markdown файлов и связанных файлов (например, картинок) на файловой системе.
- в случае привязки требований к задачам — отсутствие UNKNOWN-#XXXXXX отметок в отчете по цветовой привязке требований.

# Этап 2: Перенос аналитики между контурами

**Цель**: получение файлов с аналитикой в markdown формате на внешнем контуре

**Контур**: внутренний (VDI) + внешний

**Инструмент**: onix_ft

**DoD:**

- каталог требований в markdown формате на файловой системе во внешнем контуре.

# Этап 3: Сохранение аналитики в архив — рождение `main`

**Цель**: сохранение в Git репозиторий сервиса архива аналитики в markdown+
формате (с разметкой привязки к задачам, если требуется) для возможности
восстановления в любое время (точка отсчёта).

**Контур**: внешний

**Инструмент**: Git, GitLab

**Шаги**:

1. Влить в `main` каталог архива: путь `\sources\raw\`.
2. Получить ПРОМ-срез точки отсчёта: скопировать `\sources\raw\` в
   `\sources\confluence\`, выполнить `run-critic.bat reject-all --path .`
   по каталогу `\sources\confluence\`.
3. Влить ПРОМ-срез в `main` (MR), поставить тег `src/PROM`.

**DoD**:

- в `main` лежат `\sources\raw\` (архив как есть) и `\sources\confluence\`
  (ПРОМ-срез точки отсчёта, тег `src/PROM`).

> **Важно:** в `\sources\raw\` должен оказаться каталог с требованиями в
> оригинальном markdown формате. Не сохранять в ZIP или ином формате —
> файлы нужны следующему этапу. `\sources\raw\` с этого момента — только
> чтение, навсегда.

# Этап 4: Восстановление истории изменения аналитики — линия `history`

**Цель:** воссоздание в Git истории изменения требований в их оригинальном
составе. Формальное начало Doc-as-Code фазы: любой срез доступен по тегу.

**Контур**: внешний

**Инструменты:** confluence-tree-exporter бандл, Git, GitLab

**Шаги**:

> Ветка на задачу или на эпик — как принято в команде: эпик рассматривается
> просто как набор задач. Все действия выполняются ТОЛЬКО над каталогом
> `...\sources\confluence\`; каталог `...\sources\raw\` — ТОЛЬКО ЧТЕНИЕ.

1. Создать ветку **`history`** от коммита с тегом `src/PROM`.
2. Для очередной нереализованной задачи:
   1. скопировать архив из `\sources\raw\` в `\sources\confluence\` (да, заново);
   2. добавить Jira ID задачи к накопительному списку «реализованных»
      (GBO-ID1, GBO-ID2, … — список растёт с каждым шагом, это нормально);
   3. принять ВСЕ задачи списка: `run-critic.bat apply <ID> --path .` по
      каждому ID списка;
   4. исключить «хвост» нереализованных: `run-critic.bat reject-all --path .`;
   5. зафиксировать срез в летописи — **по выбранному командой режиму**:
      - *режим без ревью*: коммит прямо в `history` (в коммит вливается
        только diff от предыдущего среза — это и даёт версионность);
      - *режим с MR-ревью*: ветка `src/<JIRA-ID>` от `history`, коммит,
        **MR с target `history`** (не `main`!), мерж;
   6. поставить тег `src/<JIRA-ID>` на коммит среза.
3. Если «хвост» не пуст (`run-critic.bat list --path .`) — повторить шаг 2.
4. Пока идёт двойное ведение (задачи реализуются в Confluence-мире),
   новые выгрузки продолжают летопись теми же шагами — этап 4 не «закрыт»,
   а живёт параллельно этапу 5.

**DoD**:

- каждая нереализованная на ПРОМ задача представлена срезом в `history`
  с тегом `src/<JIRA-ID>` (и веткой `src/<JIRA-ID>` — в режиме MR-ревью);
- ни одна ветка/тег летописи не мержится в `main` (правило 2 политики).

# Этап 5: Миграция аналитики в AI-aware формат — линия `main`

**Цель**: переход на полу/автоматизированное создание и сопровождение
аналитики, при котором AI-агент и человек-аналитик работают совместно.

**Контур**: внешний

**Инструменты**: Cursor / VS Code, Git, скиллы `_meta`

**Шаги**:

1. Пилот по переходу части сервисов на AI-aware формат: конверсия ПРОМ-среза
   (тег `src/PROM`) в `docs/` веткой `docs/<ID-пилота>` от `main`, MR в `main`.
2. Посадка задач: по мере реализации очередной задачи — взять её дельту из
   летописи (diff тега `src/<JIRA-ID>` к предыдущему срезу), преобразовать
   скиллом в AI-aware и оформить веткой **`docs/<JIRA-ID>`** от `main`;
   в MR — ссылка на тег-источник.
   > Темп и объём конверсии определяются выбранным для сервиса вариантом
   > переноса (A — дельта, C — заморозка хвоста, D — послойно по файлам;
   > см. «Варианты переноса аналитики»). **Политика веток одинакова для
   > всех вариантов** — варианты меняют только то, что несут ветки
   > `docs/*` и когда стартует конверсия.
3. Тиражирование принятых подходов, шаблонов и инструментов на все сервисы
   Экосистемы.
4. Переход на этап развития аналитики совместно c AI-агентами.

**DoD:**

- изменения каждой бизнесовой задачи, прошедшей посадку, оформлены в
  AI-aware формате веткой `docs/<JIRA-ID>` и влиты в `main` через MR;
- у каждой такой ветки/MR есть ссылка на тег-источник `src/<JIRA-ID>`;
- подтверждение команды сервиса о готовности сопровождения аналитики в
  выбранном формате.

# Завершение миграции

Когда «хвост» исчерпан (`run-critic.bat list` пуст) и команда подтвердила
переход: летопись останавливается — ветка `history` и теги `src/*` остаются
в репозитории как архив прослеживаемости (не удаляются); новые задачи идут
только по целевому процессу: ветка `docs/<JIRA-ID>` от `main` → commit →
MR → согласование → мерж. Вопрос исключения `sources/` из переносимого
комплекта (конвенции `_meta`) решается на этом шаге отдельно.

# Почему это работает (для тех, кто хочет углубиться)

В v2 (текущий документ) конфликт невозможен по построению:

- линии не мержатся друг в друга (правило 2) — затереть чужое мержем нельзя;
- линии владеют разными каталогами (правило 3) — даже ошибочный мерж не
  даст пересечения путей;
- рабочие ветки растут только от `main` (правило 1) — «уехать в прошлое»
  можно только сознательно и только для чтения;
- двойники веток различимы именем (`src/…` против `docs/…`) — правило 4;
- связь линий сохранена не git-историей, а прослеживаемостью: тег среза ↔
  MR конверсии (правила 5–6).
