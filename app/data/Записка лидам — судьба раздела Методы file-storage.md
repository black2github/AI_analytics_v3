## Вопрос 1 (главный): источник API-слоя — код или Confluence

Канон однозначен: «SRS адаптируется только из Confluence… Код — источник
авто-выгруженных API-контрактов для `docs/api`» (conventions §1, §5.1).
Для API это оправданная асимметрия: контракт и есть код интерфейса.
Страницы методов Confluence при этом — сверочный материал (расхождение
выгрузки и постановки — открытый вопрос команде), а не источник переноса.

Загвоздка пилота: автовыгрузка контрактов из кода в изолированном контуре
не выполнялась (клонов кода в контуре прогонов нет; zip не используется
по правилам §1).

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| (а) канонический | Автовыгрузка OpenAPI из кода + сверка с Confluence-страницами; расхождения — в open-questions | Один источник истины; соответствует канону | Требует штатного процесса с клонами кода; в пилотном контуре пока невыполнимо |
| (б) reverse из Confluence | Перенос контрактной части страниц в `docs/api` руками/скиллом | Выполнимо сейчас | Нарушает §1; создаёт ТРЕТИЙ источник истины (код ≠ Confluence ≠ docs/api); при автовыгрузке позже — двойная работа и конфликт |
| (в) отложить | Категория 2 ждёт штатного процесса; страницы остаются в sources как сверочный материал | Не создаёт долгов и конфликтов | ~40 страниц постановки надолго выпадают из контура аналитики — конфликт с принципом «сохранение смысла — высший приоритет» |
| (г) постановочный уровень контрактов | Новый каталог `docs/srs/internal-contracts/` в комплекте сервиса-владельца: карточки СОБСТВЕННЫХ методов сервиса по тем же принципам, что базовые контракты внешних АС (паспорт дословно, канонические таблицы параметров, коды, примеры, механические проверки) | Информация в контуре немедленно; переиспользуются шаблон/скилл/гейты контрактов; закрываются висящие долги комплекта (PRC-005/PRC-006-OQ-019, OQ-006); «SRS только из Confluence» соблюдено — docs/api не затрагивается | Требует дополнений канона (тип, префикс ID, §5.1); при запуске автовыгрузки нужна явная граница с docs/api (ниже) |

**Рекомендация (обновлена): (г) сейчас + (а) как целевой процесс
реализационного уровня; (б) не открывать.** Граница двух уровней — та же,
что уже принята для модели данных: `internal-contracts` — ПОСТАНОВКА
(что метод должен делать; семантика параметров дословно из требований;
зона аналитика), `docs/api` — РЕАЛИЗАЦИЯ (YAML из кода; зона разработки);
расхождение уровней — открытый вопрос команде, при переходе на api-first
карточки — источник description-полей контракта, не конкурент YAML.

### Семантика internal/external — относительно границы ЭКОСИСТЕМЫ

Ось разделения — граница Экосистемы ДБО, не отдельного сервиса: все
микросервисы ДБО — внутренний контур; «внешние» системы — за пределами
Экосистемы (смежные АС банка и внешний мир: MFlash, EdgeCenter, ЕСК,
КНОСИС…). Вторая ось — роль (владелец интерфейса / потребитель):

| | Контракт (у владельца) | Вызов (у потребителя) |
|---|---|---|
| Внутри Экосистемы | `docs/srs/internal-contracts/` комплекта сервиса-владельца | Точка вызова (процесс/ЭФ/функция — ссылкой на карточку владельца); стиль отдельных карточек — в проработке |
| Вне Экосистемы | репозиторий `docs-external-contracts` | `docs/srs/contract-calls/` потребителя |

Фактическое наполнение `docs-external-contracts` (mflash, esk, knosis,
cdn, f1, bsk, sbp, tessa) оси соответствует полностью; определение EXTINT
в конвенциях («обмен с внешней АС») получает явную границу. Модель
масштабируется на межсервисные вызовы внутри Экосистемы (сервис A зовёт
метод сервиса B: контракт — у владельца B, потребление — у A) — это же
предвосхищено глоссарием («карточка потребления межсервисных контрактов»).

## В проработку после решения по (г)

- **Стили описания внутриэкосистемных вызовов**: базовое правило —
  вызов описывается в точке вызова (ссылкой на карточку владельца);
  отдельная карточка вызова — только когда один вызов используется из
  многих точек с одинаковыми правилами. Критерий доработать.
- **Место PLT в матрице**: платформенные функции — по сути частный
  случай «потребление внутриэкосистемного интерфейса»; исторически
  отдельный механизм — соотнести, не ломая выпущенного.
- **Глоссарий**: термины «Экосистема» и «ЭКО» используются по всему
  канону и нигде не определены — определить (на них теперь держится
  классификационная ось).
- Дополнения канона под (г): тип артефакта `internal-contract`,
  префикс ID (предложение — `INTC-NNN`), подраздел conventions §5.1,
  указатель в Gate скилла интеграций.

## Вопрос 2: расширять ли охват функций на методы категории 4

Методы, не имеющие страниц в разделе «Функции» источника (генерация
токенов, копирование, привязка, удаление, дайджест, потоковая выгрузка),
поведением в SRS не описаны — на них ссылаются процессы (пример —
открытый вопрос OQ-006 комплекта). Варианты: (а) создать системные
функции FUN-SYS по этим методам (полнота SRS, но охват растёт на
~15–20 артефактов); (б) считать их деталями реализации API-слоя и в SRS
не описывать (тогда ссылки процессов остаются текстом). Нужен критерий
полноты SRS — предлагаю: функция создаётся, если на метод ссылается
процесс или другой артефакт SRS; чисто технические методы без ссылок —
не описываются. Вариант (г) вопрос частично снимает: каждый метод в
любом случае получает карточку контракта в `internal-contracts`
(информация не теряется), а функция — только там, где есть поведение,
на которое ссылается SRS.
