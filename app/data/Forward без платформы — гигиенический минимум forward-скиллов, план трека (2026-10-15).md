## 0. Контекст, от которого считается план

- Платформа AI Factory — один из вариантов будущего; основная часть сервисов после миграции
  развивается **без неё**: человек правит руками по правилам либо AI-агент правит по инициативе
  человека.
- Режим ближайших дней — эволюционный: аналитик ставит ограниченную задачу и отвечает за ЧТО и
  ЗАЧЕМ; агент — за КАК (формат, правила, выдача ID, связи в матрице).
- После каждой итерации комплект проверяется гейтом `transfer_gate.py` по критериям DoR, чтобы
  сервис в любой момент был подключаем к платформе без структурных переделок.
- Цель — приступить «уже завтра»; выдавать командам полезный результат каждой правкой.

Что уже есть в каноне: режим B forward в `create-artifact` (6 строк: шаблон, вход, вопросы до
проектирования, далее шаги reverse); «Повторный заход» (документ актуализируется, ID сохраняются,
удаление — только по заданию); forward-разделы у 9 скиллов по 4–12 строк; «Проектирование с
нуля» у 6 шаблонов из ~20; прибор: внутренние сторожа без источника, реестр ID, фантомные ID,
долги, структура; гейт переноса с режимом репозитория документации. Обкатанных forward-прогонов
нет (кроме реестра `PLT` из долгов).

## 1. Что такое «источник факта» в forward — пояснение на примере

Постановка аналитика: «На форму “Заявка на присоединение” (`SCR-AGR-CL-02`) добавить поле “Дата
рождения представителя”, обязательное, формат ДД.ММ.ГГГГ, после ввода попадает в атрибут
`ENT-AGR-001.representativeBirthDate`».

Чтобы исполнить это по правилам канона, агенту нужно записать больше фактов, чем названо:

| Факт | Назван в постановке? | Откуда агент его возьмёт |
|---|---|---|
| имя поля, обязательность, формат, целевой атрибут | да | постановка |
| есть ли атрибут `representativeBirthDate` в `ENT-AGR-001`; если нет — его тип, обязательность, описание | нет | комплект (карточка модели данных); если атрибута нет — **вопрос** или **новый факт по постановке** |
| контроль формата и обязательности (`CTL-…`), текст сообщения об ошибке | нет | существующие контроли похожих полей (образец) — но текст сообщения — **новый факт** |
| какая функция сохраняет форму (`FUN-AGR-CL-03`?) и надо ли дописать шаг «сохранить дату рождения» | нет | комплект (матрица, карточка функции) |
| попадает ли поле в печатную форму заявления, уведомление, статусную модель | нет | комплект (ссылки на форму) |
| ID нового правила поля `FLD-N`, события, контроля; строки матрицы | нет | правило выдачи ID по реестру |

В reverse каждый такой факт берётся со страницы выгрузки, и прибор дословности проверяет, что
агент ничего не дорисовал. У платформы каждый факт помечен адресом (`E-NN`, SHA) или заведён как
вопрос. В forward без платформы для фактов второй и третьей строк (тип атрибута, текст
сообщения, шаг функции) **правила нет**: агент либо выдумает правдоподобное значение, либо
остановится. Первое опасно тем, что через месяц никто не отличит в карточке решение аналитика от
догадки агента; второе — тем, что агент будет останавливаться на каждом шаге.

Ответ, который предлагается: **источник forward-захода — постановка задачи как файл в
репозитории плюс существующий комплект**; каждый новый или изменённый факт в карточках агент
относит к одному из трёх происхождений — «из постановки», «из комплекта (ID карточки)», «вопрос
аналитику»; четвёртого («сам решил») нет. Отчёт дельты в конце захода перечисляет изменённые
карточки и новые факты с происхождением, и аналитик акцептует именно его, а не читает весь
комплект. Это та же асимметрия ошибок, что в reverse: лишний вопрос дешевле молчаливой догадки.

## 2. Предложение: один протокол изменения, тонкие типовые надстройки, прибор дельты

Не писать 20 forward-скиллов «проектирования с нуля». Задачи ближайших недель — изменения
существующего комплекта, не проектирование сервиса с нуля. Поэтому ядро — **один протокол
«изменение по постановке»** (режим C в `create-artifact`), типовые скиллы получают короткие
надстройки «что ещё затронуто и что спросить», а детерминированную часть (ID, матрица, дельта,
гейт) берёт прибор.

Протокол «изменение по постановке» (шаги агента):

1. Принять постановку: аналитик пишет её в промпт; агент сохраняет дословно в
   `tasks/<JIRA-ID>.md` (ID задачи, ЧТО и ЗАЧЕМ, затронутые карточки по мнению аналитика,
   ограничения, что не менять) строками `T-<JIRA-ID>-NN`, своё понимание — отдельным блоком,
   показывает и ждёт подтверждения; уточнения в ходе захода дописываются следующими строками.
2. Найти затронутые карточки по матрице и ссылкам (карта зависимостей типа: форма → атрибут →
   контроль → функция → печатная форма, уведомление, статусная модель).
3. Собрать список вопросов по пробелам постановки **до правок** (перечень обязательных вопросов —
   из надстройки типа); при пустом списке — продолжать, иначе остановиться и отдать вопросы.
4. Внести правки по текущим шаблонам типов; новые ID — по реестру матрицы; `title`,
   `confluence_page_ids` новым карточкам не выдумывать (forward-карточка без страницы-источника
   несёт `title` от аналитика и пустой `confluence_page_ids`).
5. Обновить матрицу (реестр ID, связи, долги); пробел, который аналитик решил оставить, — строка
   долга второго формата с видом и ответственным.
6. Самопроверка: `selfcheck` (внутренние сторожа), `link_debts`, `structural_facts` при правке
   README, гейт переноса в конце.
7. Отчёт дельты: изменённые файлы, новые ID, строки матрицы, факты с происхождением, вопросы. Его
   собирает прибор (`delta_report.py`), агент дополняет происхождением фактов.
8. Коммит и MR — человек; акцепт — ревью отчёта дельты и MR.

## 4. Плюсы, минусы, альтернативы

**Плюсы предложения.** Один протокол покрывает все типы с первого дня; детерминированное — в
приборе (принцип 5 итерации 2); акцепт по дельте, а не по комплекту (принцип 7); три
происхождения факта переносят асимметрию ошибок reverse в forward; гейт в конце захода держит
подключаемость к платформе без отдельной работы; «Проектирование с нуля» не пишется впустую.

**Минусы.** Происхождение факта прибор не проверяет — только перечисляет; качество отчёта
зависит от агента и ревью. Постановка как файл в репозитории — новая привычка для аналитиков
(после Confluence). Надстройки типов тонкие: сложные задачи (новый процесс, новая интеграция)
первое время идут с повышенным вниманием, как «не обкатанные» режимы reverse.

**Альтернатива A — полные forward-разделы во всех 20 скиллах и шаблонах сначала.** Полнее, но
3–4 недели до первого полезного результата и большая часть текста не будет востребована в первых
спринтах. Отклоняется по сроку.

**Альтернатива B — ждать платформу и её навыки.** Противоречит контексту (платформа — один из
вариантов, основная часть сервисов идёт без неё). Отклоняется.

**Альтернатива C — только прибор дельты и гейт, без протокола в скиллах.** Дёшево, но правила
правок остаются в голове аналитика — ровно то, от чего нужно уйти. Отклоняется как недостаточная.

## 5. Ответы владельца 15.10 и что они меняют

1. **Комплект развивается в целевом `docs-<service-id>`** (комплект в корне, журналов миграции
   нет). Следствия: вопросы forward живут в файле постановки до ответа; пробелы, оставленные
   аналитиком, — строки долга вида «открытый вопрос» в матрице (дом по Д-41); гейт в конце захода —
   в режиме репозитория документации.
2. **Постановка — вводом в промпт, агент сохраняет её в файл, аналитик подтверждает** (принято как
   основной способ; решение владельца на вопрос о замене ручного создания файла). Условия: текст
   аналитика сохраняется дословно, понимание агента — отдельным помеченным блоком; уточнения
   дописываются строками с идентификаторами `T-<JIRA-ID>-NN`, отчёт дельты ссылается на них; файл
   `tasks/<JIRA-ID>.md` едет в тот же MR, что и правки. Порядок: записать → показать →
   подтверждение → правки. Проверить в С4: каталог `tasks/` и тип `task` (объявлен в таблице типов
   README) проходят валидатор платформы и гейт; запасной вариант — постановка только в описании
   MR (слабее: прибор не ссылается на строки).
3. **Порядок С3**: поле на экранной форме → контроль → шаг функции → шаг процесса → вызов внешней
   системы (`contract-call`).
4. **Инструмент команд — VS Code**: скиллы из `.claude/skills` канона (расширение Claude Code);
   пример для команд — в этом виде.
5. **Акцепт**: отчёт дельты — в описании MR, акцепт = approve.

Исходные вопросы (для истории):

1. **Где живёт комплект, который развивают команды**: в рабочем `src-<service-id>` (комплект в
   `docs/`, рядом журналы миграции) или в целевом `docs-<service-id>` (комплект в корне, журналов
   нет)? От этого зависит, где лежат постановки и вопросы forward и в каком режиме гейт.
2. **Где фиксируется постановка задачи**: файл в репозитории (предлагаю `tasks/<JIRA-ID>.md`),
   описание MR, или Jira недоступна и источник — только текст аналитика агенту? Для трёх
   происхождений нужен файл: на него ссылается отчёт дельты и коммит.
3. **Три-пять самых частых задач первых спринтов** по типам (поле на форме, атрибут, контроль, шаг
   функции, статус, уведомление, вызов внешней системы) — задаёт порядок С3.
4. **Инструмент команд**: Cursor (`.cursor/commands`) или Claude Code (`.claude/skills`) — оба
   собраны из канона, но пример для команд должен быть в их инструменте.
5. **Акцепт**: ревью MR человеком достаточно, или нужен отдельный шаг «аналитик подтвердил отчёт
   дельты» (как HITL в `ai-sdlc.md`)? Предлагаю: отчёт дельты — в описании MR, акцепт = approve.
