# AI Factory — чек-лист DoR документации сервиса v1.1: что остаётся актуальным после сравнения канонов

Дата: 2026-10-08. Разбирается `C:\doc-as-code\ai-factory\checklist-v1.1.md` (v1.1 от 01.10.2026: 20
основных критериев, 13 дополнительных, 11 критериев готовности подключения, протокол) вместе с
`checking-rules-v1.1.md` (разделы 9–11). Контекст — итерации 1–3 разбора AI Factory: канон
платформы, её валидатор и ревьюеры, гейт переноса src → docs, решение «миграция аналитику не лечит».

## 0. Что чек-лист проверяет на самом деле

Чек-лист объединяет три разных гейта, у которых разные предметы, исполнители и моменты:

| Гейт | Критерии | Предмет | Кто может проверить | Когда |
|---|---|---|---|---|
| A. Качество аналитики | CORE-01…20, API/INT/UI/DOC/NTF/NFR/FMT | содержание требований: полнота сценариев, однозначность, исполнители, состояния, доступ | человек-эксперт или AI-ревьюер по смыслу; механически — не проверяется | до миграции (это свойство источника) либо после — как список доработок |
| B. Готовность переноса | SDLC-01, 04, 05, 07, 08, 09 (+ FMT-01, часть SDLC-02/03) | форма комплекта: структура, ID, матрица, README, конфигурационные файлы, валидность структурных файлов | детерминированно: прибор миграции + валидатор платформы | гейт переноса src → docs |
| C. Подключение к платформе | SDLC-02, 03, 06, 10, 11 | процесс и решения владельца: контракты и справочники в Git с двусторонними ссылками, решение о BRD, отчёты о качестве и сверке с кодом | владелец документации, рабочая группа | перед первой задачей платформы |

Смешение этих трёх гейтов — главный источник избыточности и один источник противоречий. Ниже — что
из каждого остаётся, что механизируется, что конфликтует с решениями по канонам.

Принцип разбора: критерий **избыточен для ручной проверки**, если он детерминированно проверяется
существующим или согласованным сторожем — тогда в чек-листе остаётся ссылка на сторож, а не пункт
для глаз. Критерий **остаётся ручным**, если проверяет смысл. Критерий **не относится к миграции**,
если оценивает содержание источника, которое миграция по решению не меняет.

## 1. Основной блок CORE-01…20 — качество аналитики

Все двадцать критериев оценивают содержание, которое миграция переносит дословно и по решению не
исправляет. Следствие: **результат блока CORE для мигрированного комплекта равен результату для его
источника в Confluence**. Проверять его после миграции можно, но исправлять найденное — не задача
миграции; это первая очередь задач платформы по сервису или доработка в Confluence до переезда.

| ID | Суть | Как проверяется сегодня | Что меняется |
|---|---|---|---|
| CORE-01, 02 | назначение сервиса и перечень возможностей | `service-vision.md` (`VIS-001`): назначение, акторы, способности, границы — у обеих сторон обязателен (платформа: новый сервис без него — блокер) | остаётся; механически проверяется только наличие документа и разделов, содержание — человек |
| CORE-03, 17 | исполнитель шага; кому разрешено действие | шаблоны функций и процессов: контур в заголовке всегда, роль и привилегия кодом из `rbac.md`; платформа — то же (чек-листы навыков) | остаётся; частично механизируется сторожем «функция без строки доступности» — у обеих сторон его пока нет |
| CORE-04 | ответственный за документацию | `CODEOWNERS` (SDLC-07), README комплекта | дублирует SDLC-07; оставить один из двух |
| CORE-05 | версия документации и связь с состоянием сервиса | git: акцепт = MR в защищённую ветку; срез канона в профиле; `confluence_page_ids` | выполняется устройством Doc-as-Code по построению — для Git-комплекта проверять нечего, кроме наличия тега/коммита в протоколе |
| CORE-06 | навигация от стартового документа | README комплекта и разделов (`<ПРЕФИКС>-000`), матрица | дублирует SDLC-08; механизируется (битые ссылки — валидатор платформы `E_LOCAL_LINK_MISSING`, у прибора миграции — долги ссылок) |
| CORE-07 | текущее описание отделено от старого и черновиков | дважды по построению: при выгрузке утверждённый срез отделяется от неутверждённых правок (CriticMarkup → reject-all, в `sources/confluence` только действующее; статус требования в комплект не переносится); в комплекте статус = влитость в `master`, черновиков нет по правилу (сторож чистовика), `sources/raw` не источник | для мигрированного комплекта выполнен по построению; ручной проверке подлежит только источник, если в Confluence действующее и неутверждённое смешаны без разметки |
| CORE-08 | правила читаются текстом, не картинкой | reverse переносит текст; сторож «источник без таблицы шагов — шаги не синтезировать» | остаётся как свойство источника; у миграции — долг, не исправление |
| CORE-09 | доступны все материалы, включая внешние | долги ссылок прибора; платформа — `E_LOCAL_LINK_*`, внешние http не проверяются | механизировано для внутренних ссылок; внешние — человек |
| CORE-10 | термины с одним значением | глоссарий `GLO-001`; сторож ссылок-названий сущностей | содержание — человек; наличие — механически |
| CORE-11, 14, 15 | проверяемость требований, однозначность правил, допустимые значения полей | платформа: `requirements-quality-review` (Вигерс A1–A9, неопределённые слова B) — AI-ревьюер; прибор миграции — нотация условий (`Если/то/иначе`), UI-типы из словаря, dotted-нотация | смысл — ревьюер платформы уже делает это для дельты; для всего комплекта — отдельный запуск того же навыка. Ручная проверка избыточна при наличии его отчёта |
| CORE-12, 13 | полный успешный сценарий; поведение при сбоях | платформа: `artifact-consistency` п. 14(а) — отказовые ветки для каждого действия и интеграции; п. 15 — вертикаль потока | то же: AI-ревьюер по дельте; для комплекта — полная проверка срезами (`slices.md`). Ручная проверка остаётся только как выборочная контрольная |
| CORE-16 | состояния и переходы | статусная модель `SM-000` + справочник статусов; `artifact-consistency` п. 14(б) — каждый статус достижим и покидаем | механизируемо частично (наличие модели, коды статусов из справочника — прибор миграции уже требует коды) |
| CORE-18 | источник и ответственный за правило | reverse: `confluence_page_ids` и дословность — источник у каждого факта; forward платформы: план + evidence `E-NN` | для мигрированного комплекта выполнен по построению (это и есть наш гейт); для forward — устройством платформы |
| CORE-19 | непротиворечивость описаний одного действия | `artifact-consistency` п. 4, 11, 15 | AI-ревьюер платформы; ручная — выборочно |
| CORE-20 | нет открытого вопроса, без ответа на который нельзя определить поведение | гейт переноса: `open-questions.md` закрыт; у платформы — строгий HITL: `DONE` только без открытых OQ | **совпадает с гейтом переноса**; остаётся как формулировка цели гейта |

Итог по блоку: как список свойств хорошей аналитики — верен и полезен; как **гейт миграции** —
неприменим, потому что миграция ничего из этого не меняет. Из двадцати критериев четыре выполняются
устройством Doc-as-Code по построению (05, 07 для комплекта, 18, 20 через гейт переноса), два
дублируют блок SDLC (04, 06), семь покрываются навыками платформы по дельте (11–16, 19) и
нуждаются в ручной проверке только как выборочный контроль, остальные — содержание, которое
проверяет человек.

До него критерий даёт только «Не проверено». Переформулировать: соответствие канону платформы и паспорту ЭКО — валидатором платформы (структура) и ревьюером (навыки) |

| SDLC-08 | README с навигацией в корне и каталогах | README комплекта (`create-docs-readme`), реестры разделов; битые ссылки — валидатор платформы | актуален; добавить к нему требование платформы: раздел «Условные обозначения» с таблицами контуров и подсервисов — его читают агенты платформы (P-19) |
| SDLC-09 | у каждой страницы код и название, включена в матрицу | frontmatter `id|partOf`, `type`, `service` (у миграции ещё `title`, `confluence_page_ids`); реестр ID матрицы; прибор миграции и валидатор платформы | **механизирован** обеими сторонами |
| SDLC-10 | отчёт о проверке качества на зафиксированной версии; нарушения исправлены | отчёт по блокам CORE и дополнительным | **ключевой вопрос**: требует READY по качеству до подключения — то есть исправления аналитики до переезда. Противоречит решению «миграция аналитику не лечит» и приоритету скорости переезда. Предложение — разделить: отчёт о качестве обязателен (как список доработок), READY по качеству — не условие подключения, а первая задача платформы |
| SDLC-11 | документация сопоставлена с кодом; расхождения разобраны владельцем | **conventions.md §1: «SRS адаптируется только из Confluence без сверки с кодом»**; платформа: «код — уточнение, не источник требований; расхождение кода с SDD или контрактом — критичный OQ» | **конфликт с действующим стандартом**. Сверка с кодом — отдельная работа с собственным владельцем решений; как условие подключения она сделает переезд невозможным для сервисов с расхождениями. Предложение — вынести из DoR подключения в задачи платформы (ревьюер SA уже требует OQ при расхождении) |

## 4. Выводы

1. **Чек-лист остаётся верным как перечень свойств хорошей документации** — ни один критерий не
   стал ложным. Но как гейт он проверяет три разных вещи одним списком, и для миграции применима
   только средняя часть.
2. **Избыточны для ручной проверки** (есть или согласован детерминированный сторож; сторож
   обнаруживает, а не исправляет — найденное в источнике остаётся долгом аналитики): FMT-01,
   SDLC-04, SDLC-09, CORE-05/06/09 (внутренние ссылки), CORE-18 и 20 для мигрированного комплекта,
   SDLC-07 после добавления сторожа. В чек-листе их место — ссылка на сторож и его отчёт.
3. **Покрываются навыками платформы по дельте**: CORE-11…16, 19 (`requirements-quality-review`,
   `artifact-consistency`). Для первичной проверки всего комплекта — те же навыки в режиме полной
   проверки срезами. Ручная проверка — выборочный контроль, не основной инструмент.
4. **Три конфликта с действующими решениями**, их должна снять рабочая группа:
   - SDLC-06 (BRD до подключения) против канона платформы (существующий комплект без `brd/` —
     норма) и против роадмапа (BRD — после миграции);
   - SDLC-10 (READY по качеству как условие подключения) против «миграция аналитику не лечит» и
     приоритета скорости переезда;
   - SDLC-11 (сверка с кодом) против conventions §1 и против позиции платформы «код — уточнение».
5. **Один критерий неопределён до решения об одном доме норм**: SDLC-01 («действующий эталон и
   скиллы») — пока эталона два, он даёт только «Не проверено».
6. **Два критерия ждут решений канона**: SDLC-03 (справочники: владелец «ничьих», обратный индекс
   `EXT`) и SDLC-08 в части формы README («Условные обозначения» платформы).
7. **Чего в чек-листе нет, а гейт переноса требует** (из канона и валидатора платформы): комплект
   в корне репозитория без обёртки `docs/`; служебные файлы миграции не перенесены; закрытый набор
   `type` либо объявленные отличия в README; раздел матрицы «Покрытие: API ↔ SRS» (даже пустой);
   отсутствие `api/`; ссылки между репозиториями через `HEAD` (внутри docs-контура — согласовано
   обеими сторонами).

| Гейт | Состав | Исполнитель | Результат |
|---|---|---|---|
| **Качество источника** (до миграции или как список доработок) | CORE-01…20, API/INT/UI/DOC/NTF/NFR без изменений формулировок; результат — отчёт и перечень дефектов, не условие переезда | аналитик сервиса; выборочно — ревьюер; для дельты после подключения — навыки платформы | перечень дефектов аналитики → первая очередь задач платформы по сервису |
| **Готовность переноса** (механический гейт src → docs) | открытых вопросов нет (CORE-20); структура: SDLC-04, 05 (наличие), 07, 08, 09; FMT-01; корень без `docs/`; служебные файлы отфильтрованы; `type` в наборе или отличия объявлены в README; «Покрытие: API ↔ SRS» есть; `api/` нет; валидатор платформы — ноль ошибок | прибор миграции + валидатор платформы, одной командой | READY / NOT READY с дословными строками сторожей |
| **Подключение** (решения владельца) | SDLC-01 (после решения об одном доме норм), 02, 03, 06 (решение о BRD как запись, а не наличие BRD), 10 (отчёт как список, не как READY), 11 (вынесено в задачи платформы либо оставлено отдельным решением) | владелец документации, рабочая группа | записанные решения в README комплекта или протоколе |

Протокол самопроверки чек-листа при этом сохраняется; меняется только то, какие строки заполняет
человек, а какие — прилагаются отчётом прибора.

## 6. Что требует решений рабочей группы

1. SDLC-06: BRD — условие подключения или первая задача BA на платформе (рекомендуется второе: у
   платформы есть навыки деривации, у миграции — нет такой задачи).
2. SDLC-10: READY по качеству — условие подключения или перечень доработок (рекомендуется второе).
3. SDLC-11: сверка с кодом — часть DoR или отдельная работа после подключения (рекомендуется
   второе; стандарт §1 менять не предлагается).
4. SDLC-01: формулировка после решения об одном доме норм.
5. SDLC-03: решения канона по справочникам.
6. Согласие на разделение чек-листа на три гейта (раздел 5) и на перенос механизированных пунктов в
   отчёт прибора.

Правки чек-листа и прибора по этому документу не начинаются до решений.
