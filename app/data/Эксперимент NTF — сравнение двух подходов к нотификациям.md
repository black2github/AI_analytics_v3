## Сравнительная таблица (критерии — постановка аналитика)

| Критерий | A: специализация FUN-SYS | B: тип notification |
|---|---|---|
| **Однозначность** | Маршрут через общий поток create-artifact (специализированного скилла нет) — агент дошёл, но конфликт «шаблон требует цитаты ↔ сторож значений требует ячейки» разрешил сам: продублировал тексты (таблица источника целиком + H3-цитаты). Недетерминированная развилка | Прямой маршрут диспетчер → create-notification; структура закреплена сторожем (ключи каналов, шаблоны M-NN, порядок E). Дублей нет. Пробел: шаблон не зафиксировал ширину E-номера (агент выдал E1/E2 вместо E01) |
| **Гибкость** | Глубокие правила клиентских нотификаций: условия отправки по каналам (подтверждение контакта, согласие), параметры платформенной функции Журнала нотификаций, «Другие статусы» как адрес по умолчанию, замена legacy-кодов. На компактном банковском источнике всё это дало шум: шаги «Не выполняется» ×2, раздел каналов размазан на 3 фрагмента | Форма «реестр каналов + карточки событий + шаблоны M-NN» ложится и на компактный (locks), и на широкий ([КК_ВК], rowspan-группы) источник без пустых секций. Но контентных правил клиентских нотификаций (условия отправки, параметры платформенной функции) НЕТ — на богатом источнике перенесёт дословно без A-шной интерпретации |
| **Восприятие человеком** | Тексты сообщений цитатами `>` — читаются хорошо; НО каждый текст существует дважды (таблица + цитаты) — два места правки, дифф двойной | Компактно, значение в одном месте; НО тексты сообщений — `<br>`-простыни одной строкой (скопированы из ячейки источника): шаблон не дал правила разворачивания. Класс С-27 «рендеримость», дефект шаблона B |
| **Восприятие LLM** | Свободная композиция function-разделов требует интерпретации; слабая LLM тащит навязанную структуру даже впустую и страхуется дублированием под гейт | Механические ключи (заголовок = ключ), реестры ↔ карточки, адресуемые события — проверяемо сторожем; слабая LLM прошла без итераций по структуре |
| **Архитектурная целостность** | Не плодит тип: нотификация живёт в существующей типологии FUN, конвенции не трогаются. Натяжки: «функция» без алгоритма и вызова (по сути реестр правил); трассировка только артефакт-уровня; «один документ на сервис» на [КК_ВК]-масштабе раздувается | Честный тип для содержимого-реестра; события NTF-NN.ENN дают точную двустороннюю трассировку (матрица B: 4 связи, включая NTF→ENT/SCR). Цена: NTF нужно внести в conventions (ещё НЕ сделано), два комплекта (inquiry, open-add-account) уже на A-форме — разнобой до миграции |

  поощряет); дозакрытие 1.24 — точка внутри текста ссылки (дословно).
- B: ни одного нового OQ — вопросы (critic-адрес, внешние ссылки)
  остались только в сдаче (A завёл OQ-023…025); title README-реестра
  дублирует title карточки; дозакрытие 1.24 — точка сохранена вне
  ссылки.
- Обе формы: правила обработки CriticMarkup в чистовике НЕТ нигде.
  A выбрал critic-ins + примечание + OQ; B сохранил оба адреса с
  разметкой (данные целее, маркер в чистовике). Кандидат на ОБЩЕЕ
  правило канона, независимо от исхода эксперимента.

## Рекомендация эксперта (решение за аналитиком)

Не «победа B», а **слияние: форма B + контентные правила A**.

1. Форма (структура документа) — тип `notification`: реестры + карточки
   событий + M-NN; подтверждена сторожем и компактностью, снимает
   дубль-конфликт с гейтом значений.
2. Контент — перенести из шаблона A разделами-правилами в шаблон B (без
   дублирования алгоритмов): условия отправки клиентских нотификаций,
   параметры платформенной функции Журнала нотификаций (в «Адрес
   доставки» пары), «Другие статусы» как строка по умолчанию таблицы
   адресов, замена legacy-кодов.
3. Волна по дефектам шаблона B: правило разворачивания `<br>`-ячеек в
   строки (рендеримость), формат `E01` явно, title README-реестра,
   правило CriticMarkup (общеканонное).
4. Судьба A-формы: create-function освобождается от специализации
   (строка §11 → отсылка к create-notification); комплекты inquiry и
   open-add-account — легаси, долг командам на миграцию при следующем
   заходе.
5. Проверка слияния — перегон на богатом источнике [КК_ВК]
   (tmp-каталог analyzer) как ретро-тест: клиентские каналы, параметры
   платформенной функции, rowspan-шаблоны.

Остались решения: вливание meta/ntf-type-experiment →
meta/phase4-scope-rule; NTF в conventions (eco-techbook); судьба
легаси-комплектов inquiry/open-add-account (A-форма); сторож голых
ID-линков (отдельная волна — заденет предсуществующие места).

Ситуации, где A-форма остаётся сильнее (если слияние отвергнуть):
сервис, где нотификация действительно одна системная функция с
алгоритмом (вычисляемые получатели, ветвящееся поведение) и без
реестра «каналы×события» в источнике — там документ-функция честнее
реестра. На источниках-реестрах (оба фактических: locks, [КК_ВК])
A-форма проигрывает по дублям и навязанной структуре.
