# Каталог сервисов и межсервисная адресация — пример

Иллюстрация предложения Д-18 на реальных сервисах пилота. Имена сервисов,
документов и внешних функций — настоящие; часть связей достроена для полноты
картины и помечена *(иллюстрация)*. Имя репозитория-хаба `EAN/dbo-hub` —
условное, физическое размещение — вопрос DevOps (раздел 6 предложения).

Сюжет выбран не случайно: функция ЕСК «Запрос на создание заявки 115»
**уже сегодня** обслуживает два сервиса — «Открытие доп счёта» (о2plus) и
«Выпуск корпоративной карты» (КК): в её таблице тегов по две колонки
формирования («Для сущности Заявка на открытие доп счета…» и «[КК_ВК] Заявка
на выпуск карты»). Это живой случай всех трёх видов адресации: сервис →
внешняя АС, сервис → сервис экосистемы, сервис → платформа.

---

## 1. `catalog.md` хаба — таблица сервисов

| service-id | Название | docs-репозиторий | Контракты | Команда | Категория | Статус миграции |
|---|---|---|---|---|---|---|
| `open-add-account` | Открытие доп счёта и заключение ДБС (О2+) | `gitlab…/EAN/docs-o2new` → `output/open-add-account/` | [`dbo-hub/open-add-account/`](#2-структура-хаба) | team-configs → О2+ | заявочный | doc-as-code |
| `inquiry` | Запрос справок для ЮЛ | `gitlab…/EAN/docs-o2new` → `output/inquiry/` | `dbo-hub/inquiry/` | team-configs → Справки | заявочный | doc-as-code |
| `cc` | Корпоративные карты | *(пока Confluence, дерево [КК])* | `dbo-hub/cc/` *(иллюстрация)* | team-configs → КК | заявочный | Confluence → миграция |
| `platform-eco` | Платформа ЭКО (общие функции ДБО) | *(свой контур)* | `dbo-hub/platform/` | команды платформы | платформенный | — |

Замечания к таблице:

- строка на сервис — **всё**, что нужно потребителю, чтобы найти поставщика;
  зависимости-потребления здесь НЕ ведутся (генерируемая проекция по
  карточкам потребителей, раздел 1 предложения);
- статус миграции — переходная колонка: у `cc` контрактов в хабе ещё нет,
  но строка уже резервирует адрес — ссылки на `dbo-hub/cc/…` не поменяются
  после расселения.

## 2. Структура хаба

```
dbo-hub/
├── catalog.md                  # таблица из раздела 1
├── address-rules.md            # правила адресации (раздел 2 предложения)
├── open-add-account/
│   ├── openapi/                # спека сплит-формой, публикует CI сервиса
│   │   └── requests/create-request.yaml
│   ├── manifest.yaml           # реестр публичных элементов сервиса
│   └── cards/                  # карточки-проекции (раздел 4 примера)
│       └── fun-cl-01-create-request.md
├── inquiry/…
├── cc/…                        # появится при миграции; адрес зарезервирован
└── platform/
    └── platform-functions.md   # базовый реестр PLT-<домен>-NNN
```

## 3. Сквозной пример: КК потребляет операцию о2plus

*(связь-иллюстрация: «Выпуск карты» при многосчетовом договоре открывает
доп счёт — правдоподобно, но в текущих документах вызов оформлен через ЕСК)*

**Звено 1 — локальная карточка потребителя** в комплекте КК
(`docs/srs/consumers/open-add-account.md` у потребителя):

```markdown
# Потребление: Открытие доп счёта (open-add-account)

- **Зачем:** при [КК_ВК] Заявка на выпуск карты.<Заключить новый
  многосчетовой договор> == true — открытие счёта в рамках выпуска карты.
- **Операция:** `POST /requests` — создание заявки на открытие счёта
  (адрес контракта: dbo-hub/open-add-account/openapi/requests/create-request.yaml,
  пин: срез 2026-07-15).
- **Обработка ошибок:** отказ создания — MSG-…, заявка КК остаётся в DRAFT.
- **Карточка поставщика:** dbo-hub/open-add-account/cards/fun-cl-01-create-request.md
```

**Звено 2 — стабильный адрес в хабе**: `метод+путь` в спеке сплит-формы
(Д-12), URL — на файл хаба, не в чужой `docs/`-комплект.

**Как это выглядит в тексте документа КК** (шаг события ЭФ):

> **EV-5.3.** Вызвать создание заявки на открытие счёта — операция и
> параметры по [карточке потребления open-add-account](../consumers/open-add-account.md).

Текст ЭФ ссылается на **свою** карточку потребителя; та — на хаб. Прямой
ссылки в `output/open-add-account/docs/…` чужого репозитория нет нигде.

## 4. Карточка-проекция поставщика — что это и как используется

`dbo-hub/open-add-account/cards/fun-cl-01-create-request.md` *(иллюстрация
по образцу карточек build_cards)*:

```markdown
# FUN-CL-01. Создание заявки на открытие доп счёта — публичная карточка

- **Сервис:** open-add-account · **Версия:** срез 2026-07-15
- **Назначение:** создать заявку 115 на открытие доп счёта и заключение ДБС.
- **Контракт:** POST /requests — openapi/requests/create-request.yaml
- **Предусловия (публичные):** активный клиент; подписание — ЭП по правилам
  сервиса.
- **Полное описание:** внутри комплекта сервиса (потребителю не требуется).
```

Комментарий к использованию:

- **Кто пишет:** никто руками — карточку публикует CI-шаг поставщика при
  релизе (прототип — `build_cards.py`: манифест + карточки + классификация
  ссылок). Состав секций — конфиг поставщика: он решает, что публично.
- **Кто читает:** аналитик сервиса-потребителя, когда заводит карточку
  потребителя (звено 1); ревьюер MR потребителя — по ссылке из карточки.
- **Чем НЕ является:** это не документация функции (она в комплекте
  поставщика) и не карточка потребителя (семантика использования у каждого
  потребителя своя). Это витрина: публичный контур + указатель на контракт.
- **Разница с EXTINT:** для внешних АС базовая карточка уже есть
  (docs-external-integrations, base/usage). Карточка-проекция переносит ту же
  модель на сервисы экосистемы: base-слой генерируется из комплекта
  поставщика, usage-слой — карточка потребителя.

## 5. Тот же сюжет с внешней АС и платформой

- **ЕСК «Запрос на создание заявки 115»**: базовая карточка — в
  docs-external-integrations (прецедент; у о2plus уже есть
  `extint-003-esk-request-115.md` — это usage-слой); КК при миграции заводит
  **свою** usage-карточку на ту же базовую. Одна внешняя функция, два
  потребителя, ноль дублей базового описания.
- **Платформа**: «Метод определения размерности экрана» сегодня — ссылка на
  страницу Confluence платформы из каждого документа ЭФ. Целевое: строка
  `PLT-UI-001` в `dbo-hub/platform/platform-functions.md`, локальные
  usage-записи в сервисах. Ссылки из условий видимости ведут на PLT-запись,
  а не на страницу чужого Confluence.

## 6. Переходный период (пока КК в Confluence)

В выгрузке КК сегодня реально живут смарт-ссылки
`doc_id: '{{CC: [КК_ВК] ЭФ Клиента: страница "Анкеты"}}'` (манифест
dbo-registry). По предложению Д-18 (раздел 5): на период миграции `{{…}}`
легальны как отложенное связывание; при публикации в хаб компилируются в
канонические адреса (`dbo-hub/cc/…`), нескомпилированная ссылка — ошибка
сборки; ключ мигрирует с имени на стабильный ID.

## 7. Краевые случаи — вопросы к обсуждению

1. **Пин версии** — *решено (2026-08-04)*: **CI-гейт** — поставщик не может
   удалить срез, пока на него есть фиксации в реестре потребителей;
   уведомления недостаточно — потребителю нужно время на адаптацию и
   внесение изменений. Уведомление остаётся сигналом, гейт — гарантией.
2. **Гранулярность карточки поставщика** — *решено (2026-08-04, ориентир)*:
   **карточка на операцию** (метод+путь). Пример в разделе 4 показывает
   функцию с одной операцией — для многооперационных функций карточек
   несколько, по числу операций.
3. **Регистрация потребителя**: строка в реестре потребителей — MR в хаб от
   потребителя (как в EXTINT). Кто approve — владелец хаба или поставщик?
4. **Недоступность хаба** для читателя (права, контур): двухзвенная схема
   деградирует — карточка потребителя остаётся читаемой (семантика на
   месте), мёртв только прыжок к контракту. Достаточно ли этого?
5. **Составные документы в хабе** — *закрыт (2026-08-04, разбор с
   пользователем)*: новое решение не требуется, ответ выводится из уже
   принятого принципа «адресуется содержимое — запись со стабильным ID;
   файл — упаковка» (обкатан Д-10, сформулирован критерием в Д-19).
   Карточка адресуется составным адресом `<service-id>/<ID артефакта>`
   (принцип 3 политики ID: `open-add-account/FUN-CL-01`), собственный
   префикс `CARD-` не вводится — карточка есть генерируемая проекция
   артефакта, второй ID тому же содержимому дублировал бы ось (принцип 4).
   Операции спеки адресуются `метод+путь` (Д-12), файлы сплит-формы —
   упаковка (partOf-модель); инвариант id/partOf выполняется в хабе
   тривиально и проверяется тем же линтером.
6. **Платформа как поставщик карточек** — *в пакет для обсуждения с
   руководителем (решение 2026-08-04)*: платформенные команды пока не пишут
   постановок — кто генерирует их base-слой, если комплекта нет (reverse из
   Confluence платформы? заглушки с владельцем-ролью?). Вопрос организационный,
   стыкуется с кандидатом «роль владельца платформенной документации»
   (раздел 4 предложения).
