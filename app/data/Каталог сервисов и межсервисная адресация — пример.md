# Каталог сервисов и межсервисная адресация — пример

Актуализирован 2026-09-03 по фактической модели канона (`contract-call`,
локальные PLT-записи, подсервис-first, поле `repo` в services.json,
межсервисный долг «у владельца»). Дохабовая редакция примера — в истории
git этого файла; целевые улучшения (хаб, карточки-проекции,
версионирование) вынесены в последний раздел. Имена сервисов и функций —
настоящие; связи, достроенные для полноты, помечены *(иллюстрация)*.

Сюжет прежний и по-прежнему живой: функция ЕСК «Запрос на создание
заявки 115» уже сегодня обслуживает два сервиса — «Открытие доп счёта»
(o2plus) и «Выпуск корпоративной карты» (КК). Это все три вида
адресации: сервис → внешняя АС, сервис → сервис Экосистемы,
сервис → платформа.

---

## 1. Каталог сервисов = `_meta/services.json`

Роль каталога выполняет справочник сервисов (место временное, до
отдельного решения). Строка на сервис; поле `repo` — абсолютный
GitLab-URL **корня комплекта** (для общих репозиториев — с подпутём
`/-/tree/HEAD/<путь>`; `HEAD` вместо имени ветки — не приколачиваем
`master`/`trunk`); поля нет — сервис ещё не мигрирован:

```json
{ "code": "locks", "key": "lck", "name": "[БлокН2Н] Сервис блокировок доступа Н2Н",
  "is_platform": true, "repo": "https://gitlab.gboteam.ru/EAN/src-locks" },
{ "code": "open-add-account", "key": "O2PLUS", "name": "[O2+NEW] Сервис заключения ДБС…",
  "is_platform": false,
  "repo": "https://gitlab.gboteam.ru/EAN/docs-o2new/-/tree/HEAD/output/open-add-account" },
{ "code": "business-cards", "key": "CORP_CARDS", "name": "[КК] Корпоративные Карты",
  "is_platform": false }
```

Правило разбора `repo` детерминировано: есть `/-/tree/<ref>/` —
репозиторий слева, путь комплекта справа; нет — комплект в корне
(по конвенции `docs/` внутри). Зависимости-потребления в каталоге не
ведутся — прямая связь живёт в карточках вызова потребителей.

**Подсервисы картину не меняют**: `business-cards` — ОДНА запись
каталога при внутренних подсервисах (`srs/cc-card-issue/…` и др.,
модель «подсервис-first в одном комплекте»): извне адресуется сервис,
матрёшка — деталь путей внутри его репозитория.

## 2. Сквозной пример: КК потребляет метод o2plus

*(связь-иллюстрация; в текущих документах вызов оформлен через ЕСК)*

Локальная карточка потребителя — это **карточка вызова** в комплекте КК:
`docs/srs/contract-call/internal/call-int-001-create-add-account-request.md`
(`CALL-INT-001`):

```markdown
# CALL-INT-001. Создание заявки на открытие доп счёта

<шапка: базовый контракт — абсолютный URL на internal-contract владельца:
https://gitlab.gboteam.ru/EAN/docs-o2new/-/blob/HEAD/output/open-add-account/docs/srs/internal-contract/intc-00N-….md>

## Назначение
Владелец — open-add-account; КК вызывает создание заявки 115 при
<Заключить новый многосчетовой договор> == true. (1–3 предложения,
карточка читается автономно.)

## Использование в сервисе business-cards
Процессы, транспорт и ДВЕ полные таблицы маппинга: чем заполняются
исходящие параметры (ENT КК → параметры контракта) и куда кладутся
входящие. Каждый параметр контракта — строкой, незаполняемый — прочерком.
```

Шаг события ЭФ ссылается на **локальную** карточку вызова:

> **EV-5.3.** Вызвать создание заявки на открытие счёта — операция и
> параметры по [CALL-INT-001 Создание заявки на открытие доп счёта](../contract-call/internal/call-int-001-….md).

Прямых ссылок вглубь чужого `docs/` из текстов НЕТ — только из шапки
карточки вызова, и только на постановочный слой владельца
(`internal-contract/`) абсолютным URL.

**Если владелец ещё не мигрирован** (не имеет комплекта/`repo` в
каталоге) — карточка вызова несёт дословное имя метода, а в матрицу
ложится **межсервисный долг с владельцем**:

```
| CALL-INT-001 | — | нет целевого артефакта internal-contract «Запрос на
создание заявки» у владельца open-add-account — требуется публикация/миграция владельцем |
```

Сторож долгов (`link_debts`) такие долги локальной просрочкой не
проверяет (цель в чужом репозитории) и показывает сводкой
«межсервисных долгов N (владельцы: …)»; дозакрытие — при появлении
комплекта владельца (вручную или резолвером миграционного связывания
по page_id/title — дополнение Д-18).

## 3. Тот же сюжет с внешней АС

**ЕСК «Запрос на создание заявки 115»**: базовый контракт — ОДИН, в
репозитории [docs-external-contracts](https://gitlab.gboteam.ru/EAN/docs-external-contracts)
(`esk/extint-esk-NNN-….md`, `EXTINT-ESK-NNN`, examples рядом). Каждый
потребитель заводит СВОЮ карточку вызова
`docs/srs/contract-call/external/call-ext-NNN-….md` (`CALL-EXT-NNN`) со
своим маппингом параметров — у o2plus и КК колонки формирования тегов
разные, это и есть usage-слой. Обратная связь — строка в таблице
«Потребители» базовой карточки (абсолютный URL на карточку вызова,
вносит потребитель своим MR). Одна внешняя функция, два потребителя,
ноль дублей базового описания.

## 4. Тот же сюжет с платформой

Развилка по гейту create-contract-call:

- платформенный метод **С опубликованной спецификацией** — обычная
  карточка вызова `CALL-INT-NNN` со ссылкой на документацию платформы
  (никакого особого типа);
- платформенная функция/проверка **БЕЗ спецификации** («Метод
  определения размерности экрана» из условий видимости ЭФ) — строка
  `PLT-NNN` в ЛОКАЛЬНОМ реестре сервиса `docs/srs/platform-functions.md`;
  ссылки из документов — `[PLT-NNN <название>](…/platform-functions.md#…)`.
  Нет записи — не создавать: имя + долг.

PLT-номера локальны каждому сервису; глобальный реестр
`PLT-<домен>-NNN` остаётся целевым улучшением (давление снизилось:
методы со спецификациями ушли в CALL).

## 5. Целевые улучшения (не текущая практика)

Из дохабовой редакции остаются кандидатами: репозиторий-хаб
(`catalog.md` + публикация спецификаций CI-шагом), карточки-проекции
поставщика с манифестом (прототип build_cards.py), версионирование
срезов с diff-отчётами и CI-гейтом удаления, глобальный PLT-реестр,
компиляция `{{…}}`-ссылок. Решения 2026-08-04 по краевым случаям
(пин-гейт, гранулярность «карточка на операцию», самообслуживание
потребителя, адрес `<service-id>/<ID артефакта>` без `CARD-`-префикса)
не отменялись — они относятся к этой целевой фазе. Мостик до неё —
миграционное связывание по `page_id`/`title` (копилка Д-18) и поле
`repo` каталога.
