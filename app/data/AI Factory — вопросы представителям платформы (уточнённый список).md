# Вопросы к представителям платформы AI Factory — уточнённый список

Дата: 2026-10-10. Цель — согласовать правила, по которым мигрированный из Confluence комплект
документации сервиса Экосистемы читается агентами платформы без переделок, и чтобы скиллы миграции
и навыки платформы не предписывали аналитику разного на одном и том же комплекте. Ответы от 07.10
учтены; ниже только то, что осталось открытым. Вопросы упорядочены по важности: первые блокируют
первые сервисы, последние уточняют детали.

Термины: «платформа» здесь — AI Factory. «Платформенный сервис» в чек-листе DoR (SDLC-06) — сервис
Экосистемы с признаком `is_platform` в каталоге сервисов канона миграции, к AI Factory отношения не
имеет.

## 1. Ссылка из комплекта на файл в репозитории кода: предложение принять `HEAD`

**Расхождение.** Канон платформы `docs-kit-canon.md`, раздел 7 «Кросс-ссылки» (строки 162–163),
требует в ссылке на репозиторий кода явную ветку: «ссылки `Источник:` ведут на файлы спецификаций с
номерами строк, и плавающий реф там указывает не туда»; паспорт ЭКО `docs-kit-layout.md` (строки
259–260) даёт пример `…/ECO_BE/ms-<service>/-/blob/develop/api-specification/…`. Стандарт аналитики
ЭКО требует `HEAD`:

- `standards/analytics/conventions.md`, строки 102–103: «Контракт API читается из репозитория кода по
  `HEAD`; если комплект описывает не основную линию кода, `ref` назван в шапке раздела матрицы
  „Покрытие: API ↔ SRS“»;
- там же, §5.3 п. 7, строки 605–610: «Колонка „Источник:“ — ссылка на файл контракта через `HEAD` и
  имя операции (`operationId` / channel) текстом; это единственное место комплекта со ссылкой на
  файл в репозитории кода … Явное имя `ref` в ссылке допустимо, только если комплект описывает не
  основную линию кода: `ref` называется один раз в шапке раздела с причиной (предпочтительно тег, не
  ветка)».

Мигрированный комплект приходит на платформу с матрицей по стандарту ЭКО; ревьюер платформы
проверяет её по своему канону и при первой задаче по сервису даёт замечание на каждую ссылку
раздела, а системный аналитик платформы дописывает раздел уже с `develop`. В одном разделе
оказываются ссылки двух видов, и ни один инструмент не считает раздел правильным.

**Предложение: единое правило — `HEAD`, как в стандарте ЭКО.** Обоснование:

1. **Так уже устроена связь документации и кода в стандарте.** `repo-topology.md`, строки 412–416:
   «при смене смысла — согласованный merge: docs в `trunk`, код — в default branch репо кода
   (ADR-0017 — целевое имя `trunk`)». `HEAD` в GitLab и есть default branch. Схема связи там же,
   строка 433: «строка матрицы ──operationId, HEAD──► операция в YAML (api-specification/)». Адрес
   контрактов чужого сервиса строится по тому же правилу (строки 298–300:
   `ECO_BE/ms-<service-id>/-/tree/HEAD/api-specification`).
2. **Явная ветка `develop` закрепляет модель, которую Экосистема выводит из оборота.** ADR-0017
   «Trunk-Based Development для frontend и backend» (статус Accepted, 26.05.2026), строка 15, называет
   проблемой «длинные ветки `develop`, `rc-*`, `hotfix-*`»; строки 57 и 62: «единственная долгоживущая
   ветка — `trunk`; `develop`, `rc-*` и `hotfix-*` не используются как долгоживущие ветки в целевой
   модели». Сегодня у репозиториев `ECO_BE` ветка по умолчанию — `develop` (проверено на
   `ms-digital-ruble-consent`), после перехода станет `trunk`. Ссылка через `HEAD` переживёт
   переход без правок; ссылки с `develop` во всех матрицах перестанут открываться в день
   переименования, и узнать об этом можно только кликнув по каждой.
3. **Довод о номерах строк форматом не подкреплён и с явной веткой не работает.** Ни один навык,
   шаблон или пример платформы ссылки с `#L…` не содержит: `api-openapi` (строки 112–114) и
   `artifact-consistency` (строки 133–135) требуют только «ссылку `Источник:` на файл спецификации».
   Ссылка `…/blob/develop/file.yaml#L120` плавает так же, как через `HEAD`: `develop` движется с
   каждым коммитом. Строку закрепляет только коммит или тег, а их канон платформы не требует.
   Единственная живая практика со строками — матрицы Цифрового рубля (`EAN/docs-digital-ruble`, 222
   ссылки `…/blob/rc-3.4.0/…yaml#L18`): они сначала были написаны через `HEAD` со строками и в тот же
   день переведены на релизную ветку, потому что со `HEAD` строки ломаются первым коммитом. Это
   переходный приём gitflow с ручным переводом ссылок на каждом выпуске; с переходом на TBD
   `rc-*` исчезают. Стандарт ЭКО для такого случая уже предусматривает исключение: явный `ref`,
   «предпочтительно тег», назван один раз в шапке раздела.
4. **Адрес операции — её имя, а не строка.** В YAML нет стабильного якоря операции; стандарт
   называет операцию `operationId` текстом рядом со ссылкой на файл. Для сверки документации с
   кодом этого достаточно; переход кликом на строку — удобство, которое платится устареванием
   ссылок при каждой правке контракта.

**Что просим подтвердить.**

- Платформа принимает правило `HEAD` для раздела «Покрытие: API ↔ SRS» и ссылок `Источник:` и
  приводит к нему раздел 7 канона и пример паспорта ЭКО; исключение для комплекта не основной
  линии — по стандарту ЭКО (явный `ref`, предпочтительно тег, один раз в шапке раздела).
- Ревьюер и системный аналитик платформы сверяют контракт на ревью по координатам ветки и коммита
  из `work_report.externalOutputs`, а не переходом по ссылке из матрицы. Пока фича-ветка кода не
  влита, ссылка через `HEAD` заведомо ведёт на прежний контракт — это свойство модели, а не дефект
  документа.
- Переход на TBD для репозиториев `ECO_BE` не меняет форму ссылок в матрицах; при явном `ref`
  ответственность за перевод ссылок лежит на владельце комплекта.

**Почему важно.** Первый мигрированный сервис с API-слоем получит замечания к матрице при первой
же задаче на платформе, а правило, принятое после этого, придётся применять к матрицам всех
переехавших сервисов руками. При переходе репозиториев кода на `trunk` ссылки с `develop` сломаются
разом во всех комплектах, где системный аналитик платформы успеет их написать. Решение до первого
подключения дешевле любого решения после.

## 2. Валидатор платформы как часть проверки перед переносом комплекта

По ответам 07.10 валидатор (`validate_analytics_docs.py` в составе навыка `artifact-consistency`) —
часть самопроверки автора «при необходимости», не серверный гейт. Миграция планирует запускать его
как обязательную проверку перед переносом комплекта из рабочего репозитория в репозиторий
документации, вместе с прибором миграции: прибор проверяет содержание против источника, валидатор —
структуру (frontmatter, уникальность ID, ссылки, разбор JSON/YAML/XML, `$ref`, `operationId`,
матрица в корне комплекта).

Вопросы:

- Можно ли использовать валидатор вне платформы как самостоятельный скрипт: как узнавать о его
  новых версиях и изменениях кодов находок, допустимо ли хранить копию в инструментах миграции?
  Зависимость от PyYAML известна.
- Включён ли валидатор в проектную конфигурацию ЭКО как обязательный шаг автора или ревьюера? Если
  нет — проверка перед переносом остаётся единственным местом, где структура комплекта проверяется
  гарантированно, и это стоит знать обеим сторонам.
- Какие коды находок валидатора соответствуют критериям чек-листа DoR (SDLC-04, SDLC-08, SDLC-09,
  FMT-01, CORE-06, CORE-09)? Нужно, чтобы раздел «технологическая совместимость» закрывался отчётом
  валидатора, а не ручной проверкой.

Почему важно: первый прогон валидатора на мигрированном комплекте нашёл три невалидных JSON-примера
и две битые ссылки, которые прибор миграции не видит. Если валидатор не обязателен ни у платформы,
ни у миграции, такие дефекты доедут до агентов платформы незамеченными.

## 3. Типы документов вне набора платформы и объявление отличий в README

У канона миграции есть типы, которых нет в закрытом наборе платформы: описание метода сервиса до
перехода на API First (`internal-contract`, два состояния: текстовая карточка → ссылка на YAML),
библиотечный контракт (`lib-contract`), переходный реестр платформенных функций Экосистемы
(`platform-function`), карточка агента (`agent`). По ответам 07.10 агенты «учитывают объявленные в
README отличия» существующего комплекта.

Вопросы:

- Что именно и в какой форме должно быть объявлено в README комплекта, чтобы агенты читали эти
  документы как источник и не создавали, не правили и не считали их ошибкой? Есть ли образец или
  схема раздела «Условные обозначения» сверх таблицы контуров и подсервисов?
- Готова ли платформа включить эти типы в паспорт раскладки ЭКО с их назначением, чтобы они
  перестали быть «документами без навыка»?
- Поля frontmatter `title` и `confluence_page_ids` мигрированный комплект несёт как провенанс
  источника. Достаточно ли объявить их в README, чтобы агенты их не удаляли и не требовали убрать?

Почему важно: без ясного правила объявления первая задача платформы по мигрированному сервису
либо проигнорирует карточки методов и контрактов (потеря связей), либо «исправит» их под закрытый
набор (разрушение комплекта). Оба исхода — переделка после миграции, которую приоритет организации
исключает. Поле `confluence_page_ids` нужно не только как след источника: пока задачи в разработке
не завершены и перенос требований из Confluence продолжается, по нему требования привязываются к
существующей структуре сервиса, и его потеря разорвёт эту привязку для всех незавершённых задач.

## 4. Вызов метода другого сервиса Экосистемы: снимок контракта или ссылка на владельца

Канон платформы для карточки вызова (`CALL-INT`) предписывает **снимок контракта** поставщика в
самой карточке («у метода нет карточки-владельца»), с оговоркой, что после переезда постановок
поставщиков в репозитории документации достаточно ссылки на документ поставщика с версией. Канон
миграции снимка не делает: карточка вызова ссылается на описание метода у сервиса-владельца; у
факта один дом.

Вопрос: можно ли согласовать переходное правило — снимок допустим только пока у владельца нет
описания метода в репозитории документации; есть описание — только ссылка; и признать это правило
в обоих канонах?

Почему важно: снимок — второй дом у факта. При изменении контракта владельцем снимки у потребителей
устаревают молча; ревьюер платформы проверяет согласованность внутри комплекта и этого не увидит.
Для сервисов Экосистемы, которые уже мигрированы и описаны, снимок создаёт расхождение с первого
дня.

## 5. Паспорт раскладки ЭКО: ведение и синхронизация со стандартом

Паспорт раскладки ЭКО (`docs-kit-layout.md` и `.yaml`) — снимок от 22.09.2026, уже не знает
решений стандарта после этой даты: библиотечный контракт, два состояния описания метода, `HEAD` как
правило, снятие каталога `api/` и генерации AsyncAPI. Значения паспорта (имена каталогов, префиксы,
адреса репозиториев) дублируют стандарт аналитики eco-techbook и каталог сервисов.

Вопросы:

- Какая версия паспорта активирована для проекта ЭКО сегодня и как она обновляется?
- Готова ли платформа принимать паспорт как **собираемый** из стандартов eco-techbook и каталога
  сервисов файл (md и yaml из одного источника одним изменением), а не как рукописный документ? Какие
  требования к формату и процедуре активации при этом нужно соблюсти?
- По той же схеме: сокращённая копия нотации в наборе знаний платформы — есть ли правило её
  синхронизации с полной нотацией eco-techbook, подобно правилу «диффом с toolkit» для правил
  проектирования API?

Почему важно: пока паспорт переписывается вручную, каждое решение стандарта рождает расхождение с
платформой. Именно так возникли вопросы 1 и 6 этого письма.

## 6. Место спецификации AsyncAPI: паспорт ЭКО следует снятой концепции техбука

Паспорт ЭКО (`docs-kit-layout.md`, строки 39 и 230) и проектные промпты системного аналитика
размещают AsyncAPI в отдельном репозитории `ECO_BE/lib-api-<service>/asyncapi/jms.yaml` со ссылкой
на концепцию техбука `architecture/concepts/api-first-async.md`. В техбуке эта концепция снята:
`architecture/concepts/_index.md` (строки 7–8) помечает её «(deprecated)», действующая —
`api-first-async-yojo.md`: «в репозитории сервиса в директории `api-specification` создаётся файл
`servicename-asyncapi.yaml`» (строка 16), генератор Yojo, пример `file-storage-internal-asyncapi.yaml`
в `ms-file-storage-service`. Общая раскладка платформы (`docs-kit-layout.md` общего слоя, строки
93–94) и стандарт аналитики ЭКО (`conventions.md`, строка 481: «контракты OpenAPI / AsyncAPI сервиса
живут в `api-specification/` репозитория кода») говорят то же. Расходится только паспорт ЭКО.

Вопрос: приводится ли паспорт ЭКО и проектные промпты к действующей концепции и общей раскладке
платформы — AsyncAPI в `api-specification/` репозитория `ms-<service>` — и остаётся ли у `lib-api-*`
какая-либо роль для системного аналитика платформы?

Почему важно: пока паспорт указывает на `lib-api-*`, системный аналитик платформы положит первый
асинхронный контракт в репозиторий, которого у сервиса может не быть, а матрица комплекта и
генерация кода по действующей концепции ищут его в `api-specification/`. Это пример того, как
рукописный паспорт расходится со стандартом без сборки из него (вопрос 5).

## 7. Долги мигрированного комплекта как вход первой задачи платформы

По ответам 07.10 планировщик читает целевую ветку репозитория документации, README и матрицу;
рабочий репозиторий миграции и ответы владельца в журнале открытых вопросов ему недоступны.
Открытые вопросы к переносу закрываются по построению. Но часть долгов переживает перенос —
прежде всего межсервисные («описание метода у владельца отсутствует»).

Вопрос: в каком месте и формате планировщик прочитает такие долги как вход первой задачи — раздел
долгов матрицы трассировки в форме записей реестра (`statement`, `basis`, `priority`, `scope`,
`addressee`), отдельный документ комплекта или только явное упоминание в постановке задачи?

Почему важно: если долги невидимы планировщику, первая задача платформы по сервису переоткроет их
как новые вопросы или, хуже, допущения агента — работа владельца по их разбору пропадёт.

## 8. BRD и сверка с кодом для мигрированного сервиса — положение в DoR

Два критерия чек-листа готовности расходятся с практикой миграции: SDLC-06 требует BRD,
восстановленный по SRS, для бизнес-сервиса; SDLC-11 — сопоставление документации с кодом до
подключения. Миграция BRD не строит (стандарт: SRS адаптируется из Confluence) и с кодом не
сверяет. По ответам 07.10 существующий комплект без `brd/` для платформы законен, а расхождение кода
с документом — критичный вопрос для системного аналитика.

Вопросы:

- Есть ли у бизнес-аналитика платформы навык вывести BRD (концепцию, фичи, use cases) из
  существующего SRS как **первую задачу по сервису**, чтобы SDLC-06 закрывался на платформе, а не до
  подключения?
- Допускает ли платформа подключение комплекта без отчёта о сверке с кодом, с тем что расхождения
  выявляются как вопросы в первых задачах системного аналитика (SDLC-11 — после подключения)?

Почему важно: если оба критерия остаются условием подключения, переезд бизнес-сервисов
откладывается на полный цикл восстановления BRD и аудита кода силами команд — против приоритета
быстрого выхода мигрированных сервисов в платформу.

## 9. Правила текста forward применительно к перенесённому тексту

Навыки платформы содержат правила к тексту требований: например, «„Обратитесь в банк“ как способ
решения — блокер», запрет неопределённых слов. Мигрированный комплект переносит текст источника
дословно, и такие формулировки в нём встречаются.

Вопрос: применяются ли эти правила ревьюером платформы к существующему тексту при первой задаче
(блокирующий отказ на весь документ) или только к изменённым агентом фрагментам?

Почему важно: при первом варианте любая дельта в документе с унаследованными формулировками будет
отвергаться до переписывания всего документа — скрытое «лечение аналитики» силами платформы вне
плана.

## 10. Первые сервисы для подключения

На каком мигрированном комплекте и в какие сроки планируется первое подключение?

Почему важно: проверку готовности (оба раздела чек-листа) и валидатор имеет смысл отработать на
реальном первом сервисе, а не только на стенде миграции; с ответом можно заранее снять находки
валидатора именно на нём.

---

Предлагаемый порядок обсуждения: вопросы 1–4 — на одной встрече, они определяют правки стандарта
ЭКО и канона миграции; 5–6 — письменно; 7–10 — по мере подготовки первого сервиса.
