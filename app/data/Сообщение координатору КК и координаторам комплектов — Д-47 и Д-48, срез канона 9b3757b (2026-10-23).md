# Координатору КК и координаторам комплектов: срез канона `9b3757b` — решения по разбору замечаний (Д-47), шаг «ревью содержания» (Д-48)

Дата: 2026-10-23. От владельца методологии. Раздел 1 — всем; раздел 2 — координатору КК (числа и
заходы по комплекту); раздел 3 — порядок приёма среза. Срез `9b3757b` содержит также FB-30 (вид
`CALL-MOD`), классы непокрытия и зону «вне Экосистемы» (Д-46), если они ещё не приняты.

## 1. Что изменилось для всех комплектов

**Новые и уточнённые нормы (Д-47)** — по разбору замечаний к миграции КК (12 карточек → 14 типов
недочётов; большинство прошли приёмку при зелёном приборе):

| Норма | Где | Что делать команде |
| --- | --- | --- |
| Состав подписываемых полей (СПП) — модель данных: раздел «Состав подписываемых полей (СПП)» в `dictionaries.md`, версии подразделами; большой состав — выносной файл `data-model/spp-<слаг>.md` | `data-model.md`, `create-artifact` (дерево метода) | страницы «СПП …», перенесённые как функции, — перенести в модель данных при ближайшем касании |
| Страница «параметры вызова функции другого сервиса» (универсальная функция ЭП и т. п.) — не функция, а карточка вызова `CALL-INT` на библиотечный контракт `LIBC` владельца; контракта нет — долг «у владельца» | `create-artifact` | то же |
| Строка таблицы кнопок без номера и названия — событие формы (§5), не кнопка и не самодельный раздел | `screen-form.md` §6 | при касании карточки ЭФ |
| Карточка контроля: способ и место показа сообщения не указываются (их дом — §7 ЭФ); чек-лист контролей приведён к полю | `controls.md` | при касании карточек контролей |
| **Приём среза = докатка норм**: `accept_canon.py` печатает дельту норм между срезами (какие шаблоны, скиллы, протокол и в каких разделах изменились); координатор или акцептующий по каждому пункту пишет в журнал координации «докатка: <что и когда>» либо «не применимо: <основание>». Срез без такой записи принят не до конца | протокол §1 | с этого среза — при каждом приёме |

**Новые предупреждения прибора** (только ⚠ и i, вердикт не меняют), по тем же типам недочётов:
копия страницы как своя («Копия» в title); способ показа в карточке контроля; «Вызов функции» без
ссылки, когда карточка-вызыватель уже есть; строка паспорта вне таблицы (`intc`, карточки вызова,
модель данных); кнопка ЭФ без полей «Видимость / При нажатии» и сообщения списком; нетонкая карточка
вызова (разделы базового контракта продублированы); склейка абзацев ячейки («Строка(19)Допустимый…»)
и сводная строка «источник с таблицами перенесён без нормализованной копии (протокол §5)»;
подозрение на неверный тип функции (СПП, параметры вызова); счётчик открытых вопросов по статусам.
Каждое предупреждение называет норму, по которой чинить.

**Шаг «ревью содержания» (Д-48).** Между сдачей исполнителя и техприёмкой появляется ревью: новая
сессия сильной модели по промпту `_meta/migration/prompt-reviewer.md` читает каждую карточку захода
против её страниц-источников и пишет `sandbox/review-<ЭТАП>-zNN.md` (замечания классами потеря /
искажение / форма / вопрос, с цитатами). В треке с координатором ревьюера запускает координатор
(`prompt-coordinator.md`, обязанность 2а), без координатора — акцептующий; исполнитель вписывает
путь и итог в сдачу (протокол §8 п. 16). **Сдача без файла ревью не принимается**; «потеря» и
«искажение» — дозаход до приёмки. Причина: прибор сверяет слова и форму, а смысл (вложенность
условий, потерянное условие, копия как своя) видит только чтение против источника — именно такие
замечания прошли приёмку в КК.

## 2. Координатору КК

Числа новых предупреждений по `master` КК (копия 1ffeb4c), все — предмет заходов, не брака:

| Предупреждение | Мест | Пример |
| --- | --- | --- |
| копия как своя | 9 карточек | `fun-sys-10` и `call-ext-011…`, `call-ext-024…030` |
| способ показа в контроле | 43 в 4 файлах | `cards-ent-003`, `cards-ent-019` |
| вызыватель без ссылки при существующей цели | 15 | `fun-cl-05` → FUN-CL-40, `fun-sys-01` → SCR-BNK-09 (в тексте стоит устаревшее «нет целевого артефакта») |
| строка паспорта вне таблицы | 7 файлов | `intc-001`, `intc-006` |
| кнопки ЭФ не по шаблону | 22 в 7 файлах + §9 списком | `scr-cl-19` |
| нетонкая карточка вызова | 10 | `call-ext-001…007`, `009`, `010`, `011` |
| склейка абзацев ячейки | 10 | `fun-sys-11`, `intc-007` |
| источник с таблицами без нормализованной копии | 86 карточек | `fun-sys-11` ← 2166860395 (перечень — в файле отчёта) |
| подозрение на неверный тип функции | 8 | `fun-cl-50`, `fun-cl-51` |

Рекомендуемый порядок заходов (план П2–П5 разбора; решает акцептующая):

1. **Сначала содержание, не форма:** вложенность условий в ЭФ и функциях, перенесённых в ISS-03
   «плоским» отклонением, — чтением карточек против источника (пример: `scr-cl-19`, B-6 — потеряно
   условие «доступен укороченный вид»); это первый живой заход с ревью Д-48. Сюда же — 86 карточек
   без нормализованной копии: по ним сверка ячеек с источником не выполнялась.
2. Механика слабой моделью по предупреждениям: способ показа, строки паспорта, устаревшие пометки
   «нет целевого артефакта» (15 + пометки в телах), склейки.
3. По решениям Д-47: СПП и «параметры вызова» (9 карточек) — в модель данных и карточки вызова;
   копии (9) — общебанковское в базу `docs-external-contracts`, своё использование в КК; нетонкие
   карточки вызова (10) — истончить.
4. Зона виджетов — по ответам на OQ-295…298 (Д-46).

Записи в `feedback.md` по этому письму не нужны; вопросы — как обычно, FB-NN.

## 3. Порядок приёма среза

1. `accept_canon.py --profile README.md` — в выводе появится блок «Дельта норм <старый>→9b3757b».
2. По каждой строке блока — запись в журнал координации: «докатка: <заход/срок>» или «не
   применимо: <основание>». Для КК докатка уже разложена по заходам выше.
3. Самопроверка: новые ⚠ ожидаемы, вердикт не меняется.
