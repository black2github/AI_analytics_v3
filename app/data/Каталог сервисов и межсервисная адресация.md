# Каталог сервисов и межсервисная адресация (предложение по Д-18)

Статус: кандидат-предложение к обсуждению. Назначение: до расселения сервисов
обкатки зафиксировать, **как сервисы находят и адресуют друг друга** — после
расселения смена этих правил потребует скоординированной правки всех команд.
Строится на уже принятых решениях: Д-15 (реестр опубликованных спецификаций +
карточка потребителя), Д-12 (стабильные адреса операций: метод+путь / файл
сплит-формы), принцип 4 политики идентификаторов (вид поставщика — свойство,
не префикс), прецедент base/usage из docs-external-integrations.
Живой сквозной пример на реальных сервисах —
[Каталог сервисов — пример](Каталог%20сервисов%20и%20межсервисная%20адресация%20—%20пример.md).

---

## 1. Каталог сервисов: что это и где живёт

**Минимальный состав каталога** (строка на сервис):

| Поле | Источник |
|---|---|
| `service-id` | канон — team-configs (`jiraDevComponent`) |
| docs-репозиторий | абсолютный URL GitLab |
| Опубликованные контракты | ссылка в реестр спецификаций (раздел 2) |
| Команда-владелец | ссылка в team-configs |
| Категория (платёжный / заявочный / платформенный) | для выбора специализации скиллов; «системный» отдельной категорией не ведётся — по факту системные справочники и функции — часть платформенных сервисов (решение 2026-08-04) |
| Статус миграции (Confluence / doc-as-code) | для переходного периода |

**Варианты размещения:**

- **(а) — рекомендация: единый репозиторий «контрактного хаба»** — тот же,
  где живёт реестр опубликованных спецификаций (Д-15, часть 1; прототип —
  ручной all-bundle). Каталог без спек пуст, реестр спек без каталога слеп —
  им естественно быть одним репозиторием: `catalog.md` (таблица сервисов) +
  `<service-id>/` (публикуемые CI-шагом спецификации). Прецедент устройства —
  docs-external-integrations.
- (б) Расширить docs-external-integrations. Смешивает ритмы: базовые контракты
  внешних АС меняются редко, спеки сервисов — каждый релиз.
- (в) В methodology-репо. Методология — правила, каталог — живой реестр;
  разные владельцы и ритмы.
- (г) Полностью генерировать из team-configs + gpb-manifest. Правильно по
  принципу «выводимое не ведётся руками», но зависимости-потребления и
  контракты там отсутствуют; генерация — целевое улучшение, не старт.

**Зависимости-потребления в каталоге не ведутся руками**: прямая связь
живёт в карточке потребителя (Д-15, часть 2), обратный индекс «кого потребляет
сервис X / кто потребляет сервис Y» — генерируемая проекция по карточкам
(механика — как таблица «Потребители» в EXTINT: строка-регистрация MR-ом
потребителя, пока нет генератора). **Регистрация — самообслуживание
потребителя (решение 2026-08-04):** строку вносит потребитель, поставщик
уведомляется, его approve не требуется — парадигма действующих обратных
ссылок Confluence сохраняется.

## 2. Правила межсервисной адресации (ядро предложения)

1. **Ссылка на чужой сервис — всегда двухзвенная**: (i) локальная карточка
   потребителя (семантика использования, обработка ошибок, пин версии) +
   (ii) стабильный адрес контракта в хабе. Прямые ссылки в чужой `docs/`-комплект
   запрещены (изоляция комплектов — уже действующее правило, распространяется
   на межсервисные связи явно).
2. **Стабильный адрес операции** — `METHOD + путь` либо файл сплит-формы
   спецификации; `operationId` — только после введения governance стабильных
   имён (Д-12 п. 5: автогенерированные `generateDigest_2` нестабильны).
3. **Ссылки между репозиториями — только абсолютные URL GitLab** (прецедент
   EXTINT); внутри репозитория — относительные.
4. **Вид поставщика — свойство карточки**, не тип ссылки: внешняя АС /
   сервис экосистемы / платформа. Одна модель карточки на все три случая
   (ин-сорсинг АС не ломает ссылок — принцип 4 политики ID).

## 3. Версионирование межсервисных контрактов

**Фаза обкатки (лайт):**

- спецификация публикуется в хаб CI-шагом при релизе сервиса, с меткой
  (дата-срез или версия сервиса); Code First и API First сервисы публикуют
  одинаково — потребителю безразлично происхождение;
- при каждой публикации — **diff-отчёт** против предыдущей (инструментарий
  класса oasdiff); breaking-изменения (удаление/переименование пути или поля,
  ужесточение обязательности) помечаются в отчёте;
- потребители уведомляются по реестру потребителей (обратный индекс, раздел 1);
- потребитель фиксирует в карточке метку версии, на которую опирается
  (фиксация версии, «пин»); переезд = MR в собственную карточку;
- **CI-гейт удаления среза (решение 2026-08-04):** поставщик не может удалить
  опубликованный срез, пока на него есть фиксации в реестре потребителей —
  уведомление остаётся сигналом, гейт даёт время на адаптацию;
- **гранулярность карточки поставщика — операция** (метод+путь; решение
  2026-08-04, ориентир до опыта обкатки).

**Целевая фаза (после обкатки):** semver для спецификаций; правило «breaking —
только мажорная версия; старая версия живёт до переезда всех потребителей по
реестру»; гейт CI на breaking без мажора. Вводить на обкатке рано — сначала
должен появиться сам поток публикаций.

## 4. Платформа: владелец платформенных описаний

**Проблема.** PLT-карточки в комплектах сервисов — заглушки «постановки нет»;
PLT-NNN нумеруются локально в каждом сервисе, поэтому одна и та же платформенная
функция (проверка подписи, доступность функций, онбординг) получает разные ID
и дублирующиеся заглушки в каждом сервисе-потребителе. С ростом числа сервисов
дубли и пустоты растут линейно.

**Предложение — применить уже работающую модель base/usage (EXTINT) к платформе:**

- **Базовый реестр платформенных функций** — в контуре платформы (свой
  docs-репо платформенных сервисов или раздел хаба): глобальные ID
  `PLT-<домен>-NNN` (по образцу `EXTINT-<AS>-NNN`), карточка = назначение,
  параметры, поведение; наполняется командами платформы по мере готовности —
  но **единый реестр из заглушек лучше, чем распределённые дубли заглушек**:
  устраняет расхождение ID уже в день создания.
- **Локальная usage-карточка** в сервисе-потребителе — как сервис вызывает
  функцию (существующие PLT-NNN сервисов становятся usage-слоем; их номера
  не меняются — добавляется ссылка на базовый ID).
- **Организационно:** нужна роль «владелец платформенной документации»
  (команды платформенных сервисов как поставщики описаний) — решение уровня
  руководителя; кандидат в дополнение пакета согласования.

## 5. Заимствования из карточного прототипа (build_cards / dbo-registry)

Разобран рабочий прототип из requirements-analyzer-v3 (2026-08-04):
`app/scripts/CI/build_cards.py` — двухпроходный CI-конвейер, публикующий в
общий репозиторий `dbo-registry/<сервис>/` карточки-проекции документов
сервиса + `manifest.yaml` (реестр публичных элементов); межсервисные ссылки —
смарт-нотацией `{{код_сервиса: имя документа}}`, разрешаемой по манифестам.

**В целевую модель НЕ берётся** замена адресации на смарт-ссылки — три
структурные слабости против разделов 1–2: (1) ключ — человекочитаемое имя,
а не стабильный ID (переименование страницы ломает ссылку тише, чем
переименование файла); (2) кастомный синтаксис вне markdown мёртв без
резолвера (GitLab-рендер, IDE, грепы, чужие линтеры) и добавляет слабым LLM
ещё одну нотацию; (3) два уровня разрешения (каталог → манифест → файл) —
две точки рассинхрона против одной у прямого URL на стабильный путь хаба.

**Берутся два элемента:**

1. **Карточка-проекция поставщика + манифест** — как формат публикации в хаб
   для не-API артефактов: сервис публикует наружу карточки своих функций/ЭФ/
   методов, внешние человеческие ссылки ведут на карточку в хабе, а не вглубь
   чужого `docs/`. Публичный контур сервиса становится явным и контролируемым;
   реестр опубликованных спецификаций (раздел 1) расширяется с API-спек на
   карточки. `build_cards.py` — работающий прототип CI-шага публикации
   (раздел 3), включая классификацию ссылок при публикации: redirect на
   публичную карточку / расплющить в текст / внешняя / межсервисная.
2. **Отложенное связывание на период миграции**: пока сервисы не расселены и
   физические адреса неизвестны, перекрёстные связи фиксируются логической
   ссылкой `{{…}}` (класс «сейчас или никогда» — после расселения
   восстанавливать связи будет некому), а при публикации **обязательно
   компилируются** в канонические адреса хаба (механика — уже принятые
   Д-3-компиляция и Д-13-линтер: неразрешимая ссылка = ошибка сборки).
   Ключ ссылки при этом мигрирует с имени на стабильный ID — тогда имена
   файлов, ломаемые скиллами `_meta`, в адресации вообще не участвуют.

## 6. Вне предложения

Автогенерация каталога из team-configs (целевое улучшение); физический выбор
GitLab-группы для хаба (DevOps); миграция существующих EXTINT-карточек (они
уже соответствуют модели); semver-гейты (целевая фаза).

## 7. Минимум к старту обкатки

1. Завести репозиторий-хаб: `catalog.md` с таблицей пилотных сервисов +
   публикация их спецификаций (можно начать ручной выкладкой из all-bundle).
2. Правила адресации (раздел 2) — страницей в хабе + строкой в conventions
   каждого комплекта («межсервисные ссылки — по правилам хаба, URL»).
3. Базовый реестр платформенных функций — хотя бы скелет с глобальными ID,
   чтобы сервисы обкатки сразу ссылались на единые идентификаторы.
4. Роль владельца платформенной документации — в пакет согласования
   руководителю.
