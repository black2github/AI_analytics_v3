# Постановка задачи: пофрагментный статус требований при переходе на Doc as Code

> Документ предназначен для кодового агента с полным доступом к исходникам репозитория.
> Агент не участвовал в проектировании, поэтому раздел «Контекст» читать обязательно —
> без него смысл требований к коду не восстанавливается.
>
> Версия 2. Учтены: разграничение переходного и целевого режимов, уже реализованные
> компоненты пайплайна, обработка сохранённых HTML-таблиц.

---

## 1. Контекст

### 1.1. Что происходит

Отдел переводит аналитику системы ДБО для юридических лиц с Confluence на Doc as Code:
требования описываются в markdown-файлах и хранятся в GitLab.

### 1.2. Как статус требования фиксируется сейчас (Confluence)

Все изменения на странице делаются **цветом**, соответствующим текущей задаче Jira
(например, GBO-12345 — сиреневый, GBO-67890 — зелёный). После ввода в эксплуатацию
(переход задачи в статус «Установлено на ПРОМ») аналитик вручную сбрасывает цвет в чёрный.

Следствия:

- **чёрный текст** = действующий функционал на промышленном контуре (утверждённые требования);
- **цветной текст** = изменение в рамках незавершённой задачи (ещё не реализовано);
- **цветной зачёркнутый текст** = требование, удаляемое в рамках задачи.

Гранулярность цвета — произвольная: цветом может быть выделен целый раздел, абзац, строка
таблицы, ячейка или **одно слово внутри предложения**. Последний случай — массовый.

Пример (типовой):

```
На ПРОМ:  Проверяется, что с пользователем связана хотя бы одна организация.
Стало:    Проверяется, что с пользователем связана хотя бы одна ДЕЙСТВУЮЩАЯ организация.
                                                                 ^^^^^^^^^^^^ цвет GBO-12345
```

За словом «действующая» на логическом уровне стоит обращение к системному справочнику
за статусом организации, то есть это полноценное требование, а не стилистическая правка.

### 1.3. Чем цвет заменяется

**CriticMarkup** — стандартная нотация правок в Markdown, дополненная обязательным
префиксом с номером задачи Jira:

| Смысл | Нотация | Аналог в Confluence |
|---|---|---|
| вставка (новое требование) | `{++GBO-12345: текст++}` | цветной текст |
| удаление (требование убирается) | `{--GBO-12345: текст--}` | цветной зачёркнутый текст |
| замена формулировки | `{~~GBO-12345: старое~>новое~~}` | зачёркнутое + новое, одним цветом |

Файл в `main` содержит **полную картину**: и утверждённые требования (чистый текст),
и неутверждённые (внутри маркеров). Разные представления получаются на сборке, а не
хранением разных версий файла или разных долгоживущих веток.

### 1.4. Переходный режим и его причина

**Ключевое для понимания задачи.** Процесс создания требований идёт непрерывно, остановить
его и дождаться, пока все текущие задачи выйдут на ПРОМ, невозможно. Значит, миграция
обязана перенести в markdown не только текст, но и **текущее положение дел**, выраженное
сегодня цветом.

Отсюда в репозитории сосуществуют две популяции маркеров с одинаковым синтаксисом,
но разного происхождения:

| | Мигрировавшие маркеры | Новые маркеры |
|---|---|---|
| Как появились | пачкой, при конвертации из Confluence | штатно: ветка → commit → MR → `main` |
| Есть ли ветка в Git | нет | да, короткоживущая |
| История появления | осталась в Confluence | в истории Git |
| Как исчезают | `critic.py apply` при выходе на ПРОМ | так же |

Разметка нужна и новым задачам тоже — это не переходный костыль. Причина: MR аналитика
сливается в `main` за дни, а на ПРОМ задача выходит через месяцы. Ветка не может нести
признак «ещё не реализовано» весь этот срок; его несёт маркер внутри текста.

**Переходный период завершается**, когда в репозитории не остаётся ни одного маркера из
числа мигрировавших. Это измеримое условие, и его нужно уметь измерять — см. требование
к `migration-manifest.yaml` (п. 4.9) и к команде `critic.py list` (п. 5.4).

### 1.5. Открытая развилка: что делать после завершения переходного периода

Решение не принято. Оба варианта поддерживаются одним и тем же кодом, различие только в
процессной дисциплине:

| | Вариант A: `main` = ПРОМ | Вариант B: `main` = полная картина |
|---|---|---|
| Незавершённая задача живёт | в отдельной ветке, месяцами | в `main`, под маркером |
| Основной риск | конфликты при ребейзе долгих веток | `main` содержит нереализованное |
| Судьба `critic.py` | отмирает вместе с хвостом миграции | постоянная инфраструктура |

**Практическое следствие для агента:** не закладываться ни на один из вариантов в
архитектуре. Модули 1–3 нужны при любом исходе. Объём инвестиций в модули 4–6 зависит от
выбора и определяется отдельно, поэтому они вынесены в поздние этапы.

### 1.6. Целевой процесс работы с маркером

1. Аналитик пишет требование новой задачи, обернув его в маркер с номером задачи.
   Ветка → MR → `main`. Для мигрировавших требований этот шаг уже выполнен — в Confluence, цветом.
2. Пока задача не на ПРОМ, маркер лежит в `main`. Требование видно в представлении
   «целевое состояние» и не видно в представлении «текущий ПРОМ».
3. Задача выходит на ПРОМ → маркеры этой задачи механически снимаются по всему
   репозиторию, создаётся MR «подтверждение требований», аналитик его сливает.
   Это автоматическая замена сегодняшнего ручного сброса цвета в чёрный.
4. Задача отменена → маркеры откатываются: вставки удаляются, удаления восстанавливаются,
   замены возвращаются к старой формулировке.

## 2. Жёсткие ограничения

Нарушение любого из пунктов делает решение неприменимым.

1. **Закрытый контур.** Нет доступа в интернет. Все зависимости — либо stdlib, либо уже
   присутствующие в контуре пакеты. Перед добавлением новой зависимости проверить,
   решается ли задача имеющимися средствами. `GitPython` и `python-gitlab` использовать
   не нужно: достаточно `subprocess` + `git` и `requests`.
2. **Jira недоступна на этапе миграции.** Конвертер Confluence → Markdown не имеет права
   обращаться к Jira ни за статусом задачи, ни за зависимостями, ни за проверкой
   существования идентификатора. Идентификаторы задач извлекаются исключительно из
   содержимого самой страницы Confluence (см. п. 4.2). Зависимости задач между собой
   (blocks / blocked by) в Jira, как правило, зафиксированы, но на миграции недоступны —
   значит, разрешать их автоматически нельзя, только фиксировать факт в отчёте.
3. **Кроссплатформенность.** Разработка в Windows (PyCharm), CI в Linux. Пути — только
   `pathlib`. Переводы строк — сохранять исходные, не нормализовать CRLF → LF молча,
   иначе diff в git будет содержать файл целиком. Кодировка — везде явно `encoding="utf-8"`.
4. **Никаких потерь содержания требований.** Правило относится к **тексту требований и
   их структуре**, а не к HTML-разметке: существующий пайплайн осознанно отбрасывает
   часть разметки и по сложной логике решает, конвертировать ли таблицу в чистый markdown
   или сохранить сырой HTML — это поведение менять не нужно и репортить не нужно.
   Репортится другое: фрагмент требования, для которого не удалось однозначно определить
   статус или номер задачи. Такой фрагмент попадает в отчёт с указанием файла, строки и
   исходного HTML. Молчаливое отбрасывание статуса — критическая ошибка.
5. **Идемпотентность.** Повторный запуск любой операции на уже обработанном файле не
   должен менять файл.

## 3. Что уже реализовано в репозитории

Перед началом работы **исследовать существующий код и встроиться в него**, а не создавать
параллельную структуру. Ниже — то, что известно на момент постановки. Фактические имена
модулей, точки расширения и стиль кода определить по репозиторию; при расхождении с
рекомендациями ниже приоритет у сложившихся соглашений.

**Готово, переиспользовать:**

- **Доступ к Confluence.** Выполняется прямым HTTP-запросом; параметры задаются
  переменными окружения и ключом запуска `--http`. Новый механизм получения storage format
  не нужен.
- **Пайплайн миграции** Confluence → Markdown: разбор разделов, генерация карточек,
  сборка манифеста, резолвинг ссылок между карточками.
- **Поиск секции «История изменений».** Реализован. Есть ключ запуска, сохраняющий раздел;
  **по умолчанию раздел удаляется**. Заново искать секцию не требуется — требуется разобрать
  таблицу внутри неё (п. 4.2).
- **`style_utils.py`** — утилиты работы со стилями, включая набор `black_colors`
  с перечнем значений, трактуемых как чёрный (см. п. 4.3).
- **Конвертация таблиц** с логикой выбора между чистой markdown-таблицей и сохранением
  сырого HTML. Логику не менять; учесть её при разметке (п. 4.7).

**Требует проверки:**

- **Плагин MkDocs**, резолвящий смарт-ссылки `{{сервис:элемент}}` в обычные markdown-ссылки,
  с обработкой fenced code blocks и `use_directory_urls`. Разрабатывался, но его текущее
  местоположение не установлено. Найти в репозитории; если отсутствует — не блокироваться:
  для настоящей задачи из него нужна только логика пропуска fenced code blocks, её
  допустимо реализовать внутри `critic.py` самостоятельно.

## 4. Модуль 1: извлечение цвета при миграции

### 4.1. Вход и выход

**Вход:** Confluence storage format (XHTML), получаемый существующим механизмом (п. 3).

**Выход:**
1. markdown-файл, где цветные фрагменты заменены на CriticMarkup с номерами задач;
2. `migration-manifest.yaml` — реестр мигрировавших задач (п. 4.9);
3. отчёт `migration-colors-report.json` + человекочитаемый `.md` — всё, что требует
   ручного разбора (п. 4.10).

### 4.2. Источник идентификатора задачи Jira — таблица в секции «История изменений»

Центральный механизм модуля. Описан подробно, потому что нигде больше не задокументирован.

В начале каждой страницы Confluence есть секция «История изменений» с таблицей,
содержащей столбцы: **дата**, **описание**, **автор**, **задача в Jira**.

Ключевое правило оформления: **текст в столбце «описание» написан тем же цветом, что и
требования, внесённые этой задачей на странице.** Отсюда алгоритм:

```
цвет фрагмента требования
   → строка таблицы «История изменений», где текст описания имеет тот же цвет
      → значение столбца «Задача в Jira» этой строки
         → идентификатор задачи
```

**а) Порядок в пайплайне — критично.** Раздел «История изменений» по умолчанию удаляется.
Разбор таблицы и построение карты `цвет → задача` обязаны выполняться **до** шага удаления
раздела. Обеспечить это явно, а не полагаться на текущий порядок вызовов.

Сохранять ли сам раздел в итоговом markdown — отдельное решение, вынести в конфиг.
Рекомендация: на время переходного периода сохранять (это обоснование проставленных
маркеров), после — отключить, поскольку роль журнала изменений переходит к истории Git.

**б) Идентификация столбцов.** Только по тексту заголовка, приведённому к нормальной форме
(нижний регистр, схлопнутые пробелы, унификация `е`/`ё`). **Никогда по порядковому номеру** —
порядок столбцов на разных страницах отличается. Варианты написания заголовков вынести в конфиг.

**в) Извлечение цвета строки.** Цвет берётся из разметки ячейки «описание». Возможные формы:

```xml
<span style="color: rgb(153,102,255);">текст</span>
<span style="color:#9966ff">текст</span>
<font color="#9966ff">текст</font>
```

Нормализовать к каноническому виду (см. п. 4.3).

**г) Извлечение идентификатора Jira.** Встречается минимум в трёх формах — реализовать
цепочку резолверов с fallback:

```xml
<!-- 1. макрос Jira -->
<ac:structured-macro ac:name="jira">
  <ac:parameter ac:name="key">GBO-12345</ac:parameter>
</ac:structured-macro>

<!-- 2. гиперссылка -->
<a href="https://jira.corp.local/browse/GBO-12345">GBO-12345</a>

<!-- 3. простой текст -->
GBO-12345
```

Финальный fallback — регулярное выражение `\b[A-Z][A-Z0-9]{1,9}-\d+\b` по текстовому
содержимому ячейки. Если найдено несколько идентификаторов — все сопоставляются одному
цвету (допустимо: серия задач одного цвета); для маркеров используется первый,
в отчёт пишется предупреждение.

Реальные примеры разметки прилагаются к постановке отдельно — резолверы писать на их
основе, каждую форму покрыть тестом.

**д) Постраничность карты.** Карта `цвет → задача` строится **заново для каждой страницы**
и никогда не переиспользуется между страницами: один и тот же оттенок на разных страницах
означает разные задачи. Кэширование карты между страницами — ошибка.

**е) Коллизии.** Если одному цвету в таблице соответствует несколько строк с разными
задачами (цвет переиспользован после закрытия предыдущей задачи) — выбрать строку с
наиболее поздней датой, пометить сопоставление как `confidence: low`, записать в отчёт
все варианты.

**ж) Неразрешённый цвет.** Цвет есть в теле страницы, но отсутствует в таблице истории.
Подставить плейсхолдер `UNKNOWN-<hex-без-решётки>` (например, `{++UNKNOWN-9966ff: текст++}`),
записать в отчёт. Плейсхолдер обязан проходить синтаксис маркера, но проваливать линтер —
чтобы такие места нельзя было слить в `main`.

### 4.3. Определение «чёрного»

Источник истины — набор `black_colors` из существующего `style_utils.py`:

```python
black_colors = {
    'black', '#000', '#000000',
    'rgb(0,0,0)', 'rgb(0, 0, 0)',
    'rgba(0,0,0,1)', 'rgba(0, 0, 0, 1)',
    'rgb(51,51,0)', 'rgb(51, 51, 0)',
    'rgb(0,51,0)', 'rgb(0, 51, 0)',
    'rgb(0,51,102)', 'rgb(0, 51, 102)',
    'rgb(51,51,51)', 'rgb(51, 51, 51)',
    'rgb(23,43,77)', 'rgb(23, 43, 77)'
}
```

Утверждённым (без маркера) считается текст, у которого нет атрибута цвета вообще либо цвет
входит в этот набор.

**Обязательная доработка — нормализация.** Сравнение сейчас идёт по литеральным строкам,
и набор покрывает не все формы записи одного и того же цвета. Например, `rgb(51,51,51)`
в наборе есть, а эквивалентный `#333333` — нет; то же для `rgb(23,43,77)` и `#172b4d`
(цвет основного текста Confluence). Если на каких-то страницах цвет отдаётся в hex,
такой текст будет ошибочно распознан как цветной, что даст лавину ложных маркеров.

Требуется:

1. функция нормализации любого представления цвета к каноническому `#rrggbb`
   (поддержать: `black` и другие именованные, `#rgb`, `#rrggbb`, `rgb()`, `rgba()`,
   произвольные пробелы, любой регистр);
2. сравнение с `black_colors` **после** нормализации обеих сторон;
3. набор `black_colors` не переписывать, а расширять — он собран на реальных данных;
   изменения согласовывать отдельно.

Дополнительно: **вывести в отчёт все встреченные цвета с частотами** и результатом
классификации (чёрный / сопоставлен задаче / не разрешён). Это диагностика для калибровки
набора после первого прогона.

**Первый прогон выполняется в режиме «только отчёт», без записи файлов.** Предусмотреть
соответствующий ключ запуска.

### 4.4. Правила конвертации

| Разметка в Confluence | Результат |
|---|---|
| цветной текст | `{++ID: текст++}` |
| цветной зачёркнутый текст (`<s>`, `<del>`, `text-decoration: line-through`) | `{--ID: текст--}` |
| цветной зачёркнутый + сразу за ним цветной обычный, **один и тот же цвет** | два отдельных маркера `{--ID: старое--}{++ID: новое++}` |

**Не пытаться автоматически схлопывать в `{~~старое~>новое~~}`.** Конструкция замены
остаётся для ручного использования аналитиками; автоматическое распознавание «это была
замена, а не удаление плюс вставка» ненадёжно и даёт неверный результат на границах
предложений.

Пробелы внутри маркера значимы: при вставке слова в середину предложения хвостовой пробел
должен попасть **внутрь** маркера (`{++ID: действующая ++}организация`), иначе после
отбрасывания правки останется двойной пробел. Реализовать нормализацию пробелов на
границах маркера, покрыть тестом.

### 4.5. Вложенность цветов

**Случай:** фрагмент одного цвета содержит внутри себя фрагмент другого цвета. Типовой
сценарий — задача B зачеркнула текст, добавленный ещё не вышедшей задачей A, и написала
свой вариант.

CriticMarkup вложенность не поддерживает, и поддерживать её не требуется. Правило уплощения:

> **В `{--…--}` и в левую часть `{~~старое~>новое~~}` попадает только текст, реально
> существующий на промышленном контуре (то есть бывший чёрным). Зачёркнутый черновик
> другой задачи не переносится вообще.**

Обоснование: такой текст никогда не был на ПРОМ и никогда там не будет. Его единственная
ценность — след «задача B переиграла предложение задачи A» — сохраняется в истории Git.

Алгоритм для вложенного фрагмента:

1. взять внешние границы всей вложенной конструкции;
2. отбросить зачёркнутый текст, принадлежавший другой (внешней) задаче;
3. обернуть результирующий текст **целиком** в один маркер с идентификатором
   **внутренней**, то есть более поздней задачи;
4. **обязательно** записать в отчёт: файл, строку, все задействованные номера задач,
   исходный HTML-фрагмент до конвертации.

Пример:

```
Исходно (розовый = GBO-12345, зелёный = GBO-67890):
  <розовый>Организация должна быть <зелёный><s>головной</s>действующей и головной</зелёный></розовый>.

Результат:
  {++GBO-67890: Организация должна быть действующей и головной++}.

В отчёт:
  вложенность GBO-12345 ⊃ GBO-67890, уплощено под GBO-67890, требуется проверка аналитиком
```

Автоматическое разрешение считается **черновым**: аналитик проходит по отчёту и решает,
оставить уплощение или переразметить фрагмент на два независимых требования.

### 4.6. Таблицы, конвертированные в markdown

Маркер на отдельной строке внутри markdown-таблицы ломает синтаксис таблицы. Поэтому:

| Что изменилось | Как размечается |
|---|---|
| изменение **внутри ячейки** | обычный CriticMarkup прямо в ячейке |
| добавлена **целая строка** | строка пишется как есть, в служебный столбец `status` → `+GBO-12345` |
| удалена **целая строка** | строка остаётся на месте, в `status` → `-GBO-12345` |

Служебный столбец добавляется последним; его имя вынести в конфиг. Если в таблице нет ни
одной размеченной строки — столбец не добавлять.

Пример (матрица контролей: строки — проверки, столбцы — группы триггеров, «V» на пересечении):

```markdown
| ID | Атрибут | Проверка | Сообщение | Гр.1 | Гр.2 | Гр.3 | status |
|----|---------|----------|-----------|------|------|------|--------|
| C-014 | <дата заявки> | Не ранее текущей даты | Дата некорректна | V | V |  |  |
| C-015 | <лимит> | Не превышает лимит продукта | Превышен лимит | V | {++GBO-12345: V++} | V |  |
| C-016 | <организация> | Организация действующая | Организация не действует | V |  |  | +GBO-12345 |
```

Здесь C-015 распространён на группу 2 (правка внутри ячейки), C-016 — новый контроль
целиком (правка на уровне строки).

### 4.7. Таблицы, сохранённые как сырой HTML

Существующий пайплайн часть таблиц оставляет сырым HTML (markdown это допускает).
**CriticMarkup внутри блока сырого HTML не работает** — markdown-расширения не разбирают
содержимое HTML-островов, и в отрисованном виде будет виден литерал `{++GBO-12345: …++}`.

Поэтому внутри сохранённых HTML-таблиц разметка ведётся HTML-средствами:

```html
<span class="critic-ins" data-task="GBO-12345">действующая </span>
<span class="critic-del" data-task="GBO-12345">старый текст</span>
<tr class="critic-row-ins" data-task="GBO-12345"> … </tr>
<tr class="critic-row-del" data-task="GBO-12345"> … </tr>
```

Операции `critic.py` для этой нотации:

| Конструкция | `apply <ID>` | `reject <ID>` |
|---|---|---|
| `<span class="critic-ins" data-task="ID">` | снять обёртку, содержимое оставить | удалить вместе с содержимым |
| `<span class="critic-del" data-task="ID">` | удалить вместе с содержимым | снять обёртку, содержимое оставить |
| `<tr class="critic-row-ins" data-task="ID">` | снять `class` и `data-task` | удалить строку целиком |
| `<tr class="critic-row-del" data-task="ID">` | удалить строку целиком | снять `class` и `data-task` |

Разбор HTML-нотации выполнять парсером разметки, а не регулярными выражениями:
атрибуты могут идти в произвольном порядке, содержимое — быть вложенным.

Классы `critic-ins` / `critic-del` совпадают с теми, что генерирует `pymdownx.critic`,
поэтому подсветка обеими нотациями обеспечивается одним набором CSS.

### 4.8. Защита существующего синтаксиса

Нотация аналитики использует символы, конфликтующие с разметкой. Регулярные выражения
обязаны это учитывать, тесты — покрывать:

- `{{сервис:элемент}}` — смарт-ссылки; фигурные скобки не должны «съедаться» разбором
  маркеров и наоборот;
- `[Имя сущности]`, `[[КК_ВК] Заявка на выпуск карты]` — имена логических элементов
  в квадратных скобках, в том числе вложенных;
- `<атрибут сущности>`, `<Входные параметры>` — угловые скобки; при конвертации из XHTML
  их нельзя интерпретировать как теги, при выводе — экранировать по правилам, уже
  принятым в пайплайне;
- `→`, `->`, `=>`, `~>` — стрелки; `~>` входит в синтаксис замены CriticMarkup, проверить
  отсутствие конфликта с текстом требований;
- fenced code blocks — внутри них разметка не применяется и не разбирается.

### 4.9. Реестр мигрировавших задач

Конвертер формирует `migration-manifest.yaml`:

```yaml
migrated_at: 2026-08-15
service: КК
tasks:
  GBO-12345:
    color: "#9966ff"
    confidence: high
    pages: [DBO/КК_ВК_контроли, DBO/КК_ВК_форма]
    markers: 7
  UNKNOWN-a3c1f0:
    color: "#a3c1f0"
    confidence: unresolved
    pages: [DBO/КК_ВК_форма]
    markers: 2
```

Назначение: отличать мигрировавшие маркеры от созданных штатным процессом (п. 1.4),
измерять остаток переходного периода, служить входом для отчётности. Файл создаётся один
раз при миграции и далее не изменяется — фактическое состояние всегда вычисляется из
содержимого репозитория, манифест только фиксирует исходную точку.

### 4.10. Отчёт

Формат JSON (для последующей обработки) плюс генерируемый из него markdown (для аналитика).
Обязательные категории:

- страницы без секции «История изменений» либо с неразобранной таблицей;
- цвета, не найденные в таблице истории (плейсхолдеры `UNKNOWN-*`);
- коллизии «цвет → несколько задач»;
- вложенные конструкции, уплощённые автоматически;
- ячейки «Задача в Jira», из которых не удалось извлечь идентификатор;
- сводка всех встреченных цветов с частотами и итоговой классификацией (п. 4.3);
- статистика: страниц обработано / фрагментов размечено / позиций требует ручного разбора.

## 5. Модуль 2: `tools/critic.py` — применение и откат правок

CLI-утилита, ядро процесса. Используется и аналитиками вручную, и в CI.
От механизма публикации не зависит: работает с текстом markdown.

### 5.1. Команды

```
critic.py apply  <TASK-ID> [--path docs/] [--dry-run] [--report out.json]
critic.py reject <TASK-ID> [--path docs/] [--dry-run] [--report out.json]
critic.py apply-all  [--path docs/]
critic.py reject-all [--path docs/]
critic.py list [--path docs/] [--format json|md|text] [--manifest migration-manifest.yaml]
critic.py lint [--path docs/]
```

### 5.2. Семантика `apply <TASK-ID>`

Обрабатываются **только** маркеры указанной задачи; маркеры остальных задач остаются
нетронутыми. Это принципиально: штатное расширение `pymdownx.critic` умеет только
«принять всё разом», чего недостаточно, поскольку задачи выходят на ПРОМ независимо.
Именно поэтому применение и откат реализуются собственным кодом, а не расширением.

| Конструкция | `apply` | `reject` |
|---|---|---|
| `{++ID: текст++}` | `текст` | удаляется целиком |
| `{--ID: текст--}` | удаляется целиком | `текст` |
| `{~~ID: старое~>новое~~}` | `новое` | `старое` |
| строка markdown-таблицы, `status` = `+ID` | ячейка `status` очищается | строка удаляется |
| строка markdown-таблицы, `status` = `-ID` | строка удаляется | ячейка `status` очищается |
| HTML-нотация (п. 4.7) | см. таблицу в п. 4.7 | см. таблицу в п. 4.7 |

После обработки: если в markdown-таблице не осталось ни одного непустого значения
`status` — столбец удалить целиком.

### 5.3. Технические требования

- Многострочные маркеры (открыт на одной строке, закрыт через несколько абзацев).
- Содержимое fenced code blocks не обрабатывается.
- Файл без изменений **не перезаписывается**.
- `--dry-run` печатает список файлов и позиций, ничего не меняя.
- Ненулевой код возврата при любой неоднозначности: лучше остановиться, чем испортить текст.
- Некорректный или незакрытый маркер — прерывание с указанием файла и номера строки.

### 5.4. `list`

Отчёт «что не реализовано»: обход всех `.md`, сбор идентификаторов задач из маркеров,
столбцов `status` и HTML-нотации, группировка. Для каждой задачи — список файлов и строк.

При переданном `--manifest` дополнительно разделять задачи на **мигрировавшие** и
**новые** и выводить остаток переходного периода: сколько задач из манифеста ещё имеет
маркеры в репозитории. Замена ручного просмотра всех страниц в поисках цветного текста.

## 6. Модуль 3: линтер

Запускается в CI на каждый MR и командой `critic.py lint`.

**Ошибки (блокируют слияние):**

- литеральная вложенность маркеров `{++A: … {++B: …++} …++}` — разбор регулярными
  выражениями даст молча неверный результат, поэтому только hard fail;
- маркер без идентификатора задачи или с идентификатором, не удовлетворяющим маске;
- плейсхолдер `UNKNOWN-*` — остаток миграции, не разобранный аналитиком;
- незакрытый или некорректно вложенный маркер;
- маркер, разрывающий синтаксическую конструкцию: открыт внутри таблицы и закрыт за её
  пределами, разрывает элемент списка, попадает в fenced block;
- маркер внутри `{{сервис:элемент}}`;
- CriticMarkup внутри блока сырого HTML — там применяется HTML-нотация (п. 4.7).

**Предупреждения:**

- маркеры разных задач внутри одного предложения — сигнал проверить, объявлена ли
  зависимость задач в Jira;
- текст в `{--…--}` или в левой части `{~~…~>…~~}` буквально совпадает с содержимым
  вставки другой задачи в том же файле — нарушение правила п. 4.5, попавшее в файл
  в обход миграции;
- маркер, существующий дольше настраиваемого срока по дате коммита — «висящая» задача.

Формат вывода — совместимый с аннотациями GitLab CI: файл, строка, уровень, сообщение.

## 7. Модуль 4: представления (реализуется после выбора генератора сайта)

**Механизм публикации на момент постановки не зафиксирован.** Модули 1–3 от него не
зависят и должны быть реализованы независимо; настоящий модуль при смене генератора
переписывается целиком, поэтому вынесен в поздний этап.

Базовая идея не зависит от инструмента: из одного исходника получаются три представления.

| Представление | Как получается | Аудитория |
|---|---|---|
| текущий ПРОМ | `critic.py reject-all` → сборка | разработка, тестирование, смежные команды, аудит |
| целевое состояние | `critic.py apply-all` → сборка | архитектура, планирование |
| рабочее, с подсветкой правок | сборка с включённым `pymdownx.critic` в режиме `view` | аналитики — визуальный аналог сегодняшнего Confluence |

Если генератором будет MkDocs, `pymdownx.critic` (пакет PyMdown Extensions) даёт третье
представление из коробки: `markdown_extensions: - pymdownx.critic: mode: view`.
Отмечу известное ограничение этого расширения: разметка, выходящая за пределы одного
абзаца или инлайна, в режиме `view` может давать некорректный HTML — что дополнительно
обосновывает правило линтера о запрете маркеров, разрывающих синтаксические конструкции.

Требования при любой реализации:

- операции над рабочей копией выполняются во временном каталоге либо откатываются между
  сборками — рабочее дерево не должно оставаться изменённым;
- сборки независимы, падение одной не блокирует остальные;
- подсветка правок разными цветами по номерам задач — низкий приоритет, косметика:
  `pymdownx.critic` красит все правки одинаково, что для старта приемлемо.

## 8. Модуль 5: автоматизация подтверждения (последний этап)

Реализуется **после** того, как модули 1–3 отработали на реальных данных, и **после**
решения по развилке из п. 1.5: если маркеры признаны временным явлением, автоматизация
может не окупиться и достаточно ручного запуска.

Scheduled pipeline в GitLab, ежедневно:

1. `critic.py list` → множество идентификаторов задач в репозитории;
2. по каждому — запрос в Jira REST (`/rest/api/2/issue/{key}?fields=status`),
   токен только на чтение;
3. для задач в статусе «Установлено на ПРОМ»:
   - ветка `chore/approve-<TASK-ID>` от `main`;
   - `critic.py apply <TASK-ID>`;
   - коммит `<TASK-ID>: подтверждение требований (установлено на ПРОМ)`;
   - push и создание MR через GitLab API (`POST /api/v4/projects/{id}/merge_requests`),
     назначенный на аналитика сервиса;
4. если MR для этой задачи уже существует — пропустить (идемпотентность).

Аналитик утром видит готовый MR, diff которого читается однозначно как «что стало чёрным»:

```diff
- ...связана хотя бы одна {++GBO-12345: действующая ++}организация.
+ ...связана хотя бы одна действующая организация.
```

Соответствие «аналитик → сервис» брать из YAML-справочника в репозитории, не из Jira.

**Опрос Jira по расписанию, а не вебхук.** Вебхук требует настройки на стороне Jira и
сетевого доступа Jira → GitLab; опрос требует только доступа GitLab → Jira. Вебхук —
возможное улучшение в будущем, в настоящей постановке не реализуется.

## 9. Тесты

Обязательное покрытие; каждый пункт — отдельный тест.

**Конвертация:**

1. Вставка одного слова в середину предложения с корректной обработкой пробелов
   (пример из п. 1.2).
2. Вставка целого абзаца.
3. Вставка целого раздела с заголовком.
4. Цветное зачёркивание чёрного (бывшего на ПРОМ) текста.
5. Вложенность двух цветов (пример из п. 4.5) — проверить результат и запись в отчёт.
6. Markdown-таблица: новая строка, удалённая строка, правка внутри ячейки, комбинация.
7. Сохранённая HTML-таблица: те же три случая в HTML-нотации (п. 4.7).
8. Страница без секции «История изменений».
9. Цвет, отсутствующий в таблице истории → плейсхолдер `UNKNOWN-*` + отчёт.
10. Все три формы идентификатора Jira (макрос, href, простой текст).
11. Нормализация цвета: `#333333`, `rgb(51,51,51)`, `RGB(51, 51, 51)`, `#333` —
    все классифицируются как чёрный.
12. Цвет, отсутствующий в `black_colors`, — порождает маркер.
13. Фрагмент, содержащий `{{сервис:элемент}}`, `[Имя]`, `<атрибут>` и стрелки.
14. Корректность `migration-manifest.yaml` на странице с тремя задачами.

**`critic.py`:**

15. `apply` для одной задачи не трогает маркеры других задач в том же файле и той же строке.
16. `apply` + `reject` одной задачи на исходном файле → исходный файл.
17. Повторный `apply` → файл не изменился (идемпотентность).
18. Многострочный маркер.
19. Маркер внутри fenced code block — не обрабатывается.
20. Удаление столбца `status` при обнулении всех его значений.
21. HTML-нотация: атрибуты в произвольном порядке, вложенное содержимое.
22. Файл с CRLF — переводы строк сохранены.
23. `list --manifest` корректно разделяет мигрировавшие и новые задачи.

**Линтер:** по одному тесту на каждое правило из п. 6.

## 10. Порядок реализации

Строго по этапам, с прогоном на реальных данных между ними.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| 1 | `critic.py`: `apply` / `reject` / `apply-all` / `reject-all`, обе нотации | тесты 15–22 зелёные; аналитик может запускать вручную |
| 2 | Линтер + подключение в CI | тесты п. 6 зелёные, MR с плохой разметкой не сливается |
| 3 | Извлечение цвета, манифест, отчёт | прогон на одном сервисе в режиме «только отчёт», отчёт разобран аналитиком |
| 4 | Боевой прогон миграции сервиса | markdown в `main`, число позиций ручного разбора известно |
| 5 | `critic.py list` + страница «Незавершённые задачи» | видно, сколько мигрировавших задач осталось |
| 6 | Представления (после выбора генератора сайта) | три представления собираются и корректно различаются |
| 7 | Автоматизация подтверждения (после решения по п. 1.5) | MR создаётся без участия аналитика |

Этап 1 выполняется первым намеренно: он даёт работоспособный процесс до того, как написан
конвертер, и позволяет проверить нотацию на живой работе. Если нотация окажется неудобной,
переделывать придётся сотню строк, а не результат прогона по всему сервису.

## 11. Чего делать не нужно

Перечислено явно, потому что это неочевидные тупики.

1. **Не писать рекурсивный парсер вложенных маркеров.** Вложенность запрещена линтером
   и уплощается на миграции. Её поддержка потребовала бы собственного рендерера вместо
   `pymdownx.critic` и сделала бы исходники нечитаемыми в редакторе.
2. **Не использовать `pymdownx.critic` для `apply` / `reject`.** Расширение умеет только
   «всё разом» и работает на этапе рендеринга HTML, а нужна операция над исходным markdown
   по конкретной задаче. Расширение задействуется только для представления с подсветкой.
3. **Не обращаться к Jira из конвертера.** См. п. 2.2.
4. **Не пытаться автоматически распознавать замену** `{~~старое~>новое~~}` при
   конвертации. См. п. 4.4.
5. **Не менять существующую логику конвертации таблиц** (выбор между markdown и сырым
   HTML) и не переписывать `black_colors` — только расширять и добавлять нормализацию.
6. **Не хранить утверждённые и неутверждённые требования в разных файлах или разных
   долгоживущих ветках.** Единственный источник истины — файл в `main`.
7. **Не нормализовать переводы строк и не переформатировать markdown** при обработке.
   Скрипт меняет только то, что относится к маркерам: иначе diff становится нечитаемым
   и теряется главное преимущество схемы — MR подтверждения должен показывать ровно
   «что стало чёрным».
8. **Не закладываться архитектурно ни на один из вариантов развилки п. 1.5** и ни на
   один конкретный генератор сайта.
