# Постановка задачи: пофрагментный статус требований при переходе на Doc as Code

> Документ предназначен для кодового агента с полным доступом к исходникам репозитория.
> Агент не участвовал в проектировании, поэтому раздел «Контекст» читать обязательно —
> без него смысл требований к коду не восстанавливается.

---

## 1. Контекст

### 1.1. Что происходит

Управление переводит аналитику системы ДБО для юридических лиц с Confluence на Doc as Code:
требования описываются в markdown-файлах, хранятся в GitLab, публикуются через MkDocs.

### 1.2. Как статус требования фиксируется сейчас (Confluence)

Все изменения на странице делаются **цветом**, соответствующим текущей задаче Jira
(например, GBO-12345 — сиреневый, GBO-67890 — зелёный). После ввода в эксплуатацию
(переход задачи в статус «Установлено на ПРОМ») аналитик вручную сбрасывает цвет в чёрный.

Следствия:

- **чёрный текст** = действующий функционал на промышленном контуре (утверждённые требования);
- **цветной текст** = изменение в рамках незавершённой задачи (ещё не реализовано);
- **цветной зачёркнутый текст** = требование, удаляемое в рамках задачи.

Гранулярность цвета — произвольная: цветом может быть выделен целый раздел, абзац, строка
таблицы, ячейка или **одно слово внутри предложения**. Последний случай — массовый.

Пример (типовой):

```
На ПРОМ:  Проверяется, что с пользователем связана хотя бы одна организация.
Стало:    Проверяется, что с пользователем связана хотя бы одна ДЕЙСТВУЮЩАЯ организация.
                                                                 ^^^^^^^^^^^^ цвет GBO-12345
```

За словом «действующая» на логическом уровне стоит обращение к системному справочнику
за статусом организации, то есть это полноценное требование, а не стилистическая правка.

### 1.3. Что должно получиться после перехода

Цвет заменяется на **CriticMarkup** — стандартную нотацию правок в Markdown, дополненную
обязательным префиксом с номером задачи Jira:

| Смысл | Нотация | Аналог в Confluence |
|---|---|---|
| вставка (новое требование) | `{++GBO-12345: текст++}` | цветной текст |
| удаление (требование убирается) | `{--GBO-12345: текст--}` | цветной зачёркнутый текст |
| замена формулировки | `{~~GBO-12345: старое~>новое~~}` | зачёркнутое + новое, одним цветом |

Файл в `main` содержит **полную картину**: и утверждённые требования (чистый текст),
и неутверждённые (внутри маркеров). Разные представления получаются на сборке, а не
хранением разных версий файла.

### 1.4. Целевой процесс

1. Аналитик пишет требование новой задачи, обернув его в маркер с номером задачи. Ветка → MR → `main`.
2. Пока задача не на ПРОМ, маркер лежит в `main`. Требование видно на сайте «целевое состояние»
   и не видно на сайте «текущий ПРОМ».
3. Задача выходит на ПРОМ → маркеры этой задачи механически снимаются по всему репозиторию,
   создаётся MR «подтверждение требований», аналитик его сливает. Это автоматическая замена
   сегодняшнего ручного «сброса цвета в чёрный».
4. Задача отменена → маркеры этой задачи откатываются (вставки удаляются, удаления
   восстанавливаются, замены возвращаются к старой формулировке).

## 2. Жёсткие ограничения

Нарушение любого из пунктов делает решение неприменимым.

1. **Закрытый контур.** Нет доступа в интернет. Все зависимости должны быть либо из stdlib,
   либо из уже присутствующих в контуре пакетов. Перед добавлением новой зависимости —
   проверить, решается ли задача имеющимися средствами. `GitPython` и `python-gitlab`
   использовать **не** нужно: достаточно `subprocess` + `git` и `requests`.
2. **Jira недоступна на этапе миграции.** Конвертер Confluence → Markdown не имеет права
   обращаться к Jira ни в каком виде: ни за статусом задачи, ни за зависимостями, ни за
   проверкой существования идентификатора. Идентификаторы задач извлекаются исключительно
   из содержимого самой страницы Confluence (см. п. 4.2).
3. **Кроссплатформенность.** Разработка ведётся в Windows (PyCharm), CI выполняется в Linux.
   Пути — только через `pathlib`. Переводы строк — сохранять исходные (не нормализовать
   молча CRLF → LF, иначе diff в git будет содержать весь файл целиком). Кодировка —
   везде явно `encoding="utf-8"`.
4. **Никаких потерь данных.** Любой фрагмент, который скрипт не смог однозначно
   интерпретировать, должен попасть в отчёт с указанием файла, строки и исходного фрагмента.
   Молчаливое отбрасывание — критическая ошибка.
5. **Идемпотентность.** Повторный запуск любой операции на уже обработанном файле не должен
   менять файл.

## 3. Что уже есть в репозитории

Перед началом работы **исследовать существующий код** и встроиться в него, а не создавать
параллельную структуру. В частности, в репозитории уже присутствуют:

- пайплайн миграции Confluence → Markdown (модули разбора разделов, генерации карточек,
  сборки манифеста, резолвинга ссылок между карточками);
- плагин MkDocs, резолвящий смарт-ссылки вида `{{сервис:элемент}}` в обычные markdown-ссылки,
  с корректной обработкой fenced code blocks и `use_directory_urls`.

Задача агента: **определить фактические точки расширения** этого пайплайна и добавить
обработку цвета как ещё один шаг, переиспользуя существующие парсеры storage format,
конфигурацию, логирование и стиль кода. Структуру каталогов и имена модулей ниже считать
рекомендацией, а не предписанием — приоритет у сложившихся в репозитории соглашений.

## 4. Модуль 1: извлечение цвета при миграции

### 4.1. Вход и выход

**Вход:** Confluence storage format (XHTML), получаемый существующим пайплайном через
REST API (`/rest/api/content/{id}?expand=body.storage`).

**Выход:**
1. markdown-файл, где цветные фрагменты заменены на CriticMarkup с номерами задач;
2. отчёт `migration-colors-report.json` (+ человекочитаемый `.md`) о всём, что потребует
   ручного разбора.

### 4.2. Источник идентификатора задачи Jira — секция «История изменений»

Это центральный механизм модуля. Описан подробно, потому что нигде больше не задокументирован.

В начале каждой страницы Confluence есть секция «История изменений» с таблицей,
содержащей столбцы: **дата**, **описание**, **автор**, **задача в Jira**.

Ключевое правило оформления: **текст в столбце «описание» написан тем же цветом, что и
требования, внесённые этой задачей на странице.** Отсюда алгоритм:

```
цвет фрагмента требования
   → строка таблицы «История изменений», где текст описания имеет тот же цвет
      → значение столбца «Задача в Jira» этой строки
         → идентификатор задачи
```

Требования к реализации:

**а) Поиск секции.** Заголовок может варьироваться («История изменений», «История версий»,
«Изменения»). Поиск — регистронезависимый, по нормализованной строке, с настраиваемым
списком вариантов в конфиге. Если секция не найдена — страница целиком уходит в отчёт,
конвертация цвета для неё не выполняется.

**б) Идентификация столбцов.** Только по тексту заголовка (нормализованному:
lowercase, схлопнутые пробелы, убранные `ё`/`е`-различия), **никогда по порядковому номеру** —
порядок столбцов на разных страницах отличается.

**в) Извлечение цвета строки.** Цвет берётся из разметки ячейки «описание». Возможные формы:

```xml
<span style="color: rgb(153,102,255);">текст</span>
<span style="color:#9966ff">текст</span>
<font color="#9966ff">текст</font>
```

Цвет нормализовать к каноническому виду `#rrggbb` в нижнем регистре.

**г) Извлечение идентификатора Jira.** Встречается минимум в трёх формах — реализовать
цепочку резолверов с fallback:

```xml
<!-- 1. макрос Jira -->
<ac:structured-macro ac:name="jira">
  <ac:parameter ac:name="key">GBO-12345</ac:parameter>
</ac:structured-macro>

<!-- 2. гиперссылка -->
<a href="https://jira.corp.local/browse/GBO-12345">GBO-12345</a>

<!-- 3. простой текст -->
GBO-12345
```

Финальный fallback — регулярное выражение `\b[A-Z][A-Z0-9]{1,9}-\d+\b` по текстовому
содержимому ячейки. Если в ячейке найдено несколько идентификаторов — все они
сопоставляются одному цвету (это допустимо: серия задач одного цвета); в отчёт пишется
предупреждение, для маркеров используется первый.

Полный набор реальных примеров разметки будет предоставлен отдельно — резолверы писать
на их основе, покрыв каждую форму тестом.

**д) Постраничность карты.** Карта `цвет → задача` строится **заново для каждой страницы**
и никогда не переиспользуется между страницами. Один и тот же оттенок на разных страницах
означает разные задачи. Кэширование карты между страницами — ошибка.

**е) Коллизии.** Если одному цвету в таблице соответствует несколько строк с разными
задачами (цвет переиспользован после закрытия предыдущей задачи) — выбрать строку с
наиболее поздней датой, пометить сопоставление как `confidence: low` и записать в отчёт
все варианты.

**ж) Неразрешённый цвет.** Цвет присутствует в теле страницы, но отсутствует в таблице
истории. Подставить плейсхолдер `UNKNOWN-<без-решётки-hex>` (например,
`{++UNKNOWN-9966ff: текст++}`), записать в отчёт. Плейсхолдер обязан проходить синтаксис
маркера, но проваливать линтер — чтобы такие места нельзя было слить в `main`.

### 4.3. Определение «чёрного»

Утверждённым (без маркера) считается текст, у которого:

- нет атрибута цвета вообще; либо
- цвет входит в список «чёрных» из конфига.

В список по умолчанию включить `#000000`, `#172b4d`, `#333333`, `#181818` и близкие —
Confluence и его темы подставляют несколько оттенков «основного текста», и трактовка их
как цветных даст лавину ложных маркеров. Дополнительно предусмотреть настраиваемый порог
близости к чёрному (по евклидову расстоянию в RGB, значение по умолчанию подобрать на
реальных страницах).

Список цветов, реально встреченных при прогоне, выводить в отчёт с частотами — это позволит
аналитику откалибровать конфиг после первого запуска.

### 4.4. Правила конвертации

| Разметка в Confluence | Результат |
|---|---|
| цветной текст | `{++ID: текст++}` |
| цветной зачёркнутый текст (`<s>`, `<del>`, `text-decoration: line-through`) | `{--ID: текст--}` |
| цветной зачёркнутый + сразу за ним цветной обычный, **один и тот же цвет** | два отдельных маркера `{--ID: старое--}{++ID: новое++}` |

Отдельно: **не пытаться автоматически схлопывать в `{~~старое~>новое~~}`**. Конструкция
замены остаётся для ручного использования аналитиками; автоматическое распознавание
«это была замена, а не удаление плюс вставка» ненадёжно и даёт неверный результат на
границах предложений.

Пробелы внутри маркера значимы: при вставке слова в середину предложения хвостовой пробел
должен попасть **внутрь** маркера (`{++ID: действующая ++}организация`), иначе после
отбрасывания правки останется двойной пробел. Реализовать нормализацию пробелов на границах
маркера и покрыть тестом.

### 4.5. Вложенность цветов

**Случай:** фрагмент одного цвета содержит внутри себя фрагмент другого цвета. Типовой
сценарий — задача B зачеркнула текст, который был добавлен ещё не вышедшей задачей A, и
написала свой вариант.

CriticMarkup вложенность не поддерживает, и поддерживать её не требуется. Правило уплощения:

> **В `{--…--}` и в левую часть `{~~старое~>новое~~}` попадает только текст, реально
> существующий на промышленном контуре (то есть бывший чёрным). Зачёркнутый черновик
> другой задачи не переносится вообще.**

Обоснование: такой текст никогда не был на ПРОМ и никогда там не будет. Его единственная
ценность — след «задача B переиграла предложение задачи A» — сохраняется в истории Git.

Алгоритм для вложенного фрагмента:

1. взять внешние границы всей вложенной конструкции;
2. отбросить зачёркнутый текст, принадлежавший другой (внешней) задаче;
3. обернуть оставшийся результирующий текст **целиком** в один маркер с идентификатором
   **внутренней**, то есть более поздней задачи;
4. **обязательно** записать в отчёт: файл, строка, все задействованные номера задач и
   исходный HTML-фрагмент до конвертации.

Пример:

```
Исходно (розовый = GBO-12345, зелёный = GBO-67890):
  <розовый>Организация должна быть <зелёный><s>головной</s>действующей и головной</зелёный></розовый>.

Результат:
  {++GBO-67890: Организация должна быть действующей и головной++}.

В отчёт:
  вложенность GBO-12345 ⊃ GBO-67890, уплощено под GBO-67890, требуется проверка аналитиком
```

Автоматическое разрешение считается **черновым**: аналитик проходит по отчёту и решает,
оставить уплощение или переразметить фрагмент на два независимых требования. Скрипт
никакие зависимости задач не проверяет и не создаёт (Jira недоступна).

### 4.6. Таблицы

Маркер, стоящий на отдельной строке внутри markdown-таблицы, ломает синтаксис таблицы.
Поэтому:

| Что изменилось | Как размечается |
|---|---|
| изменение **внутри ячейки** | обычный CriticMarkup прямо в ячейке |
| добавлена **целая строка** | строка пишется как есть, в служебный столбец `status` → `+GBO-12345` |
| удалена **целая строка** | строка остаётся на месте, в `status` → `-GBO-12345` |

Служебный столбец `status` добавляется последним. Имя столбца вынести в конфиг.
Если в таблице нет ни одной размеченной строки — столбец не добавлять.

Пример (матрица контролей: строки — проверки, столбцы — группы триггеров, «V» на пересечении):

```markdown
| ID | Атрибут | Проверка | Сообщение | Гр.1 | Гр.2 | Гр.3 | status |
|----|---------|----------|-----------|------|------|------|--------|
| C-014 | <дата заявки> | Не ранее текущей даты | Дата некорректна | V | V |  |  |
| C-015 | <лимит> | Не превышает лимит продукта | Превышен лимит | V | {++GBO-12345: V++} | V |  |
| C-016 | <организация> | Организация действующая | Организация не действует | V |  |  | +GBO-12345 |
```

Здесь C-015 распространён на группу 2 (правка внутри ячейки), C-016 — новый контроль
целиком (правка на уровне строки).

### 4.7. Защита существующего синтаксиса

Нотация аналитики уже использует символы, конфликтующие с разметкой. Регулярные выражения
обязаны это учитывать, тесты — покрывать:

- `{{сервис:элемент}}` — смарт-ссылки. Фигурные скобки не должны «съедаться» разбором
  маркеров и наоборот.
- `[Имя сущности]`, `[[КК_ВК] Заявка на выпуск карты]` — имена логических элементов
  в квадратных скобках, в том числе вложенных.
- `<атрибут сущности>`, `<Входные параметры>` — угловые скобки; при конвертации из XHTML
  их нельзя интерпретировать как теги, при выводе в markdown — экранировать по правилам,
  уже принятым в существующем пайплайне.
- `→`, `->`, `=>`, `~>` — стрелки. Символ `~>` является частью синтаксиса замены
  CriticMarkup; проверить, не порождает ли это конфликта с текстом требований, и при
  необходимости экранировать.
- Fenced code blocks — внутри них никакая разметка не применяется и не разбирается.
  В существующем плагине MkDocs эта логика уже реализована — переиспользовать её.

### 4.8. Отчёт

Формат JSON (для последующей обработки) + генерируемый из него markdown (для аналитика).
Обязательные категории записей:

- страницы без секции «История изменений»;
- цвета, не найденные в таблице истории (с плейсхолдерами `UNKNOWN-*`);
- коллизии «цвет → несколько задач»;
- вложенные конструкции, уплощённые автоматически;
- ячейки «Задача в Jira», из которых не удалось извлечь идентификатор;
- сводка: список всех встреченных цветов с частотами и итоговым сопоставлением;
- статистика: страниц обработано / фрагментов размечено / позиций требует ручного разбора.

## 5. Модуль 2: `tools/critic.py` — применение и откат правок

CLI-утилита, ядро всего процесса. Используется и аналитиками вручную, и в CI.

### 5.1. Команды

```
critic.py apply  <TASK-ID> [--path docs/] [--dry-run] [--report out.json]
critic.py reject <TASK-ID> [--path docs/] [--dry-run] [--report out.json]
critic.py apply-all  [--path docs/]     # для сборки сайта «целевое состояние»
critic.py reject-all [--path docs/]     # для сборки сайта «текущий ПРОМ»
critic.py list [--path docs/] [--format json|md|text]
critic.py lint [--path docs/]
```

### 5.2. Семантика `apply <TASK-ID>`

Обрабатываются **только** маркеры указанной задачи; маркеры всех остальных задач остаются
нетронутыми. Это принципиально: штатное расширение `pymdownx.critic` умеет только
«принять всё разом», чего недостаточно, поскольку задачи выходят на ПРОМ независимо.

| Конструкция | Результат `apply` | Результат `reject` |
|---|---|---|
| `{++ID: текст++}` | `текст` | удаляется целиком |
| `{--ID: текст--}` | удаляется целиком | `текст` |
| `{~~ID: старое~>новое~~}` | `новое` | `старое` |
| строка таблицы, `status` = `+ID` | ячейка `status` очищается | строка удаляется |
| строка таблицы, `status` = `-ID` | строка удаляется | ячейка `status` очищается |

После обработки: если в таблице не осталось ни одного непустого значения `status` —
столбец удалить целиком.

### 5.3. Технические требования

- Многострочные маркеры (маркер открыт на одной строке, закрыт через несколько абзацев).
- Содержимое fenced code blocks не обрабатывается.
- Файл, в котором изменений не было, **не перезаписывается** (иначе git увидит изменение
  mtime и, при неаккуратной работе с переводами строк, ложный diff).
- `--dry-run` печатает список файлов и позиций, ничего не меняя.
- Ненулевой код возврата при любой неоднозначности; лучше остановиться, чем испортить текст.
- Обработка файла с неизвестным / некорректным маркером — прерывание с указанием
  файла и номера строки.

### 5.4. `list`

Отчёт «что не реализовано»: обход всех `.md`, сбор идентификаторов задач из маркеров и
столбцов `status`, группировка. Для каждой задачи — список файлов и строк. Замена ручного
просмотра всех страниц в поисках цветного текста.

## 6. Модуль 3: линтер

Запускается в CI на каждый MR и командой `critic.py lint`.

**Ошибки (блокируют слияние):**

- литеральная вложенность маркеров: `{++A: … {++B: …++} …++}` — разбор регулярными
  выражениями даст молча неверный результат, поэтому только hard fail;
- маркер без идентификатора задачи или с идентификатором, не удовлетворяющим маске;
- плейсхолдер `UNKNOWN-*` (остаток миграции, не разобранный аналитиком);
- незакрытый или некорректно вложенный маркер;
- маркер, разрывающий синтаксическую конструкцию: открыт внутри таблицы и закрыт за её
  пределами, разрывает элемент списка, попадает в fenced block;
- маркер внутри `{{сервис:элемент}}`.

**Предупреждения:**

- маркеры разных задач внутри одного предложения — сигнал «проверьте, объявлена ли
  зависимость задач в Jira»;
- текст в `{--…--}` или в левой части `{~~…~>…~~}` буквально совпадает с содержимым
  вставки другой задачи в том же файле — нарушение правила из п. 4.5, попавшее в файл
  в обход миграции;
- маркер, существующий дольше настраиваемого срока (по дате коммита) — «висящая» задача.

Формат вывода — совместимый с аннотациями GitLab CI (файл, строка, уровень, сообщение).

## 7. Модуль 4: сборка сайтов

В `.gitlab-ci.yml` из одного и того же исходника собираются три сайта:

| Сайт | Как получается | Аудитория |
|---|---|---|
| `/prom/` | `critic.py reject-all` → `mkdocs build` | разработка, тестирование, смежные команды, аудит |
| `/next/` | `critic.py apply-all` → `mkdocs build` | архитектура, планирование |
| `/review/` | `mkdocs build` с `pymdownx.critic: mode: view` | аналитики — визуальный аналог сегодняшнего Confluence |

Требования:

- операции над рабочей копией выполняются во временном каталоге либо откатываются
  (`git checkout .`) между сборками — рабочее дерево не должно оставаться изменённым;
- сборки независимы, падение одной не блокирует остальные;
- `mkdocs.review.yml` наследует основной конфиг, отличаясь только режимом `critic`.

Опционально (низкий приоритет): плагин, раскрашивающий правки в разные цвета по номерам
задач — штатный `pymdownx.critic` красит все правки одинаково. Реализовывать в последнюю
очередь, это косметика.

## 8. Модуль 5: автоматизация подтверждения (последний этап)

Реализуется **после** того, как модули 1–4 отработали на реальных данных. Ранее — не начинать.

Scheduled pipeline в GitLab, ежедневно:

1. `critic.py list` → множество идентификаторов задач, присутствующих в репозитории;
2. по каждому — запрос в Jira REST (`/rest/api/2/issue/{key}?fields=status`), токен только
   на чтение;
3. для задач в статусе «Установлено на ПРОМ»:
   - ветка `chore/approve-<TASK-ID>` от `main`;
   - `critic.py apply <TASK-ID>`;
   - коммит `<TASK-ID>: подтверждение требований (установлено на ПРОМ)`;
   - push и создание MR через GitLab API (`POST /api/v4/projects/{id}/merge_requests`),
     назначенный на аналитика сервиса;
4. если MR для этой задачи уже существует — пропустить (идемпотентность).

Аналитик утром видит готовый MR, diff которого читается однозначно как «что стало чёрным»:

```diff
- ...связана хотя бы одна {++GBO-12345: действующая ++}организация.
+ ...связана хотя бы одна действующая организация.
```

Соответствие «аналитик → сервис» брать из YAML-справочника в репозитории, не из Jira.

**Опрос Jira по расписанию, а не вебхук.** Вебхук требует настройки на стороне Jira и
сетевого доступа Jira → GitLab; опрос требует только доступа GitLab → Jira, который
существует. Вебхук — возможное улучшение в будущем, в текущей постановке не реализуется.

## 9. Тесты

Обязательное покрытие. Ниже — минимальный набор кейсов, каждый должен быть отдельным тестом.

**Конвертация:**

1. Вставка одного слова в середину предложения, с корректной обработкой пробелов
   (пример с «действующая» из п. 1.2).
2. Вставка целого абзаца.
3. Вставка целого раздела с заголовком.
4. Цветное зачёркивание чёрного (бывшего на ПРОМ) текста.
5. Вложенность двух цветов (пример из п. 4.5) — проверить и результат, и запись в отчёт.
6. Таблица: новая строка, удалённая строка, правка внутри ячейки, комбинация всех трёх.
7. Страница без секции «История изменений».
8. Цвет, отсутствующий в таблице истории → плейсхолдер `UNKNOWN-*` + отчёт.
9. Все три формы идентификатора Jira (макрос, href, простой текст).
10. Цвет, близкий к чёрному, — не должен породить маркер.
11. Фрагмент, содержащий `{{сервис:элемент}}`, `[Имя]`, `<атрибут>` и стрелки.

**`critic.py`:**

12. `apply` для одной задачи не трогает маркеры других задач в том же файле и той же строке.
13. `apply` + `reject` одной и той же задачи на исходном файле → исходный файл.
14. Повторный `apply` → файл не изменился (идемпотентность).
15. Многострочный маркер.
16. Маркер внутри fenced code block — не обрабатывается.
17. Удаление столбца `status` при обнулении всех его значений.
18. Файл с CRLF — переводы строк сохранены.

**Линтер:** по одному тесту на каждое правило из п. 6.

## 10. Порядок реализации

Строго по этапам, с прогоном на реальных данных между ними.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| 1 | `critic.py`: `apply` / `reject` / `apply-all` / `reject-all` | тесты 12–18 зелёные; аналитик может запускать вручную |
| 2 | Линтер + подключение в CI | тесты п. 6 зелёные, MR с плохой разметкой не сливается |
| 3 | Модуль извлечения цвета + отчёт | прогон на одном реальном сервисе, отчёт разобран аналитиком |
| 4 | Три сборки сайтов в CI | три URL доступны и различаются корректно |
| 5 | `critic.py list` + генерация страницы «Незавершённые задачи» | страница в составе сайта |
| 6 | Автоматизация подтверждения через опрос Jira | MR создаётся без участия аналитика |

Этап 1 выполняется первым намеренно: он даёт работоспособный процесс ещё до того, как
написан конвертер, и позволяет проверить нотацию на живой работе.

## 11. Чего делать не нужно

Перечислено явно, потому что это неочевидные тупики:

1. **Не писать рекурсивный парсер вложенных маркеров.** Вложенность запрещена линтером и
   уплощается на миграции. Поддержка вложенности потребовала бы собственного рендерера
   вместо `pymdownx.critic` и сделала бы исходники нечитаемыми в редакторе.
2. **Не использовать `pymdownx.critic` для `apply`/`reject`.** Расширение умеет только
   «всё разом» и работает на этапе рендеринга HTML, а нужна операция над исходным markdown
   по конкретной задаче. Расширение задействуется только для сборки `/review/`.
3. **Не обращаться к Jira из конвертера.** См. п. 2.2.
4. **Не пытаться автоматически распознавать замену** (`{~~старое~>новое~~}`) при конвертации.
   См. п. 4.4.
5. **Не хранить утверждённые и неутверждённые требования в разных файлах или разных
   долгоживущих ветках.** Единственный источник истины — файл в `main`; представления
   получаются на сборке.
6. **Не нормализовать переводы строк и не переформатировать markdown** при обработке.
   Скрипт меняет только то, что относится к маркерам, — иначе diff становится нечитаемым
   и теряется главное преимущество схемы: MR подтверждения должен показывать ровно
   «что стало чёрным».
