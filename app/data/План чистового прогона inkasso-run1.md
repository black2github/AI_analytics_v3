# План чистового прогона inkasso-run1 (полный цикл «с нуля»)

Дата: 2026-08-17. Решение аналитика: вариант (а) — полный конвейер с
нуля на новой ветке, не докрытие exam-run1.

## Цель (двойная)

1. **Отдаточный комплект** src-inkasso-outgoing полного покрытия
   (160 страниц выгрузки) — кандидат на отдачу команде по модели
   обратной связи (MR inkasso-run1 → trunk).
2. **Валидация воспроизводимости канона** после пакета волн A–D и
   17 калибровок: репетиция mwqueue масштаба ×50. Метрика — новые
   находки на заход (ожидание: единицы против К-1…К-17/Э-1…Э-12
   экзамена) и доля заходов, принятых без дозахода.

## Правила прогона

- Ветка `inkasso-run1` — от `origin/trunk` (там sources без docs —
  чистый старт); exam-run1 не трогается (музей экзамена и протокола).
- **Заморозка канона — двухуровневая** (уточнение 2026-08-18 по вопросу
  аналитика; «канон» = весь `_meta`: методология + прибор + данные):
  - **заморожен МЕТОДОЛОГИЧЕСКИЙ СРЕЗ** — `git log -1 -- _meta/skills
    _meta/templates` = **225d5e8** (все принятые заходы собраны на нём);
    его изменение — только явным решением аналитика по блокеру, с
    записью здесь (прецеденты до первой приёмки: мини-волна Э-1/Э-2/Э-3
    6ccf569, чек-лист «На усм. арх.» 225d5e8; в ходе захода 5 — решение
    аналитика 2026-08-19: формула ТУЗ в шаблоне function выводится
    обычным шрифтом, не жирным — правка §2 «Доступность»);
  - **прибор (`_meta/tools`) из заморозки исключён**: дефекты и слепые
    зоны сторожей чинятся сразу (иначе фиктивная зелень живёт до конца
    прогона — прецедент К-20); HEAD o2new в промптах поэтому дрейфует —
    это норма и признак честного журнала;
  - версия в промпте — не заморозка, а СВЕРКА СВЕЖЕСТИ диска
    исполнителем (`git log -1`); при приёмке эксперт сверяет
    методологический срез, не HEAD.
  Находки — в протокол прогона; методология — пакетом после прогона.
- Минимальные промпты по шаблону захода/дозахода; изоляция прежняя.
- **Правило изоляции в промптах** (урок пилота-2, 2026-08-19): формула
  «остальные карточки не трогать» ВСЕГДА с оговоркой «служебные реестры
  (матрица трассировки, open-questions) — штатная зона правок». Запрет
  реестров при стороже «ссылка или долг В МАТРИЦЕ» создал противоречие,
  и исполнитель разрешил его маскировкой: удалил теги из дословного
  текста, уведя упоминания из зоны видимости сторожа (закрыто К-31
  гомоглифы / К-32 анти-дефейс).
- **Фиксированная слабая модель**: перед КАЖДЫМ запуском исполнителя
  проверить, что в Cursor выключен режим «Авто» (он самовключается при
  перезапуске агента и может подставить сильную LLM — метрика
  воспроизводимости обесценивается). Инцидент 2026-08-17: первый запуск
  захода 1 прошёл в Авто — выход не анализировался, сохранён локальной
  веткой inkasso-run1-probe-auto-llm для сравнения, стенд очищен,
  перезапуск.
- Приёмка захода: самопроверка OK → сверка эксперта (сторожа + глаза
  пользователя по файлам приёмки — канал, давший К-7/К-16/К-17) →
  коммит на inkasso-run1.
- Фаза 0 модели обратной связи: `.gitattributes` (`* text=auto`) —
  ПЕРВЫМ коммитом ветки, до генерации.

этом прогоне быть НЕ должно — полное покрытие, судьба «вне скоупа»
допустима только решением аналитика с записью).

## Контрольные точки

- После заходов 1–2: первая сверка темпа (находки/страница против
  экзамена) — решение о темпе приёмок (позаходно или пакетами).
- После партии функций 3–4: чекпоинт (объём наибольшего типа).
- После захода 15: полный selfcheck + coverage — вход в финал.
- Итог прогона — раздел в протоколе + решение об отдаче (MR).

## Ожидаемый выход

Комплект docs/ полного покрытия с вердиктом OK, feedback.md, MR
inkasso-run1 → trunk (не вливать до Approve), сводка для отчёта
пилота: «канон собрал полный сервис с нуля, находок X, дозаходов Y».
