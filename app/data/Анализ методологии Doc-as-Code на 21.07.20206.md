## Главное (bottom line)

Новый подход — **не конкурент нашим скиллам, а объемлющая рамка другого класса**: это мультиагентный SDLC (4 роли BA/SA + ревьюеры, HITL-гейты) с полным слоем BRD, которого у нас нет вообще, и с **централизацией всех связей в одной матрице трассировки**. Он методологически **чище ложится на «чистый» API First**, чем наш, в одном ключевом месте — но ценой потери двух вещей, которые мы делаем лучше: **явной привязки «поле → параметр вызова» и тождества реквизита в разных представлениях (наш DE-реестр)**. Прямых логических противоречий с doc-as-code / API First у него нет; есть **сознательный отказ** от части того, что мы фиксируем в требованиях, в пользу «контракт = граница, остальное — трассировка».

## Суть нового подхода (чтобы дальше было предметно)

- **Слои:** BRD (бизнес-аналитик) + SRS (системный аналитик) + API (генерируется из кода). Тела BRD и SRS **не ссылаются друг на друга** — единственная стыковка — `traceability-matrix.md`.
- **Матрица трассировки — единственный источник связей.** Markdown-ссылки в телах — только навигация. Связи «функция → SCR/ENT/CTL/PRN», «операция API ↔ артефакт SRS», «BRD → SRS» — все ровно один раз в матрице, с гейтами достаточности (счётчики «функций без US = 0» и т.п.).
- **forward-стиль docs/**: ни одной ссылки за пределы `docs/` (ни на код, ни на источники, ни на `_meta`). Комплект переносим целиком.
- **Контроли:** каталог `CTL` (бизнес-проверки данных заявки) + группы `CTL-GRP` (точки применения). **FE/BE-разделения нет.**
- **Экранные формы:** событийная модель (П-N/Е-N/B-N/М-N) — почти изоморфна нашей FR/EV/MSG.

## Три твои точки — разбор

### 1. Параметры вызовов методов ↔ поля формы

Твоя интуиция верна, и картина даже резче, чем «просто карточка метода — мало». В новом подходе (`conventions.md` §5.1): **«экранные формы не описывают вызовы методов и поля DTO»**. Внутренний метод сервиса в SRS не упоминается вообще; связь «операция ↔ артефакт» живёт только строкой матрицы на уровне *артефакта*, не поля.

Как они всё же не теряют маппинг полностью — через **опорную точку «физический атрибут сущности»**:

- у поля формы есть колонка «Атрибут» → `ENT-NNN.field` (точечная нотация);
- этот же `ENT-NNN.field` объявлен «стабильным ID атрибута, используемым в API-артефактах и тестах»;
- то есть join-ключ между SRS и контрактом — **физическое имя атрибута**, а не явная привязка `param = field`.

Что при этом теряется против нас:

- Связь восстановима **только для сохраняемых полей** (поле→атрибут→DTO по одинаковому имени). Для технических/платформенных параметров вызова (`digest`, `signature`, `certificateId` у подписи, которые мы в каноне заземлили по `SignCommand` из OpenAPI) — **в требованиях нет ничего**: форма лишь ссылается на PLT-функцию.
- Нет ответа на вопрос «что произойдёт с введённым значением при вызове X» на уровне требования — он вынесен в контракт и код.

Это **не дефект, а осознанная позиция «пуристского» API First**: контракт — граница, маппинг поле↔DTO — забота кода, проверяемая контрактными тестами; дублировать его в SRS — источник дрейфа. Наш подход — противоположный полюс: мы фиксируем `param = field` прямо в шаге события, потому что цель — трассируемость и генерация/ревью по требованиям. **Оба защитимы; это философская развилка, а не «кто-то неправ».**

### 2. Реестр атрибутов / представлений (наш DE-реестр)

Прямого аналога DE-реестра **нет**. Их модель данных — «только физически хранимые атрибуты», стабильный ID = `ENT-NNN.физимя`, **без отдельной нумерации реквизитов**. Тождество «один реквизит — много представлений» они якорят **на физический атрибут**: и ввод на вкладке 1, и отображение на вкладке 3 через колонку «Атрибут» указывают на один `ENT-NNN.field`.

Важное наблюдение: это **ровно тот «столбец на атрибуте» вариант, который наш rationale-документ DE рассматривал и отклонил**. Их решение платит теми же издержками, что мы описали:

- «обратный индекс» (где ещё показывается реквизит) **не хранится** — восстанавливается только grep’ом точечной нотации;
- реквизит, у которого нет физического атрибута (собирается формой, хранится позже; или части адреса в одну строку) — якорить не к чему;
- человекочитаемого «Организация вводится тут, показывается там под именем "Счёт"» из коробки нет — читатель сам сопоставляет по имени атрибута.

Так что здесь **наш DE-реестр объективно даёт то, чего у них нет** (см. п. 6).

### 3. Контроли: наш x-controls vs их модель

Здесь, наоборот, их разрез **чище нашего для API First**. У нас: `control-split` делит контроли на FE/BE и привязывает BE к методу через `x-controls`. У них FE/BE-разделения нет вовсе, а разрез другой:

- **transport-уровень** (обязательность/формат/nullable) → схема OpenAPI, генерится из Bean Validation кода;
- **бизнес-уровень** → карточки `CTL` в SRS;
- контракт **явно запрещает копировать алгоритмы контролей** — только ссылка на каталог; неуспех бизнес-проверки отдаётся в wrapper при HTTP 200.

Разрез «transport vs business» ложится на API First лучше нашего «FE/BE», потому что «на какой стороне выполняется проверка» — это **решение реализации**, которое API First считает выводимым из контракта, а не тем, что аналитик прописывает в требованиях. Ты сам отмечал, что часть команд к FE/BE-разделению не готова — их модель эту развилку просто обходит. Наш `x-controls` даёт явную привязку контроля к методу, но ценой попадания реализационной детали (сторона исполнения) в требования. Их централизация через матрицу + каталог CTL — **валидная и, вероятно, более устойчивая** альтернатива.

## Q1. Противоречия / дубликаты / двусмысленности с doc-as-code и API First

**Логических противоречий с doc-as-code и API First — нет.** Подход строго doc-as-code (markdown, ID, матрица, git-ветки) и корректно-API-First (контракт из кода как граница, SRS не дублирует DTO). Что есть:

- **Внутренняя двусмысленность API↔SRS-трассировки (единственная реальная).** Связь «операция ↔ артефакт» ведётся на уровне *артефакта*, а привязка «поле → атрибут» — на уровне *атрибута*. Между ними нет моста: по матрице нельзя дойти от параметра операции до поля экрана. Для чистого API First это by design, но как «полнота трассировки» — это разрыв гранулярности, который стоит проговорить явно (сейчас он неявный).
- **Не дубликат, а осознанный перенос ответственности:** маппинг поле↔DTO намеренно «живёт» в контракте, не в SRS. Риск — он не ревьюится аналитиком и держится только на совпадении имён атрибутов + контрактных тестах.
- **Мелкая терминологическая коллизия** для читателя, знающего оба подхода: `EXT` (справочник/сущность платформы) vs `EXTINT` (внешняя АС) vs `PLT` (платформенная функция) — три близких понятия; в их конвенциях разведены аккуратно, но порог входа высокий.

### Q2. «Один сервис — одна команда; команда — много сервисов»

**Противоречия нет, подход прямо на это спроектирован.** Переносимое ядро (`_meta/` + `.cursor/`) копируется в репозиторий каждого сервиса; `docs/` и `code/` — «проектная нагрузка», не переносится; проектная специфика вынесена в `90-project-*.mdc`, который заменяется под сервис. Матрица трассировки — пер-сервисная. То есть «один сервис = один комплект docs/ = один инстанс пайплайна» — ровно наша модель, и «команда ведёт N сервисов» = N репозиториев с одним ядром. Это **сильная сторона** их упаковки (у нас перенос ядра между репозиториями мы только что делали руками — у них это регламентировано в `PIPELINE.md`).

### Q3. Сложность конверсии наших скиллов под новые принципы

Разделю на «дёшево / средне / дорого» и отмечу вопросы к решению. **Ничего не делаю — только оценка.**

**Дёшево (косметика, 1–2 подхода правок):**

- Латинские ID у нас уже есть; их схема ID почти совпадает (у них `П/Е/B/М` кириллицей внутри ЭФ — расхождение, но это их локальное отступление от собственного же принципа латиницы).
- forward-стиль: наш событийный скилл в reverse рядом с исходником сознательно ставит исходные ссылки — под их правила нужен режим «в комплект» без внешних ссылок. У нас такой режим уже частично заложен («в SRS-комплекте — заглушки, ссылки только внутрь»).
- Разрез контролей: отказаться от FE/BE и `x-controls` в пользу «transport (контракт) + business (CTL)» — это скорее *упрощение* control-split, чем усложнение.

**Средне (структурные, но локальные):**

- **Матрица трассировки как единственный источник связей.** У нас связи распределены: ссылки в телах + DE-реестр + x-controls. Перенос на «один раз в матрице» затронет и событийный скилл (ссылки на CTL/ENT станут навигацией, трассировка уедет в матрицу), и control-split, и потребует нового скилла ведения матрицы с гейтами. **Дорого (новый объём):**

### Q6. Что у нас сделано лучше и что предложить новому подходу

**Сильные стороны нашего набора (кандидаты «предложить им»):**

1. **DE-реестр (сильнейший кандидат).** Решает то, чего их модель не умеет: тождество одного реквизита в N представлениях с разными именами полей, человекочитаемый обратный индекс, якорение реквизитов без физического атрибута. Ложится к ним **аддитивно** — как тонкий реестр рядом с моделью данных, не ломая «атрибут = join-ключ». Наш rationale-документ ровно под этот разговор и написан.
2. **Явная инициализация параметров вызовов, заземлённая в OpenAPI** — как *опциональное обогащение* для команд/случаев, где важна трассируемость «поле→параметр» (регуляторика, генерация, сложные подписи). Предложить не взамен их §5.1, а режимом «detailed calls».
3. **Машинные инварианты предпроверки** (биекции FR↔реестр, достижимость шагов, резолвинг ссылок, стабильные ID шагов как идентификаторы, а не номера). У них — DoD-чеклисты + grep-антирегрессия; наши структурные инварианты строже и реально прогоняются скриптом. Хороший вклад в их `review-artifact`/`artifact-consistency`.
4. **Общее ядро `_shared`** (нотация `=`/`==`, `→` только «найти запись», словарь UI-типов, чистота условия) — у них правила формата размазаны по 27 скиллам; вынесенное ядро сократило бы дублирование.

**Где лучше они (и что нам стоит перенять — обратный поток):**

1. **Мультиагентность с ревьюером и HITL-гейтами** — у нас нет контура качества, всё одноходово.
2. **Слой BRD целиком** — мы начинаем сразу с SRS/ЭФ, бизнес-обоснование теряется.
3. **Матрица трассировки как единый чек-пойнт связей с гейтами достаточности** — сильнее нашего распределённого хранения ссылок; убирает дрейф.
4. **Разрез контролей transport/business** — чище нашего FE/BE для API First.
5. **Регламент переноса ядра между репозиториями** (`PIPELINE.md`) — у нас это ручная операция.
6. **Отказ от поля `status` в документах** в пользу статусов в артефактах задачи — аккуратнее нашего.

| 5 | Наши машинные инварианты → их ревью | Предложение им | Средний | Дёшево, усиливает их DoD |
| 6 | Слой BRD + мультиагентность | Объём (дорого) | Низкий (стратегия) | Не «правка скилла», а смена класса системы |
| 7 | Кириллица `П/Е/B/М` vs латиница | Косметика | Низкий | Разрешается выбором канона |

**Резюме для решения:** прямых противоречий нет; новый подход — более зрелая рамка (BRD + ревью + централизация), в которую наши скиллы встраиваются как **специализированные исполнители SRS-слоя** с двумя ценными вкладами (DE-реестр, машинные инварианты) и одной философской развилкой, которую надо закрыть до любой конверсии (параметры вызовов). Рекомендую следующим шагом развести именно п.1 и п.2 — от них зависит, «подстраиваемся» мы или «дополняем».

Если хочешь, могу оформить это отдельным markdown-отчётом в репозитории или углубить любой из пунктов (например, детально расписать, как DE-реестр встраивается в их `data-model` без нарушения их принципов).

# Q и A

## биекции FR↔реестр, достижимость шагов, резолвинг ссылок

Поясняю все три инварианта — на конкретных примерах из наших же файлов.

## Контекст: почему это вообще инварианты

Событийный документ ЭФ — это по сути маленький граф с перекрёстными ссылками: поля (`FR-N`) объявляются в двух местах (реестр §2 и подразделы §4), шаги (`EV-N.M`) ссылаются друг на друга переходами, сообщения (`MSG-N`) ссылаются на шаги. «Инвариант» — это свойство, которое **обязано выполняться в корректном документе** и которое можно проверить **скриптом**, не читая смысл. Слабая модель (или уставший человек) легко его нарушает — а grep-проверка ловит мгновенно. Разберу три.

---

## 1. Биекция FR ↔ реестр

**Биекция** = взаимно однозначное соответствие: каждому элементу слева ровно один справа и наоборот, без «висяков» с обеих сторон.

Поле в событийном документе живёт **в двух местах**:

- строка в **реестре §2** («Реестр полей» — таблица-обзор: № / Блок / Поле / Тип / Обяз.);
- подраздел в **§4** («Правила полей» — `### FR-N. «Имя»` с деталями).

Инвариант требует: **множество FR в реестре = множество FR в подразделах**. Ни одного поля, которое объявлено в таблице, но не расписано в §4 (забыли описать). Ни одного `### FR-7`, которого нет в таблице (описали поле, но потеряли из обзора).

На нашей вкладке «Реквизиты ГК» проверка выглядит так — по факту она и отработала в моём прогоне:

```
FR-подразделов 20, строк реестра 20   ✓ мощности совпадают
{FR из реестра} == {FR из §4}          ✓ это одни и те же номера
```

Если бы в §4 был `### FR-21`, а в таблице максимум 20 строк — скрипт выдал бы `FR реестр!=подразделы: only sub [21]`. Это ловит типовую ошибку слабой LLM: добавила поле в детали, забыла в обзорную таблицу (или наоборот). Такое же правило у нас на **события**: каждое `EV-N` в сводной таблице §5 имеет детальный подраздел `### EV-N`, и наоборот.

Почему это важно именно машинно: реестр и §4 пишутся в разных частях документа, глазами рассинхрон между ними почти не виден — а для генерации кода/тестов «поле без правила» или «правило без поля» — это дыра.

---

## 2. Достижимость шагов

Событие (`### EV-1. Открытие формы`) — это процедура из шагов `EV-1.1, EV-1.2, …`. Шаги соединены **явными переходами**: `**то** — EV-1.10`, `**иначе** — EV-1.22`, диапазонами `выполняются шаги EV-1.15–EV-1.19`.

**Достижимость** = на каждый шаг (кроме первого в событии) существует хотя бы одна ведущая к нему ссылка. Если шаг `EV-1.13` физически написан в документе, но **ни один** переход и ни один диапазон на него не указывает — это «мёртвый код»: шаг, в который невозможно попасть. Либо забыли проставить переход, либо шаг лишний.

Это ровно та проверка, что сработала у меня в каноне (я показывал в прогоне):

```
ПРОБЛЕМ: 4
- SCR-CL-03.1: шаг EV-3.3 недостижим (нет упоминаний)
- SCR-CL-03.1: шаг EV-3.4 недостижим
...
```

Я тогда описал ветки события EV-3 списком, полагаясь на «порядок по позиции», и не проставил явные переходы `— EV-3.3`. Скрипт поймал; я добавил переходы — стало `ПРОБЛЕМ: 0`. Без скрипта это не видно: текст читается связно, «следующий шаг подразумевается» — но для машины (и для стабильных ID, где порядок задаёт не номер, а ссылки) это разрыв графа.

Инвариант парный: помимо «в шаг можно войти» проверяется и **завершимость** — каждая ветвь каждого шага заканчивается одним из: переход на существующий `EV-N.M`, «конец», именованный исход, или показ `MSG-N`. Не бывает ветки, которая просто обрывается.

Одно узаконенное исключение: шаг, недостижимый **уже в исходнике** (в reverse), переносится с пометкой `недостижим`/`дефект исходника` — тогда инвариант считается выполненным (мы не чиним дефекты оригинала, но и не прячем их). Скрипт это учитывает — ищет слово «недостижим» рядом с шагом.

---

## 3. Резолвинг ссылок

**Резолвинг** (от resolve — «разрешить ссылку») = проверка, что **каждый упомянутый идентификатор реально существует** там, куда ссылаются. Ссылка, ведущая «в никуда», — битая (dangling reference).

В событийном документе ссылаются постоянно и в разные стороны:

- шаг → шаг: `*то** — EV-1.10` — существует ли `EV-1.10`?
- сообщение → шаг: в реестре §6 колонка «Показ» = `EV-1.2` — существует ли этот шаг?
- шаг/правило → сообщение: `отображается сообщение MSG-18` — есть ли `MSG-18` в реестре §6?
- поле → DE: `Элемент данных: DE-007` — есть ли `DE-007` в `data-elements.md`?
- форма → контроль: `CTL-001` — существует ли **файл** и **якорь** заголовка?
- диапазон: `EV-1.15–EV-1.19` — существуют ли обе границы, и все ли шаги между ними реально лежат в этом промежутке?

Инвариант: **все эти ссылки разрешаются в существующие цели**. Мой скрипт для канона собирал множество объявленных шагов и проверял, что каждая ссылка-переход попадает в него; отдельно резолвил `MSG-N` (упомянутые vs объявленные в реестре), `DE-NNN` (против `data-elements.md`), и якоря `CTL` (генерил slug из фактических заголовков карточек и сверял). Пример реального улова из третьего прогона — я проверял битые якоря контролей:

```
CTL якоря: 0 битых        ✓ каждый #ctl-005-… ведёт в существующий заголовок
DE вне реестра: нет        ✓ каждый DE-NNN формы есть в реестре
```

Типовая ошибка, которую это ловит: модель написала `— EV-1.65` (опечатка, шага нет), или сослалась на `MSG-21`, которого в реестре §6 нет, или переименовала заголовок карточки CTL — и все якорные ссылки на неё протухли. Глазами в документе на 400 строк это не отследить; скрипт выдаёт точный список битых.

Особый под-случай — **резолвинг диапазона**: `EV-1.15–EV-1.19` означает «все шаги между границами в порядке документа». Скрипт проверяет, что вставленный между ними шаг действительно входит в переиспользование (или что есть оговорка-исключение) — иначе «диапазон» молча меняет смысл при вставке нового шага.

---

## Зачем это в отчёте назвал «строже, чем у них»

У нового подхода контроль качества — **DoD-чеклист** (человек глазами проходит пункты «биекция есть? ссылки целы?») и **grep-антирегрессия** (`sources/|confluence|figma|TODO` — ищет, что *не должно* встречаться). Это ловит присутствие запрещённого, но **не проверяет структурную целостность графа**: DoD-пункт «идентификаторы уникальны» человек может отметить галочкой, не пересчитывая; «все переходы ведут на существующие шаги» глазами на длинном документе не верифицируется.

Наши три инварианта — это **позитивные структурные проверки**, которые прогоняются как код и дают либо `ПРОБЛЕМ: 0`, либо точный список с адресами. Отсюда предложение в отчёте: отдать их в их скиллы `review-artifact` / `artifact-consistency` как машинный слой поверх их DoD — дёшево (один скрипт на тип документа) и ловит ровно тот класс ошибок, который у слабой модели проскакивает мимо чеклиста.
