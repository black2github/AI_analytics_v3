# Постановка координатору КК: волна PROM-5.3-CALL — переиздание карточек вызова внешних АС по шаблону B с разрезкой по подсервисам

От сессии «Точки расширения эталона» (владелец канона), 02.11.2026. Решение владельца 02.11: вариант a) — карточки не откатывать, переиздать поверх тонких. Постановку исполнителю пишет координатор по этой записке; запуск сессии исполнителя — владелец из десктопа по слову координатора «ветка готова»; приёмка — координатор; вливание в master — «Точки расширения эталона» по «принята, влей» (симуляция на временном дереве с построчной сверкой матрицы).

## 1. Повод

01.11 волна P2 сделала 16 карточек CALL-EXT тонкими по формулировке «назначение, где используется, маппинги на ENT, ссылка на базовый; пересказ формата снимается». Раздел шаблона B «Правила заполнения исходящего сообщения» (таблица «Параметр контракта | Правило сервиса») в формулировке не прозвучал, и вместе с форматом метода из карточек ушли правила заполнения сервиса: вместо таблицы — фраза «логика заполнения описана на шаге 1 FUN-SYS-10». Параллельно базовые контракты в docs-external-contracts были переизданы с нарушением норм и откатываются MR !74 к состоянию 31.10 (66d0098); после слияния базовые снова сводки. Разбор — `app/data/Разбор инцидента docs-external-contracts 01.11 — хронология решений, цитаты, последствия (2026-11-02).md`. Образец целевой карточки — `app/data/Пример тонкой карточки CALL-EXT-011 по шаблону B (2026-11-02).md`, версия 5 (решения владельца 02.11: одна карточка в подсервисе-потребителе, без карточки «общей части» в bc-component; карточка — полная инициализация одного вызова без ветвлений, два набора параметров одного метода — две карточки).

## 3. Целевое состояние карточки вызова внешней АС

Формулируется как состояние, не как запрет. Дом нормы — `_meta/templates/contract-call.md`, раздел B и блок «Шаблон карточки вызова» (:301–350), чек-лист «Карточка вызова».

3.1. **Разделы по шаблону B, все присутствуют:** шапка (`type: contract-call`, `service`, `confluence_page_ids` — страницы этого сервиса, где описан вызов; главная первой); строки «**Базовый контракт:**» (абсолютный URL по HEAD) и «**Примеры обмена:**»; «Назначение» (владелец вызываемого, направление, зачем сервису — карточка читается автономно); «Где используется» дословно по срезу; «Использование в сервисе «Корпоративные карты»» с подразделами «Процессы» (таблица), «Транспорт», «Правила заполнения исходящего сообщения» (таблица «Параметр контракта | Правило сервиса»), «Сопоставление входящего сообщения» (таблица «Параметр контракта | Куда записывается в сервисе»: атрибут сущности, выходной параметр функции или «не обрабатывается»; канон 02.11, ветка meta/call-card-response-mapping). Обе таблицы — только привязка данных: условие допустимо как условие значения одного параметра («**Если** атрибут пуст, **то** = …»); шаги, ветвления и ссылки на номера шагов функции в карточке не пишутся — алгоритм обработки живёт в функции или процессе, которые ссылаются на карточку. **Карточка — полная инициализация одного вызова (решение владельца 02.11 поздно):** условие, меняющее состав сообщения (другое имя процесса, другой набор блоков — варианты 10.1/10.2 у ЕСК), — это другой вызов и отдельная карточка с полным набором параметров, без переключателя вариантов в таблице; выбор между карточками остаётся у вызывающего (SCR-CL-20 B-2, FUN-SYS-10 шаг 1) и в карточках не повторяется. Канон — master 6122c53 (a0eecf4: шаблон раздел B + чек-лист, скилл вопрос 7), влито 02.11.

3.2. **Состав метода живёт в базовом контракте:** теги запроса и ответа с типами и кратностями, справочники кодов, коды отказов, примеры обмена. В карточке — только параметры, для которых у сервиса есть правило (что подставляется), и теги ответа, с которыми сервис что-то делает. Пока базовый контракт — сводка (после !74), долг «противоречие: базовый контракт … сводка» на карточке восстанавливается (п. 5).

3.3. **Принадлежность подсервису (шаблон, абзацы «Карточка вызова принадлежит потребителю» и «Вызов из общей функции с параметрами от заявки подсервиса» — канон master 2114290, влито 02.11).** Карточка лежит в подсервисе, чья заявка задаёт параметры вызова. Когда вызов делает общая функция bc-component (например FUN-SYS-10), а значения параметров зависят от заявки подсервиса (строки 10.1 для [КК_ВК], 10.2 для [КК_ВК]/[КК_БК]/[КК_ЛК]), на каждый подсервис-потребитель — **одна карточка целиком**: в её таблице правил заполнения все параметры, которые задаёт сервис, включая общие для всех потребителей (конверт, реквизиты организации, SessionID), и всё сопоставление входящего сообщения; общие строки в карточках bc-issue, bc-status, bc-limits повторяются дословно. Карточки «общей части» в bc-component нет — вызов не делится на две карточки. Общая функция (FUN-SYS-10) остаётся домом алгоритма вызова и обработки ответа и ссылается на карточку подсервиса заявки. В bc-component карточка лежит только когда параметры от подсервиса не зависят (CALL-EXT-003 и подобные). Страницы-источники карточки подсервиса: главная — страница подсервиса, где задаются параметры (для [КК_ВК] SCR-CL-20), дополнительные — страница-копия метода и страница функции. ID: CALL-EXT-011 переезжает в `bc-issue/contract-call/external/` с тем же ID (git mv, шапка, реестры) и описывает вариант 10.1; новые карточки — следующие свободные в CALL-EXT-000 (у КК единое пространство CALL-EXT-NNN по подсервисам, как CALL-EXT-030 в bc-issue): 036 — bc-issue вариант 10.2, 037 — bc-status (10.2), 038 — bc-limits (10.2). Объединять в одну карточку допустимо только вызовы одного подсервиса одной функции одной версии с ОДНИМ набором параметров; 10.1 и 10.2 — разные наборы, две карточки.

3.4. **Источник правил заполнения:** колонка «Логика заполнения …» таблицы запроса страницы-копии метода и таблицы шагов функций и процессов среза. Содержание ячейки — дословно по срезу, **в контексте КК**: страница-копия метода общая для нескольких сервисов Экосистемы, и их специфика не является требованием КК (решение владельца 02.11, Р-1): ветвления по чужим `ProcessName` (`GPB_ReprRegCert_Auth_Check`, `GPB_BO_AgrSign_Auth_Check` и подобные) сворачиваются до результата для КК («= [EXT-002].«РНК клиента в РКО Ф1»» вместо «Если ProcessName = … то пусто, иначе …»), точки вызова и процессы чужих сервисов в «Где используется» не переносятся. «Ничего не терять» относится к требованиям самого сервиса; чужие ветки живут на странице-источнике и в карточках тех сервисов. Следа в теле карточки это не оставляет (не пробел постановки, не долг).

3.5. **Нотация по техбуку:** присвоение через «=» («= «Клиент Банка».«РНК клиента в РКО Ф1»», не «передается …»); атрибут после ссылки на сущность — .«Атрибут»; ссылки на ENT/EXT комплекта там, где сущность заведена; литералы значений в обратных кавычках как в срезе.

3.6. **Функции и процессы, где сейчас лежат таблицы правил** (FUN-SYS-10 шаг 1 и аналоги): таблица уезжает в карточки вызова, в шаге остаётся текст шага по срезу со ссылкой на карточку вызова подсервиса и условия выбора заявок; пометки «(нет целевого артефакта contract-call — требуется заход create-contract-call)» снимаются, так как артефакт есть. Один дом у факта.

3.7. **Приоритет при конфликте правил** (записать в постановку исполнителю явно): форма разделов и принадлежность подсервису — по шаблону B и норме 31.10; содержание ячеек — дословно по срезу; запись присвоений и атрибутов — по нотации. Правило «тело = срез» действует внутри ячейки, а не вместо структуры шаблона. Конфликт, который этим не разрешается, — стоп и вопрос координатору, не выбор по умолчанию.

## 6. Мера приёмки (координатор, по каждой карточке)

- Чек-лист «Карточка вызова» шаблона B: все разделы 3.1 на месте, «Назначение» автономно, ссылка на базовый абсолютная, локального `examples/` нет, карточка в подкаталоге своего подсервиса, матрица и реестры обновлены.
- Правила заполнения: каждый параметр с правилом в колонке «Логика заполнения» источника или в таблице функции — строка таблицы; литералы колонки правил (`"Active"`, `GPB_…`, `PROD_EXEC_WRNT`, коды продуктов) присутствуют в карточке. ## 7. Связанные решения и ограничения

- Базовые контракты после !74 — сводки; ссылки карточек на них по HEAD действуют. Переиздание базовых — отдельный трек владельца, волну не блокирует.
- Волна AGG (доп. страницы агрегаторов, группа B/C: proc-024, call-ext-017/020, ent-023/027) — после CALL, по решению владельца; MR (25) канона отложен до него.
- Сроки приёмки 04.11 15:00 и переноса 05.11 владельцем не пересматривались; оценка волны — 4–6 часов исполнителя плюс две приёмки образца. Если не укладывается, координатор сообщает «Точкам» до старта тиража, решение о сдвиге — владелец.
- FUN-SYS-10 §3 «Вызов функции» перечисляет точки вызова десятков чужих сервисов (страница-копия общей функции). По решению Р-1 там должны остаться только точки вызова КК ([КК_ВК], [КК_БК], [КК_ЛК] со ссылками на ЭФ/процессы), но это отдельная волна после нормы канона «чужой контекст общей страницы» и освобождения прибора (сторож кавычечных литералов источника иначе даст ✗ на каждый снятый пункт) — в этой волне §3 не трогать, в fixlist строка «FUN-SYS-10 §3 — чужие точки вызова, отложено».
- Канон: абзац «Вызов из общей функции с параметрами от заявки подсервиса» в шаблоне, пункт чек-листа, «Пути» и вопрос 6 режима C в скилле — ВЛИТО в master канона 2114290 (130e11a + c5bfbe1, 02.11), accept_canon у координатора; исполнитель работает с `_meta` master 2114290.

## Развилки до запуска (решение владельца через «Точки расширения эталона»)

- **Р-1. Ветвления страницы по чужим `ProcessName`.** (а) Сворачивать до результата для заявок КК с указанием варианта («10.1: …; 10.2: …»), как в образце; (б) переносить ячейку целиком с «Если/то/иначе» по всем ProcessName. **Решение владельца 02.11: (а)** — чужая специфика на общей странице не является требованием КК, «ничего не терять» относится к требованиям самого сервиса; то же для «Где используется» и вызывающей функции (п. 3.4; FUN-SYS-10 §3 — п. 7).
- **Р-2. Пустые варианты источника.** **Решение владельца 02.11** — три случая: параметр без правила ни в одном источнике — строки в карточке нет (необязательное опускается, conventions §6 п. 5); источник говорит «пусто» / «не формируется» — так и пишется («= пусто»); у источника есть место под значение, а оно пустое (10.1 задан, ячейка 10.2 в таблице FUN-SYS-10 пустая — «Вариант заполнения идентификатора заявителя», PRESET_CREDENTIALS_LIST) — «10.2: в постановке не задано» плюс вопрос аналитику КК в реестре вопросов; снимать половину строки без следа нельзя.
- **Р-3. Сущность «Клиент Банка»** в правилах: в КК заведён EXT-002 «Клиент Банка» (dictionaries.md) — ссылка на него; атрибуты «РНК клиента в РКО Ф1», «ИНН/КИО», «КПП», «ОГРН/ОГРИП», «GUID клиента в ЕСК» в реестре отсутствуют — долг матрицы на атрибут, не правка реестра в этой волне. **Решение владельца 02.11: принято.**
- **Р-4. Title карточки подсервиса.** По шаблону title = дословное наименование главной страницы-источника; в примере главная — страница подсервиса SCR-CL-20 (задаёт параметры, несёт маркер контура), title «[КК_ВК] ЭФ Клиента: страница "Подтверждение"». Альтернатива — главная = страница-копия метода «Копия [КК] ЕСК_ОА_…»: одинаковый title у трёх карточек подсервисов, без маркера контура. Рекомендую страницу подсервиса (как в примере): прибор принимает её без ложного ✗, норму менять не нужно. **Решение владельца 02.11: принято — главная страница-источник карточки подсервиса = страница подсервиса, title по ней.**
- **Р-5. Класс вызова ЕСК.** SCR-CL-20 называет метод `/sign/signature/v2/check-authority` — похоже на REST-метод сервиса Экосистемы (подпись), который сам обращается в ЕСК. Если так, вызов КК внутренний (CALL-INT → контракт сервиса подписи). Рекомендую: в этой волне карточки остаются CALL-EXT с базовым ESK-003, наблюдение — вопрос аналитику КК в реестре вопросов; переклассификация, если подтвердится, — отдельным заходом, как 007–009. **Решение владельца 02.11: принято — карточки остаются CALL-EXT, вопрос аналитику КК в реестр вопросов.**
