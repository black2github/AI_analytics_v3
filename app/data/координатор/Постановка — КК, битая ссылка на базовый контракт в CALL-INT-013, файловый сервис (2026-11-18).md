## Что установлено

Замер сессии «Привязка API КК» (только чтение), примеры проверены мной по тем же ревизиям.

- Карточка `docs/srs/bc-component/contract-call/internal/call-int-013-file-download.md` и строка CALL-INT-013 в `README.md` того же каталога (src КК master `c828a4f7`) ссылаются на `…/EAN/docs-file-storage-service/-/blob/HEAD/srs/internal-contract/intc-002-download-file.md`. Такого файла нет: в `docs-file-storage-service` (trunk `cd526ec`) каталога `srs/internal-contract/` нет.
- Источник КК (страница 2370393851, экранная форма SCR-CL-04, кнопка «Экспортировать») ссылается на страницу владельца 2169862959 «[Внешний файловый сервис] Выгрузка файла». Эта страница (выгрузка `EAS/docs-file-storage`, master `f3cedcd`) называет Alias `/filestorage/external/download`, метод POST, операцию `downloadByPostUsingPOST`, тело запроса с `accessToken` и `id`.
- Спецификация владельца `api-specification/file-storage-external-openapi.yaml` (`ECO_BE/ms-file-storage-service`, trunk `8d9c1a0d`): путь `/filestorage/external/download`, метод `post`, `operationId: downloadByPost`, summary «Выгрузка файла из файлового сервиса».
- Матрица владельца (`docs-file-storage-service/traceability-matrix.md`, раздел «Покрытие: API ↔ SRS»), строка дословно: `` | `POST /filestorage/external/download` | external | FUN-CL-03 | PRC-003, PRC-010 | ENT-001, ENT-002 | EXTINT-003-01…09 | ``. Документ — `srs/functions/client/fun-cl-03-download-file.md`, заголовок «FUN-CL-03 [Файловый сервис] Клиент: Функция выгрузки файла». С FUN-CL-03 в матрице владельца связаны ещё две операции; различает их только спецификация.
- Сверка состава. Запрос: `Content-Type`, `Authorization`, `accessToken`, `id` — совпадает со спецификацией (тело `DownloadCommand`, Bearer). Ответ: `Content-Disposition` и содержимое файла совпадают; `Transfer-Encoding` в спецификации не объявлен (на странице владельца есть); в спецификации сверх карточки — необязательный заголовок запроса `Range`, заголовок ответа `Accept-Ranges`, ответ 206. FUN-CL-03 состава параметров не несёт — он описывает поведение.

## Правки

1. Карточка CALL-INT-013, строка «Базовый контракт» — целиком:

   `**Базовый контракт:** [file-storage-external-openapi.yaml](https://gitlab.gboteam.ru/ECO_BE/ms-file-storage-service/-/blob/HEAD/api-specification/file-storage-external-openapi.yaml), операция `downloadByPost` (`POST /filestorage/external/download`).`

   Основание формы: у владельца есть спецификация API — по `cross-service-addressing.md`, §5.2 (абзац об API First) целью ссылки служит файл контракта через `HEAD`, имя операции пишется текстом. Функция владельца целью ссылки не бывает (тот же §5.2) — FUN-CL-03 в строку не вписывается. Слова «(платформенный сервис, `_meta/services.json`)» из строки уходят (пункт 15 ревьюера). Наименование сервиса остаётся в «Назначении», оно там уже есть.
2. README каталога, строка CALL-INT-013, колонка базового контракта: `[downloadByPost](…/api-specification/file-storage-external-openapi.yaml)` — тот же адрес спецификации.
3. Остальное в карточке не меняется: «Транспорт» и правила заполнения — по источнику КК; параметры, которых нет в источнике КК (`Range`, `Accept-Ranges`, ответ 206), в карточку не добавляются.
4. Журнал вопросов, новая запись, статус «зафиксировано»: расхождение карточки со спецификацией владельца — `Transfer-Encoding` назван источником КК и страницей владельца, в спецификации не объявлен; вопрос владельцу контракта (file-service). Строки долга не нужно.
5. Долга «у владельца file-service» нет.

Ожидание: долгов столько же; ✗ 0; «свойства контракта записаны второй раз» не срабатывает — колонок типа, обязательности и кратности в карточке нет. Новое ⚠ или ✗ прибора на строке с двумя ссылками — строкой отчёта «Точкам», текст не подгонять.
