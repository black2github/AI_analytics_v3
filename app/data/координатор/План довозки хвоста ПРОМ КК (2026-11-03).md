# План довозки хвоста ПРОМ КК (2026-11-03)

Дом плана после принятия — `sandbox/План довозки хвоста ПРОМ КК (2026-11-03).md` репозитория КК (master); статусы шагов ведутся там, отметки — в колонке «Статус» дописыванием (☐ не начат, ▶ в работе, ◐ частично, ✓ сделан, с датой и хешем). Здесь — проект до вопросов владельца канона.

## Цель и граница

Цель: все задачи, введённые в ПРОМ после среза 0e32b01 (выгрузка 24.10) и до даты D (дата последней выгрузки), введены в репозиторий тем же порядком, что и все будущие задачи (условие 5 плана миграции — см. «Термины и определения»); комплект после каждой партии проходит гейт переноса с базлайном r08; после хвоста — один перенос в `docs-business-cards`, с даты D Confluence для КК не меняется.

Стратегия (решение владельца канона 03.11, ждёт подтверждения в п. 0.1): хвост довозится в `src-business-cards` (ветка master = ПРОМ), перенос в EAN — один раз после хвоста; снимок «для отчёта» в docs-репозиторий не делается (у комплекта один дом; отчётная точка — тег `prom-slice-0e32b01-accepted`, master d60824bc, отчёт гейта r08).

Порядок, от которого зависит атрибуция (факт 03.11: при вводе задачи в ПРОМ аналитики перекрашивают её текст в чёрный — это производственная практика синхронизации статуса; новая выгрузка снимает маркеры введённых задач, и run-history уже не сможет поставить на них теги): СНАЧАЛА ввод тегами из текущего архива (маркеры ещё есть), ПОТОМ первая новая выгрузка. Три раздельных диффа вместо одного: исправления critic (run-history на старом архиве новым бандлом), вклад каждой задачи (тег `src/<ID>`), правки аналитиков + исправления экспортёра + остатки перекраски (коммит «Выгрузка» новой выгрузки).

## Опора и утилиты

Опора: гид миграции `_meta/migration/reference.md` — «Ветки и теги репозитория сервиса» (ввод задачи — два коммита master: run-history + дельта-процесс), «Перенос комплекта в docs-репозиторий», «Изменение по постановке»; `prompt-update-slice.md` фазы D/E (категории страниц дельты); решение 03.11 о закрытии OQ через каналы изменения.

Утилиты: `run-history.bat` (бандл экспортёра 1.9.17; apply_history.py прибора) — событие «выгрузка», ввод задач тегами `src/<ID>`, хвост манифеста; `run-tree.bat` — выгрузка; `run-pick.bat` — точечная замена страниц; `selfcheck.py --raw --bundle` — сверка по архиву; `raw_oracle.py --cards` — дельта-задание по карточкам (лежит в бандле: `<бандл>/app/scripts/CI/raw_oracle.py`, в `_meta/tools` канона его нет); `transfer_gate.py` — гейт с базлайном; `link_debts.py`, `matrix_sync.py`. Утилиты «page-delta» нет: категории шага 1.5 разбираются руками по `git diff`. Запуск `.bat` — из cmd или bash: из PowerShell первая строка bat уходит в stderr как NativeCommandError при коде 0.

## Приложение А. Форма `sandbox/tail-intro-list.md` (список ввода, п. 0.3)

Файла в репозитории КК пока нет — его заводит координатор по хвосту манифеста, отметки ставит акцептующая. Шапка — две строки: дата и коммит архива, по которому снят хвост; строка run-history «не введено (по манифесту архива): N из M». Полный хвост (run-history печатает первые 20 ID), из корня `<src>`:

```powershell
git tag -l "src/*"
Select-String -Path sources/raw/migration-manifest.yaml -Pattern "^  ([A-Z][A-Z0-9]*-[0-9]+):" | ForEach-Object { $_.Matches[0].Groups[1].Value } | Where-Object { $_ -notlike "UNKNOWN-*" }
```

ID манифеста (ключи под `tasks:`), которых нет среди тегов, — хвост; страницы задачи — список `pages:` под её ключом. Таблица, строка на задачу:

| № | ID | `first_seen` | Страницы (заголовки из манифеста) | Название (необязательно) | Введена в ПРОМ (дата) | Перекрашена (координатор, с итерации 1) | Партия | Тег `src/` | Статус |
|---|---|---|---|---|---|---|---|---|---|
| 1 | TEAMTB-NNNN | 2026-10-27 | [КК_B2B] ДПК; [КК_B2B] ЖЦ Заявки на перевод | … | 2026-10-30 | да / нет / частично | 0 | ☐ | ☐ |
| 2 | TEAMTB-MMMM | 2026-10-29 | … | … | ожидается до D | | — | — | ☐ |
| 3 | GBO-NNNNN | 2023-04-17 | … | | ☐ (отметка акцептующего) | | | | ☐ |
| 4 | GBO-KKKKK | 2024-02-01 | … | | неутверждённый состав, вводится выгрузкой (1.5 е) | | — | — | — |

Правила: заготовку делает координатор из полного хвоста манифеста с колонкой `first_seen` (дата появления на страницах, не дата ввода — отсев по ней не делается); цвет и confidence задачи в таблицу не выносятся — в текущем Confluence цвета введённых задач уже нет (перекрашены), признак forced координатор учитывает у себя в разборе 1.5; «№» — порядковый номер строки заготовки, при перестановке строк акцептующим не меняется (; заготовка 03.11 — 7adac498 на `coord/tail-0`, 153 строки: forced 43, к отметке 110); ключи `UNKNOWN-<цвет>` (цвет без задачи) — отдельный раздел с колонкой «ID задачи (если известен)»; заглушки вида `BTOB-123456`, `TODO-123456` остаются в таблице, решает акцептующий; «Название» заполняет акцептующая при желании — заголовков задач и Jira в архиве нет. Порядок строк-кандидатов = порядок ввода в ПРОМ (одна дата — по `sources/raw/migration-apply-order.md`, внутри одного дня ⚠ — акцептующая; задачи без даты — в конце); «Партия» — номер итерации, в которой задача вводится тегом (0 — из текущего архива, п. 0.10); у акцептующего одна отметка — «Введена в ПРОМ (дата)» или «ожидается до D» (эти сведения есть только у команды); «Перекрашена» заполняет координатор на шаге 1.3 сравнением манифестов (в итерации 0 не нужна) — это признак для правил 1.5 (а)–(д); строки forced-задач (1.5 е) координатор помечает в заготовке «неутверждённый состав, вводится выгрузкой», акцептующий их не отмечает; «Статус» — ☐ / ✓ с хешем коммита ввода. Строки не удаляются: задача, которой не стало в хвосте манифеста (перекрашена и снята выгрузкой), получает пометку «снята выгрузкой N, введена по правилу 1.5 (д)» и тег через run-history с `--allow-unlisted`.
