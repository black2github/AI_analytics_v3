# Постановка 2.17 — второй комплект КК: методы адаптера f1-integration (2026-11-11)

**Кому:** координатор КК; исполняет исполнитель по слову владельца в чате координатора.
**От кого:** сессия «Точки расширения эталона» (постановщик, приёмка). Вопросы, образец и сдача — мне.
**Мощность модели:** разрезка карточек и сверка дословности — сильная; ссылки, реестры, матрица — средняя.
**Репозиторий:** `src-business-cards`, ветка `exec/f1-kit` от текущего master. Исполнитель коммитит
локально; push и MR в master — владелец, командами через координатора. В чужих репозиториях (`docs-external-contracts`, `docs-f1-integration`,
канон) ничего не править: только патч и текст сообщения в сдаче.

## 1. Что решено и почему

Адаптер `f1-integration` (`ECO_BE/ms-f1-integration`) — отдельный сервис Экосистемы со своим кодом и
спецификацией; в нём методы нескольких команд. Команда КК ведёт в нём свои методы. Сейчас страницы этих
методов оформлены в комплекте КК вызовами внешней системы Ф1, звено «КК → адаптер» не оформлено, а
значения параметров вызова стоят в шагах функций КК.

Решения владельца 11.11.2026:

1. Сервис нескольких команд ведётся одним репозиторием документации с комплектом на команду
   (конвенции техбука, §3.2, «Сервис нескольких команд»). Целевой репозиторий создан:
   `EAN/docs-f1-integration`, комплект КК в нём — каталог `business-cards/`.
2. Отдельный исходный репозиторий не заводится. Комплект адаптера команда КК ведёт в
   `src-business-cards` вторым корнем рядом с `docs/`: `docs-f1-integration/business-cards/`.
   Рамки домена (корневой README с таблицей комплектов, концепция, глоссарий сервиса) в исходном
   репозитории нет.
3. Идентификаторы карточек второго комплекта несут слот `BC` сразу после префикса: `INTC-BC-001`,
   `FUN-BC-SYS-01`, `CALL-EXT-BC-001`, `CTL-BC-001`.
4. Поле шапки `service` у карточек второго комплекта — `f1-integration`. Запись каталога сервисов канона
   готовит постановщик.
5. Журнал открытых вопросов один на репозиторий; запись второго комплекта несёт строку
   `- Комплект: docs-f1-integration/business-cards`.
6. Страница «РКО Ф1_Получение списка платежных систем» (2166861005) и её представление DB-Link
   (2184433383) переносятся во второй комплект; метод оформляется системным, авторизация — ТУЗ; в матрице
   комплекта КК появляется долг — раздел 7.
7. Строка 2.8 плана довозки в прежнем виде отменяется: все шесть методов закрывает эта волна.

Нормы: канон master `163062a` — `_meta/templates/sources-readme.md` (раздел «Разметка подсервисов», зона
`комплект <путь>`), `_meta/migration/reference.md` (поле «Комплект» записи журнала),
`_meta/migration/cross-service-addressing.md` §4.3, `_meta/tools/README.md` (абзац «Второй комплект
исходного репозитория»), шаблоны `internal-contracts.md`, `function.md`, `contract-call.md`, `controls.md`,
`docs-readme.md` (разделы «Сервис домена», «README каталога карточек»).

**Уточнения 11.11.**

- Форма идентификатора карточек вызова второго комплекта — `CALL-EXT-BC-NNN`: слот стоит после подтипа
  (решение владельца 11.11: префикс карточки вызова — `CALL-EXT`, `CALL-INT`, `CALL-MOD`). Корневой реестр
  вызовов — `CALL-BC-000`, реестр внешних вызовов — `CALL-EXT-BC-000`, файлы — `call-ext-bc-NNN-<слаг>.md`.
  Промежуточная форма `CALL-BC-EXT` из образца переименовывается первым коммитом тиража.
- Строки `комплект …` в профиле объявляются вместе с переносом своих карточек, чтобы на каждом коммите
  самопроверка основного комплекта давала ✗ 0.
- Страница 2166861005 (решение владельца 11.11): раздел «Привилегии», шаг 0 проверки прав, ссылка на
  описание клиентского API и строка «JSON схема» в карточки адаптера не переносятся — одна заметка об
  отклонении по форме канона в контракте и строка-заметка о снятом шаге 0 в функции; «Где используется» —
  строкой сервиса в «Потребителях» без адреса карточки вызова. В долг матрицы КК привилегии и шаг 0 не
  дописываются.

## 3. Порядок работ

Каждый шаг — отдельным коммитом (или несколькими), в одной ветке.

**Шаг 0. Накат канона.** Срез `287b003` → `163062a`, одним приёмом, как прежние накаты; первым коммитом
ветки. После наката самопроверка печатает новые предупреждения «карточка вызова — …» (сторож алгоритмов
в карточках вызова; на прошлом замере 69 карточек из 75). Вердикт они не меняют, в этой волне по ним ничего
не чинить, кроме карточек, которые волна и так переписывает. Числа до и после наката — в отчёт наката.

**Шаг 1. Проект — мне до правок.** Файл `sandbox/id-map-f1-integration.md`:

- карта «старый ID → новый ID и путь» по всем карточкам раздела 2.1;
- перечень новых карточек вызова КК (`CALL-INT-NNN`): метод, функция-потребитель, каталог части;
- по каждому методу — откуда берутся значения параметров запроса (номер шага функции КК, число
  присваиваний) и есть ли на странице метода сопоставление ответа;
- число файлов комплекта КК со ссылками на каждый снимаемый ID.

**Шаг 2. Объявление зоны и каркас.** Строки `комплект docs-f1-integration/business-cards` в профиле
источников (README корня, таблица «Разметка подсервисов») — 14 строк с матчером-номером страницы.
Каркас комплекта: `docs-f1-integration/business-cards/README.md`, `traceability-matrix.md`,
`srs/README.md`. В описи — новые целевые пути перенесённых страниц (правятся только две последние колонки).

**Шаг 3. Образец на одном методе.** Метод «Получение операций по карте» (2359763493) целиком: карточки
второго комплекта, карточка вызова в КК, правки функции-потребителя, ссылки, матрицы обоих комплектов.

## 4. Целевая форма

### 4.1. Страница метода адаптера → три карточки

Каждая из пяти страниц методов (2359763493, 2166861018, 2166861013, 2184433983, 2184433984) раскладывается
так; шестая страница (2166861005) — по разделу 7:

| Что на странице | Куда | Форма |
|---|---|---|
| паспорт метода, формат запроса, формат ответа, коды ошибок, примеры | второй комплект, `srs/internal-contract/system/intc-bc-NNN-<слаг>.md`, ID `INTC-BC-NNN` | шаблон `internal-contracts.md`: паспорт, разделы 1–5, «Потребители». Каталог `system/` — по строке «Авторизация» (Basic, ТУЗ) |
| «Логика работы», «Процесс запроса …» — шаги метода | второй комплект, `srs/function/system/fun-bc-sys-NN-<слаг>.md`, ID `FUN-BC-SYS-NN` | шаблон `function.md`; шаги дословно; чтение представления — ссылкой на карточку `CALL-EXT-BC-NNN` |
| кто и где в КК вызывает метод, значения параметров запроса, разбор ответа | основной комплект КК, `docs/srs/<часть>/contract-call/internal/call-int-NNN-<слаг>.md`, следующий свободный `CALL-INT-NNN` | шаблон `contract-call.md`, раздел B |

Текст — дословно со страницы источника. Содержимое EXTINT-F1-030 и EXTINT-F1-031 в репозитории внешних
контрактов можно использовать как заготовку разделов 1–5, но сверять с источником: при расхождении
побеждает источник.

### 4.2. Карточка вызова в комплекте КК

- Одна карточка на пару «метод, часть-потребитель»: карточка вызова принадлежит потребителю.
- Строка «Базовый контракт» — ссылка на `INTC-BC-NNN` абсолютным адресом целевого репозитория:
  `https://gitlab.gboteam.ru/EAN/docs-f1-integration/-/blob/HEAD/business-cards/srs/internal-contract/system/<файл>`.
  До выкладки второго комплекта адрес не открывается — это ожидаемо.
- «Процессы» — таблица из двух колонок «Процесс / функция | Шаг / место».
- «Правила заполнения исходящего сообщения» — значения параметров запроса. Сейчас они стоят в шагах
  функций КК (пример: функция «ЭКО_Получение отчета по карте из Ф1» (FUN-SYS-13), шаг 4 — восемь
  присваиваний). Присваивания переносятся в карточку вызова дословно, таблицей или списком
  «параметр = значение»; в шаге функции остаётся вызов со ссылкой на карточку вызова. Шаги, ветвления и
  обработка ошибок остаются в функции.
- «Сопоставление входящего сообщения» — куда КК кладёт параметры ответа, если страница это задаёт; иначе
  «в постановке не задано».
- Разделов «Логика работы», «Где используется», «Обработка входящих ответов», «Исходящие параметры»
  в карточке вызова нет. Перед удалением текста шагов проверить, что он дословно есть в функции КК; если
  нет — сначала перенести в функцию.

### 4.3. Представления DB-Link

Карточки CALL-EXT-001, 002, 003, 004, 005, 006 переезжают во второй комплект: `srs/contract-call/external/`,
ID `CALL-EXT-BC-001…006`, перенос `git mv` с правкой шапки и ссылок. Базовые контракты EXTINT-F1-024…029
остаются в `docs-external-contracts`; в «Процессах» потребитель — функция `FUN-BC-SYS-NN`
второго комплекта вместо карточки CALL-EXT метода.

CALL-EXT-003 и CALL-EXT-006 имеют один главный источник (2184433381). Дубль в этой волне не лечить:
перенести обе, в сдаче назвать отдельной строкой.

### 4.4. Контроли

Строки реестра контролей КК по снятым номерам убрать, новые номера — в карту ID.

- **Журнал открытых вопросов.** Открытым записям о страницах раздела 2.1 дописать строку
  `- Комплект: docs-f1-integration/business-cards`. Прибор сам покажет записи без поля, которые называют
  страницу второго комплекта.
- **Опись.** Целевые пути перенесённых страниц — новые; проверка описи `--check` чистая.

## 6. Чего не делать

- Не лечить аналитику: противоречие или пробел страницы — запись журнала и долг, текст дословно.
- Не заводить в `docs-f1-integration/` корневой README, концепцию и глоссарий сервиса.
- Не обходить прибор. Если прибор даёт ✗, которого по этой постановке быть не должно (слот `BC` в
  идентификаторах, каталог второго комплекта, покрытие, код сервиса `f1-integration` вне каталога
  сервисов), — остановиться и прислать строку отчёта мне. Второй комплект прибор поддерживает с
  сегодняшнего дня, живого комплекта ещё не видел.
- Не трогать обмены Kafka и карточки, которых нет в разделе 2.1.
- Не заводить в комплекте КК карточку вызова и внутренний контракт для метода списка платежных систем:
  по решению владельца там остаётся только долг (раздел 7).
- Не править карточки прочих вызовов по новым предупреждениям сторожа алгоритмов.

## 7. Метод «РКО Ф1_Получение списка платежных систем» (2166861005) и его представление (2184433383)

Решение владельца 11.11.2026, исполнять именно так.

**Факт.** На странице 2166861005 ошибка исходной аналитики. Адрес `/business-cards/payment-systems` и
авторизация токеном пользователя относятся к методу КК. Параметры запроса и ответа и работа с
представлением DB-Link относятся к методу адаптера `/integration/f1/business-cards/payment-systems`,
который вызывается под ТУЗ и устроен так же, как остальные методы адаптера.

**1. Карточки метода и его представления переносятся во второй комплект.**

- Страница метода 2166861005 раскладывается по разделу 4.1 на `INTC-BC-NNN` и `FUN-BC-SYS-NN` второго
  комплекта. Метод — системный: каталог `srs/internal-contract/system/`, функция — `function/system/`.
- Авторизация — ТУЗ. Признак клиентской функции — токен авторизации на странице — игнорируется: по нему
  метод клиентским не считать и в каталог `client/` не класть.
- Отступление от текста страницы оформляется заметкой о санкционированном отклонении по форме канона:
  что стоит на странице (токен пользователя, адрес `/business-cards/payment-systems`), что записано в
  карточке (ТУЗ, адрес метода адаптера) и основание — решение владельца канона 11.11.2026. Остальной текст
  страницы — дословно.
- Карточка представления CALL-EXT-004 (2184433383) переезжает во второй комплект по разделу 4.3:
  `CALL-EXT-BC-NNN`, потребитель в «Процессах» — функция метода во втором комплекте.
- Карточки CALL-EXT-009 и CALL-EXT-004 из комплекта КК уходят, номера снимаются.

**2. В матрице комплекта КК появляется долг.**

- Причина долга: с экранной формы идёт ссылка на вызов функции, которой в комплекте КК больше нет.
- Карточка вызова и внутренний контракт для этого метода в комплекте КК не заводятся.
- Места комплекта КК, которые называют метод (на момент постановки: экранные формы «Фильтр списка карт»
  (SCR-CL-02) и «Заявка на выпуск карты» в режиме создания/редактирования (SCR-CL-19) — по разделу «Где
  используется» страницы; упоминания по имени в справочниках части bc-issue и в функции FUN-CL-55; строка
  матрицы о тождестве имени по CALL-EXT-019), оформляются по правилу долгов канона: имя цели дословно и
  строка долга в матрице КК с этими карточками в FROM. Перечень мест уточнить по комплекту и приложить к
  карте ID.
- Прежний долг «противоречие» по CALL-EXT-009 закрывается по норме с отсылкой на новый долг.

Вопросов команде и строк долга во втором комплекте по этому методу постановка не требует. Если при
разрезке страницы встретится текст, который нельзя отнести ни к методу адаптера, ни снять заметкой об
отклонении (раздел «Привилегии», шаг проверки прав пользователя), — не решать самим: список таких
фрагментов мне до правок, вместе с картой ID.

## 8. Приёмка

- Самопроверка основного комплекта: ✗ 0; строка «разметка комплектов … выдержано ✓»; в покрытии «другой
  комплект: N», пробелов не прибавилось.
- Самопроверка второго комплекта (`--docs docs-f1-integration/business-cards` с ключами источников):
  ✗ 0; покрытие — пробелов 0, замороженные страницы в своём классе.
- Гейт переноса обоих комплектов: READY либо перечень блокеров с разбором, что из них — ограничение
  прибора.
- `matrix_sync.py --check` обоих комплектов чист; `link_debts.py` — числа до и после.
- Сторож алгоритмов: в новых и переписанных карточках вызова предупреждений нет.
- Дословность: по каждой странице методов — ни одного потерянного абзаца, строки таблицы, присваивания;
  сверка по источнику, не по прежней карточке.
- Ссылок на снятые ID в комплекте КК — 0 (кроме карты ID и записей журнала).
