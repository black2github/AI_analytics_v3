Дата: 2026-08-23. Контекст канона: docs-o2new на master (HEAD c46ca2b),
оси сверки с эталоном закрыты — единственное число каталогов srs,

## Постановка (кейс «Корпоративные карты»)

Крупный сервис ДБО из слабосвязанных подсервисов («Открытие счёта и
выпуск карты», «Управление лимитами», «Изменение статуса карты») с
общей частью (список карт, детали, отчёты); для пользователя — один
раздел ДБО с закладками Заявки/Карты/Отчёты/Тарифы. Эталон компактен и
учебен, но на 180 сервисах бизнес- и платформенные нюансы в рамки
шаблонов не вписываются. Четыре методологических вопроса + перспектива
forward-режима (AI-агенту нужна детерминированная адресация «куда
класть новое»).

Сквозной тезис (позиция Клода, согласована в обсуждении): лучшие
практики (product line engineering, DDD, arc42) делают не универсальную
структуру, а компактное ядро + управляемые ТОЧКИ РАСШИРЕНИЯ с
деревьями выбора; «эталон — частный случай» задаётся правилами выбора,
не расширением структуры впрок. Сторожа проверяют правила механически.

## Вопрос 1. Сервис из подсервисов с общей частью

- 1A один большой комплект: одна картина/UI-взгляд, но реестры-монстры
  и гонки команд.
- 1B комплект на подсервис + комплект общей части (cards-core), связи
  через каталог сервисов и межсервисную адресацию (документ 23.08):
  масштаб и эталонность кирпичей; минусы — целостность раздела не
  видна, охрану границ core надо держать.
- 1C ЗОНТИЧНЫЙ комплект (DDD context map) поверх 1B: лёгкий комплект
  «Корпоративные карты» = service-vision + карта подсервисов +
  UI-структура закладок + маршрутизация; требований не содержит.
- РЕКОМЕНДАЦИЯ: 1C поверх 1B (зонтик ≈ расширенный
  service-vision + docs-readme, почти без нового типа).

## Вопрос 2. «Методы» (части функций, разделяемые алгоритмы)

Уточнение (вопрос аналитика 2026-08-23): слово «метод» в
Confluence-источниках двусмысленно, и ПЕРВЫЙ вопрос дерева — снятие
этой двусмысленности:

- **(б) метод API сервиса** (есть интерфейс: параметры запроса/ответа,
  вызывающая сторона — фронт или другой сервис): это НЕ часть функции —
  отношение обратное, функция часть метода (inkasso: «функция
  вызывается в рамках метода»). Оформление — канонная пара
  INTC-карточка (контракт) + FUN-SYS-карточка (алгоритм, «функция
  метода», параметры ссылкой на INTC). CALL-INT сюда НЕ относится
  (это вызовы других внутренних сервисов) — ранняя формулировка «INTC +
  вызовы CALL-INT» была ошибочной, исправлена.
- **(а) алгоритмическая подпрограмма** (интерфейса нет) — собственно
  «часть функции»:
  - один потребитель → инлайн-раздел H2 (`## <имя>`) в карточке
    функции (разрешено шаблоном function: «технические подразделы,
    в источнике вынесенные в подстраницы, — отдельными H2»);
  - несколько потребителей → FUN-SYS «библиотечная процедура»
    (шаблон function §2), при разделении подсервисами — в общей части
    по в.1.
- Новый тип method/ — НЕ вводить (размывает function).
- Прецедент к закрытию: долги «[РРКО_ИПИ] Методы» в inkasso-run1 —
  там источниковые «Методы» = случай (б).

Проверка по канону (2026-08-23): дерево УЖЕ РЕАЛИЗОВАНО — определитель
метода в create-artifact, четыре ветви (1 внешняя АС →
external-integration+contract-call; 2 верхнеуровневые «Методы»/признаки
эндпоинта → пара FUN-SYS «функция метода»+INTC; 3 подкаталог функций
без эндпоинта → библиотечная FUN-SYS; 4 не подпадает → открытый
вопрос, тип не выдумывать), согласован с create-internal-contracts,
create-function (режим «функция метода») и шаблонами. Инлайн-H2 покрыт
правилом шаблона function («подстраницы источника — отдельными H2»):
reverse-критерий — ПОЛОЖЕНИЕ страницы в дереве источника, детерминнее
«числа потребителей». Хвост вопроса 2 только один: forward-критерий
выбора (без дерева источника) — эвристика «один потребитель → инлайн».

## Вопрос 3. Фронтовые vs бэковые контроли

- 3A единый реестр CTL с колонкой контура — смешение уровней.
- 3B (РЕКОМЕНДАЦИЯ, обкатано на КК_ВК скиллами control-split
  Вариант A + событийная ЭФ v2): BE-контроли в control/ (атрибуты,
  Зона 1; реализация ссылкой на функцию/INTC-валидатор), FE — в
  карточках ЭФ (FLD/EV, режимы R/V, Зона 3), связь по назначению через
  ID контроля; x-controls к OpenAPI. Нужен сторож парности
  (FE без BE-пары и наоборот — предупреждение).
- 3C секции FE/BE в одной карточке — хронически полупустые.

Проверка по живому эталону (2026-08-23): ПРОТИВОРЕЧИЯ С ЭТАЛОНОМ НЕТ —
эталонные ЭФ уже событийные (scr-bnk-01: реестр полей, FLD-карточки
«Правила полей (статика)», реестр EV + по-событийные разборы с шагами,
кнопки), т.е. совпадают с шаблоном screen-form канона. Связь
ЭФ↔контроли в эталоне наполовину есть: control/README §2 — группы
CTL-GRP-N с триггером и ссылками на обе стороны (вкладки ЭФ и
функции/процессы), вплоть до события («EV-1 ш. 21, EV-2»). Не хватает
обратного направления на уровне ПОЛЕЙ: связи FLD-правил с CTL «по
назначению». Для 3B нужны две АДДИТИВНЫЕ доделки (ничего не ломается):
(1) правило+образец «Контроль: CTL-NNN» в FLD/EV-карточках шаблона ЭФ
и зеркальная колонка контура реализации в карточке CTL (FE — FLD/EV,
BE — функция/INTC); (2) сторож парности в selfcheck (ссылка на
несуществующий CTL — брак; CTL контура FE без ссылающейся строки —
предупреждение). LLM-реструктуризация ЭФ под это выполнима:
прецеденты КК_ВК и A/B NTF («v2 OK с первого захода»); сторожа
дословности переупаковку переживают по построению; по-шаговые сторожа
на screen-form сознательно не действуют (steps_apply). Граница —
качество нарезки на события (глаза, как «Назначения» функций).

## Вопрос 4. «Шаблонизация» обработки категорий документов

Термин: закрепить «типовая обработка»/«категория» (слово «шаблон»
перегружено трижды).
- 4A (ПО УМОЛЧАНИЮ): один PROC + таблица вариативности
  «категория → отличия».
- 4B база + переопределения (паттерн asyncapi-overrides) — при многих

- 4C полные копии — только как reverse-фиксация фактического
  состояния источника, не целевое.

## Ответы аналитика (2026-08-23) и смена рекомендации по в.1

1. Подсервисы ВСЕГДА ведёт команда сервиса — это внутрикомандный
   инструмент борьбы со сложностью, границы подвижны.
2. «Отчёты» и «Тарифы» — общая часть, не подсервисы.
3. Про вторую матрёшку — уточнение задано (ещё один сервис той же
   анатомии: слабосвязанные блоки + общая часть; кандидаты — депозиты,
   зарплатные, ВЭД, кредиты; и как матрёшки устроены в Confluence).

РЕКОМЕНДАЦИЯ в.1 ФИНАЛЬНАЯ → «подсервис-first в одном комплекте»
(синтез после возражения аналитика к «тип→подсервис»: аналогия с
контурами НЕ переносится — контуры техническое измерение с
фиксированными значениями, подсервис прикладное, рабочая сессия
человека и партия миграции = «всё по лимитам», locality of work бьёт
единообразие путей):
- один сервис-комплект, одна запись каталога сервисов, ЕДИНЫЕ матрица/
  open-questions/ID-пространство (сквозная нумерация, подсервис в ID
  не кодируется — границы подвижны), связи — относительные ссылки;
- сегмент подсервиса СРАЗУ ПОСЛЕ srs/: `srs/<подсервис>/<тип>/…`
  (не над docs — у подсервиса нет своих BRD/api, пустые уровни не
  плодим); внутри подсервиса — эталонная структура типов с контурами;
- общая часть — корень srs/ без сегмента (как эталон); Отчёты/Тарифы
  здесь;
- реестры типов единые сводные в корне типа с колонкой «Подсервис»,
  в подсервисных каталогах — только навигационные README; перенос
  карточки = mv + колонка, ID и ссылки живы;
- зонтик = service-vision + docs-readme с картой «закладки UI →
  подсервисы/общая часть»; новых типов ноль;
- эталон = частный случай «ноль сегментов» буквально.
Правки коры (обе точечные): правило пути «srs/[<подсервис>/]<тип>/» в
конвенцию и шаблоны; белые списки скоуп-гейта скиллов → глобы
`srs/**/<тип>/**`. Прибор индифферентен (диспетчер мэппит по
frontmatter, не по глубине путей).

Операционная механика (вопросы аналитика 2026-08-23):
- разметка «подсервис/общая часть» — ДЕКЛАРАЦИЕЙ в профиле источников
  sources/README.md (механизм канона уже есть): таблица «подкаталог
  выгрузки → подсервис|общая часть»; дерево выгрузки — кандидат,
  предлагает плановик, утверждает аналитик (как 15 вопросов
  плановика); сторож мэппинга возможен (page_id подсервиса X →
  карточка в srs/X/);
- миграция ОДНА на сервис; подкаталог выгрузки = зона захода в сетке
  «подсервис × тип», не отдельная миграция; матрица/OQ единые,
  партионность последовательная; coverage-гейт сервисный (забытый
  подкаталог невозможен);
- порядок: общее ядро первым (подсервисы ссылаются на общее — долги
  минимизируются; DM почти весь общий; UI-каркас для зонтика) →
  ОДИН подсервис целиком как пилот схемы (урок «пилот на одном») →
  остальные партиями → финальный coverage и отдача.

Проверка на второй матрёшке — СБП (2026-08-23, дерево от аналитика;
~15 подсервисов, теги [СБП_ПК]/[СБП_ТСП]/[СБП_QR]/…):
ПОДТВЕРДИЛОСЬ: подсервисы в источнике размечены ПРЕФИКСАМИ ТЕГОВ
(машинный кандидат разметки для профиля — плановик строит, аналитик
утверждает); общая часть — верхнеуровневые [СБП]-страницы; каждый
подсервис внутри уже устроен по-эталонному (Процесс/ЖЦ/МД/Функции/
ЭФ/Контроли/Нотификация) — «подсервис = мини-сервис» отражает
реальность источника; определитель методов получает десятки
применений («Параметры вызова…»).
ТРИ УТОЧНЕНИЯ СХЕМЫ: (а) подсервисы ПЛОСКИМ списком, вложенность
srs/<под>/<под>/ запрещена — группы источника («Сервис платежей» ⊃
B2B, B2C) живут только в карте зонтика; (б) тег — кандидат, семантика
— решение: [СБП_УСЗ]/[СБП_Story] при своих тегах — кросс-подсервисный
UI, кандидаты в общую часть; (в) порядок миграции получает слой
core-подсервисов: общая часть → core (напр. [СБП_QR] ядро QR) →
зависимые (QR_C2B/B2B/блокировка/входящие).
ОПЕРАЦИОННОЕ: гигиена тегов реальна ([СПБ_QR] опечатка, [СБП_В2B]
кириллическая В — класс К-31) — сторож мэппинга работает по
утверждённой таблице профиля, расхождения в OQ; Draft/Архив/«delete»
страницы — судьба в профиле (прецедент Д-5).

Масштабирование план-генерации (вопрос аналитика 2026-08-23; базовый
замер: 94 страницы ≈ 5 минут): время линейно ДО порога контекста,
после — сверхлинейно и с молчаливыми потерями страниц (главный риск —
полнота, не минуты). Оценка сверху — не экстраполяцией, а замером 2–3
точек с ИНСТРУМЕНТАЛЬНОЙ сверкой потерь (source_coverage). Решение —
декомпозиция по схеме в.1: план = ядро + планы подсервисов (куски
50–150 стр. = измеренный режим) + сводный порядок; линейность
гарантируется архитектурой (Корпкарты ~700 стр. ≈ 5–7 кусков ≈ 40 мин,
тяжеловес 1400 ≈ 15 кусков). Контекст: плану нужны титул+тег+дерево
(~100 ток./стр.), содержимое — точечно для неоднозначных; O(N) —
инструментам вне контекста. Правило: токены ≈ N×100 + 50К канона ×1.5;
с декомпозицией любой сервис влезает в 80К. Отбор LLM: эффективный
контекст МЕНЬШЕ номинального (потери в длинных перечнях до
переполнения) — тестировать перечнем ~700 строк со сверкой
инструментом; требования к промпту (классификация по титулам,
coverage гейтом) важнее требований к модели.

Вторая итерация дерева СБП (финальная версия от аналитика,
2026-08-23): ДВА ПРЕДСКАЗАНИЯ ПОДТВЕРЖДЕНЫ КОМАНДОЙ НЕЗАВИСИМО —

КОДИРУЕТСЯ ПРЕФИКСОМ СЛАГА подсервиса (srs/qr-c2b/, qr-b2b/, qr-out/,
onb-client/, pay-b2b/, core-ims/…) — сортировка собирает группу,

группы также в карте зонтика (закладки UI). Агенты выделены командой
в штатные подразделы «Агенты» (тип agent получает регулярное место);
пометки (???) в дереве — готовые open-questions профиля. Команда
реструктурирует Confluence ДО миграции — деревья выбора нужны ей как
чек-лист уже сейчас (аргумент руководителю о срочности в.1).
Зафиксированный трейдофф: сквозные ID удешевляют перегруппировку,
удорожают редкое отпочкование подсервиса в отдельный сервис — ставка
на «всегда одна команда»; если руководитель видит иначе, развилка
возвращается.

## Вопрос 5 (добавлен 2026-08-26). Граница контура исполнения внутри сервиса

Кейс КК (первый на ~180 сервисов): виджеты просмотра реквизитов
(PAN/CVV) и установки ПИН реализованы командой КК, но исполняются на
устройстве пользователя через каналы РОЗНИЦЫ (PCI DSS-контур);
данные через Экосистему не проходят, привилегии Экосистемы не
применяются. Структурное размещение их аналитики внутри SRS сервиса —
ложь о контуре обработки чувствительных данных (риск для
PCI-аудита/ИБ). Аналогия — встраиваемый платёжный виджет (iframe
процессинга, SAQ-A): у «мерчанта» описываются точка встраивания и
контракт, не внутренности.

РЕШЕНИЕ (паттерн тот же: декларация + правило выбора + сторож):
- разделить ДВА предмета: (а) точки встраивания и граница — в
  комплекте Экосистемы (EV-шаги «передача/возврат управления» в ЭФ;
  CALL-EXT-карточка «Виджеты Розницы» с честной строкой контура;
  базовые контракты эндпоинтов Розницы — docs-external-contracts);
  (б) спецификация виджетов — мини-комплект `widgets-rtl/` ВНЕ docs/
  (сосед в репо сервиса): README-паспорт границы + файл на виджет
  (методы-интерфейс для встраивающей страницы, поведение);
- Confluence до миграции: страница-паспорт границы (формулировки — с
  ИБ; артефакт для аудита) + перевесить ветки [КК_Виджет_ПИН]/
  [КК_Виджет_РЕКВ] под неё; теги НЕ переименовывать; строка в профиле
  источников «→ вне Экосистемы → widgets-rtl/» — конвейер не размажет,
  ручной перенос не нужен;
- НЕ использовать: general (прячет комплаенс-значимый факт), отдельный
  «сервис» в каталоге (не микросервис Экосистемы), размещение в SRS
  (давит экосистемные конвенции, неприменимые вне контура).
Ответы аналитика: «Карты к выдаче» — обычный экосистемный виджет
(остаётся подсервисом); коллбеков виджет→Экосистема нет (OTP — уже в
Экосистеме); передача Рознице малореальна (каталог в репо, не
отдельный репозиторий; перенос каталога = готовность к передаче);
серверной части нет — только скрипты с методами.
МАТЕРИАЛИЗАЦИЯ (к реальной миграции КК): widgets-rtl/ в белый список
сторожа корня; белый список путей вне docs/ для сторожа ссылок
чистовика (аналог _HTTP_WHITELIST) — до него связь из CALL-EXT
текстовым путём. Разметку экспериментального плана КК в песочнице
(cc-pin-widget/cc-requisites-widget как «зависимые подсервисы»)
при реальной миграции заменить на «вне Экосистемы».

Уточнение (2026-08-26, обмен токена): виджеты самостоятельно обменивают
токен Экосистемы на токен Розницы через выделенный эндпоинт Розницы
(вне RFC 8693; общий метод обоих виджетов). Следствия: (1) паспорт
границы получает ОБЯЗАТЕЛЬНЫЙ пункт — единственная точка пересечения
границы артефактом Экосистемы (токеном), формулировка для ИБ/аудита;
(2) в мини-комплекте третий файл wdg-common-token-exchange.md —
библиотечная процедура по дереву в.2 (несколько потребителей), дерево
сработало и вне контура Экосистемы без поправок; (3) контракты ПЯТИ
эндпоинтов Розницы в docs-external-contracts/rtl/: обмен токена,
получение PAN, получение CVV, ввод ПИН, отправка ПИН; (4) Confluence: страницу метода перевесить под паспорт
границы сестрой веток виджетов, тег не менять (разметка по ветви).
