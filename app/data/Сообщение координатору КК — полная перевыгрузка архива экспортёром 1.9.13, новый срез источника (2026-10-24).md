# Координатору комплекта КК: полная перевыгрузка архива экспортёром 1.9.13 — событие «выгрузка», новый срез источника

Дата: 2026-10-24. От владельца канона. Продолжение сообщения 23.10 «дельта TEAMTB-3633 по 8 страницам
изменилась»: там был перевыгружен только один заход, здесь — весь архив. Решения 22–23.10 (ISS-03-R2
остановить и пересобрать, дельта-заходы режима изменения) остаются, меняется срез источника.

## 1. Что случилось

После 23.10 экспортёр починен ещё в шести версиях (1.9.8 → 1.9.13). Главное для КК:

- **строки таблиц за первой секцией `<tbody>` терялись с самой первой выгрузки** — архив сентября
  был неполон, и не только у КК; вложенный список без `<li>` терялся так же (1.9.11);
- пункты списков в ячейках вложенных таблиц не получали цветных маркеров — это «второй дефект» из
  п. 4 сообщения 23.10, починен (1.9.8);
- частичное перекрытие цвета чёрным и чёрный текст внутри цветных элементов уходили во вставку, то есть
  выпадали из ПРОМ-среза (1.9.9, 1.9.11);
- добавлен сторож «ПРОМ не потерян»: текст reject-all сверяется с чёрным текстом источника на каждой
  странице (1.9.10, без ложных сигналов с 1.9.13).

24.10 весь архив КК выгружен заново версией 1.9.13 со сторожем. В репозиторий перенесены только
страницы, которые отличаются от архива (утилита run-pick, всё или ничего, ошибок 0).

## 3. Что делать команде

1. ISS-03-R2: по журналу вы дошли до P12 (r10) на срезе 717b11f. Новый срез источника — **0e32b01**;
   дельта по страницам захода с 717b11f: главная ЭФ создания/редактирования и «Подтверждение» —
   «изменён текст» (SCR-CL-19, SCR-CL-20), «в режиме просмотра» — «дополнен текст» (SCR-CL-22),
   «Документы и вложения», «Ввод адреса», «Согласие №2» — только разметка (SCR-CL-23, ENT-013, SCR-CL-21).
   Переключать ли P12 на новый срез или закрыть на 717b11f и дать дельта-заход — решение координатора;
   в сдаче строка «Срез источника» должна называть фактический срез.
2. Дельта-заходы режима изменения — по тому же срезу; карточки из списка «только дополнен» — дозаход
   по полноте без привязки к задаче.
3. Опись: 12 новых страниц добавить (в приложении помечены «нет в описи»): «Статус выпуска карты»,
   «Карты клиентов», «Первичное наполнение сущности Карты клиентов», «Список статусов и состояний
   карт в АБС Ф1», «Система: Функция сохранения информации по карте», «АБС Ф1_ОТСГДС_MQ_Синхронизация
   данных по карте», «Клиент: Функция получения организаций», «ЭФ Клиента: страница Установка
   лимитов», две «Система: Функция…» [КК_ЛК], «РКО Ф1_Получение актуальных данных по картам», «[РКО Ф1]
   DBLINK_Представление актуальные Корп. карты Клиента».
4. **12 страниц архива в новой выгрузке отсутствуют** (удалены в Confluence, перемещены из дерева или
   попали под правила исключения экспортёра) — в архиве они оставлены как были, до решения:
   - без карточек: четыре `Delete-[КК_B2B] Метод …` (расшифрование/шифрование/валидация PAN,
     принадлежность карты Банку), `DELETE() [КК_ЛК] Справочник кодов параметров лимитов`,
     `DELETE РКО Ф1 Корпоративные карты` (последние две — только в матрице трассируемости);
   - **с карточками**: `OLD — [КК_БК] Контроли заявки` (2166860778 → ENT-015, README), и пять
     «РКО Ф1. Представление …» (2184433420…424 → CALL-EXT-001…005: данные операций по карте, по счёту,
     корп. карты Клиента, счета клиента для корп. карт, список платёжных систем).
   Просьба: OQ владельцу дерева — где теперь источники CALL-EXT-001…005 (в дереве есть похожие
   «[РКО Ф1] DBLINK_Представление …» 2184433380/2184433381 и новая 2568657747 — другие page_id); по
   ответу либо перепривязка карточек, либо удаление страниц из архива отдельным событием «выгрузка».
5. Запись в журнал координации: событие «выгрузка» 887637c/0e32b01, причина — полная
   перевыгрузка после починки экспортёра.

## 4. Оговорки (важно)

**Перевыгруженные страницы несут текущее состояние Confluence, не снимок сентября.** Разметка шести
задач, которых в сентябре не было, при пересборке отклонена (тегов нет): TEAMTB-4218, 4292, 4518, 4520,
4521, 4586. Их неразмеченный текст, если он есть, остаётся в ПРОМ-срезе (случай «Процедура сохранения
заявки» / TEAMTB-4518 из сообщения 23.10 остаётся OQ автору; случай «в режиме просмотра» закрыт починкой
второго дефекта).

**Три известных класса сторожа «ПРОМ не потерян» не чинились** (решение владельца пилота, 24.10;
разобраны вручную, реальной потери действующего текста нет):

- «ЭКО_Получение числа карт на счете» (2184433973): цвет внутри инлайн-кода — в ПРОМ-срезе лишние
  23 слова (идентификаторы из примера запроса);
- ЭФ Клиента «Детальная информация по карте» (2166860490): цвет в тексте ссылки — лишние 2 слова
  («параметры», «исходящие»);
- «РКО Ф1_Получение списка карт клиента» (2184433983): модель ТЗ п. 4.5 — в ПРОМ-срезе нет 2 слов
  (`card_type`, `token_number`).

**«Детальная информация по карте» (2166860490) изменилась сильно** (в ПРОМ-срезе ушла 71 строка
старых полей — «Наименование продукта», «Блок лимитов по карте», `accountRestAmount` и т. п., добавлено
154: «Форма состоит из общей части и вкладок», «Редизайн вкладка тарифы»). Это не экспортёр: в HTML
страницы с контура этих полей нет, сторож подтверждает совпадение с источником. Страница в описи
«заморожено GBO-70412», её правят в Confluence без цвета — к карточкам не переносить до решения по
GBO-70412.

**Неразрешённые цвета (UNKNOWN-\*)** — 10 на 7 страницах, цвет не найден в «Истории изменений»; в
ПРОМ-срез такой текст не попадает (отклоняется как чужая вставка), в архиве он помечен плейсхолдером:
«Список карт» (×9), «Детальная информация по карте» (×20), «DBLINK_Представление актуальные Корп.
карты Клиента», «АБС Ф1_ОТСГДС_MQ_Синхронизация данных по карте» (×5, ячейка «Задача в Jira» без id),
«РКО Ф1_Получение актуальных данных по картам» (×2), «Клиент: Функция редактирования заявки на
выпуск карты…», «[КК_Виджет_РЕКВ] Клиент: Скрипт получения PAN» (×2, ячейка без id). Просьба: OQ
авторам — дописать задачу в историю или снять цвет.
