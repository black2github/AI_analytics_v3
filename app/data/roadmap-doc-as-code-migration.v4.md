Версия 4: две парные репозитории — **docs-\*** (чистый AI-aware комплект) и
**src-\*** (сырьё, архив, летопись Confluence). Смысл «двух линий без
git-merge» сохранён, но линии разведены по **разным remote**, а не по веткам
`master`/`history` внутри одного docs-репо. Путь комплекта:
`<service-id>/docs/` (не `output/…`). Именование: `docs-<id>`, `src-<id>`.

**Правила:**
[repo-topology](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/repo-topology.md) ·
[git-workflow](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md) ·
[conventions §1](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/standards/analytics/conventions.md) ·
[analyst-docs-guide](analyst-docs-guide.md).

**Создание нового docs-репозитория** — пошагово в
[analyst-docs-guide § Новый docs-репозиторий](analyst-docs-guide.md#новый-docs-репозиторий).

## Модель двух репозиториев (прочитать до этапов)

После миграции у сервиса — **два парных remote** с разной природой и разным
режимом состава:

| Репозиторий | Назначение | Ветка по умолчанию | Состав remote |
| - | - | - | - |
| **`docs-<id>`** | чистый AI-aware комплект; доступ аналитики + разработка + QA | `master` (+ короткие feature-ветки) | **ограниченный**: `<service-id>/docs/` + инфра (`README`, `gpb-manifest`, `CODEOWNERS`, `.gitignore`) |
| **`src-<id>`** | сырьё, архив, летопись; доступ **только аналитики**; без обязательных манифеста/CODEOWNERS | своя линия (часто `master`) | **без лимита**: `sources/raw/`, `sources/confluence/`, прочее |

- **Линия настоящего — `docs-*`, ветка `master`.** AI-aware аналитика в
  `<service-id>/docs/`, движется только вперёд. Здесь работают аналитики и
  AI-агенты; рабочие ветки — короткие `docs/…` от `master`.
- **Линия прошлого — `src-*`.** Реконструкция истории изменений требований в
  оригинальном составе (`sources/confluence/`): срез за срезом, задача за
  задачей — летопись того, как аналитика менялась в Confluence. Пополняется,
  пока сервис живёт двойным ведением; в прошлое не вносят правок — его
  дописывают. Ветки и теги летописи (`src/<JIRA-ID>`) живут **здесь**, не в
  docs-репо.

Ветки `history` **внутри docs-репо не требуется**: летопись и архив — зона
`src-*`.

Каталоги не пересекаются по remote:

| Каталог / путь | Владелец | Режим |
| - | - | - |
| `sources/raw/` | `src-*` (этап 3) | только чтение — навсегда |
| `sources/confluence/` | `src-*` (летопись) | меняется только в ветках/коммитах летописи |
| `<service-id>/docs/` | `docs-*`, линия `master` | меняется только в AI-aware ветках |

`sources/code/` — локальные клоны backend/frontend; в remote docs-репо **не**
входит. При необходимости клоны держат локально рядом с `src-*` / рабочей
областью — по соглашению команды.

**Мост между линиями — не git-merge, а преобразование**: скилл (drcs-ai-toolkit)
берёт срез задачи из летописи в `src-*` (тег) и оформляет её изменения в
AI-aware формате отдельной веткой от `master` в `docs-*`. Git-слияний между
репозиториями не существует.

### Политика веток (правила без исключений)

1. **Рабочие AI-aware ветки создаются только от `master` в `docs-*`.** От
   веток и тегов летописи в `src-*` рабочие docs-ветки не создаются — теги
   летописи открывают только для чтения и сравнения (просмотр среза, diff).
2. **`src-*` никогда не мержится в `docs-*` и наоборот** (разные remote —
   merge физически невозможен; запрет осознанный, не технический).
3. Ветка/коммит летописи в `src-*` изменяет только сырьё
   (`sources/confluence/` и согласованный архив); AI-aware ветка в `docs-*` —
   только `<service-id>/docs/` (+ инфра при необходимости). Нарушение —
   стоп-сигнал на ревью.
4. **Имена веток разводят линии**: летопись в `src-*` — `src/<JIRA-ID>`;
   AI-aware в `docs-*` — `docs/<topic>/<JIRA-ID>`
   ([git-workflow §5](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md#5-ветки)).
   У одной задачи Jira законно существуют обе ветки — в **разных** репо: это
   разные представления одной задачи, а не дубли.
5. Каждый срез летописи в `src-*` помечается тегом **`src/<JIRA-ID>`** (первый
   — `src/PROM`). Тег — точка чтения, не точка роста.
6. **Прослеживаемость**: MR ветки `docs/…/<JIRA-ID>` в `docs-*` ссылается на
   тег `src/<JIRA-ID>` в `src-*` и содержит «Откуда взяты факты:». В комплекте
   `docs-*` нет ссылок на Confluence / `sources/`.
7. В `docs-*` каталога `sources/` **нет** (и не требуется): актуальная
   летопись и архив — только в `src-*`.
8. Прямых коммитов в `master` docs-репо нет: MR → ревью → squash. Для
   летописи в `src-*` — предпочтителен MR; коммит прямо в основную ветку
   летописи — только явное ослабление ревью на пилоте команды.

Схема:

```text
docs-<id>  master  ──●───────────●──────────●──→   <service-id>/docs/
                      \     MR docs/…/GBO-2    MR docs/…/GBO-5
                       \            ↑ конверсия дельты (скилл), не merge
src-<id>               └──A──P──С1────С2────С3──→   sources/… (архив + летопись)
                                │      │
                             src/PROM  src/GBO-2  (теги срезов)

A — архив в sources/raw/;  P — ПРОМ-срез (точка отсчёта)
```

## Этап 1: Выгрузка аналитики из Confluence в markdown формат

**Цель**: выгрузка требований аналитики в markdown формат в привязке к задачам Jira

**Контур**: внутренний (VDI)

**Инструмент**: confluence-tree-exporter

> Видео о том, как установить и использовать:
> <https://disk.yandex.ru/i/4vZvS0dJiukLKw>.
> Рекомендуется до просмотра попробовать сразу по инструкции внутри пакета.

**DoD**:

- каталог выгруженных требований в виде markdown файлов и связанных файлов
  (например, картинок) на файловой системе;
- в случае привязки требований к задачам — отсутствие UNKNOWN-#XXXXXX отметок
  в отчете по цветовой привязке требований.

**Владелец результата:** сырьё для последующего размещения в **`src-*`**
(не в docs-репо).

## Этап 2: Перенос аналитики между контурами

**Цель**: получение файлов с аналитикой в markdown формате на внешнем контуре

**Контур**: внутренний (VDI) + внешний

**Инструмент**: onix_ft

**DoD:**

- каталог требований в markdown формате на файловой системе во внешнем контуре.

**Владелец результата:** по-прежнему сырьё → дальше в **`src-*`**.

## Этап 3: Сохранение аналитики в архив — рождение `src-*`

**Цель**: сохранение в парный **src-репозиторий** сервиса архива аналитики в
markdown+ формате (с разметкой привязки к задачам, если требуется) для
возможности восстановления в любое время (точка отсчёта).

**Контур**: внешний

**Инструмент**: Git, GitLab

**Шаги**:

1. Завести парные репо — `docs-<id>` и `src-<id>` (см.
   [новый docs](analyst-docs-guide.md#новый-docs-репозиторий) и
   [новый src](analyst-docs-guide.md#новый-src-репозиторий)). В `docs-*`:
   ограниченный состав (`<service-id>/docs/` + инфра), `gpb-manifest` +
   `CODEOWNERS`, доступ аналитики + разработка + QA. В `src-*`: состав без
   лимита (архив/летопись `sources/raw/`, `sources/confluence/`, …), **без**
   обязательных манифеста и CODEOWNERS, доступ **только аналитики**.
2. Влить в основную ветку **`src-*`** каталог архива: путь `sources/raw/`
   (MR).
3. Получить ПРОМ-срез точки отсчёта: скопировать `sources/raw/` в
   `sources/confluence/`, выполнить `run-critic.bat reject-all --path .`
   по каталогу `sources/confluence/`.
4. Влить ПРОМ-срез в `src-*` (MR), поставить тег `src/PROM`.

**DoD**:

- в `src-*` лежат `sources/raw/` (архив как есть) и `sources/confluence/`
  (ПРОМ-срез точки отсчёта, тег `src/PROM`);
- в `docs-*` на этом этапе ещё может не быть комплекта — он появится на
  этапе 5; `sources/` в docs-remote **не** кладётся.

> **Важно:** в `sources/raw/` должен оказаться каталог с требованиями в
> оригинальном markdown формате. Не сохранять в ZIP или ином формате —
> файлы нужны следующему этапу. `sources/raw/` с этого момента — только
> чтение, навсегда.

## Этап 4: Восстановление истории изменения аналитики — линия `src-*`

**Цель:** воссоздание в Git (`src-*`) истории изменения требований в их
оригинальном составе. Формальное начало Doc-as-Code фазы: любой срез доступен
по тегу в src-репо.

**Контур**: внешний

**Инструменты:** confluence-tree-exporter бандл, Git, GitLab

**Шаги**:

> Ветка на задачу или на эпик — как принято в команде: эпик рассматривается
> просто как набор задач. Все действия выполняются ТОЛЬКО над каталогом
> `sources/confluence/` в **`src-*`**; каталог `sources/raw/` — ТОЛЬКО ЧТЕНИЕ.
> Docs-репо на этом этапе не трогают.

1. Работать в **`src-<id>`** от коммита с тегом `src/PROM` (отдельная ветка
   `history` в docs-репо **не** создаётся).
2. Для очередной нереализованной задачи:
   1. скопировать архив из `sources/raw/` в `sources/confluence/` (да, заново);
   2. добавить Jira ID задачи к накопительному списку «реализованных»
      (GBO-ID1, GBO-ID2, … — список растёт с каждым шагом, это нормально);
   3. принять ВСЕ задачи списка: `run-critic.bat apply <ID> --path .` по
      каждому ID списка;
   4. **запомнить «хвост»** — список оставшихся задач
      (`run-critic.bat list --path .`);
   5. исключить «хвост» из текущего каталога:
      `run-critic.bat reject-all --path .`;
   6. зафиксировать срез в летописи — **по выбранному командой режиму**:
      - *режим с MR-ревью (предпочтительно)*: ветка `src/<JIRA-ID>` в `src-*`,
        коммит, **MR в основную ветку `src-*`** (не в `docs-*`!), мерж;
      - *режим без ревью (пилот)*: коммит прямо в основную ветку `src-*`
        (в коммит вливается только diff от предыдущего среза — это и даёт
        версионность);
   7. поставить тег `src/<JIRA-ID>` на коммит среза в `src-*`.
3. Если «хвост», полученный на шаге 2.4, не пуст — повторить шаг 2.
4. Пока идёт двойное ведение (задачи реализуются в Confluence-мире),
   новые выгрузки продолжают летопись теми же шагами — этап 4 не «закрыт»,
   а живёт параллельно этапу 5.

**DoD**:

- каждая нереализованная на ПРОМ задача представлена срезом в `src-*`
  с тегом `src/<JIRA-ID>` (и веткой `src/<JIRA-ID>` — в режиме MR-ревью);
- ни одна ветка/тег летописи не мержится и не копируется в `docs-*` как
  `sources/` (правило 2 и 7 политики).

## Этап 5: Миграция аналитики в AI-aware формат — линия `docs-*`

**Цель**: переход на полу/автоматизированное создание и сопровождение
аналитики, при котором AI-агент и человек-аналитик работают совместно.

**Контур**: внешний

**Инструменты**: Cursor / VS Code, Git, скиллы [drcs-ai-toolkit](https://gitlab.gboteam.ru/drcs/drcs-ai-toolkit)

**Шаги**:

1. Пилот по переходу части сервисов на AI-aware формат: конверсия ПРОМ-среза
   (тег `src/PROM` в **`src-*`**) в `<service-id>/docs/` веткой
   `docs/<topic>/<ID-пилота>` от `master` в **`docs-*`**, MR в `master`.
2. Посадка задач: по мере реализации очередной задачи — взять её дельту из
   летописи в `src-*` (diff тега `src/<JIRA-ID>` к предыдущему срезу),
   преобразовать скиллом в AI-aware и оформить веткой
   **`docs/<topic>/<JIRA-ID>`** от `master` в `docs-*`; в MR — ссылка на
   тег-источник в `src-*` и «Откуда взяты факты:».
   Темп и объём конверсии выбирает команда (дельта по задаче, заморозка
   хвоста, послойно по файлам); **политика веток одинакова** — варианты
   меняют только содержимое веток `docs/*` и момент старта конверсии.
3. При смене API / поведения для реализации — [парный MR + совместный
   merge](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md#долгоживущие-ветки--trunk-based-development-tbd)
   с backend/frontend.
4. Тиражирование принятых подходов, шаблонов и инструментов на все сервисы
   Экосистемы.
5. Переход на этап развития аналитики совместно с AI-агентами.

**DoD:**

- изменения каждой бизнесовой задачи, прошедшей посадку, оформлены в
  AI-aware формате веткой `docs/…/<JIRA-ID>` и влиты в `master` **`docs-*`**
  через MR;
- у каждой такой ветки/MR есть ссылка на тег-источник `src/<JIRA-ID>` в
  `src-*`;
- подтверждение команды сервиса о готовности сопровождения аналитики в
  выбранном формате;
- критерии завершения пилота ревью —
  [git-workflow §8](https://gitlab.gboteam.ru/ED/eco-techbook/-/blob/master/cookbook/analytics/git-workflow.md#8-ревью).

## Завершение миграции

Когда «хвост» исчерпан (`run-critic.bat list` пуст) и команда подтвердила
переход: пополнение летописи в `src-*` останавливается — теги `src/*` и
история `src-*` остаются как архив прослеживаемости (не удаляются);
`sources/raw/` и `sources/confluence/` **остаются в `src-*`**, в целевой
remote **`docs-*` не входят**.
Новые задачи идут только по целевому процессу: ветка `docs/<topic>/<JIRA-ID>`
от `master` в `docs-*` → commit → MR → согласование → squash merge.

## Почему это работает (для тех, кто хочет углубиться)

В v4 конфликт линий невозможен по построению:

- линии живут в разных remote (`docs-*` vs `src-*`) и не мержатся друг в
  друга (правило 2) — затереть чужое мержем нельзя;
- линии владеют разными каталогами и разными репо (правило 3) — пересечения
  путей в одном remote нет;
- рабочие AI-aware ветки растут только от `master` в `docs-*` (правило 1) —
  «уехать в прошлое» можно только сознательно и только для чтения срезов в
  `src-*`;
- двойники веток различимы именем и репо (`src/…` в `src-*` против `docs/…`
  в `docs-*`) — правило 4;
- связь линий сохранена не git-историей, а прослеживаемостью: тег среза в
  `src-*` ↔ MR конверсии в `docs-*` (правила 5–6);
- состав remote согласован с topology: в `docs-*` — ограниченный комплект
  `<service-id>/docs/`; сырьё и летопись — только в `src-*` (правило 7).
