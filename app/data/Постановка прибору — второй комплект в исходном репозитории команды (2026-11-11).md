# Постановка прибору — второй комплект в исходном репозитории команды (2026-11-11)

**Кому:** сессия «Правки прибора, акцепт и рутина».
**От кого:** сессия «Точки расширения эталона» (постановщик, приёмка). Ответ и сдача — этой же сессии.
**Мощность модели:** средняя. Правка затрагивает три утилиты и общий разбор профиля; дословных срезов нет.
**Порядок:** сначала оценка и план (раздел 7), после моего подтверждения — код. Коммит в analyzer — только
по слову владельца в вашем чате. Копия в канон — отдельной веткой после приёмки, коммит и MR — владелец.

## 1. Зачем

Решение владельца 11.11.2026 (реестр решений, Д-64): сервис, который развивают несколько команд, ведётся
доменным репозиторием документации с комплектом на команду-участника. Отдельный исходный репозиторий под
такой сервис не заводится: команда ведёт свой комплект этого сервиса в своём исходном репозитории, вторым
корнем рядом с `docs/`. Норма влита в техбук (`conventions` §3.2, пункт «Сервис нескольких команд», master
561d8a9).

Первый случай — КК. Адаптер `f1-integration` — отдельный сервис, в нём методы нескольких команд. Страницы
методов адаптера, которые ведёт команда КК, лежат в дереве Confluence КК. Их карточки должны жить во втором
комплекте:

```
src-business-cards/
  docs/                                  ← комплект КК, как сейчас (цель выкладки — docs-business-cards)
  docs-f1-integration/business-cards/    ← второй комплект (цель выкладки — docs-f1-integration, каталог business-cards/)
  sources/ inventory.md migration-plan.md open-questions.md …   ← одни на репозиторий
```

Второй корень повторяет раскладку целевого репозитория: `<имя целевого репозитория>/<каталог комплекта
команды>/`. Рамки домена (README с таблицей комплектов, концепция, глоссарий) в исходном репозитории нет —
она живёт только в целевом.

Сейчас прибор такой репозиторий не поддержит. Два места видны в коде, прогоном не проверены:

1. `selfcheck._kc_repo_root` — каталог `docs-f1-integration` в корне репозитория попадёт в «посторонние
   файлы» (✗).
2. `source_coverage` — покрытие считается по одной описи на один комплект: страницы зоны второго комплекта
   выйдут пробелами у `docs/`, а при прогоне второго комплекта пробелами выйдут все остальные страницы.

## 2. Что уже есть и к чему пристраиваться

- Несколько комплектов в одном исходном репозитории уже бывают: домен (`src-common-dictionary`,
  `output/<service-id>/`). Признак — `domain_context()` в `kitcheck/checks/_common.py`: README родителя
  комплекта несёт таблицу сервисов. В профиле источников зона записывается формой `сервис <service-id>`
  (`_SERVICE_ZONE_RE` в `source_profile.py`), сторож «страница → свой сервис» — там же,
  `check_subservice_mapping`.
- Наш случай этим механизмом не закрывается: у второго корня в исходном репозитории нет README с таблицей
  сервисов (рамки нет по решению), основной комплект `docs/` в домен не входит, а покрытие источников зон
  комплектов не знает вовсе.
- Корень комплекта уже передаётся параметром: `selfcheck --docs`, `transfer_gate --docs`,
  `source_coverage --output`.

Legacy-пути не трогать. Репозиторий без объявленного второго комплекта обязан давать отчёты до байта те же
(эталон `C:\tmp\tool-golden`, 0 отличий).

## 3. Объявление второго комплекта — один дом

Дом — профиль источников (README корня исходного репозитория), таблица «Разметка подсервисов». Новая форма
зоны:

```
| Матчер | Зона |
|---|---|
| 2359763493 | комплект docs-f1-integration/business-cards |
```

- `комплект <путь>` — путь корня комплекта от корня репозитория, прямые косые. Страница, попавшая под
  строку, принадлежит этому комплекту.
- Страница, не попавшая ни под одну строку `комплект …`, принадлежит основному комплекту (`docs/`).
  Умолчание в сторону сохранения: новая страница без строки остаётся в основном комплекте и видна там
  пробелом, пока её не разметят.
- Новый вид матчера — `page_id` (ячейка из одних цифр): ровно эта страница, без потомков. Нужен потому,
  что зона КК — не папка целиком: в папке «[КК] АБС Ф1» два обмена Kafka остаются в КК, а общего префикса
  титула у страниц адаптера нет. Действующие виды матчера (тег-префикс титула, имя верхней ветви) для
  строки `комплект …` тоже допустимы и работают как сейчас; правило «первая подошедшая строка выигрывает»
  сохраняется.
- Необязательная зона части через запятую, как у формы `сервис <id>` (`комплект <путь>, подсервис <слаг>`),
  — только если получается без усложнения разбора; иначе не делать и сказать в сдаче.

Если при оценке увидите, что чище переиспользовать форму `сервис <id>` или иной существующий признак, —
напишите это в плане до кода с доводами; решение за мной.

## 4. Что должно измениться

### 4.1. Общий разбор объявления

Одна функция (место — рядом с `_load_subservice_map`), которая по профилю отдаёт: перечень объявленных
корней комплектов и для страницы — её комплект (объявленный корень либо основной). Все три утилиты ниже
пользуются ею, второго разбора таблицы не заводить.

### 4.2. `selfcheck` — сторож корня репозитория

- Верхний каталог каждого объявленного корня комплекта в корне исходного репозитория — штатный.
- Объявленный корень, которого на диске нет, — ⚠ одной строкой (объявление без комплекта), вердикт не
  меняет: комплект может ещё не быть заведён.
- Каталог в корне, не объявленный в профиле, остаётся «посторонним», как сейчас (тест на несрабатывание:
  `docs-чужое/` без строки профиля даёт прежний ✗).
- Прогон по второму комплекту (`--docs docs-f1-integration/business-cards`): проверить, что именно
  определяется корнем проверки и не появляется ли ложных ✗; результат назвать в сдаче. Корень исходного
  репозитория в этом прогоне проверять не требуется — он проверен прогоном основного комплекта.

### 4.3. `selfcheck` — сторож «страница → свой комплект»

По образцу действующей проверки «страница → свой сервис» (`check_subservice_mapping`): карточка, чей
источник размечен в комплект X, лежит в комплекте Y — ✗ с обоими путями. Работает в обе стороны: при
прогоне `docs/` ловит карточку по странице второго комплекта, при прогоне второго комплекта — карточку по
странице основного.

Исключение, которое надо предусмотреть и покрыть тестом: карточка вызова в основном комплекте ссылается на
метод второго комплекта и вправе назвать страницу метода в «Доп. источниках». Проверяется главный источник
карточки (`page_id` шапки), а не любое упоминание страницы.

### 4.4. `source_coverage` — покрытие по комплекту

- Новый структурный класс непокрытия: страница принадлежит другому комплекту репозитория. Название —
  «другой комплект». Место в закрытом перечне `CLASS_ORDER` — на ваше усмотрение, обосновать.
- Страница класса «другой комплект» в пробелы измеряемого комплекта не входит. В отчёте — одна строка `i`
  со счётчиком и путём корня другого комплекта, без перечня страниц (при прогоне второго комплекта их
  сотни).
- Страница, размеченная в комплект X и не покрытая в X, — обычный пробел в прогоне X. Ни одна страница
  выгрузки не выпадает из обоих прогонов сразу: страница либо покрыта в своём комплекте, либо пробел там,
  либо отнесена к прежним структурным классам.
- Признак класса узкий: только строка профиля. Слова в описи («адаптер», «f1») признаком не считаются.
- Измеряемый комплект определяется сравнением `--output` с объявленными корнями от корня репозитория;
  не совпал ни с одним — основной.
- Опись, план миграции и журнал вопросов — одни на репозиторий. Сейчас `find_kit_file` ищет их в корне
  `--output` или в его родителе; для второго корня родитель — `docs-f1-integration/`, там их нет. Для
  объявленного комплекта искать также в корне репозитория. Проверьте то же для `selfcheck --inventory` и
  для поиска `open-questions.md` в гейте.

### 4.5. `transfer_gate` — второй комплект

- `--docs docs-f1-integration/business-cards` при `--src <корень>`: гейт собирает и проверяет второй
  комплект, прибор и покрытие идут с учётом пунктов 4.2–4.4. Проверить прогоном, что сборка во временный
  каталог, поиск источников, описи и журнала вопросов работают; расхождения назвать.
- Целевая раскладка второго комплекта — каталог команды внутри доменного репозитория, а не корень
  репозитория. В этой постановке `--out` для второго комплекта не дорабатывать: целевого репозитория
  адаптера ещё нет. Если гейт при `--out` положит комплект в корень цели — это известное ограничение,
  назвать его в сдаче отдельной строкой; молча не оставлять.
- Открытые вопросы и долги: журнал `open-questions.md` один на репозиторий. Как гейт второго комплекта
  отличит вопросы своего комплекта от чужих — оцените в плане и предложите вариант (например, вопрос
  относится к комплекту по карточке, на которую ссылается); без моего подтверждения не реализовывать.

## 5. Чего не делать

- Не менять поведение на репозиториях без строки `комплект …` — ни текстов отчёта, ни счётчиков.
- Не расширять молча действующий матчер «ветвь» на вложенные папки: у КК в профиле есть строка
  `[КК]-Виджеты`, её поведение меняться не должно.
- Не вводить рамку домена во второй корень исходного репозитория и не требовать её.
- Не трогать комплекты команд и клоны gboteam: замеры — на копиях или worktree в `C:\tmp`.
- Не заводить словарных признаков по словам источника.

## 6. Тесты и замер

- Тесты на срабатывание: штатный каталог второго корня; ⚠ на объявленный, но отсутствующий корень; ✗
  «страница → свой комплект» в обе стороны; класс «другой комплект» в обоих прогонах; пробел в своём
  комплекте остаётся пробелом; поиск описи из второго корня.
- Тесты на НЕсрабатывание: необъявленный каталог в корне — прежний ✗; репозиторий без строк `комплект …`
  — отчёты прежние; карточка вызова с «Доп. источником» из другого комплекта — без ✗; строка `комплект …`
  с матчером, не совпавшим ни с одной страницей, — ничего не снимает из пробелов.
- Эталон отчётов (`app/scripts/dev/golden_master.py`, `C:\tmp\tool-golden`) — 0 отличий.
- Полный набор тестов сверить с базлайном (на `bdc203ab` с несданным сторожем карточек вызова в рабочем
  дереве было 58 failed / 4 errors / 3189 passed); числа — из прогона.
- Живой замер на копии КК (`C:\doc-as-code\EAS\src-business-cards-exec`, HEAD 58d011aa, только чтение через
