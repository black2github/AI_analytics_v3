
### Что знать заранее

**ИНВАРИАНТ заморозки (уровень 2 сделан, уровень 1 за владельцем).** При лечении КАЖДОЙ выгрузки —
независимо от версии экспортёра — на замороженные поддеревья обязателен
`run-repair --flag-page <JIRA-ID>` (и отдельным запуском на корневую страницу
поддерева, она лежит рядом с каталогом). Причина: frontmatter-флаг
`unapproved_jira` — единственный канал, которым решение о заморозке доезжает до
миграции Doc-as-Code: `source_inventory` выносит по нему маркер `frozen:<ID>` в
опись, а промпт плана относит страницу в «вне SRS: заморожено до задачи». Пустая
страница БЕЗ флага для миграции неотличима от штатного пустого контейнера, то
есть потеря флага молчаливая. Экспортёр сегодня пишет флаг только для страниц из
списка `--unapproved-jira` (путь forced-unapproved); у замороженных страниц нет
ни истории изменений, ни маркеров — вывести задачу ему неоткуда.
С коммита `e697b507` экспортёр ставит флаг САМ там, где весь состав страницы
снимается откатом и принадлежит одной задаче (сторож против «задачу забыли в
списке»; на дереве [КК] дал 0 новых флагов и совпал с уже стоящими на 216
страницах). Замороженные страницы этим не закрываются — у них нет ни истории,
ни маркеров, поэтому `--flag-page` остаётся обязательным. Снимет его только
уровень 1: строка «Истории изменений» со ссылкой на задачу на самой странице
Confluence плюс эта задача в `--unapproved-jira` при выгрузке — тогда сработает
forced-путь и флаг придёт из экспортёра. Перечень замороженных задач свой у
каждого сервиса и каждой выгрузки: номера нигде не зашиты.

- `critic list` считает только маркеры и **не видит страничные флаги**. Задачи
  замороженных поддеревьев попадают в «хвост» лишь потому, что встречаются
  маркерами и есть в манифесте; флаг задачи, которой в дереве нет, был бы
  невидим — на это и поставлен сторож в `--flag-page`.
- Корневая страница поддерева лежит **рядом** с каталогом, а не внутри него:
  для неё нужен отдельный запуск починки.
- Выгрузка снята сборкой не выше 1.4.2 — до правила «первое упоминание в тексте
  ячейки» (1.5.1). Привязка маркеров к задачам в многозадачных строках истории
  там по старому правилу; пересъёмка это исправит.
- В выгрузке остались 6 страниц с заголовками `Delete…`/`DELETE…`: префикс попал
  в правила уже после экспорта, отвалятся при следующей выгрузке.
- Линт по вылеченному `raw/`: 22 ошибки (E5 ×7 — маркеры поперёк строк таблицы,
  E7 ×15 — CriticMarkup внутри сырого HTML) и 158 предупреждений W1. Не блокируют:
  `reject-all` даёт нулевой остаток, таблицы целы.
- Предсуществующие падения тестов: 26 в выборке
  `critic|repair|migrat|color|task_id|yaml|bundle|table|extractor|unapproved`
  (`test_color_map`, `test_table_lists`, `test_routes/*`). Сверять с чистым `HEAD`
  через `git worktree add --detach <tmp> HEAD`, скопировав в worktree `.env`.

## Ключевые решения (согласованы 2026-07-27)

- **Канонический вход миграции — HTTP rendered view** (`page_cache.fetch_page_data_via_http`,
  `viewpage.action`), НЕ Confluence API (`body.storage`): на внутреннем контуре API закрыт.
  Резолверы Jira — под rendered-формы, а не под форму-макрос из ТЗ 4.2.г №1.
- **jira-макрос в rendered view сломан**: «Невозможно найти сервер Jira для этого макроса»,
  ключа нет (макросы рассчитаны на внешний Jira, при переносе не менялись). В колонке
  «Задача в JIRA» ключ есть только как гиперссылка `browse/GBO-…` или plain-text.
- **UNKNOWN-\* ожидаем и нормой**: страницы без извлекаемого ключа дают сплошь `UNKNOWN-*` →
  в отчёт. Режим «только отчёт» первого прогона, не ошибка.
- **Обходной путь для восстановления ключей** (проверить на контуре): в режиме РЕДАКТИРОВАНИЯ
  страницы ключ Jira виден. Storage/editor-формат достаётся тем же браузероподобным
  `_confluence_http_get` через `/plugins/viewstorage/viewpagestorage.action?pageId=` или
  edit-эндпоинт. Источник HTML истории проектировался подключаемым (view ↔ storage).
- Карта `цвет→задача` строится только по НЕ-чёрным строкам истории (чёрная = задача на ПРОМ).

## ΔE near-black (ТЗ 4.3.1/4.3.2)

Цвет вне палитры редактора, перцептивно неотличимый от чёрного, → чёрный. `style_utils`:
`_srgb_hex_to_lab` (CIE Lab, D65, линеаризация гаммы), `delta_e_to_black` (CIE76 до
БЛИЖАЙШЕГО элемента `black_colors`), `is_near_black` (порог `NEAR_BLACK_DELTA_E`, default 3,
калибруется по ΔE-столбцу отчёта; default тугой — ловит только очень близкое типа `#0a0a0a`;
`#444444`≈7.6, `#202122` требуют повышения порога). Порядок ОБЯЗАТЕЛЕН (4.3.2): точный-чёрный
→ UI → задача-в-истории → ΔE → UNKNOWN; ΔE строго ПОСЛЕ истории (единый предикат
`content_extractor._is_edit_color`: цвет из color_map = правка даже near-black). near-black НЕ
добавляется в `black_colors` (набор ручной); legacy `is_black_color`/approved НЕ трогали.

## Признак 2 «примыкание» (ТЗ 4.5.2, срез 2 — 2026-07-31)

Зачёркнутый цветной фрагмент вплотную к вставке ДРУГОЙ задачи = черновик, на ПРОМ не был →
отбрасывается, в отчёт с `confidence: medium`. `content_extractor`: `_adjacent_foreign_insertion`
