# Инструкции агенту

Правила работы над этим репозиторием. Полный живой документ договорённостей —
[WORKING_AGREEMENTS.md](WORKING_AGREEMENTS.md); здесь только то, что обязательно
к исполнению. При расхождении приоритет у `WORKING_AGREEMENTS.md` — он ведётся вручную
и обновляется чаще.

## Гейты (не делать без явного запроса)

1. **Коммит — только по явному запросу.** Никаких авто-коммитов после выполненной задачи.
   Готов кусок → показать результат и спросить «коммитить?». Так же с push и любыми
   необратимыми действиями (`reset --hard`, `push --force`, удаление веток). Ветку под
   задачу выбирает пользователь.
2. **В коммит — только свои файлы:** `git add -- <перечисление>`, никогда `git add .` и
   `git add -A`. В репозитории много несвязанного untracked-мусора, он не должен уезжать
   в коммит попутно.
3. **Перед крупным или рискованным — сначала оценка и план, потом код.** Для больших
   модулей: оценка сложности → нарезка на срезы → подтверждение → реализация.
4. **Неоднозначность в ТЗ — спросить, а не угадать.** Развилки выносить явно, с
   рекомендацией и обоснованием, и ждать решения.

## Обязательные практики

- **Асимметрия ошибок.** Молчаливая потеря требования хуже лишнего маркера или шума в
  отчёте. Поведение по умолчанию всегда выбирается в сторону сохранения данных; там, где
  эвристика может отбросить содержательный фрагмент, нужен ограничитель и тест на
  НЕсрабатывание.
- **Каждая правка кода — с тестами**, после правки гоняется релевантный набор.
- **Регресс сверяется с базлайном.** Упавшие тесты проверять на чистом `HEAD`
  (`git worktree add --detach <tmp> HEAD`), чтобы отличить «я сломал» от предсуществующих
  фейлов. В репозитории есть предсуществующие падения — они не повод останавливаться, но
  и не повод молчать.
- **Встраиваться в существующую структуру, не плодить параллельную.** Новое поведение —
  режимом или флагом рядом с существующим, по умолчанию выключенным; legacy-пути не трогать.
- **Согласованные наборы данных расширять, а не переписывать** (например `black_colors`
  в `app/utils/style_utils.py`).
- **Сохранять байты:** переводы строк (CRLF), кодировку (везде явно `encoding="utf-8"`),
  отсутствие переформатирования. Неизменённый файл не перезаписывать (идемпотентность).
- **Докладывать как есть:** что проверено — прямо, что отложено — явно, компромиссы и
  расхождения не заминать. Числа брать из прогонов, а не по памяти.
- **Чекпоинты.** На заметных вехах фиксировать точку возврата (что готово / что осталось /
  как запускать / ключевые файлы) в статус-файл репозитория — например
  `CRITICMARKUP_STATUS.md`.

## Среда

- **Закрытый контур.** Новых зависимостей без offline-wheel не вводить. Confluence API
  закрыт → используется HTTP rendered view; Jira на миграции недоступна → плейсхолдеры
  `UNKNOWN-*` ожидаемы и нормальны.
- **Кроссплатформенность.** Разработка в Windows, CI в Linux: пути только через `pathlib`,
  кодировка везде явно.
- **Запуск тестов.** Локальный `venv` сломан (ссылается на несуществующий базовый
  интерпретатор), поэтому тесты гоняются системным Python с venv в `PYTHONPATH` и
  отключённым cov-гейтом:

  ```
  PYTHONPATH="$PWD;$PWD/.venv/Lib/site-packages" PYTHONIOENCODING=utf-8 \
    <системный-python> -m pytest tests/<...> -q -o addopts=""
  ```

  `PYTHONIOENCODING=utf-8` обязателен — иначе кириллица в выводе превращается в мозаику.
  Путь к интерпретатору зависит от машины (на одной из них — `/c/Python312/python.exe`).

## Стиль

По-русски, по делу: сначала вывод, потом детали; таблицы и списки для сравнений.
Комментарии и термины в коде — как в окружающем коде (он русскоязычный, с ссылками на
пункты ТЗ вида «ТЗ п. 4.5.2»).
