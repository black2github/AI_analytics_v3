# Правила совместной работы (агент ↔ аналитик)

Живой документ: договорённости о том, **как** мы ведём работу над кодом. Смотреть иногда и
дополнять. Формулировки — коротко: правило + зачем.

> Легенда: **[С]** — явно согласовано в ходе работы; **[П]** — сложившаяся практика, которую
> предлагаю закрепить; **?** — открытый вопрос на подумать.

## Git и коммиты

- **[С] Коммит — только по явному запросу.** Никаких авто-коммитов. После готового куска —
  показываю результат и спрашиваю «коммитить?».
- **[П] Коммичу только свои файлы.** В репозитории много несвязанного мусора (untracked) —
  добавляю в коммит точечно (`git add -- <файлы>`), не `git add .`.
- **[П] Сообщение коммита — по-русски, описательное**, с трейлером `Co-Authored-By`. Один
  коммит = один логический кусок (срез/фикс), а не «всё сразу».
- **[С] Не пушу и не делаю необратимого** без запроса. Ветку под задачу выбираешь ты.

## Планирование и подтверждение

- **[С] Перед крупным/рискованным — сначала оценка и план**, только потом код. Для больших
  модулей — «оценка сложности → нарезка на срезы → подтверждение → реализация».
- **[С] Ambiguity в ТЗ — задаю вопросы, не угадываю.** Развилки выношу явно, с рекомендацией и
  обоснованием; жду решения.
- **[П] Флагаю асимметрию ошибок.** Молчаливая потеря требования хуже, чем лишний маркер/шум —
  выбор поведения по умолчанию делаю в сторону сохранения данных.

## Нарезка и тесты

- **[С] Большую работу режу на срезы**, каждый — самостоятельный, с тестами и отдельным
  коммитом; между срезами ты в контуре.
- **[П] Каждая правка кода сопровождается тестами**; после правки гоняю релевантный набор.
- **[П] Регресс проверяю против базлайна.** Упавшие тесты сверяю с чистым HEAD (git checkout/
  worktree), чтобы отличить «я сломал» от предсуществующих фейлов; предсуществующие фиксирую в
  памяти, чтобы не перепроверять.
- **[П] Прогон тестов в этой среде:** venv сломан → системный Python + venv в `PYTHONPATH`,
  `PYTHONIOENCODING=utf-8`, cov-гейт отключаю (`-o addopts=""`). Детали — в памяти агента.

## Бережность к рабочему коду

- **[С] Встраиваюсь в существующую структуру, не пложу параллельную.** Новое поведение —
  режимом/флагом рядом с существующими (пример: `--tasks` в общем скрипте, а не отдельный
  инструмент).
- **[П] Новое поведение по умолчанию выключено** (напр. `critic_mode`), legacy-пути не трогаю;
  минимизирую поверхность изменений.
- **[С] Согласованные наборы данных не переписываю, а расширяю** (напр. `black_colors`);
  изменение поведения общего кода — только с флагом «безопасно только расширяет».
- **[П] Перед правкой продового файла — diff-first:** убеждаюсь, что меняю ровно намеченную
  дельту, а не задеваю чужую логику.
- **[С] Сохраняю байты, где это важно:** переводы строк (CRLF), кодировку, отсутствие
  переформатирования; идемпотентность (неизменённый файл не перезаписываю).

## Честность отчётов

- **[П] Докладываю как есть:** что сделано и проверено — прямо; что отложено — явно; расхождения
  и компромиссы (напр. оракул на HTML-таблицах) не заминаю.
- **[П] Числа и факты — из прогонов**, не по памяти; при разборе отчётов сверяю с реальными
  данными (открываю дампы страниц, а не додумываю).

## Память и точки возврата

- **[С] На чекпоинтах сохраняю статус в память** (что готово / что осталось / как запускать /
  ключевые файлы), чтобы вернуться в любой момент. По запросу выгружаю в файл репозитория
  (`CRITICMARKUP_STATUS.md`).
- **[П] Отложенное и известные ограничения веду явным списком** — не теряются.

## Офлайн / закрытый контур

- **[С] Новых зависимостей без колёс не ввожу.** Если библиотека нужна — добавляю wheel для
  offline-установки; проверяю целостность импорт-графа в среде бандла.
- **[П] Учитываю ограничения контура** (API закрыт → HTTP-путь; самоподписанные сертификаты;
  Jira недоступна → UNKNOWN ожидаем).

## Стиль общения

- **[С] По-русски, по делу**, без воды; таблицы/списки для сравнения; сначала вывод, потом
  детали. Термины и стиль кода — как в окружающем коде.

- **? Порог «крупности» для план-режима.** Сейчас по ощущению; стоит ли задать явный критерий
  (напр. >2 файлов или >~50 строк → сначала план)?
- **? Где живут такие правила.** Часть можно перенести в `CLAUDE.md` / память как **feedback**,
  тогда они применяются автоматически, а не «на память». Решить, что делать обязательным.
- **? Политика веток.** Фиксировать ли «фича-ветка под задачу, PR в main», или оставляешь за
  собой.
- **? Границы автономности.** Что можно делать без спроса (тесты, smoke, разведка) vs что всегда
  с подтверждением (правки продовых скриптов, миграции). Сейчас разделяю по чутью — можно
  формализовать.
- **? Формат отчётов о прогоне** (какие метрики всегда показывать: позиции на разбор, регресс,
  дельта к прошлому прогону).
